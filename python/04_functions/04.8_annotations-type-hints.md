# 04.8 Annotations and Type Hints — An Introduction

## Learning Objectives

- Distinguish **annotations** (syntactic slot) from **type hints** (semantic usage) and from runtime enforcement (which Python does **not** do).
- Annotate parameters, return values, and variables with built-in and `typing` / modern generic syntax, including `Optional`, `Union`, `|`, `List`/`Dict`/`Tuple`, and `Any`.
- Understand `TYPE_CHECKING`, stringified annotations, and tools like `mypy` / `pyright` / `basedpyright`.
- Avoid annotation pitfalls: circular imports, runtime evaluation, over-annotation.

---

## 1. What Annotations Are — And Are Not

### 1.1 Annotations are syntax, not semantics

Since Python 3.0 (PEP 3107) every parameter and return slot may carry an **annotation** — any expression placed after `:` or `->`:

```python
def add(a: int, b: int) -> int:
    return a + b

class Box:
    value: int          # variable annotation (PEP 526, Python 3.6+)
    count: int = 0      # annotated assignment
```

An annotation can be **any expression**:

```python
def weird(x: "totally not a type", y: 42, z: print) -> None:
    pass

print(weird.__annotations__)
# {'x': 'totally not a type', 'y': 42, 'z': <built-in function print>, 'return': None}
```

`__annotations__` stores the unevaluated or evaluated annotation objects; Python itself **never** checks them. `add(2.5, "hello")` still runs and returns `"hellohellohello"?` plus float? Depends on runtime — no annotation-driven error.

So: **Annotations are data attached to objects, not constraints enforced by the interpreter.** This is the single most important misunderstanding to clear up.

### 1.2 Type hints are a *convention* built on annotations

Since PEP 483/484 (Python 3.5+) the community agreed: by convention, annotations should hold **type hints** — descriptions of expected value types that **static** analyzers (`mypy`, `pyright`/`basedpyright`, `pytype`, `pyre`) verify **without running** the code, and that IDEs use for autocompletion.

```python
# Type hint by convention — a static checker verifies this, the interpreter ignores it:
def add(a: int, b: int) -> int:
    return a + b

add(1, 2)          # mypy: OK
add("a", "b")      # mypy error: Argument 1 has incompatible type "str"; expected "int"
                   # python runtime: still runs and returns "ab" — no runtime error
```

Table:

| Layer | Who checks | When | Fails if ignored |
|---|---|---|---|
| Annotation syntax | Python parser | Import/definition time | SyntaxError only if malformed |
| Runtime call | Python interpreter | At call | Only if code inside breaks — not annotation |
| Static type hint | `mypy` / `pyright` etc. | Before running, via separate tool | Reported error, but runtime still succeeds |

## 2. Basic Parameter and Return Annotations

### 2.1 Syntax

```python
# Parameter:  name: Type
# Return:     def f(...) -> Type:
# Variable:   name: Type = value  OR  name: Type

def greet(name: str, excited: bool = False) -> str:
    suffix = "!" if excited else "."
    return f"Hello, {name}{suffix}"

print(greet("Ada"))               # Hello, Ada.
print(greet("Ada", excited=True)) # Hello, Ada!

# Introspection:
print(greet.__annotations__)                  # {'name': <str>, 'excited': <bool>, 'return': <str>}
import inspect
print(inspect.signature(greet))               # (name: str, excited: bool = False) -> str
for param in inspect.signature(greet).parameters.values():
    print(param.name, param.annotation)
```

No behavior changes:

```python
def add(a: int, b: int) -> int:
    print(f"adding {a!r} and {b!r}")
    return a + b

print(add("a", "b"))  # adding 'a' and 'b' -> 'ab' — hints ignored at runtime
```

### 2.2 Annotating everything vs nothing

Type hints are **gradual**: you may annotate none, some, or all of a codebase. Unannotated params have implicit annotation `inspect.Parameter.empty` and checker treats them as `Any` (dynamic):

```python
def partly(a: int, b):  # b is Any to type checkers
    return a + b

# Versus annotated both:
def fully(a: int, b: int) -> int:
    return a + b
```

You can also annotate locally:

```python
x: int = 5            # variable annotation
y: list[int] = []     # since Python 3.9, list[int] works at runtime too
z: str                # no value — stored in __annotations__ but NameError if read before assignment
print(__annotations__)
```

## 3. The `typing` Module and Modern Generic Syntax

### 3.1 Evolution: why two ways exist

| Era | Generic collections syntax | Notes |
|---|---|---|
| Before Python 3.9 | `from typing import List, Dict, Tuple, Set` and `List[int]`, `Dict[str, int]` | `list[int]` was **not** valid at runtime (type subscription error) |
| Python 3.9+ (PEP 585) | **Built-in** `list[int]`, `dict[str, int]`, `tuple[int, ...]`, `set[str]`, `type[int]` work at runtime | Preferred for new code in 3.9+ |
| Python 3.10+ (PEP 604) | `X | Y` for unions instead of `Union[X, Y]` | Preferred in 3.10+ |
| Python 3.12+ (PEP 695) | `def f[T](x: T) -> T:` inline type params; `type Alias = X | Y` | Latest evolution |

Support matrix — choose based on your minimum Python:

```python
# Modern (Python 3.10+):
def modern(items: list[int], mapping: dict[str, float]) -> dict[str, list[int]]:
    ...

# Compatible backport (any Python, including older):
from typing import List, Dict
def legacy(items: List[int], mapping: Dict[str, float]) -> Dict[str, List[int]]:
    ...

# Union:
# Modern 3.10+:  def f(x: int | str) -> int | None:
# Legacy:       from typing import Union, Optional
#               def f(x: Union[int, str]) -> Optional[int]:
```

**Recommendation:** New courses targeting Python 3.10+ should teach `list[int]` and `X | Y` as default, and show `typing.List`/`Union` as legacy for readers who encounter older codebases.

### 3.2 Core types — progression simple → advanced

```python
# --- Builtins ---
def takes_basic(a: int, b: float, c: str, d: bool, e: bytes) -> None:
    pass

# --- Collections (3.9+ built-in generic) ---
def takes_collections(
    items: list[int],                    # list with int elements
    mapping: dict[str, int],             # dict from str to int
    uniq: set[str],                      # set of str
    point: tuple[int, int],              # exactly two ints (fixed length)
    varying: tuple[int, ...],            # tuple of any number of ints
    frozen: frozenset[str],              # frozen set variant
) -> None:
    pass

# Legacy equivalent (pre-3.9):
# from typing import List, Dict, Set, Tuple, FrozenSet
# items: List[int]; mapping: Dict[str, int]; varying: Tuple[int, ...]

# --- None and void ---
def void_func() -> None:                 # returns None (implicit or explicit)
    print("hi")

def maybe_str(x: int) -> str | None:     # may return str or None
    return str(x) if x % 2 == 0 else None

# --- Optional ---
# Optional[X] is sugar for X | None (legacy). Modern prefers X | None.
from typing import Optional

def optional_old(x: Optional[int]) -> None:
    # x may be int or None
    pass

def optional_new(x: int | None) -> None:  # identical, modern syntax
    pass

# --- Union ---
# Union[X, Y, Z] is legacy for X | Y | Z
from typing import Union

def union_old(x: Union[int, str]) -> None:
    pass

def union_new(x: int | str) -> None:     # identical
    pass

# Multiple unions — often an Enum or Literal is better:
from typing import Literal

def parse_mode(mode: Literal["r", "w", "a"]) -> str:  # enumerates string values
    return mode.upper()

# parse_mode("r")  # OK
# parse_mode("x")  # checker error

# --- Any ---
from typing import Any

def accept_any(x: Any) -> Any:
    """Any is escape hatch — checker allows anything, but you lose checking."""
    return x

# Use sparingly; prefer precise type or object.

# --- Callable ---
from typing import Callable

def apply(func: Callable[[int], str], value: int) -> str:
    return func(value)

print(apply(str, 42))  # '42' — Callable[[int], str]

# Callable with var args: Callable[..., int] (any args -> int)

# --- Type variables / Generics preview ---
from typing import TypeVar

T = TypeVar("T")     # before PEP 695 TypeParamSyntax
def first(items: list[T]) -> T | None:
    return items[0] if items else None

print(first([1, 2, 3]))    # 1 — inferred T=int
print(first(["a", "b"]))   # a — inferred T=str
```

### 3.3 `list[int]` vs `List[int]` — runtime gotcha

Before Python 3.9:

```python
# Python 3.8:
# items: list[int]  # TypeError: 'type' object is not subscriptable at runtime
#                   # Must: from typing import List; items: List[int]
#                   # Or:  from __future__ import annotations  (PEP 563) — makes annotations strings
```

Since 3.9 it works at runtime thanks to `GenericAlias`; checker and runtime agree. For cross-version libraries that must parse at runtime (Pydantic, FastAPI, dataclasses runtime), use `from __future__ import annotations` or quoted annotations.

### 3.4 `tuple` special cases

```python
point: tuple[int, int]       # exactly 2 elements: int, int
point3: tuple[int, int, int] # exactly 3
ints: tuple[int, ...]        # any length, all ints (variable length)
mixed: tuple[int, str]       # exactly 2: int then str
empty: tuple[()]             # exactly empty tuple (rare)

# tuple[int, ...] appears where List[int] untagged length variable size.
# typing.Tuple compatibility: same forms.
```

### 3.5 `dict` vs `Mapping` vs `TypedDict`

```python
from typing import Mapping, TypedDict

# Concrete mutable dict:
def takes_dict(d: dict[str, int]) -> None: ...

# Abstract read-only mapping — accepts dict and other Mapping impls:
def takes_mapping(m: Mapping[str, int]) -> None: ...

# Structured dict with fixed string keys and specific value types:
class Movie(TypedDict):
    title: str
    year: int

def use_movie(m: Movie) -> None:
    print(m["title"])  # checker knows key 'title' exists and is str

use_movie({"title": "Dune", "year": 2021})  # OK
# use_movie({"title": "Dune"})              # checker error (missing year if TypedDict total=True)
```

## 4. No Runtime Enforcement — What Actually Checks Hints

### 4.1 Interpreter ignores hints (again, because this needs repetition)

```python
def add(a: int, b: int) -> int:
    return a + b

print(add("a", "b"))     # 'ab' — no TypeError from Python itself
print(add(None, None))   # TypeError only because None + None fails inside the body (unsupported operand), not annotation

x: int = "oops"
print(x)                 # "oops" — assignment succeeded

# Only libraries that opt-in (see below) do anything:
```

If you need runtime checks, use a library that voluntarily enforces — it is not automatic:

```python
# Example: pydantic validates at call time because it chooses to inspect annotations:
from pydantic import validate_call  # pydantic v2

@validate_call
def add_strict(a: int, b: int) -> int:
    return a + b

print(add_strict(2, 3))   # 5
# add_strict("a", "b")    # pydantic.ValidationError — opt-in enforcement

# Example: typeguard
# from typeguard import typechecked
# @typechecked
# def add_checked(a: int, b: int) -> int:
#     return a + b
# add_checked("a","b")  # typeguard.TypeCheckError
```

> **Lesson:** Treat hints as **machine-checked documentation**, not runtime contracts. Tests must still exercise real inputs.

### 4.2 Static checkers: `mypy`, `pyright`/`basedpyright`, `pytype`

Run **outside** the interpreter, before or alongside tests:

```bash
# mypy (original checker, most strict by default with --strict)
pip install mypy
mypy your_project/

# pyright / basedpyright (faster, used inside VS Code Pylance)
pip install basedpyright
basedpyright your_project/

# Example error:
# demo.py:5: error: Argument 1 to "add" has incompatible type "str"; expected "int"  [arg-type]
```

Each checker has its own config (`mypy.ini` / `pyproject.toml [tool.mypy]`, `pyrightconfig.json` / `[tool.pyright]`). Typical progression for a project:

```toml
[tool.mypy]
python_version = "3.10"
warn_return_any = true
warn_unused_configs = true
ignore_missing_imports = true
# then enable stricter gradually: strict = true
```

### 4.3 `mypy` vs `pyright` differences (brief)

| Checker | Invocation | Strengths | Notes |
|---|---|---|---|
| `mypy` | CLI / daemon `dmypy` | Reference impl for PEP 484, most docs/examples | Slightly slower, most ecosystem `stub` files |
| `pyright` / `basedpyright` | CLI + VS Code Pylance | Faster, great for large codebases; stricter inference in some generics | Used by default in VS Code |

They **mostly agree**, but edge-case inference diverges (e.g., overloaded returns, `TypeGuard`). Pick one and configure it; don't run both with competing strictnesses unless you like noise.

## 5. `TYPE_CHECKING`, Circular Imports, and String Annotations

### 5.1 Problem: imports needed for hints but cause circular imports at runtime

```python
# models.py
import services  # at runtime

def process(user: services.User) -> None:  # needs service.User only for hint
    ...
```

If `services.py` also imports `models.py` (common), a cycle forms. Solution: **put hint-only imports under `if TYPE_CHECKING`** so they exist for checkers but **not** at runtime, and **quote** or **future-annotate** the usage:

```python
# models.py
from __future__ import annotations  # makes all annotations lazy strings; optional but helpful
from typing import TYPE_CHECKING

if TYPE_CHECKING:            # False at runtime; True for mypy/pyright
    import services          # never imported at runtime — checker still sees it
    from services import User

def process(user: User) -> None:          # with future annotations, ok as-is
    # or quoted: def process(user: "services.User") -> None:
    print(user)

print(process.__annotations__)
# {'user': 'User'}  — string because of from __future__ import annotations (PEP 563) or quotes

# Equivalently, without future import, quote the hint:
from typing import TYPE_CHECKING as _TC
if _TC:
    import services

def process2(user: "services.User") -> None:  # quoted string — not evaluated at runtime
    ...
```

Why `if TYPE_CHECKING:` works:
- At runtime `typing.TYPE_CHECKING` is `False`, so the block is skipped — no import, no cycle.
- Static checkers pretend it is `True` and analyze inside.

Without `TYPE_CHECKING`, you would either pay runtime import cost and risk cycles, or fail to type-check.

### 5.2 `from __future__ import annotations` and quoted hints

PEP 563 / Python 3.14 PEP 649 evolution is in flux — current pragmatic guidance (Python 3.10–3.12, moving toward 3.14):

```python
from __future__ import annotations          # defer evaluation of all annotations in this file

def f(x: int | str) -> list[int]:           # stored as strings; never evaluates list[int] at import
    return []

print(f.__annotations__)                    # {'x': 'int | str', 'return': 'list[int]'} — strings
import inspect
print(inspect.get_annotations(f))           # evaluates on demand (Python 3.14+ inspect.get_annotations)

# Without future annotations, some hints may fail at runtime:
# def g(x: list[int]) -> None: ...  # In Python 3.8, list[int] raises TypeError at definition
# Fix either:  from __future__ import annotations,  or  x: "list[int]", or  from typing import List; List[int]
```

Recommendation for a **new project targeting 3.10+**: place `from __future__ import annotations` at the top of files that have complex forward references, and use modern `X | Y` syntax. For libraries supporting older Pythons, use quoted hints + `if TYPE_CHECKING`.

### 5.3 `typing.cast` and `typing.assert_type` (suppressing / asserting checker)

```python
from typing import cast, assert_type

value = 42
casted = cast(str, value)          # tells checker "treat value as str here"; no runtime conversion
print(casted)                      # 42 — runtime unchanged, just a checker directive

# assert_type (Python 3.11+, typing 3.10+) — checks checker agrees at that line:
assert_type(value, int)            # checker will error if value not int
```

`cast` is a **lie you promise is safe** — use rarely, when you know more than the checker (e.g., after an `isinstance` that the checker could not propagate). Prefer `isinstance` guards or `TypeGuard` (below) instead.

## 6. Gradual Typing in Real Code — How Much to Annotate

### 6.1 Annotated realistic example

```python
from __future__ import annotations

from collections.abc import Sequence, Mapping, Callable
from typing import Any
# Or: from typing import TYPE_CHECKING; if TYPE_CHECKING: import heavy_module

def summarize(
    items: Sequence[int],
    *,
    name: str = "items",
    verbose: bool = False,
) -> dict[str, int]:
    """Return summary {'count': int, 'total': int, 'max': int}."""
    if not items:
        return {"count": 0, "total": 0, "max": 0}
    if verbose:
        print(f"{name}: {list(items)}")
    return {"count": len(items), "total": sum(items), "max": max(items)}

print(summarize([1, 2, 3], name="nums"))  # {'count': 3, 'total': 6, 'max': 3}
```

Why `Sequence[int]` not `list[int]`? Accepts `list`, `tuple`, `range` — more general, follows "be liberal in what you accept." `Mapping[str, T]` vs `dict[str, T]` analogous.

```python
# Choosing container hint:
# Param accepts any iterable once, iterate only:  Iterable[int] (collections.abc)
# Param accepts any indexed sequence:            Sequence[int]
# Param needs .get/.keys:                        Mapping[str, int]
# Return builds a real dict you own:             dict[str, int]

# Small realistic service function:

def fetch_user(
    user_id: int,
    /,
    timeout: float = 10.0,
    *,
    cache: dict[int, dict[str, Any]] | None = None,
) -> dict[str, Any] | None:
    """Fetch by ID — placeholder demo. Cache injectable for tests."""
    if cache is not None and user_id in cache:
        return cache[user_id]
    # ... real I/O
    return {"id": user_id, "name": "Ada"}

print(fetch_user(42, cache={42: {"id": 42, "name": "Ada"}}))
```

### 6.2 Where not to annotate

- **Trivial locals** inferred from assignment: `x = 5` needs no `x: int = 5`.
- **Private throwaway lambdas**: `key=lambda u: u["age"]` — inferred.
- **Duck-typed helpers** that truly accept anything: use `Any` or leave unannotated rather than force a spurious `object`.

### 6.3 Using `Any` vs `object` vs omitted

| Hint | Meaning to checker |
|---|---|
| `x: Any` | Compatible with everything — no errors, but also loses checking |
| `x: object` | Most general *checked* type — can assign any value, but operations need narrowing (`isinstance(x, str)`) |
| `x` unannotated | **Implicit** `Any` (ingradual code). With `--strict`, mypy flags missing annotations |

Prefer `object` over `Any` when you truly want "anything but must be interrogated before use."

### 6.4 `TypedDict`, `NamedTuple`, `dataclass` as typed structures

```python
from typing import TypedDict, NamedTuple
from dataclasses import dataclass

class UserDict(TypedDict):
    name: str
    age: int

def greet_dict(u: UserDict) -> str:
    return f"{u['name']} {u['age']}"

class UserTuple(NamedTuple):
    name: str
    age: int

def greet_tuple(u: UserTuple) -> str:
    return f"{u.name} {u.age}"

@dataclass
class UserClass:
    name: str
    age: int

def greet_obj(u: UserClass) -> str:
    return f"{u.name} {u.age}"
```

Choose based on whether your data is dict-like (JSON round-trip), tuple-like (positional + named), or object-like (methods, validation).

## 7. Common Annotation Pitfalls

### 7.1 Mutable default with precise type — still need None sentinel

```python
# Checker happy, but still shares list at runtime — same pitfall as §04.2!
def bad(items: list[int] = []):   # mypy OK; runtime shares one [] across calls
    items.append(1)
    return items

# Correct: None sentinel typed as | None
def good(items: list[int] | None = None) -> list[int]:
    if items is None:
        items = []
    items.append(1)
    return items

print(bad())  # [1]
print(bad())  # [1, 1] — leaked
print(good()); print(good())  # [1] [1] — independent
```

### 7.2 Confusing `list[int]` with `list`

```python
# list        — legacy hint meaning "any list elements" (equivalent to list[Any])
# list[int]   — list whose elements are known to be int
# list[Any]   — explicit Any — similar but explicit

def takes_any_list(x: list) -> None:  # mypy == list[Any]
    pass
```

### 7.3 `Optional` misread — it is not an optional parameter

`Optional[int]` (= `int | None`) means "value may be `int` or `None`" — it **does not** mean "parameter may be omitted." Only a **default** makes a parameter optional:

```python
def a(x: int | None) -> None: ...        # x required, but may be None (still caller must pass)
def b(x: int | None = None) -> None: ... # x optional AND may be None
def c(x: int = 0) -> None: ...           # x optional, never None

# a(42) and a(None) required;  a() is error (missing arg)
# b() is OK (defaults to None)
```

### 7.4 Over-annotating with `Union` instead of `Literal` or `TypedDict`

```python
# Over-broad:
def handle(mode: str) -> None: ...  # checker knows nothing about valid strings

# Precise:
from typing import Literal
def handle2(mode: Literal["r", "w", "a"]) -> None: ...

# Similarly for heterogeneous dict return — prefer data class:
# def bad() -> dict[str, Any]:  # little checking
# Better:
@dataclass
class Result:
    ok: bool
    value: int | None
```

## 8. Advanced Peek — `TypeGuard`, `Protocol`, Generics (awareness only)

For reading others' code you will meet these; mastery belongs to a dedicated typing course:

```python
# TypeGuard — custom narrowing (PEP 647)
from typing import TypeGuard

def is_str_list(value: list[object]) -> TypeGuard[list[str]]:
    return all(isinstance(x, str) for x in value)

# Checker then knows:
items: list[object] = ["a", "b"]
if is_str_list(items):
    reveal = items[0].upper()  # OK — narrowed to list[str]

# Protocol — structural typing ("duck typing" as a type, PEP 544)
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> None: ...

def render(x: Drawable) -> None:
    x.draw()  # any object with .draw() qualifies — no inheritance needed

# PEP 695 modern generic syntax (Python 3.12+):
# def first[T](items: list[T]) -> T | None:
#     return items[0] if items else None
```

## 10. Quick Reference

| Concept | Modern (3.10+) | Legacy (`typing` import) |
|---|---|---|
| List | `list[int]` | `List[int]` |
| Dict | `dict[str, int]` | `Dict[str, int]` |
| Fixed tuple | `tuple[int, int]` | `Tuple[int, int]` |
| Any-len tuple | `tuple[int, ...]` | `Tuple[int, ...]` |
| May be None | `int \| None` | `Optional[int]` |
| Either/or | `int \| str` | `Union[int, str]` |
| Literal choice | `Literal["r","w"]` | same (still `typing`) |
| Any value | `Any` | `Any` |
| Callable | `Callable[[int], str]` | same |
| Variable | `x: int = 5` | same |
| Hints only? | `if TYPE_CHECKING: import ...` + `from __future__ import annotations` | same |

**Rules to remember:**

1. Annotations are **data**; hints are **convention**; checking is **static**; runtime enforces **nothing** unless you add a library (`pydantic`, `typeguard`).
2. `Optional[X]` ≠ omitted param — it is `X | None`. Only `= default` makes it omittable.
3. `list[int]` before 3.9 needs `typing.List` or `from __future__ import annotations`.
4. Imports used only for hints belong under `if TYPE_CHECKING:` to avoid circular runtime imports.
5. `Any` disables checking — use `object` when you want "anything but must narrow before use."
