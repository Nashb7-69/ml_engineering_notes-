# 04.6 First-Class Functions and Lambdas

## Learning Objectives

- Treat functions as values: pass, store, compose, and return them.
- Master `lambda`: syntax, limits, closures, and when *not* to use it.
- Choose correctly between `lambda`, `def`, comprehensions, and `functools`/`operator` alternatives.
- Apply higher-order functions and replace `map`/`filter`/`reduce` with more Pythonic forms when appropriate.

---

## 1. Functions Are First-Class Citizens

A value is **first-class** if a language lets you:

1. Bind it to a name / store it in a data structure,
2. Pass it as an argument,
3. Return it from a function,
4. Create it at runtime.

Python functions satisfy all four (see lessons 04.1–04.5). Numbers and strings are trivially first-class; functions deserve emphasis because not every language allows *this* fluently (e.g., C function pointers are restricted; Java pre-8 required anonymous classes).

### 1.1 Assignment and containers

```python
import math

def square(x):
    return x * x

# 1. Bind to name (alias)
alias = square
print(alias(5))            # 25
print(alias is square)     # True — same object

# 2. Store in data structures
ops = {
    "square": square,
    "cube": lambda x: x ** 3,
    "sqrt": math.sqrt,
}
print(ops["cube"](3))      # 27

callbacks = [square, math.sqrt, str]
print([f(16) for f in callbacks])  # [256, 4.0, '16'] — heterogeneous callables

# Dispatch table pattern (realistic):
def handle_add(a, b): return a + b
def handle_mul(a, b): return a * b
def handle_pow(a, b): return a ** b

dispatch = {"+": handle_add, "*": handle_mul, "**": handle_pow}
print(dispatch["*"](6, 7)) # 42
```

Explanation: Each value in `ops`, `callbacks`, `dispatch` is a function object. Looking up the dict yields a callable; appending `()` calls it. This dispatch pattern replaces a switch/if-else chain.

### 1.2 Functions as arguments (higher-order functions)

A **higher-order function** takes or returns a function:

```python
def apply(func, value):
    return func(value)

print(apply(square, 4))               # 16
print(apply(lambda x: x + 10, 4))     # 14

def repeat(func, value, n):
    for _ in range(n):
        value = func(value)
    return value

print(repeat(square, 2, 3))  # ((2^2)^2)^2 = 256? Check: 2→4→16→256

# Realistic: retry with pluggable policy
def with_retry(func, should_retry, max_attempts=3):
    for attempt in range(1, max_attempts + 1):
        try:
            return func()
        except Exception as exc:
            if not should_retry(exc) or attempt == max_attempts:
                raise
            print(f"retry {attempt} after {exc}")
```

### 1.3 Functions as return values (factories and decorators)

```python
def make_adder(n):
    def adder(x):
        return x + n
    return adder                  # factory — returns a new function per n

add5 = make_adder(5)
print(add5(10))   # 15

# Returning a wrapper is the basis of decorators (lesson 04.7):
def loud(func):
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper
```

## 2. `lambda`: Anonymous Single-Expression Functions

### 2.1 Syntax: the expression form of `def`

```
lambda [parameters] : expression
```

`lambda` is an **expression** that creates and returns a function object. It is *not* a statement like `def`. The body must be a **single expression** — no statements, no `if` block, no `for`, no `return`, no annotations (though `lambda` params may have no defaults that are positional-only/keyword-only markers — `lambda a, /, b, *, c: ...` is not valid; `lambda` only allows simple args).

Examples progressing from simple to realistic:

```python
# 01 Simple
square = lambda x: x * x            # same as def square(x): return x*x
print(square(6))                    # 36

# 02 Multiple parameters, defaults
concat = lambda a, b, sep=" ": f"{a}{sep}{b}"
print(concat("hello", "world"))     # hello world
print(concat("a", "b", sep="-"))    # a-b

# 03 *args, **kwargs allowed
var = lambda *args, **kwargs: (args, kwargs)
print(var(1, 2, x=3))               # ((1, 2), {'x': 3})

# 04 No parameters
get_answer = lambda: 42
print(get_answer())                 # 42

# 05 Conditional expression (ternary) — the only "if" allowed
classify = lambda n: "positive" if n > 0 else "non-positive"
print(classify(-3))                 # non-positive

# The name of a lambda is always '<lambda>' — poor for tracebacks:
print(classify.__name__)            # <lambda>
print(square.__name__)              # <lambda> — not 'square'
```

Because `lambda` is an expression, it can appear **anywhere an expression can**:

```python
# Inside a call:
print(sorted(["bob", "alice", "charlie"], key=lambda s: len(s)))
# ['bob', 'alice', 'charlie']? len bob=3, alice=5, charlie=7 -> ['bob', 'alice', 'charlie']

# Inside a literal:
pairs = [(1, lambda x: x * 1), (2, lambda x: x * 2)]
print(pairs[1][1](10))  # 20

# Immediately invoked:
print((lambda x: x + 1)(10))  # 11 — rare but shows it's an expression
```

### 2.2 What `lambda` can and cannot contain

| Allowed in body | Not allowed (statements) |
|---|---|
| Any expression: `x*2`, `f(x)`, `a and b`, `a if cond else b` | `return` (implicit), `if` block, `for`, `while`, `with` |
| Comprehensions (`[x*2 for x in xs]` — expressions) | Assignments (`x = 1` — statement; `:=` walrus is expression, allowed but discouraged) |
| Calls, `or`/`and`, `lambda` nesting | `raise` (statement in Python 3.7-) — in 3.8+ `raise` is still statement-like |
| Conditional expression | `assert`, `del`, `pass`, `yield` (as statement) |

```python
# Conditional expression is the lambda-friendly "if":
# This is OK:
abs_val = lambda x: x if x >= 0 else -x

# This is a SyntaxError:
# bad = lambda x: if x >= 0: x else: -x

# Comprehensions are OK because they are expressions:
words = lambda s: [w.strip() for w in s.split(",")]
print(words(" a, b, c "))  # ['a', 'b', 'c']

# Tuple packing via comma:
swap_key = lambda pair: (pair[1], pair[0])

# For complex logic, just use def:
def process(value):
    if value is None:
        return 0
    cleaned = value.strip().lower()
    if not cleaned:
        return 0
    return len(cleaned)
# Cannot be a lambda — needs statements
```

### 2.3 `lambda` vs `def` — choosing correctly

| Criterion | Use `lambda` | Use `def` |
|---|---|---|
| Name needed / reused / debuggable | Never — `__name__` will be `'<lambda>'` | Yes — gives proper `__name__`, `__qualname__`, traceback |
| Body is one expression and small | Good: key/reducer/predicate |  |
| Used once as argument (`key=`, callbacks) | Ideal | Overkill |
| Body needs statements, assignments, docstring | Impossible | Required |
| Needs annotations/type safety or introspection | Not practical | Preferred |

PEP 8 rule: **Never** write `f = lambda ...` to name a function — just use `def`:

```python
# PEP 8 says don't:
f = lambda x: x * 2           # odd, worse name/traceback

# Do:
def double(x):
    return x * 2
```

The lambda alias `f.__name__` is `'<lambda>'`, stack traces show `'<lambda>'`, and you cannot attach docstring. `def` is always superior for named functions.

### 2.4 Closures vs lambdas: lambdas close, too

Lambdas are closures just like `def`; they share the **late-binding** pitfall:

```python
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])  # [2, 2, 2]

# Fix with default:
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])  # [0, 1, 2]

# Or factory:
def make_fn(i):
    return lambda: i
funcs = [make_fn(i) for i in range(3)]
print([f() for f in funcs])  # [0, 1, 2]
```

See lesson 04.5 for full treatment.

### 2.5 Lambdas in sorting / `key` functions

The most common and defensible use of `lambda` — tiny `key`s:

```python
users = [
    {"name": "Alice", "age": 36},
    {"name": "Bob", "age": 30},
    {"name": "Carol", "age": 40},
]

# Sort by age:
print(sorted(users, key=lambda u: u["age"]))
# [Bob 30, Alice 36, Carol 40]

# Sort by lowercase name length then alphabetically:
words = ["Python", "java", "C", "Go"]
print(sorted(words, key=lambda w: (len(w), w.lower())))
# ['C', 'Go', 'java', 'Python']

# Multi-level sort — key returns tuple ordered lexicographically:
from operator import itemgetter  # see §6 for better alternative for item keys
```

Limit lambdas to trivial keys. For reuse, name a `def`:

```python
def age_key(u):
    return u["age"]

# Now testable, documentable, lintable
sorted(users, key=age_key)
```

## 3. Higher-Order Functions in Practice

### 3.1 Your own higher-order helpers

```python
def map_apply(func, seq):
    return [func(x) for x in seq]

print(map_apply(str.upper, ["a", "b", "c"]))  # ['A', 'B', 'C']

def filter_apply(pred, seq):
    return [x for x in seq if pred(x)]

print(filter_apply(lambda x: x % 2 == 0, range(10)))  # [0, 2, 4, 6, 8]

def compose(f, g):
    """Return h(x) = f(g(x))."""
    def h(x):
        return f(g(x))
    return h

strip_and_upper = compose(str.upper, str.strip)
print(strip_and_upper("  hello "))  # HELLO
```

`compose` is a classic closure factory returning a function that closes over `f` and `g`.

### 3.2 Function registry pattern

```python
registry = {}

def register(name):
    """Register func under name; use as @register('key') — preview of decorators."""
    def decorator(func):
        registry[name] = func
        return func
    return decorator

@register("greet")
def greet(name):
    return f"Hello, {name}!"

@register("farewell")
def farewell(name):
    return f"Goodbye, {name}!"

print(registry)                  # {'greet': <function ...>, 'farewell': ...}
print(registry["greet"]("Ada"))# Hello, Ada!
```

## 4. `map`, `filter`, `reduce` vs Pythonic Alternatives

Python inherits `map`/`filter` from functional programming, but the community usually prefers **comprehensions** and **generator expressions** because they read as declarative data flow and avoid small lambdas.

### 4.1 `map` — apply a function element-wise

```python
nums = [1, 2, 3, 4]

# map version — lazy iterator in Python 3
doubled = map(lambda x: x * 2, nums)
print(list(doubled))  # [2, 4, 6, 8]

# Pythonic — comprehension (eager; clearer; handles complex expr)
doubled2 = [x * 2 for x in nums]
print(doubled2)       # [2, 4, 6, 8]

# map with named function — OK, but still less readable?
import math
print(list(map(math.sqrt, nums)))          # iterator, need list()
print([math.sqrt(x) for x in nums])        # same, arguably clearer
```

Rule-of-thumb: If you pick `map` only because the function already exists (`map(str, nums)`), both are accepted; many style guides still prefer `[str(x) for x in nums]` for uniformity.

### 4.2 `filter` — keep elements where predicate true

```python
nums = range(10)
evens = filter(lambda x: x % 2 == 0, nums)
print(list(evens))  # [0, 2, 4, 6, 8]

# Pythonic
evens2 = [x for x in nums if x % 2 == 0]
print(evens2)  # [0, 2, 4, 6, 8]

# With named predicate:
def is_even(n): return n % 2 == 0
print(list(filter(is_even, nums)))           # iterator form
print([x for x in nums if is_even(x)])       # often more explicit
```

### 4.3 `functools.reduce` — collapse sequence with binary op

```python
from functools import reduce

nums = [1, 2, 3, 4, 5]
total = reduce(lambda a, b: a + b, nums)           # sum
print(total)  # 15

product = reduce(lambda a, b: a * b, nums, 1)      # with initializer
print(product)  # 120

# Pythonic alternatives:
print(sum(nums))                                     # 15 — don't reduce for sum
import math
print(math.prod(nums))                               # 120 — Python 3.8+
# Or for generic op, a loop is clearer to most readers:
acc = 1
for n in nums:
    acc *= n
print(acc)  # 120
```

Why reduce is discouraged in style guides: a reduction can be **any** binary folding, so `reduce(lambda...)` hides control flow. A `for` loop or purpose-built summary (`sum`, `max`, `math.prod`, `collections.Counter`) communicates intent instantly.

Lazy vs eager: `map`/`filter` return iterators (lazy), comprehensions return lists (eager). Use generator expressions for lazy Pythonic form:

```python
lazy_doubled = (x * 2 for x in nums)       # generator expression — lazy like map
lazy_evens = (x for x in nums if x % 2==0) # lazy like filter
```

### 4.4 `zip`, `enumerate`, and other functional helpers (bonus)

These pair naturally with first-class function patterns:

```python
names = ["Ada", "Bob"]
scores = [95, 80]
print(list(zip(names, scores)))          # [('Ada', 95), ('Bob', 80)]

for i, v in enumerate(["a", "b", "c"], start=1):
    print(i, v)  # 1 a 2 b 3 c
```

## 5. `functools.partial` — Freezing Arguments

`functools.partial(func, *args, **kwargs)` returns a **new callable** that behaves like `func` with those arguments pre-filled. Unlike closures, `partial` preserves `func`'s signature introspection better (though `inspect.signature` wraps it), and avoids the lambda late-binding trap.

```python
import functools

def power(base, exp):
    return base ** exp

square = functools.partial(power, exp=2)
cube = functools.partial(power, exp=3)
print(square(5))  # 25
print(cube(5))    # 125

# Positional pre-fill (leftmost):
double = functools.partial(lambda x, y: x * y, 2)  # x=2 frozen
print(double(10))  # 20

# Realistic: specialized container constructors
from functools import partial
int_base2 = partial(int, base=2)  # parse binary strings
print(int_base2("1010"))  # 10

# Sorting with partial — pre-bind a key helper:
users = [{"name": "Alice", "age": 36}, {"name": "Bob", "age": 30}]
# Suppose getter is def get_field(obj, field): return obj[field]
def get_field(obj, field): return obj[field]
by_age = partial(get_field, field="age")
print(sorted(users, key=by_age))  # Bob then Alice

# Partial preserves attributes:
print(square.func)      # <function power ...>
print(square.args)      # ()
print(square.keywords)  # {'exp': 2}
```

`partial` vs lambda closure:

| Aspect | `lambda: func(1, 2)` | `partial(func, 1, 2)` |
|---|---|---|
| Introspection | `__name__ == '<lambda>'`, hides signature | `.func`, `.args`, `.keywords` + `functools.update_wrapper`-like via `WRAPPER_ASSIGNMENTS` |
| Late binding risk | Yes (captured names are variables) | No (args frozen at `partial` creation) |
| `isinstance(..., partial)` | False | True |
| Overheads | Tiny (extra function) | Also tiny (C implementation) |

For argument freezing, **prefer `partial`**. Use `lambda` when you need to transform/compute arguments (`lambda x: f(x+1)`), which `partial` cannot.

## 6. The `operator` Module — Replacing Trivial Lambdas

Many small lambdas are just wrappers around an operator or attribute access. `operator` supplies **named callables** that are faster, pickleable, and more introspectable than equivalent lambdas.

```python
import operator

nums = [3, 1, 4, 1, 5]

# Instead of lambda x: x[0]
pairs = [(3, "c"), (1, "a"), (2, "b")]
print(sorted(pairs, key=lambda p: p[0]))        # works
print(sorted(pairs, key=operator.itemgetter(0))) # same — operator version

# itemgetter with multiple indices returns tuple — great for multi-field sorts:
print(sorted(pairs, key=operator.itemgetter(1))) # sort by second

people = [
    {"name": "Ada", "age": 36},
    {"name": "Bob", "age": 30},
]
print(sorted(people, key=operator.itemgetter("age")))  # Bob then Ada

# attrgetter for attribute access:
from dataclasses import dataclass
@dataclass
class Point:
    x: int
    y: int

pts = [Point(3, 1), Point(1, 4), Point(2, 2)]
print(sorted(pts, key=operator.attrgetter("x")))       # sorted by x
print(sorted(pts, key=operator.attrgetter("y")))

# methodcaller for method calls:
words = ["  hello ", " WOrld "]
print(list(map(operator.methodcaller("strip"), words)))  # ['hello', 'WOrld']
print(list(map(operator.methodcaller("strip", "h"), words)))  # variant with args (strip 'h')

# Arithmetic / comparison operators:
import functools, operator
# sum via reduce vs operator.add — operator version:
print(functools.reduce(operator.add, [1, 2, 3, 4], 0))    # 10
print(functools.reduce(operator.mul, [1, 2, 3, 4], 1))    # 24 — use math.prod instead

# For sorting by negation or negation of attribute — attrgetter + neg:
# sorted(users, key=lambda u: -u["score"]) vs:
#   can't with itemgetter alone — keep lambda here
```

Full roster worth knowing:

| Task | Lambda form | `operator` / alternative |
|---|---|---|
| Get item / key | `lambda x: x["key"]` | `operator.itemgetter("key")` |
| Get attribute | `lambda o: o.attr` | `operator.attrgetter("attr")` |
| Call method | `lambda s: s.strip()` | `operator.methodcaller("strip")` |
| Add / mul | `lambda a,b: a+b` | `operator.add`, `operator.mul` |
| Negate | `lambda x: -x` | `operator.neg` |
| Compose truthiness tests | `lambda x: x is None` | `operator.is_`, etc. (niche) |

Why `itemgetter` over lambda?
- **Picklable**: lambda is not pickleable; `itemgetter` is (matters for `multiprocessing`).
- **Faster**: `itemgetter` is implemented in C.
- **Clean tracebacks**: lambda frames show `'<lambda>'`.

### 6.1 Comprehension beats operator vs lambda micro-optimizations

For outright list transforms, neither:

```python
nums = range(10)
# Avoid:
print(list(map(operator.neg, nums)))
# Prefer:
print([-x for x in nums])
# Same for:
# list(map(lambda x: x*2, nums)) -> [x*2 for x in nums]
```

## 7. Putting It All Together: Realistic Pipeline

```python
from functools import partial, reduce
import operator

orders = [
    {"id": 1, "customer": "Ada",  "amount": 120, "active": True},
    {"id": 2, "customer": "Bob",  "amount":  35, "active": False},
    {"id": 3, "customer": "Ada",  "amount":  80, "active": True},
    {"id": 4, "customer": "Carol","amount": 200, "active": True},
]

# Goal: sum of active orders over 50, grouped by customer, sorted descending by total.

# Step 1: filter — keep active and amount>50 (comprehension preferred)
filtered = [o for o in orders if o["active"] and o["amount"] > 50]
# filter variant for comparison (more verbose here):
# filtered = list(filter(lambda o: o["active"] and o["amount"] > 50, orders))

# Step 2: map — enrich / project (comprehension again)
# Add discounted_amount via partial-applied computation:
def discount(amount, pct):
    return round(amount * (1 - pct), 2)

discount10 = partial(discount, pct=0.10)
# map variant: projected = list(map(lambda o: {**o, "discounted": discount10(o["amount"])}, filtered))
projected = [{**o, "discounted": discount10(o["amount"])} for o in filtered]

print(projected)
# [{'id': 1, 'amount': 120, 'discounted': 108.0, ...}, {'id': 3, ...}, {'id': 4, ...}]

# Step 3: reduce/group — sum by customer (loop >> reduce for readability)
from collections import defaultdict
by_customer = defaultdict(list)
for o in projected:
    by_customer[o["customer"]].append(o["discounted"])

totals = {c: sum(amts) for c, amts in by_customer.items()}
print(totals)  # {'Ada': 188.0, 'Carol': 180.0}

# Step 4: sort — descending by total, operator or lambda:
sorted_customers = sorted(totals.items(), key=operator.itemgetter(1), reverse=True)
# equivalent lambda: sorted(totals.items(), key=lambda kv: kv[1], reverse=True)
print(sorted_customers)  # [('Ada', 188.0), ('Carol', 180.0)]

# Entire pipeline as functions:
def pipeline(data, min_amount=50, discount_pct=0.10):
    filtered = [o for o in data if o["active"] and o["amount"] > min_amount]
    disc = partial(discount, pct=discount_pct)
    projected = [{**o, "discounted": disc(o["amount"])} for o in filtered]
    by_c = defaultdict(list)
    for o in projected:
        by_c[o["customer"]].append(o["discounted"])
    totals = {c: sum(vs) for c, vs in by_c.items()}
    return sorted(totals.items(), key=operator.itemgetter(1), reverse=True)

print(pipeline(orders))
```

Explanation: Each stage picks the most readable higher-order pattern. `partial` freezes `pct`; comprehensions replace `map`/`filter` for clarity; `itemgetter` replaces a simple `lambda` key for picklability/speed. The pipeline composes plain functions — no framework needed.

## 8. Common Mistakes & Edge Cases

```python
# 1. Naming a lambda (PEP 8)
# Don't:
neg = lambda x: -x  # use def neg(x): return -x

# 2. Over-complex lambda — use def
# Don't:
# parse = lambda s: int(s.strip().split(":")[1]) if ":" in s else -1  # hard to debug
def parse(s):
    if ":" not in s:
        return -1
    return int(s.strip().split(":")[1])

# 3. Late binding in loop lambdas — see lesson 04.5
# Bad:  funcs = [lambda: i for i in range(3)] -> all 2
# Fixed: funcs = [lambda i=i: i for i in range(3)] or use partial/make_fn

# 4. Assuming map/filter are lists — they are lazy iterators (Python 3)
m = map(str, [1, 2, 3])
print(m)        # <map object ...>
print(list(m))  # ['1', '2', '3']
print(list(m))  # [] — exhausted!

# 5. pickle & multiprocessing can't handle lambdas
import pickle
fn = lambda x: x * 2
# pickle.dumps(fn)  # AttributeError: Can't pickle local object
# Use def or operator:
import operator
print(pickle.dumps(operator.itemgetter(0)))  # works

# 6. reduce without initializer on empty -> TypeError
from functools import reduce
# reduce(operator.add, [])  # TypeError: reduce() of empty iterable with no initial value
print(reduce(operator.add, [], 0))  # 0 — always supply initializer when emptiness possible
```

## 9. Quick Reference

| Pattern | When | Pythonic? |
|---|---|---|
| `def f(...): return ...` | Named reusable functions, anything non-trivial | Always |
| `lambda x: expr` | Tiny throwaway `key`, inline predicate (one expr) | Yes — short only |
| `x for x in ... if pred` | `filter(pred, ...)` | *More* Pythonic than `filter`+`lambda` |
| `[f(x) for x in ...]` | `map(f, ...)` | *More* Pythonic than `map`+`lambda` |
| `for acc in ...: total = op(total, x)` | `reduce(op, ...)` | Loop / `sum` / `math.prod` preferred |
| `partial(func, args, kwargs)` | Freeze some arguments | Preferred over `lambda: func(args)` for freezing |
| `itemgetter` / `attrgetter` / `methodcaller` | Replace `lambda x: x[k]` / `x.attr` / `x.meth()` | Faster, picklable |
| Dispatch dict | Switch on value | `{"+": add, "*": mul}[op](a, b)` |
