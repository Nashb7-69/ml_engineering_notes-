# 04.1 Defining Functions

## Learning Objectives

By the end of this lesson you will be able to:

- Define functions with `def` and understand exactly what Python does at definition time vs call time.
- Predict return values, including implicit `None`, bare `return`, and multiple values via tuple packing.
- Write proper docstrings and use `help()` and introspection attributes.
- Treat functions as first-class objects: assign, inspect, and pass them around.
- Avoid the most common beginner pitfalls around `return` and `None`.

---

## 1. Why Functions Matter in Python

If you already program in another language, you know functions: named blocks that take inputs, do work, and produce outputs. Python's functions add a few twists:

| Feature | In Python | Compared to C / Java / JavaScript |
|---|---|---|
| Definition | `def` statement is **executable** code | Not a compile-time declaration |
| Values | Functions are **objects** at runtime | Like JS first-class functions, unlike C |
| Return | Every function returns something; no `void` | Falling off the end returns `None` |
| Multiple returns | `return a, b` packs a tuple | Not comma-separated values — a single tuple |
| Overloading | No overloading by arity/type | Last definition wins |
| Typing | Dynamically typed, optionally annotated | No mandatory signatures |

The key mental model: `def` is an **executable statement** that creates a function object and binds it to a name, just as `x = 3` binds an integer object to `x`.

## 2. The `def` Statement

### 2.1 Minimal syntax

```python
def greet():
    print("hello")
```

Explanation:
- `def` — keyword starting a **compound statement**.
- `greet` — the name to bind. Must be a valid identifier.
- `()` — parameter list (empty here).
- `:` — introduces a new **suite** (indented block).
- Body — one or more statements indented consistently (PEP 8: 4 spaces).

Calling it:

```python
greet()          # prints "hello", returns None
result = greet()
print(result)    # None
```

Calling executes the body. If execution falls off the end without `return`, Python returns `None` implicitly.

### 2.2 What `def` actually does at runtime

This often surprises programmers from compiled languages. `def` runs **when the interpreter reaches it**, not ahead of time:

```python
print("before def")

def foo():
    print("inside foo")

print("after def")
print(foo)          # <function foo at 0x...>
print(type(foo))    # <class 'function'>
print(callable(foo))# True

foo()  # now the body runs
```

Explanation: The three `print` calls at the top run in order. The `def` creates a `function` object containing the code and default bindings, then assigns it to `foo` in the current namespace. No code inside `foo` has run yet — `print("inside foo")` only executes on `foo()`.

This also means you can define functions conditionally and even inside other functions or loops — `def` is just a statement:

```python
if DEBUG := False:  # assignment expression, Python 3.8+
    def log(msg):
        print(f"[DEBUG] {msg}")
else:
    def log(msg):
        pass  # no-op when not debugging

log("test")  # does nothing in this branch
```

> **Takeaway:** A function definition is not hoisted. You must define before you call (at runtime flow), unlike JavaScript function declarations or C forward declarations.

### 2.3 Body requirements: `pass` and docstrings

An indented block cannot be empty. Use `pass` as a syntactic placeholder:

```python
def todo():
    pass  # syntactically valid, does nothing, returns None

todo()  # returns None
```

`pass` is a no-op statement that exists purely to satisfy the grammar. It is distinct from "return nothing" — it just means "no statement here."

## 3. `return`: Explicit, Implicit, Early, and Bare

### 3.1 Explicit return

```python
def add(a, b):
    return a + b

print(add(2, 3))   # 5
```

`return <expr>` evaluates `<expr>`, exits the function immediately, and makes that value the result of the call expression.

### 3.2 Implicit `None`

If there is no `return`, or execution falls off the end, the return value is `None`:

```python
def noisy(x):
    print(f"got {x}")

value = noisy(10)
print(value)       # None
print(value is None)  # True
```

`None` is a singleton object of type `NoneType`. It is **not** `0`, `False`, or `""`, though it is falsy (`bool(None)` is `False`). Implicit `None` is why functions called only for side effects (like `print`) evaluate to `None`.

### 3.3 Bare `return`

A `return` without an expression is equivalent to `return None`:

```python
def guard(x):
    if x < 0:
        return        # early exit, returns None
    return x * 2

print(guard(-1))  # None
print(guard(5))   # 10
```

Style note: PEP 8 says **be consistent**. If a function can return a value in one branch, every branch should return a value (or explicitly `None`). Mixing "sometimes value, sometimes implicit None" confuses callers.

```python
# Confusing — implicit None on one path
def find_positive(nums):
    for n in nums:
        if n > 0:
            return n
    # falls off -> None

# Clear — explicit on both paths
def find_positive(nums):
    for n in nums:
        if n > 0:
            return n
    return None
```

The second version is self-documenting: the reader knows `None` means "not found."

### 3.4 Early returns — the Pythonic guard clause

Python idiom favors early returns to flatten nesting, instead of deeply nested `if/else`:

```python
# Nested — harder to read
def process(payload):
    if payload is not None:
        if "data" in payload:
            if isinstance(payload["data"], list):
                return len(payload["data"])
            else:
                return 0
        else:
            return 0
    else:
        return 0

# Guard clauses — flat, idiomatic
def process(payload):
    if payload is None:
        return 0
    if "data" not in payload:
        return 0
    if not isinstance(payload["data"], list):
        return 0
    return len(payload["data"])
```

Both return the same value. The second reads top-to-bottom as a series of preconditions.

### 3.5 What `return` does *not* do

- It does **not** print anything. REPLs print the `repr` of non-`None` return values, but scripts do not.
- `return` works only inside a function. Using it at module level raises `SyntaxError`.
- `return` inside a `try/finally` still runs `finally`:

```python
def demo():
    try:
        return 1
    finally:
        print("finally runs even after return")

print(demo())
# finally runs even after return
# 1
```

## 4. Multiple Return Values — Tuple Packing

Python appears to return multiple values, but it actually returns **one tuple**:

```python
def min_max(values):
    return min(values), max(values)   # tuple packing

lo, hi = min_max([3, 1, 4, 1, 5])    # tuple unpacking
print(lo, hi)       # 1 5
print(type(min_max([1, 2])))  # <class 'tuple'>
```

Explanation:
- `return min(values), max(values)` is `return (min(values), max(values))` — parentheses are optional in packing. One tuple object `(1, 5)` is returned.
- `lo, hi = ...` unpacks the two-element tuple into two names.

You can return any composite value. Tuple packing is idiomatic for fixed-structure, small heterogeneous results:

```python
def parse_user(line: str):
    """Return (name, age) parsed from 'name:age'."""
    name, age_str = line.split(":")
    return name.strip(), int(age_str)

name, age = parse_user("Ada: 36")
```

Alternative patterns and when to use them:

| Return shape | When to use | Example |
|---|---|---|
| Tuple `a, b` | Fixed small number, positional meaning | `return lo, hi` |
| `dict` | Named fields, variable keys | `return {"lo": lo, "hi": hi}` |
| `namedtuple` / `dataclass` | Named + typed + reusable | `return Bounds(lo, hi)` |
| `None` sentinel | Search failure | `return None` |

Destructuring works with any iterable return, but tuples are conventional and cheapest:

```python
def head_tail(seq):
    if not seq:
        return None, []   # still a 2-tuple, second element is []
    return seq[0], seq[1:]

h, t = head_tail([10, 20, 30])
print(h, t)  # 10 [20, 30]
```

> **Common mistake:** Writing `return a, b` and expecting two values on the stack. There is only one object. For instance, `len(min_max(...))` is `2`, and `min_max(...) == (lo, hi)` is a single comparison.

Swapping via tuple packing is idiomatic precisely because of this:

```python
a, b = b, a  # RHS packs (b, a), LHS unpacks
```

## 5. Functions Are Objects

### 5.1 Assignment, inspection, passing

```python
def square(x):
    """Return x squared."""
    return x * x

f = square              # no parentheses -> alias, no call
print(f)                # <function square at 0x...>
print(f(5))             # 25 — same object
print(f is square)      # True
print(f.__name__)       # 'square'
print(square.__doc__)   # 'Return x squared.'
```

Explanation: `square` is a name bound to a `function` object. `f = square` binds another name to the **same** object. `square()` with parentheses calls it; without parentheses it is just a value.

Because functions are objects, you can:
- Store them in lists/dicts
- Pass them to other functions
- Return them from functions (used heavily in decorators/closures — see lessons 04.5–04.7)

```python
def apply(func, value):
    return func(value)

print(apply(square, 4))            # 16
print(apply(lambda x: x + 10, 4))  # 14

ops = {"square": square, "neg": lambda x: -x}
print(ops["square"](6))  # 36
```

### 5.2 Type of a function

```python
import types

def example(): pass

print(type(example))                        # <class 'function'>
print(isinstance(example, types.FunctionType))  # True
print(isinstance(example, types.BuiltinFunctionType))  # False
```

- `function` — user-defined with `def` or `lambda`.
- `builtin_function_or_method` — implemented in C, e.g., `len`, `print`, `list.append`. They lack `__code__` and `__closure__`.

```python
print(type(len))          # <class 'builtin_function_or_method'>
print(hasattr(len, "__code__"))   # False
print(hasattr(example, "__code__"))  # True
```

### 5.3 Useful function attributes (introspection)

Every `def`-created function carries metadata:

```python
def tagged(a, b=2):
    """Add with default."""
    return a + b

print(tagged.__name__)      # 'tagged'
print(tagged.__qualname__)  # 'tagged' (includes enclosing scope; 'Outer.inner' if nested)
print(tagged.__doc__)       # 'Add with default.'
print(tagged.__code__)      # code object with bytecode, varnames, etc.
print(tagged.__defaults__)  # (2,) — tuple of defaults for trailing params
print(tagged.__kwdefaults__)# None if no kw-only defaults
print(tagged.__dict__)      # {} — arbitrary attributes dict
print(tagged.__module__)    # '__main__'

# You can even attach attributes:
tagged.author = "Ada"
print(tagged.author)        # Ada
```

These are used by `help()`, debuggers, and decorators. Do not mutate `__defaults__` directly — treat as read-only.

## 6. Docstrings — The Third Dimension of `def`

### 6.1 Syntax and placement

A docstring is a string literal as the **first statement** in the body. Python stores it as `__doc__`; tools display it:

```python
def divide(a, b):
    """Return a divided by b.

    Raises ZeroDivisionError if b is zero.
    """
    return a / b

print(divide.__doc__)
help(divide)  # prints nicely formatted docstring
```

If the first statement is not a string literal, there is no docstring (`__doc__` is `None`):

```python
def no_doc():
    x = 1
    """This is just a string expression, NOT a docstring."""
    return x

print(no_doc.__doc__)  # None
```

Triple quotes (`"""..."""`) are convention, even for one-liners, per PEP 257.

### 6.2 PEP 257 conventions (summary)

| Rule | Example |
|---|---|
| One-line docstring: single line, ends with period, triple quotes | `"""Return x squared."""` |
| Multi-line: summary line, blank line, elaboration | See `divide` above |
| Document params, return, raises | Use Sphinx/Google/NumPy style if your project picks one |
| Use `__doc__` for introspection | `help()`, IDEs, `pydoc` |

Three popular docstring styles (pick one per project):

```python
# Google style
def connect(host, port, timeout=10):
    """Open a TCP connection.

    Args:
        host: Hostname or IP.
        port: TCP port number.
        timeout: Seconds to wait before failing.

    Returns:
        A connected socket object.

    Raises:
        TimeoutError: If the connection times out.
    """
    ...

# Sphinx / reST style
def connect(host, port, timeout=10):
    """Open a TCP connection.

    :param host: Hostname or IP.
    :param port: TCP port number.
    :param timeout: Seconds to wait.
    :return: A connected socket.
    """

# NumPy style (verbose, great for scientific code)
def connect(host, port, timeout=10):
    """
    Open a TCP connection.

    Parameters
    ----------
    host : str
    port : int
    timeout : int, optional

    Returns
    -------
    socket
    """
```

No style is enforced by Python; consistency within a project is the rule.

## 7. `None` — The Absence of a Useful Return

`None` deserves special attention:

```python
x = None
print(x is None)          # True — always test None with `is`
print(x == None)          # works but discouraged (could be overloaded)
print(type(x))            # <class 'NoneType'>
print(bool(None))         # False
```

Idiomatic check: `if result is None:` or `if result is not None:`, never `==`.

Why `None` instead of `void`?

```python
# Python has no void — every call yields an object.
def log(msg):
    print(msg)

out = log("hi")  # prints "hi", out is None
if out is None:
    print("log returned nothing useful")
```

`None` also appears as a default sentinel (lesson 04.2) and as an explicit "not found" signal. Let callers distinguish `None` from other falsy values (`0`, `[]`, `""`):

```python
def first_even(nums):
    for n in nums:
        if n % 2 == 0:
            return n
    return None

result = first_even([1, 3, 5])
if result is None:          # correct — distinguishes from 0
    print("no even found")
# NOT: if not result: — would misfire if the even is 0
```

## 8. Parameter Lists — A Preview

The bare `def greet():` is the simplest form. Real functions take parameters:

```python
def greet(name, greeting="Hello"):
    return f"{greeting}, {name}!"

print(greet("Ada"))                 # Hello, Ada!
print(greet("Grace", "Hi"))         # Hi, Grace!
print(greet("Linus", greeting="Hey"))  # Hey, Linus!
```

Parameter kinds — positional, default, `*args`, keyword-only, `**kwargs`, positional-only `/` — are covered in deep detail in lessons **04.2**, **04.3**, and **04.4**. For now, know that `def` declares **parameters** and a call supplies **arguments**.

## 9. Common Mistakes and Edge Cases

### 9.1 Forgetting `return`

```python
def add(a, b):
    a + b           # computed, then discarded

print(add(2, 3))   # None — body had no return
```

No error; the addition happens, its result is thrown away, and `None` is returned. Linters (`flake8`, `pylint`) can warn, but Python itself will not.

### 9.2 Unreachable code after `return`

```python
def fun(x):
    return x * 2
    print("never reached")  # dead code

print(fun(5))  # 10
```

Python does not warn. Static analyzers might.

### 9.3 Printing vs returning

Novice confusion between side effect and result:

```python
def double(x):
    print(x * 2)     # side effect

def double2(x):
    return x * 2     # value

print(double(5))   # prints 10, then prints None (the return)
print(double2(5))  # prints 10 (the return)
```

If you `print` inside, the **caller** cannot use the value. Prefer `return` for computation and let the caller decide to print.

### 9.4 Rebinding a function name

Because `def` is an assignment, redefining silently overwrites:

```python
def fetch(url):
    return f"fetching {url}"

def fetch(url):   # oops, second definition overwrites first
    return f"NEW fetching {url}"

print(fetch("http://example.com"))  # NEW ...
```

Python has **no overloading**. Two `def fetch(...)` in the same scope — only the last survives. Use default arguments or `*args` to handle varying signatures.

### 9.5 Defining functions inside loops

Legal but subtle — the function object is recreated each iteration, closing over the loop variable (late-binding pitfall detailed in lesson 04.5):

```python
funcs = []
for i in range(3):
    def f():
        return i
    funcs.append(f)

print([fn() for fn in funcs])  # [2, 2, 2] — not [0, 1, 2]!
```

This is not a bug in `def` — it is closure late-binding, fixed by capturing `i` as a default: `def f(i=i): return i`.

### 9.6 The `lambda` comparison

A `lambda` is an **expression** that creates a function, limited to one expression:

```python
double = lambda x: x * 2  # equivalent to def double(x): return x*2
print(double(5))          # 10
print(double.__name__)    # '<lambda>' — poor introspection
```

PEP 8 discourages `double = lambda...` — just use `def` when giving a name. Lambdas shine as small, throwaway arguments (see lesson 04.6).

## 10. Realistic Example: Validation Pipeline

Putting definitions, returns, and docstrings together:

```python
import re

_EMAIL_RE = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")

def normalize_email(raw: str) -> str:
    """Strip whitespace and lowercase the email."""
    return raw.strip().lower()

def is_valid_email(email: str) -> bool:
    """Return True if email looks syntactically valid."""
    return bool(_EMAIL_RE.match(email))

def parse_emails(raw_lines):
    """Parse lines into (valid_emails, errors).

    Each line should contain one email. Blank lines are skipped.
    Returns a tuple of (list_of_valid, list_of_error_strings).
    """
    valid = []
    errors = []
    for lineno, line in enumerate(raw_lines, start=1):
        cleaned = line.strip()
        if not cleaned:
            continue          # blank line — skip, not an error
        email = normalize_email(cleaned)
        if is_valid_email(email):
            valid.append(email)
        else:
            errors.append(f"line {lineno}: invalid email {cleaned!r}")
    return valid, errors  # tuple packing — single return

# Usage — tuple unpacking at the call site:
raw = ["  Ada@Example.COM ", "not-an-email", "", "bob@host.org"]
good, bad = parse_emails(raw)
print(good)  # ['ada@example.com', 'bob@host.org']
print(bad)   # ["line 2: invalid email 'not-an-email'"]
```

Explanation:
- `normalize_email` and `is_valid_email` are small, single-purpose, easily testable.
- `parse_emails` returns a **tuple** of two lists. The caller unpacks; the docstring spells out the structure.
- Early `continue` skips blanks without nesting.
- Annotations (`-> str`, `-> bool`) are hints only — no runtime effect (see lesson 04.8).

## 11. Quick Reference

| Concept | Key point |
|---|---|
| `def f():` | Executable statement; creates function object |
| Call `f()` | Executes body; result is `return` value or `None` |
| `return` | Exits immediately; exits `try/finally` after `finally` |
| `return` (bare) | Same as `return None` |
| `return a, b` | Returns one tuple `(a, b)` |
| `pass` | Empty body placeholder |
| `"""doc"""` | First-statement string → `__doc__` |
| `f is g` | Same object? (alias test) |
| `type(f)` | `function` (user-defined) vs `builtin_function_or_method` |
