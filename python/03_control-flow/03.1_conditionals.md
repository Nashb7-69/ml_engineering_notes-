# 3.1 Conditionals

> **What you will learn:** How Python expresses branching logic with `if`/`elif`/`else`, why the colon-and-indentation syntax matters, how truthiness replaces explicit boolean checks, how to write idiomatic ternary expressions, chained comparisons, identity vs. equality, short-circuit evaluation, guard clauses, and PEP 8 style for conditionals.

---

## 1. Why Python Conditionals Look Different

If you come from C, Java, JavaScript, Go, or Rust, Python's conditional syntax will feel stripped down. There are no parentheses required around the condition, no curly braces delimiting blocks, and no `else if` — it is `elif`. Every compound statement in Python follows the same visual contract:

```
<header line ending with colon>:
    <indented block>
```

This is not decoration. The colon (`:`) tells the parser "a suite follows", and the indentation *is* the block structure. The compiler will reject inconsistent indentation.

```python
# Minimal if — no parentheses needed.
temperature = 22

if temperature > 30:
    print("It's hot")

# You *can* add parentheses, but they are redundant.
if (temperature > 30):
    print("It's hot")

# Braces do NOT create blocks — they create dicts/sets.
# This is NOT a block delimiter:
if temperature > 30:  # <- colon required
    print("It's hot")  # <- indentation required (4 spaces conventionally)
```

**Explanation:** The first example is canonical Python. The second works but is unidiomatic — extra parentheses add visual noise. The third comment warns C-family programmers not to reach for `{}`.

### The `elif` Keyword

Python collapses `else if` into a single keyword `elif`. It is not two words, and it avoids the "dangling else" ambiguity that plagues brace languages.

```python
score = 87

if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
elif score >= 70:
    grade = "C"
else:
    grade = "F"

print(grade)  # B
```

**Explanation:** Only one branch executes — the first whose condition is truthy. If `score` were 95, the `elif` and `else` branches would not even be evaluated. Each condition is tested top-to-bottom.

### Indentation Rules — Precisely

- The conventional indent is **4 spaces** per level (PEP 8). Tabs work but mixing tabs and spaces raises `TabError`.
- The block can be on the same line after the colon for trivial bodies, but this is discouraged beyond one-liners in scripts:

```python
if x < 0: x = 0  # legal, but only for very short bodies

# Preferred for anything non-trivial:
if x < 0:
    x = 0
    print("clamped")
```

- An empty block requires `pass`:

```python
if debug:
    pass  # TODO: add logging
else:
    run()
```

Forgetting `pass` and leaving a blank line after `if debug:` is a `SyntaxError` / `IndentationError`.

## 2. `if` / `elif` / `else` — Full Semantics

### Syntax

```python
if <condition>:
    <suite>
elif <condition>:   # zero or more
    <suite>
else:               # zero or one, must be last
    <suite>
```

- `elif` and `else` are optional.
- `else` without a preceding `if` is a syntax error.
- `elif` after `else` is a syntax error — `else` must terminate the chain.

```python
# Simple two-way branch
is_authenticated = True

if is_authenticated:
    print("Welcome")
else:
    print("Please log in")

# Multi-way with elif
http_status = 404

if http_status == 200:
    print("OK")
elif http_status == 404:
    print("Not Found")
elif http_status == 500:
    print("Server Error")
else:
    print(f"Unexpected status: {http_status}")
```

**Explanation:** The `http_status` chain demonstrates the idiomatic way to dispatch on discrete values before we have `match` (3.3). For many branches on a single value, `match`/`case` is often cleaner in Python 3.10+.

### Conditions Are Expressions — Any Object

Unlike languages that require a `boolean` type, Python accepts **any object** as a condition. It is evaluated for *truthiness* (see Section 3). This is why you see:

```python
if my_list:          # truthy if non-empty
    process(my_list)

if not my_list:      # cleaner than `if len(my_list) == 0`
    print("empty")
```

## 3. Truthiness — The Heart of Python Conditionals

### Truthy and Falsy Values

Every object in Python has a boolean interpretation. The built-in `bool()` makes it explicit.

**Falsy values** — the complete list:

| Value | Type | Why falsy |
|---|---|---|
| `None` | `NoneType` | The null singleton |
| `False` | `bool` | The false singleton |
| `0`, `0.0`, `0j` | `int`, `float`, `complex` | Numeric zero |
| `Decimal(0)`, `Fraction(0, 1)` | `decimal`, `fractions` | Numeric zero |
| `""` | `str` | Empty string |
| `[]`, `()`, `{}` | `list`, `tuple`, `dict` | Empty collections |
| `set()`, `frozenset()` | `set` | Empty sets |
| `range(0)` | `range` | Empty range |
| Objects where `__bool__` returns `False` or `__len__` returns `0` | custom | User-defined |

**Everything else is truthy** — including non-empty strings (`"0"`, `"False"`), non-zero numbers (`-1`, `0.0001`), non-empty collections (`[0]`, `[None]`), and most objects.

```python
# Demonstrating truthiness explicitly
bool("")        # False
bool("hello")   # True
bool("0")       # True — non-empty string, even though it looks like zero!
bool(0)         # False
bool(42)        # True
bool([])        # False
bool([0])       # True — list has one element, even though that element is falsy
bool(None)      # False
bool([None])    # True
```

**Explanation:** A common beginner trap is `if my_string == "False"` vs. `if my_string`. The string `"False"` is truthy because it is non-empty. Truthiness checks the *container*, not a semantic interpretation of content.

### Custom Truthiness: `__bool__` and `__len__`

Python determines truthiness by calling `__bool__()`. If that is not defined, it falls back to `__len__()` (zero length = falsy). If neither is defined, the object is truthy.

```python
class Container:
    def __init__(self, items):
        self.items = items

    def __len__(self):
        return len(self.items)

    # No __bool__ defined, so len == 0 means falsy

print(bool(Container([])))       # False — __len__ returns 0
print(bool(Container([1, 2])))   # True  — __len__ returns 2

class AlwaysTruthy:
    def __bool__(self):
        return True

    def __len__(self):
        return 0

print(bool(AlwaysTruthy()))      # True — __bool__ takes precedence over __len__

class ExplicitlyFalsy:
    def __bool__(self):
        return False

print(bool(ExplicitlyFalsy()))   # False regardless of __len__
```

**Explanation:** If you define `__bool__`, it must return a `bool`. Returning a non-bool does not raise immediately but `bool()` will coerce it. Always return `True`/`False`.

### Idiomatic Truthiness vs. Explicit Comparisons

```python
# --- Bad: redundant comparisons ---
if my_list == []:          # works but unpythonic
    print("empty")
if my_string == "":         # verbose
    print("empty")
if x is not None and len(x) > 0:  # overly explicit for simple emptiness check
    print("has items")

# --- Good: idiomatic truthiness ---
if not my_list:
    print("empty")
if not my_string:
    print("empty")
if x:
    print("has items")

# --- When to be EXPLICIT (important!) ---
# If 0 or "" are valid meaningful values, truthiness conflates them with "missing":

def process_quantity(qty):
    # Bug: qty=0 is falsy but is a valid quantity
    if not qty:
        print("no quantity provided")  # incorrectly triggers for qty=0

    # Fix: test for None explicitly when None means "not provided"
    if qty is None:
        print("no quantity provided")
    elif qty == 0:
        print("quantity is zero")

# Sentinel check: distinguish None from other falsy values
value = 0
if value is not None:   # True — 0 is not None
    print(f"Value present: {value}")

if value:               # False — 0 is falsy
    print("truthy")
else:
    print("falsy")      # this prints
```

**Explanation:** The last example is the critical nuance. Use truthiness when "empty / zero / missing" are all equivalent. Use `is None` or `== 0` when they carry different meanings. APIs that return `None` for "not found" and `0` or `""` for "found but empty" require explicit checks.

## 4. Commonly Confused: `==` vs. `is`

This distinction is a frequent source of bugs for newcomers.

| Operator | Tests | Meaning |
|---|---|---|
| `==` | Equality | Do these objects have the **same value**? (calls `__eq__`) |
| `is` | Identity | Are these the **same object in memory**? (`id(a) == id(b)`) |

```python
# Equality vs identity
a = [1, 2, 3]
b = [1, 2, 3]
c = a

print(a == b)   # True  — same contents
print(a is b)   # False — different objects in memory
print(a is c)   # True  — c points to the same object as a
print(a == c)   # True  — same object implies equal (usually)

# String interning can mislead — NEVER rely on `is` for value comparison
s1 = "hello"
s2 = "hello"
print(s1 is s2)  # True on CPython due to interning — but don't depend on it!

s3 = "".join(["hel", "lo"])
print(s1 == s3)  # True
print(s1 is s3)  # False (usually) — same value, different object

# Correct usage of `is`
x = None
if x is None:       # correct — None is a singleton
    print("x is None")

if x is not None:   # correct
    print("x has a value")

# Also correct for other singletons:
if flag is True:    # technically works but AVOID — see next section
    pass
```

**Rule:** Use `is` / `is not` **only** for `None`, and occasionally for sentinel singletons you created yourself. For everything else — including `True`, `False`, numbers, strings — use `==`.

```python
# Sentinel pattern — legitimate use of `is`
_MISSING = object()  # unique sentinel

def find_user(user_id, default=_MISSING):
    user = database_lookup(user_id)
    if user is _MISSING:
        # actually check — cannot use `==` because _MISSING is unique
        raise KeyError(user_id)
    return user
```

**Explanation:** `object()` creates a unique instance. No other value will ever be `==` to it in a meaningful way, so `is` is the only correct test. This is the textbook case where `is` is required.

## 5. Avoiding `if x == True` / `if x == False`

This is one of the most visible markers of non-idiomatic Python.

```python
# --- Bad: never do this ---
if x == True:
    print("yes")
if x == False:
    print("no")
if x is True:       # also bad for general truthiness checks
    print("yes")
if x != True:
    print("no")

# Why it breaks:
x = 1
print(x == True)    # True — because True == 1 in Python!
print(x is True)    # False — 1 is not the True singleton
print(bool(x))      # True

x = [1]
print(x == True)    # False — a list never equals True
print(bool(x))      # True — but it IS truthy

# --- Good ---
if x:
    print("yes — x is truthy")
if not x:
    print("no — x is falsy")

# --- When you genuinely need to check for the bool value True ---
# (rare — e.g., API returns True/False/None with different meanings)
if x is True:       # correct ONLY when you mean "exactly the True singleton"
    print("specifically True")
elif x is False:
    print("specifically False")
else:
    print("neither — probably None")
```

**Explanation:** `bool` is a subclass of `int` in Python (`True == 1`, `False == 0`). Comparing with `== True` conflates `1` with `True` and fails for truthy non-bool values. The idiomatic form `if x:` handles all truthy values correctly.

## 6. Chained Comparisons — A Python Superpower

In most languages, `a < b < c` is parsed as `(a < b) < c`, which compares a boolean to `c` — almost always a bug. Python chains them mathematically: `a < b < c` means `a < b and b < c`, with `b` evaluated **only once**.

```python
# Simple chaining — reads like mathematics
x = 15
if 0 < x < 100:
    print("x is between 0 and 100 exclusive")

# Equivalent verbose form:
if 0 < x and x < 100:
    print("same result, more typing")

# But chaining evaluates the middle expression ONCE:
def get_value():
    print("get_value called")
    return 5

# `get_value()` is called once:
if 0 < get_value() < 10:
    print("in range")
# Output:
#   get_value called
#   in range

# Contrast with `and` form — calls twice:
if 0 < get_value() and get_value() < 10:
    print("in range")
# Output:
#   get_value called
#   get_value called
#   in range

# Chaining works with any comparison operators
if 0 <= x <= 100:       # inclusive range
    print("0..100 inclusive")
if 10 > x > 0:          # reversed — same meaning
    print("same")
if a == b == c:         # all three equal — NOT (a==b)==c
    print("all equal")
if a is b is c:         # all identical objects
    print("all same object")
if 0 < x < 100 != y:    # chains: 0<x and x<100 and 100!=y
    print("mixed operators chain too")

# Common idiom: validate range
def validate_age(age):
    if not 0 <= age <= 150:
        raise ValueError(f"Invalid age: {age}")

# Edge case: chaining with `in` and `is`
if x is not None and 0 <= x < 100:
    print("x is a valid percentage")
# Cannot chain `is not None` with `<` — different operator families
# `x is not None < 100` would mean `x is not None and None < 100` — wrong!
```

**Explanation:** Chained comparisons are syntactic sugar that is both more readable and more efficient (single evaluation). They work with `<`, `<=`, `>`, `>=`, `==`, `!=`, `is`, `is not`, `in`, `not in` — all comparison operators participate in the chain.

## 7. Boolean Operators, Short-Circuit, and `and`/`or` Return Values

### Short-Circuit Evaluation

Python's `and` and `or` do **not** necessarily return `True`/`False`. They return **one of the operands**, and they short-circuit — the right side is not evaluated if the result is already determined.

```python
# `and`: returns first falsy value, or last value if all truthy
print(0 and 42)         # 0 — first value is falsy, short-circuits
print(42 and 0)         # 0 — second value is falsy
print(42 and 100)       # 100 — both truthy, returns last
print("" and "hello")   # "" — empty string is falsy

# `or`: returns first truthy value, or last value if all falsy
print(0 or 42)          # 42 — first is falsy, returns second
print(42 or 0)          # 42 — first is truthy, short-circuits
print("" or "default")  # "default"
print("" or 0 or None)  # None — all falsy, returns last

# `not`: always returns True or False (unlike and/or)
print(not 0)            # True
print(not 42)           # False
print(not "")           # True
```

**Explanation:** This is fundamentally different from C/Java where `&&`/`||` always produce a boolean. In Python, `and`/`or` are value-selecting operators.

### Practical Short-Circuit Patterns

```python
# Guard against None / attribute errors
name = user and user.name  # if user is None/falsy, returns user (None) without accessing .name
# More commonly written as:
name = user.name if user else None

# Default values — the `or` idiom (with caveat)
# Works when falsy values are not valid inputs:
display_name = user_input or "Anonymous"  # if user_input is "" or None, use default

# Bug when 0 or "" ARE valid:
count = 0
result = count or 10  # 10 — oops, 0 was a valid count!
# Fix: explicit None check
result = count if count is not None else 10  # 0 — correct
count = None
result = count if count is not None else 10  # 10 — correct for None

# Short-circuit avoids expensive / dangerous operations
if user is not None and user.is_admin:  # user.is_admin not evaluated if user is None
    grant_access()

if data and len(data) > 100:  # len not called if data is None/empty
    process(data)

# Division guard
if denominator != 0 and numerator / denominator > threshold:
    print("ratio exceeds threshold")
# numerator/denominator never evaluated when denominator is 0
```

### Operator Precedence in Conditionals

From highest to lowest in boolean context: `not` > `and` > `or`. Comparisons bind tighter than boolean operators.

```python
# `not` binds tighter than `and`/`or`
print(not True and False)     # (not True) and False → False and False → False
print(not (True and False))   # not (True and False) → not False → True

# `and` binds tighter than `or`
print(True or False and False)  # True or (False and False) → True or False → True
print((True or False) and False)  # (True or False) and False → True and False → False

# Comparison before boolean
x = 5
if 0 < x and x < 10 or x == 20:  # (0 < x and x < 10) or x == 20
    print("x in (0,10) or exactly 20")

# Explicit parentheses for clarity — always preferred in complex conditions
if (0 < x < 10) or (x == 20):
    print("same, but clearer")
```

## 8. The Ternary Expression — `x if cond else y`

Python's ternary (conditional expression) puts the condition **in the middle**: `true_value if condition else false_value`. This ordering surprises programmers from C/Java (`cond ? a : b`).

```python
# Basic form: <value_if_true> if <condition> else <value_if_false>
age = 20
status = "adult" if age >= 18 else "minor"
print(status)  # adult

# Compare to if/else statement:
if age >= 18:
    status = "adult"
else:
    status = "minor"

# Ternary is an EXPRESSION — it returns a value and can be used anywhere
# As a function argument:
print("adult" if age >= 18 else "minor")

# In a list literal:
labels = ["even" if x % 2 == 0 else "odd" for x in range(5)]
print(labels)  # ['even', 'odd', 'even', 'odd', 'even']

# Nested ternary — legal but often unreadable:
score = 85
grade = "A" if score >= 90 else "B" if score >= 80 else "C" if score >= 70 else "F"
print(grade)  # B

# Chained ternary above is equivalent to:
if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
elif score >= 70:
    grade = "C"
else:
    grade = "F"
```

**Explanation:** The ternary is right-associative: `a if c1 else b if c2 else c` parses as `a if c1 else (b if c2 else c)`. Deeply nested ternaries should be rewritten as `if`/`elif`/`else` or `match` for readability.

### Realistic Ternary Examples

```python
# Example 1: Safe attribute access with default
user_input = ""
display = user_input if user_input else "(empty)"
print(display)  # (empty)

# Example 2: Pluralization
count = 1
print(f"{count} {'item' if count == 1 else 'items'}")    # 1 item
count = 5
print(f"{count} {'item' if count == 1 else 'items'}")    # 5 items

# Example 3: Clamping
value = 150
clamped = 100 if value > 100 else 0 if value < 0 else value
print(clamped)  # 100

# Example 4: Conditional assignment — very common
import os
env = os.getenv("ENV", "")
is_production = True if env == "production" else False
# Simpler — the comparison already returns a bool!
is_production = env == "production"  # no ternary needed when result is bool

# Example 5: Ternary in a return statement
def describe_number(n: int) -> str:
    return "zero" if n == 0 else "positive" if n > 0 else "negative"

# Example 6: Avoiding ternary when if/else is clearer
# Ternary with side effects — confusing:
print("yes") if condition else print("no")  # works but odd — use if/else statement
# Prefer:
if condition:
    print("yes")
else:
    print("no")
```

### Ternary Pitfalls

```python
# Pitfall: truthy/falsy confusion in the condition
# `x if x else y` uses truthiness, not `x is not None`
x = 0
result = "has value" if x else "no value"  # "no value" — 0 is falsy!
result = "has value" if x is not None else "no value"  # "has value" — correct if 0 valid

# Pitfall: operator precedence
# Ternary has LOWER precedence than `or`, `and`, and comparisons
# This:
value = a if condition else b or c  # parses as: a if condition else (b or c)
# If you meant:
value = (a if condition else b) or c  # need explicit parens

# Pitfall: trying to use statement keywords inside ternary
# This is illegal — `pass`, `break`, `continue`, `return` are statements, not expressions:
# x = pass if condition else 42  # SyntaxError
# Fix: use if/else statement for control-flow keywords
```

## 9. Guard Clauses — Flatten Your Logic

Deeply nested `if` blocks are hard to read. A **guard clause** inverts the condition and returns (or continues, breaks, raises) early, keeping the "happy path" at the lowest indentation level.

```python
# --- Nested (hard to follow) ---
def process_order(order):
    if order is not None:
        if order.items:
            if order.is_paid:
                if order.shipping_address:
                    ship(order)
                    return "shipped"
                else:
                    return "missing address"
            else:
                return "not paid"
        else:
            return "empty order"
    else:
        return "no order"

# --- Guard clauses (flat, readable) ---
def process_order(order):
    if order is None:
        return "no order"
    if not order.items:
        return "empty order"
    if not order.is_paid:
        return "not paid"
    if not order.shipping_address:
        return "missing address"

    ship(order)
    return "shipped"
```

**Explanation:** Each guard clause handles one failure mode and exits immediately. The reader can verify each precondition independently without tracking nesting depth. The main logic (`ship(order)`) sits at the base indentation — easy to find.

```python
# More guard clause examples

def calculate_discount(user, cart):
    """Calculate discount — demonstrates multiple guard patterns."""
    if user is None:
        raise ValueError("user is required")
    if not cart or not cart.items:
        return 0.0
    if user.is_banned:
        return 0.0
    if cart.total < 10:
        return 0.0  # minimum purchase

    # Happy path — only reached if all guards pass
    if user.is_premium:
        return cart.total * 0.2
    if user.loyalty_years >= 5:
        return cart.total * 0.15
    return cart.total * 0.05


def handle_request(request):
    """Guard clauses in a request handler."""
    if request is None:
        return {"error": "no request"}, 400
    if request.method != "POST":
        return {"error": "method not allowed"}, 405
    if not request.json:
        return {"error": "missing body"}, 400
    if "email" not in request.json:
        return {"error": "email required"}, 422

    # All preconditions met — process normally
    return create_user(request.json)


# Guard clause with `continue` inside loops (see 3.2)
for user in users:
    if not user.is_active:
        continue  # skip inactive users — guard
    if user.is_banned:
        continue  # skip banned — guard
    process(user)  # only active, non-banned users reach here

# Guard clause with `raise`
def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b
```

### When NOT to Use Guard Clauses

- If the function is short (3–5 lines) and has only one condition, a simple `if`/`else` may be clearer.
- If both branches are equally important (no single "happy path"), `if`/`else` communicates the symmetry better.
- Do not use guard clauses that duplicate expensive checks.

## 10. PEP 8 Style for Conditionals

### Line Length and Multi-line Conditions

When a condition exceeds the line length limit (conventionally 88–100 characters), break it using parentheses — Python's implicit line continuation inside brackets.

```python
# --- Bad: long line ---
if user.is_authenticated and user.has_permission("admin") and request.method == "POST" and request.json is not None:
    handle_admin_post(request)

# --- Good: parenthesized multi-line ---
if (
    user.is_authenticated
    and user.has_permission("admin")
    and request.method == "POST"
    and request.json is not None
):
    handle_admin_post(request)

# Alternative: extract to a variable for readability
is_admin_post = (
    user.is_authenticated
    and user.has_permission("admin")
    and request.method == "POST"
)
if is_admin_post and request.json is not None:
    handle_admin_post(request)

# Backslash continuation — legal but DISCOURAGED (fragile, whitespace-sensitive)
if user.is_authenticated and \
   user.has_permission("admin"):
    pass
```

### Yoda Conditions — Don't

```python
# Yoda condition (common in C to avoid =/== typo) — unpythonic in Python
if 42 == x:          # confusing to read
    print("x is 42")

if "hello" == name:  # no benefit in Python — `=` vs `==` typo raises SyntaxError anyway
    print("hi")

# Pythonic:
if x == 42:
    print("x is 42")
if name == "hello":
    print("hi")
```

### Comparing to `None`, `True`, `False`

Per PEP 8:

```python
# --- Correct ---
if x is None:
    pass
if x is not None:
    pass

# --- Wrong (works but violates PEP 8) ---
if x == None:       # use `is` for None
    pass
if x == True:       # use `if x:` or `if x is True:` (rare)
    pass

# Truthiness checks:
if items:           # preferred — checks non-empty
    pass
if not items:
    pass

# NOT:
if len(items) > 0:      # redundant — `if items:` is idiomatic
    pass
if len(items) == 0:     # redundant — `if not items:`
    pass
if items != []:         # creates a new list just to compare — wasteful
    pass
```

### Compound Conditions — Extract Helpers

```python
# Hard to read:
if (user.age >= 18 and user.has_verified_email and not user.is_banned) or (
    user.is_admin and request.headers.get("X-Override") == "true"
):
    grant_access()

# Better: extract predicates
def can_access(user, request) -> bool:
    is_eligible_user = user.age >= 18 and user.has_verified_email and not user.is_banned
    is_admin_override = user.is_admin and request.headers.get("X-Override") == "true"
    return is_eligible_user or is_admin_override

if can_access(user, request):
    grant_access()
```

**Explanation:** Named booleans and helper functions turn complex boolean logic into self-documenting code. They are also independently testable.

## 11. Advanced and Subtle Behaviors

### Assignment in Conditionals — The Walrus Operator (`:=`)

Python 3.8+ allows assignment *inside* an expression via `:=` (the "walrus" operator, because `:=` looks like walrus eyes and tusks). It assigns and returns the value, so you can test it in the same `if`.

```python
# Without walrus — redundant computation or extra lines
data = input("Enter something: ")
if data:
    print(f"You entered: {data}")

# With walrus — assign and test in one line
if data := input("Enter something: "):
    print(f"You entered: {data}")

# Realistic: avoid calling an expensive function twice
def fetch_user(user_id):
    # ... database lookup ...
    return {"name": "Alice"} if user_id == 1 else None

# Without walrus:
user = fetch_user(1)
if user:
    print(f"Found {user['name']}")

# With walrus — eliminates the separate assignment line
if user := fetch_user(1):
    print(f"Found {user['name']}")

# Walrus in elif chain — each branch binds a different value
import re

text = "order-12345-confirmed"
if m := re.search(r"order-(\d+)", text):
    print(f"Order number: {m.group(1)}")
elif m := re.search(r"invoice-(\d+)", text):
    print(f"Invoice number: {m.group(1)}")
else:
    print("No match")

# Caveat: walrus has lower precedence than `,` — use parens in some contexts
# This does NOT do what it looks like:
# if x := 3, 4:  # SyntaxError or unexpected tuple
# Correct:
if (x := 3):
    print(x)
```

**Explanation:** The walrus is ideal when you need the value both for the condition test and for the body. Do not overuse it — if the assignment makes the condition hard to read, a separate line is better.

### `if` Without `else` Returns Nothing (Statement vs. Expression)

```python
# `if` is a STATEMENT — it does not produce a value
result = if True: 42  # SyntaxError — cannot assign a statement

# The ternary IS an expression — it produces a value
result = 42 if True else 0  # OK

# Common mistake: trying to use `if` where an expression is needed
# Bad:
# values = [if x > 0: x else: 0 for x in numbers]  # SyntaxError

# Good:
values = [x if x > 0 else 0 for x in numbers]

# Lambda can only contain expressions — use ternary, not if/else statement
key = lambda x: "positive" if x > 0 else "non-positive"
# NOT:
# key = lambda x: if x > 0: "positive" else: "non-positive"  # SyntaxError
```

### Mutable Default Gotcha in Conditional Initialization

```python
# Bug: conditional init with mutable default
def add_item(item, items=None):
    # Correct pattern — None sentinel
    if items is None:
        items = []
    items.append(item)
    return items

print(add_item("a"))        # ['a']
print(add_item("b"))        # ['b'] — independent list, not ['a', 'b']

# Bug version — shared mutable default:
def add_item_bug(item, items=[]):
    items.append(item)
    return items

print(add_item_bug("a"))    # ['a']
print(add_item_bug("b"))    # ['a', 'b'] — same list object!

# Safe inline conditional init for dicts
config = existing_config if existing_config is not None else {}
```

### `elif` vs. Multiple `if` — Semantics Differ

```python
x = 15

# Multiple `if` — EVERY condition is checked, multiple blocks can execute
if x > 10:
    print("greater than 10")
if x > 5:
    print("greater than 5")
if x > 0:
    print("greater than 0")
# Prints all three lines

# `elif` chain — stops at FIRST match
if x > 10:
    print("greater than 10")
elif x > 5:
    print("greater than 5")  # skipped — first branch already matched
elif x > 0:
    print("greater than 0")  # skipped
# Prints only "greater than 10"

# Rule: use `elif` when branches are mutually exclusive;
# use separate `if` when multiple conditions can hold simultaneously
```

## 12. Common Mistakes and How to Fix Them

| Mistake | Why it fails | Fix |
|---|---|---|
| `if x = 5:` | `=` is assignment, not comparison — `SyntaxError` | `if x == 5:` or `if x := 5:` (walrus) |
| `if x == True:` | Conflates `1` with `True`, fails for truthy non-bools | `if x:` or `if x is True:` (if strict) |
| `if my_list == []:` | Works but creates garbage list, unpythonic | `if not my_list:` |
| `if x is 5:` | `is` compares identity — may fail for larger ints | `if x == 5:` |
| `if a < b < c:` expecting `(a<b)<c` | Misunderstanding chaining — actually correct chaining, but if you expected C behavior you will be confused | Know that Python chains; use `(a < b) < c` if you truly want bool-vs-int |
| `if x == None:` | PEP 8 violation — `None` is a singleton | `if x is None:` |
| `if not x is None:` | Works but reads poorly, `not` precedence | `if x is not None:` |
| Missing colon | `SyntaxError` | Add `:` at end of `if`/`elif`/`else` line |
| Inconsistent indentation | `IndentationError` / `TabError` | Use 4 spaces consistently |

```python
# Mistake: `is` with literals — fragile due to interning
x = 1000
y = 1000
print(x is y)   # False — larger ints not interned (CPython detail, not guaranteed)
print(x == y)   # True — correct

# Mistake: `=` vs `==` — Python catches this, unlike C
# if x = 5:  # SyntaxError: invalid syntax. Maybe you meant '==' or ':=' ?
# Python's error message even suggests the fix!

# Mistake: falsy valid value treated as missing
def greet(name):
    if not name:  # "" is valid? Or should it trigger default?
        name = "Guest"
    return f"Hello, {name}"

print(greet(""))     # Hello, Guest — maybe wrong if "" was intentional
print(greet(None))   # Hello, Guest — correct for None

# Better when "" and None mean different things:
def greet_strict(name):
    if name is None:
        name = "Guest"
    return f"Hello, {name}"

print(greet_strict(""))    # Hello,  — preserves empty string
print(greet_strict(None))  # Hello, Guest
```

## 13. Putting It All Together — Realistic Example

```python
from dataclasses import dataclass
from typing import Optional


@dataclass
class Order:
    id: int
    total: float
    is_paid: bool
    coupon: Optional[str] = None
    items: list = None

    def __post_init__(self):
        if self.items is None:
            self.items = []


def calculate_final_total(order: Optional[Order]) -> float:
    """Calculate the final total with discounts — showcases all conditional idioms."""

    # Guard clauses — fail fast
    if order is None:
        raise ValueError("order must not be None")
    if not order.items:
        raise ValueError("order has no items")
    if order.total < 0:
        raise ValueError(f"negative total: {order.total}")

    # Chained comparison for range validation
    if not 0 < order.total < 1_000_000:
        raise ValueError(f"total out of range: {order.total}")

    # Identity check for None, not truthiness — "" is a different coupon than None
    if order.coupon is None:
        has_coupon = False
        discount_rate = 0.0
    elif not order.coupon.strip():
        # Coupon is "" or whitespace — treat as no coupon, but warn
        print(f"Warning: order {order.id} has empty coupon string")
        has_coupon = False
        discount_rate = 0.0
    elif order.coupon == "SAVE20":
        has_coupon = True
        discount_rate = 0.20
    elif order.coupon == "SAVE10":
        has_coupon = True
        discount_rate = 0.10
    else:
        print(f"Warning: unknown coupon '{order.coupon}' — no discount")
        has_coupon = False
        discount_rate = 0.0

    # Ternary for conditional suffix
    coupon_msg = f" (coupon {order.coupon})" if has_coupon else ""

    # Short-circuit: only apply discount if paid
    # `and` returns the discount amount or 0.0
    discount = order.total * discount_rate if order.is_paid else 0.0

    final = order.total - discount

    # Walrus: compute and test in one line
    if (savings := order.total - final) > 0:
        print(f"Order {order.id}: saved ${savings:.2f}{coupon_msg}")

    # Ternary in f-string for status
    status = "PAID" if order.is_paid else "UNPAID"
    print(f"Order {order.id} [{status}]: ${final:.2f}")

    return final


# Demo
orders = [
    Order(id=1, total=100.0, is_paid=True, coupon="SAVE20", items=["widget"]),
    Order(id=2, total=50.0, is_paid=False, coupon="SAVE20", items=["gadget"]),
    Order(id=3, total=75.0, is_paid=True, coupon=None, items=["thing"]),
    Order(id=4, total=200.0, is_paid=True, coupon="  ", items=["stuff"]),
]

for o in orders:
    calculate_final_total(o)
    print("---")
```

**Explanation:** This example weaves together guard clauses (`is None`, `not items`), chained comparisons (`0 < total < 1_000_000`), `is None` vs. truthiness (`coupon is None` vs. `not coupon.strip()`), `elif` chains, ternary expressions, short-circuit logic, and the walrus operator — all in a realistic order-processing context.

## 14. Quick Reference

```python
# ─── Basic conditionals ───
if condition:
    ...
elif other_condition:
    ...
else:
    ...

# ─── Truthiness ───
if items:               # non-empty?
if not items:           # empty?
if x is None:           # specifically None?
if x is not None:       # not None? (0 and "" pass this)

# ─── Chained comparisons ───
if 0 < x < 100:         # 0 < x and x < 100, x evaluated once
if 0 <= x <= 100:       # inclusive
if a == b == c:         # all equal

# ─── Equality vs identity ───
a == b                  # equal value?
a is b                  # same object?
a is None               # is None? (correct)
a == None               # works but PEP 8 violation

# ─── Ternary ───
value = a if condition else b
status = "yes" if x else "no"

# ─── Short-circuit ───
value = x or default    # default if x falsy (careful if 0/"" valid)
value = x if x is not None else default  # safe default
if a and b:             # b not evaluated if a falsy
if a or b:              # b not evaluated if a truthy

# ─── Guard clauses ───
def func(x):
    if x is None:
        return
    if not x:
        return default
    # happy path — no nesting
    ...

# ─── Walrus in conditionals ───
if (m := re.search(pattern, text)):
    print(m.group(1))
```

## 15. Preview: Where `match` Fits

Python 3.10 introduced `match`/`case` (structural pattern matching, covered in 3.3). It often replaces long `if`/`elif` chains that dispatch on the *shape* or *type* of data. A taste:

```python
# if/elif dispatch — works but verbose
def handle(value):
    if isinstance(value, int):
        print(f"integer {value}")
    elif isinstance(value, str):
        print(f"string {value}")
    elif isinstance(value, list) and len(value) == 0:
        print("empty list")
    else:
        print("unknown")

# match/case — cleaner for structural dispatch (full details in 3.3)
def handle(value):
    match value:
        case int(n):
            print(f"integer {n}")
        case str(s):
            print(f"string {s}")
        case []:
            print("empty list")
        case _:
            print("unknown")
```

For simple boolean conditions, `if`/`elif`/`else` remains the right tool. Reach for `match` when you are destructuring data, matching types, or branching on structure rather than on boolean predicates.
