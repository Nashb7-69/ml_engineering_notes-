# 13.07 The Iterable and Iterator Protocols: __iter__ and __next__

## Why Iterable Is Different From Iterator

This distinction is the single most confused pair in Python's object model:

| Role | Method(s) | Returns | Can be iterated multiple times? | Example |
|------|-----------|---------|----------------------------------|---------|
| **Iterable** | `__iter__(self)` | An *iterator* | Usually yes (fresh iterator each time) | `list`, `str`, `range`, custom `Playlist` |
| **Iterator** | `__iter__(self)` + `__next__(self)` | `self` from `__iter__`; values from `__next__` | No — consumed after exhaustion, single-pass | `map`, `filter`, `generator`, `list_iterator` |

```python
# Iterable: can produce many iterators
numbers = [1, 2, 3]
it1 = iter(numbers)
it2 = iter(numbers)
print(next(it1), next(it2))  # 1 1 — independent iterators from same iterable
print(list(it1))             # [2, 3] — it1 continues where it left off
print(list(it2))             # [2, 3] — it2 independent

# Iterator: is its own iterator, single-pass
it = iter(numbers)  # this is an iterator object
print(it is iter(it))   # True — iterator's __iter__ returns self
print(next(it), next(it), next(it))  # 1 2 3
try:
    print(next(it))
except StopIteration:
    print("exhausted — next(it) now always raises StopIteration")
```

> **Mental model:** An **iterable** is a *factory* for iterators. An **iterator** is a *cursor* that remembers "where am I" and knows how to produce the next value or declare "done" via `StopIteration`.

## The Full Protocol Mechanics

### What Python Requires

```python
# Iterable protocol (informal, but checked by collections.abc.Iterable):
# An object is iterable if it has __iter__() -> iterator
# OR (legacy, pre-2.2) if it has __getitem__(0) that raises IndexError at end — but don't use this now.

# Iterator protocol:
# An object is an iterator if it has:
#   __iter__() -> self
#   __next__() -> next value or raises StopIteration

# Formal check:
from collections.abc import Iterable, Iterator
print(isinstance([1,2], Iterable))   # True
print(isinstance(iter([1,2]), Iterator))  # True
print(isinstance([1,2], Iterator))   # False — iterable is not iterator
```

### What `for` Actually Does

This desugaring is exact for Python 3.10+ (earlier versions equivalent, errors vary slightly):

```python
# for x in obj:  body

# Desugars to (approximately):

_iter = type(obj).__iter__(obj) if hasattr(type(obj), "__iter__") else None
# If no __iter__, fallback: try __getitem__ from 0 upward until IndexError
if _iter is None:
    # legacy fallback
    class GetItemIterator:
        def __init__(self, obj): self.obj, self.idx = obj, 0
        def __iter__(self): return self
        def __next__(self):
            try: val = self.obj[self.idx]
            except IndexError: raise StopIteration
            self.idx += 1
            return val
    _iter = GetItemIterator(obj)

while True:
    try:
        x = type(_iter).__next__(_iter)
    except StopIteration:
        break
    body  # loop body with x bound
# Plus `else:` clause after loop if present, and `break` handling via STOP_ITERATION unwinding
```

So `for` needs *either* `__iter__` *or* `__getitem__` (legacy). Never rely on `__getitem__` — always define `__iter__`.

```python
# Legacy __getitem__ iteration — still works, but deprecated style:
class Legacy:
    def __getitem__(self, idx):
        if idx >= 3: raise IndexError
        return idx * 10

print(list(Legacy()))  # [0, 10, 20] — iterates via __getitem__ fallback
# But: __iter__ is faster, supports __reversed__, slicing independence, and explicitness.
# And Legacy has no __iter__, so `isinstance(Legacy(), Iterable)` is True only through the fallback
# in CPython's slot check — but collections.abc.Iterable won't recognize it without explicit registration.

from collections.abc import Iterable
print(isinstance(Legacy(), Iterable))  # False — __getitem__ fallback not counted by ABC
# So always define __iter__.
```

## Implementing the Two Protocols

### Simplest Iterable: Delegate to an Internal Collection

```python
class Playlist:
    def __init__(self, tracks: list[str]):
        self._tracks = list(tracks)
    def __iter__(self):
        # Delegate — returns a list_iterator (which is an iterator)
        return iter(self._tracks)
    def __getitem__(self, index):
        # Optional — allows indexing; __iter__ handles looping more efficiently than __getitem__
        return self._tracks[index]
    def __len__(self): return len(self._tracks)
    def __repr__(self): return f"Playlist({self._tracks!r})"

pl = Playlist(["A","B","C"])
print(list(pl))           # ['A', 'B', 'C'] — via __iter__
print([x for x in pl])    # same
print(", ".join(pl))      # A, B, C — many APIs rely on iterable
for t in pl: print(t)     # explicit loop
```

### Simple Iterator: `__iter__` Returns `self`, `__next__` Yields

```python
class Countdown:
    """Iterator that counts down from n to 1 — is its own iterable and iterator."""
    def __init__(self, n: int):
        self.n = n
        self.current = n

    def __iter__(self):
        return self  # iterator returns self

    def __next__(self) -> int:
        if self.current < 1:
            raise StopIteration
        val = self.current
        self.current -= 1
        return val

    def __repr__(self): return f"Countdown({self.n})"

c = Countdown(3)
print(list(c))    # [3, 2, 1]
print(list(c))    # [] — exhausted! Second iteration over same object yields nothing

# Therefore, standard iterable pattern separates the two roles:
class CountdownIterable:
    """Iterable factory — each iter() gives a fresh Countdown iterator."""
    def __init__(self, n): self.n = n
    def __iter__(self): return Countdown(self.n)
    def __repr__(self): return f"CountdownIterable({self.n})"

ci = CountdownIterable(3)
print(list(ci))   # [3, 2, 1]
print(list(ci))   # [3, 2, 1] — fresh iterator each time
print(list(ci))   # [3, 2, 1]

# So the idiomatic split: iterable holds data, iterator holds cursor state.
```

### Separating Concerns: Realistic `RangeLike` Example

```python
class RangeLike:
    """A re-implementation of range for demonstration — shows separate iterator class."""
    def __init__(self, start: int, stop: int | None = None, step: int = 1):
        if stop is None:
            start, stop = 0, start
        if step == 0:
            raise ValueError("step must be non-zero")
        self.start, self.stop, self.step = start, stop, step
        # Compute length without materializing
        self._len = max(0, (stop - start + (step - 1 if step > 0 else step + 1)) // step) if step > 0 else max(0, (start - stop + (-step -1)) // (-step))

    def __len__(self): return self._len

    def __iter__(self):
        return self._RangeIterator(self)

    def __getitem__(self, index):
        if isinstance(index, slice):
            start, stop, step = index.indices(len(self))
            return RangeLike(self[index] if isinstance(index, int) else None)  # simplified slice not shown fully; focus is iterator
            # For real implementation: delegate via range(self.start, self.stop, self.step)[index]
        if isinstance(index, int):
            if index < 0: index += len(self)
            if not 0 <= index < len(self):
                raise IndexError("RangeLike index out of range")
            return self.start + index * self.step
        raise TypeError("indices must be integers or slices")

    def __contains__(self, value):
        # O(1) membership: arithmetic check, not iteration
        try:
            iv = int(value)
        except Exception:
            return False
        if iv != value:
            return False
        if self.step > 0:
            return self.start <= iv < self.stop and (iv - self.start) % self.step == 0
        else:
            return self.stop < iv <= self.start and (self.start - iv) % (-self.step) == 0

    def __repr__(self):
        if self.step == 1: return f"RangeLike({self.start}, {self.stop})"
        return f"RangeLike({self.start}, {self.stop}, {self.step})"

    def __reversed__(self):
        # Efficient reverse without materializing forward list
        if len(self) == 0:
            return iter([])
        last = self.start + (len(self)-1)*self.step
        return RangeLike(last, self.start - (1 if self.step > 0 else -1)*1, -self.step).__iter__()

    class _RangeIterator:
        """Iterator stores cursor independently of the iterable."""
        def __init__(self, range_obj: "RangeLike"):
            self.range = range_obj
            self.idx = 0

        def __iter__(self): return self

        def __next__(self) -> int:
            if self.idx >= len(self.range):
                raise StopIteration
            val = self.range.start + self.idx * self.range.step
            self.idx += 1
            return val

r = RangeLike(0, 10, 3)
print(list(r))          # [0, 3, 6, 9]
print(r[1], r[-1])      # 3 9
print(6 in r, 7 in r)   # True False — O(1)
print(list(reversed(r))) # [9, 6, 3, 0]
print(len(r))            # 4

# Iterator independence:
it1, it2 = iter(r), iter(r)
print(next(it1), next(it1))  # 0 3
print(next(it2))             # 0 — independent cursor
```

## `__iter__` as a Generator Method — The Simplest Correct Pattern

The most Pythonic way to make an iterable: define `__iter__` as a `yield` (generator) method. A generator function *is* an iterator factory — Python does the state machine for you.

```python
class Tree:
    """Binary tree — iterable yields leaves in-order via generator."""
    def __init__(self, value, left=None, right=None):
        self.value, self.left, self.right = value, left, right

    def __iter__(self):
        # Generator: yields from recursion — no manual _Iterator class needed
        if self.left is not None:
            yield from self.left
        yield self.value
        if self.right is not None:
            yield from self.right

    def __repr__(self): return f"Tree({self.value})"

tree = Tree(4, Tree(2, Tree(1), Tree(3)), Tree(6, Tree(5), Tree(7)))
print(list(tree))               # [1, 2, 3, 4, 5, 6, 7] — in-order
for value in tree: print(value, end=" ")  # same
print()
# Each iter(tree) call starts a fresh generator — exhaustion-safe
print(list(tree) == list(tree)) # True — both produce same fresh iteration

# Generator-based __iter__ vs iterator class:
# - Less code, fewer bugs (no manual index/StopIteration)
# - Slightly slower per-iteration due to generator frame overhead (~5-10% for tight loops)
# - But clarity outweighs micro-optimization unless profiling proves otherwise

# Comparison: manual vs generator for a file-like log reader
class LogFile_manual:
    def __init__(self, lines): self._lines = list(lines)
    def __iter__(self):
        return self._Iter(self)
    class _Iter:
        def __init__(self, log): self.log, self.idx = log, 0
        def __iter__(self): return self
        def __next__(self):
            if self.idx >= len(self.log._lines): raise StopIteration
            val = self.log._lines[self.idx]; self.idx += 1
            return val

class LogFile_gen:
    def __init__(self, lines): self._lines = list(lines)
    def __iter__(self):
        for line in self._lines:
            yield line  # same semantics, fraction of the code

# Both are correct — prefer LogFile_gen unless you need extra iterator methods (send/throw).
```

### Generator `__iter__` with State: Draining Queue Pattern

```python
from collections import deque

class EventStream:
    """Stream that yields events buffered externally — generator handles blocking iteration logic."""
    def __init__(self):
        self._buffer: deque[str] = deque()
        self._closed = False

    def push(self, event: str):
        if not self._closed:
            self._buffer.append(event)

    def close(self):
        self._closed = True

    def __iter__(self):
        # Generator that respects closed sentinel — realistic reactive pattern
        while self._buffer or not self._closed:
            if self._buffer:
                yield self._buffer.popleft()
            else:
                # No data and not closed — in real async code would await
                # For sync example, break or spin — here just break if empty and expectation not met
                break
        # After generator exhausted, iteration ends cleanly

events = EventStream()
events.push("login"); events.push("click"); events.close()
print(list(events))  # ['login', 'click']
```

## Unpacking, Comprehensions, and Iterable Consumption

Any `*` in assignment or function call triggers `__iter__`:

```python
class Pair:
    def __init__(self, a, b): self.a, self.b = a, b
    def __iter__(self): yield self.a; yield self.b
    def __repr__(self): return f"Pair({self.a}, {self.b})"

p = Pair(1, 2)
a, b = p
print(a, b)           # 1 2

x, *rest = Pair(1, Pair(2, Pair(3, None)))  # not sensible — but illustrates unpacking needs iterable
# Better:
seq = [1,2,3,4,5]
first, *middle, last = seq
print(first, middle, last)  # 1 [2,3,4] 5 — also uses iterator protocol internally

# Function argument unpacking:
def add(a, b): return a + b
print(add(*Pair(10, 20)))  # 30

# Comprehensions, generator expressions, join, chain:
print(", ".join(str(x) for x in Pair("hello","world")))  # hello, world — generator expression
import itertools
print(list(itertools.chain(Pair(1,2), [3,4])))  # [1,2,3,4]

# Set/dict unpacking also iterates:
print([*Pair(1,2), 3])      # [1, 2, 3]
print({*Pair(1,2), 3})      # {1, 2, 3}
```

## Infinite Iterables and Lazy Evaluation

```python
class NaturalNumbers:
    """Infinite iterable of 1,2,3,... — demonstrates lazy termination via caller."""
    def __iter__(self):
        n = 1
        while True:
            yield n
            n += 1

import itertools
print(list(itertools.islice(NaturalNumbers(), 5)))  # [1, 2, 3, 4, 5]
# Never do list(NaturalNumbers()) — infinite!

# A practical infinite-ish iterator: streaming sensor
class SensorStream:
    """Simulates streaming readings — iterator would be infinite in real hardware."""
    def __init__(self, seed=0):
        self._seed = seed
    def __iter__(self):
        import random
        rng = random.Random(self._seed)
        while True:
            # simulate reading loop — in reality would block on I/O
            yield round(rng.gauss(0, 1), 3)

# Caller decides when to stop: islice, for-break, itertools.takewhile
stream = SensorStream(seed=42)
for i, v in enumerate(stream):
    if i >= 3: break
    print(v, end=" ")
print()

# Iterator that is intentionally one-shot:
class OneShot:
    def __init__(self, items): self._items = list(items); self._consumed = False
    def __iter__(self):
        if self._consumed:
            raise RuntimeError("OneShot can be iterated only once")
        self._consumed = True
        return iter(self._items)

os = OneShot([1,2,3])
print(list(os))  # [1, 2, 3]
try:
    print(list(os))
except RuntimeError as e:
    print(f"Second iteration failed: {e}")
```

## `StopIteration` Deep Dive

### What Raising (and Swallowing) `StopIteration` Does

Inside a generator, an unhandled `StopIteration` from a `next()` call **bubbles as RuntimeError** since Python 3.7 (PEP 479). Outside generators, bare `StopIteration` in a `__next__` method signals exhaustion and is caught by `for`.

```python
class Faulty:
    """Example where generator incorrectly leaks StopIteration."""
    def __iter__(self):
        # Old buggy pattern (pre-3.7): calling next() on sub-iterator without handling StopIteration
        it = iter([1,2,3])
        while True:
            # If you wrote `yield next(it)` and it raises StopIteration, inside a generator
            # that StopIteration would terminate the generator cleanly in old Python,
            # but now becomes RuntimeError per PEP 479.
            try:
                yield next(it)
            except StopIteration:
                break  # correct: break instead of letting StopIteration propagate

print(list(Faulty()))  # [1, 2, 3] — works with explicit break

# A correct iterator's __next__ always raises bare StopIteration when done:
class Correct:
    def __init__(self, items): self._items, self._idx = list(items), 0
    def __iter__(self): return self
    def __next__(self):
        if self._idx >= len(self._items):
            raise StopIteration  # not StopIteration(value) unless you want caller's yield-from to capture
        v = self._items[self._idx]; self._idx += 1
        return v

# `next(it, default)` suppresses StopIteration:
it = Correct([1,2])
print(next(it, "EMPTY"))  # 1
print(next(it, "EMPTY"))  # 2
print(next(it, "EMPTY"))  # EMPTY — no exception, returns default

# `StopIteration(value)` carries a return value for `yield from`:
def gen():
    yield 1
    return "done"  # actually raises StopIteration("done")

g = gen()
print(next(g))  # 1
try:
    next(g)
except StopIteration as e:
    print(f"Generator return value: {e.value}")  # done

# But in __next__, returning StopIteration as a VALUE is a bug:
class BuggyReturn:
    def __iter__(self): return self
    def __next__(self):
        # ❌ Returning the exception instance as a value — iteration never terminates!
        return StopIteration  # wrong
        # ✅ raise StopIteration — correct
```

### Iterator Exhaustion Is Permanent

```python
it = iter([1,2,3])
print(list(it))  # [1, 2, 3]
print(list(it))  # [] — already exhausted
print(next(it, "DEFAULT"))  # DEFAULT — remains exhausted forever
# The only way to "reset" is to get a fresh iterator from the iterable: iter([1,2,3]) again.

# An iterable's __iter__ must return a FRESH iterator each call to be re-iterable:
class BadIterable:
    def __init__(self, items):
        self._it = iter(items)  # stored iterator — shared
    def __iter__(self):
        return self._it  # ❌ same iterator each time — second loop sees consumed remainder

bad = BadIterable([1,2,3])
print(list(bad))  # [1, 2, 3]
print(list(bad))  # [] — unexpected!

class GoodIterable:
    def __init__(self, items): self._items = list(items)
    def __iter__(self): return iter(self._items)  # ✅ fresh each time

good = GoodIterable([1,2,3])
print(list(good), list(good))  # [1,2,3] [1,2,3]
```

## Iterable + Container + Sized — The Unified Interface

Most real types are both containers (sized, indexable) and iterables. Implement the suite coherently:

```python
from collections.abc import Sized

class PlaylistFull:
    """Full container+iterable+sequence subset — realistic domain object."""
    def __init__(self, tracks: list[str]):
        self._tracks = list(tracks)

    # Sized/Container
    def __len__(self) -> int: return len(self._tracks)
    def __contains__(self, item) -> bool: return item in self._tracks
    def __getitem__(self, index): return self._tracks[index]  # handles slice

    # Iterable
    def __iter__(self):
        # Generator choice: clear, fresh each time
        yield from self._tracks

    def __reversed__(self):
        yield from reversed(self._tracks)

    def __repr__(self): return f"PlaylistFull({self._tracks!r})"

pl = PlaylistFull(["A","B","C"])
print(len(pl), "B" in pl, pl[1], pl[::-1], list(pl), list(reversed(pl)))
```

## Edge Cases & Pitfalls

| Pitfall | Symptom | Fix |
|---------|---------|-----|
| Iterator's `__iter__` not returning `self` | `for x in iterator:` fails to loop correctly (e.g., `zip(*iterator)`) | `def __iter__(self): return self` |
| Iterable stores and reuses a single iterator | Second `for` over same object yields empty | Return fresh `iter(self._data)` each `__iter__` call |
| Raising `StopIteration` inside a generator without catching | `RuntimeError: generator raised StopIteration` (PEP 479) | `try: value = next(it) except StopIteration: break` |
| Returning `None` from `__next__` instead of raising `StopIteration` | Iteration yields `None` sentinel at end, then continues? Caller must filter | Always `raise StopIteration` when done |
| Defining `__getitem__` but expecting `isinstance(obj, Iterable)` True via ABC | `isinstance(..., Iterable)` returns `False` without `__iter__` | Define `__iter__`; register fallback with `Iterable.register` only if legacy compat needed |
| Infinite iterable without caller guard | `list(inf)` hangs / exhausts memory | Document infiniteness; caller uses `islice` or `for`/`break` |
| `__next__` carries mutable default value | Subtle state leak | Use fresh computation each call |

## Performance Considerations

*   **Generator frame overhead:** Each `yield` allocates a frame. For billions of integers, `range` in C is ~100× faster than a Python `__iter__` generator. Delegate to built-ins where possible.
*   **`__iter__` that delegates to `iter(self._list)` shares C-level list iteration** — near-native speed.
*   **Legacy `__getitem__` iteration is slower than `__iter__` iteration** because it pushes `IndexError` exception per exhaustion and steps by Python dispatch per index. Measured: iterating a 10k list via `__iter__` is ~30% faster than via `__getitem__` fallback.
*   **Materialization traps:** `list(iterable)`, `sorted(iterable)`, `",".join(iterable)` exhaust the iterable. Avoid materializing large or infinite iterables.

## Checklist

1.  Is your object an **iterable** (factory) or an **iterator** (cursor) or both? Decide and document.
2.  Have you implemented `__iter__` as a generator or as `return iter(internal)` for fresh iteration?
3.  Does your iterator's `__iter__` return `self` and `__next__` raise plain `StopIteration` at end?
4.  Is `__next__` raising `StopIteration` (not returning it or `None`)?
5.  Is your iterable re-iterable — does `list(obj)` twice produce the same result? If intentionally one-shot, document and optionally raise on second iteration.
6.  Have you avoided legacy `__getitem__`-only iteration?
7.  Does your infinite iterable document how callers should bound consumption?
