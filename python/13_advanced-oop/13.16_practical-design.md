# 13.16 Practical OOP Design: Putting It All Together

## From Procedural to Domain Objects — Why We Design

A program starts as a script:

```python
# Procedural draft — a banking ledger as loose functions + dicts
balances = {}           # account_id -> cents
transactions = []       # list of dicts

def create_account(aid, owner): balances[aid] = 0
def deposit(aid, cents): balances[aid] += cents; transactions.append({"type":"deposit","aid":aid,"cents":cents})
def withdraw(aid, cents):
    if balances[aid] < cents: raise ValueError("insufficient")
    balances[aid] -= cents; transactions.append({"type":"withdraw","aid":aid,"cents":cents})

create_account("A1", "Alice")
deposit("A1", 10_000)
withdraw("A1", 2_500)
print(balances, transactions)
```

It works. Then the rules compound: currency per account, overdraft, statement formatting, equality of transactions, ledger sorting by date, persistent identities, API for inventory or e-commerce. Loose dicts pass bugs by construction; there is no place to attach invariants, representations, or protocols. Object orientation is not dogma — it is the disciplined move from *implicit conventions* to *encapsulated contracts*.

This capstone walks a domain model (banking *and* inventory) through iterative design: procedural → basic OOP → Pythonic protocol-rich OOP (using lessons **13.01–13.15** deliberately) → layered architecture with SOLID, composition, and testing.

## 1. The Evolving Example — Banking Domain (Primary Narrative)

### Iteration 0 → 1: Packaging State and Behavior

```python
# Procedural iteration 1: wrap mutable maps into a class — already gains names and invariant guard points
from datetime import datetime, timezone

class AccountV1:
    def __init__(self, account_id: str, owner: str, currency: str = "USD"):
        if not account_id: raise ValueError("account_id required")
        self.account_id, self.owner, self.currency = account_id, owner, currency
        self.balance_cents: int = 0
        self.transactions: list[dict] = []

    def deposit(self, cents: int):
        if cents <= 0: raise ValueError("positive cents required")
        self.balance_cents += cents
        self.transactions.append({"type": "deposit", "cents": cents, "at": datetime.now(timezone.utc)})

    def withdraw(self, cents: int):
        if cents <= 0: raise ValueError("positive cents required")
        if self.balance_cents < cents:
            raise ValueError("insufficient funds")
        self.balance_cents -= cents
        self.transactions.append({"type": "withdraw", "cents": cents, "at": datetime.now(timezone.utc)})

    def transfer(self, other: "AccountV1", cents: int):
        # Transfer withdraws from self, deposits to other — but bugs if deposit after withdraw fails? (no rollback)
        self.withdraw(cents)
        other.deposit(cents)

a = AccountV1("A1","Alice")
b = AccountV1("A2","Bob")
a.deposit(10_000)
a.transfer(b, 2_500)
print(a.balance_cents, b.balance_cents)  # 7500 2500
print(a.transactions[0])
```

**Deficiencies of V1:**

*   Dict transactions — string keys not typo-proof; no `repr`/`eq`/`order`
*   Currency not enforced — USD account could deposit EUR cents silently
*   `transfer` not transactional — partial failure leaves inconsistent ledger
*   Polluting mutable list returned by reference — caller can `account.transactions.append(...)` raw
*   No protocol: `Account` not iterable over transactions, no `len(account)` semantically, no equality by id vs value confusion, no formatting hook for statements

### Iteration 1 → 2: Domain Primitives and Encapsulation

Introduce value types: `Money` (immutable, hashable, currency-checked) and `Transaction` (frozen, hashable for deduplication, ordering by timestamp, `repr`/`str`/`format`).

```python
from __future__ import annotations
from dataclasses import dataclass, field
from datetime import datetime, timezone
from decimal import Decimal
from typing import Literal

# Money as immutable value type — shares 13.03/13.04/13.12 patterns
@dataclass(frozen=True, slots=True, order=True)
class Money:
    cents: int
    currency: str = field(compare=True, hash=True)  # part of equality — included
    # order=True means comparison uses (cents, currency) tuple — same as eq
    # frozen+slots gives hashable + memory-efficient

    def __post_init__(self):
        if self.currency.upper() != self.currency:
            raise ValueError("currency must be uppercase")
        if not isinstance(self.cents, int):
            raise TypeError("cents must be int")

    @classmethod
    def from_units(cls, units: Decimal | float | str, currency: str = "USD") -> "Money":
        cur = currency.upper()
        cents = int((Decimal(str(units)) * 100).quantize(Decimal("1")))
        return cls(cents, cur)

    @property
    def units(self) -> Decimal: return Decimal(self.cents) / 100

    # Human-facing formatting (13.03)
    def __str__(self) -> str:
        sym = {"USD": "$", "EUR": "€", "GBP": "£"}.get(self.currency, self.currency + " ")
        return f"{sym}{self.units:,.2f}"          # $75.00

    def __format__(self, spec: str) -> str:
        # Custom specs: "iso" -> 75.00 USD, "raw" -> cents int
        if spec == "iso": return f"{self.units:.2f} {self.currency}"
        if spec == "raw": return str(self.cents)
        if not spec: return str(self)
        raise ValueError(f"Unknown Money format {spec!r}")

    # Operator overloading in a guarded way (13.12)
    def __add__(self, other: Money) -> Money:
        if not isinstance(other, Money): return NotImplemented  # cooperative dispatch
        if self.currency != other.currency:
            raise ValueError(f"Cannot add {self.currency} and {other.currency}")
        return Money(self.cents + other.cents, self.currency)
    __radd__ = __add__

    def __sub__(self, other: Money) -> Money:
        if not isinstance(other, Money): return NotImplemented
        if self.currency != other.currency:
            raise ValueError(f"Cannot subtract {other.currency} from {self.currency}")
        return Money(self.cents - other.cents, self.currency)
    __rsub__ = __sub__

    def __neg__(self) -> Money: return Money(-self.cents, self.currency)
    def __abs__(self) -> Money: return Money(abs(self.cents), self.currency)


@dataclass(frozen=True, slots=True, order=True)
class Transaction:
    id: str
    account_id: str
    kind: Literal["deposit","withdraw","transfer_in","transfer_out"]
    amount: Money
    at: datetime
    counterparty: str | None = None

    def __post_init__(self):
        if self.at.tzinfo is None:  # always UTC — normalize in post_init for ordering determinism
            raise ValueError("at must be timezone-aware")

    def __format__(self, spec: str) -> str:
        if spec == "line":
            return f"{self.at:%Y-%m-%d %H:%M} {self.kind:12} {self.amount!s:>10} ({self.id})"
        if not spec: return str(self)
        raise ValueError(f"Unknown Transaction format {spec!r}")

    def __repr__(self) -> str:
        # Dataclass auto repr is fine — but can be verbose for nested Money
        return f"Transaction(id={self.id!r}, kind={self.kind!r}, amount={self.amount!r}, at={self.at!r})"


# Domain exception as class hierarchy (13.16 API design guidance):
class BankingError(RuntimeError): pass
class InsufficientFunds(BankingError): pass
class CurrencyMismatch(BankingError): pass

# Now Account wraps these primitives coherently (iteration is next lesson design decision)
import uuid

class Account:
    """
    Account is an ENTITY (identity-based) — equality by account_id, not by contents.
    This is the crucial modeling choice that distinguishes order types.
    """
    __slots__ = ("_id", "_owner", "_currency", "_balance", "_log", "_frozen")

    def __init__(self, account_id: str, owner: str, currency: str = "USD"):
        self._id, self._owner, self._currency = account_id, owner, currency.upper()
        self._balance: Money = Money(0, self._currency)
        self._log: list[Transaction] = []
        self._frozen = False

    # ---- Identity semantics (13.04): Account is not Money — don't confuse equality rules
    def __eq__(self, other: object) -> bool:
        if isinstance(other, Account): return self._id == other._id  # identity, not balance equality
        return NotImplemented

    def __hash__(self) -> int:
        return hash(self._id)

    def __repr__(self) -> str:
        return f"Account(id={self._id!r}, owner={self._owner!r}, balance={self._balance!r})"

    def __str__(self) -> str:
        return f"Account {self._id} ({self._owner}) — {self._balance}"

    # ---- Container/value delegation: read-only views, not raw list export
    @property
    def account_id(self) -> str: return self._id

    @property
    def owner(self) -> str: return self._owner

    @property
    def currency(self) -> str: return self._currency

    @property
    def balance(self) -> Money: return self._balance  # Money is frozen — safe to return directly

    def __len__(self) -> int: return len(self._log)    # 13.06 — account has length = number of transactions
    def __iter__(self):   # 13.07 — iterable over transactions, oldest first
        return iter(tuple(self._log))  # fresh iterator over snapshot — not shared cursor
    def __contains__(self, tx: Transaction) -> bool:    # 13.06 — transaction membership (identity by id)
        if not isinstance(tx, Transaction): return False
        return any(t.id == tx.id for t in self._log)
    def __getitem__(self, idx):                         # 13.06 — indexed/sliced access to log by position
        return self._log[idx]  # handles int and slice natively via list delegation

    def __format__(self, spec: str) -> str:
        if spec == "statement":
            header = f"Statement for Account {self._id} — {self._owner} — Balance {self._balance!s}\n"
            lines = "\n".join(f"{t:line}" for t in self._log)  # Transaction __format__("line")
            return header + lines if self._log else header + "(no transactions)"
        if not spec: return str(self)
        raise ValueError(f"Unknown Account format {spec!r}")

    # ---- Operations — explicit methods, not operators (13.12 when not to overload)
    def deposit(self, amount: Money) -> Transaction:
        self._check_not_frozen()
        self._check_currency(amount)
        if amount.cents <= 0: raise ValueError("deposit must be positive")
        self._balance = self._balance + amount
        tx = self._record("deposit", amount)
        return tx

    def withdraw(self, amount: Money) -> Transaction:
        self._check_not_frozen()
        self._check_currency(amount)
        if amount.cents <= 0: raise ValueError("withdraw must be positive")
        if self._balance.cents < amount.cents:
            raise InsufficientFunds(f"Need {amount}, have {self._balance}")
        self._balance = self._balance - amount
        tx = self._record("withdraw", amount)
        return tx

    # Transfer is NOT an instance method of either account — it is a free function that spans two entities
    # Maintaining single-responsibility and opening transaction-guard possibilities.
    def __call__(self, amount: Money) -> Money:
        """Callable sugar: account(amount) adds amount (deposit) for fluent batching — optional (13.08)."""
        self.deposit(amount)
        return self._balance

    # Context manager pattern for a guarded balance/statement session? Could expose a context (13.09).

    def _check_currency(self, amount: Money):
        if amount.currency != self._currency:
            raise CurrencyMismatch(f"Account currency {self._currency} vs amount {amount.currency}")

    def _check_not_frozen(self):
        if self._frozen: raise BankingError("Account is frozen")

    def freeze(self): self._frozen = True
    def unfreeze(self): self._frozen = False

    def _record(self, kind: Literal["deposit","withdraw","transfer_in","transfer_out"], amount: Money, counterparty: str | None = None) -> Transaction:
        tx = Transaction(
            id=str(uuid.uuid4())[:8],
            account_id=self._id,
            kind=kind,
            amount=amount,
            at=datetime.now(timezone.utc),
            counterparty=counterparty,
        )
        self._log.append(tx)
        return tx

    # Mutation teardown: if account needs to be serialized/pickled, __slots__ strategy applies (13.15)
    def to_dict(self) -> dict:  # alternative to __dict__ for slotted types
        import dataclasses
        return {"id": self._id, "owner": self._owner, "currency": self._currency,
                "balance": self._balance.__dict__ if hasattr(self._balance, "__dict__") else {"cents": self._balance.cents, "currency": self._balance.currency}}

def transfer(src: Account, dst: Account, amount: Money) -> tuple[Transaction, Transaction]:
    """
    Transactional transfer: all-or-nothing across two accounts.
    Design move: function (not method) enforces symmetry, and is testable without account coupling.
    Demonstrates 13.09 — could be exposed as context manager alternative for explicit transactions.
    """
    if not isinstance(amount, Money): raise TypeError("amount must be Money")
    # Currency check is performed inside withdraw/deposit, but lifting for diagnostics is explicit.
    # Rollback strategy: try/catch with undo. Production code would use a TransactionGuard context (13.09).
    tx_out = src.withdraw(amount)   # raises InsufficientFunds early if fails — nothing to roll back
    try:
        tx_in = dst.deposit(amount)
    except Exception:
        # Undo withdrawal — create compensating entry instead of mutating ledger blindly
        # Real ledger would append reversal transaction — never edit history
        src._balance = src._balance + amount
        src._log.append(Transaction(
            id=str(uuid.uuid4())[:8], account_id=src.account_id,
            kind="transfer_in", amount=amount, at=datetime.now(timezone.utc),
            counterparty=dst.account_id
        ))
        raise
    # Augment kind for audit trails — optionally update via replacement if Transaction were mutable
    # Here we keep original kinds per account (transfer_out vs transfer_in is done by re-recording with real kinds):
    # Override the kind for semantics — reclaim the last entries and mark as transfer variants
    # (Simpler offline: _record with transfer kind instead — omitted for brevity — tests show deposit/withdraw vs transfer.)
    return tx_out, tx_in


# Usage of iteration-2 types:
if __name__ == "__main__":
    alice = Account("A1", "Alice", "USD")
    bob   = Account("B1", "Bob",   "USD")

    alice.deposit(Money(10_000, "USD"))
    alice.withdraw(Money(2_000, "USD"))
    transfer(alice, bob, Money(3_000, "USD"))

    # Protocols in action:
    print(repr(alice))                 # Account(...) — unambiguously recreatable
    print(alice)                       # user-facing balance summary
    print(f"{alice:statement}")        # custom Account __format__
    print(len(alice),  list(alice))    # 3 transactions, via __len__, __iter__
    print(alice[0])                    # indexed access via __getitem__
    print(alice[1:])                   # slicing via __getitem__ slice delegation
    print(alice.balance == Money(5_000, "USD"))  # value comparison
    print(alice in [])                 # not an iterable expectation, but transaction membership: not used
    print(bob.balance, bob.currency)
    print(f"{Money(1_23, 'USD'):iso}")  # $1.23 — iso format
    print(f"{Money(1_23, 'USD'):raw}")  # 123 — cents
```

### Composition vs Inheritance — Decision Guide

```python
# ❌ Inheritance where composition wins:
class SavingsAccountWithLimit(Account):   # limit policy couples to hierarchy — many such limits explode combinatorics
    def __init__(self, *a, overdraft=0, **kw): ...
    def withdraw(self, amount):  # overridden with limit check — violates OCP as limits multiply
        if self._balance.cents - amount.cents < -overdraft: raise ...
        super().withdraw(amount)

# ✅ Composition: policy object injected — extensible without subclass tax
class WithdrawPolicy:
    """Policy is a callable predicate — passed, tested, composed (13.08, 13.10)."""
    def __init__(self, overdraft_cents: int = 0):
        self.overdraft = overdraft_cents
    def __call__(self, account: Account, amount: Money) -> None:
        if account.balance.cents - amount.cents < -self.overdraft:
            raise InsufficientFunds(f"Overdraft {self.overdraft} exceeded")
    def __repr__(self): return f"WithdrawPolicy(overdraft={self.overdraft})"

# Equivalent to strategy: interchange policy per account in a service, not via subclass
class PricedProduct:
    """Inventory analog: pricing policy as callable injected (13.08)."""
    def __init__(self, price: Money, strategy=None):
        self.price = price
        self.strategy = strategy or (lambda p: p)  # identity default
    def price_for(self, qty: int) -> Money:
        # Callable strategy(p, qty) customizes discount/vat
        if callable(self.strategy):
            cents = self.strategy(self.price.cents, qty)  # or Protocol-prescribed
            return Money(int(cents), self.price.currency)
        return self.price

# When inheritance wins: a true is-a relationship with shared layout and contract invariants.
# `class Money(DecimalStyle): pass` — is not helpful; `Money` composes `Decimal`.
# `class FrozenMoney(Money): ...` with frozen semantics via subclass defaults uses dataclass inheritance correctly.
```

### ABC vs `Protocol` — When to Choose

```python
from abc import ABC, abstractmethod
from typing import Protocol

# Choose ABC when:
# - The framework requires `isinstance(x, Base)` to succeed (classic hierarchy + shared implementation)
# - Shared base logic or state (e.g., common `_validate_x`)

class AccountRepository(ABC):
    @abstractmethod
    def get(self, account_id: str) -> Account: ...
    @abstractmethod
    def save(self, account: Account) -> None: ...
    def commit(self): ...  # default no-op impl — shared logic

# Choose Protocol when:
# - You need structural duck typing for any object with `__enter__`/`__exit__`, `__lt__` etc. (special-method families)
# - Third-party objects or built-ins should qualify without modifying their MRO
# (This is more often correct — 13.01/13.10 themes: protocols are structural, not nominal.)

class MoneyLike(Protocol):
    @property
    def cents(self) -> int: ...
    @property
    def currency(self) -> str: ...
    def __add__(self, other: "MoneyLike") -> "MoneyLike": ...  # but return type width — etc.
    def format_as(self, spec: str) -> str: ...

# In practice, Money directly implements MoneyLike as a concrete @dataclass, no need for separate ABC lean hierarchy.
# So the rule: for domain registries or ORM-like APIs where the invariant lives in base, inherit ABC;
# for flexible "anything arithmetic" or "anything with __len__/__iter__" swallowing duck types, define Protocol.

# You can have both: abstract base implements Protocol for runtime isinstance narrowing:
# runtime_checkable decorator + ABC base: Protocol describes the interface, ABC provides default state+method sharing.
```

## 3. Protocols Realized in the Banking Domain — Decision Table

Each of the 16 dunder families deserves an explicit "will I implement it here?" entry — this table is an API design checklist:

| Dunder family | Account entity | Money value type | Transaction (log entry) | Decision / rationale |
|---------------|---------------|-----------------|------------------------|---------------------|
| `__new__`/`__init__`/`__call__` | `__init__` + `_record`; `__call__` as convenience deposit hook | `__new__` not needed (frozen dataclass path via `__init__`/`__post_init__`); `Money(...)` concrete | `__init__` via dataclass | Use `__post_init__` validation for Money/Transaction. `__new__` only for interning color-like Flyweight types. |
| `__repr__`/`__str__`/`__format__` | `__repr__` for reconstruction; `__str__` for user badge; `__format__(":statement")` for multi-line ledger | `__repr__` for value; `__str__` symbol; `__format__("iso"/"raw")` for report/signal paths | `__format__("line")` for statement rendering, `__repr__` full | Every domain type gets at least `__repr__`. `__format__` supports single-spec rendering for pipelines. |
| `__eq__`/`__hash__` | `__eq__` by `account_id`; `hash(account_id)` — entity semantics | `__eq__` by `(cents, currency)`; `hash` tuple — value semantics | `__eq__` by all fields; `hash` frozen tuple | The identity vs value distinction is the most common design error — decide and document per type. |

| Callable (`__call__`) | `Account(Money)` prints convenience deposit | `Money` not callable | Not callable | Callable is a feature-tax — use sparingly (counter/strategy). Here deposit shorthand only. |
| Context manager | `AccountTransaction` context — see ledger guard below | Not resource | Not resource | Use `ExitStack` to bundle multi-account atomic transfers (13.09) |
| Descriptors (`__get__/__set__`) | Not directly — via property for `balance` read-only exposure | Not descriptors — dataclass handles | Not descriptors | Prefer `property` for computed fields (balance read-only) over `__getattr__`. |
| Attribute access (`__getattribute__/__getattr__`) | `__getattr__` for virtual read-only `meta_` on enriched subclasses? Only if domain demands | Not dynamic | Not dynamic | Don't proxy known attributes; `__getattr__` reserved for dynamic delegation (13.11). |
| Operator overloading | Deliberately NOT overloaded (`+` = unclear cash-merge) | `__add__`/`__sub__`/`__mul__` by scalar | Not overloaded | Only overload when mathematical intuition is unambiguous — Money and Vector yes, Account no. |

| Slots/Performance | `__slots__` on Account for millions of accounts scenario | Slots via dataclass param | Slots via dataclass param | Slots awareness matters for microservices managing millions of entities. |

## 4. A Transaction-Guard Context Manager (13.09 Put To Work)

```python
import contextlib
from datetime import datetime, timezone

# Manager that spans multiple accounts and enforces atomicity by recording compensating transactions on failure:
class TransactionGuard:
    """
    Usage:
        with TransactionGuard() as guard:
            guard.transfer(src, dst, Money(100, "USD"))
            guard.transfer(a, b, Money(50, "USD"))
        # Either all succeed or compensating reversals leave ledgers consistent.
    """
    def __init__(self):
        self._effects: list[tuple[Account, Account, Money]] = []
        self._committed = False

    def __enter__(self) -> "TransactionGuard":
        return self

    def transfer(self, src: Account, dst: Account, amount: Money) -> tuple[Transaction, Transaction]:
        # Perform immediately but remember for rollback
        out, inp = transfer(src, dst, amount)  # uses the atomic transfer function above
        self._effects.append((src, dst, amount))
        return out, inp

    def deposit(self, account: Account, amount: Money) -> Transaction:
        tx = account.deposit(amount)
        self._effects.append((None, account, amount))  # sentinel None for solo deposit
        return tx

    def __exit__(self, exc_type, exc_val, exc_tb):
        if exc_type is None:
            self._committed = True
            return False
        # Failure — attempt compensation (reverse effects LIFO)
        for src, dst, amount in reversed(self._effects):
            try:
                if src is None:
                    # undo deposit — withdraw same
                    dst.withdraw(amount)
                else:
                    # undo prior transfer — reverse direction
                    transfer(dst, src, amount)
                # Real system would not edit Transaction order; reversal appended
            except Exception as e:
                print(f"[TransactionGuard] rollback step failed: {e}")
        return False  # don't suppress original exception — caller must handle it

# Demo:
alice = Account("A1","Alice"); bob = Account("B1","Bob")
alice.deposit(Money(10_000, "USD"))
with contextlib.ExitStack() as stack:
    # Combining TransactionGuard with lock/status context:
    timer_ctx = stack.enter_context(TransactionGuard())  # if Timer were a context, we'd nest it too
    # Simulated activity: guarded multi-transfer
    try:
        timer_ctx.transfer(alice, bob, Money(5_000, "USD"))
        timer_ctx.transfer(alice, bob, Money(10_000, "USD"))  # raises InsufficientFunds at this point
    except InsufficientFunds as e:
        print(f"guarded block raised: {e}")
        # Automatically rolled back first 5_000 transfer via __exit__ LIFO
print("alice balance after guarded failure:", alice.balance)  # restored to 10_000
print("bob balance after failure:", bob.balance)               # restored to 0
```

> A `contextlib.ExitStack` version allows nesting arbitrary guard+locks+timers: `with ExitStack() as s: s.enter_context(TransactionGuard()); s.enter_context(LockGuard(...)):` — see 13.09's stacking patterns.

## 5. Inventory Domain — Second Narrative Showing Same Tools In Different Topology

Swap the narrative: products are value identities (SKU), inventory is mutable mapping with ordering mechanics:

```python
from dataclasses import dataclass, field
from collections import defaultdict
from collections.abc import Mapping, Sequence
import bisect

@dataclass(frozen=True, slots=True)
class SKU:
    code: str
    def __post_init__(self):
        if not self.code.isupper(): raise ValueError("SKU uppercase required")
    def __str__(self): return self.code
    # hash via dataclass (frozen, so auto)

@dataclass(frozen=True, slots=True)
class Product:
    sku: SKU
    name: str
    price: Money           # reuse Money from banking domain — cross-domain reuse of value type
    category: str = ""

    def __repr__(self): return f"Product({self.sku!r}, {self.price!r})"
    # comparisons on Product? Not ordering — catalog sorting by price is explicit `key=lambda p: p.price` etc.

class Stock:
    """Mutable container: sku -> qty — mapping-like (13.06) + iterable (13.07)."""
    def __init__(self):
        self._qty: dict[SKU, int] = {}
        self._products: dict[SKU, Product] = {}  # catalog wrapper — composition (entity catalog separate from stock count)

    def stock(self, sku: SKU, qty: int) -> None:
        self._qty[sku] = self._qty.get(sku, 0) + qty
        # _products set elsewhere via register

    def register(self, product: Product):
        self._products[product.sku] = product

    def __len__(self) -> int: return len(self._products)
    def __getitem__(self, sku: SKU) -> tuple[Product, int]:
        # Mapping access: stock[sku] -> (product, qty)
        return self._products[sku], self._qty.get(sku, 0)
    def __setitem__(self, sku: SKU, value: tuple[Product, int]):
        prod, qty = value
        self._products[sku] = prod
        self._qty[sku] = qty
    def __delitem__(self, sku: SKU):
        del self._products[sku]; del self._qty[sku]
    def __contains__(self, sku: object) -> bool: return sku in self._products
    def __iter__(self): return iter(self._products)  # iterates SKU keys
    def __reversed__(self): return reversed(list(self._products))
    def __repr__(self): return f"Stock({len(self)} products)"

    # Real inventory needs low-stock query — descriptor/___ compare concerns:
    def low_stock(self, threshold: int = 10) -> list[tuple[Product,int]]:
        return [(self._products[k], v) for k,v in self._qty.items() if v <= threshold]

    # Sorted low-stock by qty using explicit ordering (13.05 not via Product ordering):
    def low_stock_sorted(self, threshold: int = 10) -> list[tuple[Product,int]]:
        data = self.low_stock(threshold)
        return sorted(data, key=lambda kv: kv[1])  # qty ordering explicit

# Demonstrating with Money, SKU, Stock:
if __name__ == "__main__" and False:
    inv = Stock()
    w = Product(SKU("WIDGET-001"), "Widget", Money(999, "USD"), "tools")
    g = Product(SKU("GADGET-002"), "Gadget", Money(1999, "USD"), "tools")
    inv.register(w); inv.stock(w.sku, 5)
    inv.register(g); inv.stock(g.sku, 50)
    print(inv)
    print(SKU("WIDGET-001") in inv)            # True — __contains__
    print(len(inv))                             # 2
    print(inv[SKU("WIDGET-001")])               # (Product(...), 5)
    print(list(inv))                            # [SKU(WIDGET-001), SKU(GADGET-002)]
    print(inv.low_stock(10))                    # Widget low
```

### Descriptors In Inventory — Pricing Strategy As Descriptor (13.10)

```python
class Priced:
    """Descriptor that validates Money price on set and expresses discount strategy."""
    def __set_name__(self, owner, name): self.name, self.private = name, f"_{name}"
    def __get__(self, obj, owner=None):
        if obj is None: return self
        return getattr(obj, self.private, Money(0, "USD"))
    def __set__(self, obj, value: Money):
        if not isinstance(value, Money): raise TypeError(f"{self.name} must be Money")
        if value.currency != getattr(obj, "currency", value.currency):
            raise CurrencyMismatch("category currency mismatch")
        setattr(obj, self.private, value)

class ShelfItem:
    price = Priced()  # validated per-item vs global catalog price (duplicate via strategy)
    def __init__(self, sku: SKU, price: Money):
        self.sku = sku
        self.currency = price.currency
        self.price = price

item = ShelfItem(SKU("ITEM-99"), Money(1000, "USD"))
print(item.price)                   # $10.00
try: item.price = Money(10, "EUR")
except CurrencyMismatch as e: print(e)
```

## 6. The Pythonic Class Design Checklist

End every design review with these yes/no items. If any answer is "no and I don't know why", the design needs revisiting.

### Representation

- [ ] Does each domain type implement `__repr__` that is unambiguous and ideally `eval`-like? Are secrets hidden (`field(repr=False)`)?
- [ ] Does `__str__` differ from `__repr__` where user vs developer audience diverges?
- [ ] Is `__format__` handled — `f"{obj:spec}"` valid for statement/csv/raw etc.?

### Equality, Hashing, Ordering

- [ ] Is `__eq__` vs identity (`id`/`account_id` vs value `(cents,currency)`) deliberately chosen, and is `NotImplemented` returned for foreign types?
- [ ] If `__eq__` overridden, is `__hash__` either correct value-hash or `None` (mutable/value-typed)?
- [ ] If ordering desired, is it total (`@total_ordering` or explicit `__lt__/__gt__/...`) and based on business semantics, not on repr artifact?

### Container / Iterable

- [ ] Is `__len__` O(1)? Is `bool(obj)` semantically tied to `__len__` vs explicit `__bool__`?
- [ ] Does `__getitem__` handle both int and `slice` via `slice.indices`?
- [ ] Is `__iter__` yielding fresh iterators (no reused internal iterator) and are infinite iterables documented as such?
- [ ] Is `__contains__` optimized beyond linear scan for large containers?

### Behavioral

- [ ] Should the class be callable (`__call__`)? Is there explicit state + inspectable `__repr__`/`signature` for it? (If not, prefer plain function)
- [ ] Is the context manager protocol (`__enter__`/`__exit__`) modeled for resources with setup/teardown rather than manual `try/finally`?
- [ ] Does `__exit__` return `False`/`True` narrowly — not broadly swallowing exceptions?

### Structural

- [ ] Are descriptors (`__get__`/`__set__`) used for fixed, reusable attribute validation vs `__getattr__` for dynamic fallback vs `__getattribute__` only for proxies/audits (with recursion guard)?
- [ ] Is operator overloading (`__add__`/`__mul__` etc.) limited to mathematically clear domains and does `return NotImplemented` for unknowns (so reflected path can try)?
- [ ] Is the need for a metaclass genuine, or can `__init_subclass__`, `__class_getitem__`, or a class decorator achieve same?
- [ ] Are dataclasses used for pure value types (`frozen`, `slots`, `order` toggling) and hand-rolled `__slots__` or plain class for identity entities?
- [ ] Is `__slots__` adopted only after memory profiling confirms wins, with child `__slots__ = ()` discipline, `__dict__`/`__weakref__` chosen intentionally?

### Architecture & Public API

- [ ] Are entity types (identity-based `Account`, `SKU`) separated from value types (`Money`, `Transaction`)?
- [ ] Is composition favored over inheritance for policy/behavior extension?
- [ ] Is coupling inverted via `Protocol`/ABC so tests can pass fakes?
- [ ] Does the error hierarchy name the failure mode (`InsufficientFunds`, `CurrencyMismatch`) rather than a single `ValueError` bin?
- [ ] Is the public constructor surface `kw_only` for long argument lists? Is `field(default_factory=...)` used for mutable defaults?
- [ ] Is the module `__all__` and docstrings sufficient that `help(Account)` explains every decision above?

## 7. Testing Protocol-Aware Design — Practical Pattern

```python
# test_banking.py style — demonstrate protocol contract testing, not just logic:
import pytest
from datetime import datetime, timezone

def test_money_equality_is_by_value():
    a = Money(100, "USD")
    b = Money(100, "USD")
    assert a == b
    assert hash(a) == hash(b)
    assert a is not b

def test_money_currency_guard():
    with pytest.raises(ValueError):
        Money(100, "USD") + Money(100, "EUR")

def test_account_identity_not_balance():
    a = Account("A1", "Alice")
    b = Account("A1", "Bob")  # same id, different owner/balance
    assert a == b             # equality by id
    assert {a, b} == {a}      # hash dedup by id

def test_account_iterable_protocol():
    a = Account("A1", "Alice")
    a.deposit(Money(100, "USD"))
    a.deposit(Money(50, "USD"))
    assert len(a) == 2
    assert all(isinstance(t, Transaction) for t in a)
    assert a[0].kind == "deposit"
    assert a[1:][0].kind == "deposit"

def test_transaction_guard_atomicity():
    alice, bob = Account("A1","Alice"), Account("B1","Bob")
    alice.deposit(Money(10_000, "USD"))
    with TransactionGuard() as guard:
        guard.transfer(alice, bob, Money(5_000, "USD"))
        try:
            guard.transfer(alice, bob, Money(10_000, "USD"))  # fails
        except InsufficientFunds:
            raise
    # Guard __exit__ rolled back first transfer:
    assert alice.balance == Money(10_000, "USD")
    assert bob.balance == Money(0, "USD")

def test_format_protocols():
    a = Account("A1","Alice")
    a.deposit(Money(1_00, "USD"))
    stmt = f"{a:statement}"
    assert "Balance" in stmt and "deposit" in stmt.lower()
    assert f"{Money(123,'USD'):iso}" == "1.23 USD"
    assert f"{Transaction('t','A1','deposit',Money(123,'USD'), datetime.now(timezone.utc)):line}"  # non-empty

def test_slots_memory_contract():
    s = Stock()
    # ensure low_stock_sorted respects explicit key ordering, not Product __lt__
    w = Product(SKU("W-001"), "W", Money(100, "USD"))
    g = Product(SKU("G-001"), "G", Money(200, "USD"))
    s.register(w); s.stock(w.sku, 5)
    s.register(g); s.stock(g.sku, 50)
    low = s.low_stock_sorted(10)
    assert low[0][0].sku == SKU("W-001")  # smallest qty first, independent of price/ordering
```

> Protocol testing checklist: for each dunder family, test the contract, not just the happy path — equality-hash invariant, `NotImplemented` for unknowns, `__contains__` fast path, `__enter__`/`__exit__` both normal and exceptional exits, `__iter__` re-iterability, `isinstance(..., Iterable)` via `collections.abc`.

```python
import logging
log = logging.getLogger("banking")

def ledger_transfer(alice: Account, bob: Account, amount: Money, logger=log) -> bool:
    try:
        transfer(alice, bob, amount)
        logger.info("transfer %r -> %r amount %s", alice.account_id, bob.account_id, f"{amount:iso}")
```

## 9. Coda — The Decision Ladder (When You Reach for Which Tool)

```
Domain modeling starts — plain functions + dicts for speed of thought.
        ↓ when invariants accumulate
Class with __init__, methods, invariants in __post_init__.
        ↓ when value identity matters
Dataclass(value: frozen+slots+order?) or plain identity entity with __slots__.
        ↓ when logs/exhibit behavior
__repr__, __str__, __format__ per 13.03.
        ↓ when comparing/searching
__eq__, __hash__, ordering per 13.04/13.05 — total vs partial distinguished, NotImplemented.
        ↓ when container/iteration over history
__len__, __getitem__, __contains__, __iter__, __reversed__, __missing__ per 13.06/13.07.
        ↓ when behavior is a value
__call__ callable strategies or policies per 13.08 — callable vs closure/partial decided.
        ↓ when resources have lifecycles
__enter__, __exit__, contextlib.stacking per 13.09 — transaction guards.
        ↓ when validation/reuse per attribute
Descriptors/__set_name__ or property vs __getattr__ per 13.10/13.11 — data vs non-data distinguished.
        ↓ when arithmetic is intrinsic
Operator overloading per 13.12 — with NotImplemented + augmented-assignment returns, sparingly.
        ↓ when class creation itself needs policy
Metaclass — but prefer __init_subclass__ / class decorator per 13.13 unless namespace pre-processing demanded.
        ↓ when value typing dominates
Dataclass field toggles per 13.14.
        ↓ when millions of instances demand measurement
__slots__ + profiling per 13.15 — only after proof.
        → Full architecture review via this checklist (13.16).
```

> *The ladder above is also the rough reading order of this module — each step adds one protocol family only when the domain's next invariant demands it. The art is in knowing which step **not** to take.*

## Closing — What Mastery Feels Like

When you can look at any class definition and answer, in order:

*   *What is its equality identity, and does its hashing obey that?*
*   *Which protocols does it satisfy as a container/iterable/callable/context, and which does it deliberately *not* satisfy?*
*   *Where is state stored (slots vs `__dict__` vs external cache), and what does that cost at scale?*
*   *What inheritance burden does it carry — and where would a decorator or `__init_subclass__` lighter alternative win?*

— then you read Python's own stdlib (logging, decimal, pathlib, asyncio) and libraries (attrs, sqlalchemy, click, pydantic) *as transparent uses of these same 16 primitives*, rather than opaque magic. The protocols cease to be trivia and become your compositional palette for APIs that feel native.

> **A Pythonic class does not show how clever its author is — it disappears, leaving only the domain's language, proven invariants, and a handful of well-chosen protocols that make the type behave exactly as a reader would expect.**
