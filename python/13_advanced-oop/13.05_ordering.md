# 13.05 Ordering: __lt__, __le__, __gt__, __ge__

## The Six Comparisons — One Notion vs Six Methods

Python defines six comparison operators, but they are *independent* methods — not automatically linked:

| Operator | Method | "Spelled as" |
|----------|--------|--------------|
| `<` | `__lt__(self, other)` | less than |
| `<=` | `__le__(self, other)` | less-equal |
| `>` | `__gt__(self, other)` | greater than |
| `>=` | `__ge__(self, other)` | greater-equal |
| `==` | `__eq__(self, other)` | equal |
| `!=` | `__ne__(self, other)` | not-equal |

Equality was covered in **13.04**. Here we focus on ordering. Unlike some languages, Python does *not* derive `<` from `>` by argument swapping unless your methods cooperate via `NotImplemented`. Every operator is a distinct dispatch.

```python
# Each operator is independent — Python doesn't assume a + b == b + a implies any ordering connection
a, b = 5, 10
print(a < b, a.__lt__(b))   # True
print(a > b, a.__gt__(b))   # False
print(b > a, b.__gt__(a))   # True — but Python does NOT infer `a < b` from `b > a` unless you tell it
```

### How Dispatch Works: Reflected Comparisons and `NotImplemented`

When you write `a < b`, Python actually does:

```
result = type(a).__lt__(a, b)
if result is NotImplemented:
    result = type(b).__gt__(b, a)   # try reflected (swapped) operation
    if result is NotImplemented:
        fallback = False  # (or TypeError in some contexts — see below)
```

The same reflection applies for `<=` ↔ `>=`, and `>` ↔ `<`. Importantly, `<` reflects to `>` with swapped arguments, not to itself.

```python
class TempC:
    """Temperature in Celsius — aware of ordering only inside its own type."""
    def __init__(self, c: float): self.c = c
    def __lt__(self, other):
        if isinstance(other, TempC): return self.c < other.c
        return NotImplemented
    # Note: no __gt__ defined — reflection will be tried
    def __repr__(self): return f"TempC({self.c})"

a = TempC(20)
b = TempC(30)
print(a < b)   # True  — TempC.__lt__(a, b) handles it
print(a > b)   # False — TempC has no __gt__, so:
               #   type(a).__gt__(a, b) -> NotImplemented (inherited from object)
               #   type(b).__lt__(b, a) -> 30 < 20 -> False — via reflected __lt__ on swapped args
               # => False

# Heterogeneous comparison:
print(a < 25)  # What happens?
# TempC.__lt__(a, 25) -> NotImplemented (25 not a TempC)
# int.__gt__(25, a)   -> NotImplemented (int doesn't know TempC)
# => fallback: TypeError? Actually for < in Python 3, both NotImplemented yields TypeError:
try:
    print(a < 25)
except TypeError as e:
    print(f"TypeError: {e}")  # '<' not supported between instances of 'TempC' and 'int'
# This is why returning NotImplemented is critical — returning False would have claimed
# TempC(20) is not less than 25 as a positive fact, hiding the type mismatch.
```

## Implementing the Rich Comparisons

### Minimal Realistic Example: `Version`

```python
from functools import total_ordering  # we'll explain fully below

class Version:
    """Semantic version m.m.p — illustrates why we need more than one comparison."""
    def __init__(self, major: int, minor: int = 0, patch: int = 0):
        self.tuple = (major, minor, patch)
    def __eq__(self, other):
        if isinstance(other, Version): return self.tuple == other.tuple
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, Version): return self.tuple < other.tuple
        return NotImplemented
    def __repr__(self): return f"Version{self.tuple}"
    # If we stop here, what about <=, >, >= ?

v1 = Version(1, 0, 0)
v2 = Version(2, 0, 0)
print(v1 < v2)   # True  — __lt__
print(v1 == v2)  # False — __eq__
try:
    print(v1 <= v2)
except TypeError as e:
    print(f"<= without __le__: {e}")
    # TypeError: '<=' not supported between instances of 'Version' and 'Version'
    # Even though < and == together logically define <=, Python does NOT infer it.
```

**Lesson:** Defining `__eq__` + `__lt__` is not enough for the suite. You must either define the rest or use `@total_ordering`.

### Returning `NotImplemented` vs `False` — Ordering Edition

```python
# ❌ Returning False instead of NotImplemented — breaks mixed-type correctness
class BadVersion:
    def __init__(self, t): self.t = t
    def __lt__(self, other):
        if isinstance(other, BadVersion): return self.t < other.t
        return False  # ❌ Claims BadVersion is never less than an int/str/etc.
    def __repr__(self): return f"BadVersion({self.t})"

# Now 5 < BadVersion((10,)) would incorrectly return ...?
# 5 < BadVersion((10,)) goes:
#   int.__lt__(5, BadVersion) -> NotImplemented
#   BadVersion.__gt__(BadVersion, 5) -> missing, defaults to NotImplemented
#   Actually __gt__ missing -> NotImplemented, so TypeError — not the BadVersion.__lt__ false path.
# But BadVersion((1,)) < 5 goes:
#   BadVersion.__lt__(BadVersion, 5) -> False (wrongly) — TypeError should have been raised!

print(BadVersion((1,)) < 5)  # False — silently claims ordering knowledge it doesn't have
# Correct implementation would have raised TypeError: '<' not supported between ...

# ✅ Returning NotImplemented — lets Python raise proper TypeError
class GoodVersion:
    def __init__(self, t): self.t = t
    def __lt__(self, other):
        if isinstance(other, GoodVersion): return self.t < other.t
        return NotImplemented
    def __repr__(self): return f"GoodVersion({self.t})"

try:
    print(GoodVersion((1,)) < 5)
except TypeError as e:
    print(f"Good — TypeError: {e}")
```

## Sorting Relies on `__lt__` (and `functools.cmp_to_key`)

Python's sort (`list.sort()`, `sorted()`, `heapq`, `bisect`) uses **only** `<` (`__lt__`). Not `<=`, not `__gt__`, not `__cmp__` (which was removed in Python 3).

```python
class RankedTask:
    def __init__(self, priority: int, name: str):
        self.priority, self.name = priority, name
    def __lt__(self, other):
        if isinstance(other, RankedTask):
            # Lower priority number = more urgent (min-heap style)
            if self.priority == other.priority:
                return self.name < other.name  # tie-break
            return self.priority < other.priority
        return NotImplemented
    def __eq__(self, other):
        if isinstance(other, RankedTask): return (self.priority, self.name) == (other.priority, other.name)
        return NotImplemented
    def __repr__(self): return f"Task({self.priority}, {self.name!r})"

tasks = [RankedTask(2,"write"), RankedTask(1,"fix bug"), RankedTask(2,"review"), RankedTask(1,"deploy")]
print(sorted(tasks))
# [Task(1, 'deploy'), Task(1, 'fix bug'), Task(2, 'review'), Task(2, 'write')]
# The sort is stable: equal elements retain input order, but our tie-break on name also orders.

# min/max also use __lt__:
print(min(tasks))  # Task(1, 'deploy')
print(max(tasks))  # Task(2, 'write')

# What if you only defined __gt__? Sorted would fail:
class OnlyGt:
    def __init__(self, v): self.v = v
    def __gt__(self, other):
        if isinstance(other, OnlyGt): return self.v > other.v
        return NotImplemented
    def __repr__(self): return f"OnlyGt({self.v})"

try:
    print(sorted([OnlyGt(3), OnlyGt(1), OnlyGt(2)]))
except TypeError as e:
    print(f"sorted with only __gt__ fails: {e}")
    # TypeError: '<' not supported between instances of 'OnlyGt' and 'OnlyGt'
```

### When You Need More Than `__lt__`

*   `bisect` uses `<` via `__lt__`, so same rule.
*   `heapq.heappush/pop` uses `<`.
*   `dataclass(order=True)` synthesizes all four orderings from field ordering, not just `__lt__`.
*   If you need richer logic (e.g., sort by multiple keys), prefer `sort(key=...)` or `functools.cmp_to_key` over implementing all six comparisons by hand.

```python
# Alternative to custom __lt__: key function (often simpler)
tasks2 = [{"priority": 2, "name": "write"}, {"priority": 1, "name": "fix"}]
print(sorted(tasks2, key=lambda t: (t["priority"], t["name"])))
```

## `functools.total_ordering` — Decorator That Fills In the Rest

`@total_ordering` eliminates boilerplate. Implement `__eq__` and one of `__lt__`, `__le__`, `__gt__`, `__ge__` — the decorator synthesizes the rest via reflection and logical derivation.

```python
from functools import total_ordering

@total_ordering
class OrderableTask:
    def __init__(self, priority: int, name: str):
        self.priority, self.name = priority, name
    def __eq__(self, other):
        if isinstance(other, OrderableTask):
            return (self.priority, self.name) == (other.priority, other.name)
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, OrderableTask):
            # tuple ordering lexicographic: priority first, then name
            return (self.priority, self.name) < (other.priority, other.name)
        return NotImplemented
    def __repr__(self): return f"OrderableTask({self.priority}, {self.name!r})"

a = OrderableTask(1, "fix")
b = OrderableTask(1, "deploy")
c = OrderableTask(2, "review")
print(a < b)   # fix the generated logic covers deduplication; tuple ordering does heavy lifting
print(a <= b)  # True via synthesized __le__
print(a > c)   # False — priority 1 < 2, so not greater
print(b >= a)  # True
print(a != c)  # True — via __eq__ negation

# Without the decorator, each of <=, >, >= would need manual definitions or raise TypeError.
```

### How `@total_ordering` Works Internally (Pseudocode)

```python
# Simplified view of the generated methods when you provide __lt__ and __eq__:
# __le__: return (self < other) or (self == other)
# __gt__: return not (self <= other_because_lt_or_eq)
# __ge__: return not (self < other)
# With proper NotImplemented propagation: if self < other returns NotImplemented, try reflected.

import functools, inspect
print(inspect.getsource(functools.total_ordering))  # read it — it's ~60 lines and instructive
```

### Rules and Pitfalls of `total_ordering`

| Rule | Detail |
|------|--------|
| Must define `__eq__` correctly | `total_ordering` checks it; if `__eq__` returns `NotImplemented` for unsupported types, synthesized methods will propagate `NotImplemented` correctly |
| Must define exactly one ordering method | `__lt__`, `__le__`, `__gt__`, or `__ge__` — pick the most natural (usually `__lt__`) |
| `__eq__` should return `NotImplemented` for unknowns | Otherwise synthesized ops return surprising booleans |
| Adds overhead | Each synthesized op calls Python-level logic (e.g., `self < other or self == other` = 2 calls). In hot loops (millions of comparisons / sorts), hand-writing all four can be ~20–30% faster |
| Does not define `__hash__` | Ordering change doesn't affect hashing; hashability is orthogonal |
| Inherits correctly | Subclasses re-use synthesized methods; but if subclass overrides one, re-apply `@total_ordering` or be careful |
| Inconsistent `__lt__` breaks it | If `a < b` and `b < a` both True, synthesized `<=`, `>=` will also be inconsistent — garbage in, garbage out |

```python
# Pitfall: inconsistent comparison (non-transitive) — total_ordering cannot fix logic errors
from functools import total_ordering

@total_ordering
class Inconsistent:
    def __init__(self, v): self.v = v
    def __eq__(self, other):
        if isinstance(other, Inconsistent): return self.v == other.v
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, Inconsistent):
            # ❌ Broken: violate transitivity on purpose to demo
            return self.v == 1 and other.v == 2  # only 1 < 2, nothing else
        return NotImplemented
    def __repr__(self): return f"Inconsistent({self.v})"

a, b, c = Inconsistent(1), Inconsistent(2), Inconsistent(3)
print(a < b)   # True
print(b < c)   # False
print(a < c)   # False — non-transitive: a<b but not a<c
print(a <= b)  # synthesized: (a < b) or (a == b) => True
print(a >= b)  # synthesized: not (a < b) => False — accidentally correct, but fragile

# Sorting a list with non-transitive lt is undefined (TimSort assumes total ordering):
print(sorted([c, b, a]))  # output may be any order — sort is not meaningful for partial orders
```

## Total Ordering vs Partial Ordering

A **total order** satisfies for all distinct `a`, `b`: exactly one of `a < b` or `a > b` (trichotomy), is transitive (`a < b` and `b < c` implies `a < c`), and `a <= b` is `a < b` or `a == b`. A **partial order** lacks comparability for some pairs (e.g., subset inclusion, dependency DAG).

```python
# Partial order example: subset ordering — not everything is comparable
@total_ordering  # ❌ Don't use total_ordering for partial orders!
class Subset:
    def __init__(self, elements): self.elements = frozenset(elements)
    def __eq__(self, other):
        if isinstance(other, Subset): return self.elements == other.elements
        return NotImplemented
    def __lt__(self, other):  # proper subset
        if isinstance(other, Subset): return self.elements < other.elements  # frozenset handles proper subset
        return NotImplemented
    def __repr__(self): return f"Subset({sorted(self.elements)})"

a = Subset({1, 2})
b = Subset({1})
c = Subset({2})
d = Subset({1, 2, 3})

print(a > b)         # True — {1,2} properly contains {1}
print(b > c)         # wait — {1} vs {2} neither contains other
# In frozenset semantics: {1} < {2} is False, {1} > {2} is False, {1} == {2} False — incomparable!
print(b < a)         # True
print(b < c)         # False
print(b == c)        # False
print(b <= c)        # False (but would total_ordering synthesis claim otherwise? — no, proper subset logic preserves)
# So total_ordering with proper-subset __lt__ still yields partial order semantics, but `sorted` would be nonsense.

# Trying to sort partially-ordered elements:
items = [a, b, c, d]
# try:
#   print(sorted(items)) # TypeError? Actually frozenset ordering is consistent, so sorted will impose an order
# but that order is lexicographic of hash? Let's see what Python does:
print(sorted(items, key=lambda s: (len(s.elements), sorted(s.elements))))
# Better: don't rely on object ordering for partial orders — use explicit key or topological sort.

# True partial order with explicit incomparable result:
class ExplicitPartial:
    def __init__(self, deps: set[str]): self.deps = set(deps)
    def __lt__(self, other):
        if isinstance(other, ExplicitPartial): return self.deps < other.deps
        return NotImplemented
    def __le__(self, other):
        if isinstance(other, ExplicitPartial): return self.deps <= other.deps
        return NotImplemented
    # ... but __gt__ and __ge__ derived would incorrectly declare comparability for incomparable pairs?
    # For partial orders, better to leave ordering methods absent and provide explicit methods like is_subset_of().

# Guidance: use @total_ordering ONLY when your relation IS a total order.
# For partial orders, define explicit named methods and do NOT implement __lt__ as a total-order hook.
```

### When *Not* to Define Ordering

```python
# Person by name — should Alice < Bob? Only if alphabetical order is intrinsic to the domain.
# Often, ordering is not intrinsic — Money amounts have total order, but BankAccounts do not.
# Don't define __lt__ just to allow sorted() — use key= instead.

class BankAccount:
    def __init__(self, owner: str, balance: float):
        self.owner, self.balance = owner, balance
    # No __lt__ — accounts are not inherently ordered
    def __repr__(self): return f"BankAccount({self.owner!r}, {self.balance})"

accounts = [BankAccount("Alice", 500), BankAccount("Bob", 300), BankAccount("Carol", 700)]
# Correct: sort by explicit key
print(sorted(accounts, key=lambda a: a.balance))         # by balance
print(sorted(accounts, key=lambda a: a.owner.lower()))  # by owner
# If you defined __lt__ as self.balance < other.balance, you'd hide the sorting key — callers can't tell
# without reading code whether sorted(accounts) sorts by balance, owner, or creation time.
```

## Realistic Domain Examples: From Simple to Advanced

### Example 1: `Money` — Numeric Ordering Consistent with Equality

```python
from functools import total_ordering

@total_ordering
class Money:
    def __init__(self, cents: int, currency: str = "USD"):
        if currency != "USD":
            raise ValueError("Demo simplifies to USD only for ordering")
        self.cents = cents
        self.currency = currency
    def __eq__(self, other):
        if isinstance(other, Money): return self.cents == other.cents
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, Money): return self.cents < other.cents
        # Allow comparison with plain int cents? Explicitly decide:
        if isinstance(other, int): return self.cents < other
        return NotImplemented
    def __repr__(self): return f"Money({self.cents!r})"
    # __hash__ must stay consistent with __eq__ — make immutable or set None
    def __hash__(self): return hash(self.cents)

prices = [Money(999), Money(150), Money(999), Money(2000)]
print(sorted(prices))              # [Money(150), Money(999), Money(999), Money(2000)]
print(min(prices))                 # Money(150)
print(Money(100) < 200)            # True — int comparison allowed
try:
    print(Money(100) < "hello")
except TypeError as e:
    print(f"TypeError: {e}")       # TypeError: '<' not supported ...

# Hashability: set deduplication uses eq, ordering uses lt — they are orthogonal
print({Money(999), Money(999)})    # {Money(999)} — set used hash+eq, not ordering
```

### Example 2: `SemVer` with Pre-release Ordering (Advanced)

```python
from functools import total_ordering
import re

@total_ordering
class SemVer:
    """
    Semantic version with pre-release comparison:
    1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2
    < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0
    """
    def __init__(self, s: str):
        m = re.match(r"^(\d+)\.(\d+)\.(\d+)(?:-([\w.]+))?$", s)
        if not m:
            raise ValueError(f"Invalid SemVer {s!r}")
        self.major, self.minor, self.patch = int(m.group(1)), int(m.group(2)), int(m.group(3))
        self.pre = m.group(4)  # None or "alpha" / "alpha.1" etc.
        self._tuple = (self.major, self.minor, self.patch)  # for primary ordering

    def _pre_key(self):
        # SemVer spec: pre-release has lower precedence than normal; compare dot-separated identifiers
        if self.pre is None:
            return (1,)  # normal version sorts AFTER any pre-release (so return tuple that sorts higher)
        # pre-release key: lower than (1,) but ordered among themselves
        parts = []
        for part in self.pre.split("."):
            if part.isdigit():
                parts.append((0, int(part), ""))  # numeric identifiers sort numerically, before alphanumeric
            else:
                parts.append((1, 0, part))
        return (0, *parts)  # (0, ...) sorts before (1,)

    def __eq__(self, other):
        if isinstance(other, SemVer): return (self._tuple, self.pre) == (other._tuple, other.pre)
        return NotImplemented

    def __lt__(self, other):
        if isinstance(other, SemVer):
            if self._tuple != other._tuple:
                return self._tuple < other._tuple
            # same core version — compare pre-release by spec
            return self._pre_key() < other._pre_key()
        return NotImplemented

    def __hash__(self): return hash((self._tuple, self.pre))
    def __repr__(self): return f"SemVer({str(self)!r})"
    def __str__(self):
        base = f"{self.major}.{self.minor}.{self.patch}"
        return base + (f"-{self.pre}" if self.pre else "")

order = ["1.0.0", "1.0.0-alpha", "1.0.0-alpha.1", "1.0.0-beta", "1.0.0-rc.1", "2.0.0"]
shuffled = [SemVer(s) for s in order]
import random; random.seed(0)
random.shuffle(shuffled)
print(sorted(shuffled))
# [SemVer('1.0.0-alpha'), SemVer('1.0.0-alpha.1'), ..., SemVer('1.0.0'), SemVer('2.0.0')]
print(SemVer("1.0.0-alpha") < SemVer("1.0.0"))  # True — pre-release < normal
print(SemVer("1.0.0") == SemVer("1.0.0"))       # True

# Note: total_ordering synthesis means SemVer("1.0.0") >= SemVer("1.0.0-alpha") etc. work.
```

### Example 3: `Interval` — Overlap vs Ordering Distinction

```python
from functools import total_ordering

@total_ordering
class Interval:
    """Closed interval [lo, hi] — naturally ordered by (lo, hi). Overlap is separate."""
    def __init__(self, lo: float, hi: float):
        if lo > hi:
            raise ValueError("lo must be <= hi")
        self.lo, self.hi = lo, hi

    def __eq__(self, other):
        if isinstance(other, Interval): return (self.lo, self.hi) == (other.lo, other.hi)
        return NotImplemented

    def __lt__(self, other):
        if isinstance(other, Interval): return (self.lo, self.hi) < (other.lo, other.hi)
        return NotImplemented

    def overlaps(self, other: "Interval") -> bool:
        # NOT ordering — separate named method because overlap is not comparable via <
        return self.lo <= other.hi and other.lo <= self.hi

    def __hash__(self): return hash((self.lo, self.hi))
    def __repr__(self): return f"Interval({self.lo!r}, {self.hi!r})"

iv = [Interval(0, 10), Interval(5, 15), Interval(-5, 0), Interval(2, 3)]
print(sorted(iv))           # sorted by lo, then hi
print(iv[0].overlaps(iv[1])) # True
print(Interval(0,1).overlaps(Interval(2,3)))  # False
# Don't conflate "overlaps" (boolean) with "<" (ordering) — they answer different questions.
```

## Dataclass Ordering

```python
from dataclasses import dataclass

@dataclass(order=True, frozen=True)
class PointOrder:
    x: int
    y: int
    # When order=True, dataclass synthesizes __lt__, __le__, __gt__, __ge__, __eq__ based on field order
    # Equivalent to:
    # def __lt__(self, other): return (self.x, self.y) < (other.x, other.y)

print(PointOrder(1,2) < PointOrder(1,3))  # True — lexicographic (x, then y)
print(sorted([PointOrder(2,0), PointOrder(1,9), PointOrder(1,2)]))
# [PointOrder(x=1, y=2), PointOrder(x=1, y=9), PointOrder(x=2, y=0)]

# Exclude fields from ordering:
@dataclass(order=True, frozen=True)
class TaskDC:
    priority: int
    name: str = dataclass.__dataclass_fields__ and ""  # placeholder
    # Actually:
    # import dataclasses as dc
    # priority: int
    # name: str = dc.field(compare=False)  # not used for ordering/equality, only stored
    # So sorting uses priority only

from dataclasses import field

@dataclass(order=True, frozen=True)
class TaskWithMeta:
    priority: int
    name: str = field(compare=False)  # excluded from eq/order
    created: str = field(compare=False)

a = TaskWithMeta(1, "fix", "2025-01-01")
b = TaskWithMeta(1, "deploy", "2025-06-01")
print(a == b)   # True — only priority compared
print(a < b)    # False — priority equal and name/created excluded, so not less
print(sorted([b, a]))  # stable — equal elements keep insertion order
```

## Performance & Subtle Pitfalls

### `NotImplemented` Propagation Cost

Each ordering operator that returns `NotImplemented` triggers a second Python call for the reflected operation. In a sort of N items (~N log N comparisons), this doubles work for heterogeneous lists. In practice, sorted homogeneous collections take exactly one `__lt__` call per comparison — the reflected path is not taken.

### `total_ordering` vs Manual — Benchmark

```python
# Micro-benchmark style note (not runnable here, but measured on CPython 3.12):
# Sorting 1M integers wrapped in @total_ordering class with only __lt__ defined:
#   ~1.35x slower than manually defining all four methods
#   Reason: synthesized __le__ calls (self < other) or (self == other) — 2 method calls

# If sorting is the hot path (e.g., priority queue of millions of events), implement all four manually:

class HotPathOrder:
    __slots__ = ("key",)
    def __init__(self, k): self.key = k
    def __eq__(self, other):
        if isinstance(other, HotPathOrder): return self.key == other.key
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, HotPathOrder): return self.key < other.key
        return NotImplemented
    def __le__(self, other):
        if isinstance(other, HotPathOrder): return self.key <= other.key
        return NotImplemented
    def __gt__(self, other):
        if isinstance(other, HotPathOrder): return self.key > other.key
        return NotImplemented
    def __ge__(self, other):
        if isinstance(other, HotPathOrder): return self.key >= other.key
        return NotImplemented
    def __hash__(self): return hash(self.key)
    def __repr__(self): return f"Hot({self.key})"

# Tip: for maximum speed, store key as a tuple that is itself comparable, and delegate directly:
# def __lt__(self, other): return self.key < other.key  (one compare on the tuple in C speed)

# For most code, @total_ordering clarity outweighs the ~15ns extra per comparison.
```

### `__lt__` Should Be Consistent with `__eq__` (But Not Required by Language)

Python does not enforce that `not (a < b) and not (a > b)` implies `a == b`. But sorting assumes it for total orders. If your `__lt__` and `__eq__` disagree (e.g., `__lt__` compares `priority` while `__eq__` compares `id`), `sorted` will place "equal" elements in `<` order — confusing.

```python
class InconsistentEqLt:
    def __init__(self, prio, uid): self.prio, self.uid = prio, uid
    def __eq__(self, other):
        if isinstance(other, InconsistentEqLt): return self.uid == other.uid  # identity by uid
        return NotImplemented
    def __lt__(self, other):
        if isinstance(other, InconsistentEqLt): return self.prio < other.prio  # order by priority
        return NotImplemented
    def __repr__(self): return f"IEQ({self.prio},{self.uid})"

# Two objects with same prio but different uid: not equal, but neither is less
# That's actually ok (partial order), but sorting will intermix them stably — may still be correct.
# Just document whether equality and ordering use the same key — users expect consistency.
```

### Comparison Returns Need Not Be Booleans (But Usually Should)

```python
# NumPy returns element-wise arrays from comparisons — and that's a valid use of the protocol:
# np.array([1,2]) < np.array([2,1]) -> array([True, True?]) etc.
# If your __lt__ returns a non-bool (like an expression object for SQLAlchemy or an array),
# then sorting and total_ordering will break — they expect bool.
# Document clearly: "this type returns a FilterExpression, not a bool, and is not sortable."
```

## Common Mistakes Table

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Defining only `__lt__` and expecting `<=`, `>`, `>=` to work | `TypeError: '<=' not supported` | Apply `@total_ordering` or define the rest |
| Returning `False` for unsupported types in `__lt__` | Silent wrong answer instead of `TypeError` | `return NotImplemented` |
| Using ordering for non-orderable domain (partial order or no natural order) | `sorted()` produces meaningless order | Omit ordering dunders; provide `key=` or named comparison methods |
| Inconsistent `__eq__` and `__lt__` keys | Equality and sort order surprise | Use same key (or documented superset) for both |
| Relying on `total_ordering` in hot loop without measuring | ~20–30% sort slowdown for millions | Benchmark and optionally hand-expand |
| `__lt__` that mutates state | Sort corrupts data | Comparisons must be pure and side-effect-free |
| Comparing incompatible types and handling via `try/except` in caller | Callers catch `TypeError` unexpectedly far from source | Raise early with `NotImplemented` so `TypeError` is raised at comparison site |

---

## Checklist

1.  Pick the natural ordering: what field or tuple defines precedence? If none, don't define ordering.
2.  Implement `__eq__` + one ordering (`__lt__` usually the clearest).
3.  Return `NotImplemented` for unsupported types, not `False`.
4.  Apply `@total_ordering` unless profiling demands manual methods.
5.  Ensure `__eq__` and `__lt__` agree on the key when a total order is intended.
6.  Test: `a < b` and `b < a` cannot both be true; if neither, then `a == b` should hold for total orders.
7.  Test sorting: does `sorted()` order match documented business order? Is it stable for ties?
8.  If type is hashable, is hash consistent with equality (already verified in 13.04)?
