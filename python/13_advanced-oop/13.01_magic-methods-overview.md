# 13.01 Magic Methods Overview

## What Are Magic Methods?

Magic methods — formally **special methods** and colloquially **dunder methods** (double-underscore methods) — are the hooks that connect Python's syntax and built-in operations to your own types. When you write `len(obj)`, `obj1 + obj2`, `for x in obj`, or `with obj as f`, Python does not execute ad-hoc logic. It dispatches to a well-defined special method on the object's type: `__len__`, `__add__`, `__iter__`, `__enter__`/`__exit__`, respectively.

> **Mental model:** Python's syntax is thin sugar over method calls. Operators, built-ins, and statements are *protocols* — contracts that say "if your type implements these methods, it will behave like a native type."

This is fundamentally different from many languages where operators are fixed to primitive types or where you must call methods explicitly. In Python, `a + b` is `type(a).__add__(a, b)` (with fallback), `obj[key]` is `type(obj).__getitem__(obj, key)`, and so on. Understanding this single idea unlocks the entire object model.

### Terminology

| Term | Meaning |
|------|---------|
| **Special / magic / dunder method** | Method with name `__name__`, defined by the language specification. |
| **Dunder** | Pronounced "dunder", contraction of "double underscore". Community slang. |
| **Protocol** | Informal interface: a collection of special methods that together enable a behavior (e.g., the sequence protocol). Python rarely requires formal inheritance for protocols. |
| **Hook** | Points where Python lets you intercept or customize built-in behavior. |

### Why `__double_underscores__`?

The naming convention serves two purposes:

1.  **Namespace protection.** The language reserves `__*__` names today and in the future. User code should never invent its own `__my_method__` — use a single underscore `_internal` or plain name. This reserves evolution space for Python.
2.  **Visual signal.** When you see `__len__` you know instantly: this is a language protocol, not ordinary application logic.

> **Rule:** Never invent a `__custom__` name. Lint tools (pylint, ruff) will flag `invalid-name` for invented dunders. Only implement names documented in the [Python Data Model](https://docs.python.org/3/reference/datamodel.html).

## Python's Object Model in One Page

Everything in Python is an object — integers, functions, classes, modules. Every object has three things:

1.  **Identity** — memory address (`id(obj)`), never changes.
2.  **Type** — `type(obj)`, determines the methods and operations available.
3.  **Value** — mutable or immutable state.

Special methods live on the **type**, not on the instance dictionary. This is a critical, performance-motivated design choice:

```python
class Widget:
    def __len__(self):
        return 42

w = Widget()
print(w.__len__())          # works: lookup on instance succeeds
print(len(w))               # works: Python looks up type(w).__len__

# But patching the instance does NOT affect the protocol:
w.__len__ = lambda: 999
print(w.__len__())          # 999 — instance attribute shadows
print(len(w))               # 42  — still uses type slot!

# Only changing the type affects the protocol:
Widget.__len__ = lambda self: 999
print(len(Widget()))        # 999

# Even mapping proxy tricks:
import types
# type.__call__ etc. are slot wrappers, not plain functions
print(type(Widget.__len__))  # <class 'function'> originally
print(type(len))             # <class 'builtin_function_or_method'>
```

**Why on the type?** For CPython, type slots are C-level function pointers (`tp_as_number`, `sq_item`, etc.) giving O(1) dispatch without per-instance dictionary lookup. This is both a semantic rule and a performance optimization.

### Attribute Lookup in Brief

When Python executes `obj.attr`:

1.  Check `type(obj).__getattribute__` (data descriptors, slots).
2.  Check `type(obj).__dict__` and base classes via MRO.
3.  Invoke `__getattr__` fallback if defined.
4.  Raise `AttributeError`.

Special-method lookup bypasses steps 1 and 3 for instances — it goes directly to the type's slot wrappers. This is why `obj.__add__` can be shadowed but `obj + other` ignores the instance attribute.

## Taxonomy: The Complete Category Table

The data model defines ~80 special methods. Grouping them by purpose makes them learnable:

### 1. Object Creation & Lifecycle

| Method | Syntax / Trigger | Purpose |
|--------|------------------|---------|
| `__new__(cls, ...)` | `Cls(...)` (first phase) | Create and return a new instance (the actual constructor) |
| `__init__(self, ...)` | `Cls(...)` (second phase) | Initialize an already-created instance |
| `__del__(self)` | garbage collection | Destructor — rarely used, `weakref.finalize` preferred |
| `__call__(self, ...)` | `obj(...)` | Make instance callable like a function |
| `__init_subclass__(cls)` | `class Child(Parent):` | Hook on parent when subclass is defined |
| `__class_getitem__(cls, key)` | `Cls[int]` | Generic alias support (`list[int]`) |

### 2. Representation & Formatting

| Method | Trigger | Purpose |
|--------|---------|---------|
| `__repr__(self)` | `repr(obj)`, REPL | Unambiguous developer-facing representation |
| `__str__(self)` | `str(obj)`, `print(obj)`, `f"{obj}"` | Human-readable string (falls back to `__repr__`) |
| `__format__(self, spec)` | `format(obj, spec)`, `f"{obj:spec}"` | Custom format specifications |
| `__bytes__(self)` | `bytes(obj)` | Bytes representation |
| `__bool__(self)` | `bool(obj)`, `if obj:` | Truthiness (falls back to `__len__`) |

### 3. Comparison & Ordering

| Method | Operator | Notes |
|--------|----------|-------|
| `__eq__(self, other)` | `==` | Equality. Return `NotImplemented` for unsupported types |
| `__ne__(self, other)` | `!=` | Auto-negates `__eq__` if not defined |
| `__lt__(self, other)` | `<` | Rich comparisons |
| `__le__(self, other)` | `<=` | |
| `__gt__(self, other)` | `>` | |
| `__ge__(self, other)` | `>=` | |
| `__hash__(self)` | `hash(obj)`, dict/set keys | Must be immutable-consistent; `None` if unhashable |
| `__contains__(self, item)` | `in` | Membership; falls back to iteration |

### 4. Container / Sequence / Mapping Protocol

| Method | Syntax | Purpose |
|--------|--------|---------|
| `__len__(self)` | `len(obj)` | Size |
| `__getitem__(self, key)` | `obj[key]`, slicing | Indexed access |
| `__setitem__(self, key, value)` | `obj[key] = value` | Indexed assignment |
| `__delitem__(self, key)` | `del obj[key]` | Indexed deletion |
| `__missing__(self, key)` | `obj[key]` miss in Mapping | Custom missing-key behavior (dict subclass) |
| `__iter__(self)` | `iter(obj)`, `for` | Iterator factory |
| `__reversed__(self)` | `reversed(obj)` | Reverse iteration |
| `__contains__(self, item)` | `item in obj` | Optimized membership |

### 5. Iteration Protocol

| Method | Trigger |
|--------|---------|
| `__iter__(self)` | `iter(obj)` — must return an iterator |
| `__next__(self)` | `next(it)` — return next value or raise `StopIteration` |
| `__getitem__` (legacy) | `for x in obj` if `__iter__` missing, index from 0 until `IndexError` |

### 6. Callable & Descriptor

| Method | Role |
|--------|------|
| `__call__(self, ...)` | Instance is callable |
| `__get__(self, obj, objtype)` | Descriptor read (non-data if only `__get__`) |
| `__set__(self, obj, value)` | Descriptor write (data descriptor) |
| `__delete__(self, obj)` | Descriptor delete |
| `__set_name__(self, owner, name)` | Notified of attribute name on class creation |

### 7. Context Manager

| Method | With-statement phase |
|--------|---------------------|
| `__enter__(self)` | `with obj as x:` — return bound value |
| `__exit__(self, exc_type, exc, tb)` | Block exit — `True` suppresses exception |

### 8. Attribute Access Customization

| Method | When called |
|--------|-------------|
| `__getattribute__(self, name)` | Every attribute access (precedes normal lookup) |
| `__getattr__(self, name)` | Only when normal lookup fails |
| `__setattr__(self, name, value)` | Every `obj.name = value` |
| `__delattr__(self, name)` | `del obj.name` |
| `__dir__(self)` | `dir(obj)` |
| `__getstate__`, `__setstate__`, `__reduce__` | Pickling |

### 9. Numeric / Operator Overloading

| Category | Methods |
|----------|---------|
| Arithmetic | `__add__`, `__radd__`, `__sub__`, `__rsub__`, `__mul__`, `__rmul__`, `__truediv__`, `__rtruediv__`, `__floordiv__`, `__rfloordiv__`, `__mod__`, `__rmod__`, `__pow__`, `__rpow__`, `__matmul__`, `__rmatmul__` |
| Augmented | `__iadd__`, `__isub__`, `__imul__`, ... (in-place; fallback to non-in-place) |
| Unary | `__neg__`, `__pos__`, `__abs__`, `__invert__` |
| Bitwise | `__and__`, `__rand__`, `__or__`, `__ror__`, `__xor__`, `__rxor__`, `__lshift__`, `__rlshift__`, `__rshift__`, `__rrshift__` |
| Conversion | `__int__`, `__float__`, `__complex__`, `__index__`, `__round__` |

### 10. Async (completeness)

| Method | Async counterpart |
|--------|-------------------|
| `__await__`, `__aiter__`, `__anext__`, `__aenter__`, `__aexit__` | `async for`, `async with`, `await` |

## Syntax Sugar: When Are They Invoked?

This table is the most important thing to memorize. Every row answers: what syntax triggers what method?

```python
# Mapping: syntax -> dunder call

# Object creation
obj = MyClass(1, 2)          # type(MyClass).__call__(MyClass, 1, 2)
                             #   -> MyClass.__new__(MyClass, 1, 2)
                             #   -> MyClass.__init__(obj, 1, 2) if __new__ returns correct type

# Representation
str(obj)                      # type(obj).__str__(obj)  — fallback type(obj).__repr__(obj)
repr(obj)                     # type(obj).__repr__(obj)
f"{obj!r}"                    # type(obj).__repr__(obj)
f"{obj!s}"                    # type(obj).__str__(obj)
f"{obj:spec}"                 # type(obj).__format__(obj, "spec")
bool(obj)                     # type(obj).__bool__(obj) else type(obj).__len__(obj) else True
len(obj)                      # type(obj).__len__(obj)
bytes(obj)                    # type(obj).__bytes__(obj)

# Comparison
a == b                        # type(a).__eq__(a, b) — try type(b).__eq__ if returns NotImplemented
a != b                        # type(a).__ne__ or not (a == b)
a < b                         # type(a).__lt__(a, b)
hash(a)                       # type(a).__hash__(a)
a in container                # type(container).__contains__(container, a) else iteration

# Container
container[key]                # type(container).__getitem__(container, key)
container[key] = val          # type(container).__setitem__(container, key, val)
del container[key]            # type(container).__delitem__(container, key)
container[start:stop:step]    # type(container).__getitem__(container, slice(start, stop, step))

# Iteration
for x in obj: ...             # it = type(obj).__iter__(obj); while True: x = type(it).__next__(it)
iter(obj)                     # type(obj).__iter__(obj)
next(it)                      # type(it).__next__(it)
x, y = obj                    # type(obj).__iter__(obj) and unpack 2 items
*a, b = obj                   # extended unpacking via iterator

# Callable
obj(*args, **kw)              # type(obj).__call__(obj, *args, **kw)

# Context manager
with obj as x: ...            # enter = type(obj).__enter__(obj); ...; type(obj).__exit__(obj, exc...)

# Attribute
obj.attr                      # type(obj).__getattribute__(obj, "attr") -> __getattr__ fallback
obj.attr = val                # type(obj).__setattr__(obj, "attr", val)
del obj.attr                  # type(obj).__delattr__(obj, "attr")

# Operators
a + b                         # type(a).__add__(a, b) else type(b).__radd__(b, a)
a += b                        # type(a).__iadd__(a, b) else type(a).__add__(a, b)
-a                            # type(a).__neg__(a)
abs(a)                        # type(a).__abs__(a)
a[key]                        # __getitem__ as above
```

> **Key distinction:** Some are hooks on the *class* object (`__new__`, `__init__`, `__call__` on metaclass) and some are hooks on *instances* (`__len__`, `__iter__`, `__getitem__`). The dispatch rule is the same: look up on `type(obj)` — but for `MyClass(...)`, `obj` is the class itself and `type(obj)` is its metaclass (`type`).

## Explicit vs Implicit Invocation

Should you call `__len__` directly or use `len()`?

```python
class Bag:
    def __init__(self, items):
        self._items = items
    def __len__(self):
        return len(self._items)
    def __iter__(self):
        return iter(self._items)

bag = Bag([1, 2, 3])

# Never do this in application code:
bag.__len__()           # Works, but brittle and un-Pythonic
# Always do this:
len(bag)                # Correct — works via protocol, handles subclass, uses slot

# Same for iteration:
it = bag.__iter__()     # Explicit — defeats abstraction
it = iter(bag)          # Correct — also supports __getitem__ fallback

# Operator vs method:
# Explicit:
bag.__contains__(2)
# Idiomatic:
2 in bag
```

**Guideline:** Application code uses the syntax/built-in; library code implements the dunder. Calling `obj.__len__()` bypasses protocol guarantees and will confuse readers.

One exception: within an implementation, calling the parent's method explicitly is correct:

```python
class SizedBag(Bag):
    def __len__(self):
        # Delegate to parent protocol implementation
        return super().__len__() + 1
```

## Naming Conventions & Pitfalls

### Do vs Don't

```python
# ✅ Correct: implementing a documented special method
class Money:
    def __repr__(self): ...
    def __eq__(self, other): ...
    def __hash__(self): ...

# ❌ Wrong: inventing your own dunder — no protocol will call it
class Bad:
    def __my_custom_hook__(self):  # Nothing invokes this; just a misleading name
        ...

# ✅ Correct: single underscore for internal / non-public API
class Account:
    def _apply_interest(self): ...
    def _validate_amount(self, v): ...

# ✅ Correct: double leading underscore for name-mangling (avoid collisions in inheritance)
class Base:
    def __private_method(self):  # mangled to _Base__private_method
        ...

# ❌ Wrong: double leading AND trailing without spec — confusing
class Confusing:
    def __also_mangled__(self):  # actually NOT mangled because trailing __ prevents mangling
        ...
```

### Name Mangling vs Dunder

```python
class Demo:
    __mangled = 1        # -> _Demo__mangled
    __dunder__ = 2       # unchanged — recognized as special
    __private = 3        # -> _Demo__private
    __init__ = 4         # unchanged

print([x for x in dir(Demo) if "mangled" in x.lower() or "dunder" in x.lower() or "private" in x.lower()])
# ['_Demo__mangled', '_Demo__private', '__dunder__']
```

Only names with **exactly** two leading and two trailing underscores and at least one interior character are considered special and exempt from mangling.

## A Progression of Realistic Examples

We move from the simplest possible protocol use to a realistic, multi-protocol type. This preview motivates every later lesson.

### Example 1: The Minimal Protocol — `__len__` and `__bool__`

```python
class TrainCar:
    """A railway car carrying cargo. Truthiness means non-empty."""
    def __init__(self, cargo: list[str]):
        self.cargo = list(cargo)

    def __len__(self) -> int:
        return len(self.cargo)

    # No __bool__ — Python falls back to __len__:
    #   bool(car) == (len(car) != 0)

empty = TrainCar([])
loaded = TrainCar(["coal", "steel"])
print(bool(empty), bool(loaded))   # False True
print(len(loaded))                 # 2

# Edge: if neither __bool__ nor __len__ exists, every instance is truthy
class AlwaysTruthy:
    pass
print(bool(AlwaysTruthy()))        # True
```

### Example 2: Two Protocols Together — Container + Iterable

```python
from collections.abc import Sequence
from typing import Iterator

class Playlist:
    """A music playlist that behaves like a read-only sequence."""
    def __init__(self, tracks: list[str]):
        self._tracks = list(tracks)

    def __len__(self) -> int:
        return len(self._tracks)

    def __getitem__(self, index):
        # Supports int indexing, slicing, and negative indices for free
        # because we delegate to the underlying list.
        return self._tracks[index]

    def __contains__(self, track: object) -> bool:
        # Optimize membership: faster than iterating via __getitem__
        return track in self._tracks

    def __iter__(self) -> Iterator[str]:
        return iter(self._tracks)

    def __repr__(self) -> str:
        return f"Playlist({self._tracks!r})"

pl = Playlist(["A", "B", "C"])
print(pl[1])            # B
print(pl[-1])           # C — negative index works via list delegation
print(pl[1:])           # ['B', 'C'] — slice support
print("B" in pl)        # True
print(list(pl))         # ['A', 'B', 'C']
print(repr(pl))         # Playlist(['A', 'B', 'C'])

# Bonus: without __iter__, Python would iterate via __getitem__ from 0 until IndexError.
# Defining __iter__ is faster and allows non-integer iterables.
```

### Example 3: Making Something Callable

```python
class Retry:
    """A callable that retries a function up to N times."""
    def __init__(self, attempts: int = 3):
        self.attempts = attempts

    def __call__(self, func):
        """Use as @Retry(attempts=5) decorator or Retry()(func)()."""
        import functools, time
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exc = None
            for n in range(self.attempts):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    last_exc = e
                    time.sleep(0.1 * (2 ** n))
            raise last_exc
        return wrapper

# As decorator factory:
@Retry(attempts=3)
def flaky():
    import random
    if random.random() < 0.7:
        raise RuntimeError("flaky!")
    return "ok"

# As callable object:
counter = Retry(attempts=2)
print(callable(counter))   # True
```

### Example 4: Full Preview — A Domain Type Using Many Protocols

```python
from __future__ import annotations
import math
from functools import total_ordering

@total_ordering
class Vector:
    """2-D vector: arithmetic + equality + ordering by magnitude + hashing + formatting."""

    __slots__ = ("_x", "_y")   # memory optimization (lesson 13.15)

    def __init__(self, x: float, y: float):
        self._x = float(x)
        self._y = float(y)

    # Representation
    def __repr__(self) -> str:
        return f"Vector({self._x!r}, {self._y!r})"
    def __str__(self) -> str:
        return f"({self._x}, {self._y})"
    def __format__(self, spec: str) -> str:
        if spec == "polar":
            r = math.hypot(self._x, self._y)
            theta = math.degrees(math.atan2(self._y, self._x))
            return f"{r:.2f}@{theta:.1f}°"
        return str(self).__format__(spec)

    # Container-like access
    def __len__(self) -> int:
        return 2
    def __getitem__(self, index: int) -> float:
        if index in (0, -2):
            return self._x
        if index in (1, -1):
            return self._y
        raise IndexError("Vector index out of range")
    def __iter__(self):
        yield self._x
        yield self._y

    # Arithmetic
    def __add__(self, other: Vector) -> Vector:
        if isinstance(other, Vector):
            return Vector(self._x + other._x, self._y + other._y)
        return NotImplemented
    __radd__ = __add__  # commutative

    def __mul__(self, scalar: float) -> Vector:
        if isinstance(scalar, (int, float)):
            return Vector(self._x * scalar, self._y * scalar)
        return NotImplemented
    __rmul__ = __mul__

    def __abs__(self) -> float:
        return math.hypot(self._x, self._y)

    # Comparison
    def __eq__(self, other: object) -> bool:
        if isinstance(other, Vector):
            return math.isclose(self._x, other._x) and math.isclose(self._y, other._y)
        return NotImplemented

    def __lt__(self, other: Vector) -> bool:
        if isinstance(other, Vector):
            return abs(self) < abs(other)
        return NotImplemented

    def __hash__(self) -> int:
        return hash((self._x, self._y))

    # Callable: projection onto direction
    def __call__(self, scalar: float) -> Vector:
        """Scale the vector: v(2) == v * 2."""
        return self * scalar

v = Vector(3, 4)
print(repr(v))              # Vector(3.0, 4.0)
print(f"{v:polar}")         # 5.00@53.1°
print(v + Vector(1, 1))     # (4.0, 5.0)
print(v * 2)                # (6.0, 8.0)
print(3 * v)                # (6.0, 12.0)
print(abs(v))               # 5.0
print(v(0.5))               # (1.5, 2.0)
print(Vector(3, 4) == Vector(3, 4))  # True
print(hash(v))              # usable as dict key
print(sorted([Vector(3,4), Vector(1,1), Vector(0,5)]))  # sorted by magnitude
```

This example touches 14 different dunder methods — and that is still not exhaustive. Every later lesson deep-dives one protocol family.

## Distinctions That Confuse Learners (from Other Languages)

### Python vs Java / C# / C++

| Concern | Java/C# | Python |
|---------|---------|--------|
| Operator overloading | Forbidden (Java) or verbose (C# `operator+`) | Natural via `__add__` etc.; any type can participate |
| Interfaces/protocols | Explicit `implements List<T>` | Informal — if you implement `__len__` and `__getitem__`, you *are* a sequence |
| Truthiness | `if (obj != null)` | `if obj:` calls `__bool__`/`__len__`; empty containers are falsy |
| Equality | `equals()` + `hashCode()` contract | `__eq__` + `__hash__` contract — identical logic, different names |
| Constructors | `new Cls()` calls constructor | `Cls()` calls `__new__` then `__init__` — two phases |
| Callable objects | Single-method interface (`Runnable`) | `__call__` — instance *is* a function, holds state |
| `toString()` | `toString()` | `__repr__` (developer) + `__str__` (user) — two methods, not one |
| Resource management | `try/finally`, `using`/`try-with-resources` | `with` + `__enter__`/`__exit__` |
| Static typing | Nominal | Structural for protocols (`collections.abc`, `typing.Protocol`) |

### Duck Typing and Protocols

Python's philosophy: **if it walks like a duck and quacks like a duck, it's a duck.** Formalized since Python 3.8 via `typing.Protocol` and since earlier via `collections.abc`:

```python
from collections.abc import Sequence, Mapping
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> None: ...

def render(obj: Drawable) -> None:
    obj.draw()  # Any object with draw() qualifies — no inheritance needed

# Likewise for special methods:
def total_length(items) -> int:
    # Works with any object that implements __len__ + __iter__
    return sum(len(x) for x in items)

# collections.abc lets you test protocol membership:
print(isinstance([1,2], Sequence))   # True
print(isinstance("hello", Sequence)) # True — strings are sequences!
```

Special methods are the foundation of duck typing. You do not declare "I am iterable"; you implement `__iter__` and you *are* iterable.

## How to Discover What Python Will Call

### Introspection Toolkit

```python
class Example:
    def __len__(self): return 1
    def __iter__(self): return iter([])
    def __getitem__(self, k): return k

e = Example()

# What special methods does the type define?
print([m for m in dir(type(e)) if m.startswith("__") and m.endswith("__")])

# What does the class dictionary contain?
print(Example.__dict__.keys())

# What protocol does an object satisfy?
from collections.abc import Sized, Iterable, Container
print(isinstance(e, Sized))      # True — has __len__
print(isinstance(e, Iterable))   # True — has __iter__

# What slot wrappers exist on the type?
print(type(e).__len__)   # <slot wrapper '__len__' of 'Example' objects>
```

### The Single Most Useful Debugging Exercise

When `len(obj)` raises `TypeError: object of type 'X' has no len()`, Python is telling you `type(obj).__len__` does not exist or returned a non-int. The traceback will not mention `__len__` — you must know the mapping table. Keep it bookmarked.

## Performance and Memory Considerations

*   **Slot dispatch is O(1).** Calling `len(obj)` via `type(obj).__len__` is a C-level slot lookup, not a Python dict lookup. Overriding `__len__` in Python adds a Python call overhead (~50–100 ns extra) but remains fast.
*   **`__getattr__`/`__getattribute__` are hot paths.** They run on *every* attribute access if defined naively. A heavy `__getattribute__` can dominate runtime. Prefer descriptors or `__getattr__` fallback over universal interception unless necessary.
*   **`__slots__` (lesson 13.15)** eliminates per-instance `__dict__` by declaring fixed attributes. This saves ~50–100 bytes per instance and speeds attribute access ~15–30 %. It interacts with special methods in subtle ways (e.g., `__weakref__` slot, `__dict__` slot).
*   **Don't over-implement.** Every dunder has a cost in cognitive load. Implement only the protocol your type semantically satisfies. A `BankAccount` should not implement `__iter__` just because it can.

## Common Mistakes — A Preview

| Mistake | What Goes Wrong | Fix |
|---------|-----------------|-----|
| Defining `__eq__` without `__hash__` | Instances become unhashable (`TypeError: unhashable type`) | Define `__hash__` explicitly or set `__hash__ = None` |
| `__hash__` on mutable object | Hash changes after insertion into dict/set — item "lost" | Make type immutable or set `__hash__ = None`; use frozen dataclass |
| `__bool__` returning non-bool | Works but confusing; `bool(obj)` may not be `True`/`False` singleton | Always `return True`/`False` explicitly |
| Patching `instance.__len__` | `len(instance)` ignores it | Patch on the class: `Type.__len__ = ...` |
| Inventing `__my_hook__` | Never called by syntax | Use normal method names |
| `__getattribute__` without `object.__getattribute__` fallback | Infinite recursion | Delegate: `object.__getattribute__(self, name)` |
| Returning `None` instead of `NotImplemented` in `__eq__`/`__add__` | Prevents reflected operation (`__radd__`, `__eq__` on other type) from running | `return NotImplemented` for unsupported types |
| `__del__` for resource cleanup | Non-deterministic, may not run, resurrects objects | Use `__enter__`/`__exit__`, `weakref.finalize`, or `atexit` |
