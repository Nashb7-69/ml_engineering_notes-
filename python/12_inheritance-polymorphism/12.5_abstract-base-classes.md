# 12.5 Abstract Base Classes

## Learning Objectives

By the end of this lesson you will be able to:

- Define abstract base classes (ABCs) with `abc.ABC` and `@abstractmethod`.
- Prevent instantiation of abstract classes and enforce subclass contracts.
- Use `@abstractproperty`, `@abstractclassmethod`, `@abstractstaticmethod` (and their modern replacements).
- Leverage `collections.abc` ABCs (`Sequence`, `Mapping`, `Set`, etc.) for interface reuse.
- Register virtual subclasses with `ABC.register()` without inheritance.
- Decide when to use an ABC vs. a Protocol (Lesson 12.6) vs. duck typing (Lesson 12.4).

---

## 1. Why Abstract Base Classes?

Duck typing (Lesson 12.4) is powerful but has a weakness: **the contract is invisible**. Nothing declares "a `PaymentProcessor` must have `charge()` and `refund()`." You discover violations at runtime, when a missing method raises `AttributeError` deep in a call stack.

Abstract Base Classes make the contract **explicit and enforced**:

| Approach | Contract Visibility | Enforcement Time | Coupling |
|----------|---------------------|------------------|----------|
| Duck typing | Implicit — read the code/docs | Runtime (when method is called) | None |
| ABC | Explicit — abstract methods declared | Class definition + instantiation time | Nominal (must inherit or register) |
| Protocol (Lesson 12.6) | Explicit — structural | Static type checker time (mypy/pyright) + optional runtime | Structural (no inheritance needed) |

**Mental model:** An ABC is a *template with blanks*. It says "every concrete subclass must fill in these blanks (abstract methods) before it can be instantiated." It is Python's answer to Java interfaces and C++ pure virtual classes — but more flexible.

### 1.1 What Problem Do ABCs Solve?

1. **Fail fast:** Catch missing implementations at instantiation, not at call time.
2. **Self-documenting:** The ABC's abstract methods *are* the interface documentation.
3. **Shared concrete logic:** ABCs can provide concrete methods built on top of abstract ones (Template Method pattern).
4. **Type checking:** `isinstance(obj, MyABC)` works, including for virtual subclasses.
5. **Framework enforcement:** Libraries (e.g., `collections.abc`, `io`, `numbers`) use ABCs to define extension points.

## 2. Defining an ABC — `abc.ABC` and `@abstractmethod`

### 2.1 Minimal Example

```python
from abc import ABC, abstractmethod

class PaymentProcessor(ABC):
    """Abstract payment processor — subclasses must implement charge and refund."""

    @abstractmethod
    def charge(self, amount: float) -> str:
        """Charge the given amount. Return a transaction ID."""
        ...

    @abstractmethod
    def refund(self, transaction_id: str, amount: float) -> str:
        """Refund amount for the given transaction. Return a refund ID."""
        ...

# Cannot instantiate the ABC itself:
try:
    PaymentProcessor()
except TypeError as e:
    print(e)  # Can't instantiate abstract class PaymentProcessor with abstract methods charge, refund

# Subclass that forgets a method — also cannot be instantiated:
class IncompleteProcessor(PaymentProcessor):
    def charge(self, amount: float) -> str:
        return f"charged {amount}"

try:
    IncompleteProcessor()
except TypeError as e:
    print(e)  # Can't instantiate abstract class IncompleteProcessor with abstract method refund

# Complete subclass — works:
class CardProcessor(PaymentProcessor):
    def charge(self, amount: float) -> str:
        return f"card-txn-{amount:.0f}"

    def refund(self, transaction_id: str, amount: float) -> str:
        return f"card-refund-{amount:.0f}"

print(CardProcessor().charge(100))  # card-txn-100
print(isinstance(CardProcessor(), PaymentProcessor))  # True
```

Explanation:

- `class PaymentProcessor(ABC)` — inheriting from `ABC` marks the class as abstract. Equivalently, `class PaymentProcessor(metaclass=ABCMeta)`.
- `@abstractmethod` on `charge` and `refund` marks them as required. The ABC tracks them in `PaymentProcessor.__abstractmethods__`.
- Attempting to instantiate a class with unimplemented abstract methods raises `TypeError` immediately — no need to wait for a method call.

### 2.2 How It Works Under the Hood

```python
from abc import ABC, abstractmethod

class MyABC(ABC):
    @abstractmethod
    def required(self): ...

print(MyABC.__abstractmethods__)          # frozenset({'required'})
print(MyABC.__abstractmethods__)          # frozenset({'required'})

class Child(MyABC):
    def required(self): return 42

print(Child.__abstractmethods__)          # frozenset() — empty, all implemented
print(Child().__class__.__abstractmethods__)  # frozenset()

# The check happens in ABCMeta.__call__ (the class's constructor):
# if cls.__abstractmethods__: raise TypeError(...)
```

The enforcement is done by the metaclass `ABCMeta`. When you call `MyClass()`, `ABCMeta.__call__` checks `__abstractmethods__` before delegating to `__new__`/`__init__`.

### 2.3 ABCs Can Have Concrete Methods (Template Method Pattern)

```python
from abc import ABC, abstractmethod

class DataParser(ABC):
    """Template: subclasses provide parse_line, ABC provides parse_all."""

    @abstractmethod
    def parse_line(self, line: str) -> dict:
        """Parse a single line into a dict."""
        ...

    def parse_all(self, text: str) -> list[dict]:
        """Concrete method built on the abstract one."""
        return [self.parse_line(line) for line in text.strip().splitlines() if line.strip()]

    def parse_file(self, path: str) -> list[dict]:
        with open(path) as f:
            return self.parse_all(f.read())

class CSVParser(DataParser):
    def parse_line(self, line: str) -> dict:
        keys = ["name", "age", "city"]
        values = line.split(",")
        return dict(zip(keys, values))

class JSONLineParser(DataParser):
    def parse_line(self, line: str) -> dict:
        import json
        return json.loads(line)

csv = CSVParser()
print(csv.parse_all("Alice,30,NYC\nBob,25,LA"))
# [{'name': 'Alice', 'age': '30', 'city': 'NYC'}, {'name': 'Bob', 'age': '25', 'city': 'LA'}]
```

The ABC provides `parse_all` and `parse_file` for free — subclasses only implement `parse_line`. This is the **Template Method** pattern: the ABC defines the algorithm skeleton, subclasses fill in the steps.

### 2.4 Abstract Properties, Class Methods, and Static Methods

#### Modern Syntax (Python 3.3+)

The `@abstractproperty`, `@abstractclassmethod`, `@abstractstaticmethod` decorators are **deprecated** since Python 3.3. Use the stacked form:

```python
from abc import ABC, abstractmethod

class Configurable(ABC):
    @property
    @abstractmethod
    def config(self) -> dict:
        """Subclasses must provide a config property."""
        ...

    @classmethod
    @abstractmethod
    def from_config(cls, config: dict) -> "Configurable":
        """Subclasses must provide a from_config constructor."""
        ...

    @staticmethod
    @abstractmethod
    def validate(config: dict) -> bool:
        """Subclasses must provide validation logic."""
        ...

class MyConfig(Configurable):
    def __init__(self, config: dict):
        self._config = config

    @property
    def config(self) -> dict:
        return self._config

    @classmethod
    def from_config(cls, config: dict) -> "MyConfig":
        if not cls.validate(config):
            raise ValueError("Invalid config")
        return cls(config)

    @staticmethod
    def validate(config: dict) -> bool:
        return "name" in config

print(MyConfig.from_config({"name": "test"}).config)  # {'name': 'test'}
```

**Decorator order matters:**

| Desired Abstract | Correct Order | Wrong Order |
|------------------|---------------|-------------|
| Abstract property | `@property` then `@abstractmethod` | `@abstractmethod` then `@property` — `abstractmethod` would wrap the property object incorrectly in older Python |
| Abstract classmethod | `@classmethod` then `@abstractmethod` | Reversed — same issue |
| Abstract staticmethod | `@staticmethod` then `@abstractmethod` | Reversed |

In modern Python (3.3+), the order of `@abstractmethod` relative to `@classmethod`/`@staticmethod`/`@property` is more forgiving, but `@property` must be outermost for properties. Stick to the table above for clarity.

#### Deprecated Syntax (Still Seen in Legacy Code)

```python
from abc import abstractproperty, abstractclassmethod, abstractstaticmethod
# Deprecated — do not use in new code, but recognize in old code:

class OldStyle(ABC):
    @abstractproperty
    def name(self): ...

    @abstractclassmethod
    def create(cls): ...

    @abstractstaticmethod
    def helper(): ...
```

If you see `abstractproperty` in a codebase, it is equivalent to `@property @abstractmethod` and should be modernized.

### 2.5 Abstract `__init__`

An ABC can have an abstract `__init__` — but be careful:

```python
from abc import ABC, abstractmethod

class Base(ABC):
    @abstractmethod
    def __init__(self, name: str):
        self.name = name  # concrete body — still abstract!

class Child(Base):
    def __init__(self, name: str):
        super().__init__(name)  # must call super().__init__ to get self.name

print(Child("Alice").name)  # Alice
```

An abstract `__init__` with a body is unusual but valid: it provides shared initialization logic that subclasses must still explicitly opt into by defining their own `__init__` and calling `super().__init__()`. The abstract flag just forces subclasses to define `__init__` — it does not prevent the ABC's `__init__` body from running when called via `super()`.

## 3. Instantiation Prevention — How and When It Fires

### 3.1 What Triggers the Check

```python
from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self): ...

class Circle(Drawable):
    pass  # forgot draw()

# No error at class definition time:
print("Circle defined successfully")  # this prints — no error yet

# Error at instantiation time:
try:
    Circle()
except TypeError as e:
    print(e)  # Can't instantiate abstract class Circle with abstract method draw

# Subclasses of abstract classes are themselves abstract until all methods are implemented:
class PartialCircle(Drawable):
    def draw(self): print("Drawing circle")

print(PartialCircle())  # works — all abstract methods implemented
```

**Key point:** The error is at *instantiation*, not at *class definition*. You can define an incomplete subclass without error — you just cannot create an instance of it. This allows intermediate abstract classes:

```python
class Shape(ABC):
    @abstractmethod
    def area(self): ...
    @abstractmethod
    def perimeter(self): ...

class Polygon(Shape):
    @abstractmethod
    def num_sides(self): ...
    # Still abstract — area, perimeter, and num_sides all abstract
    # But no error defining Polygon

class Triangle(Polygon):
    def area(self): return 0.5 * self.base * self.height
    def perimeter(self): return self.a + self.b + self.c
    def num_sides(self): return 3
    def __init__(self, a, b, c, base, height):
        self.a = a; self.b = b; self.c = c
        self.base = base; self.height = height

print(Triangle(3, 4, 5, 4, 3).area())  # 6.0
```

### 3.2 Checking Abstract Status Programmatically

```python
import inspect

print(inspect.isabstract(Drawable))      # True
print(inspect.isabstract(Circle))        # True — still has abstract methods
print(inspect.isabstract(PartialCircle)) # False — fully implemented

# Also:
print(hasattr(Circle, "__abstractmethods__"))
print(Circle.__abstractmethods__)        # frozenset({'draw'})
print(bool(Circle.__abstractmethods__))  # True — abstract
print(bool(PartialCircle.__abstractmethods__))  # False — concrete
```

### 3.3 Abstract Methods Can Have Implementations

An `@abstractmethod` can have a body. Subclasses must still override it, but they can call the abstract implementation via `super()`:

```python
from abc import ABC, abstractmethod

class Encoder(ABC):
    @abstractmethod
    def encode(self, data: str) -> str:
        """Encode data. Subclasses must override but can call super().encode()."""
        # Default: basic escaping
        return data.replace("&", "&amp;").replace("<", "&lt;")

class HTMLEncoder(Encoder):
    def encode(self, data: str) -> str:
        # Use default escaping, then add HTML-specific logic
        base = super().encode(data)
        return base.replace('"', "&quot;")

print(HTMLEncoder().encode('Say "hi" & <bye>'))
# Say &quot;hi&quot; &amp; &lt;bye&gt;
```

This pattern says: "You must explicitly override `encode`, but here is a useful default you can delegate to." It forces the subclass author to make a conscious decision rather than silently inheriting a default.

## 4. `collections.abc` — The Standard Library's ABC Showcase

### 4.1 Why `collections.abc` Matters

`collections.abc` provides ABCs for every major Python container concept. They serve two purposes:

1. **Interface definition:** Inherit from them to declare "I am a Sequence/Mapping/Set."
2. **Mixin functionality:** They provide concrete methods built on a minimal abstract core.

### 4.2 The Hierarchy

```
Iterable
  └── Collection
        ├── Sequence  (list, tuple, str)
        │     └── MutableSequence  (list)
        ├── Mapping  (dict)
        │     └── MutableMapping  (dict)
        ├── Set  (set, frozenset)
        │     └── MutableSet  (set)
        └── ...
```

### 4.3 `Sequence` — Implement `__getitem__` and `__len__`, Get Everything Else

```python
from collections.abc import Sequence

class EvenNumbers(Sequence):
    """A virtual sequence of even numbers 0, 2, 4, ..., 2*(n-1)."""

    def __init__(self, n: int):
        self.n = n

    def __getitem__(self, index):
        if isinstance(index, slice):
            # Handle slicing — delegate to range for simplicity
            return [self[i] for i in range(*index.indices(len(self)))]
        if index < 0:
            index += len(self)
        if not 0 <= index < len(self):
            raise IndexError(index)
        return index * 2

    def __len__(self) -> int:
        return self.n

evens = EvenNumbers(5)
print(list(evens))          # [0, 2, 4, 6, 8] — __iter__ provided by Sequence
print(evens[2])             # 4
print(evens[1:4])           # [2, 4, 6] — via __getitem__ slice handling
print(3 in evens)           # False — __contains__ provided (linear scan)
print(4 in evens)           # True
print(evens.index(6))       # 3 — provided
print(evens.count(4))       # 1 — provided
print(isinstance(evens, Sequence))  # True
```

`Sequence` requires only `__getitem__` and `__len__`. It provides `__iter__`, `__contains__`, `index`, `count`, and `__reversed__` for free.

### 4.4 `MutableMapping` — The Dict Interface

```python
from collections.abc import MutableMapping

class CaseInsensitiveDict(MutableMapping):
    def __init__(self):
        self._data: dict[str, str] = {}

    def __getitem__(self, key: str) -> str:
        return self._data[key.lower()]

    def __setitem__(self, key: str, value: str) -> None:
        self._data[key.lower()] = value

    def __delitem__(self, key: str) -> None:
        del self._data[key.lower()]

    def __iter__(self):
        return iter(self._data)

    def __len__(self) -> int:
        return len(self._data)

# MutableMapping provides: get, keys, values, items, pop, popitem, clear, update, setdefault
d = CaseInsensitiveDict()
d["Hello"] = "world"
print(d["HELLO"])              # world
print(d.get("hello"))          # world
print(d.get("missing", "default"))  # default
print(list(d.keys()))          # ['hello']
print("hello" in d)            # True — __contains__ via __getitem__ try/except
d.update({"Foo": "bar", "HELLO": "updated"})
print(d["hello"])              # updated
print(d.pop("foo"))            # bar
```

Abstract methods for `MutableMapping`: `__getitem__`, `__setitem__`, `__delitem__`, `__iter__`, `__len__`. Everything else is a mixin.

### 4.5 Other `collections.abc` ABCs

| ABC | Required Abstract Methods | Provides (Mixin) | Example |
|-----|---------------------------|------------------|---------|
| `Iterable` | `__iter__` | — | Any for-loop target |
| `Iterator` | `__next__`, `__iter__` | `__iter__` returns self | Generators |
| `Sized` | `__len__` | — | `len()` support |
| `Container` | `__contains__` | — | `in` operator |
| `Collection` | `__iter__`, `__len__`, `__contains__` | — | `Sized` + `Iterable` + `Container` |
| `Sequence` | `__getitem__`, `__len__` | `__iter__`, `__contains__`, `index`, `count`, `__reversed__` | `list`, `tuple` |
| `MutableSequence` | + `__setitem__`, `__delitem__`, `insert` | `append`, `reverse`, `extend`, `pop`, `remove` | `list` |
| `Mapping` | `__getitem__`, `__iter__`, `__len__` | `get`, `keys`, `values`, `items`, `__contains__` | `dict` (read-only view) |
| `MutableMapping` | + `__setitem__`, `__delitem__` | `pop`, `update`, `setdefault`, `clear` | `dict` |
| `Set` | `__iter__`, `__len__`, `__contains__` | `__and__`, `__or__`, `__sub__`, `__xor__`, `isdisjoint` | `frozenset` |
| `MutableSet` | + `add`, `discard` | `pop`, `remove`, `clear`, `update` | `set` |
| `Awaitable` | `__await__` | — | Coroutines |
| `Coroutine` | `send`, `throw`, `close`, `__await__` | — | `async def` |

### 4.6 `numbers` — Numeric Tower

```python
from numbers import Number, Integral, Real

print(isinstance(42, Integral))   # True
print(isinstance(3.14, Real))     # True
print(isinstance(3.14, Integral)) # False
print(isinstance(True, Integral)) # True — bool is a subclass of int!
```

The `numbers` ABCs are rarely subclassed directly but are useful for type dispatch.

### 4.7 `io` — I/O Hierarchy

```python
from io import RawIOBase, BufferedIOBase, TextIOBase

# io ABCs define the file-like hierarchy:
# IOBase -> RawIOBase, BufferedIOBase, TextIOBase
# Useful for checking file-like capabilities:
import io
print(isinstance(open("/dev/null"), io.IOBase))  # True
print(isinstance(io.StringIO(), io.TextIOBase))   # True
```

## 5. Virtual Subclasses — `register()` Without Inheritance

### 5.1 The Problem `register()` Solves

Sometimes you want `isinstance(obj, MyABC)` to return `True` for a class that does *not* inherit from `MyABC` — perhaps because it comes from a third-party library or you want to avoid coupling.

```python
from abc import ABC, abstractmethod

class Barkable(ABC):
    @abstractmethod
    def bark(self) -> str: ...

# Third-party class — cannot modify to inherit from Barkable
class ThirdPartyDog:
    def bark(self) -> str:
        return "Woof!"

# Without register:
print(isinstance(ThirdPartyDog(), Barkable))  # False — no inheritance

# With register — virtual subclass:
Barkable.register(ThirdPartyDog)

print(isinstance(ThirdPartyDog(), Barkable))  # True — virtual subclass!
print(issubclass(ThirdPartyDog, Barkable))    # True
```

Explanation:

- `Barkable.register(ThirdPartyDog)` adds `ThirdPartyDog` to `Barkable`'s virtual subclass registry.
- `isinstance` and `issubclass` check this registry in addition to the MRO.
- **No inheritance is created.** `ThirdPartyDog.__mro__` does not include `Barkable`. `ThirdPartyDog` does not gain any methods from `Barkable`.
- Abstract method checking is **not enforced** for virtual subclasses — you could register a class that does not implement `bark()`, and `isinstance` would still return `True`. The ABC trusts you.

### 5.2 `register` as a Decorator

```python
from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self) -> str: ...

@Drawable.register
class Circle:
    def draw(self) -> str:
        return "Drawing circle"

print(isinstance(Circle(), Drawable))  # True
```

### 5.3 Virtual Subclasses and `__subclasshook__`

For more dynamic virtual subclassing, override `__subclasshook__` to make `isinstance` structural:

```python
from abc import ABC, abstractmethod

class Sized(ABC):
    @abstractmethod
    def __len__(self) -> int: ...

    @classmethod
    def __subclasshook__(cls, C):
        if cls is Sized:
            if any("__len__" in B.__dict__ for B in C.__mro__):
                return True
        return NotImplemented

class MyCollection:
    def __len__(self): return 42

print(isinstance(MyCollection(), Sized))  # True — has __len__, no inheritance needed!
print(issubclass(MyCollection, Sized))    # True

class NoLen: pass
print(isinstance(NoLen(), Sized))         # False — no __len__
```

`__subclasshook__` is how `collections.abc` ABCs work — `isinstance([], Sequence)` is `True` not because `list` inherits from `Sequence`, but because `Sequence.__subclasshook__` checks for `__getitem__` and `__len__`.

**Important nuances:**

| Aspect | `register()` | `__subclasshook__` |
|--------|--------------|---------------------|
| Mechanism | Explicit registration | Dynamic check on every `isinstance`/`issubclass` |
| Performance | Fast (registry lookup) | Slower (inspects `__mro__`/`__dict__`) |
| Enforcement | No abstract method check | No abstract method check — just structural presence |
| Use case | Known external class to associate with ABC | Open-ended structural check ("anything with `__len__` is Sized") |

### 5.4 When `register()` Is Useful vs. Misleading

**Good uses:**

```python
# Adapting third-party types to your ABC without modifying them
import numpy as np
from collections.abc import Sequence

# numpy arrays are sequences but don't inherit from Sequence on all Python versions
Sequence.register(np.ndarray)  # if needed — modern numpy already does this
```

**Bad uses:**

```python
# Registering a class that doesn't actually satisfy the contract — lies to isinstance
class NotReallyBarkable:
    pass  # no bark()!

Barkable.register(NotReallyBarkable)
print(isinstance(NotReallyBarkable(), Barkable))  # True — but .bark() will fail!
# This defeats the purpose of the ABC. Don't register non-conforming classes.
```

## 6. ABC vs Concrete — Design Patterns

### 6.1 Pure Abstract ABC (Interface Only)

```python
from abc import ABC, abstractmethod

class Serializer(ABC):
    @abstractmethod
    def serialize(self, obj) -> str: ...

    @abstractmethod
    def deserialize(self, data: str): ...
```

No concrete methods — purely a contract. Equivalent to a Java interface or a `Protocol` (Lesson 12.6).

### 6.2 ABC With Concrete Helpers (Template Method)

```python
from abc import ABC, abstractmethod

class Validator(ABC):
    @abstractmethod
    def validate(self, value) -> bool: ...

    def validate_all(self, values) -> dict:
        return {v: self.validate(v) for v in values}

    def assert_valid(self, value) -> None:
        if not self.validate(value):
            raise ValueError(f"Invalid value: {value!r}")

class EmailValidator(Validator):
    def validate(self, value) -> bool:
        return "@" in value and "." in value
```

### 6.3 ABC With `__init__` and State

```python
from abc import ABC, abstractmethod

class Account(ABC):
    def __init__(self, balance: float = 0):
        if balance < 0:
            raise ValueError("balance must be >= 0")
        self.balance = balance

    @abstractmethod
    def apply_interest(self) -> None: ...

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")
        self.balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount

class SavingsAccount(Account):
    rate = 0.02

    def apply_interest(self) -> None:
        self.balance *= 1 + self.rate

class CheckingAccount(Account):
    def apply_interest(self) -> None:
        pass  # no interest — but must still implement the method

print(SavingsAccount(1000).balance)  # 1000
s = SavingsAccount(1000)
s.apply_interest()
print(s.balance)  # 1020.0
```

The ABC owns shared state (`balance`) and concrete methods (`deposit`, `withdraw`), while requiring subclasses to implement `apply_interest`.

### 6.4 Intermediate Abstract Classes

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Polygon(Shape):
    @abstractmethod
    def num_sides(self) -> int: ...

    def is_triangle(self) -> bool:
        return self.num_sides() == 3

# Polygon is still abstract — cannot instantiate until area + num_sides are implemented
class Triangle(Polygon):
    def __init__(self, base, height):
        self.base = base; self.height = height
    def area(self) -> float:
        return 0.5 * self.base * self.height
    def num_sides(self) -> int:
        return 3
```

## 7. When to Use ABC vs Protocol vs Duck Typing

| Criterion | ABC | Protocol (Lesson 12.6) | Duck Typing |
|-----------|-----|------------------------|-------------|
| **Contract explicit?** | Yes — abstract methods | Yes — protocol members | No — implicit |
| **Enforcement** | Runtime (`TypeError` at instantiation) | Static (mypy/pyright), optional runtime with `@runtime_checkable` | Runtime (`AttributeError` at call) |
| **Requires inheritance?** | Yes (or `register`) | No — structural | No |
| **Provides mixin methods?** | Yes — concrete methods in ABC | No — protocols should not have logic | No |
| **Supports virtual subclasses?** | Yes — `register` + `__subclasshook__` | No (but `isinstance` with `@runtime_checkable`) | N/A |
| **Third-party adaptation** | `register()` (no modification) | Nothing needed (structural) | Nothing needed |
| **Best for** | Framework extension points, Template Method, shared logic + required interface | Decoupled interfaces, type-safe duck typing, library APIs | Internal code, simple cases, rapid prototyping |

### Decision Guide

```
Need an interface contract?
├── Need shared concrete logic / Template Method / mixin helpers?
│   └── Yes → ABC
├── Need to adapt third-party classes without modifying them?
│   ├── And need isinstance checks at runtime? → ABC with register() or Protocol with @runtime_checkable
│   └── Only need static checking? → Protocol (preferred — no registration)
├── Need runtime isinstance without static checking?
│   └── ABC (or @runtime_checkable Protocol for structural check)
├── Simple internal code, one or two methods?
│   └── Duck typing (EAFP) — no ABC/Protocol overhead
└── Library public API where callers shouldn't need to inherit?
    └── Protocol — least coupling
```

### Example: Same Contract, Three Ways

```python
# 1. ABC — nominal, requires inheritance
from abc import ABC, abstractmethod

class RendererABC(ABC):
    @abstractmethod
    def render(self) -> str: ...

class HTMLRenderer(RendererABC):
    def render(self) -> str: return "<html>"

# 2. Protocol — structural, no inheritance needed
from typing import Protocol

class RendererProto(Protocol):
    def render(self) -> str: ...

class HTMLRenderer2:  # no base! just has render()
    def render(self) -> str: return "<html>"

def display(r: RendererProto) -> None:  # type checker verifies structural match
    print(r.render())

display(HTMLRenderer2())  # passes type check — structural match

# 3. Duck typing — no contract at all
def display_duck(r) -> None:
    print(r.render())  # just call it — hope it exists

display_duck(HTMLRenderer2())  # works at runtime if render() exists
```

## 8. Common Mistakes and Edge Cases

### 8.1 Forgetting `ABC` Base

```python
from abc import abstractmethod

class Bad(abstractmethod):  # wrong — abstractmethod is a decorator, not a base
    pass

# Correct:
from abc import ABC, abstractmethod

class Good(ABC):
    @abstractmethod
    def method(self): ...
```

Or equivalently:

```python
from abc import ABCMeta, abstractmethod

class Good2(metaclass=ABCMeta):
    @abstractmethod
    def method(self): ...
```

`ABC` is just `class ABC(metaclass=ABCMeta): pass` — a convenience.

### 8.2 Instantiating an ABC Directly

```python
from abc import ABC, abstractmethod

class MyABC(ABC):
    @abstractmethod
    def method(self): ...

MyABC()  # TypeError — always. ABCs are never directly instantiable if they have abstract methods.
```

If an ABC has *no* abstract methods, it *can* be instantiated — but then it is just a regular class.

### 8.3 `@abstractmethod` Without `ABC` Does Nothing

```python
from abc import abstractmethod

class Fake(ABC):  # needs ABC or ABCMeta
    pass

class NotAbstract:
    @abstractmethod
    def method(self): ...  # no error, no enforcement — NotAbstract is not an ABC!

print(NotAbstract().method())  # works (returns None) — @abstractmethod is inert without ABCMeta
```

`@abstractmethod` just sets `__isabstractmethod__ = True` on the function. Only `ABCMeta` checks this flag. Without `ABCMeta`, the flag is ignored.

### 8.4 Abstract Method Called on `super()` Without Override

```python
from abc import ABC, abstractmethod

class Base(ABC):
    @abstractmethod
    def process(self):
        print("Base.process default logic")

class Child(Base):
    def process(self):
        super().process()  # calls Base.process even though it's abstract — works!

Child().process()  # Base.process default logic
```

Abstract methods *can* have bodies and *can* be called via `super()`. The `abstract` flag only prevents instantiation of classes that have not overridden the method — it does not make the method uncallable.

### 8.5 Multiple Inheritance With ABCs — MRO Still Applies

```python
from abc import ABC, abstractmethod

class Drawable(ABC):
    @abstractmethod
    def draw(self): ...

class Movable(ABC):
    @abstractmethod
    def move(self, x, y): ...

class Sprite(Drawable, Movable):
    def draw(self): print("Drawing")
    def move(self, x, y): print(f"Moving to {x},{y}")

print(Sprite.__mro__)
# (Sprite, Drawable, Movable, ABC, object) — ABC appears once via MRO deduplication
print(Sprite.__abstractmethods__)  # frozenset() — all implemented
```

All ABC rules compose with MI and MRO (Lesson 12.2). If `Sprite` missed either `draw` or `move`, it would remain abstract.

## 9. Realistic Example: Plugin System With ABC

```python
from abc import ABC, abstractmethod
from typing import Any

class Plugin(ABC):
    """Base for all plugins. Provides lifecycle hooks."""

    @property
    @abstractmethod
    def name(self) -> str: ...

    @abstractmethod
    def activate(self) -> None: ...

    @abstractmethod
    def execute(self, data: Any) -> Any: ...

    def deactivate(self) -> None:
        """Optional hook — concrete with no-op default."""
        pass

    def __repr__(self) -> str:
        return f"{self.__class__.__name__}(name={self.name!r})"

class UppercasePlugin(Plugin):
    name = "uppercase"

    def activate(self) -> None:
        print(f"[{self.name}] activated")

    def execute(self, data: Any) -> Any:
        return str(data).upper()

class ReversePlugin(Plugin):
    name = "reverse"

    def activate(self) -> None:
        print(f"[{self.name}] activated")

    def execute(self, data: Any) -> Any:
        return str(data)[::-1]

class PluginManager:
    def __init__(self):
        self._plugins: dict[str, Plugin] = {}

    def register(self, plugin: Plugin) -> None:
        if not isinstance(plugin, Plugin):
            raise TypeError(f"Expected Plugin, got {type(plugin).__name__}")
        self._plugins[plugin.name] = plugin
        plugin.activate()

    def run(self, data: Any) -> Any:
        for plugin in self._plugins.values():
            data = plugin.execute(data)
        return data

    def shutdown(self) -> None:
        for plugin in self._plugins.values():
            plugin.deactivate()

manager = PluginManager()
manager.register(UppercasePlugin())
manager.register(ReversePlugin())
print(manager.run("hello"))  # OLLEH — uppercased then reversed
manager.shutdown()

# Enforcement:
class BadPlugin(Plugin):
    name = "bad"
    def activate(self): pass
    # forgot execute() — abstract!

try:
    manager.register(BadPlugin())
except TypeError as e:
    print(e)  # Can't instantiate abstract class BadPlugin with abstract method execute
```

The ABC guarantees that every registered plugin has `name`, `activate`, and `execute` — violations fail at instantiation, not during `manager.run()`.

## 10. Summary

| Concept | Key Takeaway |
|---------|--------------|
| `ABC` + `@abstractmethod` | Declare required methods; instantiation fails if any are unimplemented. |
| `__abstractmethods__` | `frozenset` of remaining abstract method names; empty means concrete. |
| Concrete methods in ABC | Template Method pattern — ABC provides algorithm, subclasses fill in steps. |
| `@property` + `@abstractmethod` | Modern replacement for `@abstractproperty`; order matters. |
| `collections.abc` | Ready-made ABCs that provide mixin implementations for minimal abstract cores. |
| `register()` | Virtual subclass — `isinstance` returns `True` without inheritance; trusts caller. |
| `__subclasshook__` | Dynamic structural check for `isinstance` — used by `collections.abc`. |
| ABC vs Protocol | ABC for shared logic + nominal coupling; Protocol for structural, decoupled contracts. |
