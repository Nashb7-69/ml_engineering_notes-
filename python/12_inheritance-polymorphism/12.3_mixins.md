# 12.3 Mixins

## Learning Objectives

By the end of this lesson you will be able to:

- Define a mixin precisely and distinguish it from base classes and composition.
- Apply the `*Mixin` naming convention and explain why ordering (mixin first) matters.
- Write state-light, cooperative mixins that compose safely.
- Handle method and attribute collisions in mixin hierarchies.
- Recognize and adapt real-world mixin patterns from Django, `collections.abc`, and the standard library.
- Decide between mixin, base class, trait, and composition for a given reuse problem.

## 1. What Is a Mixin?

A **mixin** is a small, focused class that provides a *single orthogonal capability* to be *mixed into* other classes via multiple inheritance. It is not meant to stand alone.

### 1.1 The Five Properties of a Canonical Mixin

| Property | Explanation | Why It Matters |
|----------|-------------|----------------|
| **Small & targeted** | One responsibility — logging, caching, serialization, validation | Keeps MRO predictable; easy to test in isolation |
| **Not standalone** | Cannot be instantiated meaningfully on its own | Signals intent: this is a building block, not an entity |
| **No (or minimal) state** | Ideally no `__init__` state; if state, uses cooperative `**kwargs` | Avoids `__init__` collision and attribute shadowing |
| **Orthogonal** | Does not overlap with other mixins' method names | Prevents accidental override |
| **Cooperative** | Calls `super()` so the MRO chain continues | Composes with other mixins without hard-coded parent calls |

Contrast with adjacent concepts:

| Concept | Purpose | Standalone? | State | Inheritance Role |
|---------|---------|-------------|-------|------------------|
| **Base class** | Defines core is-a identity (`Animal`, `Payment`) | Yes | Yes — owns primary state | First non-mixin in MRO (often last base) |
| **Mixin** | Adds one capability (`Loggable`, `Serializable`) | No | Minimal | Before the base class |
| **Abstract base class** | Defines interface contract | No (cannot instantiate) | None | Base or mixin, but with `@abstractmethod` |
| **Composition (has-a)** | Delegates to a helper object | Helper is standalone | Helper owns state | No inheritance — attribute holds helper |
| **Trait** (other languages) | Like mixin but with conflict resolution | No | Varies | Not native to Python — mixin is the Python trait |

**Mental model:** A base class is the *noun* ("a Document *is a* PersistentObject"). A mixin is an *adjective* ("a Document is *auditable*, *cacheable*, *validatable*"). You stack adjectives before the noun.

### 1.2 A Minimal Mixin

```python
class LoggableMixin:
    """Mixin that adds structured logging to any class with a .save() method."""

    def save(self, *args, **kwargs):
        print(f"[LOG] {self.__class__.__name__}.save called")
        result = super().save(*args, **kwargs)  # type: ignore[misc]
        print(f"[LOG] {self.__class__.__name__}.save completed")
        return result
```

Explanation:

- `LoggableMixin` does not define `__init__` and holds no state — it is purely behavioral.
- It overrides `save()` but delegates via `super().save()` — cooperative, so it composes with any other `save()` provider.
- It has no parent besides `object` and is useless alone (`LoggableMixin().save()` would fail — `object` has no `save`).

Usage:

```python
class Repository:
    def save(self, record: dict) -> None:
        print(f"Saving {record}")

class LoggedRepository(LoggableMixin, Repository):
    pass

LoggedRepository().save({"id": 1})
# [LOG] LoggedRepository.save called
# Saving {'id': 1}
# [LOG] LoggedRepository.save completed
```

## 2. Naming Convention — `*Mixin`

### 2.1 The Convention

By universal Python convention, mixin classes end with `Mixin`:

```python
class CacheMixin: ...
class AuthMixin: ...
class TimestampedMixin: ...
class SerializableMixin: ...
```

Why?

- **Readability:** `class Document(AuditableMixin, CacheableMixin, BaseModel)` instantly signals which bases are mixins vs. the primary base.
- **Tooling:** Linters and type checkers can apply mixin-specific rules (e.g., allow `super()` without knowing the full hierarchy).
- **Documentation:** Readers know not to instantiate `CacheMixin` directly.

Some codebases use `*ableMixin` or `*ibleMixin` (`Cacheable`, `Loggable`) to emphasize capability. Django uses `LoginRequiredMixin`, `PermissionRequiredMixin`, `SuccessMessageMixin`.

### 2.2 What Not to Do

```python
# Bad: no Mixin suffix — looks like a standalone class
class Logger:
    def log(self, msg): ...

# Bad: mixin that sounds like an entity
class User:  # if this is a mixin, the name lies
    def authenticate(self): ...

# Good:
class LoggingMixin:
    def log(self, msg): ...

class AuthMixin:
    def authenticate(self): ...
```

## 3. Ordering — Mixin First, Base Last

### 3.1 The Rule

```python
class MyView(LoginRequiredMixin, CacheMixin, BaseView):
    pass
#        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^
#        mixins first (left)               base last (right)
```

**Why mixins come first:**

- MRO is left-to-right. A mixin listed *before* the base class gets first chance to intercept method calls.
- If the base were first, its method would be found before the mixin's — the mixin would never execute.

```python
class Base:
    def greet(self) -> str:
        return "Base"

class GreetingMixin:
    def greet(self) -> str:
        return "Mixin -> " + super().greet()  # type: ignore[misc]

class Correct(GreetingMixin, Base):
    pass

class Wrong(Base, GreetingMixin):
    pass

print(Correct().greet())  # Mixin -> Base — mixin wraps base
print(Wrong().greet())    # Base — mixin never called!
print(Correct.__mro__)    # (Correct, GreetingMixin, Base, object)
print(Wrong.__mro__)      # (Wrong, Base, GreetingMixin, object)
```

### 3.2 Multiple Mixins — Order Among Themselves Matters

Mixins are applied left-to-right as a pipeline. The leftmost mixin is outermost.

```python
class AuthMixin:
    def handle(self, req): 
        print("Auth check")
        return super().handle(req)  # type: ignore[misc]

class CacheMixin:
    def handle(self, req):
        print("Cache check")
        return super().handle(req)  # type: ignore[misc]

class BaseHandler:
    def handle(self, req): return "200 OK"

# Auth outermost, then Cache, then Base
class Handler1(AuthMixin, CacheMixin, BaseHandler): pass
# Cache outermost, then Auth, then Base
class Handler2(CacheMixin, AuthMixin, BaseHandler): pass

print(Handler1.__mro__)
# (Handler1, AuthMixin, CacheMixin, BaseHandler, object)
# handle() order: Auth -> Cache -> Base

print(Handler2.__mro__)
# (Handler2, CacheMixin, AuthMixin, BaseHandler, object)
# handle() order: Cache -> Auth -> Base
```

In `Handler1`, auth runs even on cache hits. In `Handler2`, cache can short-circuit before auth (see Lesson 12.2, Section 5.4). Choose based on desired semantics.

### 3.3 The "Mixin First" Heuristic Has an Exception

If a mixin is designed to be a *fallback* (provide a default implementation that a base might override), it should come *after* the base. This is rare and should be documented explicitly. Default is mixin-first.

## 4. Mixin vs Base Class vs Composition — Decision Framework

### 4.1 Side-by-Side Comparison

```python
# --- Mixin approach ---
class TimestampedMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        from datetime import datetime
        self.created_at = datetime.now()

class NamedMixin:
    def __init__(self, *, name: str, **kwargs):
        super().__init__(**kwargs)
        self.name = name

class Product(TimestampedMixin, NamedMixin):
    def __init__(self, *, sku: str, **kwargs):
        super().__init__(**kwargs)
        self.sku = sku

# --- Base class approach (single inheritance chain) ---
class Timestamped:
    def __init__(self, name, sku):
        from datetime import datetime
        self.name = name
        self.sku = sku
        self.created_at = datetime.now()

class Product2(Timestamped): pass  # all state in one chain — no reuse

# --- Composition approach ---
from datetime import datetime

class Timestamp:
    def __init__(self):
        self.created_at = datetime.now()

class Product3:
    def __init__(self, name, sku):
        self.name = name
        self.sku = sku
        self.timestamp = Timestamp()  # has-a, not is-a
```

| Criterion | Mixin | Base Class | Composition |
|-----------|-------|------------|-------------|
| Reuse across unrelated hierarchies | Excellent — mix into any class | Poor — requires shared ancestor | Good — inject helper anywhere |
| State ownership | Minimal / none | Primary | Helper owns its state |
| MRO complexity | Adds to MRO — keep mixins small | Single chain — simple | No MRO impact |
| Coupling | Tight (inheritance) but narrow (one capability) | Tight and broad | Loose — depends on interface |
| Testability | Test mixin with a minimal stub base | Test whole hierarchy | Test helper in isolation, mock easily |
| When to choose | Orthogonal, cross-cutting capability | Core identity, is-a | Has-a, or when MI would be confusing |

### 4.2 When Composition Wins Over a Mixin

Use composition when:

- The capability has significant state or lifecycle (e.g., a database connection pool — not a mixin).
- You need runtime swapping (Strategy pattern).
- The MRO would become deep or diamond-heavy.
- You want to avoid any method-name collision risk.

```python
# Composition — no MRO, no super() chain, no collision
class Serializer:
    def serialize(self, obj): return str(obj)

class Document:
    def __init__(self, content: str):
        self.content = content
        self.serializer = Serializer()  # explicit delegate

    def save(self):
        data = self.serializer.serialize(self.content)
        print(f"Saving {data}")
```

### 4.3 When a Mixin Wins Over Composition

Use a mixin when:

- The capability must *intercept* or *wrap* a method defined in the base (e.g., `save`, `dispatch`, `handle`).
- Framework conventions expect mixins (Django CBVs, DRF, `collections.abc`).
- The capability is truly orthogonal and stateless.

## 5. Writing Well-Behaved Mixins — Patterns

### 5.1 Stateless Mixin — Pure Behavior

The simplest and safest kind. No `__init__`, no instance attributes.

```python
class ReprMixin:
    """Adds a useful __repr__ based on __dict__."""

    def __repr__(self) -> str:
        attrs = ", ".join(f"{k}={v!r}" for k, v in self.__dict__.items())
        return f"{self.__class__.__name__}({attrs})"

class Point(ReprMixin):
    def __init__(self, x: float, y: float):
        self.x = x
        self.y = y

print(Point(1, 2))  # Point(x=1, y=2)
```

No `super()` needed here because `__repr__` is a leaf — it does not need to chain. But if another mixin also provides `__repr__`, only the first in MRO wins. For chainable `__repr__`, use `super()`.

### 5.2 Stateful Mixin — Cooperative `__init__`

When a mixin needs state, it must participate in the cooperative `__init__` protocol:

```python
from datetime import datetime

class TimestampedMixin:
    """Adds created_at / updated_at. Stateful — needs cooperative __init__."""

    def __init__(self, *, created_at: datetime | None = None, **kwargs) -> None:
        super().__init__(**kwargs)
        self.created_at = created_at or datetime.now()
        self.updated_at = self.created_at

    def touch(self) -> None:
        self.updated_at = datetime.now()

class VersionedMixin:
    """Adds version counter."""

    def __init__(self, **kwargs) -> None:
        super().__init__(**kwargs)
        self.version = 1

    def bump_version(self) -> None:
        self.version += 1

class Document(TimestampedMixin, VersionedMixin):
    def __init__(self, *, title: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.title = title

doc = Document(title="Hello")
print(doc.title, doc.version, doc.created_at)
doc.bump_version()
doc.touch()
print(doc.version, doc.updated_at)
print(Document.__mro__)
# (Document, TimestampedMixin, VersionedMixin, object)
```

Explanation:

- Each mixin's `__init__` pops its own kwargs and forwards the rest.
- `TimestampedMixin.__init__` extracts `created_at`; `VersionedMixin.__init__` extracts nothing but still forwards `**kwargs` and initializes `version`.
- `Document.__init__` extracts `title` and forwards everything else.
- The chain ends at `object.__init__()` with empty kwargs — safe.

### 5.3 Method-Intercepting Mixin — The Wrapper Pattern

Most useful mixins wrap an existing method:

```python
import time
from typing import Any, Callable

class TimingMixin:
    """Logs wall-clock time for any method named 'execute'."""

    def execute(self, *args: Any, **kwargs: Any) -> Any:
        start = time.perf_counter()
        try:
            return super().execute(*args, **kwargs)  # type: ignore[misc]
        finally:
            elapsed = time.perf_counter() - start
            print(f"[{self.__class__.__name__}.execute] {elapsed:.4f}s")

class RetryMixin:
    """Retries execute() up to N times on failure."""

    retries: int = 3

    def execute(self, *args: Any, **kwargs: Any) -> Any:
        last_exc: BaseException | None = None
        for attempt in range(1, self.retries + 1):
            try:
                return super().execute(*args, **kwargs)  # type: ignore[misc]
            except Exception as exc:
                last_exc = exc
                print(f"[Retry] attempt {attempt} failed: {exc}")
        raise last_exc  # type: ignore[misc]

class BaseExecutor:
    def execute(self, task: str) -> str:
        if task == "fail":
            raise RuntimeError("simulated failure")
        return f"Executed {task}"

class RobustExecutor(RetryMixin, TimingMixin, BaseExecutor):
    pass

print(RobustExecutor.__mro__)
# (RobustExecutor, RetryMixin, TimingMixin, BaseExecutor, object)

executor = RobustExecutor()
print(executor.execute("hello"))
# [Retry] not triggered, [Timing] logs, then BaseExecutor runs
print("---")
try:
    executor.execute("fail")
except RuntimeError:
    print("All retries exhausted")
# RetryMixin retries 3 times, TimingMixin times the whole retry loop
```

Notice the pipeline: `RetryMixin` is outermost (first base), so it wraps `TimingMixin`, which wraps `BaseExecutor`. Swapping `RetryMixin` and `TimingMixin` would time each retry individually vs. the whole operation — a semantic choice.

### 5.4 Attribute-Providing Mixin

```python
import json

class SerializableMixin:
    """Adds to_json / from_json based on __dict__."""

    def to_json(self) -> str:
        return json.dumps(self.__dict__, default=str)

    @classmethod
    def from_json(cls, data: str):
        obj = cls.__new__(cls)  # bypass __init__
        obj.__dict__.update(json.loads(data))
        return obj

class User(SerializableMixin):
    def __init__(self, name: str, age: int):
        self.name = name
        self.age = age

u = User("Alice", 30)
payload = u.to_json()
print(payload)           # {"name": "Alice", "age": 30}
u2 = User.from_json(payload)
print(u2.name, u2.age)   # Alice 30
```

State-light, no `__init__` override, no `super()` needed — but still not standalone (`SerializableMixin().to_json()` would serialize an empty `__dict__`, not useful).

### 5.5 Advanced: Mixin With Class-Level State

```python
class RegistryMixin:
    """Mixin that auto-registers subclasses in a class-level registry."""

    _registry: dict[str, type] = {}

    def __init_subclass__(cls, **kwargs) -> None:
        super().__init_subclass__(**kwargs)
        RegistryMixin._registry[cls.__name__] = cls

class Payment(RegistryMixin):
    pass

class CardPayment(Payment):
    pass

class BankPayment(Payment):
    pass

print(RegistryMixin._registry)
# {'Payment': <class 'Payment'>, 'CardPayment': <class 'CardPayment'>, ...}
```

This uses `__init_subclass__` (a class-creation hook) rather than instance state. Each subclass registers itself without any instance-level coordination.

## 6. Collision Handling

### 6.1 Method Name Collision

If two mixins define the same method name, MRO decides — the first wins, the second is shadowed.

```python
class AMixin:
    def process(self) -> str:
        return "A -> " + super().process()  # type: ignore[misc]

class BMixin:
    def process(self) -> str:
        return "B -> " + super().process()  # type: ignore[misc]

class Base:
    def process(self) -> str:
        return "Base"

class Combined(AMixin, BMixin, Base):
    pass

print(Combined().process())  # A -> B -> Base — both run via super() chain

# But if either mixin forgets super():
class ABadMixin:
    def process(self) -> str:
        return "ABad"  # forgot super() — chain broken, BMixin and Base skipped

class CombinedBad(ABadMixin, BMixin, Base):
    pass

print(CombinedBad().process())  # ABad — BMixin never runs
```

**Prevention:**

- Keep mixin method names unique and namespaced when possible (`audit_save` vs `validate_save` if both wrap `save` via distinct hooks — but wrapping the same `save` cooperatively is intentional).
- Always call `super()` in wrapping mixins.
- Test mixin composition explicitly — instantiate the combined class and verify all expected side effects.

### 6.2 Attribute Name Collision

```python
class TimestampedMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.created_at = "timestamped"

class AuditedMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.created_at = "audited"  # collision! overwrites TimestampedMixin's value

class Doc(TimestampedMixin, AuditedMixin):
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

print(Doc().created_at)  # audited — TimestampedMixin's value was overwritten
# MRO: Doc -> TimestampedMixin -> AuditedMixin -> object
# TimestampedMixin.__init__ runs first, sets created_at, then AuditedMixin overwrites it.
```

**Fixes:**

| Strategy | Example |
|----------|---------|
| Namespace attributes | `self._timestamped_created_at`, `self._audited_created_at` |
| Use distinct names | `self.audit_created_at` vs `self.record_created_at` |
| Single source of truth | Only one mixin owns `created_at`; the other uses a different name |
| Property with cooperative storage | Store in `self.__dict__` with prefixed keys |

The real lesson: stateful mixins must coordinate attribute names. Stateless mixins avoid this entirely.

### 6.3 `__init__` Signature Collision

If two mixins both want the same kwarg name with different semantics, the cooperative `**kwargs` protocol breaks:

```python
# Both mixins want 'name' but mean different things
class DisplayNameMixin:
    def __init__(self, *, name: str, **kwargs):
        super().__init__(**kwargs)
        self.display_name = name

class StorageNameMixin:
    def __init__(self, *, name: str, **kwargs):
        super().__init__(**kwargs)
        self.storage_name = name

class Bad(DisplayNameMixin, StorageNameMixin):
    pass

# Bad(name="x") -> DisplayNameMixin pops name="x", forwards {},
# StorageNameMixin never gets name -> TypeError: missing required argument 'name'
```

**Fix:** Use distinct, descriptive parameter names:

```python
class DisplayNameMixinFixed:
    def __init__(self, *, display_name: str, **kwargs):
        super().__init__(**kwargs)
        self.display_name = display_name

class StorageNameMixinFixed:
    def __init__(self, *, storage_name: str, **kwargs):
        super().__init__(**kwargs)
        self.storage_name = storage_name

class Good(DisplayNameMixinFixed, StorageNameMixinFixed):
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

print(Good(display_name="Pretty", storage_name="pretty_001").display_name)
```

## 7. Real-World Mixin Examples

### 7.1 Django Class-Based Views — The Canonical Mixin Ecosystem

Django's CBVs are the most widely used mixin system in Python:

```python
# Simplified sketch of Django's design (not actual Django code)
class View:
    def dispatch(self, request, *args, **kwargs):
        handler = getattr(self, request.method.lower(), self.http_method_not_allowed)
        return handler(request, *args, **kwargs)

    def http_method_not_allowed(self, request, *args, **kwargs):
        return "405 Method Not Allowed"

class LoginRequiredMixin:
    def dispatch(self, request, *args, **kwargs):
        if not getattr(request, "user_is_authenticated", False):
            return "403 Forbidden — login required"
        return super().dispatch(request, *args, **kwargs)  # type: ignore[misc]

class PermissionRequiredMixin:
    permission_required: str = ""

    def dispatch(self, request, *args, **kwargs):
        if not self.has_permission(request):
            return "403 Forbidden — permission denied"
        return super().dispatch(request, *args, **kwargs)  # type: ignore[misc]

    def has_permission(self, request) -> bool:
        return getattr(request, "permission", "") == self.permission_required

class SuccessMessageMixin:
    success_message: str = ""

    def form_valid(self, form):
        response = super().form_valid(form)  # type: ignore[misc]
        print(f"[Message] {self.success_message}")
        return response

# Composing:
class ArticleCreateView(LoginRequiredMixin, PermissionRequiredMixin, View):
    permission_required = "articles.add_article"

    def post(self, request, *args, **kwargs):
        return "201 Created"

# MRO: ArticleCreateView -> LoginRequiredMixin -> PermissionRequiredMixin -> View -> object
# dispatch() chains: Login check -> Permission check -> View.dispatch -> post()
```

Key observations:

- Every mixin overrides `dispatch` and calls `super().dispatch` — cooperative.
- Mixins are ordered by *precedence*: login check outermost, then permission, then core dispatch.
- `SuccessMessageMixin` wraps `form_valid` similarly — same pattern, different method.

### 7.2 `collections.abc` — Mixins That Provide Default Implementations

The `collections.abc` module uses mixins to give you methods for free when you implement a minimal interface:

```python
from collections.abc import MutableMapping

class CaseInsensitiveDict(MutableMapping):
    """Only need to implement 5 abstract methods; mixin provides the rest."""

    def __init__(self):
        self._data: dict[str, str] = {}

    def __getitem__(self, key: str) -> str:
        return self._data[key.lower()]

    def __setitem__(self, key: str, value: str) -> None:
        self._data[key.lower()] = value

    def __delitem__(self, key: str) -> None:
        del self._data[key.lower()]

    def __iter__(self):
        return iter(self._data)

    def __len__(self) -> int:
        return len(self._data)

# MutableMapping mixin provides: get, keys, values, items, pop, __contains__, etc.
d = CaseInsensitiveDict()
d["Hello"] = "world"
print(d["HELLO"])          # world
print("hello" in d)        # True — provided by MutableMapping mixin
print(list(d.keys()))      # ['hello'] — provided
print(d.get("missing"))    # None — provided
```

`MutableMapping` is technically an ABC, but it acts as a mixin: it provides concrete methods (`get`, `pop`, `keys`, ...) implemented in terms of the abstract methods you provide. You inherit it *and* get behavior — the mixin pattern via ABC.

### 7.3 Standard Library — `socketserver`, `io`, `unittest`

```python
# io — BufferedReader is conceptually BufferedMixin + RawIOBase
# socketserver — ThreadingMixIn, ForkingMixIn
# unittest — TestCase mixins for assertions

# Example: socketserver.ThreadingMixIn sketch
class ThreadingMixin:
    def process_request(self, request, client_address):
        import threading
        t = threading.Thread(target=self.process_request_thread,
                             args=(request, client_address))
        t.daemon = True
        t.start()

class ForkingMixin:
    def process_request(self, request, client_address):
        import os
        if os.fork() == 0:
            try:
                super().process_request(request, client_address)  # type: ignore[misc]
            finally:
                os._exit(0)

class TCPServer:
    def process_request(self, request, client_address):
        print(f"Handling {client_address}")

class ThreadedTCPServer(ThreadingMixin, TCPServer): pass
class ForkingTCPServer(ForkingMixin, TCPServer): pass
# Choose threading vs forking by swapping one mixin — no code duplication
```

### 7.4 Dataclass Mixins — Combining `dataclass` With Mixins

```python
from dataclasses import dataclass

class TimestampedMixin2:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        from datetime import datetime
        # Only set if not already set (dataclass may have set it)
        if not hasattr(self, "created_at") or self.created_at is None:
            self.created_at = datetime.now()

# Note: dataclass + mixin ordering is subtle — dataclass generates __init__,
# so cooperative __init__ needs care. Often better to use composition or
# __post_init__ with mixins that don't override __init__.
```

## 8. Anti-Patterns — How Mixins Go Wrong

### 8.1 The God Mixin

```python
# Bad: one mixin does everything — not a mixin, just a base class in disguise
class UtilsMixin:
    def log(self): ...
    def cache(self): ...
    def validate(self): ...
    def serialize(self): ...
    def authenticate(self): ...
```

**Fix:** Split into `LoggingMixin`, `CacheMixin`, `ValidationMixin`, etc. One responsibility each.

### 8.2 Stateful Mixin With Positional Args

```python
# Bad: positional __init__ args in a mixin — breaks cooperative forwarding
class BadMixin:
    def __init__(self, name, value):  # positional — collides with other mixins
        super().__init__()
        self.name = name
        self.value = value
```

**Fix:** Always use keyword-only args with `**kwargs` in mixins:

```python
class GoodMixin:
    def __init__(self, *, name=None, value=None, **kwargs):
        super().__init__(**kwargs)
        if name is not None:
            self.name = name
```

### 8.3 Mixin That Calls a Hard-Coded Parent

```python
class BadMixin:
    def save(self):
        Base.save(self)  # breaks MRO — skips sibling mixins
```

**Fix:** Always use `super().save()`.

### 8.4 Deep Mixin Hierarchies

```python
# Fragile: 5 mixins deep, hard to reason about MRO
class View(AuditMixin, CacheMixin, AuthMixin, ValidationMixin, LoggingMixin, BaseView):
    pass
# MRO is 7 classes long — method collisions and __init__ ordering become error-prone
```

**Fix:** If you need 5+ mixins, consider whether some should be composed (has-a) or whether middleware/decorator patterns fit better.

## 9. Testing Mixins

Mixins should be tested in isolation with a minimal stub:

```python
import unittest

class TimestampedMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        from datetime import datetime
        self.created_at = datetime.now()

    def is_recent(self, seconds: int = 60) -> bool:
        from datetime import datetime, timedelta
        return datetime.now() - self.created_at < timedelta(seconds=seconds)

# Test with a minimal stub — no real base class needed
class StubBase:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

class TimestampedStub(TimestampedMixin, StubBase):
    pass

def test_timestamped_mixin():
    obj = TimestampedStub()
    assert hasattr(obj, "created_at")
    assert obj.is_recent(seconds=10) is True
    print("TimestampedMixin tests passed")

test_timestamped_mixin()

# Also test composition:
class NamedMixin:
    def __init__(self, *, name: str, **kwargs):
        super().__init__(**kwargs)
        self.name = name

class Combined(TimestampedMixin, NamedMixin, StubBase):
    pass

def test_combined_mixins():
    obj = Combined(name="test")
    assert obj.name == "test"
    assert hasattr(obj, "created_at")
    print("Combined mixin tests passed")

test_combined_mixins()
```

## 10. Summary

| Concept | Key Takeaway |
|---------|--------------|
| Mixin definition | Small, targeted, not standalone, minimal state, cooperative. |
| Naming | Always `*Mixin` suffix. |
| Ordering | `class Child(MixinA, MixinB, Base)` — mixins first, base last. Leftmost mixin is outermost. |
| `super()` | Every wrapping mixin method must call `super()` to continue the chain. |
| `__init__` | Stateful mixins use `*, own_param, **kwargs` + `super().__init__(**kwargs)`. |
| Collisions | Namespace attributes/methods; use distinct kwarg names. |
| Mixin vs composition | Mixin for method interception/wrapping; composition for stateful helpers or runtime swapping. |
| Real-world | Django CBVs, `collections.abc`, `socketserver`, `io` — all use mixins pervasively. |

### Decision Flowchart

```
Need to reuse behavior?
├── Must intercept/wrap a base method (save, dispatch, handle)?
│   └── Yes → Mixin (if orthogonal & stateless/light) or decorator/middleware
├── Just need a helper's functionality without wrapping?
│   └── Yes → Composition (has-a)
├── Defining core identity (is-a)?
│   └── Yes → Base class (single inheritance)
├── Defining a contract/interface?
│   └── Yes → ABC (Lesson 12.5) or Protocol (Lesson 12.6)
└── Unsure / deep hierarchy forming?
    └── Prefer composition — flatter, more explicit.
```
