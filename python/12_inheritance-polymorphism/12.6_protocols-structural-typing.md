# 12.6 Protocols & Structural Typing

## Learning Objectives

By the end of this lesson you will be able to:

- Explain structural vs nominal typing and why Python supports both.
- Define and use `typing.Protocol` for explicit structural contracts.
- Apply `@runtime_checkable` for `isinstance` checks on protocols.
- Declare methods, attributes, properties, and generic type parameters on protocols.
- Choose between Protocol, ABC, and duck typing using a principled decision table.
- Use protocols to decouple code — depend on structure, not inheritance.

---

## 1. Nominal vs Structural Typing — The Core Distinction

### 1.1 Definitions

| Typing Discipline | "Is X a Duck?" Means | Requires | Example Languages |
|-------------------|----------------------|----------|-------------------|
| **Nominal** | "Was X *declared* as a `Duck` (or subclass of `Duck`)?" | Explicit inheritance / `implements` | Java, C#, C++ (mostly), Python ABCs |
| **Structural** | "Does X *have* the structure of a `Duck` (walk + quack methods)?" | Matching attributes/methods, no declaration needed | Go interfaces, TypeScript, Python Protocols, duck typing |

```python
# Nominal — must inherit from Duck
class Duck:
    def quack(self): return "Quack!"

class Mallard(Duck):
    def quack(self): return "Quack from Mallard!"

print(isinstance(Mallard(), Duck))  # True — nominal: Mallard declared as Duck subclass

class FakeDuck:
    def quack(self): return "Quack!"  # same structure, but not nominal

print(isinstance(FakeDuck(), Duck))  # False — not a Duck, despite quacking
```

```python
# Structural — just needs quack(), no inheritance
from typing import Protocol, runtime_checkable

@runtime_checkable
class Quacker(Protocol):
    def quack(self) -> str: ...

class FakeDuck2:
    def quack(self) -> str: return "Quack!"

print(isinstance(FakeDuck2(), Quacker))  # True — structural: has quack(), no inheritance needed
```

### 1.2 Where Python Fits

Python supports **all three**:

| Mechanism | Typing Style | Declaration | Checked When |
|-----------|--------------|-------------|--------------|
| Duck typing (Lesson 12.4) | Structural (implicit) | None — just call methods | Runtime (AttributeError) |
| ABC (Lesson 12.5) | Nominal (explicit inheritance or `register`) | `class MyClass(MyABC)` | Runtime (TypeError at instantiation) + `isinstance` |
| Protocol (this lesson) | Structural (explicit contract) | `class MyProto(Protocol)` + type annotations | Static (mypy/pyright) + optional runtime (`@runtime_checkable`) |

**Mental model:** Think of typing disciplines as a spectrum of *explicitness*:

```
Implicit ◄──────────────────────────────────────────────► Explicit
Duck typing          Protocol              ABC          Concrete base class
(no contract)    (structural contract)  (nominal contract)  (shared implementation)
  just call it    declare the shape      declare the name    declare + share code
```

Protocols occupy the sweet spot: explicit enough for tooling and documentation, loose enough to avoid coupling.

### 1.3 Why Structural Typing Matters

**The coupling problem with nominal typing:**

```python
# Nominal — every closable thing must inherit from Closeable
from abc import ABC, abstractmethod

class Closeable(ABC):
    @abstractmethod
    def close(self): ...

class MyFile(Closeable):
    def close(self): print("closed")

class ThirdPartyConnection:
    def close(self): print("connection closed")
    # Cannot inherit from Closeable — it's third-party code!

def shutdown(resource: Closeable):  # nominal — only accepts Closeable subclasses
    resource.close()

shutdown(MyFile())                # works
shutdown(ThirdPartyConnection())  # type checker ERROR — not a Closeable
# Must do: Closeable.register(ThirdPartyConnection) — manual, easy to forget
```

**Structural — no coupling:**

```python
from typing import Protocol

class Closeable(Protocol):
    def close(self) -> None: ...

class MyFile2:
    def close(self) -> None: print("closed")

class ThirdPartyConnection2:
    def close(self) -> None: print("connection closed")

def shutdown2(resource: Closeable) -> None:  # structural — anything with close()
    resource.close()

shutdown2(MyFile2())                # type checker OK
shutdown2(ThirdPartyConnection2())  # type checker OK — structural match, no registration
```

No inheritance. No registration. No modification of third-party code. The type checker verifies structure, not lineage.

## 2. `typing.Protocol` — Defining Structural Contracts

### 2.1 Minimal Protocol

```python
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> str: ...

# Any class with draw() -> str satisfies Drawable — no inheritance needed
class Circle:
    def draw(self) -> str:
        return "Drawing circle"

class Text:
    def draw(self) -> str:
        return "Drawing text"

class Icon:
    def draw(self) -> str:
        return "Drawing icon"

def render(obj: Drawable) -> None:
    print(obj.draw())

render(Circle())  # OK — structural match
render(Text())    # OK
render(Icon())    # OK

# Type checker would reject:
class NoDraw:
    pass

# render(NoDraw())  # mypy error: Argument 1 to "render" has incompatible type "NoDraw"
```

Explanation:

- `class Drawable(Protocol)` declares a structural contract: "anything with `draw() -> str` is a `Drawable`."
- `Circle`, `Text`, `Icon` do not inherit from `Drawable` — they just happen to have `draw()`.
- A static type checker (mypy, pyright, pytype) verifies at *analysis time* that arguments to `render` satisfy `Drawable`. No runtime cost.
- At runtime, `Protocol` has no effect — `render` just calls `obj.draw()`. If you pass a `NoDraw`, you get `AttributeError` at call time (same as duck typing).

### 2.2 Protocols Are Not Instantiable (By Design, With Nuance)

```python
from typing import Protocol

class MyProto(Protocol):
    def method(self) -> int: ...

# MyProto()  # At runtime: creates an instance, but useless — no concrete method
# Type checkers will flag MyProto() as an error if the protocol has non-default members
```

Protocols are *type-checker constructs*. Instantiating them at runtime is not useful and may be flagged. They exist to be used as type annotations.

### 2.3 Protocols With Attributes

Protocols can require attributes, not just methods:

```python
from typing import Protocol

class Named(Protocol):
    name: str

class Person:
    def __init__(self, name: str):
        self.name = name

class Product:
    def __init__(self, name: str):
        self.name = name

def greet(obj: Named) -> None:
    print(f"Hello, {obj.name}!")

greet(Person("Alice"))   # OK — has name: str
greet(Product("Widget")) # OK — has name: str

class Nameless:
    pass

# greet(Nameless())  # mypy error: "Nameless" has no attribute "name"
```

Attribute types are checked structurally. `name: str` in the protocol means "must have an attribute `name` that is a `str`."

### 2.4 Protocols With Properties

```python
from typing import Protocol

class HasArea(Protocol):
    @property
    def area(self) -> float: ...

class Circle2:
    def __init__(self, radius: float):
        self.radius = radius

    @property
    def area(self) -> float:
        return 3.14 * self.radius ** 2

class Rectangle:
    def __init__(self, width: float, height: float):
        self.width = width
        self.height = height

    @property
    def area(self) -> float:
        return self.width * self.height

def print_area(shape: HasArea) -> None:
    print(f"Area: {shape.area:.2f}")

print_area(Circle2(5))        # Area: 78.50
print_area(Rectangle(4, 6))   # Area: 24.00
```

The protocol requires a *property* named `area`. A plain attribute `area: float` would also satisfy it if the type matches (since attribute access is uniform in Python), but declaring it as `@property` documents intent.

### 2.5 Protocols With Methods + Attributes Combined

```python
from typing import Protocol

class Repository(Protocol):
    name: str

    def save(self, record: dict) -> None: ...

    def load(self, key: str) -> dict | None: ...

    @property
    def count(self) -> int: ...

# Satisfying class — needs all four members:
class InMemoryRepository:
    def __init__(self, name: str):
        self.name = name
        self._data: dict[str, dict] = {}

    def save(self, record: dict) -> None:
        self._data[record["id"]] = record

    def load(self, key: str) -> dict | None:
        return self._data.get(key)

    @property
    def count(self) -> int:
        return len(self._data)

def backup(repo: Repository) -> None:
    print(f"Backing up {repo.name} with {repo.count} records")

backup(InMemoryRepository("main"))  # OK — all members present
```

### 2.6 Optional Members and Default Implementations

Protocols can have non-abstract members (concrete defaults) — but this is unusual. Prefer keeping protocols purely abstract:

```python
from typing import Protocol

class Logger(Protocol):
    def log(self, msg: str) -> None: ...

    def log_error(self, msg: str) -> None:
        # Default implementation — rarely used in protocols, but valid
        self.log(f"ERROR: {msg}")

# A class with only log() still satisfies Logger structurally for type checking,
# but at runtime log_error would call the protocol's default — which may not be
# what you want. Prefer ABCs when you need shared default implementations.
```

**Guideline:** If your protocol needs concrete helper methods, consider whether an ABC (Lesson 12.5) is more appropriate. Protocols are best as pure structural contracts.

## 3. `@runtime_checkable` — `isinstance` for Protocols

### 3.1 The Problem

By default, `isinstance` does **not** work with protocols:

```python
from typing import Protocol

class Drawable(Protocol):
    def draw(self) -> str: ...

class Circle:
    def draw(self) -> str: return "circle"

print(isinstance(Circle(), Drawable))  # TypeError: Instance and class checks can only be used with @runtime_checkable protocols
```

Protocols are static-only by default. The type checker understands them, but at runtime they are not real classes for `isinstance`.

### 3.2 The Solution — `@runtime_checkable`

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Drawable(Protocol):
    def draw(self) -> str: ...

class Circle:
    def draw(self) -> str: return "circle"

class NoDraw:
    pass

print(isinstance(Circle(), Drawable))   # True — has draw()
print(isinstance(NoDraw(), Drawable))   # False — no draw()
print(issubclass(Circle, Drawable))     # True
print(issubclass(NoDraw, Drawable))     # False
```

Explanation:

- `@runtime_checkable` enables `isinstance`/`issubclass` checks that verify the *presence* of required attributes (via `hasattr`).
- The check is **shallow**: it verifies that attributes *exist*, not that they have the correct type or signature.

### 3.3 Shallow Checking — The Critical Limitation

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Processor(Protocol):
    def process(self, data: str) -> int: ...

class GoodProcessor:
    def process(self, data: str) -> int:
        return len(data)

class BadProcessor:
    # Wrong signature — takes no args, returns str — but hasattr check passes!
    def process(self):
        return "oops"

class AlsoBad:
    process = "not even callable"  # attribute exists but is a string!

print(isinstance(GoodProcessor(), Processor))  # True — correct
print(isinstance(BadProcessor(), Processor))   # True — WRONG! signature mismatch not detected
print(isinstance(AlsoBad(), Processor))        # True — WRONG! not callable, but hasattr passes

# At runtime, @runtime_checkable only checks hasattr, not types or signatures.
# The type checker (mypy) WOULD catch BadProcessor and AlsoBad statically.
```

**Rules for `@runtime_checkable`:**

| Aspect | Behavior |
|--------|----------|
| What it checks | `hasattr(obj, "method_name")` for each protocol member |
| What it does NOT check | Types, signatures, return values, callability, attribute types |
| When to use `isinstance` | Only when you need runtime branching on protocol conformance |
| When NOT to use | When static checking suffices — just annotate with the protocol and let mypy verify |

### 3.4 Only Protocols Can Be Runtime-Checkable

```python
from typing import Protocol, runtime_checkable

# Works:
@runtime_checkable
class MyProto(Protocol):
    def method(self) -> None: ...

# Fails — not a Protocol:
# @runtime_checkable
# class NotAProtocol:
#     def method(self) -> None: ...
# TypeError: @runtime_checkable can only be applied to protocols
```

### 3.5 Performance of `@runtime_checkable`

Each `isinstance(obj, Proto)` does `hasattr` checks for every member of `Proto`. For protocols with many members or in hot loops, this has measurable cost. Prefer static checking (annotations + mypy) and reserve runtime checks for system boundaries.

## 4. Generic Protocols

### 4.1 Why Generic Protocols?

Often a structural contract is parameterized by a type: "a `Box` that holds a `T`," "a `Parser` that produces a `T`."

```python
from typing import Protocol, TypeVar

T = TypeVar("T")
T_co = TypeVar("T_co", covariant=True)
T_contra = TypeVar("T_contra", contravariant=True)

class Box(Protocol[T]):
    """A box that holds a value of type T."""
    def get(self) -> T: ...
    def set(self, value: T) -> None: ...

class IntBox:
    def __init__(self):
        self._value: int = 0
    def get(self) -> int:
        return self._value
    def set(self, value: int) -> None:
        self._value = value

def process_box(box: Box[int]) -> None:
    box.set(42)
    print(box.get())

process_box(IntBox())  # OK — IntBox structurally matches Box[int]
```

### 4.2 Realistic Generic Protocol — Repository

```python
from typing import Protocol, TypeVar, Optional

T = TypeVar("T")
Key = TypeVar("Key")

class Repository(Protocol[T, Key]):
    def save(self, entity: T) -> Key: ...
    def find_by_id(self, key: Key) -> Optional[T]: ...
    def delete(self, key: Key) -> bool: ...

class User:
    def __init__(self, name: str):
        self.name = name

class InMemoryUserRepo:
    def __init__(self):
        self._store: dict[int, User] = {}
        self._next_id = 0

    def save(self, entity: User) -> int:
        self._next_id += 1
        self._store[self._next_id] = entity
        return self._next_id

    def find_by_id(self, key: int) -> Optional[User]:
        return self._store.get(key)

    def delete(self, key: int) -> bool:
        if key in self._store:
            del self._store[key]
            return True
        return False

def user_service(repo: Repository[User, int]) -> None:
    key = repo.save(User("Alice"))
    user = repo.find_by_id(key)
    print(user.name if user else "not found")

user_service(InMemoryUserRepo())  # OK — structurally matches Repository[User, int]
```

### 4.3 Covariance and Contravariance in Protocols

Variance controls when `Box[Dog]` can be used as `Box[Animal]`:

```python
from typing import Protocol, TypeVar

T_co = TypeVar("T_co", covariant=True)    # producer — Box produces T
T_contra = TypeVar("T_contra", contravariant=True)  # consumer — Box consumes T

class Reader(Protocol[T_co]):
    """Produces T — covariant: Reader[Dog] is a Reader[Animal] if Dog <: Animal."""
    def read(self) -> T_co: ...

class Writer(Protocol[T_contra]):
    """Consumes T — contravariant: Writer[Animal] is a Writer[Dog] if Dog <: Animal."""
    def write(self, value: T_contra) -> None: ...

# Invariant (default) — Box[T] is neither covariant nor contravariant
T = TypeVar("T")

class Box(Protocol[T]):
    def get(self) -> T: ...
    def set(self, value: T) -> None: ...
# Box[Dog] is NOT Box[Animal] — invariant
```

| Variance | When | `Container[Dog]` vs `Container[Animal]` |
|----------|------|------------------------------------------|
| **Covariant** (`T_co`) | Type only *produced* (return values) | `Container[Dog]` <: `Container[Animal]` |
| **Contravariant** (`T_contra`) | Type only *consumed* (parameters) | `Container[Animal]` <: `Container[Dog]` |
| **Invariant** (`T`) | Type both produced and consumed | Neither is subtype of the other |

Most protocols are either `covariant` (read-only) or `invariant` (read-write). Declare variance correctly to get accurate type checking — but this is an advanced topic. When in doubt, start invariant and add variance when the type checker complains.

## 5. Protocol vs ABC vs Duck Typing — Decision Table

### 5.1 Comprehensive Comparison

| Dimension | Duck Typing | ABC (`abc.ABC`) | Protocol (`typing.Protocol`) |
|-----------|-------------|-----------------|------------------------------|
| **Contract** | Implicit — no declaration | Explicit — abstract methods | Explicit — protocol members |
| **Enforcement** | `AttributeError` at call site | `TypeError` at instantiation | Static (mypy/pyright); runtime only with `@runtime_checkable` |
| **Requires inheritance?** | No | Yes (or `register`) | No — structural |
| **Third-party types** | Works automatically | Needs `register()` | Works automatically (structural) |
| **Shared logic / mixins** | No | Yes — concrete methods in ABC | No (protocols should be pure contracts) |
| **`isinstance` support** | `hasattr` / `try/except` manually | `isinstance(obj, ABC)` always works | Only with `@runtime_checkable` (shallow) |
| **Type checker support** | No — checker cannot verify | Yes — nominal check | Yes — structural check (most powerful) |
| **Coupling** | None | Tight (nominal) | Loose (structural) |
| **Runtime cost** | Zero | Metaclass check at instantiation | Zero (static only) or `hasattr` scan (runtime) |
| **Best for** | Internal code, quick scripts, 1-2 methods | Framework extension points, Template Method, `collections.abc` | Library APIs, decoupled interfaces, large codebases with type checking |

### 5.2 Decision Flowchart

```
Need to define an interface?
│
├── Need shared concrete implementation / Template Method?
│   └── Yes → ABC — protocols shouldn't carry logic
│
├── Building a public library API where callers shouldn't inherit?
│   └── Yes → Protocol — zero coupling for callers
│
├── Need isinstance checks at runtime?
│   ├── And types are known / controlled? → ABC (reliable isinstance)
│   ├── And types are open-ended / third-party? → Protocol + @runtime_checkable (shallow check)
│   └── Only for static analysis? → Protocol without @runtime_checkable
│
├── Need to adapt existing third-party classes?
│   ├── Want to avoid modifying them AND want static checking? → Protocol
│   ├── OK with explicit registration? → ABC.register()
│   └── Just need it to work at runtime? → Duck typing (EAFP)
│
├── Simple internal code, 1-2 methods, no type checker?
│   └── Duck typing — simplest, no ceremony
│
└── Large codebase with mypy/pyright?
    └── Protocol — best static guarantees with least coupling
```

### 5.3 Can You Combine Them?

Yes — a class can satisfy both an ABC and a Protocol, and you can use both in the same codebase:

```python
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable

# ABC for framework internals that need shared logic
class PluginBase(ABC):
    @abstractmethod
    def execute(self, data: str) -> str: ...

    def execute_all(self, items: list[str]) -> list[str]:
        return [self.execute(x) for x in items]

# Protocol for external callers that shouldn't need to inherit
@runtime_checkable
class Executable(Protocol):
    def execute(self, data: str) -> str: ...

# Internal plugin — uses ABC for shared logic
class UpperPlugin(PluginBase):
    def execute(self, data: str) -> str:
        return data.upper()

# External plugin — just needs the right method, no inheritance
class ExternalPlugin:
    def execute(self, data: str) -> str:
        return data[::-1]

def run_internal(plugin: PluginBase) -> None:
    print(plugin.execute_all(["hello", "world"]))

def run_external(plugin: Executable) -> None:
    print(plugin.execute("hello"))

run_internal(UpperPlugin())    # uses ABC path — has execute_all
run_external(ExternalPlugin()) # uses Protocol path — structural
run_external(UpperPlugin())    # also works — UpperPlugin has execute()
```

## 6. Benefits of Protocols for Decoupling

### 6.1 Dependency Inversion — Depend on Abstractions

Without protocols (tight coupling):

```python
# Tightly coupled — EmailService depends on concrete SMTPClient
class SMTPClient:
    def send(self, to: str, body: str) -> None:
        print(f"SMTP: sending to {to}")

class EmailService:
    def __init__(self, client: SMTPClient):  # concrete dependency
        self.client = client

    def notify(self, user: str, message: str) -> None:
        self.client.send(user, message)

# Cannot test without a real SMTPClient, cannot swap to a different sender
```

With protocols (decoupled):

```python
from typing import Protocol

class MessageSender(Protocol):
    def send(self, to: str, body: str) -> None: ...

class SMTPClient2:
    def send(self, to: str, body: str) -> None:
        print(f"SMTP: sending to {to}")

class MockSender:
    def __init__(self):
        self.sent: list[tuple[str, str]] = []
    def send(self, to: str, body: str) -> None:
        self.sent.append((to, body))

class InMemorySender:
    def send(self, to: str, body: str) -> None:
        print(f"[InMemory] {to}: {body}")

class EmailService2:
    def __init__(self, client: MessageSender):  # depends on Protocol, not concrete
        self.client = client

    def notify(self, user: str, message: str) -> None:
        self.client.send(user, message)

# Swappable — any MessageSender works:
EmailService2(SMTPClient2()).notify("alice@example.com", "Hello!")
mock = MockSender()
EmailService2(mock).notify("bob@example.com", "Hi!")
assert mock.sent == [("bob@example.com", "Hi!")]
EmailService2(InMemorySender()).notify("carol@example.com", "Hey!")

# Type checker verifies all three satisfy MessageSender — no inheritance needed.
```

### 6.2 Testing Without Mocks Framework

Protocols make it trivial to create test doubles — just implement the required methods:

```python
from typing import Protocol

class DataStore(Protocol):
    def get(self, key: str) -> str | None: ...
    def set(self, key: str, value: str) -> None: ...

# Production:
class RedisStore:
    def get(self, key: str) -> str | None: ...
    def set(self, key: str, value: str) -> None: ...

# Test double — 5 lines, no mocking library:
class FakeStore:
    def __init__(self):
        self._data: dict[str, str] = {}
    def get(self, key: str) -> str | None:
        return self._data.get(key)
    def set(self, key: str, value: str) -> None:
        self._data[key] = value

def test_cache():
    store: DataStore = FakeStore()  # type checker confirms conformance
    store.set("key", "value")
    assert store.get("key") == "value"
    assert store.get("missing") is None
```

### 6.3 Adapter Pattern Without Inheritance

```python
from typing import Protocol

class FileLike(Protocol):
    def read(self, n: int = -1) -> str: ...
    def write(self, data: str) -> int: ...

# Third-party API with different method names:
class LegacyBuffer:
    def fetch(self, n: int = -1) -> str:
        return "legacy data"[:n] if n >= 0 else "legacy data"
    def store(self, data: str) -> int:
        print(f"Storing: {data}")
        return len(data)

# Adapter — makes LegacyBuffer quack like FileLike, no inheritance from FileLike needed:
class LegacyAdapter:
    def __init__(self, buf: LegacyBuffer):
        self._buf = buf
    def read(self, n: int = -1) -> str:
        return self._buf.fetch(n)
    def write(self, data: str) -> int:
        return self._buf.store(data)

def process_file(f: FileLike) -> None:
    data = f.read(5)
    f.write(data.upper())

process_file(LegacyAdapter(LegacyBuffer()))  # works — adapter satisfies FileLike
```

## 7. Advanced Protocol Features

### 7.1 `Self` Type in Protocols (Python 3.11+)

```python
from typing import Protocol, Self

class Cloneable(Protocol):
    def clone(self) -> Self: ...

class Document:
    def __init__(self, content: str):
        self.content = content
    def clone(self) -> Self:
        return Document(self.content)

# Self ensures clone() returns the same type as self, not just Cloneable
```

For Python <3.11, use `from typing_extensions import Self`.

### 7.2 Protocols With `__call__`

```python
from typing import Protocol

class Transformer(Protocol):
    def __call__(self, data: str) -> str: ...

def apply_all(data: str, transformers: list[Transformer]) -> str:
    for t in transformers:
        data = t(data)
    return data

class Upper:
    def __call__(self, data: str) -> str:
        return data.upper()

def exclaim(data: str) -> str:
    return data + "!"

print(apply_all("hello", [Upper(), exclaim]))  # HELLO!
# Both Upper instance and plain function satisfy Transformer — both are callable with (str) -> str
```

### 7.3 Callback Protocols (PEP 544)

```python
from typing import Protocol

class OnEvent(Protocol):
    def __call__(self, event: str, data: dict) -> None: ...

def register_handler(handler: OnEvent) -> None:
    handler("user_login", {"user": "alice"})

def my_handler(event: str, data: dict) -> None:
    print(f"Event {event}: {data}")

register_handler(my_handler)  # OK — function matches OnEvent protocol

class HandlerClass:
    def __call__(self, event: str, data: dict) -> None:
        print(f"Class handler: {event}")

register_handler(HandlerClass())  # OK — instance with __call__ matches too
```

### 7.4 Merging Protocols — Protocol Inheritance

```python
from typing import Protocol

class Readable(Protocol):
    def read(self) -> str: ...

class Writable(Protocol):
    def write(self, data: str) -> int: ...

class ReadWritable(Readable, Writable, Protocol):
    """Requires both read() and write()."""
    ...

class MyBuffer:
    def read(self) -> str: return "data"
    def write(self, data: str) -> int: return len(data)

def process_rw(buf: ReadWritable) -> None:
    buf.write(buf.read())

process_rw(MyBuffer())  # OK — has both

class ReadOnly:
    def read(self) -> str: return "data"

# process_rw(ReadOnly())  # mypy error: missing write()
```

### 7.5 Explicit `Protocol` Base Is Required

```python
from typing import Protocol

# Correct — explicitly inherits from Protocol:
class MyProto(Protocol):
    def method(self) -> None: ...

# Wrong — looks like a protocol but isn't:
class NotAProtocol:
    def method(self) -> None: ...

# Type checkers only treat classes inheriting from Protocol as structural.
# NotAProtocol is nominal — isinstance checks and type compatibility are nominal.
```

## 8. Common Mistakes and Pitfalls

### 8.1 Forgetting `@runtime_checkable` Then Using `isinstance`

```python
from typing import Protocol

class MyProto(Protocol):
    def method(self) -> None: ...

# isinstance(MyProto(), MyProto) — TypeError at runtime!
# Fix: add @runtime_checkable
```

### 8.2 Assuming `@runtime_checkable` Validates Types

As shown in Section 3.3, it only checks attribute existence. Do not rely on it for type safety — that is the static checker's job.

### 8.3 Using Protocols Where an ABC Is Better

```python
# Bad: protocol with shared logic — should be ABC
from typing import Protocol

class BadProto(Protocol):
    def required(self) -> int: ...
    def helper(self) -> int:
        return self.required() * 2  # concrete logic in protocol — unusual

# Better as ABC:
from abc import ABC, abstractmethod

class GoodABC(ABC):
    @abstractmethod
    def required(self) -> int: ...
    def helper(self) -> int:
        return self.required() * 2  # natural in ABC
```

### 8.4 Over-Specifying Protocols

```python
# Over-specified — requires too many members, hard to satisfy
from typing import Protocol

class OverSpecified(Protocol):
    def connect(self) -> None: ...
    def disconnect(self) -> None: ...
    def send(self, data: str) -> None: ...
    def receive(self) -> str: ...
    def ping(self) -> bool: ...
    def get_status(self) -> str: ...

# Better: split into focused protocols (Interface Segregation Principle)
class Connectable(Protocol):
    def connect(self) -> None: ...
    def disconnect(self) -> None: ...

class Sendable(Protocol):
    def send(self, data: str) -> None: ...

class Receivable(Protocol):
    def receive(self) -> str: ...
```

Smaller protocols are easier to satisfy and compose. This mirrors the mixin philosophy (Lesson 12.3): small, focused, composable.

### 8.5 Confusing `Protocol` With `ABC` Registration

```python
from typing import Protocol

class MyProto(Protocol):
    def method(self) -> None: ...

# Protocols don't have register() — that's an ABC feature
# MyProto.register(MyClass)  # AttributeError — no such method

# For protocols, structural matching is automatic — no registration needed
class MyClass:
    def method(self) -> None: pass

# MyClass already satisfies MyProto structurally — nothing to do
```

## 9. Realistic End-to-End Example: E-Commerce System With Protocols

```python
from typing import Protocol, TypeVar, Optional
from dataclasses import dataclass

# --- Protocols (interfaces) ---

class PaymentProcessor(Protocol):
    def charge(self, amount: float) -> str: ...
    def refund(self, transaction_id: str, amount: float) -> str: ...

class Notifier(Protocol):
    def notify(self, recipient: str, message: str) -> None: ...

class Inventory(Protocol):
    def check_stock(self, product_id: str) -> int: ...
    def reserve(self, product_id: str, quantity: int) -> bool: ...
    def release(self, product_id: str, quantity: int) -> None: ...

# --- Concrete implementations — no inheritance from protocols! ---

@dataclass
class Order:
    product_id: str
    quantity: int
    amount: float
    customer_email: str

class StripeProcessor:
    def charge(self, amount: float) -> str:
        print(f"[Stripe] Charging ${amount:.2f}")
        return f"stripe-txn-{amount:.0f}"

    def refund(self, transaction_id: str, amount: float) -> str:
        print(f"[Stripe] Refunding ${amount:.2f} for {transaction_id}")
        return f"stripe-refund-{amount:.0f}"

class EmailNotifier:
    def notify(self, recipient: str, message: str) -> None:
        print(f"[Email] To {recipient}: {message}")

class InMemoryInventory:
    def __init__(self):
        self._stock: dict[str, int] = {"widget": 100, "gadget": 5}

    def check_stock(self, product_id: str) -> int:
        return self._stock.get(product_id, 0)

    def reserve(self, product_id: str, quantity: int) -> bool:
        if self._stock.get(product_id, 0) >= quantity:
            self._stock[product_id] -= quantity
            return True
        return False

    def release(self, product_id: str, quantity: int) -> None:
        self._stock[product_id] = self._stock.get(product_id, 0) + quantity

# --- Business logic — depends ONLY on protocols ---

class OrderService:
    def __init__(
        self,
        payments: PaymentProcessor,
        notifications: Notifier,
        inventory: Inventory,
    ):
        self.payments = payments
        self.notifications = notifications
        self.inventory = inventory

    def place_order(self, order: Order) -> str | None:
        # Check inventory
        if self.inventory.check_stock(order.product_id) < order.quantity:
            self.notifications.notify(order.customer_email, "Out of stock")
            return None

        # Reserve stock
        if not self.inventory.reserve(order.product_id, order.quantity):
            self.notifications.notify(order.customer_email, "Failed to reserve")
            return None

        # Charge
        try:
            txn_id = self.payments.charge(order.amount)
        except Exception as e:
            self.inventory.release(order.product_id, order.quantity)
            self.notifications.notify(order.customer_email, f"Payment failed: {e}")
            return None

        self.notifications.notify(order.customer_email, f"Order confirmed: {txn_id}")
        return txn_id

# --- Wiring — swap any implementation ---

service = OrderService(
    payments=StripeProcessor(),
    notifications=EmailNotifier(),
    inventory=InMemoryInventory(),
)

txn = service.place_order(Order("widget", 2, 49.99, "alice@example.com"))
print(f"Transaction: {txn}")

# --- Testing — trivial fakes, no mocking library needed ---

class FakePayments:
    def __init__(self):
        self.charges: list[float] = []
    def charge(self, amount: float) -> str:
        self.charges.append(amount)
        return "fake-txn-1"
    def refund(self, transaction_id: str, amount: float) -> str:
        return "fake-refund-1"

class FakeNotifier:
    def __init__(self):
        self.messages: list[tuple[str, str]] = []
    def notify(self, recipient: str, message: str) -> None:
        self.messages.append((recipient, message))

class FakeInventory:
    def __init__(self, stock: int = 10):
        self.stock = stock
        self.reserved: list[tuple[str, int]] = []
    def check_stock(self, product_id: str) -> int:
        return self.stock
    def reserve(self, product_id: str, quantity: int) -> bool:
        if self.stock >= quantity:
            self.stock -= quantity
            self.reserved.append((product_id, quantity))
            return True
        return False
    def release(self, product_id: str, quantity: int) -> None:
        self.stock += quantity

def test_order_success():
    payments = FakePayments()
    notifications = FakeNotifier()
    inventory = FakeInventory(stock=10)
    svc = OrderService(payments, notifications, inventory)
    txn = svc.place_order(Order("widget", 2, 49.99, "alice@example.com"))
    assert txn == "fake-txn-1"
    assert payments.charges == [49.99]
    assert any("confirmed" in m[1] for m in notifications.messages)
    print("test_order_success passed")

def test_order_out_of_stock():
    svc = OrderService(FakePayments(), FakeNotifier(), FakeInventory(stock=0))
    txn = svc.place_order(Order("widget", 5, 99.99, "bob@example.com"))
    assert txn is None
    print("test_order_out_of_stock passed")

test_order_success()
test_order_out_of_stock()
```

Key observations:

- `OrderService` has **zero knowledge** of `StripeProcessor`, `EmailNotifier`, or `InMemoryInventory`. It depends only on three protocols.
- Swapping Stripe for PayPal, email for SMS, or in-memory inventory for a database requires **no changes** to `OrderService`.
- Test fakes are 5-line classes — no `unittest.mock`, no inheritance, no registration. Any object with the right methods works.
- A static type checker verifies that every argument to `OrderService.__init__` satisfies its protocol — at development time, not at runtime.

## 10. Summary

| Concept | Key Takeaway |
|---------|--------------|
| Structural vs nominal | Structural asks "what can you do?"; nominal asks "what are you declared to be?" |
| `Protocol` | Explicit structural contract — type checker verifies, no inheritance needed. |
| `@runtime_checkable` | Enables `isinstance`/`issubclass` — but only checks `hasattr`, not types. |
| Methods + attributes | Protocols can require methods, attributes, properties — any combination. |
| Generic protocols | `Protocol[T]` for type-parameterized contracts; declare variance (`T_co`, `T_contra`, `T`). |
| Protocol vs ABC | Protocol for decoupled structural contracts; ABC for shared logic + nominal coupling. |
| Protocol vs duck typing | Protocol makes the duck contract explicit and statically verifiable; duck typing is implicit. |
| Decoupling | Depend on protocols, not concretes — enables swapping, testing, and adapter patterns. |

### The Big Picture — All Four Mechanisms Together

```
                  Coupling ◄────────────────────────► Flexibility
                         │                              │
Concrete class ──── ABC ──── Protocol ──── Duck typing
 (tightest)        (nominal)  (structural)   (implicit)
                         │                              │
                  Enforcement ◄──────────────────────► Freedom
```

No single mechanism is "best." Use each where it fits:

- **Concrete class** when you own the type and want shared code.
- **ABC** when you need Template Method, mixin helpers, or strict nominal `isinstance`.
- **Protocol** when you want explicit contracts without coupling — especially for public APIs and large typed codebases.
- **Duck typing** when the contract is trivial (1-2 methods) and you are inside a small, trusted scope.

The mark of a mature Python design is choosing the *lightest* mechanism that provides the guarantees you need.
