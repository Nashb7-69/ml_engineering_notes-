## 1. What Polymorphism Really Means

**Polymorphism** (from Greek *poly* "many" + *morphe* "form") means a single interface works with many types. The caller does not know or care what concrete type it holds — it just calls a method and the right implementation runs.

Most textbooks introduce polymorphism *through* inheritance:

```
Animal → Dog, Cat, Bird  (inheritance hierarchy, virtual dispatch)
```

Python supports that (Lessons 12.1–12.3), but it is the *least interesting* form of polymorphism in Python. The more powerful form requires **no inheritance at all**.

### 1.1 Two Kinds of Polymorphism

| Kind | Mechanism | Needs Shared Base? | Example |
|------|-----------|--------------------|---------|
| **Subtype (inheritance) polymorphism** | Shared base class, virtual dispatch via MRO | Yes | `Dog(Animal)`, `Cat(Animal)` — `animal.speak()` dispatches via MRO |
| **Duck (structural) polymorphism** | Shared method *names/signatures*, no base needed | No | Any object with `.read()` works with `read_data(obj)` |

Python supports both, but idiomatic Python leans heavily on the second.

### 1.2 Inheritance Polymorphism — The Familiar Way

```python
class Animal:
    def speak(self) -> str:
        raise NotImplementedError

class Dog(Animal):
    def speak(self) -> str:
        return "Woof"

class Cat(Animal):
    def speak(self) -> str:
        return "Meow"

def make_speak(animal: Animal) -> None:
    print(animal.speak())

make_speak(Dog())  # Woof
make_speak(Cat())  # Meow
```

This works. But notice: `make_speak` only *needs* `animal.speak()` to exist. It never uses `isinstance(animal, Animal)` or any `Animal`-specific state. The base class is just a namespace for the contract.

### 1.3 Duck Polymorphism — No Base Needed

```python
class Dog:
    def speak(self) -> str:
        return "Woof"

class Cat:
    def speak(self) -> str:
        return "Meow"

class Robot:
    def speak(self) -> str:
        return "Beep boop"

class Human:
    def speak(self) -> str:
        return "Hello"

def make_speak(speaker) -> None:
    print(speaker.speak())

for s in [Dog(), Cat(), Robot(), Human()]:
    make_speak(s)
# Woof
# Meow
# Beep boop
# Hello
```

No shared base. No `Animal`. No inheritance. Yet `make_speak` is fully polymorphic — it works with *any* object that has a `speak()` method.

**This is duck typing.** The name comes from the aphorism (attributed to James Whitcomb Riley):

> "If it walks like a duck and quacks like a duck, then it must be a duck."

In Python: if an object has the methods/attributes you need, it *is* the right type — regardless of its class.

## 2. Duck Typing in Depth

### 2.1 Duck Typing Is Structural, Not Nominal

| Typing Discipline | "What type is X?" | Example |
|-------------------|-------------------|---------|
| **Nominal** (Java, C#) | "Is X declared as an instance of `Duck` or its subclass?" | `if (x instanceof Duck)` |
| **Structural** (Python duck typing) | "Does X have `walk()` and `quack()`?" | `if hasattr(x, "quack")` — or just call `x.quack()` |
| **Gradual structural** (Python `Protocol`) | "Does X satisfy the `Duck` Protocol?" | `isinstance(x, Duck)` with `@runtime_checkable` Protocol |

Duck typing is *implicitly* structural — you never declare the structure, you just use it.

### 2.2 The Canonical Example: File-Like Objects

Python's I/O is the best real-world duck typing example. `open()` returns a file object, but *any* object with `.read()`, `.write()`, or `.readline()` can be used wherever a file is expected:

```python
import io

def count_lines(source) -> int:
    """Counts lines in any file-like object — no base class required."""
    return sum(1 for _ in source)

# Real file
with open("/etc/hosts") as f:
    print(count_lines(f))

# In-memory string buffer — no file on disk, but quacks like a file
buf = io.StringIO("hello\nworld\n")
print(count_lines(buf))  # 2

# Custom file-like — just needs __iter__
class ListSource:
    def __iter__(self):
        return iter(["a\n", "b\n", "c\n"])

print(count_lines(ListSource()))  # 3

# Even a generator works
print(count_lines(line for line in ["x\n", "y\n"]))  # 2
```

`count_lines` never checks `isinstance(source, io.IOBase)`. It just iterates. Anything iterable works.

### 2.3 More Duck Typing Examples

```python
# Example 1: Any object with __len__ works with len()
print(len([1, 2, 3]))    # list
print(len("hello"))       # str
print(len({"a": 1}))      # dict

class CustomCollection:
    def __len__(self):
        return 42

print(len(CustomCollection()))  # 42 — no base class needed

# Example 2: Any object with __iter__ works in for loops
class Countdown:
    def __init__(self, n: int):
        self.n = n
    def __iter__(self):
        return self
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

for x in Countdown(3):
    print(x)  # 3, 2, 1

# Example 3: Context managers — any object with __enter__/__exit__
class Timer:
    def __enter__(self):
        import time
        self.start = time.perf_counter()
        return self
    def __exit__(self, *args):
        import time
        print(f"Elapsed: {time.perf_counter() - self.start:.4f}s")

with Timer():
    sum(range(1_000_000))

# Example 4: Callables — any object with __call__
class Multiplier:
    def __init__(self, factor: float):
        self.factor = factor
    def __call__(self, x: float) -> float:
        return x * self.factor

double = Multiplier(2)
print(double(21))  # 42
print(callable(double))  # True
```

### 2.4 Duck Typing vs. `hasattr` Checks

A naive duck typing check:

```python
def play_sound(obj):
    if hasattr(obj, "speak"):
        print(obj.speak())
    else:
        print("Silent")
```

This is *LBYL duck typing* — checking before acting. It works but is not the most Pythonic form (see Section 3). True duck typing just *calls* the method and handles failure:

```python
def play_sound(obj):
    try:
        print(obj.speak())
    except AttributeError:
        print("Silent")
```

More on this choice in Section 3.

### 2.5 When Duck Typing Breaks Down

```python
class Duck:
    def quack(self): return "Quack!"

class Person:
    def quack(self): return "I'm quacking like a duck!"

# Both quack, but Person is not a Duck — duck typing conflates them.
# If quack() has side effects or different semantics, this is a bug.

# Also: name collisions
class Car:
    def read(self): return "car data"  # read() means something different than file read()

def process_file(f):
    print(f.read())  # works with Car, but semantics are wrong — Car.read is not file read
```

**Limitations:**

- Relies on method *names* alone — no semantic guarantee.
- No way to declare "I intend to be file-like" — tooling cannot verify.
- `hasattr` checks are fragile (attribute might exist but be non-callable, or callable with wrong signature).

Protocols (Lesson 12.6) solve these by making the structural contract *explicit* and *type-checkable*.

## 3. EAFP vs LBYL — Two Philosophies

### 3.1 Definitions

| Philosophy | Full Name | Approach | Origin |
|------------|-----------|----------|--------|
| **EAFP** | Easier to Ask Forgiveness than Permission | Try the operation; handle the exception if it fails | Pythonic, encouraged by Python docs |
| **LBYL** | Look Before You Leap | Check preconditions before acting | Common in C, Java; defensive programming |

```python
# EAFP: just do it, apologize if it fails
def get_value_eafp(mapping, key):
    try:
        return mapping[key]
    except KeyError:
        return None

# LBYL: check first, then act
def get_value_lbyl(mapping, key):
    if key in mapping:
        return mapping[key]
    else:
        return None
```

Both return the same result. The difference is in *how* they handle the missing-key case — and in subtle correctness and performance implications.

### 3.2 EAFP Examples — The Pythonic Default

```python
# Example 1: Dictionary access
def process_user(user_dict: dict):
    try:
        name = user_dict["name"]
    except KeyError:
        name = "Anonymous"
    print(f"Hello, {name}")

# Example 2: File operations
import os

def read_config_eafp(path: str) -> str:
    try:
        with open(path) as f:
            return f.read()
    except FileNotFoundError:
        return "default config"
    except PermissionError:
        return "permission denied"

# Example 3: Attribute access
def get_name_eafp(obj) -> str:
    try:
        return obj.name
    except AttributeError:
        return "unnamed"

# Example 4: Type coercion
def parse_int_eafp(value: str) -> int | None:
    try:
        return int(value)
    except ValueError:
        return None

# Example 5: Duck typing in action — EAFP style
def render(obj) -> str:
    try:
        return obj.render()  # try duck method
    except AttributeError:
        return str(obj)      # fallback
```

### 3.3 LBYL Examples — When You Check First

```python
# Example 1: Dictionary access
def process_user_lbyl(user_dict: dict):
    if "name" in user_dict:
        name = user_dict["name"]
    else:
        name = "Anonymous"
    print(f"Hello, {name}")

# Example 2: File operations
def read_config_lbyl(path: str) -> str:
    if not os.path.exists(path):
        return "default config"
    if not os.access(path, os.R_OK):
        return "permission denied"
    with open(path) as f:
        return f.read()

# Example 3: Attribute access
def get_name_lbyl(obj) -> str:
    if hasattr(obj, "name"):
        return obj.name
    else:
        return "unnamed"

# Example 4: Type coercion
def parse_int_lbyl(value: str) -> int | None:
    if value.lstrip("-").isdigit():
        return int(value)
    else:
        return None

# Example 5: Duck typing — LBYL style
def render_lbyl(obj) -> str:
    if hasattr(obj, "render") and callable(getattr(obj, "render")):
        return obj.render()
    else:
        return str(obj)
```

### 3.4 EAFP vs LBYL — Detailed Comparison

| Dimension | EAFP | LBYL |
|-----------|------|------|
| **Correctness (race conditions)** | Safe — operation and check are atomic (one syscall) | Vulnerable — state can change between check and use (TOCTOU bug) |
| **Performance (happy path)** | Faster when success is common — no extra check | Faster when failure is common — avoids exception overhead |
| **Performance (failure path)** | Slower — exception creation has cost | Faster — simple branch |
| **Readability** | Cleaner when many preconditions — one `try` vs many `if`s | Clearer when precondition logic is complex or has side effects |
| **Exception specificity** | Must catch precise exceptions (`KeyError`, not bare `except`) | No exceptions — but must enumerate all failure modes |
| **Works with duck typing** | Naturally — just call the method | Requires `hasattr`/`callable` checks, which are incomplete |

### 3.5 The Race Condition (TOCTOU) — EAFP's Killer Argument

**TOCTOU** = Time Of Check, Time Of Use. Between your check and your use, the world can change.

```python
import os

# LBYL — race condition:
if os.path.exists("data.csv"):       # check: file exists? yes
    # <-- another process deletes data.csv here!
    with open("data.csv") as f:      # use: FileNotFoundError!
        data = f.read()

# EAFP — no race:
try:
    with open("data.csv") as f:      # single atomic operation
        data = f.read()
except FileNotFoundError:
    data = None
```

The same applies to dict access in threaded code, attribute checks on mutable objects, and permission checks:

```python
# LBYL dict access — race in threaded code:
if key in shared_dict:           # check
    # <-- another thread deletes shared_dict[key] here!
    value = shared_dict[key]     # KeyError!

# EAFP — atomic:
try:
    value = shared_dict[key]
except KeyError:
    value = None
```

**Rule of thumb:** If the check and the use are *separate operations* that could be interleaved, prefer EAFP.

### 3.6 Performance Tradeoffs — When LBYL Wins

Exception handling in Python is *fast* when no exception is raised, but *slow* when one is:

```python
import timeit

# EAFP faster when key usually exists (common case, no exception)
print(timeit.timeit(
    'try:\n d["key"]\nexcept KeyError: pass',
    setup='d = {"key": 1}', number=1_000_000
))
# ~0.04s

print(timeit.timeit(
    'if "key" in d: d["key"]',
    setup='d = {"key": 1}', number=1_000_000
))
# ~0.06s — slightly slower (extra hash lookup)

# LBYL faster when key usually MISSING (exception is expensive)
print(timeit.timeit(
    'try:\n d["missing"]\nexcept KeyError: pass',
    setup='d = {"key": 1}', number=1_000_000
))
# ~0.25s — exception overhead dominates

print(timeit.timeit(
    'if "missing" in d: d["missing"]',
    setup='d = {"key": 1}', number=1_000_000
))
# ~0.05s — branch is cheap
```

**Guideline:**

- If you *expect* success (key usually exists, file usually present, attribute usually there) → EAFP is both cleaner and faster.
- If you *expect* failure (probing many possible keys, many of which are absent) → LBYL may be faster. But measure — the difference rarely matters outside hot loops.

### 3.7 EAFP Pitfalls — Catching Too Broadly

The #1 EAFP mistake is catching too broad an exception:

```python
# BAD: bare except hides bugs
def get_name_bad(obj):
    try:
        return obj.name.upper()  # AttributeError if no .name, but also if .name is None!
    except:  # catches everything, including bugs in .upper()
        return "unnamed"

# BAD: catching Exception hides programming errors
def parse_bad(value):
    try:
        return int(value.strip().upper())  # ValueError, AttributeError, etc.
    except Exception:
        return None  # silently swallows TypeError if value is not a string

# GOOD: catch the specific exception you expect
def get_name_good(obj):
    try:
        return obj.name
    except AttributeError:
        return "unnamed"

def parse_good(value):
    try:
        return int(value)
    except ValueError:
        return None
    except AttributeError:
        raise TypeError(f"Expected str, got {type(value).__name__}")

# GOOD: keep try block minimal — only wrap the operation that might fail
def get_name_minimal(obj):
    try:
        name = obj.name       # only this line might raise AttributeError
    except AttributeError:
        return "unnamed"
    return name.upper()       # if this fails, it's a real bug — don't catch it
```

**Rules for EAFP:**

1. Catch the *narrowest* exception type that represents the expected failure.
2. Keep the `try` block as small as possible — wrap only the fallible operation.
3. Never use bare `except:` or `except Exception:` for EAFP control flow.

## 4. `isinstance` vs Duck Typing vs Protocol — Choosing the Right Check

### 4.1 The Spectrum

```
Strict nominal ◄──────────────────────────────────────► Pure duck typing
isinstance(x, ConcreteClass)    isinstance(x, ABC)    hasattr / try-except    Protocol
     ▲                                  ▲                     ▲                    ▲
  Tightest coupling              Looser (virtual subclasses)  No coupling      Explicit structural contract
```

### 4.2 `isinstance` — When It Is Appropriate

`isinstance` is *not* un-Pythonic per se. It is the right tool when:

- You need to handle fundamentally different types with different logic (not just different method names).
- You are at a system boundary (parsing JSON, user input, API response) where types are truly unknown.
- You use ABCs or Protocols with `@runtime_checkable` (Lessons 12.5–12.6).

```python
# Appropriate isinstance — handling genuinely different types
def serialize(obj) -> str:
    if isinstance(obj, str):
        return f'"{obj}"'
    elif isinstance(obj, (int, float)):
        return str(obj)
    elif isinstance(obj, list):
        return "[" + ", ".join(serialize(x) for x in obj) + "]"
    elif hasattr(obj, "__dict__"):
        return serialize(obj.__dict__)
    else:
        return str(obj)

# Appropriate isinstance — ABC check (Lesson 12.5)
from collections.abc import Mapping

def process_mapping(data) -> None:
    if isinstance(data, Mapping):
        for k, v in data.items():
            print(k, v)
    else:
        raise TypeError(f"Expected a mapping, got {type(data).__name__}")

# Works with dict, OrderedDict, custom Mapping subclasses, and virtual subclasses
print(isinstance({}, Mapping))  # True
print(isinstance({"a": 1}, Mapping))  # True
```

### 4.3 `isinstance` Considered Harmful — The Anti-Pattern

```python
# BAD: isinstance dispatch that should be polymorphism
def make_sound(animal):
    if isinstance(animal, Dog):
        print("Woof")
    elif isinstance(animal, Cat):
        print("Meow")
    elif isinstance(animal, Bird):
        print("Tweet")
    else:
        raise TypeError(f"Unknown animal: {type(animal)}")

# Every new animal requires editing this function — violates Open/Closed Principle.
# The isinstance chain grows without bound.

# GOOD: let the object decide — polymorphic dispatch
def make_sound_good(animal):
    print(animal.speak())  # duck typing — no isinstance needed

# GOOD: if you must dispatch on type, use singledispatch
from functools import singledispatch

@singledispatch
def make_sound_dispatch(animal):
    raise TypeError(f"Unknown animal: {type(animal)}")

@make_sound_dispatch.register
def _(animal: Dog):
    print("Woof")

@make_sound_dispatch.register
def _(animal: Cat):
    print("Meow")
# Extensible without modifying make_sound_dispatch itself
```

### 4.4 Duck Typing vs `isinstance` — Decision Table

| Situation | Recommended Approach | Example |
|-----------|---------------------|---------|
| Need one method/attribute, any provider | Duck typing (EAFP) | `try: obj.read()` |
| Need multiple related methods (interface) | Protocol or ABC | `isinstance(obj, Readable)` with Protocol |
| Handling truly distinct types differently | `isinstance` or `singledispatch` | `if isinstance(x, str): ... elif isinstance(x, int):` |
| At system boundary, untrusted input | `isinstance` + validation | `if not isinstance(data, dict): raise` |
| Inside core logic, trusted objects | Duck typing — no check | `obj.process()` directly |
| Need to support virtual subclasses | ABC + `register` | `MyDict.register(dict)` |
| Performance-critical hot loop | LBYL `isinstance` if failure is common | `if key in d` vs `try: d[key]` |

### 4.5 `hasattr` vs `try/except` vs `getattr` — Duck Typing Mechanics

```python
class Duck:
    def quack(self): return "Quack!"

class Silent:
    pass

# Method 1: hasattr (LBYL)
def quack_lbyl(obj):
    if hasattr(obj, "quack"):
        return obj.quack()
    return "..."

# Method 2: try/except (EAFP)
def quack_eafp(obj):
    try:
        return obj.quack()
    except AttributeError:
        return "..."

# Method 3: getattr with default
def quack_getattr(obj):
    quack = getattr(obj, "quack", None)
    if callable(quack):
        return quack()
    return "..."

# Method 4: getattr + EAFP hybrid
def quack_hybrid(obj):
    try:
        quack = getattr(obj, "quack")
    except AttributeError:
        return "..."
    if callable(quack):
        return quack()
    return "..."
```

Subtle differences:

- `hasattr(obj, "quack")` internally does `try: getattr(obj, "quack"); return True; except AttributeError: return False` — it is EAFP under the hood! But it also swallows exceptions raised *inside* `__getattr__`/`__getattribute__`, which can hide bugs.
- `getattr(obj, "quack", None)` avoids the exception but conflates "attribute is None" with "attribute missing."
- `try: obj.quack()` is the most direct — it tests both existence and callability in one step.

For callable duck typing, `try: obj.quack()` is almost always preferred.

## 5. Realistic Domain Examples

### 5.1 Payment Processing — Duck Typing Over Inheritance

```python
# No base class — each payment type just needs .charge(amount) and .refund(amount)

class CardPayment:
    def __init__(self, card_id: str):
        self.card_id = card_id

    def charge(self, amount: float) -> str:
        return f"Charged ${amount:.2f} to card {self.card_id}"

    def refund(self, amount: float) -> str:
        return f"Refunded ${amount:.2f} to card {self.card_id}"

class CryptoPayment:
    def __init__(self, wallet: str):
        self.wallet = wallet

    def charge(self, amount: float) -> str:
        return f"Charged ${amount:.2f} to wallet {self.wallet}"

    def refund(self, amount: float) -> str:
        return f"Refunded ${amount:.2f} to wallet {self.wallet}"

class StoreCredit:
    def __init__(self, balance: float):
        self.balance = balance

    def charge(self, amount: float) -> str:
        if amount > self.balance:
            raise ValueError("Insufficient store credit")
        self.balance -= amount
        return f"Charged ${amount:.2f} from store credit (remaining: ${self.balance:.2f})"

    def refund(self, amount: float) -> str:
        self.balance += amount
        return f"Refunded ${amount:.2f} to store credit (new balance: ${self.balance:.2f})"

# Polymorphic function — works with ANY object that has charge/refund
def process_payment(payment, amount: float) -> None:
    try:
        result = payment.charge(amount)
        print(result)
    except AttributeError:
        print(f"Payment method {type(payment).__name__} does not support charge()")
    except ValueError as e:
        print(f"Payment failed: {e}")

# All three work without sharing a base:
for method in [CardPayment("4242"), CryptoPayment("0xABC"), StoreCredit(100)]:
    process_payment(method, 50)

# Even a mock for testing — no inheritance needed:
class MockPayment:
    def charge(self, amount): return f"Mock charged {amount}"
    def refund(self, amount): return f"Mock refunded {amount}"

process_payment(MockPayment(), 10)  # works!
```

### 5.2 Data Pipeline — Duck-Typed Transformers

```python
# Each transformer just needs .transform(data) — no base class

class Normalizer:
    def transform(self, data: list[float]) -> list[float]:
        m = max(data) if data else 1
        return [x / m for x in data]

class Filter:
    def __init__(self, threshold: float):
        self.threshold = threshold
    def transform(self, data: list[float]) -> list[float]:
        return [x for x in data if x >= self.threshold]

class Logger:
    def transform(self, data: list[float]) -> list[float]:
        print(f"[Logger] data: {data}")
        return data

def run_pipeline(data: list[float], steps) -> list[float]:
    for step in steps:
        # EAFP duck typing — try to call transform, fail clearly if missing
        try:
            transform = step.transform
        except AttributeError:
            raise TypeError(f"Pipeline step {type(step).__name__!r} has no transform() method") from None
        data = transform(data)
    return data

result = run_pipeline([0.1, 0.5, 0.9], [Logger(), Filter(0.3), Normalizer()])
print(result)  # [Logger] data: [0.1, 0.5, 0.9] → [0.5, 0.9] → [0.55, 1.0]

# Adding a new step requires zero changes to run_pipeline:
class Doubler:
    def transform(self, data): return [x * 2 for x in data]

print(run_pipeline([1, 2, 3], [Doubler()]))  # [2, 4, 6]
```

### 5.3 Notification System — `singledispatch` as an Alternative to `isinstance` Chains

```python
from functools import singledispatch

class EmailNotification:
    def __init__(self, address: str, body: str):
        self.address = address
        self.body = body

class SMSNotification:
    def __init__(self, phone: str, body: str):
        self.phone = phone
        self.body = body

class PushNotification:
    def __init__(self, device_id: str, body: str):
        self.device_id = device_id
        self.body = body

@singledispatch
def send(notification) -> str:
    raise TypeError(f"No handler for {type(notification).__name__}")

@send.register
def _(n: EmailNotification) -> str:
    return f"Email to {n.address}: {n.body}"

@send.register
def _(n: SMSNotification) -> str:
    return f"SMS to {n.phone}: {n.body}"

@send.register
def _(n: PushNotification) -> str:
    return f"Push to {n.device_id}: {n.body}"

for n in [
    EmailNotification("alice@example.com", "Hello!"),
    SMSNotification("+1234567890", "Hi!"),
    PushNotification("device-123", "Hey!"),
]:
    print(send(n))

# Adding a new notification type doesn't modify send() — just register a new handler.
# This is polymorphism via dispatch, not inheritance.
```

## 6. Performance and Correctness Tradeoffs — Summary

### 6.1 When Each Style Wins

| Scenario | Best Choice | Why |
|----------|-------------|-----|
| File exists / key present 90%+ of time | EAFP (`try/except`) | No extra check on happy path |
| Key missing 90%+ of time, hot loop | LBYL (`if key in dict`) | Avoids expensive exception creation |
| Concurrent / multi-process I/O | EAFP | Avoids TOCTOU race |
| Need to distinguish "missing" from "None" | EAFP or `sentinel` pattern | `dict.get` conflates the two |
| Multiple preconditions to check | EAFP (single `try`) | Cleaner than nested `if`s |
| Precondition check has side effects | LBYL (check explicitly) | EAFP would trigger side effects |
| Public API, untrusted input | `isinstance` + validation | Fail fast with clear error |

### 6.2 The `dict.get` / `getattr` Middle Ground

```python
# dict.get — LBYL-like but concise, no exception
value = my_dict.get("key")           # None if missing (conflates None value)
value = my_dict.get("key", sentinel) # use sentinel to distinguish

_sentinel = object()
value = my_dict.get("key", _sentinel)
if value is _sentinel:
    print("key truly missing")

# getattr — same pattern for attributes
name = getattr(obj, "name", None)
name = getattr(obj, "name", _sentinel)
```

These are LBYL internally but read cleanly. Use them when `None` is a valid value and you need to distinguish absence.

## 7. Common Mistakes and Anti-Patterns

### 7.1 Over-Checking Types (Java in Python Clothing)

```python
# Un-Pythonic: checking types everywhere
def area(shape):
    if isinstance(shape, Circle):
        return 3.14 * shape.radius ** 2
    elif isinstance(shape, Rectangle):
        return shape.width * shape.height
    elif isinstance(shape, Triangle):
        return 0.5 * shape.base * shape.height
    else:
        raise TypeError("Unknown shape")

# Pythonic: let each shape know its area
class Circle:
    def __init__(self, radius): self.radius = radius
    def area(self): return 3.14 * self.radius ** 2

class Rectangle:
    def __init__(self, width, height): self.width = width; self.height = height
    def area(self): return self.width * self.height

def area_duck(shape):
    return shape.area()  # duck typing — no isinstance

# Or: use a Protocol (Lesson 12.6) for type safety without inheritance
```

### 7.2 Bare `except` in EAFP

```python
# Dangerous — hides bugs
try:
    result = obj.process()
except:  # catches KeyboardInterrupt, SystemExit, and every bug in process()
    result = None

# Safe — catches only the expected failure
try:
    result = obj.process()
except AttributeError:
    result = None
```

### 7.3 Using `hasattr` to Check Method Existence When You Should Just Call It

```python
# Verbose and racy:
if hasattr(obj, "save") and callable(obj.save):
    obj.save()

# Concise and correct:
try:
    obj.save()
except AttributeError:
    pass
```

Exception: when the method's *absence* is a normal, expected branch (not an error), `hasattr` can be more readable. Use judgment.

### 7.4 `type(x) == SomeClass` vs `isinstance`

```python
class Animal: pass
class Dog(Animal): pass

d = Dog()
print(type(d) == Animal)      # False — exact match only, rejects subclasses
print(isinstance(d, Animal))  # True — respects inheritance
print(type(d) is Dog)         # True — exact match, but isinstance is almost always preferred
```

Use `isinstance` unless you specifically need exact-type matching (rare — e.g., serialization that must not treat subclasses as their parent).

## 8. Summary

| Concept | Key Takeaway |
|---------|--------------|
| Polymorphism | One interface, many types. In Python, usually without inheritance. |
| Duck typing | "If it has the right methods, it is the right type." No base class needed. Use `try: obj.method()` (EAFP). |
| EAFP | Try the operation, handle the exception. Preferred in Python. Avoids TOCTOU, cleaner for expected-success cases. |
| LBYL | Check before acting. Better when failure is common or checks are cheap and operations are racy-free. |
| `isinstance` | Appropriate at system boundaries, for ABC/Protocol checks, and `singledispatch`. Anti-pattern as a polymorphic dispatch chain. |
| `hasattr`/`getattr` | LBYL duck typing — works but `try/except AttributeError` is usually more direct. |
| `singledispatch` | Clean alternative to `isinstance` chains — extensible without modifying the dispatcher. |

### Decision Flowchart

```
Need polymorphism?
├── All types share a meaningful is-a hierarchy?
│   └── Yes → Inheritance + method override (Lessons 12.1–12.3)
├── Types are unrelated but share method names?
│   └── Yes → Duck typing (this lesson) or Protocol (Lesson 12.6)
│       ├── Need static type checking? → Protocol
│       └── Just runtime? → EAFP duck typing
├── Handling fundamentally different types with different logic?
│   └── Yes → isinstance / singledispatch
└── At system boundary / untrusted input?
    └── Yes → isinstance + validation, then duck typing internally
```
