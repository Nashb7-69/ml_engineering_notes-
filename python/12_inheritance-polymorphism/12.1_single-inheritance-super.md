# 12.1 Single Inheritance & `super()`

## Learning Objectives

By the end of this lesson you will be able to:

- Model is-a relationships with single inheritance correctly in Python.
- Override methods intentionally and extend — not just replace — parent behavior.
- Explain what `super()` *actually* is (an MRO-aware proxy, not "the parent class").
- Use zero-argument `super()` and understand why it only works inside a class body.
- Write cooperative `__init__` chains with `**kwargs` forwarding.
- Diagnose the five most common `super()` mistakes.

---

## 1. Why Single Inheritance in Python Is Different

If you come from Java, C#, or C++ you already know inheritance as "a subclass reuses and specializes a superclass." Python agrees — then adds twists:

| Concern | Java / C# | Python |
|---------|-----------|--------|
| Inheritance model | Single + interfaces | Single *and* multiple (C3 MRO) |
| Root of hierarchy | `Object` | `object` — *everything* inherits from it |
| Method dispatch | Compile-time overload + runtime override | Purely runtime attribute lookup via MRO |
| `super` | Keyword referring to immediate parent | Built-in returning a *proxy* that follows the MRO |
| Constructors | `super(...)` must be first line | `super().__init__(...)` is a normal call you may place anywhere — or omit |
| Access control | `private`/`protected` keywords | Convention: `_single` and `__double` name mangling |

**Mental model:** Think of a Python class as a *namespace dictionary* plus an ordered list of ancestors (its MRO). Attribute lookup walks that list. Inheritance does not copy anything — it links.

### 1.1 The `object` Base

Every class implicitly inherits from `object` in Python 3:

```python
class Account:
    pass

print(Account.__bases__)   # (<class 'object'>,)
print(Account.__mro__)     # (<class 'Account'>, <class 'object'>)
print(isinstance(Account(), object))  # True
```

> Historical note: In Python 2 you had to write `class Account(object):` to get a "new-style" class. In Python 3 this is automatic. Section 10 covers the history.

## 2. Defining Single Inheritance

### 2.1 Minimal Example

```python
class Employee:
    """Base class — generic employee."""

    def __init__(self, name: str, salary: float) -> None:
        self.name = name
        self.salary = salary

    def pay_raise(self, percent: float) -> None:
        self.salary *= 1 + percent / 100

    def __repr__(self) -> str:
        return f"{self.__class__.__name__}(name={self.name!r}, salary={self.salary:.2f})"


class Developer(Employee):
    """Specialized employee who has a programming language."""

    def __init__(self, name: str, salary: float, language: str) -> None:
        super().__init__(name, salary)   # reuse parent initialization
        self.language = language

    def __repr__(self) -> str:
        # Extend rather than replace — delegate to parent then add detail
        base = super().__repr__()
        return base[:-1] + f", language={self.language!r})"
```

Explanation:

- `class Developer(Employee):` declares that `Developer` inherits from `Employee`. The tuple `Developer.__bases__` is now `(Employee,)`.
- `Developer` inherits `pay_raise` without redeclaring it. Attribute lookup finds `Employee.pay_raise` via the MRO.
- `__repr__` is *overridden* — `Developer` provides its own version that shadows the parent's.

```python
dev = Developer("Ada", 120_000, "Python")
print(dev)              # Developer(name='Ada', salary=120000.00, language='Python')
dev.pay_raise(10)
print(dev.salary)       # 132000.0
print(isinstance(dev, Employee))  # True — is-a holds
print(issubclass(Developer, Employee))  # True
```

### 2.2 Realistic Domain Example: Payment Processing

```python
from datetime import date

class Payment:
    def __init__(self, amount: float, currency: str = "USD") -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")
        self.amount = amount
        self.currency = currency
        self.created_on = date.today()

    def fee(self) -> float:
        """Base fee: 1 %."""
        return self.amount * 0.01

    def total(self) -> float:
        return self.amount + self.fee()

    def describe(self) -> str:
        return f"{self.amount:.2f} {self.currency} (fee {self.fee():.2f})"


class CardPayment(Payment):
    def __init__(self, amount: float, card_last4: str, **kwargs) -> None:
        super().__init__(amount, **kwargs)
        if len(card_last4) != 4 or not card_last4.isdigit():
            raise ValueError("card_last4 must be 4 digits")
        self.card_last4 = card_last4

    def fee(self) -> float:
        # Card payments cost more: base fee + $0.30 + 0.5 % extra
        return super().fee() + 0.30 + self.amount * 0.005

    def describe(self) -> str:
        return f"Card *{self.card_last4} — " + super().describe()


class BankTransferPayment(Payment):
    def fee(self) -> float:
        # Flat fee, cheaper for large amounts
        return 1.50
```

Explanation:

- `CardPayment.fee` *extends* the parent fee via `super().fee()`. `BankTransferPayment.fee` *replaces* it entirely — both are valid overriding strategies.
- `CardPayment.__init__` forwards `currency` via `**kwargs` so the parent signature can evolve without changing the child. More on this in Section 6.

## 3. Method Overriding — The Mechanics

### 3.1 What "Override" Means in Python

There is no `override` keyword. If a subclass defines an attribute with the same name as an ancestor, attribute lookup finds the subclass version first and stops.

```python
class Base:
    def greet(self) -> str:
        return "Hello from Base"

class Child(Base):
    def greet(self) -> str:
        return "Hello from Child"

print(Child().greet())   # Hello from Child
print(Base().greet())    # Hello from Base  — unaffected
```

Resolution order for `Child().greet()`:

1. Look in `Child.__dict__` → found → return it.
2. (Would look in `Base.__dict__`, then `object.__dict__` if not found.)

### 3.2 Three Overriding Strategies

| Strategy | Pattern | When to Use |
|----------|---------|-------------|
| **Replace** | Define new method, never call `super()` | Child behavior is fully independent |
| **Extend (before)** | Do work, then call `super().method()` | Pre-processing, validation |
| **Extend (after)** | Call `super().method()`, then do work | Post-processing, augmenting return value |
| **Wrap (around)** | Work before *and* after `super()` call | Logging, timing, transactions |

```python
import time
import logging

class Repository:
    def save(self, record: dict) -> None:
        print(f"Saving {record}")

class LoggingRepository(Repository):
    def save(self, record: dict) -> None:
        logging.info("save called with %s", record)   # before
        super().save(record)                           # delegate
        logging.info("save completed")                 # after
```

### 3.3 Overriding `__init__` Is Not Special

`__init__` is just another method. Python does **not** automatically call the parent `__init__`. If you override it and still want parent initialization, you must call `super().__init__()` explicitly.

```python
class Base:
    def __init__(self) -> None:
        print("Base.__init__")
        self.base_ready = True

class ChildNoSuper(Base):
    def __init__(self) -> None:
        print("ChildNoSuper.__init__ — forgot super()")
        self.child_ready = True

c = ChildNoSuper()
print(hasattr(c, "base_ready"))  # False — bug! Base init never ran
```

**Rule:** If the parent `__init__` does meaningful work (sets attributes, validates, registers), the child *must* call `super().__init__()`.

### 3.4 Can You Override Without `super()` and Still Be Correct?

Yes, when the parent method has no essential side effects or you intentionally replace them. Example: `BankTransferPayment.fee` above. But for `__init__`, forgetting `super()` is the #1 inheritance bug.

### 3.5 Method Resolution Is Dynamic — `self` Matters

```python
class Animal:
    def speak(self) -> str:
        return "..."

    def speak_twice(self) -> str:
        # Note: calls self.speak() — virtual dispatch
        return f"{self.speak()} and {self.speak()}"

class Dog(Animal):
    def speak(self) -> str:
        return "Woof"

print(Dog().speak_twice())  # Woof and Woof — not "... and ..."
```

Even though `speak_twice` is defined in `Animal`, `self.speak()` dispatches to `Dog.speak` because `self` is a `Dog`. This is *polymorphism through inheritance* — the same mechanism as virtual methods in Java/C#, but always "virtual" in Python.

## 4. `super()` Deep Dive — It Is Not "Call My Parent"

### 4.1 The Common Misconception

Most tutorials say "`super()` calls the parent class." This is **wrong** in two important ways:

1. `super()` does not necessarily call the *parent* — it calls the *next class in the MRO* after the current one.
2. In single inheritance the next class *happens* to be the parent, so the misconception is invisible — until multiple inheritance appears (Lesson 12.2).

**Accurate mental model:** `super()` returns a *proxy object* that delegates attribute lookup to the MRO starting *after* the current class.

### 4.2 The Two Forms

```python
# Zero-argument form — Python 3 only, most common
super().method()

# Two-argument form — explicit, works everywhere
super(CurrentClass, self).method()
super(CurrentClass, CurrentClass).method()  # for classmethods / alternative
```

They are equivalent inside an instance method of `CurrentClass`. The zero-argument form is syntactic sugar that the compiler fills in.

### 4.3 What `super()` Actually Returns

```python
class A:
    def method(self) -> str:
        return "A"

class B(A):
    def method(self) -> str:
        print(type(super()))          # <class 'super'>
        print(super())                # <super: <class 'B'>, <B object>>
        return super().method() + " -> B"

print(B().method())
```

`super()` is not a class and not an instance of the parent. It is a `super` object that knows two things: (1) where to *start* searching in the MRO, and (2) what `self` to bind to.

Internally `super().method` does roughly:

```python
# Conceptual — not actual CPython code
def super_method_lookup(cls, obj, name):
    mro = type(obj).__mro__          # e.g. (B, A, object)
    idx = mro.index(cls)             # find B
    for next_cls in mro[idx + 1:]:   # search A, then object
        if name in next_cls.__dict__:
            attr = next_cls.__dict__[name]
            # Bind descriptor (function -> method) if needed
            if hasattr(attr, "__get__"):
                return attr.__get__(obj, type(obj))
            return attr
    raise AttributeError
```

### 4.4 Zero-Argument `super()` Requires Lexical Scope

This surprises even experienced developers:

```python
class Child(Base):
    def greet(self) -> str:
        return super().greet() + "!"
```

How does `super()` know it is inside `Child.greet` without arguments? The compiler injects a hidden closure variable `__class__` into every method that uses `super()` or references `__class__`.

```python
class Demo:
    def method(self):
        print(__class__)          # <class 'Demo'> — implicitly created
        return super()

print(Demo.__dict__["method"].__code__.co_varnames)
# Inspect: contains __class__ as a free variable
```

**Consequences / edge cases:**

```python
# 1. Works: called inside a method body
class Child(Base):
    def greet(self):
        return super().greet()

# 2. FAILS: outside a class body — no __class__ in scope
def standalone():
    return super()  # RuntimeError: super(): no arguments

# 3. FAILS: inside a nested function without proper closure (Python <3.10 quirk,
#    now fixed, but still illustrative — always call super() directly in the method)
class Child2(Base):
    def greet(self):
        def inner():
            return super().greet()  # Works in Python 3.10+ via closure, but fragile
        return inner()

# 4. FAILS: assigning method outside class loses __class__ binding
def external_greet(self):
    return super().greet()  # RuntimeError — __class__ not defined here

Child.greet2 = external_greet
Child().greet2()  # error
```

**Rule:** Use zero-argument `super()` only *directly* inside a method defined with `def` inside a `class` body. For any indirection (decorators that move the function, `exec`, dynamically assigned functions), use the explicit two-argument form:

```python
def external_greet(self):
    return super(Child, self).greet()
```

### 4.5 `super()` With Different Method Types

```python
class Base:
    def instance_method(self):
        return "instance"

    @classmethod
    def class_method(cls):
        return f"class_method of {cls.__name__}"

    @staticmethod
    def static_method():
        return "static"

class Child(Base):
    def instance_method(self):
        return super().instance_method() + " -> child"

    @classmethod
    def class_method(cls):
        # super() inside a classmethod receives the class, not an instance
        return super().class_method() + f" -> child({cls.__name__})"

    @staticmethod
    def static_method():
        # No self/cls — super() has nothing to bind, but can still find the function
        # Use two-arg form or just call Base.static_method() directly
        return super(Child, Child).static_method() + " -> child"
        # Alternatively: return Base.static_method() + " -> child"
```

Important subtlety: inside a `@classmethod`, zero-argument `super()` binds to `cls`, not an instance. Inside a `@staticmethod`, there is no implicit first argument, so `super()` is less useful — direct parent access is clearer.

### 4.6 `super()` Is Lazy — No Call Happens Until You Access an Attribute

```python
class Child(Base):
    def greet(self):
        s = super()   # no lookup yet
        print("proxy created, no method called")
        return s.greet()  # lookup happens here
```

This matters for performance (negligible) and for understanding that `super().__init__` and `super().greet` are two different proxy lookups.

## 5. Cooperative vs Non-Cooperative Inheritance

### 5.1 Definitions

| Style | `__init__` Pattern | `super()` Usage | Chain Breaks? |
|-------|--------------------|-----------------|---------------|
| **Cooperative** | Every class calls `super().__init__(...)` and forwards unknown args via `**kwargs` | Always | No — chain continues through MRO |
| **Non-cooperative** | Calls parent by name: `Base.__init__(self, ...)` or omits call | Rarely / never | Yes — siblings in MRO are skipped |

In *single* inheritance, both styles work. The difference only matters when the class later participates in *multiple* inheritance (Lesson 12.2). But writing cooperatively from the start is the Pythonic habit.

```python
# Non-cooperative — works today, breaks in diamond/multiple inheritance
class DeveloperNC(Employee):
    def __init__(self, name, salary, language):
        Employee.__init__(self, name, salary)  # hard-coded parent
        self.language = language

# Cooperative — future-proof
class DeveloperC(Employee):
    def __init__(self, name, salary, language, **kwargs):
        super().__init__(name, salary, **kwargs)
        self.language = language
```

**Why cooperative is preferred:**

- If `Employee` later gains a mixin parent, `super()` will find it; `Employee.__init__(self, ...)` will skip it.
- `super()` follows the MRO; hard-coded `Parent.__init__` does not.
- Cooperative classes compose; non-cooperative classes calcify.

### 5.2 When Non-Cooperative Is Acceptable

- Leaf classes you control and will never use in multiple inheritance.
- When you intentionally want to *skip* part of the chain (rare — document clearly).
- When calling `object.__init__` subtleties arise (see Section 6.3).

## 6. `super()` in `__init__` — Patterns and Pitfalls

### 6.1 Basic `super().__init__` Pattern

```python
class AuditedPayment(Payment):
    def __init__(self, amount: float, **kwargs) -> None:
        self.audit_log: list[str] = []
        super().__init__(amount, **kwargs)
        self.audit_log.append(f"Created payment of {amount}")

# Works with optional currency:
p = AuditedPayment(100, currency="EUR")
print(p.currency)    # EUR
print(p.audit_log)   # ['Created payment of 100']
```

### 6.2 Forwarding With `*args` and `**kwargs`

The cooperative `__init__` idiom:

```python
class Timestamped:
    def __init__(self, *, created_at=None, **kwargs) -> None:
        super().__init__(**kwargs)  # forward remaining kwargs down the chain
        from datetime import datetime
        self.created_at = created_at or datetime.now()

class Named:
    def __init__(self, *, name: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.name = name

class Valued:
    def __init__(self, *, value: float, **kwargs) -> None:
        super().__init__(**kwargs)
        self.value = value
```

Each `__init__` extracts *its own* parameters and forwards the rest. The chain ends at `object.__init__`, which accepts no arguments — so every kwarg must be consumed somewhere, or you get `TypeError: object.__init__() takes exactly one argument`.

**Key rules for cooperative `__init__`:**

1. Use keyword-only arguments (`*,`) to avoid positional collision.
2. Always include `**kwargs` and forward it via `super().__init__(**kwargs)`.
3. Every class in the chain must follow the same protocol — one non-cooperative class breaks the chain.

### 6.3 The `object.__init__` Trap

```python
class A:
    def __init__(self, **kwargs):
        print(f"A got {kwargs}")
        super().__init__(**kwargs)  # eventually calls object.__init__()

class B(A):
    def __init__(self, x, **kwargs):
        print(f"B got x={x}")
        super().__init__(**kwargs)

# If you forget to consume x, it reaches object.__init__:
# B(1, y=2) -> A(y=2) -> object(y=2) -> TypeError!
# Fix: B must not forward x; A must not forward unknown kwargs blindly
```

Solutions:

```python
# Option 1: Each class pops its own args
class BFixed(A):
    def __init__(self, x, **kwargs):
        self.x = x
        super().__init__(**kwargs)  # x not forwarded — safe

# Option 2: Guard the terminal super() call
class AGuarded:
    def __init__(self, **kwargs):
        # Don't call super().__init__ with kwargs if next is object
        if kwargs:
            raise TypeError(f"Unexpected kwargs: {kwargs}")
        super().__init__()
```

In practice, frameworks like Django handle this by ensuring the MRO chain is designed so `object.__init__` is called with no arguments.

### 6.4 Realistic Chain: E-Commerce Order

```python
from datetime import datetime

class Entity:
    """Root entity — assigns ID and timestamp."""
    _next_id = 0

    def __init__(self, **kwargs) -> None:
        super().__init__(**kwargs)
        Entity._next_id += 1
        self.id = Entity._next_id
        self.created_at = datetime.now()

class Priced(Entity):
    def __init__(self, *, amount: float, currency: str = "USD", **kwargs) -> None:
        super().__init__(**kwargs)
        if amount < 0:
            raise ValueError("amount must be >= 0")
        self.amount = amount
        self.currency = currency

class Discountable(Priced):
    def __init__(self, *, discount: float = 0, **kwargs) -> None:
        super().__init__(**kwargs)
        if not 0 <= discount <= 1:
            raise ValueError("discount must be between 0 and 1")
        self.discount = discount

    @property
    def net_amount(self) -> float:
        return self.amount * (1 - self.discount)

class Order(Discountable):
    def __init__(self, *, customer: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.customer = customer

# All kwargs are consumed cooperatively:
order = Order(customer="Acme", amount=1000, discount=0.1, currency="EUR")
print(order.net_amount)   # 900.0
print(order.id)           # 1
print(Order.__mro__)
# (Order, Discountable, Priced, Entity, object)
```

Trace of `Order(customer="Acme", amount=1000, ...)`:

1. `Order.__init__` pops `customer`, forwards `amount, discount, currency`.
2. `Discountable.__init__` pops `discount`, forwards `amount, currency`.
3. `Priced.__init__` pops `amount, currency`, forwards `{}`.
4. `Entity.__init__` pops nothing, calls `object.__init__()` with no args — safe.

## 7. Diamond Preview — Why `super()` Is Not Just "Parent"

Consider the classic diamond:

```
      Base
     /    \
  Left   Right
     \    /
     Diamond
```

```python
class Base:
    def greet(self) -> str:
        return "Base"

class Left(Base):
    def greet(self) -> str:
        return "Left -> " + super().greet()

class Right(Base):
    def greet(self) -> str:
        return "Right -> " + super().greet()

class Diamond(Left, Right):
    def greet(self) -> str:
        return "Diamond -> " + super().greet()

print(Diamond().greet())
# Diamond -> Left -> Right -> Base
print(Diamond.__mro__)
# (Diamond, Left, Right, Base, object)
```

Explanation:

- `Diamond().greet()` calls `Left.greet` (first in MRO after `Diamond`).
- `Left.greet` calls `super().greet()` — which is **not** `Base.greet` but `Right.greet`, because `Right` is next in the MRO after `Left`.
- `Right.greet` then calls `Base.greet`.

If `Left` had used `Base.greet(self)` instead of `super().greet()`, `Right.greet` would be skipped entirely — a bug in cooperative hierarchies. Lesson 12.2 dissects this fully.

## 8. Old-Style vs New-Style Classes — Historical Context

| Era | Syntax | MRO Algorithm | `super()` |
|-----|--------|---------------|-----------|
| Python 2, old-style | `class Foo:` (no `object`) | Depth-first, left-to-right | Not available / broken |
| Python 2, new-style | `class Foo(object):` | C3 linearization | `super(Foo, self)` |
| Python 3 | `class Foo:` (implicit `object`) | C3 linearization | `super()` (zero-arg) |

**Why it matters today:**

- You may encounter `class Foo(object):` in legacy code — it is harmless but redundant in Python 3.
- Old-style MRO had incorrect diamond resolution (it visited `Base` twice). C3 fixed this.
- `super()` in Python 2 required explicit arguments and only worked with new-style classes. The zero-argument form is Python 3 only.
- If you maintain code that must run on both Python 2 and 3 (rare now), use `from builtins import super` or the explicit form.

You do not need to write old-style classes. Know they existed so you understand Stack Overflow answers from 2010.

## 9. Common `super()` Mistakes — A Catalog

### Mistake 1: Forgetting `super().__init__()`

```python
class Child(Base):
    def __init__(self, x):
        self.x = x  # forgot super().__init__() — parent state missing
```

**Symptom:** `AttributeError` later when accessing parent attributes. **Fix:** Always call `super().__init__()` if the parent `__init__` does work.

### Mistake 2: Calling `super().__init__` Without Parentheses

```python
class Child(Base):
    def __init__(self):
        super().__init__   # missing () — no call, silent bug!
```

**Symptom:** No error, but parent `__init__` never executes. Linters catch this; tests should too.

### Mistake 3: Hard-Coding the Parent Class

```python
class Child(Base):
    def greet(self):
        return Base.greet(self) + "!"  # bypasses MRO — breaks cooperative MI
```

**Symptom:** Works in single inheritance, fails when a mixin is inserted. **Fix:** Use `super().greet()`.

### Mistake 4: Passing `self` Explicitly to `super()`

```python
class Child(Base):
    def greet(self):
        return super().greet(self)  # TypeError: greet() takes 1 positional arg but 2 given
```

`super()` already binds `self`. Do not pass it again.

### Mistake 5: Inconsistent `*args`/`**kwargs` Forwarding

```python
class A:
    def __init__(self, x, **kwargs):
        super().__init__(**kwargs)
        self.x = x

class B(A):
    def __init__(self, y):          # forgot **kwargs, forgot super().__init__
        self.y = y
        # TypeError when used cooperatively; silent chain break otherwise
```

**Fix:** Every cooperative `__init__` must accept and forward `**kwargs` (or `*args, **kwargs` if positional args are needed).

### Mistake 6: Using `super()` Outside a Method

```python
# At module level or in a function not defined inside a class:
super().something  # RuntimeError: super(): no arguments
```

**Fix:** Use `super(ExplicitClass, obj)` or restructure.

### Mistake 7: `super()` in `__init__` After Using `self`

```python
class Child(Base):
    def __init__(self):
        self.derived = self.compute()  # uses self before parent init
        super().__init__()             # parent may overwrite or depend on derived
```

Not always wrong, but order matters. Initialize parent *first* unless you have a reason not to — parent may set up invariants that `compute()` relies on.

## 10. When *Not* to Use Inheritance

Inheritance is not always the answer. Prefer composition when:

- The relationship is has-a, not is-a (`Car` has an `Engine`, not is an `Engine`).
- You want to reuse behavior without coupling hierarchies.
- The subclass would need to *remove* parent behavior (violates Liskov Substitution Principle).

```python
# Composition alternative:
class Engine:
    def start(self): print("Engine started")

class Car:
    def __init__(self):
        self.engine = Engine()  # has-a

    def start(self):
        self.engine.start()
```

Lesson 12.3 (Mixins) and 12.4 (Duck Typing) explore lighter-weight reuse mechanisms.

## 11. Summary

| Concept | Key Takeaway |
|---------|--------------|
| Single inheritance | Subclass reuses parent namespace via MRO; every class inherits from `object`. |
| Overriding | Define same-name attribute in subclass; use `super()` to extend. |
| `super()` | MRO-aware proxy, not parent reference. Zero-arg form needs `__class__` closure. |
| Cooperative `__init__` | Each `__init__` pops its own args, forwards `**kwargs` via `super()`. |
| Diamond preview | `super()` follows MRO, so `Left.super()` may call `Right`, not `Base`. |
| Old vs new style | Historical; Python 3 is always new-style with C3 MRO and zero-arg `super()`. |
| Common mistakes | Forgetting `()`, hard-coding parent, double-passing `self`, breaking `**kwargs` chain. |
