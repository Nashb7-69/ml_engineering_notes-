## 1. Why Multiple Inheritance Exists in Python

Most mainstream languages avoid multiple inheritance (MI). Java and C# replace it with interfaces; C++ allows it but warns you. Python embraces it — carefully.

**Why Python can afford MI:**

- No method overloading ambiguity (no compile-time overload resolution).
- A well-defined, predictable MRO (C3 linearization) with no surprises.
- `super()` as an MRO-aware proxy that makes cooperative MI possible.
- Mixins (Lesson 12.3) as the idiomatic, small-scale use case.

**Mental model:** A class with multiple bases is not "two parents" in the folk sense. It is a *single linear order* of ancestors. Every attribute lookup walks that one line. MI is syntactic sugar for declaring a linear precedence.

### 1.1 Minimal Multiple Inheritance

```python
class FileReadable:
    def read(self) -> str:
        return "reading file"

class NetworkReadable:
    def read(self) -> str:
        return "reading network"

class MultiReader(FileReadable, NetworkReadable):
    pass

print(MultiReader().read())       # reading file — FileReadable wins
print(MultiReader.__mro__)
# (<class 'MultiReader'>, <class 'FileReadable'>, <class 'NetworkReadable'>, <class 'object'>)
```

Explanation:

- `MultiReader` inherits from two classes. Its MRO is `[MultiReader, FileReadable, NetworkReadable, object]`.
- `read` is found in `FileReadable` first, so `NetworkReadable.read` is shadowed. No ambiguity, no error — just precedence.

## 2. The Diamond Problem — And Why Naive MRO Fails

### 2.1 The Classic Diamond

```
      Base
     /    \
  Left   Right
     \    /
     Child
```

```python
class Base:
    def greet(self) -> str:
        return "Base"

class Left(Base):
    def greet(self) -> str:
        return "Left"

class Right(Base):
    def greet(self) -> str:
        return "Right"

class Child(Left, Right):
    pass

print(Child().greet())       # Left
print(Child.__mro__)
# (Child, Left, Right, Base, object)
```

So far so good. But *how* should the MRO be computed? Two historical strategies:

| Strategy | Order for Diamond | Problem |
|----------|-------------------|---------|
| **Depth-first, left-to-right** (Python 2 old-style) | `Child → Left → Base → Right → Base` | Visits `Base` twice; `Right` comes *after* `Base`, so `Right.greet` is never reached even though `Right` is a direct parent of `Child`. |
| **C3 linearization** (Python 3) | `Child → Left → Right → Base` | Each class appears once; respects local precedence (Left before Right) *and* monotonicity (a class never appears before its parents). |

### 2.2 Why Depth-First Is Wrong

Imagine `Base` defines `save()`, `Right` overrides it with transaction logic, `Left` does not override `save`. With depth-first MRO, `Child.save()` would find `Base.save` before `Right.save` — skipping the transaction logic that `Right` intentionally provides. C3 ensures `Right` is checked before `Base`.

### 2.3 A More Realistic Diamond

```python
class Payment:
    def fee(self) -> float:
        return 1.0

    def process(self) -> str:
        return f"Processing with fee {self.fee():.2f}"

class CardMixin(Payment):
    def fee(self) -> float:
        return super().fee() + 0.30

class PromoMixin(Payment):
    def fee(self) -> float:
        # 50% discount on fee
        return super().fee() * 0.5

class PromoCardPayment(CardMixin, PromoMixin):
    pass

# MRO: PromoCardPayment -> CardMixin -> PromoMixin -> Payment -> object
print(PromoCardPayment.__mro__)
p = PromoCardPayment()
print(p.fee())      # ((1.0 * 0.5) + 0.30) ??? Let's trace
# Actually: CardMixin.fee -> super().fee() -> PromoMixin.fee -> super().fee() -> Payment.fee
# = (1.0 * 0.5) + 0.30 = 0.80  — wait, order matters. Let's compute precisely.
```

Trace `PromoCardPayment().fee()`:

1. `CardMixin.fee` is found first. It calls `super().fee()` → next in MRO is `PromoMixin.fee`.
2. `PromoMixin.fee` calls `super().fee()` → next is `Payment.fee` which returns `1.0`.
3. `PromoMixin` returns `1.0 * 0.5 = 0.5`.
4. `CardMixin` returns `0.5 + 0.30 = 0.80`.

If we flip the base order to `PromoMixin, CardMixin`, the fee becomes `(1.0 + 0.30) * 0.5 = 0.65`. **Base order matters.** C3 respects the order you write.

## 3. C3 Linearization — How Python Computes the MRO

### 3.1 The Algorithm (Conceptual)

C3 linearization for a class `C(B1, B2, ..., BN)` is:

```
L(C) = [C] + merge(L(B1), L(B2), ..., L(BN), [B1, B2, ..., BN])
```

Where `merge` repeatedly:

1. Takes the first head that does not appear in the tail of any other list.
2. Appends it to the result and removes it from all lists.
3. If no such head exists, the hierarchy is *inconsistent* → `TypeError`.

Three properties C3 guarantees:

- **Local precedence:** If `class C(A, B)`, then `A` appears before `B` in `C`'s MRO.
- **Monotonicity:** If `A` appears before `B` in a parent's MRO, it stays before `B` in the child's MRO.
- **No duplication:** Each class appears exactly once.

### 3.2 Worked Example — Step by Step

```python
class O: pass
class A(O): pass
class B(O): pass
class C(O): pass
class D(A, B): pass
class E(B, C): pass
class F(D, E): pass

# Compute L(F) where F(D, E)
# L(D) = [D, A, B, O]
# L(E) = [E, B, C, O]
# merge([D,A,B,O], [E,B,C,O], [D,E])
```

Merge steps:

| Step | Lists | Chosen Head | Result |
|------|-------|-------------|--------|
| 1 | `[D,A,B,O]`, `[E,B,C,O]`, `[D,E]` | `D` (not in any tail) | `[F, D]` |
| 2 | `[A,B,O]`, `[E,B,C,O]`, `[E]` | `A` (not in any tail) | `[F, D, A]` |
| 3 | `[B,O]`, `[E,B,C,O]`, `[E]` | `E` (B is in tail of `[E,B,C,O]`, so skip B) | `[F, D, A, E]` |
| 4 | `[B,O]`, `[B,C,O]` | `B` | `[F, D, A, E, B]` |
| 5 | `[O]`, `[C,O]` | `C` | `[F, D, A, E, B, C]` |
| 6 | `[O]`, `[O]` | `O` | `[F, D, A, E, B, C, O]` |

```python
print(F.__mro__)
# (F, D, A, E, B, C, O, object)
```

Notice `B` appears *after* `E` even though `D` lists `B` — because `E` must come before `B` (E's local precedence), and monotonicity wins.

### 3.3 Another Example — The "Bad" Diamond That C3 Rejects

```python
class A: pass
class B(A): pass
class C(A, B): pass  # TypeError: Cannot create a consistent MRO
```

Why inconsistent? `C` says `A` before `B`, but `B` already says `B` before `A` (since `B(A)` → MRO is `B, A`). No linear order satisfies both constraints.

C3 detects this at class *definition* time:

```python
try:
    class Inconsistent(A, B):
        pass
except TypeError as e:
    print(e)  # Cannot create a consistent method resolution order (MRO) for bases A, B
```

**Rule:** If `class C(X, Y)` and `X` is a subclass of `Y`, listing `X` before `Y` is fine. Listing `Y` before `X` is inconsistent when `X` inherits from `Y` transitively. The fix is to reorder bases.

### 3.4 MRO Is Computed Once at Class Creation

```python
class Base: pass
class Child(Base): pass

print(Child.__mro__)  # computed at def time, cached
# Monkey-patching __bases__ recomputes it:
Child.__bases__ = (Base,)
# But mutating parent classes does NOT automatically reorder — you must reassign __bases__
```

## 4. Inspecting the MRO

### 4.1 Four Ways to See the MRO

```python
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass

# 1. __mro__ — tuple, read-only, on the class
print(D.__mro__)
# (D, B, C, A, object)

# 2. __mro__ via instance
print(D().__class__.__mro__)  # same

# 3. mro() — returns list, can be called on class or via type
print(D.mro())
# [D, B, C, A, object]
print(type.mro(D))
# [D, B, C, A, object]

# 4. help() / inspect.getmro()
import inspect
print(inspect.getmro(D))
# (D, B, C, A, object)
```

Differences:

| Accessor | Returns | Notes |
|----------|---------|-------|
| `Cls.__mro__` | `tuple` | Attribute on class, also visible via instance `__class__`. Read-only. |
| `Cls.mro()` | `list` | Method — can be overridden to customize MRO (advanced, rare). |
| `type.mro(Cls)` | `list` | Same as `Cls.mro()` but works even if `Cls` overrides `mro()`. |
| `inspect.getmro(Cls)` | `tuple` | Wrapper around `Cls.__mro__`. |

### 4.2 Overriding `mro()` — Rare but Possible

```python
class OrderedMeta(type):
    def mro(cls):
        # Custom MRO: reverse the normal order (don't do this in production!)
        return super().mro()[::-1]

class Weird(metaclass=OrderedMeta):
    pass
```

You will almost never override `mro()`. It exists for exotic metaclass use cases (e.g., `collections` ABCs). Mentioned here so you recognize it if you see it.

### 4.3 `__mro_entries__` — Implicit MRO Expansion (Python 3.7+)

When you write `class C(X):` and `X` is not a type, Python calls `X.__mro_entries__(bases)` to allow `X` to expand into multiple bases. Used by `typing` generics:

```python
from typing import Generic, TypeVar
T = TypeVar("T")

class MyGeneric(Generic[T]):
    pass

print(MyGeneric.__mro__)
# Generic specialization expands via __mro_entries__
```

You do not need to implement `__mro_entries__` yourself unless you build generic-like libraries.

## 5. Cooperative Multiple Inheritance With `super()` Chaining

### 5.1 Why `super()` Is Essential in MI

In single inheritance, `super()` vs `Parent.method(self)` is a style choice. In MI, it is a *correctness* requirement. Only `super()` follows the MRO chain; hard-coded parent calls skip siblings.

```python
class Base:
    def save(self) -> None:
        print("Base.save")

class AuditMixin:
    def save(self) -> None:
        print("AuditMixin.save — logging")
        super().save()

class ValidationMixin:
    def save(self) -> None:
        print("ValidationMixin.save — validating")
        super().save()

# Cooperative — each save() calls super().save(), chain is unbroken
class Document(AuditMixin, ValidationMixin, Base):
    def save(self) -> None:
        print("Document.save")
        super().save()

Document().save()
# Document.save
# AuditMixin.save — logging
# ValidationMixin.save — validating
# Base.save
print(Document.__mro__)
# (Document, AuditMixin, ValidationMixin, Base, object)
```

Trace:

1. `Document.save` → `super()` finds `AuditMixin.save`.
2. `AuditMixin.save` → `super()` finds `ValidationMixin.save` (not `Base`!).
3. `ValidationMixin.save` → `super()` finds `Base.save`.
4. `Base.save` → `super()` finds `object` (no `save`, chain ends).

If `AuditMixin` had called `Base.save(self)` instead, `ValidationMixin.save` would be skipped entirely.

### 5.2 The Non-Cooperative Counterexample

```python
class AuditMixinBad:
    def save(self) -> None:
        print("AuditMixinBad.save — logging")
        Base.save(self)  # hard-coded — skips ValidationMixin!

class ValidationMixinBad:
    def save(self) -> None:
        print("ValidationMixinBad.save — validating")
        Base.save(self)

class DocumentBad(AuditMixinBad, ValidationMixinBad, Base):
    def save(self) -> None:
        print("DocumentBad.save")
        AuditMixinBad.save(self)  # only Audit path runs

DocumentBad().save()
# DocumentBad.save
# AuditMixinBad.save — logging
# Base.save              — ValidationMixinBad.save never called!
```

**Lesson:** In any class designed for MI, every overriding method that has a parent implementation *must* call `super()`, not a named parent.

### 5.3 When to *Not* Call `super()` in MI

If you intentionally want to *stop* the chain (e.g., `Base` is the terminator), simply do not call `super()` there:

```python
class Base:
    def save(self) -> None:
        print("Base.save — terminator, no super() call")

class Mixin:
    def save(self) -> None:
        print("Mixin.save")
        super().save()  # will find Base.save, then stop
```

The chain naturally ends when a method does not call `super()` or when `object` has no such method.

### 5.4 Realistic Example: Request Handler Pipeline

```python
from typing import Any

class Request:
    def __init__(self, path: str, user: str | None = None) -> None:
        self.path = path
        self.user = user

class BaseHandler:
    def handle(self, request: Request) -> str:
        return f"200 OK: {request.path}"

class AuthMixin:
    def handle(self, request: Request) -> str:
        if request.user is None:
            return "401 Unauthorized"
        print(f"[Auth] user={request.user} authenticated")
        return super().handle(request)  # type: ignore[misc]

class CacheMixin:
    _cache: dict[str, str] = {}

    def handle(self, request: Request) -> str:
        if request.path in self._cache:
            print(f"[Cache] hit for {request.path}")
            return self._cache[request.path]
        print(f"[Cache] miss for {request.path}")
        response = super().handle(request)  # type: ignore[misc]
        self._cache[request.path] = response
        return response

class LoggingMixin:
    def handle(self, request: Request) -> str:
        print(f"[Log] {request.path} requested")
        response = super().handle(request)  # type: ignore[misc]
        print(f"[Log] response: {response}")
        return response

class AppHandler(LoggingMixin, CacheMixin, AuthMixin, BaseHandler):
    pass

print(AppHandler.__mro__)
# (AppHandler, LoggingMixin, CacheMixin, AuthMixin, BaseHandler, object)

handler = AppHandler()
print(handler.handle(Request("/api/data", user="alice")))
# [Log] /api/data requested
# [Cache] miss for /api/data
# [Auth] user=alice authenticated
# [Log] response: 200 OK: /api/data

print(handler.handle(Request("/api/data", user="alice")))
# [Log] /api/data requested
# [Cache] hit for /api/data
# [Log] response: 200 OK: /api/data  — Auth not even checked on cache hit!

print(handler.handle(Request("/secret")))
# [Log] /secret requested
# [Cache] miss for /secret
# 401 Unauthorized — BaseHandler never reached
```

Explanation:

- Mixin order defines pipeline order. `LoggingMixin` first → logs every request. `CacheMixin` second → short-circuits on hit. `AuthMixin` third → only runs on cache miss.
- Reordering bases changes semantics: `AppHandler(AuthMixin, CacheMixin, ...)` would authenticate even on cache hits.
- Each mixin calls `super().handle(request)` to delegate — the MRO does the rest.

## 6. Cooperative `__init__` in Multiple Inheritance

### 6.1 The `**kwargs` Forwarding Protocol

Every `__init__` in a cooperative hierarchy must:

1. Accept `*args`/`**kwargs` (or at least `**kwargs` with keyword-only args).
2. Extract its own parameters.
3. Forward the remainder via `super().__init__(**kwargs)`.

```python
class Timestamped:
    def __init__(self, *, created_at=None, **kwargs) -> None:
        super().__init__(**kwargs)
        from datetime import datetime
        self.created_at = created_at or datetime.now()

class Named:
    def __init__(self, *, name: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.name = name

class Priced:
    def __init__(self, *, price: float, **kwargs) -> None:
        super().__init__(**kwargs)
        if price < 0:
            raise ValueError("price must be >= 0")
        self.price = price

class Product(Timestamped, Named, Priced):
    def __init__(self, *, sku: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.sku = sku

# MRO: Product -> Timestamped -> Named -> Priced -> object
print(Product.__mro__)

p = Product(name="Widget", price=9.99, sku="W-001")
print(p.name, p.price, p.sku, p.created_at)
```

Trace of `Product(name="Widget", price=9.99, sku="W-001")`:

| Call | Extracts | Forwards |
|------|----------|----------|
| `Product.__init__(sku="W-001", name="Widget", price=9.99)` | `sku` | `name, price` |
| `Timestamped.__init__(name="Widget", price=9.99)` | `created_at` (default) | `name, price` |
| `Named.__init__(name="Widget", price=9.99)` | `name` | `price` |
| `Priced.__init__(price=9.99)` | `price` | `{}` |
| `object.__init__()` | — | — (no args, safe) |

### 6.2 What Happens When One Class Breaks the Protocol

```python
class BrokenMixin:
    def __init__(self, name):  # no **kwargs, no super() call
        self.name = name

class AlsoNeedsInit:
    def __init__(self, *, value, **kwargs):
        super().__init__(**kwargs)
        self.value = value

class BadProduct(BrokenMixin, AlsoNeedsInit):
    pass

# BadProduct(name="x", value=1) — BrokenMixin.__init__ is called first,
# it takes 'name' positionally, never calls super(), so AlsoNeedsInit.__init__ is skipped.
# AlsoNeedsInit.__init__ would never run — value is never set.
```

**Symptoms of a broken chain:**

- Missing attributes (`AttributeError` later).
- `TypeError: object.__init__() takes exactly one argument` — an unconsumed kwarg reached `object`.
- Silent data loss — an `__init__` ran but downstream `__init__` did not.

**Diagnosis:** Print `Class.__mro__` and verify every `__init__` in the chain calls `super().__init__(**kwargs)`.

### 6.3 The `object.__init__` Trap Revisited

```python
class A:
    def __init__(self, **kwargs):
        print(f"A.__init__ kwargs={kwargs}")
        super().__init__(**kwargs)  # forwards to object — BOOM if kwargs non-empty

class B:
    def __init__(self, *, x, **kwargs):
        print(f"B.__init__ x={x}")
        super().__init__(**kwargs)

class C(A, B):
    pass

# C(x=1) -> A.__init__(x=1) -> B.__init__(x=1) -> object.__init__() — but A forwarded x!
# Fix: A must NOT forward kwargs it didn't consume, or must ensure chain ends cleanly.

# Correct: A consumes or discards, then calls super().__init__() with no args if next is object
class AFixed:
    def __init__(self, **kwargs):
        # AFixed has no own params — just forward
        super().__init__(**kwargs)

class BFixed:
    def __init__(self, *, x, **kwargs):
        super().__init__(**kwargs)
        self.x = x

class CFixed(AFixed, BFixed):
    pass

print(CFixed(x=1).x)  # 1 — works, empty dict reaches object
```

**Rules:**

- Use keyword-only arguments so each `__init__` knows exactly which kwargs are its own.
- Never forward a kwarg you were supposed to consume.
- The last `super().__init__()` in the chain must be called with no remaining kwargs.

## 7. Pitfalls When Not Calling `super()`

### 7.1 Skipped Initializers

Already covered — the most common MI bug. Every `__init__` that does not call `super().__init__()` silently prevents downstream initializers from running.

### 7.2 Skipped Method Logic

```python
class SaveBase:
    def save(self): print("SaveBase")

class AuditMixin:
    def save(self):
        print("Audit")
        # forgot super().save() — ValidationMixin.save never runs
        # super().save()

class ValidationMixin:
    def save(self):
        print("Validate")
        super().save()

class Doc(AuditMixin, ValidationMixin, SaveBase): pass

Doc().save()  # Only Audit — Validate and SaveBase skipped
```

### 7.3 Double Execution With Hard-Coded Calls

```python
class Base:
    def __init__(self):
        print("Base.__init__")

class Left(Base):
    def __init__(self):
        print("Left.__init__")
        Base.__init__(self)
        super().__init__()  # also calls Base.__init__ via MRO — Base runs twice!

class Right(Base):
    def __init__(self):
        print("Right.__init__")
        super().__init__()

class Diamond(Left, Right):
    def __init__(self):
        super().__init__()

Diamond()
# Left.__init__
# Base.__init__   — via Base.__init__(self)
# Right.__init__
# Base.__init__   — via super() chain — duplicate!
```

**Fix:** Use *either* `super()` *or* hard-coded calls, never both, and prefer `super()`.

### 7.4 `super()` With No Common Ancestor Method

```python
class MixinA:
    def process(self): return super().process()  # hopes someone else has process()

class MixinB: pass  # no process()

class Combined(MixinA, MixinB): pass

Combined().process()  # AttributeError: 'super' object has no attribute 'process'
# Because MRO is Combined -> MixinA -> MixinB -> object, and none after MixinA has process()
```

**Fix:** Either ensure a base class provides the method, or guard:

```python
class MixinASafe:
    def process(self):
        try:
            return super().process()
        except AttributeError:
            return "default"
```

## 8. MRO Inconsistency Errors — Diagnosis and Repair

### 8.1 Reproducing the Error

```python
class X: pass
class Y(X): pass

# Inconsistent: says X before Y, but Y already implies Y before X
try:
    class Z(X, Y): pass
except TypeError as e:
    print(e)
    # Cannot create a consistent method resolution order (MRO) for bases X, Y
```

### 8.2 More Subtle Inconsistency

```python
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass  # OK: B before C, both before A — consistent
class E(C, B): pass  # OK: C before B — also consistent (different order, still valid)

# But:
class F(D, E): pass  # TypeError! D says B before C, E says C before B — irreconcilable
```

```python
try:
    class F(D, E): pass
except TypeError as e:
    print(e)
```

### 8.3 Repair Strategies

| Problem | Fix |
|---------|-----|
| `class Z(X, Y)` where `Y(X)` | Swap to `class Z(Y, X)` — put more specific first |
| `class F(D, E)` with conflicting orders | Reorder `F`'s bases or refactor `D`/`E` to share a consistent order |
| Library classes with incompatible MROs | Use composition instead of MI, or create an adapter |

**General rule:** List bases from *most specific* to *most general*, and ensure that if `B` inherits from `A`, `B` appears before `A` in any MRO that includes both.

## 9. Method Resolution in Practice — Attribute Lookup Walkthrough

```python
class A:
    x = "A.x"
    def method(self): return "A.method"

class B(A):
    x = "B.x"

class C(A):
    def method(self): return "C.method"

class D(B, C):
    pass

d = D()
print(d.x)        # B.x — found in B, before C and A
print(d.method()) # C.method — B has no method, so C wins over A
print(D.__mro__)  # (D, B, C, A, object)
```

Step-by-step for `d.method()`:

1. `D.__dict__` — no `method`.
2. `B.__dict__` — no `method`.
3. `C.__dict__` — found `method` → return `C.method` bound to `d`.
4. (`A.__dict__` would be next if `C` had no `method`.)

For `d.x`:

1. `D.__dict__` — no `x`.
2. `B.__dict__` — found `x = "B.x"` → return it. Stop.

**Key insight:** MRO is a *single* linear search. It does not "search all parents of B before parents of C" — it interleaves according to C3.

## 10. When to Use Multiple Inheritance — And When Not To

### 10.1 Good Use Cases

| Use Case | Example | Why MI Fits |
|----------|---------|-------------|
| Mixins | `class View(LoginRequiredMixin, CacheMixin, View)` | Small, orthogonal behaviors composed linearly |
| Abstract base combos | `class MyDict(MutableMapping, Serializable)` | Combining interfaces |
| Framework extension | Django class-based views, `collections.abc` | Framework designed for cooperative MI |

### 10.2 Bad Use Cases

| Anti-Pattern | Problem | Better Alternative |
|--------------|---------|--------------------|
| Deep diamond hierarchies | MRO hard to predict, fragile | Composition or Strategy pattern |
| MI for code reuse without `super()` | Chain breaks, silent bugs | Composition, delegates |
| Two unrelated "is-a" parents with overlapping methods | Ambiguity, order-dependent bugs | Composition or Protocol/ABC |
| MI with stateful parents that both set `self.x` | Attribute collision | Composition or explicit initialization |

### 10.3 Alternatives to MI

```python
# Instead of MI for reuse:
class Engine: ...
class Wheels: ...

# Composition — explicit, no MRO surprises
class Car:
    def __init__(self):
        self.engine = Engine()
        self.wheels = Wheels()

# MI — implicit, MRO-dependent
class CarMI(Engine, Wheels): pass  # fragile if Engine and Wheels overlap
```

**Heuristic:** If you cannot explain the MRO of your class in one sentence, use composition.

---

## 11. Summary

| Concept | Key Takeaway |
|---------|--------------|
| MRO | Single linear order computed by C3; every attribute lookup walks it. |
| C3 | `L(C) = [C] + merge(L(B1)..L(BN), [B1..BN])`; guarantees local precedence + monotonicity. |
| Diamond | C3 visits each class once, respecting base order — depth-first would be wrong. |
| `__mro__` / `mro()` | `__mro__` is tuple (read-only), `mro()` is list (overridable). |
| Cooperative MI | Every method calls `super()`; every `__init__` forwards `**kwargs`. |
| `object.__init__` trap | Last `super().__init__()` must receive empty kwargs. |
| Inconsistency error | `TypeError: Cannot create a consistent MRO` — reorder bases from specific to general. |
| When to use MI | Mixins and interface combos — yes. Deep stateful diamonds — no. |
