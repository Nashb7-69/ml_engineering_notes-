# 9.2 Functional Tools — Map, Filter, Reduce and the functools Arsenal

> Python is not a functional language. It borrows functional *tools* — `map`, `filter`, `lambda`, `functools` — but idiomatic Python often prefers comprehensions and loops. Understanding *both* styles, and when each wins, is what makes you Pythonic.

## Learning Goals

- Understand `lambda`: what it is, what it is not, and why it is limited to an expression.
- Master `map`, `filter`, and `functools.reduce`: laziness, multi-iterable behavior, and their comprehension equivalents.
- Use the `operator` module to replace trivial lambdas with faster, picklable, readable callables.
- Master `functools`: `partial`, `partialmethod`, `wraps`, `lru_cache`/`cache`, `cached_property`, `total_ordering`/`singledispatch` (brief), and why you need them.
- Internalize when comprehensions are preferred, when functional style is Pythonic, and how to choose without dogma.
- Avoid classic pitfalls: late-binding closures in lambdas, `map` with exhausted iterators, `lru_cache` with mutable/unhashable args, `partial` with mutable defaults.

---

## 1. Why Functional Tools Exist in Python (and Why They Are Controversial)

Python's creator, Guido van Rossum, once tried to remove `map`/`filter`/`reduce`/`lambda` entirely. His argument: list/dict/set comprehensions and generator expressions do the same jobs *more readably* for most Python code. He succeeded in making `reduce` non-builtin (it moved to `functools` in Python 3).

Yet functional tools remain because:

- They express *pipelines as data*: you can pass `map(func, data)` around without writing a loop body.
- They are *lazy* (in Python 3): `map` and `filter` return iterators, not lists — memory efficient for large streams.
- They compose well with `itertools`, `concurrent.futures`, and `operator`.
- `functools` fills gaps that comprehensions cannot: memoization, partial application, decorator hygiene.

**Takeaway:** You are not writing Haskell in Python. You are using functional *idioms* where they clarify and imperative/comprehension idioms where *they* clarify. This chapter teaches the decision rule.

## 2. `lambda` — Anonymous Functions, Precisely

A `lambda` is just a function — anonymous, restricted to a single expression, with no statements.

### 2.1 Syntax and Equivalence

```python
# These two are semantically identical:
def square(x):
    return x * x

square_lambda = lambda x: x * x

print(square(5))         # 25
print(square_lambda(5))  # 25
print(square_lambda.__name__)  # '<lambda>' — not 'square_lambda'!
import inspect
print(inspect.signature(square_lambda))  # (x)

# Multi-arg lambda
add = lambda a, b: a + b
print(add(2, 3))  # 5

# With defaults, *args, **kwargs — lambdas support the full parameter grammar
f = lambda a, b=10, *args, kw=None, **kwargs: (a, b, args, kw, kwargs)
print(f(1))                # (1, 10, (), None, {})
print(f(1, 2, 3, 4, kw="x", extra=99))  # (1, 2, (3, 4), 'x', {'extra': 99})

# Lambda is an *expression* — you can use it where `def` cannot:
pairs = [(1, "b"), (2, "a")]
pairs.sort(key=lambda p: p[1])  # inline key function
print(pairs)  # [(2, 'a'), (1, 'b')]
```

*Explanation:* `lambda params: expr` creates a function object whose body is `return expr`. There are no statements, no `if` blocks, no assignments — only an expression. Use `lambda` when the function is trivial and used once as an argument. If it needs a name, statements, or reuse, use `def`.

### 2.2 What Lambda Cannot Do (and Why PEP 8 Discourages Assignment)

```python
# Bad style (PEP 8: E731) — don't bind a lambda to a name; use def
# This assigns a lambda to 'bad' — loses the function's real name and docstring
bad = lambda x: x + 1  # linter will complain: do not assign lambda, use a def

# Good style
def good(x):
    """Increment x."""
    return x + 1

print(good.__name__, good.__doc__)   # good, Increment x.
print(bad.__name__, bad.__doc__)     # <lambda>, None

# What you cannot do with lambda: statements
# lambda x: if x > 0: return x else: return -x   # SyntaxError — `if` is a statement
# Instead, use a conditional expression:
abs_lambda = lambda x: x if x >= 0 else -x

# No assignments, no loops, no try/except inside lambda
# lambda x: (y := x+1)  # Walrus operator *does* work (it's an expression), but please don't
```

### 2.3 The Classic Pitfall: Late-Binding Closures

This is the #1 functional bug in Python — and it affects `lambda`, `def` inside loops, `map`, `filter`, `partial`, and comprehensions differently.

```python
# Simple → trap
funcs = []
for i in range(3):
    funcs.append(lambda: i)

print([f() for f in funcs])  # [2, 2, 2] — not [0, 1, 2]!

# Why? lambda captures the *variable* `i`, not its value at creation time.
# All three lambdas close over the same cell; when called, i is 2 (the final value).

# Fix 1: Default argument binds the current value eagerly
funcs_fixed = []
for i in range(3):
    funcs_fixed.append(lambda i=i: i)

print([f() for f in funcs_fixed])  # [0, 1, 2]

# Fix 2: Use functools.partial (see §6)
import functools
funcs_partial = [functools.partial(lambda x: x, i) for i in range(3)]
# But note: partial binds args eagerly too — here we bind i at creation
print([f() for f in funcs_partial])  # [0, 1, 2]

# Fix 3: Define a helper factory (most explicit)
def make_printer(n):
    return lambda: n

funcs_factory = [make_printer(i) for i in range(3)]
print([f() for f in funcs_factory])  # [0, 1, 2]

# Same pitfall with map/filter if you build lambdas in a loop
thresholds = [10, 20, 30]
# Bad: all lambdas share the same `t`
predicates = [lambda x: x > t for t in thresholds]
print([pred(25) for pred in predicates])  # [False, False, False]? Actually t==30 for all → [False, False, False]
# Good:
predicates = [lambda x, t=t: x > t for t in thresholds]
print([pred(25) for pred in predicates])  # [True, True, False]
```

*Rule:* Any time you create a function inside a loop that references the loop variable, use `default-argument binding` or `functools.partial` or a factory function to capture the *value*.

### 2.4 When Lambda Is Appropriate vs When to Use `def` or `operator`

| Situation | Prefer |
|---|---|
| Key function for `sort`/`sorted`/`min`/`max` that is a simple projection | `lambda` or `operator.itemgetter`/`attrgetter` |
| Predicate for `filter` that is a one-liner | `lambda` (or often a comprehension instead) |
| Multi-line logic, reuse, docstring, type hints | `def` |
| Accessing an attribute or item (`x.attr`, `x["key"]`) | `operator.attrgetter`/`itemgetter` (faster, picklable) |
| Arithmetic (`a + b`, `a * b`) | `operator.add`/`mul` |

```python
# Realistic: sorting by multiple criteria
from operator import itemgetter, attrgetter

users = [
    {"name": "Ada", "age": 30},
    {"name": "Bob", "age": 25},
    {"name": "Ada", "age": 22},
]
# Lambda version
print(sorted(users, key=lambda u: (u["name"], u["age"])))
# Operator version — often faster and more declarative for simple item/attr access
# itemgetter can fetch multiple keys at once, returning a tuple
print(sorted(users, key=itemgetter("name", "age")))

# But lambda can do computations operator cannot:
print(sorted(users, key=lambda u: u["age"] * 2))  # operator has no "multiply age by 2"
```

## 3. `map` — Lazy Transformation

`map(function, iterable, ...)` applies `function` to each element(s) and returns a *lazy iterator*.

### 3.1 Basic Behavior

```python
# Simple: single iterable
nums = [1, 2, 3]
squared = map(lambda x: x * x, nums)
print(squared)          # <map object at 0x...>
print(list(squared))    # [1, 4, 9]

# Squared is exhausted after one pass — it's an iterator, not a list!
print(list(squared))    # [] — already consumed

# Must re-create if you need it again
print(list(map(lambda x: x * x, nums)))  # [1, 4, 9]

# Comprehension equivalent — what most Python code uses instead:
print([x * x for x in nums])  # [1, 4, 9] — eager list; use (x*x for x in nums) for lazy

# Map with a named function — more readable for non-trivial logic
def celsius_to_fahrenheit(c: float) -> float:
    return c * 9 / 5 + 32

temps_c = [0, 20, 37, 100]
print(list(map(celsius_to_fahrenheit, temps_c)))  # [32.0, 68.0, 98.6, 212.0]
print([celsius_to_fahrenheit(c) for c in temps_c])  # identical, and usually preferred
```

### 3.2 Multiple Iterables — `map` Zips, Then Maps

```python
# Advanced: map with N iterables — stops at the shortest
a = [1, 2, 3]
b = [10, 20, 30]
c = [100, 200]

print(list(map(lambda x, y: x + y, a, b)))        # [11, 22, 33]
print(list(map(lambda x, y, z: x + y + z, a, b, c)))  # [111, 222] — stops when c exhausted

# Equivalent comprehension with zip (more explicit):
print([x + y for x, y in zip(a, b)])  # [11, 22, 33]
# For strict length checking, Python 3.10+ has strict zip:
try:
    print([x + y + z for x, y, z in zip(a, b, c, strict=True)])
except ValueError as exc:
    print(f"zip strict error: {exc}")  # zip() argument 2 is shorter

# Realistic: element-wise addition with operator.add
import operator
print(list(map(operator.add, a, b)))  # [11, 22, 33] — cleaner than lambda
```

### 3.3 Laziness and Memory (Why Python 3 Made `map` Lazy)

In Python 2, `map` returned a `list` — eagerly allocating all results. In Python 3, `map` is lazy: it computes one element at a time.

```python
# Memory demo: map doesn't allocate until consumed
import sys

large = range(10_000_00)  # range is also lazy
mapped = map(lambda x: x * 2, large)
print(sys.getsizeof(mapped))  # ~48 bytes — just the iterator object

# vs list comprehension — allocates a million ints:
# eager = [x * 2 for x in large]  # ~8 MB

# Consuming lazily with a loop — constant memory
total = 0
for value in map(lambda x: x * 2, range(10)):  # lazy pipeline
    total += value
print(total)

# Pitfall: if the mapped function has side effects, laziness defers them!
def noisy(x):
    print(f"processing {x}")
    return x * 2

m = map(noisy, [1, 2, 3])
print("map created — no output yet")
print(next(m))  # now prints "processing 1" and returns 2
# The other elements aren't processed until consumed
print(list(m))  # processes 2, 3

# Pitfall: map with an exhausted iterator yields nothing — silently
it = iter([1, 2, 3])
print(list(map(lambda x: x * 10, it)))  # [10, 20, 30]
print(list(map(lambda x: x * 10, it)))  # [] — iterator already exhausted, no error!
```

### 3.4 `map` Edge Cases

```python
# map with None as function — was legal in Python 2, REMOVED in Python 3
try:
    print(list(map(None, [1, 2, 3])))
except TypeError as exc:
    print(f"map(None, ...) error: {exc}")  # 'NoneType' object is not callable

# map with an empty iterable
print(list(map(lambda x: x * 2, [])))  # []

# map doesn't handle exceptions specially — they propagate
def risky(x):
    if x == 2:
        raise ValueError("bad value 2")
    return x * 10

try:
    print(list(map(risky, [1, 2, 3])))
except ValueError as exc:
    print(f"mapped function raised: {exc}")
```

## 4. `filter` — Lazy Selection

`filter(function, iterable)` yields elements where `function(element)` is truthy. In Python 3, lazy (iterator). If `function is None`, it filters by truthiness of the element itself.

### 4.1 Basics

```python
nums = range(10)
evens = filter(lambda x: x % 2 == 0, nums)
print(list(evens))  # [0, 2, 4, 6, 8]

# Comprehension equivalent — strongly preferred in Python:
print([x for x in nums if x % 2 == 0])  # [0, 2, 4, 6, 8]
# Generator equivalent — lazy like filter:
print(list(x for x in nums if x % 2 == 0))

# filter with None — removes falsy values
mixed = [0, 1, "", "hello", None, [], [1], False, True]
print(list(filter(None, mixed)))  # [1, 'hello', [1], True]
# Equivalent comprehension:
print([x for x in mixed if x])  # same

# With operator for reuse
import operator
# No direct operator for "is even", but you can use a helper:
def is_even(n: int) -> bool:
    return n % 2 == 0

print(list(filter(is_even, nums)))
```

### 4.2 `filter` vs `map` vs Comprehension: Readability

```python
# All three produce evens-squared, but which reads best?

# Functional:
print(list(map(lambda x: x * x, filter(lambda x: x % 2 == 0, range(10)))))

# Comprehension (Pythonic):
print([x * x for x in range(10) if x % 2 == 0])

# Generator + map/filter hybrid — sometimes seen in pipelines:
from itertools import islice
result = map(lambda x: x * x, filter(lambda x: x % 2 == 0, range(100)))
print(list(islice(result, 5)))  # [0, 4, 16, 36, 64] — lazy + sliced

# Realistic benchmark: comprehensions are often *faster* for simple ops
# because they avoid a Python function call per element.
# map/filter win when the function is already a builtin/C function (e.g., str.strip, operator.add)
```

### 4.3 Realistic Example: Cleaning Data

```python
# Cleaning a CSV-like stream: strip whitespace, drop empties, parse ints
raw = [" 1 ", "  ", "2", " 3 ", "", "  4 "]

# Functional pipeline — each step lazy
stripped = map(str.strip, raw)          # lazy strip
non_empty = filter(None, stripped)      # lazy drop empties (filter(None,...))
parsed = map(int, non_empty)            # lazy parse
print(list(parsed))  # [1, 2, 3, 4]

# Comprehension equivalent — arguably clearer:
print([int(s.strip()) for s in raw if s.strip()])  # but calls strip() twice!
# Better comprehension avoiding double work:
print([int(stripped_s) for s in raw if (stripped_s := s.strip())])
# Or with a generator pipeline — hybrid style:
print([int(x) for x in (s.strip() for s in raw) if x])

# When the pipeline is long, functional composition or a generator function is cleanest:
def clean_ints(lines):
    for line in lines:
        stripped = line.strip()
        if stripped:
            yield int(stripped)

print(list(clean_ints(raw)))  # [1, 2, 3, 4]
```

*Lesson:* For one-off transformations, prefer the construct that minimizes function calls and double work. For reusable multi-step pipelines, `map`/`filter`/generator functions are all valid; pick the one your team finds readable.

## 5. `functools.reduce` — Cumulative Folding

`functools.reduce(function, iterable[, initializer])` repeatedly applies `function(accumulator, next_element)` to collapse an iterable to a single value. It was demoted from builtin to `functools` because explicit loops are clearer for most folds.

### 5.1 How `reduce` Works

```python
import functools
import operator

nums = [1, 2, 3, 4, 5]

# Sum via reduce
print(functools.reduce(operator.add, nums))        # 15 — (((1+2)+3)+4)+5
print(functools.reduce(lambda acc, x: acc + x, nums))  # same, but use operator.add

# Product
print(functools.reduce(operator.mul, nums))        # 120
# Empty iterable: reduce without initializer raises TypeError
try:
    print(functools.reduce(operator.add, []))
except TypeError as exc:
    print(f"reduce empty without init: {exc}")

# With initializer — acts as the starting accumulator, also handles empty case
print(functools.reduce(operator.add, [], 0))       # 0
print(functools.reduce(operator.add, nums, 100))   # 115 — starts from 100

# Equivalent loop — what most Python code uses:
def reduce_loop(func, iterable, initializer=None):
    it = iter(iterable)
    if initializer is None:
        try:
            acc = next(it)
        except StopIteration:
            raise TypeError("reduce() of empty iterable with no initial value")
    else:
        acc = initializer
    for x in it:
        acc = func(acc, x)
    return acc

print(reduce_loop(operator.add, nums))  # 15
```

### 5.2 Realistic Uses (and Misuses)

```python
import functools
import operator

# Good: flatten a list of lists — but careful, O(n²) with + on lists!
lists = [[1, 2], [3, 4], [5]]
print(functools.reduce(operator.add, lists, []))  # [1, 2, 3, 4, 5] — but slow for many lists
# Better for flattening one level: itertools.chain or a comprehension
import itertools
print(list(itertools.chain.from_iterable(lists)))  # [1, 2, 3, 4, 5]
print([x for sub in lists for x in sub])           # same

# Good: composing functions — pipeline of callables
def compose(*funcs):
    """Return a function that applies funcs left-to-right: compose(f,g)(x) == g(f(x))."""
    def composed(x):
        return functools.reduce(lambda acc, f: f(acc), funcs, x)
    return composed

add1 = lambda x: x + 1
double = lambda x: x * 2
pipeline = compose(add1, double, str)  # (x+1)*2, then stringify
print(pipeline(5))  # "12"

# Good: finding max with a custom key via reduce (though `max` with key is clearer)
words = ["apple", "banana", "kiwi"]
longest = functools.reduce(lambda a, b: a if len(a) >= len(b) else b, words)
print(longest)  # "banana"
print(max(words, key=len))  # same, far clearer — prefer the builtin

# Bad: using reduce where a builtin exists — less readable, slower
# Don't do this:
print(functools.reduce(operator.add, nums))  # use sum(nums)
print(sum(nums))  # clearer
# Don't do this:
print(functools.reduce(lambda a, b: a if a > b else b, nums))  # use max(nums)
print(max(nums))
```

*Rule of thumb:* If Python has a builtin or `itertools` that does the same thing (`sum`, `max`, `min`, `any`, `all`, `itertools.chain`, `math.prod` in 3.8+), use it — not `reduce`. Use `reduce` for genuine custom left-folds where no builtin fits (e.g., function composition, merging dicts with a policy).

```python
# Python 3.8+: math.prod replaces reduce(mul, ...)
import math
print(math.prod([1, 2, 3, 4]))  # 24

# Merging dicts with reduce (Python 3.9+ has `|` for dict union, but reduce shows the pattern)
dicts = [{"a": 1}, {"b": 2}, {"a": 3}]
# Last-write-wins merge
merged = functools.reduce(operator.or_, dicts, {})  # dict.__or__ in 3.9+
print(merged)  # {'a': 3, 'b': 2}
# Pre-3.9 equivalent with a lambda:
merged2 = functools.reduce(lambda acc, d: {**acc, **d}, dicts, {})
print(merged2)
```

### 5.3 Edge Cases

```python
# Single element, no initializer — returns that element without calling func
print(functools.reduce(operator.add, [42]))  # 42 — func never called!

# Single element WITH initializer — func called once
print(functools.reduce(operator.add, [42], 10))  # 52 — 10 + 42

# Infinite iterable — reduce will hang! Only use on finite inputs
# functools.reduce(operator.add, itertools.count())  # never terminates

# Non-associative operations — order matters; reduce is always left-to-right
print(functools.reduce(operator.sub, [10, 3, 2]))    # (10-3)-2 = 5
print(functools.reduce(operator.sub, [10, 3, 2], 0)) # ((0-10)-3)-2 = -15 — different!
```

## 6. The `operator` Module — Replacing Trivial Lambdas

`operator` exposes Python's operators as functions. Why?

- **Readability:** `operator.add` says "addition" more clearly than `lambda a, b: a + b`.
- **Performance:** `operator` functions are implemented in C — faster when used with `map`/`filter`/`sorted`/`functools.reduce`.
- **Picklability:** Lambdas cannot be pickled (for `multiprocessing`); `operator` functions can.
- **Composability:** `itemgetter`, `attrgetter`, `methodcaller` are mini-function factories.

### 6.1 Arithmetic, Comparison, Logical, Sequence Operators

```python
import operator

# Arithmetic
print(operator.add(2, 3))        # 5 — same as 2 + 3
print(operator.mul(3, 4))        # 12
print(operator.truediv(7, 2))    # 3.5
print(operator.floordiv(7, 2))   # 3
print(operator.pow(2, 10))       # 1024
print(operator.neg(5))           # -5

# Comparison — return bool, useful with `filter` + `functools.partial` (see below)
print(operator.gt(5, 3))         # True — 5 > 3
print(operator.eq("a", "a"))     # True

# Sequence / mapping
lst = [1, 2, 3]
print(operator.getitem(lst, 1))          # 2 — lst[1]
operator.setitem(lst, 1, 99)
print(lst)                               # [1, 99, 3]
operator.delitem(lst, 0)
print(lst)                               # [99, 3]

d = {"a": 1}
print(operator.getitem(d, "a"))          # 1

# In-place operators — return the result, don't mutate immutables; mutate mutables in place
# These mirror `+=`, `*=`, etc.
x = 5
print(operator.iadd(x, 3))       # 8 — for ints, returns new int (immutables can't mutate)
lst = [1, 2]
operator.iadd(lst, [3, 4])       # lst += [3, 4] — mutates list in place
print(lst)                       # [1, 2, 3, 4]

# `is_` and `is_not` — identity checks as functions
print(operator.is_(None, None))  # True
```

### 6.2 `itemgetter`, `attrgetter`, `methodcaller` — Function Factories

These return *callables* configured to fetch items/attributes or call methods.

```python
import operator

# itemgetter — fetch one or more items
get_second = operator.itemgetter(1)
print(get_second([10, 20, 30]))     # 20
print(get_second("hello"))          # "e"

# Multiple indices → returns a tuple
get_first_and_last = operator.itemgetter(0, -1)
print(get_first_and_last([10, 20, 30]))  # (10, 30)

# Works on dicts too — by key
users = {"name": "Ada", "age": 30, "city": "London"}
get_name_age = operator.itemgetter("name", "age")
print(get_name_age(users))  # ('Ada', 30)

# attrgetter — fetch one or more attributes (supports dotted paths)
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(3, 4)
get_x = operator.attrgetter("x")
print(get_x(p))  # 3

# Dotted path — traverses attributes
class Rect:
    def __init__(self, origin):
        self.origin = origin

r = Rect(Point(1, 2))
print(operator.attrgetter("origin.x")(r))  # 1
print(operator.attrgetter("origin.y")(r))  # 2

# Multiple attrs → tuple
print(operator.attrgetter("x", "y")(p))  # (3, 4)

# methodcaller — call a named method with preset args
# operator.methodcaller(name, *args, **kwargs)(obj) == obj.name(*args, **kwargs)
words = ["hello world", "foo bar", "python"]
print(list(map(operator.methodcaller("split"), words)))
# [['hello', 'world'], ['foo', 'bar'], ['python']]
print(list(map(operator.methodcaller("upper"), words)))
# ['HELLO WORLD', 'FOO BAR', 'PYTHON']

# With arguments:
print(operator.methodcaller("replace", "o", "0")("hello world"))  # "hell0 w0rld"
print(list(map(operator.methodcaller("startswith", "hello"), words)))
# [True, False, False]
```

*Realistic comparison: lambda vs operator for common ops*

| Task | Lambda | Operator (preferred) |
|---|---|---|
| Sort by second element | `key=lambda x: x[1]` | `key=operator.itemgetter(1)` |
| Sort by `.name` | `key=lambda x: x.name` | `key=operator.attrgetter("name")` |
| Sort by `.address.city` | `key=lambda x: x.address.city` | `key=operator.attrgetter("address.city")` |
| Upper all strings | `map(lambda s: s.upper(), lst)` | `map(operator.methodcaller("upper"), lst)` |
| Sum with `reduce` | `reduce(lambda a,b: a+b, xs)` | `reduce(operator.add, xs)` |
| Filter > threshold | `filter(lambda x: x > 10, xs)` | `filter(functools.partial(operator.lt, 10), xs)` *or* comprehension |

```python
# Advanced: operator + sorted pitfall — attrgetter with missing attr raises AttributeError (like lambda)
data = [Point(1, 2), Point(3, 4)]
# If some Points lack .z, both lambda and attrgetter raise:
try:
    print(sorted(data, key=operator.attrgetter("z")))
except AttributeError as exc:
    print(f"attrgetter missing: {exc}")

# For optional attrs, you still need lambda with getattr:
print(sorted(data, key=lambda p: getattr(p, "z", 0)))
```

## 7. `functools` — The Functional Toolkit

### 7.1 `functools.partial` — Partial Application (Currying Lite)

`partial(func, *args, **kwargs)` returns a new callable with some arguments pre-filled.

```python
import functools

def power(base, exponent):
    return base ** exponent

square = functools.partial(power, exponent=2)
cube = functools.partial(power, exponent=3)
print(square(5))  # 25 — power(5, exponent=2)
print(cube(3))    # 27

# Positional partial — binds from the left
def add(a, b, c):
    return a + b + c

add_10 = functools.partial(add, 10)  # a=10
print(add_10(20, 30))  # 60 — 10+20+30
add_10_20 = functools.partial(add, 10, 20)
print(add_10_20(30))   # 60

# Keyword partial — binds by name, any position
def greet(greeting, name, punctuation="!"):
    return f"{greeting}, {name}{punctuation}"

hello = functools.partial(greet, greeting="Hello")
print(hello("Ada"))               # "Hello, Ada!"
print(hello("Bob", punctuation="."))  # "Hello, Bob."

# Introspection — partial objects keep references to the original
print(hello.func)   # <function greet>
print(hello.args)   # ()
print(hello.keywords)  # {'greeting': 'Hello'}
```

#### Realistic: `partial` with `map`/`filter`/`sorted`

```python
import functools, operator

nums = [1, 5, 10, 15, 20]

# Filter "greater than 10" — without lambda!
greater_than_10 = functools.partial(operator.lt, 10)  # lambda x: 10 < x  →  x > 10
# Be careful: operator.lt(a, b) == a < b, so partial(operator.lt, 10)(x) == 10 < x == x > 10
print(list(filter(greater_than_10, nums)))  # [15, 20]

# Also readable as:
print([x for x in nums if x > 10])  # comprehension — often clearer

# Sorting with a custom comparator? Use functools.cmp_to_key (see §7.5) + partial
```

#### `partial` Pitfalls: Late Binding and Mutability

```python
# Pitfall 1: partial captures the *object*, not a copy — mutable defaults bite
def append_to(value, lst=[]):  # classic mutable default trap
    lst.append(value)
    return lst

# Don't do this with partial either:
bad = functools.partial(append_to, lst=[])
print(bad(1))  # [1]
print(bad(2))  # [1, 2] — same list object!

# Fix: use None and create inside
def append_to_fixed(value, lst=None):
    if lst is None:
        lst = []
    lst.append(value)
    return lst

# Pitfall 2: partial args are evaluated at creation, but if they're mutable and mutated later...
shared = [1, 2]
p = functools.partial(operator.add, shared)  # not sensible, but illustrates holding a reference
shared.append(3)
# p still references the mutated list

# Pitfall 3: partial doesn't help with argument *order* for non-keyword functions
# operator.gt(threshold, x) checks threshold > x, but you want x > threshold
# You must think about argument order!
import operator
# To filter x > 5, you need 5 < x, i.e., operator.lt(5, x) or operator.gt(x, 5)
# So:
print(list(filter(functools.partial(operator.lt, 5), [3, 7, 2, 9])))  # [7, 9] — 5 < x
# Not:
# functools.partial(operator.gt, 5) → 5 > x → x < 5 — the opposite!
```

#### `functools.partialmethod` — `partial` for Methods (Descriptor-Aware)

`partial` does NOT work correctly as a method decorator (it is not a descriptor). Use `partialmethod`.

```python
import functools

class Cell:
    def set(self, value, *, strict=False):
        print(f"set({value!r}, strict={strict})")

    # partial would bind incorrectly — it captures `self` at class-creation time? No, but it doesn't bind.
    # partialmethod is descriptor-aware and binds `self` correctly per instance.
    set_strict = functools.partialmethod(set, strict=True)

c = Cell()
c.set(10)           # set(10, strict=False)
c.set_strict(10)    # set(10, strict=True) — correctly binds self
```

### 7.2 `functools.wraps` — Preserving Decorator Metadata

Without `wraps`, a decorator replaces the wrapped function's `__name__`, `__doc__`, `__annotations__`, `__module__`, `__qualname__`, and `__wrapped__`. Tools like `help()`, `inspect.signature`, debuggers, and documentation generators then see the *wrapper*, not the original.

```python
import functools
import inspect

# Without wraps — metadata lost
def my_decorator_no_wraps(func):
    def wrapper(*args, **kwargs):
        """Wrapper docstring (useless)."""
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@my_decorator_no_wraps
def greet(name: str) -> str:
    """Greet someone."""
    return f"Hello, {name}!"

print(greet.__name__)              # 'wrapper' — wrong!
print(greet.__doc__)               # 'Wrapper docstring (useless).' — wrong!
print(inspect.signature(greet))    # (*args, **kwargs) — signature lost!
help(greet)                        # shows wrapper, not greet

# With wraps — metadata preserved
def my_decorator(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@my_decorator
def greet2(name: str) -> str:
    """Greet someone."""
    return f"Hello, {name}!"

print(greet2.__name__)              # 'greet2' — correct!
print(greet2.__doc__)               # 'Greet someone.' — correct!
print(inspect.signature(greet2))    # (name: str) -> str — preserved via __wrapped__!
print(greet2.__wrapped__)           # <function greet2> — original accessible

# What wraps does under the hood:
# WRAPPER_ASSIGNMENTS = ('__module__', '__name__', '__qualname__', '__doc__', '__annotations__')
# WRAPPER_UPDATES = ('__dict__',)
# functools.update_wrapper(wrapper, wrapped, assigned=..., updated=...)
# functools.wraps is just a convenience for update_wrapper as a decorator
```

*Rule:* Always use `@functools.wraps(func)` inside every decorator. No exceptions.

```python
# Advanced: wraps + signature preservation for decorators that change the signature
import functools

def with_prefix(prefix: str):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            # If your decorator *adds* a parameter, wraps alone won't update the signature.
            # For full signature rewriting, use `inspect.signature` manipulation or `decorator` lib.
            # But __wrapped__ still lets tools peel back to the original.
            print(prefix, end=" ")
            return func(*args, **kwargs)
        return wrapper
    return decorator

@with_prefix("[LOG]")
def add(a, b): return a + b

print(add(2, 3))  # [LOG] 5
print(inspect.signature(add))           # (*args, **kwargs) — not ideal, but __wrapped__ helps
print(inspect.signature(add.__wrapped__))  # (a, b)
```

### 7.3 `functools.lru_cache` and `functools.cache` — Memoization

`lru_cache` memoizes function results keyed by arguments. Subsequent calls with the same arguments return the cached value without re-executing.

```python
import functools
import time

# Simple → lru_cache basics
@functools.lru_cache(maxsize=128)
def fib(n: int) -> int:
    """Naive recursive Fibonacci — exponential without caching, linear with it."""
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(30))  # 832040 — fast with cache, glacial without
print(fib.cache_info())
# CacheInfo(hits=..., misses=..., maxsize=128, currsize=...)

# maxsize=None → unbounded cache (Python 3.9+ alias: @functools.cache)
@functools.cache
def fib2(n: int) -> int:
    if n < 2:
        return n
    return fib2(n - 1) + fib2(n - 2)

# Typed variant — cache separately for 3 vs 3.0 if typed=True
@functools.lru_cache(maxsize=None, typed=True)
def typed_func(x):
    return x

print(typed_func(3), typed_func(3.0))
print(typed_func.cache_info())  # two misses if typed=True, one hit if typed=False
```

#### How `lru_cache` Works

1. Arguments are turned into a cache key via hashing. **All arguments must be hashable.**
2. If the key is in the cache, return the cached value (`hits += 1`).
3. Otherwise, call the function, store the result, return it (`misses += 1`).
4. When `maxsize` is exceeded, the *least recently used* entry is evicted. `maxsize=None` never evicts.

```python
# Hits vs misses
@functools.lru_cache(maxsize=2)
def square(n):
    print(f"computing square({n})")
    return n * n

print(square(2))  # computing square(2) → 4 (miss)
print(square(3))  # computing square(3) → 9 (miss)
print(square(2))  # 4 (hit — no print)
print(square(4))  # computing square(4) → 16 (miss, evicts 3 — LRU)
print(square(3))  # computing square(3) → 9 (miss again — was evicted)
print(square.cache_info())

# Manual cache management
square.cache_clear()       # empty the cache
print(square.cache_info()) # hits=0, misses=0
print(square.cache_parameters())  # {'maxsize': 2, 'typed': False}
```

#### Critical Pitfalls and Edge Cases

```python
import functools

# Pitfall 1: Unhashable arguments — TypeError
@functools.lru_cache(maxsize=None)
def bad(arg):
    return arg

try:
    bad([1, 2, 3])  # list is unhashable
except TypeError as exc:
    print(f"unhashable: {exc}")

# Fix: convert to hashable (tuple, frozenset) or don't cache, or use a custom key
@functools.lru_cache(maxsize=None)
def good(arg: tuple):
    return sum(arg)

print(good((1, 2, 3)))  # 6

# Pitfall 2: Mutable return values — cache returns the SAME object, not a copy
@functools.lru_cache(maxsize=None)
def get_list(n):
    return [n] * 3

a = get_list(5)
print(a)  # [5, 5, 5]
a.append(99)
print(get_list(5))  # [5, 5, 5, 99] — mutated the cached object!

# Fix: return immutable, or copy on return, or document "do not mutate"
@functools.lru_cache(maxsize=None)
def get_tuple(n):
    return (n,) * 3  # tuple is immutable — safe

# Pitfall 3: Caching functions with side effects or non-determinism
import random

@functools.lru_cache(maxsize=None)
def random_with_cache(n):
    return random.random()

print(random_with_cache(1))  # e.g., 0.42
print(random_with_cache(1))  # 0.42 again — not random anymore!

# Pitfall 4: Methods — `self` is part of the cache key, so each instance has its own cache
# But `self` must be hashable (usually it is, via object identity hash)
class Calculator:
    @functools.lru_cache(maxsize=None)
    def compute(self, x):
        print(f"Computing {x}")
        return x * x

c1 = Calculator()
c2 = Calculator()
print(c1.compute(5))  # Computing 5
print(c1.compute(5))  # cached (hit)
print(c2.compute(5))  # Computing 5 — separate cache per instance (different self)
# Note: this leaks `self` — the cache holds a reference to the instance!
# For per-instance caching, use `cached_property` or a WeakKeyDictionary pattern.

# Pitfall 5: Recursive functions — cache helps, but only within the same decorated function
# Mutually recursive functions each need their own cache

# Pitfall 6: Cache is not thread-safe for the *function* itself (but lru_cache's internal dict is
# protected by a lock in CPython). For cached_property, see below.

# Cache on classmethods / staticmethods — order matters!
class MyClass:
    @classmethod
    @functools.lru_cache(maxsize=None)
    def cached_classmethod(cls, x):
        print(f"cm {cls.__name__} {x}")
        return x * 2

    @staticmethod
    @functools.lru_cache(maxsize=None)
    def cached_staticmethod(x):
        print(f"sm {x}")
        return x * 3

# Correct order: @classmethod/@staticmethod OUTER, @lru_cache INNER
# Reversed order would try to cache the descriptor object, not the function
```

#### When to Use `lru_cache`

| Use `lru_cache` when | Do NOT use when |
|---|---|
| Function is *pure* (same inputs → same output) | Function has side effects, reads mutable state, or is random/IO-bound without invalidation |
| Arguments are hashable | Arguments are lists/dicts/sets |
| You call it repeatedly with overlapping arguments | Each call uses unique arguments (cache just wastes memory) |
| Computation is expensive | Computation is cheap (cache overhead not worth it) |
| Memory for cached results is bounded or `maxsize` limits it | Results are huge and unbounded |

### 7.4 `functools.cached_property` — Lazy Once-Per-Instance Attribute

`cached_property` is a descriptor that computes the value on first access, caches it in the instance's `__dict__`, and on subsequent accesses returns the cached value directly (bypassing the descriptor). Introduced in Python 3.8.

```python
import functools
import time

class DataSet:
    def __init__(self, data: list[int]):
        self.data = data

    @functools.cached_property
    def mean(self) -> float:
        print("Computing mean...")
        return sum(self.data) / len(self.data) if self.data else 0.0

    @functools.cached_property
    def sorted_data(self) -> list[int]:
        print("Sorting...")
        return sorted(self.data)

ds = DataSet([3, 1, 2])
print(ds.mean)   # Computing mean...  → 2.0
print(ds.mean)   # 2.0 — no recomputation! (from __dict__)
print(ds.__dict__["mean"])  # 2.0 — cached in instance dict
print("mean" in DataSet.__dict__)  # False — cached_property lives on class, value on instance

# Cache invalidation — just delete the attribute
del ds.mean
print(ds.mean)   # Computing mean... → 2.0 — recomputed!

# Assignment also works — you can *set* the cached value
ds.mean = 99.0
print(ds.mean)   # 99.0 — no computation, just the assigned value

# Edge: cached_property is NOT thread-safe in the computation phase
# Two threads could both compute simultaneously (both see no cache, both compute).
# For thread safety, wrap with a lock if needed.

# Comparison with manual lazy pattern:
class DataSetManual:
    def __init__(self, data):
        self.data = data
        self._mean = None
        self._mean_computed = False

    @property
    def mean(self):
        if not self._mean_computed:
            print("Computing mean (manual)...")
            self._mean = sum(self.data) / len(self.data) if self.data else 0
            self._mean_computed = True
        return self._mean

# cached_property does the same with less boilerplate, plus it places the value in __dict__
# so inspect and serialization see it naturally.
```

*Key difference from `lru_cache` on a method:* `cached_property` caches *one value per instance*, has no `maxsize`, no args (it's a property), and deletes the cache entry with `del obj.attr` instead of `cache_clear()`.

```python
# When to use which

# cached_property — expensive per-instance derived data, no args
class Circle:
    def __init__(self, radius: float):
        self.radius = radius

    @functools.cached_property
    def area(self) -> float:
        import math
        return math.pi * self.radius ** 2

# lru_cache — expensive function with args, possibly shared across instances
@functools.lru_cache(maxsize=256)
def expensive_lookup(key: str) -> str:
    time.sleep(0.01)
    return key.upper()
```

### 7.5 Other `functools` Gems (Brief but Important)

#### `functools.total_ordering` — Fill In Missing Comparisons

```python
import functools

@functools.total_ordering
class Version:
    def __init__(self, major: int, minor: int):
        self.major = major
        self.minor = minor

    def __eq__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return (self.major, self.minor) == (other.major, other.minor)

    def __lt__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return (self.major, self.minor) < (other.major, other.minor)

# total_ordering generates __le__, __gt__, __ge__ from __eq__ + __lt__
print(Version(1, 0) < Version(2, 0))   # True
print(Version(1, 0) <= Version(1, 0))  # True (generated)
print(Version(2, 0) > Version(1, 0))   # True (generated)
# Cost: generated methods are slower (they call __lt__/__eq__ repeatedly). For hot paths, implement manually.
```

#### `functools.singledispatch` — Simple Generic Functions

Not covered deeply here, but know it exists: `@singledispatch` lets you overload a function by the type of the first argument.

```python
import functools

@functools.singledispatch
def process(value):
    print(f"generic: {value!r}")

@process.register(int)
def _(value):
    print(f"int: {value * 2}")

@process.register(list)
def _(value):
    print(f"list of length {len(value)}")

process("hello")  # generic: 'hello'
process(5)        # int: 10
process([1, 2])   # list of length 2
```

#### `functools.cmp_to_key` — Old-Style Comparators for `sorted`

```python
import functools

# Old cmp: returns negative/0/positive. Python 3 removed cmp, but cmp_to_key bridges.
def cmp(a, b):
    # Sort by absolute value, then by actual value
    if abs(a) != abs(b):
        return -1 if abs(a) < abs(b) else 1
    return -1 if a < b else (1 if a > b else 0)

nums = [-3, 2, -2, 3, 0]
print(sorted(nums, key=functools.cmp_to_key(cmp)))  # [0, -2, 2, -3, 3]
# Prefer `key=` with a real key function when possible — cmp_to_key is slower (O(n log n) Python calls)
# Use only when the ordering logic truly needs pairwise comparison (e.g., locale-aware collation).
```

## 8. Comprehensions vs Functional Style — The Pythonic Choice

### 8.1 The Official Guidance

Guido's preference (and PEP 8's implication):

> **Comprehensions are preferred** for most transformations and filtering. They are explicit, they handle nested logic, and they avoid an extra function call per element.

The Zen of Python applies: *Explicit is better than implicit. Readability counts.*

### 8.2 Head-to-Head Comparisons

```python
nums = range(10)

# --- Map vs comprehension ---
print(list(map(lambda x: x * 2, nums)))
print([x * 2 for x in nums])        # preferred — no lambda, no function call overhead
# With a named function, map is competitive:
def double(x): return x * 2
print(list(map(double, nums)))       # okay — but [double(x) for x in nums] is still often clearer

# --- Filter vs comprehension ---
print(list(filter(lambda x: x % 2 == 0, nums)))
print([x for x in nums if x % 2 == 0])  # preferred

# --- Map + filter vs comprehension ---
print(list(map(lambda x: x * x, filter(lambda x: x % 2 == 0, nums))))
print([x * x for x in nums if x % 2 == 0])  # preferred — single pass, no nested lambdas

# --- When operator/builtin makes map cleaner ---
import operator
words = ["  hello  ", "  world ", "  python "]
print(list(map(str.strip, words)))          # clean — builtin, no lambda needed
print([s.strip() for s in words])           # also clean — toss-up
# For str.strip, either is fine; for operator.itemgetter, map can be nice:
data = [(1, "b"), (2, "a")]
print(sorted(data, key=operator.itemgetter(1)))  # declarative

# --- Performance (CPython) ---
# For simple expressions: comprehension is usually faster (no per-element Python call)
# For builtins/C functions: map can be faster (the loop is in C, function is in C)
# Always profile if it matters — but default to comprehension for clarity
```

### 8.3 When Functional Style *Is* Pythonic

Despite the preference for comprehensions, functional style wins in these cases:

| Scenario | Why functional wins | Example |
|---|---|---|
| **You already have a named function** | No lambda needed, `map(func, data)` is concise | `map(str.strip, lines)` vs `[s.strip() for s in lines]` |
| **Pipeline is passed as an object** | `map` returns an iterator you can compose/store | `pipeline = map(transform, filter(predicate, data))` |
| **Multiple iterables** | `map(func, a, b, c)` zips naturally | `map(operator.add, list1, list2)` |
| **Need picklability** (multiprocessing) | Lambdas/comprehensions aren't easily pickled as functions; `operator` callables are | `Pool.map(operator.methodcaller("upper"), words)` |
| **Partial application / currying** | `partial` clearly expresses "pre-fill args" | `sorted(items, key=partial(getattr, name="attr"))` — but `attrgetter` often better |
| **Memoization** | Only `functools` provides it | `@lru_cache` is irreplaceable |
| **Lazy infinite or large streams** | `map`/`filter` compose lazily with `itertools` | `islice(map(...), 100)` |

```python
# Example where functional style is genuinely clearer: building a processing pipeline as data
import functools, operator, itertools

def pipeline_example():
    data = range(100)
    # Functional pipeline — each stage is a composable object
    cleaned = filter(lambda x: x % 2 == 0, data)
    transformed = map(lambda x: x ** 2, cleaned)
    limited = itertools.islice(transformed, 5)
    return list(limited)

print(pipeline_example())  # [0, 4, 16, 36, 64]

# Equivalent as a generator expression — also fine, and often preferred for short pipelines:
print(list(x ** 2 for x in range(100) if x % 2 == 0)[:5])

# Realistic: multiprocessing — operator/methodcaller are picklable, lambdas are not
# from multiprocessing import Pool
# with Pool() as pool:
#     results = pool.map(operator.methodcaller("upper"), ["hello", "world"])  # works
#     results = pool.map(lambda s: s.upper(), ["hello", "world"])             # fails: can't pickle lambda
```

### 8.4 Hybrid Style — The Pragmatic Middle Ground

Most real Python code mixes styles without dogma:

```python
import functools, operator, itertools

# Hybrid: use comprehensions for filtering/transforming, functools for caching/partial
@functools.lru_cache(maxsize=256)
def normalize(name: str) -> str:
    return name.strip().lower()

users = ["  Alice ", "BOB", "  alice ", "Charlie"]

# Comprehension for the main transformation (readable), cached function for the expensive part
normalized = [normalize(u) for u in users]
print(normalized)

# Functional where the function already exists (no lambda tax):
# Removing duplicates while preserving order? Use dict.fromkeys (Python 3.7+)
print(list(dict.fromkeys(normalized)))  # preserves first occurrence

# Or with operator for sorting:
from operator import itemgetter
records = [{"name": "Bob", "score": 85}, {"name": "Alice", "score": 92}]
print(sorted(records, key=itemgetter("score")))  # functional key, comprehension not needed

# Partial for configuring a callback:
import json
pretty_json = functools.partial(json.dumps, indent=2, sort_keys=True)
print(pretty_json({"b": 2, "a": 1}))
```

## 9. Edge Cases and Common Mistakes Roundup

### 9.1 `map`/`filter`/`reduce` Gotchas

```python
import functools, operator

# Gotcha 1: map/filter are exhausted after one use — they are iterators, not lists
m = map(lambda x: x * 2, [1, 2, 3])
print(list(m))  # [2, 4, 6]
print(list(m))  # [] — silent emptiness
# Fix: re-create, or materialize with list() if you need reuse, or use a comprehension

# Gotcha 2: map with multiple iterables stops at shortest — silent truncation
print(list(map(operator.add, [1, 2, 3], [10, 20])))  # [11, 22] — 3 is silently dropped
# Fix: use itertools.zip_longest if you need to handle unequal lengths, or strict zip

# Gotcha 3: filter(None, ...) removes ALL falsy values — not just None
print(list(filter(None, [0, "", None, [], False, 1, "hi"])))  # [1, 'hi'] — 0 and "" gone too!
# Fix: use a precise predicate if you only want to drop None:
print([x for x in [0, "", None, [], False, 1, "hi"] if x is not None])  # [0, '', [], False, 1, 'hi']

# Gotcha 4: lambda late binding (covered in §2.3) — also bites map/filter built in loops
funcs = [lambda x: x + i for i in range(3)]
# All three have i=2 (final value)
print([f(10) for f in funcs])  # [12, 12, 12]
# Fix: lambda x, i=i: x + i

# Gotcha 5: reduce on empty iterable without initializer — TypeError
try:
    functools.reduce(operator.add, [])
except TypeError as e:
    print(e)

# Gotcha 6: Using reduce where a builtin exists — less readable and often slower
# Bad: functools.reduce(operator.add, xs) — use sum(xs)
# Bad: functools.reduce(operator.mul, xs) — use math.prod(xs) (3.8+)
# Bad: functools.reduce(lambda a, b: a if a > b else b, xs) — use max(xs)
```

### 9.2 `functools` Gotchas

```python
import functools

# Gotcha 1: lru_cache with unhashable args — TypeError at call time, not decoration time
@functools.lru_cache(maxsize=None)
def cached(x):
    return x

cached((1, 2))  # ok — tuple is hashable
try:
    cached([1, 2])  # TypeError
except TypeError as e:
    print(f"lru_cache unhashable: {e}")

# Gotcha 2: lru_cache caches exceptions? No — if the function raises, nothing is cached
@functools.lru_cache(maxsize=None)
def may_fail(n):
    print(f"called with {n}")
    if n == 0:
        raise ValueError("zero")
    return n * 2

try: may_fail(0)
except ValueError: pass
try: may_fail(0)  # called again — not cached, so it re-executes and re-raises
except ValueError: pass

# Gotcha 3: lru_cache on methods holds a reference to self — can prevent GC of instances
# If instances are short-lived but cache is long-lived, this leaks memory.
# For per-instance memoization that doesn't leak, consider weakref or cached_property.

# Gotcha 4: partial with mutable objects — holds a reference, not a snapshot
base = [1, 2]
p = functools.partial(operator.add, base)  # nonsense but shows reference semantics
# If base is mutated elsewhere, p sees the mutation.

# Gotcha 5: Forgetting @functools.wraps — breaks help(), signature, and pickling
# Always use wraps inside decorators.

# Gotcha 6: cached_property cannot take arguments — it's a property
# If you need a cached method with args, use lru_cache on a method (with self caveat) or manual dict.
```

## 10. Realistic End-to-End Example: Configurable Data Pipeline

This example integrates `lambda`, `map`, `filter`, `reduce`, `operator`, `partial`, `lru_cache`, and `wraps` into a pipeline you might actually write.

```python
import functools
import operator
import itertools
import json
from typing import Callable

# --- Step 1: Cached parsing (functools.cache) ---
@functools.cache
def parse_line(line: str) -> dict:
    """Parse a JSON line — cached because duplicates are common in logs."""
    return json.loads(line)

# --- Step 2: Configurable filter via partial ---
def min_score(record: dict, threshold: int) -> bool:
    return record.get("score", 0) >= threshold

# Pre-configure the threshold — partial makes the predicate reusable
at_least_80 = functools.partial(min_score, threshold=80)
# Note: partial binds threshold as keyword, so the remaining arg (record) is positional.
# For filter, we need predicate(record) → at_least_80(record) → min_score(record, threshold=80) — correct.
# But our signature is min_score(record, threshold) — first arg is record, so we need threshold as kw!

# Actually, to make filter work naturally, write the threshold-first variant:
def has_min_score(threshold: int, record: dict) -> bool:
    return record.get("score", 0) >= threshold

at_least_80_v2 = functools.partial(has_min_score, 80)  # threshold=80 pre-filled, record remains
print(at_least_80_v2({"score": 90}))  # True
# Now at_least_80_v2 is a unary predicate suitable for filter()

# --- Step 3: Transform via map + operator + lambda ---

raw_lines = [
    '{"name": "Ada", "score": 95}',
    '{"name": "Bob", "score": 60}',
    '{"name": "Carla", "score": 88}',
    '{"name": "Ada", "score": 95}',  # duplicate — cache helps
]

# Pipeline: parse → filter → transform → reduce to summary
parsed = map(parse_line, raw_lines)                          # lazy parse (cached)
passing = filter(at_least_80_v2, parsed)                     # lazy filter
# Transform: extract "name" with itemgetter (no lambda needed)
names = map(operator.itemgetter("name"), passing)            # lazy projection
print(list(names))  # ['Ada', 'Carla', 'Ada']

# --- Step 4: Decorator with wraps for logging ---

def log_calls(func: Callable) -> Callable:
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"→ {func.__name__}{args}")
        result = func(*args, **kwargs)
        print(f"← {result!r}")
        return result
    return wrapper

@log_calls
def count_names(names_iter) -> int:
    """Count names in an iterable."""
    return functools.reduce(lambda acc, _: acc + 1, names_iter, 0)
    # Note: reduce here is just len(list(...)) or sum(1 for _ in iter) — but shows the pattern.
    # Pythonic alternative: sum(1 for _ in names_iter) — clearer!

# Rebuild pipeline (iterators were consumed)
parsed = map(parse_line, raw_lines)
passing = filter(at_least_80_v2, parsed)
names = map(operator.itemgetter("name"), passing)
print(count_names(names))  # → count_names(...)  ← 3 (Ada, Carla, Ada)
print(count_names.__name__, count_names.__doc__)  # count_names, Count names...  — wraps preserved!

# --- Step 5: cached_property for a pipeline result object ---

class Report:
    def __init__(self, lines: list[str]):
        self.lines = lines

    @functools.cached_property
    def passing_names(self) -> list[str]:
        parsed = map(parse_line, self.lines)
        passing = filter(at_least_80_v2, parsed)
        return list(map(operator.itemgetter("name"), passing))

    @functools.cached_property
    def summary(self) -> dict:
        from collections import Counter
        return dict(Counter(self.passing_names))

r = Report(raw_lines)
print(r.passing_names)  # ['Ada', 'Carla', 'Ada']
print(r.summary)        # {'Ada': 2, 'Carla': 1}
print(r.summary)        # cached — no recomputation
```

*Explanation:* This pipeline shows where each tool earns its keep: `cache` for repeated JSON parsing, `partial` for configurable predicates, `operator.itemgetter` to replace `lambda r: r["name"]`, `map`/`filter` for lazy stages, `reduce` for folding (though `sum`/`Counter` would be more Pythonic), `wraps` for decorator hygiene, and `cached_property` for a lazy report object.

## 11. Performance Notes

| Pattern | Relative speed | Notes |
|---|---|---|
| `[f(x) for x in data]` with inline expression | **Fastest** for simple expressions | No function call per element; comprehension loop is in C |
| `map(builtin, data)` e.g. `map(str.strip, data)` | **Very fast** — loop + function in C | Can beat comprehension when function is a C builtin |
| `map(lambda x: ..., data)` | **Slower** than comprehension | `lambda` is a Python function call per element |
| `filter(lambda, data)` | **Slower** than `if` in comprehension | Same reason |
| `reduce` with Python lambda | **Slow and verbose** | Prefer builtins (`sum`, `max`, `math.prod`) |
| `lru_cache` | **Fast hits, overhead on misses** | Cache lookup is hashing + dict; worthwhile only if function body is expensive |

```python
# Micro-benchmark style (use timeit in real code)
import timeit
data = list(range(1000))
print(timeit.timeit("[x*2 for x in data]", globals={"data": data}, number=10000))
print(timeit.timeit("list(map(lambda x: x*2, data))", globals={"data": data}, number=10000))
# Comprehension wins for lambda case
print(timeit.timeit("list(map(str, data))", globals={"data": data}, number=10000))
print(timeit.timeit("[str(x) for x in data]", globals={"data": data}, number=10000))
# Map + builtin may win or tie — measure, don't guess
```

## Summary

- `lambda` creates anonymous single-expression functions; prefer `def` for anything reusable or with statements.
- `map(function, iterable)` and `filter(predicate, iterable)` are lazy iterators; `map` zips multiple iterables; both are often replaced by comprehensions for readability.
- `functools.reduce(function, iterable, initializer)` is a left fold; prefer builtins (`sum`, `max`, `math.prod`, `itertools.chain`) when they exist.
- The `operator` module replaces trivial lambdas (`lambda x: x[0]` → `itemgetter(0)`, `lambda x: x.name` → `attrgetter("name")`, `lambda x: x.upper()` → `methodcaller("upper")`) with faster, picklable C callables.
- `functools.partial` pre-fills arguments; `partialmethod` is the descriptor-aware variant for methods.
- `functools.wraps` (via `update_wrapper`) preserves `__name__`, `__doc__`, `__annotations__`, and `__wrapped__` in decorators — always use it.
- `functools.lru_cache`/`cache` memoizes pure functions with hashable args; watch for unhashable args, mutable return values, `self` leaks, and non-deterministic functions.
- `functools.cached_property` lazily caches a per-instance computed attribute in `__dict__`; invalidate with `del obj.attr`.
- Comprehensions are idiomatic for most transforms/filters; functional tools shine for *pipelines as objects*, *picklable callables*, *pre-configured predicates*, and *memoization*.
