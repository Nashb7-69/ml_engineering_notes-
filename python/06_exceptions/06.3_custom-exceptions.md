# 06.3 Custom Exceptions: Designing Your Own Exception Types

Python's built-in exceptions cover generic failures — wrong type, missing key, IO error — but they cannot express domain concepts like "insufficient funds", "invalid ISBN", or "payment gateway timeout". Custom exceptions bridge that gap: they make error handling *semantic*, enable precise `except` clauses, and document your API's failure modes as part of its type signature.

## Why Create Custom Exceptions?

Consider code that only uses built-ins:

```python
# Without custom exceptions — caller must parse messages or guess
def transfer_funds(source, target, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if source.balance < amount:
        raise ValueError("insufficient funds")  # same type as above!
    if source.is_frozen:
        raise RuntimeError("account frozen")

# Caller cannot distinguish "bad amount" from "insufficient funds"
# without fragile string matching:
try:
    transfer_funds(a, b, 100)
except ValueError as exc:
    if "insufficient funds" in str(exc):
        handle_insufficient()
    elif "amount must be positive" in str(exc):
        handle_bad_amount()
    # Fragile — message changes break this; l10n breaks this; typo breaks this
```

With custom exceptions:

```python
class InsufficientFundsError(Exception):
    pass

class InvalidAmountError(ValueError):
    pass

class AccountFrozenError(RuntimeError):
    pass

def transfer_funds_v2(source, target, amount):
    if amount <= 0:
        raise InvalidAmountError(f"amount must be positive, got {amount}")
    if source.is_frozen:
        raise AccountFrozenError(f"account {source.id} is frozen")
    if source.balance < amount:
        raise InsufficientFundsError(
            f"account {source.id} has {source.balance}, need {amount}"
        )

# Caller handles each case precisely:
try:
    transfer_funds_v2(a, b, 100)
except InsufficientFundsError as exc:
    handle_insufficient(exc)
except InvalidAmountError as exc:
    handle_bad_amount(exc)
except AccountFrozenError as exc:
    handle_frozen(exc)
```

**Explanation:** Each failure mode gets its own *type*. Handling is by type identity (`isinstance`), not string parsing — stable, toolable, and self-documenting.

## The Minimal Custom Exception

```python
# The simplest useful custom exception — just a distinct type with a message
class AppError(Exception):
    """Base for all application-specific errors."""
    pass

class ValidationError(AppError):
    pass

# Usage
raise ValidationError("email must contain '@'")

# Catching
try:
    raise ValidationError("bad email")
except AppError as exc:
    print(f"App error: {exc}")  # AppError catches ValidationError (subclass)
except Exception as exc:
    print(f"Other error: {exc}")
```

**Why subclass `Exception`, not `BaseException`:**

| Base | Consequence |
|------|-------------|
| `Exception` | Correct — caught by `except Exception`, excluded from bare-`except` bypass. Interoperates with all normal handling. |
| `BaseException` | Wrong — bypasses `except Exception` handlers. Your errors become uncatchable by generic code. Only for system-level signals. |
| `object` / no base | Syntax error at raise time — `raise` requires `BaseException` subclass. |

> **Rule:** Always inherit from `Exception` (or one of its subclasses). Never from `BaseException` directly.

## Storing Context — Beyond a Message String

Real errors carry structured data: which account, what balance, what was attempted. Store it as attributes so handlers can *programmatically* inspect it.

### Basic: Pass Message via super().__init__

```python
class InsufficientFundsError(Exception):
    """Raised when an account lacks funds for a transfer."""
    pass

# Single-arg message — the common case
try:
    raise InsufficientFundsError("account 123: balance 50, need 100")
except InsufficientFundsError as exc:
    print(str(exc))    # 'account 123: balance 50, need 100'
    print(exc.args)    # ('account 123: balance 50, need 100',)
    print(exc.args[0]) # same
```

**Explanation:** `Exception.__init__(*args)` stores all args in `.args` and `str(exc)` formats them. For a single string arg, `str(exc)` is that string. For multiple args, `str(exc)` shows a tuple repr — which is why the single-message convention matters.

### Intermediate: Structured Attributes

```python
class InsufficientFundsError(Exception):
    """Raised when an account lacks funds.

    Attributes:
        account_id: Identifier of the source account.
        balance: Current balance.
        amount: Attempted debit amount.
        deficit: How much more was needed (amount - balance).
    """

    def __init__(self, account_id, balance, amount, message=None):
        self.account_id = account_id
        self.balance = balance
        self.amount = amount
        self.deficit = amount - balance
        # Build a default message if none provided, and pass to base
        if message is None:
            message = (
                f"account {account_id!r} has insufficient funds: "
                f"balance={balance}, required={amount}, deficit={self.deficit}"
            )
        super().__init__(message)

# Raising with structured data
try:
    raise InsufficientFundsError(account_id="ACC-123", balance=50.0, amount=100.0)
except InsufficientFundsError as exc:
    print(str(exc))
    # 'account 'ACC-123' has insufficient funds: balance=50.0, required=100.0, deficit=50.0'
    print(f"Account: {exc.account_id}")
    print(f"Balance: {exc.balance}, Amount: {exc.amount}, Deficit: {exc.deficit}")
    print(f"Args: {exc.args}")  # ('account ... deficit=50.0',)

    # Handler can make decisions from structured data, not string parsing:
    if exc.deficit > 1000:
        print("Large deficit — escalate to manager")
    else:
        print(f"Offer overdraft for {exc.deficit}")
```

**Key design points:**

1. **Call `super().__init__(message)`** — ensures `str(exc)` and `.args` work correctly for logging/traceback display. If you store attributes but forget `super().__init__`, `str(exc)` will be empty.
2. **Store raw values, not just formatted strings** — handlers need numbers, IDs, not substrings to parse.
3. **Use keyword arguments** for clarity at the raise site.

### Advanced: Rich Context with __str__ and __repr__

```python
class PaymentError(Exception):
    """Base for payment failures."""

class CardDeclinedError(PaymentError):
    """Card was declined by the processor."""

    def __init__(self, card_last4, amount, processor_code, processor_message, decline_type="generic"):
        self.card_last4 = card_last4
        self.amount = amount
        self.processor_code = processor_code
        self.processor_message = processor_message
        self.decline_type = decline_type
        super().__init__(
            f"card ending {card_last4} declined for ${amount:.2f}: "
            f"[{processor_code}] {processor_message}"
        )

    def __str__(self):
        # str(exc) — human-readable, used in tracebacks and logs
        return super().__str__()

    def __repr__(self):
        # repr(exc) — unambiguous, useful in debugging
        return (
            f"{type(self).__name__}("
            f"card_last4={self.card_last4!r}, amount={self.amount!r}, "
            f"processor_code={self.processor_code!r}, decline_type={self.decline_type!r})"
        )

try:
    raise CardDeclinedError(
        card_last4="4242", amount=99.99,
        processor_code="insufficient_funds",
        processor_message="Card has insufficient funds",
        decline_type="insufficient_funds"
    )
except CardDeclinedError as exc:
    print(str(exc))   # human message
    print(repr(exc))  # structured repr
    print(exc.processor_code)  # programmatic access

    # Realistic handler — route by decline_type, not message
    if exc.decline_type == "insufficient_funds":
        print("Suggest different card")
    elif exc.decline_type == "expired_card":
        print("Ask to update expiry")
```

### Storing the Causing Exception (Wrapping)

```python
class ConfigError(Exception):
    """Failed to load configuration."""

    def __init__(self, path, cause=None):
        self.path = path
        self.cause = cause  # store original exception for inspection
        msg = f"failed to load config from {path!r}"
        if cause:
            msg += f": {cause}"
        super().__init__(msg)

# Wrapping a lower-level error with domain context
def load_config(path):
    try:
        with open(path) as f:
            import json
            return json.load(f)
    except FileNotFoundError as exc:
        raise ConfigError(path, cause=exc) from exc  # chaining — see 06.4
    except PermissionError as exc:
        raise ConfigError(path, cause=exc) from exc
    except ValueError as exc:  # json.JSONDecodeError is a ValueError subclass
        raise ConfigError(path, cause=exc) from exc

try:
    load_config("/missing/config.json")
except ConfigError as exc:
    print(f"Config error: {exc}")
    print(f"Path: {exc.path}")
    print(f"Cause: {exc.cause!r}")
    print(f"Chained cause (__cause__): {exc.__cause__!r}")
```

## Hierarchy Design — Flat vs Deep

### When to Create a Hierarchy vs a Single Exception

```python
# OPTION A: Flat — one exception per failure mode, all siblings
# Good when: few failure modes, or modes are unrelated
class AppError(Exception): pass
class NotFoundError(AppError): pass
class PermissionDeniedError(AppError): pass
class RateLimitError(AppError): pass

# OPTION B: Hierarchical — groups by category
# Good when: callers want to handle categories broadly OR specifically
class AppError(Exception):
    """Base for all app errors."""
    pass

class StorageError(AppError):
    """Any storage-layer failure."""
    pass

class NotFoundError(StorageError):
    """Entity not found."""
    def __init__(self, entity_type, entity_id):
        self.entity_type = entity_type
        self.entity_id = entity_id
        super().__init__(f"{entity_type} {entity_id!r} not found")

class PermissionDeniedError(StorageError):
    """Access denied."""
    def __init__(self, resource, action, principal):
        self.resource = resource
        self.action = action
        self.principal = principal
        super().__init__(f"{principal!r} cannot {action} {resource!r}")

class NetworkError(AppError):
    """Network-related failures."""
    pass

class TimeoutError(NetworkError):  # careful: shadows built-in TimeoutError — see below
    pass

class ConnectionFailedError(NetworkError):
    pass

# Caller can choose granularity:
try:
    fetch_user("123")
except NotFoundError as exc:
    print(f"Specific: {exc}")  # only missing entities

try:
    fetch_user("123")
except StorageError as exc:
    print(f"Any storage problem: {exc}")  # catches NotFoundError + PermissionDeniedError

try:
    fetch_user("123")
except AppError as exc:
    print(f"Any app problem: {exc}")  # catches everything in the app hierarchy
```

**Guidance — how deep?**

| Depth | When to use | Example |
|-------|-------------|---------|
| 1 level (flat under AppError) | < 5 exceptions, no natural grouping | Small script, CLI tool |
| 2 levels (category -> specific) | Natural categories exist, callers need both granular and broad handling | Web service (Storage, Network, Validation) |
| 3+ levels | Large framework/library with many error types | ORM, cloud SDK, compiler |

> **Preferred:** Start flat, add hierarchy when you see callers writing `except (A, B, C):` repeatedly — that's a missing parent category.

### Naming Conventions

```python
# PEP 8: exception names should end with "Error" (or "Exception" / "Warning")
# Good
class ValidationError(Exception): pass
class InsufficientFundsError(Exception): pass
class PaymentFailedError(Exception): pass

# Also acceptable — "Exception" suffix for broader base classes
class PaymentException(Exception): pass
class AppException(Exception): pass

# Avoid — no suffix, unclear it's an exception
class BadPayment(Exception): pass      # confusing
class InvalidInput(Exception): pass    # ambiguous vs regular class

# Avoid shadowing built-ins unless you INTEND to extend them
class TimeoutError(Exception): pass  # shadows builtins.TimeoutError — confusing!
# Better: domain-qualify
class PaymentTimeoutError(Exception): pass
class RequestTimeoutError(TimeoutError):  # OK if intentionally subclassing built-in
    pass
```

### Inheriting from Built-in vs Pure Custom

```python
# Subclassing a built-in — useful when your error IS-A built-in error
class NegativeAgeError(ValueError):
    """Age cannot be negative — is a ValueError."""
    def __init__(self, age):
        self.age = age
        super().__init__(f"age cannot be negative, got {age}")

class EmptyNameError(ValueError):
    """Name cannot be empty."""
    pass

# Now generic ValueError handlers also catch your domain errors:
def set_age(age):
    if age < 0:
        raise NegativeAgeError(age)
    if not isinstance(age, int):
        raise TypeError("age must be int")

try:
    set_age(-5)
except ValueError as exc:  # catches NegativeAgeError AND built-in ValueError
    print(f"Bad value: {exc} (type: {type(exc).__name__})")

# But specific handlers can still distinguish:
try:
    set_age(-5)
except NegativeAgeError as exc:
    print(f"Specific: age {exc.age} is negative — show age field error")
except ValueError as exc:
    print(f"Generic value error: {exc}")

# When NOT to subclass built-in — your error is NOT a ValueError/TypeError
class InsufficientFundsError(Exception):  # NOT ValueError — it's a business rule, not a bad value
    pass

# Misleading if you do:
class InsufficientFundsErrorAsValue(ValueError):  # implies "you passed a bad value" — not quite right
    pass
```

**Decision framework:**

| Question | If yes | If no |
|----------|--------|-------|
| Would a generic `except ValueError` handler correctly handle your error? | Subclass `ValueError` | Subclass `Exception` directly |
| Is your error fundamentally "wrong type"? | Subclass `TypeError` | Don't |
| Is your error "missing resource"? | Subclass `LookupError` or `FileNotFoundError` | Don't |
| Is it a domain/business rule? | Usually `Exception` or domain base like `AppError` | — |

## Complete Domain Example — E-Commerce Order System

```python
"""Domain exception hierarchy for an e-commerce system."""

from __future__ import annotations
from dataclasses import dataclass

# ── Base ──────────────────────────────────────────────────────────
class ShopError(Exception):
    """Base for all shop domain errors."""
    pass

# ── Validation (subclass ValueError for interop) ──────────────────
class ValidationError(ShopError, ValueError):
    """Input failed validation."""
    pass

class InvalidQuantityError(ValidationError):
    def __init__(self, product_id: str, quantity: int, reason: str = ""):
        self.product_id = product_id
        self.quantity = quantity
        self.reason = reason
        msg = f"invalid quantity {quantity} for product {product_id!r}"
        if reason:
            msg += f": {reason}"
        super().__init__(msg)

class InvalidCouponError(ValidationError):
    def __init__(self, coupon_code: str, reason: str):
        self.coupon_code = coupon_code
        self.reason = reason
        super().__init__(f"coupon {coupon_code!r} invalid: {reason}")

# ── Inventory ─────────────────────────────────────────────────────
class InventoryError(ShopError):
    """Inventory-related failure."""
    pass

class OutOfStockError(InventoryError):
    def __init__(self, product_id: str, requested: int, available: int):
        self.product_id = product_id
        self.requested = requested
        self.available = available
        super().__init__(
            f"product {product_id!r} out of stock: "
            f"requested {requested}, available {available}"
        )

class ProductNotFoundError(InventoryError, LookupError):
    """Also a LookupError so generic lookup handlers catch it."""
    def __init__(self, product_id: str):
        self.product_id = product_id
        super().__init__(f"product {product_id!r} not found")

# ── Payment ───────────────────────────────────────────────────────
class PaymentError(ShopError):
    """Payment processing failed."""
    pass

class InsufficientFundsError(PaymentError):
    def __init__(self, account_id: str, balance: float, required: float):
        self.account_id = account_id
        self.balance = balance
        self.required = required
        self.deficit = required - balance
        super().__init__(
            f"account {account_id!r}: balance ${balance:.2f} < required ${required:.2f} "
            f"(deficit ${self.deficit:.2f})"
        )

class CardDeclinedError(PaymentError):
    def __init__(self, last4: str, code: str, message: str):
        self.last4 = last4
        self.code = code
        self.message = message
        super().__init__(f"card *{last4} declined [{code}]: {message}")

# ── Order ─────────────────────────────────────────────────────────
class OrderError(ShopError):
    pass

class OrderAlreadyPlacedError(OrderError):
    def __init__(self, order_id: str):
        self.order_id = order_id
        super().__init__(f"order {order_id!r} already placed — cannot modify")

# ── Usage ─────────────────────────────────────────────────────────
def place_order(product_id: str, quantity: int, account_id: str, coupon: str | None = None):
    # Validation
    if quantity <= 0:
        raise InvalidQuantityError(product_id, quantity, "must be positive")
    if quantity > 100:
        raise InvalidQuantityError(product_id, quantity, "max 100 per order")

    # Coupon check
    if coupon and coupon != "SAVE10":
        raise InvalidCouponError(coupon, "unknown coupon code")

    # Inventory check (simulated)
    inventory = {"widget": 5, "gadget": 0}
    if product_id not in inventory:
        raise ProductNotFoundError(product_id)
    if inventory[product_id] < quantity:
        raise OutOfStockError(product_id, quantity, inventory[product_id])

    # Payment (simulated)
    balances = {"acc-1": 20.0}
    price = 10.0 * quantity
    if coupon == "SAVE10":
        price *= 0.9
    balance = balances.get(account_id, 0)
    if balance < price:
        raise InsufficientFundsError(account_id, balance, price)

    return {"order_id": "ORD-001", "total": price}

# ── Handling at different granularities ───────────────────────────
test_cases = [
    ("widget", -1, "acc-1", None),       # InvalidQuantity
    ("widget", 10, "acc-1", None),       # OutOfStock
    ("nonexistent", 1, "acc-1", None),   # ProductNotFound
    ("widget", 3, "acc-1", None),        # InsufficientFunds (30 > 20)
    ("widget", 1, "acc-1", "BADCODE"),   # InvalidCoupon
    ("widget", 1, "acc-1", "SAVE10"),    # Success (9.0 <= 20)
]

for args in test_cases:
    try:
        order = place_order(*args)
    except InvalidQuantityError as exc:
        print(f"[validation] {exc} (qty={exc.quantity})")
    except InvalidCouponError as exc:
        print(f"[coupon] {exc} (code={exc.coupon_code!r})")
    except ProductNotFoundError as exc:
        print(f"[not found] {exc}")
        # Also caught by LookupError handlers elsewhere:
        assert isinstance(exc, LookupError)
    except OutOfStockError as exc:
        print(f"[stock] {exc} — available={exc.available}")
    except InsufficientFundsError as exc:
        print(f"[payment] {exc} — deficit=${exc.deficit:.2f}")
    except ValidationError as exc:
        print(f"[any validation] {exc}")
    except InventoryError as exc:
        print(f"[any inventory] {exc}")
    except ShopError as exc:
        print(f"[any shop error] {exc}")
    else:
        print(f"[success] {order}")
```

**Explanation:** The hierarchy lets each layer choose its precision. The checkout UI might catch `InvalidQuantityError` to highlight the quantity field, while a top-level handler catches `ShopError` to return a 400 response. The `LookupError` mixin on `ProductNotFoundError` means generic "not found" infrastructure also handles it.

## Best Practices and Common Mistakes

### Practice 1: Always Pass a Message to super().__init__

```python
# BAD — str(exc) is empty, logs show nothing
class MyError(Exception):
    def __init__(self, code):
        self.code = code
        # forgot super().__init__

try:
    raise MyError(42)
except MyError as exc:
    print(f"str: '{str(exc)}'")  # '' — empty!
    print(f"args: {exc.args}")   # () — no message

# GOOD
class MyErrorFixed(Exception):
    def __init__(self, code, message=None):
        self.code = code
        super().__init__(message or f"error code {code}")

try:
    raise MyErrorFixed(42)
except MyErrorFixed as exc:
    print(f"str: '{str(exc)}'")  # 'error code 42'
```

### Practice 2: Don't Over-Engineer — Use Dataclasses for Data-Heavy Exceptions

```python
from dataclasses import dataclass

@dataclass
class ApiError(Exception):
    """Exception as dataclass — auto-generates __init__, __repr__, __eq__."""
    status_code: int
    url: str
    body: str = ""

    def __str__(self):
        return f"API {self.status_code} for {self.url}: {self.body[:100]}"

# Note: dataclass Exception needs care — Exception.__init__ expects *args
# The dataclass __init__ will set attributes but NOT populate .args
# Fix: explicitly set args or override __init__

@dataclass
class ApiErrorFixed(Exception):
    status_code: int
    url: str
    body: str = ""

    def __post_init__(self):
        # Populate Exception's args for correct str/repr/traceback
        super().__init__(f"API {self.status_code} for {self.url}: {self.body[:100]}")

try:
    raise ApiErrorFixed(404, "https://api.example.com/users/123", "Not Found")
except ApiErrorFixed as exc:
    print(str(exc))
    print(f"status: {exc.status_code}")
    print(f"args: {exc.args}")

# Alternative — don't use @dataclass, write explicit __init__ (often clearer for exceptions)
```

> **Recommendation:** For most exceptions, explicit `__init__` is clearer than dataclass magic. Use dataclasses only when you have many data fields and equality testing matters.

### Practice 3: Document What You Raise

```python
def withdraw(account, amount: float) -> float:
    """Withdraw amount from account.

    Args:
        account: Account to debit.
        amount: Positive amount to withdraw.

    Returns:
        New balance.

    Raises:
        InvalidAmountError: If amount <= 0 or not a number.
        AccountFrozenError: If account is frozen.
        InsufficientFundsError: If balance < amount. Inspect .deficit for shortfall.
    """
    ...
```

### Practice 4: Provide Both Specific and Category Bases

```python
# Library design — expose both for flexibility
# mylib/errors.py
class MyLibError(Exception):
    """Base for all mylib errors — catch this for any mylib failure."""
    pass

class MyLibValueError(MyLibError, ValueError):
    """A ValueError from mylib — also caught by 'except ValueError'."""
    pass

# User can choose:
#   except MyLibError: — any mylib problem
#   except ValueError: — any value problem (including yours)
#   except MyLibValueError: — specifically your value problem
```

### Mistake 1: Creating an Exception for Every Little Case

```python
# OVER-ENGINEERED — don't create exceptions you'd never handle differently
class NameTooShortError(ValueError): pass
class NameTooLongError(ValueError): pass
class NameContainsDigitsError(ValueError): pass
class NameContainsSpecialCharsError(ValueError): pass

# Caller will just do:
#   except ValueError: print("bad name")
# So a single ValidationError with a message/reason field is better:

class InvalidNameError(ValueError):
    def __init__(self, name, reason):
        self.name = name
        self.reason = reason
        super().__init__(f"invalid name {name!r}: {reason}")

# Now caller CAN distinguish if needed, but doesn't have to:
try:
    validate_name("Jo123")
except InvalidNameError as exc:
    if exc.reason == "contains_digits":
        print("Remove digits")
    else:
        print(f"Bad name: {exc.reason}")
```

**Heuristic:** Create a new exception type when callers need to *handle it differently* (different except branch). If they'd handle two failures the same way, one type with a reason field suffices.

### Mistake 2: Forgetting That Exceptions Are Part of Your Public API

```python
# Exceptions are API — renaming/removing them is a breaking change
# mylib/__init__.py
from .errors import MyLibError, ValidationError, NotFoundError

__all__ = ["MyLibError", "ValidationError", "NotFoundError"]
# Document them, don't expose internal exception names casually
```

### Mistake 3: Raising Generic Exception

```python
# BAD — 'Exception' is too generic; caller can't distinguish your error
raise Exception("something went wrong in checkout")

# GOOD — specific type
raise CheckoutError("payment gateway timeout after 30s")

# Also bad — raising string (Python 2 leftover, now TypeError)
# raise "error"  # TypeError: exceptions must derive from BaseException
```

## Quick Decision Checklist

| Question | Action |
|----------|--------|
| Should I create a custom exception? | Yes if caller needs to handle it differently from built-ins, or you need structured data, or you want semantic API. |
| What should it inherit from? | `Exception` (or domain base -> `Exception`). Subclass built-in only if IS-A relationship holds. |
| How to store context? | Attributes + `super().__init__(message)`. Single message string in `.args[0]`. |
| Flat or hierarchical? | Start flat; add parent categories when you see repeated `except (A, B, C)`. |
| Naming? | End with `Error` or `Exception`. Domain-qualify to avoid shadowing built-ins. |
| Dataclass? | Usually no — explicit `__init__` is clearer. Use dataclass only for data-heavy cases and fix `.args`. |
| How many types? | One per *handling branch*, not per validation rule. Use a reason/code field for variants handled uniformly. |

---

## Summary

- Subclass **`Exception`** (never `BaseException`), name with `Error` suffix.
- Call **`super().__init__(message)`** so `str(exc)` and traceback display work; store structured data in attributes for programmatic handling.
- Design a **shallow hierarchy** first (`AppError` -> specific errors); add intermediate categories when callers need broad handling.
- **Subclass built-ins** (`ValueError`, `LookupError`) only when your error genuinely *is* that kind of error — it determines whether generic handlers catch you.
- One exception type per **distinct handling path**; use fields/codes for variants that are handled the same way.
- Exceptions are **public API** — document them in docstrings, export them intentionally, and treat renames as breaking changes.
