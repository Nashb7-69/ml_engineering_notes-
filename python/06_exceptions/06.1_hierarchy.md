# 06.1 Exception Hierarchy: BaseException, Exception, and Built-in Types

Python's exception system is not a flat bag of error names — it is a carefully designed class hierarchy rooted in `BaseException`. Understanding that hierarchy is essential for writing correct `except` clauses, for deciding what to catch and what to let propagate, and for designing your own exceptions that play well with the ecosystem.

## Why a Hierarchy at All?

In many languages, errors are just integers or strings. Python makes every exception an *object* — an instance of a class — so you can:

1. **Catch by category.** `except LookupError` catches both `KeyError` and `IndexError` without listing them separately.
2. **Attach structured data.** An exception can carry attributes beyond a message.
3. **Distinguish fatal signals from recoverable errors.** `SystemExit` and `KeyboardInterrupt` are not ordinary bugs.

> **Mental model:** Think of the hierarchy as a taxonomy of *failure modes*. The higher you catch, the broader the net. The lower you catch, the more precise your handling.

---

## The Root: BaseException

Every exception in Python inherits — directly or indirectly — from `BaseException`.

```
BaseException
 ├── SystemExit          # interpreter exit request
 ├── KeyboardInterrupt   # Ctrl+C / SIGINT
 ├── GeneratorExit       # generator.close() signal
 └── Exception           # <-- almost everything else
      ├── StopIteration, StopAsyncIteration
      ├── ArithmeticError, LookupError, ...
      └── ...
```

`BaseException` itself is deliberately minimal:

```python
# What BaseException gives you
try:
    raise BaseException("raw base")
except BaseException as exc:
    print(type(exc))       # <class 'BaseException'>
    print(exc.args)        # ('raw base',)
    print(str(exc))        # 'raw base'
```

**Explanation:** `BaseException` stores its constructor arguments in `.args` (a tuple) and uses the first arg for `str(exc)`. You will almost never raise or catch it directly.

### The Three Outsiders: Children of BaseException That Are *Not* Exception

| Class | Raised by | Meaning | Should you catch it? |
|-------|-----------|---------|----------------------|
| `SystemExit` | `sys.exit()`, interpreter shutdown | Request to terminate the process. Carries `code`. | Almost never. Let it propagate — or catch only to clean up and re-raise. |
| `KeyboardInterrupt` | SIGINT (Ctrl+C), `raise KeyboardInterrupt` | User asked to interrupt. | Almost never. If you catch it, you prevent Ctrl+C from working. |
| `GeneratorExit` | `generator.close()` | Generator is being garbage-collected / closed. | Never in normal code; only inside generators needing cleanup. |

```python
import sys

# SystemExit is NOT an Exception
try:
    sys.exit(42)
except Exception:
    print("This will NOT print — SystemExit is not an Exception")

try:
    sys.exit(42)
except BaseException as exc:
    print(f"Caught BaseException: {exc!r}, code={exc.code}")
    # If you catch it and don't re-raise, the process WON'T exit!
    raise  # re-raise to actually exit
```

**Explanation:** The first `except Exception` block does not fire because `SystemExit` bypasses it. The second shows that catching `BaseException` *does* intercept it — but suppressing it silently would be a bug: the program would keep running when the caller explicitly asked to exit.

```python
# KeyboardInterrupt demo — don't do this in production!
try:
    # imagine a long-running loop
    raise KeyboardInterrupt("user pressed Ctrl+C")
except Exception:
    print("Exception handler missed KeyboardInterrupt")
except BaseException:
    print("BaseException handler caught it")
```

> **Rule of thumb:** If you write `except Exception:`, you *intentionally exclude* `SystemExit`, `KeyboardInterrupt`, and `GeneratorExit`. That is almost always what you want.

## The Workhorse: Exception

Everything you normally raise and catch descends from `Exception`. Its direct children include several *abstract* category exceptions and a few concrete ones:

```
BaseException

      ├── ArithmeticError
      │    ├── FloatingPointError
      │    ├── OverflowError
      │    └── ZeroDivisionError
      ├── AssertionError
      ├── AttributeError
      ├── BufferError
      ├── EOFError
      ├── ImportError
      │    └── ModuleNotFoundError   (3.6+, subclass of ImportError)
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── MemoryError
      ├── NameError
      │    └── UnboundLocalError
      ├── OSError  (aliases: IOError, EnvironmentError)
      │    ├── BlockingIOError
      │    ├── ChildProcessError
      │    ├── ConnectionError
      │    │    ├── BrokenPipeError
      │    │    ├── ConnectionAbortedError
      │    │    ├── ConnectionRefusedError
      │    │    └── ConnectionResetError
      │    ├── FileExistsError
      │    ├── FileNotFoundError
      │    ├── InterruptedError
      │    ├── IsADirectoryError
      │    ├── NotADirectoryError
      │    ├── PermissionError
      │    ├── ProcessLookupError
      │    └── TimeoutError
      ├── ReferenceError
      ├── RuntimeError
      │    ├── NotImplementedError
      │    └── RecursionError
      ├── StopIteration
      ├── StopAsyncIteration

      │    └── IndentationError
      │         └── TabError
      ├── SystemError

      │         └── UnicodeTranslateError
      ├── Warning  (and its many subclasses — not errors)
      └── ExceptionGroup / BaseExceptionGroup  (3.11+)
```

You can introspect this at runtime:

```python
def print_hierarchy(cls, indent=0):
    print("  " * indent + cls.__name__)
    for sub in sorted(cls.__subclasses__(), key=lambda c: c.__name__):
        print_hierarchy(sub, indent + 1)

print_hierarchy(BaseException)
```

**Explanation:** `__subclasses__()` returns direct children at runtime. Note that dynamically created subclasses also appear — the hierarchy is open.

## The Most Common Built-in Exceptions — When Python Raises Them

### ValueError vs TypeError — The Classic Confusion

| Exception | Meaning | Example that triggers it |
|-----------|---------|--------------------------|
| `TypeError` | Wrong *type* — operation is meaningless for this type | `"a" + 5`, `len(5)`, `def f(a,b): ...; f(1)` |
| `ValueError` | Right type, wrong *value* | `int("hello")`, `int("3.14")` fails, `["a","b"].remove("c")` |

```python
# TypeError: operation not defined for these types
try:
    result = "age: " + 30
except TypeError as exc:
    print(f"TypeError: {exc}")  # can only concatenate str (not "int") to str

# ValueError: type is correct (str), but content is not convertible
try:
    n = int("not-a-number")
except ValueError as exc:
    print(f"ValueError: {exc}")  # invalid literal for int() with base 10

# Subtle distinction:
try:
    # Both are str, but "%" formatting expects specific placeholders
    "hello %s %s" % ("only-one",)
except TypeError as exc:
    print(f"TypeError (arg count): {exc}")

try:
    int("  12  ")   # OK — whitespace is allowed
    int("12.5")    # ValueError — decimal point not allowed for int()
except ValueError as exc:
    print(f"ValueError: {exc}")
```

**Python difference vs other languages:** Python *never* coerces silently where the type is wrong. JavaScript would produce `"age: 30"` or `NaN`; Python raises `TypeError`/`ValueError` immediately. This is deliberate — explicit failure over silent corruption.

### LookupError Family

```python
# LookupError is the common parent of KeyError and IndexError
mapping = {"a": 1}
sequence = [10, 20, 30]

try:
    mapping["missing"]
except LookupError as exc:
    print(f"LookupError caught KeyError: {exc!r}")
    # KeyError stores the missing key as args[0]
    print(f"Missing key: {exc.args[0]}")

try:
    sequence[99]
except LookupError as exc:
    print(f"LookupError caught IndexError: {exc}")

# Catching the parent is useful for "any lookup failed" logic:
def get_nested(data, keys):
    try:
        for k in keys:
            data = data[k]
        return data
    except LookupError as exc:
        print(f"Path failed at {k!r}: {exc}")
        return None

print(get_nested({"a": {"b": [1, 2]}}, ["a", "b", 5]))  # IndexError path
print(get_nested({"a": {"b": [1, 2]}}, ["a", "missing"]))  # KeyError path
```

**Subtlety — KeyError's display:**

```python
try:
    {}["key"]
except KeyError as exc:
    print(str(exc))   # "'key'" — note the quotes, from repr of the key
    print(exc.args[0])  # 'key' — raw key without extra quoting
```

If you log `str(exc)` you get quoted keys; use `exc.args[0]` if you need the raw value.

### ArithmeticError Family

```python
try:
    1 / 0
except ArithmeticError as exc:
    print(f"ArithmeticError: {exc}")  # catches ZeroDivisionError
    print(isinstance(exc, ZeroDivisionError))  # True

try:
    import math
    math.exp(1000)  # may raise OverflowError on some platforms
except OverflowError as exc:
    print(f"Overflow: {exc}")

# FloatingPointError is DISABLED by default — need fpectl
import math
try:
    math.sqrt(-1)  # raises ValueError, not FloatingPointError
except ValueError as exc:
    print(f"ValueError for math domain: {exc}")
```

### OSError Family (The IO Workhorse)

Since Python 3.3, all IO-related errors are `OSError` subclasses and carry useful attributes:

```python
import errno
import os

try:
    open("/nonexistent/path/file.txt")
except OSError as exc:
    print(f"errno: {exc.errno} ({errno.errorcode.get(exc.errno)})")
    print(f"strerror: {exc.strerror}")
    print(f"filename: {exc.filename}")
    print(f"filename2: {exc.filename2}")  # for rename etc.
    print(f"Is FileNotFoundError? {isinstance(exc, FileNotFoundError)}")
    print(f"Is OSError? {isinstance(exc, OSError)}")  # True — parent catches child

# Specific subclass handling — order matters (most specific first):
try:
    os.mkdir("/tmp")  # already exists on most systems
except FileExistsError:
    print("File exists — maybe OK to ignore")
except PermissionError:
    print("No permission")
except OSError as exc:
    print(f"Other OS error: {exc}")
```

**Explanation:** `OSError` instances expose `.errno`, `.strerror`, `.filename`. Catching `OSError` catches *all* file/network/permission failures — useful for broad IO handling. But catching `FileNotFoundError` specifically lets you distinguish "file missing" from "permission denied".

### NameError, AttributeError, ImportError

```python
# NameError — name not found in any scope
try:
    print(undefined_variable)
except NameError as exc:
    print(f"NameError: {exc}")

# UnboundLocalError — subtle subclass of NameError
def tricky():
    print(x)  # Python sees 'x = ...' below, so x is local throughout
    x = 10

try:
    tricky()
except UnboundLocalError as exc:
    print(f"UnboundLocalError: {exc}")
    print(f"Also NameError? {isinstance(exc, NameError)}")  # True

# AttributeError
try:
    s = "hello"
    s.push("x")  # str has no push
except AttributeError as exc:
    print(f"AttributeError: {exc}")
    # Python 3.10+ adds .obj and .name attributes:
    if hasattr(exc, 'obj'):
        print(f"obj: {exc.obj!r}, name: {exc.name!r}")

# ImportError vs ModuleNotFoundError
try:
    import definitely_missing_module_xyz
except ModuleNotFoundError as exc:
    print(f"ModuleNotFoundError: {exc} (subclass of ImportError: {isinstance(exc, ImportError)})")
    print(f"Missing name: {exc.name}")

try:
    from math import definitely_missing_name
except ImportError as exc:
    print(f"ImportError: {exc}")
    print(f"name: {exc.name}, path: {exc.path}")
```

**Distinction:**

| Situation | Exception |
|-----------|-----------|
| `import no_such_module` | `ModuleNotFoundError` |
| `from pkg import no_such_name` | `ImportError` |
| Circular import failing at runtime | `ImportError` |

### RuntimeError, StopIteration, and Friends

```python
# RuntimeError — generic "something went wrong that doesn't fit other categories"
# NotImplementedError — subclass of RuntimeError for abstract methods
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        raise NotImplementedError("Subclasses must implement area()")

# RecursionError — subclass of RuntimeError
try:
    def recurse():
        return recurse()
    recurse()
except RecursionError as exc:
    print(f"Recursion limit hit: {exc}")

# StopIteration — NEVER catch this casually; it controls iteration
def gen():
    yield 1
    yield 2

it = iter(gen())
try:
    while True:
        print(next(it))
except StopIteration:
    print("Iterator exhausted — this is normal loop termination, not an error")

# Since Python 3.7, StopIteration escaping a generator becomes RuntimeError
def bad_gen():
    yield 1
    raise StopIteration("oops")  # don't do this

try:
    list(bad_gen())
except RuntimeError as exc:
    print(f"StopIteration inside generator -> RuntimeError: {exc}")
    print(f"__cause__: {exc.__cause__}")
```

### SyntaxError and Friends (Compile-time)

```python
# SyntaxError is raised at parse/compile time, not at runtime in the same file
# You trigger it via eval/exec/compile or import of bad file
try:
    compile("x = 1 + ", "<string>", "exec")
except SyntaxError as exc:
    print(f"SyntaxError: {exc}")
    print(f"  filename: {exc.filename}")
    print(f"  lineno: {exc.lineno}, offset: {exc.offset}")
    print(f"  text: {exc.text!r}")
    print(f"  msg: {exc.msg}")

try:
    compile("x = \t  y", "<string>", "exec")  # inconsistent tabs/spaces
except TabError as exc:
    print(f"TabError (subclass of IndentationError -> SyntaxError): {exc}")
```

### Warning Hierarchy (Not Errors, But Part of the Tree)

`Warning` is *not* an error — it inherits from `Exception`, but the `warnings` module does not raise it by default; it *emits* it.

```python
import warnings

# Warnings don't interrupt control flow unless configured to
warnings.warn("deprecated API", DeprecationWarning)
print("This still prints — warning didn't raise")

# Turn warnings into errors:
warnings.filterwarnings("error", category=DeprecationWarning)
try:
    warnings.warn("now it's an error", DeprecationWarning)
except DeprecationWarning as exc:
    print(f"Warning as exception: {exc}")
finally:
    warnings.resetwarnings()
```

## What to Catch — The Cardinal Rules

### Rule 1: Never Use Bare `except:`

```python
# ANTI-PATTERN — bare except catches BaseException including SystemExit and KeyboardInterrupt
try:
    risky()
except:  # bare!
    print("Caught everything — even Ctrl+C and sys.exit()!")
    # Also catches SyntaxError, MemoryError, and hides bugs
    # Linters (flake8, ruff) flag this as E722

# What you almost certainly meant:
try:
    risky()
except Exception as exc:  # catches all *regular* exceptions, not the outsiders
    print(f"Caught regular exception: {exc}")
```

**Why bare `except:` is dangerous — a realistic horror story:**

```python
import sys

def process_file(path):
    try:
        data = open(path).read()
        return data.strip()
    except:  # bare — catches everything
        # Developer intended to handle "file not found"
        # but also suppresses KeyboardInterrupt, SystemExit, and even typos
        print("Something went wrong, returning empty")
        return ""

# User hits Ctrl+C during open — program ignores it and returns ""!
# sys.exit() inside risky() is swallowed — program doesn't exit!
# A NameError from a typo (e.g., 'stripp' instead of 'strip') is silently hidden!
```

**Equivalent explicit forms:**

| Code | Catches | Equivalent to |
|------|---------|---------------|
| `except:` | `BaseException` | `except BaseException:` |
| `except Exception:` | All regular errors | Excludes `SystemExit`, `KeyboardInterrupt`, `GeneratorExit` |
| `except BaseException:` | Everything | Same as bare, but explicit and intentional |

> **Pythonic idiom:** If you *must* catch everything (e.g., a top-level crash handler that logs and re-raises), write `except BaseException as exc:` explicitly and document why. Bare `except:` should never appear in reviewed code.

### Rule 2: Be As Specific As Possible

```python
# Too broad — masks bugs
try:
    user = db.get_user(user_id)
    send_email(user.email, template.render(user=user))
except Exception:
    print("Something failed")  # Was it DB? Template? Email? Who knows!

# Specific — each failure mode handled appropriately
try:
    user = db.get_user(user_id)
except LookupError as exc:
    print(f"User {user_id} not found: {exc}")
    # handle missing user

try:
    body = template.render(user=user)
except (AttributeError, KeyError, ValueError) as exc:
    print(f"Template error: {exc}")
    body = fallback_template.render(user=user)

try:
    send_email(user.email, body)
except (ConnectionError, TimeoutError) as exc:
    print(f"Email failed, will retry: {exc}")
    queue_for_retry(user, body)
```

### Rule 3: Order Matters — Specific Before General

```python
# WRONG — general handler shadows specific ones (linter warns: unreachable code)
try:
    open("data.csv")
except OSError:
    print("Any OS error")
except FileNotFoundError:  # NEVER REACHED — FileNotFoundError is an OSError
    print("File not found")

# CORRECT — most specific first
try:
    open("data.csv")
except FileNotFoundError as exc:
    print(f"File missing: {exc.filename}")
except PermissionError as exc:
    print(f"Permission denied: {exc.filename}")
except IsADirectoryError as exc:
    print(f"Expected file, got directory: {exc.filename}")
except OSError as exc:
    print(f"Other OS error [{exc.errno}]: {exc.strerror}")
```

## Inspecting Exceptions Programmatically

```python
# The args tuple and attributes
try:
    raise ValueError("bad value", 42, {"extra": "data"})
except ValueError as exc:
    print(f"args: {exc.args}")        # ('bad value', 42, {'extra': 'data'})
    print(f"str: {str(exc)}")         # "('bad value', 42, {'extra': 'data'})" — tuple repr!
    print(f"first arg: {exc.args[0]}")

# Single-arg convention — most code expects exc.args[0] to be the message
try:
    raise ValueError("bad value for 'age': -5 is not positive")
except ValueError as exc:
    print(str(exc))       # 'bad value for 'age': -5 is not positive'
    print(exc.args[0])    # same

# Programmatic hierarchy checks
exc = FileNotFoundError(2, "No such file", "missing.txt")
print(isinstance(exc, OSError))       # True
print(isinstance(exc, FileNotFoundError))  # True
print(issubclass(FileNotFoundError, OSError))  # True
print(type(exc).__mro__)
# (<class 'FileNotFoundError'>, <class 'OSError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
```

## ExceptionGroup and BaseExceptionGroup (Python 3.11+)

Traditional exceptions represent a *single* failure. `ExceptionGroup` (and `BaseExceptionGroup`) represent *multiple* failures happening concurrently — essential for `asyncio.TaskGroup`, structured concurrency, and parallel validation.

```python
import sys

if sys.version_info >= (3, 11):
    # Creating an ExceptionGroup — multiple exceptions bundled together
    try:
        raise ExceptionGroup("validation failed", [
            ValueError("age must be >= 0"),
            TypeError("name must be str"),
            FileNotFoundError("config.toml not found"),
        ])
    except ExceptionGroup as eg:
        print(f"Group message: {eg.message}")
        print(f"Number of sub-exceptions: {len(eg.exceptions)}")
        for sub in eg.exceptions:
            print(f"  - {type(sub).__name__}: {sub}")

    # ExceptionGroup IS an Exception — caught by except Exception
    try:
        raise ExceptionGroup("oops", [ValueError("a"), ValueError("b")])
    except Exception as exc:
        print(f"Caught group via Exception: {type(exc).__name__}")

    # BaseExceptionGroup can contain BaseExceptions (e.g., KeyboardInterrupt)
    try:
        raise BaseExceptionGroup("mixed", [
            ValueError("regular"),
            KeyboardInterrupt("interrupt"),
        ])
    except BaseExceptionGroup as beg:
        print(f"Base group: {beg.message}")
    except BaseException:
        print("Caught via BaseException")

    # except* — the new syntax for handling groups (see 06.4 for detail)
    try:
        raise ExceptionGroup("multiple", [
            ValueError("bad value 1"),
            TypeError("bad type"),
            ValueError("bad value 2"),
        ])
    except* ValueError as eg:
        print(f"Caught ValueErrors: {[str(e) for e in eg.exceptions]}")
    except* TypeError as eg:
        print(f"Caught TypeErrors: {[str(e) for e in eg.exceptions]}")
else:
    print("ExceptionGroup requires Python 3.11+")

# Polyfill awareness — on 3.10 and below, you can use the 'exceptiongroup' backport:
#   pip install exceptiongroup
#   from exceptiongroup import ExceptionGroup, BaseExceptionGroup
```

**Key properties:**

| Property | Value |
|----------|-------|
| Inherits from | `ExceptionGroup(Exception)`, `BaseExceptionGroup(BaseException)` |
| Caught by `except Exception`? | `ExceptionGroup` yes, `BaseExceptionGroup` only by `except BaseException` |
| Attributes | `.message` (str), `.exceptions` (tuple of sub-exceptions), `.args` |
| Nesting | Groups can contain other groups -> tree structure; `.exceptions` may include groups |
| Traceback | Group has its own traceback; sub-exceptions have theirs |

> **When to care now:** Even if you don't use Python 3.11+, be aware that `except Exception` will catch `ExceptionGroup` (it's a subclass). If a library raises one, your handler will fire — but `str(exc)` won't show sub-exception details the way you expect. Check `isinstance(exc, BaseExceptionGroup)` if needed.

## Common Mistakes and How to Avoid Them

### Mistake 1: Catching Too Broadly and Silencing Bugs

```python
# BAD — hides programming errors
def parse_age(s):
    try:
        return int(s)
    except Exception:
        return 0  # Also catches KeyboardInterrupt? No — but catches TypeError from None, etc.

# GOOD — only handle the expected failure
def parse_age_fixed(s):
    try:
        return int(s)
    except (ValueError, TypeError) as exc:
        print(f"Invalid age {s!r}: {exc}")
        return 0

parse_age_fixed(None)   # TypeError — handled explicitly
parse_age_fixed("abc")  # ValueError — handled
# parse_age_fixed still lets KeyboardInterrupt propagate
```

### Mistake 2: Assuming Exception Text Is Stable

```python
# FRAGILE — message text changes across Python versions
try:
    int("xyz")
except ValueError as exc:
    if "invalid literal" in str(exc):
        print("Bad int string")
    # Better: just catch ValueError — don't parse the message

# For OSError, use .errno instead of message parsing:
try:
    open("/nope")
except OSError as exc:
    import errno
    if exc.errno == errno.ENOENT:
        print("File not found — errno is stable, message is not")
```

### Mistake 3: Confusing Warning with Exception

```python
import warnings

# This does NOT raise — it just prints to stderr by default
warnings.warn("careful", UserWarning)
print("Program continues after warn")

# Only if you configure warnings to error does it raise:
warnings.filterwarnings("error")
try:
    warnings.warn("now it raises", UserWarning)
except Warning as exc:  # Warning is an Exception subclass
    print(f"Caught warning as exception: {exc}")
finally:
    warnings.resetwarnings()
```

## Quick Reference Table

| Exception | Parent | Typical Cause |
|-----------|--------|---------------|
| `ValueError` | `Exception` | Correct type, invalid value |
| `TypeError` | `Exception` | Wrong type for operation |
| `KeyError` | `LookupError` | Missing dict key |
| `IndexError` | `LookupError` | Sequence index out of range |
| `AttributeError` | `Exception` | Missing attribute |
| `NameError` / `UnboundLocalError` | `Exception` | Name not defined / local used before assignment |
| `FileNotFoundError` | `OSError` | Path does not exist |
| `PermissionError` | `OSError` | Insufficient permissions |
| `ZeroDivisionError` | `ArithmeticError` | Division by zero |
| `OverflowError` | `ArithmeticError` | Result too large |
| `ImportError` / `ModuleNotFoundError` | `Exception` | Import failure |
| `RuntimeError` / `RecursionError` | `Exception` | Generic runtime / recursion limit |
| `StopIteration` | `Exception` | Iterator exhausted (control flow, not error) |
| `SystemExit` | `BaseException` | `sys.exit()` — do not catch with `Exception` |
| `KeyboardInterrupt` | `BaseException` | Ctrl+C — do not catch with `Exception` |
| `ExceptionGroup` | `Exception` | Multiple errors (3.11+) |

---

## Summary

- **`BaseException`** is the root; **`Exception`** is the root for *regular* errors. Never catch `BaseException` (or bare `except:`) unless you have a specific reason and re-raise.
- The hierarchy groups related errors: `LookupError` -> `KeyError`/`IndexError`, `OSError` -> `FileNotFoundError`/`PermissionError`, `ArithmeticError` -> `ZeroDivisionError`, etc.
- Catch the **most specific** exception you can handle; order `except` clauses from specific to general.
- `ValueError` (right type, wrong value) vs `TypeError` (wrong type) is the most frequently confused pair.
- `OSError` subclasses carry `.errno`, `.strerror`, `.filename` — use them instead of parsing messages.
- `ExceptionGroup` (3.11+) holds *multiple* exceptions; it is an `Exception` subclass, so `except Exception` catches it.
