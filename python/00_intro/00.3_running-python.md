# 00.3 Running Python

Installing Python is not the same as *running* it. The same interpreter can be invoked in half a dozen modes — interactive REPL, script file, module-as-script, piped stdin, shebang-executed program — and each mode sets `sys.path`, `__name__`, and standard streams slightly differently. This lesson makes every mode concrete, shows how the import search path (`PYTHONPATH` / `sys.path`) is built at runtime, and covers the interactive helpers (`help`, `dir`, `_`) that make the REPL a genuinely productive environment rather than a toy calculator.

---

## 1. The Execution Model in One Picture

Every invocation follows the same pipeline:

```
Source text (.py, stdin, or string)
        │
        ▼
  Parse → AST → Compile to bytecode (in memory, optionally cached as .pyc)
        │
        ▼
  Python VM executes bytecode top-to-bottom in a module namespace
        │
        ▼
  Result: side effects, printed output, exit code
```

What changes between modes is *where source text comes from*, *what `__name__` is set to*, and *what directory is placed first on `sys.path`*. Those three details explain most "why does `import` work here but not there?" confusion.

## 2. The REPL — Read, Eval, Print, Loop

### 2.1 Starting It

Run the interpreter with no arguments:

```bash
python3        # or `python`, `py` — whichever you verified in 00.2
```

You get a banner and a prompt:

```
Python 3.12.4 (main, Jun  6 2024, 18:26:44) [GCC 13.2.0] on linux
Type "help", "copyright", "credits" or "license" for more information.
>>> 
```

The triple `>>>` is the *primary prompt* (ready for a new statement). `...` is the *secondary prompt* (inside a block).

```python
>>> 2 + 2
4
>>> x = 10
>>> x * 3
30
>>> for i in range(3):
...     print(i)
... 
0
1
2
```

Each line you type is compiled and executed immediately; expression results are printed via `repr()`, statements produce no automatic output.

The REPL is ideal for:

- Testing a one-liner (`"hello".upper()`, `sorted([3,1,2])`).
- Exploring an unknown API (`dir(requests)`, `help(str.split)`).
- Verifying a fix before editing a file.

It is not where finished code lives — that belongs in `.py` files under version control.

### 2.2 The `_` Family — Last Results

The interactive interpreter stashes recent expression results in special names. These exist *only* in the REPL (and in `python -i`), not in scripts.

```python
>>> 3 + 4
7
>>> _
7
>>> _ * 2
14
>>> "hello".upper()
'HELLO'
>>> _          # now 'HELLO', not 14
'HELLO'
>>> x = 100    # assignment is a statement — _ is NOT updated
>>> _
'HELLO'
>>> 42
42
>>> __
'HELLO'
>>> ___
14
```

Rules:

- `_` — result of the last *expression* that was not `None` and not an assignment. Overwritten on every new expression.
- `__` — second-last, `___` — third-last (CPython convenience; not all REPLs provide these).
- If you assign `_` explicitly (`_ = 5`), you shadow the magic variable until you `del _`.

Common pitfall: naming a variable `_` in scripts for "unused" values is idiomatic, but in the REPL it collides with this feature. Use `__` or `_unused` in the REPL if you need a throwaway name.

```python
# Idiomatic "unused" in scripts:
for _ in range(5):
    print("hello")  # _ signals "loop count unused"

# In the REPL, prefer a different throwaway to avoid shadowing `_`:
for _i in range(3):
    print(_i)
```

In IPython (Section 2.5), the history is richer: `_`, `__`, `___`, plus `Out[1]`, `_1`, etc. — numbered by execution count.

### 2.3 `python -i` — Run a Script, Then Stay Interactive

`python -i` (interactive) runs a script and then drops you into a REPL with the script's globals still alive. Invaluable for post-mortem inspection:

```python
# demo.py
data = [3, 1, 4, 1, 5, 9]
total = sum(data)
print(f"total={total}")
```

```bash
python3 -i demo.py
# total=15
>>> data
[3, 1, 4, 1, 5, 9]
>>> total
15
>>> total / len(data)
3.5
>>> 
```

Without `-i`, the process would exit after printing and you would lose `data` and `total`. With `-i`, you keep the namespace to experiment, plot, or debug.

You can also use `-i` with `-m` and `-c` (see below):

```bash
python3 -i -m json.tool   # interact after running a module
python3 -i -c "x=42"      # start REPL with x already defined
```

### 2.4 Quitting

```python
>>> exit()      # or quit(), both are builtins added by the interactive startup (not available in scripts)
>>> Ctrl-D      # Unix (EOF)
# Ctrl-Z then Enter on Windows
```

`exit`/`quit` are `Quitter` objects that raise `SystemExit` when called. In scripts, prefer `raise SystemExit(0)` or `sys.exit(0)`.

### 2.5 IPython — A Better REPL

The standard REPL is deliberately minimal. For daily work many developers replace it with **IPython** (and, on top of it, Jupyter notebooks):

```bash
python3 -m pip install ipython
ipython
```

Key improvements:

| Feature | Example |
|---|---|
| Numbered history | `In [1]:`, `Out[1]:`, access via `_1`, `Out[3]` |
| Shell escapes | `!ls -la`, `!pip list` |
| Magic commands | `%timeit sorted(x)`, `%run script.py`, `%load`, `%debug` |
| Rich display | Pretty-printed dataframes, images in terminal |
| Autocomplete | `str.<Tab>` shows methods; `import<Tab>` completes |

```python
# In IPython:
In [1]: data = [3, 1, 4, 1, 5]

In [2]: %timeit sorted(data)
1.23 µs ± 12 ns per loop (mean ± std. dev. of 7 runs, 1,000,000 loops each)

In [3]: !echo "hello from shell"
hello from shell

In [4]: data?
Type:        list
String form: [3, 1, 4, 1, 5]
Length:      5
Docstring:   Built-in mutable sequence.

In [5]: Out[1]
Out[5]: [3, 1, 4, 1, 5]
```

This course shows the standard `>>>` REPL so examples work everywhere, but be aware IPython exists — many data-science and debugging workflows assume it.

Jupyter (`jupyter lab`) is IPython plus a browser-based notebook where code lives in cells with interleaved Markdown. Same language, different UX — not covered further here.

## 3. Running Script Files

### 3.1 `python script.py`

The most common non-interactive invocation:

```bash
python3 script.py
python3 path/to/script.py arg1 arg2
```

```python
# script.py
import sys
print("name:", __name__)
print("argv:", sys.argv)
print("hello from script")
```

```bash
python3 script.py foo bar
# name: __main__
# argv: ['script.py', 'foo', 'bar']
# hello from script
```

Details:

- The script's directory (`path/to/`) is prepended to `sys.path` so sibling imports work (Section 6).
- `__name__ == "__main__"` — the file is the entry point, not an imported module.
- `sys.argv[0]` is the script path as given on the command line; `sys.argv[1:]` are arguments.
- Bytecode is compiled in memory; no `.pyc` is left for a top-level script (imported modules *do* cache `.pyc` in `__pycache__`).
- Exit code is `0` on success, non-zero on unhandled exception. Check with `echo $?` (Unix) or `echo %ERRORLEVEL%` (Windows).

A realistic script with argument handling:

```python
# greet.py
import argparse
import sys

def greet(name: str, loud: bool = False) -> str:
    msg = f"Hello, {name}!"
    return msg.upper() if loud else msg

def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(description="Greet someone.")
    parser.add_argument("name", help="name to greet")
    parser.add_argument("--loud", action="store_true", help="uppercase the greeting")
    args = parser.parse_args(argv)
    print(greet(args.name, args.loud))
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

```bash
python3 greet.py Ada
# Hello, Ada!
python3 greet.py Ada --loud
# HELLO, ADA!
python3 greet.py --help
# usage: greet.py [-h] [--loud] name
```

The `if __name__ == "__main__":` guard is *the* idiom for making a file both importable and executable (see 3.4).

### 3.2 `python -m module` — Module as Script

`python -m` runs a *module* found on `sys.path` as the main program. This is the correct way to invoke tooling and package entry points:

```bash
python3 -m pip install requests    # pip as a module
python3 -m venv .venv              # venv as a module
python3 -m http.server 8000        # stdlib http server
python3 -m json.tool data.json     # pretty-print JSON
python3 -m unittest                # test discovery
python3 -m mypackage               # runs mypackage/__main__.py or mypackage/__init__.py
```

Why prefer `-m` over direct script paths?

- **Correct `sys.path`.** `python script.py` puts the *script's parent directory* first; `python -m pkg.script` puts the *current working directory* first and respects packages. This avoids double-import bugs where the same file is loaded under two names (`__main__` and `pkg.script`).
- **Works without knowing the file path.** `python -m http.server` works regardless of where the stdlib lives.
- **Required for packages.** `python mypackage/__main__.py` breaks relative imports; `python -m mypackage` does not.

```python
# mypackage/__main__.py
from .core import main  # relative import — only works with -m

if __name__ == "__main__":
    raise SystemExit(main())
```
```bash
python3 -m mypackage              # works
python3 mypackage/__main__.py     # ImportError: attempted relative import with no known parent package
```

Other `-m` idioms you will see:

```bash
# Run a single file as a module from the project root
python3 -m mypackage.submodule  # finds mypackage/submodule.py via sys.path

# Compile all files to .pyc without executing (syntax check)
python3 -m py_compile script.py
python3 -m compileall .

# Start an interactive REPL after a module
python3 -i -m mymodule
```

### 3.3 `python -c "code"` — One-Liner

Execute a string as a program — handy for quick checks and shell scripting:

```bash
python3 -c "import sys; print(sys.version)"
python3 -c "import pathlib; print(list(pathlib.Path('.').glob('*.py')))"
python3 -c "import json, sys; print(json.dumps({'hello': 'world'}))"
```

On Windows PowerShell, watch quoting:

```powershell
py -c "import sys; print(sys.version)"
py -c 'print("hello")'   # single quotes work in PowerShell too
```

`python -c` sets `sys.argv[0]` to `"-c"` and `__name__` to `"__main__"`, just like a script.

### 3.4 `__name__ == "__main__"` and `__main__.py`

Every `.py` file has a `__name__` attribute:

- When **imported**: `__name__` is the module's dotted path (`"mypackage.utils"`).
- When **executed as the entry point**: `__name__` is `"__main__"`.

This dual identity lets a file be both a library and a CLI:

```python
# utils.py
def add(a: int, b: int) -> int:
    return a + b

# Only runs when `python utils.py` or `python -m utils`
if __name__ == "__main__":
    import sys
    a, b = map(int, sys.argv[1:3])
    print(add(a, b))
```

```bash
python3 utils.py 2 3        # 5
python3 -c "import utils; print(utils.add(10, 20))"  # 30 — guard prevents CLI from running
```

For packages, `__main__.py` provides the entry point for `python -m package`:

```
mypackage/
├── __init__.py
├── __main__.py   # executed by `python -m mypackage`
├── core.py
└── cli.py
```

### 3.5 Shebang — Making a Script Directly Executable (Unix/macOS)

On Unix-like systems you can make a `.py` file executable so users run `./script.py` instead of `python3 script.py`:

```python
#!/usr/bin/env python3
# greet.py — first line is the shebang (must be the very first line, no blank lines before)
import sys
print(f"Hello, {sys.argv[1] if len(sys.argv) > 1 else 'world'}!")
```

```bash
chmod +x greet.py     # give execute permission
./greet.py Ada        # Hello, Ada!
```

Notes:

- `#!/usr/bin/env python3` is the portable idiom — it respects `PATH` and `pyenv` shims. Avoid hard-coding `/usr/bin/python3` (points to system Python, breaks per-project versions).
- For `pyenv` or version-specific needs: `#!/usr/bin/env python3.12`.
- Windows ignores shebangs natively but the `py` launcher reads them: `py greet.py` respects `#!/usr/bin/env python3`.
- The shebang has no effect when you run `python3 greet.py` — only when the OS executes the file directly.

You can also combine shebang with `__main__` guard for a CLI that works both ways:

```python
#!/usr/bin/env python3
"""greet — a tiny CLI that is also importable."""

def greet(name: str) -> str:
    return f"Hello, {name}!"

def main() -> int:
    import argparse
    p = argparse.ArgumentParser()
    p.add_argument("name", nargs="?", default="world")
    args = p.parse_args()
    print(greet(args.name))
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

## 4. Stdin, Pipes, and Here-Docs

Python can read source from standard input — useful for pipelines and inline generation:

```bash
# Pipe source via stdin (no filename argument)
echo 'print("hello from stdin")' | python3
# hello from stdin

# Explicit stdin marker:
echo 'print("piped")' | python3 -

# Here-doc (shell feature — feeds multi-line stdin)
python3 << 'PY'
import math
for i in range(5):
    print(i, math.sqrt(i))
PY

# Process data piped into a script via sys.stdin
echo "hello world" | python3 -c "import sys; print(sys.stdin.read().upper())"
# HELLO WORLD
```

A realistic filter script that reads stdin line-by-line:

```python
#!/usr/bin/env python3
# filter_errors.py — print only lines containing "ERROR"
import sys

for line in sys.stdin:
    if "ERROR" in line:
        sys.stdout.write(line)
```

```bash
cat app.log | python3 filter_errors.py
tail -f app.log | python3 filter_errors.py   # streaming
```

When source comes from stdin, `sys.argv[0]` is `"-"` and `sys.path[0]` is `""` (empty string, meaning current directory).

## 5. Command-Line Options You Should Know

| Option | What it does | Example |
|---|---|---|
| `-i` | Drop into REPL after script/module/`-c` | `python3 -i script.py` |
| `-m module` | Run module as `__main__` | `python3 -m pip list` |
| `-c cmd` | Run string as program | `python3 -c "print(42)"` |
| `-u` | Unbuffered stdout/stderr (flush immediately) | `python3 -u script.py | cat` |
| `-B` | Do not write `.pyc` files | `python3 -B script.py` |
| `-O` / `-OO` | Optimize (remove `assert`, strip docstrings with `-OO`) | `python3 -O script.py` |
| `-W` | Warning control | `python3 -W error script.py` (turn warnings into errors) |
| `-q` | Quiet — suppress banner in REPL | `python3 -q` |
| `-E` | Ignore `PYTHON*` env vars | `python3 -E script.py` (sanitized run) |
| `-I` | Isolated mode (`-E` + `-P` + no user site) | For embedded/system use |

Show all with `python3 --help`.

## 6. `PYTHONPATH` and `sys.path` — How Imports Find Files at Runtime

Import confusion almost always traces to `sys.path`. Understanding how it is built lets you diagnose and fix `ModuleNotFoundError` without guessing.

### 6.1 What `sys.path` Is

`sys.path` is the ordered list of directories Python searches for imports. You can inspect it anywhere:

```python
import sys
import pprint
pprint.pprint(sys.path)
```

Example output (paths vary by OS and install):

```
['/home/you/projects/demo',
 '/home/you/.pyenv/versions/3.12.4/lib/python312.zip',
 '/home/you/.pyenv/versions/3.12.4/lib/python3.12',
 '/home/you/.pyenv/versions/3.12.4/lib/python3.12/lib-dynload',
 '/home/you/.pyenv/versions/3.12.4/lib/python3.12/site-packages']
```

### 6.2 How It Is Built (Order Matters)

At startup, the interpreter constructs `sys.path` in this priority:

1. **The entry-point directory** (highest priority):
   - `python script.py` → `script.py`'s directory.
   - `python -m pkg.mod` → current working directory.
   - REPL / `python -` (stdin) → `""` (current directory).
   - `-c` → `""`.
2. **`PYTHONPATH` environment variable** — colon-separated (semicolon on Windows) list of directories, prepended if set.
3. **Standard library** paths (determined at compile time: `lib/python3.12`, `lib-dynload`, zip file).
4. **Site-packages** paths — third-party and user installs (including `.pth` files).
5. **`.pth` processing** — any `.pth` files in site-packages can add further paths.

You can influence it at several timescales:

```bash
# One invocation (most common, no permanent change):
PYTHONPATH=/home/you/projects/shared:$PYTHONPATH python3 script.py

# Windows (PowerShell):
$env:PYTHONPATH="C:\projects\shared"; py script.py

# Linux/macOS — verify it took effect:
PYTHONPATH=/tmp/my_modules python3 -c "import sys; print(sys.path[1])"
# /tmp/my_modules
```

```python
# At runtime (inside code) — mutation affects subsequent imports:
import sys
sys.path.insert(0, "/home/you/projects/shared")
import mymodule  # now found

# At startup via .pth file (for persistent project paths):
# Create .../site-packages/myproject.pth containing one path per line:
# /home/you/projects/shared
```

Also relevant:

```python
import site
print(site.getsitepackages())      # global site-packages dirs
print(site.getusersitepackages())  # user dir (~/.local/... on Linux)
print(site.ENABLE_USER_SITE)       # whether user site is enabled
# python3 -s  disables user site
# python3 -I  disables both user site and PYTHONPATH
```

### 6.3 PYTHONPATH at Runtime — Patterns and Pitfalls

`PYTHONPATH` is powerful and frequently misused.

**Good uses (temporary, per-invocation):**

```bash
# Running tests against the source tree without installing:
PYTHONPATH=src python3 -m pytest

# Ad-hoc shared utility directory on a cluster:
PYTHONPATH=/opt/team_utils python3 pipeline.py
```

**Avoid as a permanent global setting:**

```bash
# Do NOT add to ~/.bashrc permanently:
# export PYTHONPATH=/home/you/projects/myapp:$PYTHONPATH  # anti-pattern
# It makes every Python invocation see that directory, causing surprising
# shadowing (e.g., your `random.py` shadows the stdlib `random`).
```

**Modern alternative — installable packages + virtual environments:**

Instead of stretching `PYTHONPATH`, make your project installable so it lands on `sys.path` via `site-packages`:

```bash
# pyproject.toml declares the package; then:
python3 -m pip install -e .     # editable install — changes to source take effect immediately
# Now `import mypackage` works everywhere inside the venv, no PYTHONPATH needed.
```

This is the approach used in professional projects. Reserve `PYTHONPATH` for ephemeral, one-off runs.

### 6.4 Common `ModuleNotFoundError` Diagnoses

| Symptom | Likely cause | Fix |
|---|---|---|
| `ModuleNotFoundError: No module named 'mypackage'` when running `python script.py` from a subdirectory | `sys.path[0]` is the subdirectory, not the project root | `cd` to project root and run `python -m package.script`, or set `PYTHONPATH` to project root. |
| Same error in tests but app runs | Test runner's working directory differs | Run `python -m pytest` from project root; ensure `src` layout is handled via `PYTHONPATH=src` or editable install. |
| `import X` works in REPL but not in script | REPL's `""` entry resolves differently than script's directory | Print `sys.path` in both; align by running script via `python -m`. |
| Shadowing: `import random` gives your `random.py` | A file in an early `sys.path` entry shadows stdlib | Rename your file; never name modules after stdlib names. |

Diagnostic snippet to paste when lost:

```python
import sys, pathlib, pprint
print("cwd:      ", pathlib.Path.cwd())
print("argv[0]:  ", sys.argv[0])
print("path[0]:  ", sys.path[0])
print("exe:      ", sys.executable)
pprint.pprint(sys.path)
try:
    import mypackage
    print("mypackage:", mypackage.__file__)
except ModuleNotFoundError as e:
    print("import failed:", e)
```

## 7. Interactive Helpers — `help`, `dir`, `type`, and Friends

The Python REPL ships with a small toolkit for exploration. These work anywhere but are most valuable interactively.

### 7.1 `help(obj)` — Documentation in the Terminal

```python
>>> help(str.split)
Help on method_descriptor:
split(self, /, sep=None, maxsplit=-1)
    Return a list of the words in the string, using sep as the delimiter.

>>> help(len)
Help on built-in function len in module builtins:
len(obj, /)
    Return the number of items in a container.

>>> import pathlib
>>> help(pathlib.Path)
# full class documentation, navigable with arrow keys / q to quit

>>> help()          # enter the help browser
help> modules       # list available modules (slow, scans sys.path)
help> keywords      # Python keywords
help> quit
```

In IPython, `obj?` and `obj??` (show source) are shorthands for `help`.

### 7.2 `dir(obj)` — What's Inside

`dir` lists attribute names, including inherited ones:

```python
>>> dir("hello")
['__add__', '__class__', '__contains__', ..., 'capitalize', 'casefold', 'count', 'encode', ...]

>>> import math
>>> [x for x in dir(math) if not x.startswith("_")]
['acos', 'acosh', 'asin', 'asinh', 'atan', 'atan2', 'ceil', 'comb', 'copysign', ...]

>>> class Point:
...     def __init__(self, x, y): self.x, self.y = x, y
...     def move(self, dx, dy): self.x += dx; self.y += dy
...
>>> dir(Point)
['__class__', '__delattr__', ..., 'move']
>>> dir(Point(1, 2))
['__class__', ..., 'move', 'x', 'y']  # instance dir includes attributes
```

Tip: `dir()` with no argument lists names in the current scope — essentially `list(locals().keys())`.

### 7.3 Other Builtins for Exploration

```python
>>> x = [1, 2, 3]
>>> type(x)          # <class 'list'>
>>> isinstance(x, list)  # True — prefer isinstance over type(x) == list
>>> len(x)           # 3

>>> import pathlib
>>> p = pathlib.Path(".")
>>> isinstance(p, pathlib.PurePath)  # True — subclass check

>>> callable(len)    # True
>>> callable("hello")# False

>>> ord("A"), chr(65)  # 65, 'A'
>>> bin(42), hex(42), oct(42)  # '0b101010', '0x2a', '0o52'
```

### 7.4 `sys` and `inspect` for Deeper Introspection

```python
import sys, inspect, textwrap

# Where am I?
print(sys.executable, sys.version)

# Source of a function (if available — not for C builtins)
def greet(name): return f"Hello, {name}!"
print(inspect.getsource(greet))

# Signature
print(inspect.signature(greet))  # (name)

# File location
import pathlib
print(inspect.getfile(pathlib.Path))  # .../pathlib.py
```

## 8. A Note on Errors and Exit Codes

When Python fails, it prints a traceback and exits non-zero. Understanding the exit code helps in shell scripting:

```bash
python3 -c "raise ValueError('oops')"
echo $?   # 1 (Unix) — non-zero

python3 -c "import sys; sys.exit(42)"
echo $?   # 42

python3 missing_file.py
echo $?   # 2 or 1 depending on error type
```

In Python, `sys.exit(n)` raises `SystemExit(n)`, which the interpreter catches at the top level to set the process exit code. This is why `if __name__ == "__main__": raise SystemExit(main())` is the idiomatic CLI pattern — it lets `main()` return an int that becomes the shell-visible status.

## 9. Summary — Choosing the Right Invocation

| Goal | Command | `sys.path[0]` | `__name__` |
|---|---|---|---|
| Explore interactively | `python3` | `""` (cwd) | N/A (REPL) |
| Run a file | `python3 script.py args` | `script.py`'s directory | `"__main__"` |
| Run a module/package | `python3 -m pkg.mod` | cwd | `"__main__"` |
| Keep namespace after run | `python3 -i script.py` | script's directory | `"__main__"` |
| One-liner | `python3 -c "code"` | `""` | `"__main__"` |
| Pipe source | `echo "code" \| python3` | `""` | `"__main__"` |
| Executable script (Unix) | `./script.py` | script's directory | `"__main__"` |

And for imports: `sys.path` is built from the entry directory → `PYTHONPATH` → stdlib → site-packages. When `import` fails, print `sys.path` and `sys.argv[0]` before changing code — the answer is almost always *which directory was first*.

4. **PYTHONPATH.** Create `/tmp/my_modules/greet.py` containing `def hello(): return "hi"`. Without modifying `sys.path` in code, run a one-liner `python3 -c "import greet; print(greet.hello())"` by setting `PYTHONPATH` only for that invocation. Then do the same by inserting into `sys.path` inside the one-liner — compare.

5. **Help-driven discovery.** Without web search, use only `help` and `dir` in the REPL to discover how `str.strip` differs from `str.lstrip`/`str.rstrip`, and how `list.sort` differs from `sorted`.
