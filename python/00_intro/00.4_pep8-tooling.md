# 00.4 PEP 8, Tooling, and File Structure

PEP 8 is not a suggestion — it is the shared dialect that lets any Python programmer read any other Python programmer's code without first learning a new layout. This lesson covers the standard in depth, distinguishes it from the related PEP 20 (The Zen) and PEP 257 (docstrings), shows how linters and formatters automate enforcement, explains type checking with `mypy`, and teaches how to structure a single file and a comment style so your code reads like idiomatic Python from day one.

---

## 1. What "PEP" Means

**PEP** stands for **Python Enhancement Proposal**. It is the design-document process for the language (PEP 1 defines the process itself). PEPs are numbered and have statuses:

| Status | Meaning |
|---|---|
| **Draft / Active** | Under discussion |
| **Accepted / Final** | Approved and in force |
| **Informational** | Guidelines, not language changes (PEP 8, PEP 20, PEP 257 are informational) |
| **Withdrawn / Rejected** | Not adopted |
| **Superseded** | Replaced by a later PEP |

You will hear PEP numbers as shorthand. The three that govern everyday code style are:

- **PEP 8** — *Style Guide for Python Code* (code layout, naming, whitespace).
- **PEP 20** — *The Zen of Python* (philosophy, `import this`).
- **PEP 257** — *Docstring Conventions* (how to document modules, classes, functions).

PEPs that change the language (e.g., PEP 484 for type hints, PEP 572 for the walrus operator) are separate from style. Style PEPs tell you *how to write* code; language PEPs tell you *what you can write*.

---

## 2. PEP 20 — The Zen, Briefly Revisited

Covered in Lesson 00.1, but as a reminder `import this` prints 19 aphorisms that PEP 8 implements concretely. Two lines deserve special attention here:

> *Readability counts.*
> *There should be one — and preferably only one — obvious way to do it.*

PEP 8 is how the community agreed on the "one obvious way" to format code. When PEP 8 says "use 4 spaces," it is not claiming 4 is mathematically superior to 2 — it is claiming that *everyone using the same rule* is superior to everyone choosing their own.

## 3. PEP 8 in Depth

The full guide lives at `https://peps.python.org/pep-0008/`. Below is a faithful, example-heavy distillation organized by the questions you actually ask while writing.

### 3.1 The Spirit: Consistency and Common Sense

PEP 8 opens with a crucial paragraph often skipped:

> *A style guide is about consistency. Consistency with this style guide is important. Consistency within a project is more important. Consistency within one module or function is most important.*

In practice:

- New, green-field code should follow PEP 8 fully.
- When editing a file that already violates PEP 8 locally (e.g., uses 2-space indent throughout), match the file's existing style for that change; migrate the file separately if you want to fix it.
- **Never break backward compatibility** just to fix a naming violation. `http.client` still exports `HTTPResponse` with that exact spelling because renaming would break callers.

A Foolish Consistency warning appears verbatim: know when to be inconsistent — sometimes local style must defer to a higher priority (correctness, readability).

### 3.2 Indentation

- **4 spaces per level.** No tabs. Configure your editor to insert spaces when you press Tab.
- Continuation lines: align with the opening delimiter or use a hanging indent.

```python
# Good — 4 spaces, aligned with opening delimiter
foo = long_function_name(var_one, var_two,
                         var_three, var_four)

# Good — hanging indent (nothing on first line, indented one level)
foo = long_function_name(
    var_one, var_two,
    var_three, var_four
)

# Good — hanging indent with extra indent to distinguish from next block
if (this_is_a_very_long_condition
        and that_is_another_long_condition):
    do_something()

# Bad — misaligned continuation
foo = long_function_name(var_one, var_two,
    var_three, var_four)  # not aligned, hard to scan
```

Tabs vs spaces — settled definitively:

```python
# Python 3 forbids mixing tabs and spaces for indentation (TabError).
# Configure your editor:
# VS Code:  "editor.insertSpaces": true, "editor.tabSize": 4
# Vim:      set expandtab shiftwidth=4 softtabstop=4
# Emacs:    (setq-default indent-tabs-mode nil) (setq-default tab-width 4)
```

### 3.3 Line Length

- **79 characters** for code (soft limit, historically for 80-column terminals).
- **72 characters** for comments and docstrings.
- Modern practice: many teams adopt **88** (Black's default) or **100** and configure the linter to match. PEP 8 explicitly says teams may agree on a longer limit for code that already does so — just be consistent and enforce it with a tool.

**How to wrap long lines:**

```python
# Bad — exceeds 79/88 and forces horizontal scrolling
result = some_very_long_function_name(argument_one, argument_two, argument_three, argument_four, argument_five)

# Good — wrap with parentheses (preferred over backslash)
result = some_very_long_function_name(
    argument_one, argument_two, argument_three, argument_four, argument_five
)

# Good — break before binary operator (PEP 8 recommends this for readability)
total = (first_variable
         + second_variable
         - third_variable)

# Backslash only when parentheses/brackets/braces cannot be used
# (and even then, prefer parentheses)
with open("/path/to/some/file/you/want/to/read") as file_1, \
     open("/path/to/some/file/being/written", "w") as file_2:
    file_2.write(file_1.read())

# Better — use parentheses to avoid backslash entirely
with (
    open("/path/to/some/file/you/want/to/read") as file_1,
    open("/path/to/some/file/being/written", "w") as file_2,
):
    file_2.write(file_1.read())
```

The Python parser joins adjacent string literals, which helps wrap without `+`:

```python
# Implicit concatenation — no runtime cost
message = (
    "This is a very long message that would otherwise exceed "
    "the line limit, but by splitting it into parenthesized "
    "adjacent literals we keep it readable."
)
```

### 3.4 Blank Lines

```python
# Top-level functions and classes: two blank lines between them
import pathlib


def helper_a() -> None:
    pass


def helper_b() -> None:
    pass


class MyClass:
    pass


class Other:
    pass

# Methods inside a class: one blank line between methods
class Example:
    def first(self) -> None:
        pass

    def second(self) -> None:
        pass

    # Use a blank line sparingly inside functions to separate logical sections
    def complex(self) -> None:
        raw = self._load()
        cleaned = self._clean(raw)

        result = self._analyze(cleaned)
        self._save(result)
```

Extra blank lines may be used to group related functions; avoid more than two consecutive blank lines anywhere.

### 3.5 Imports

PEP 8's import rules prevent circular imports, slow star-import bugs, and unreadable namespaces.

**Order — three groups separated by a blank line, and alphabetically within each group (isort enforces this):**

```python
# Good import order — stdlib, third-party, local
import os
import sys
from pathlib import Path

import requests
import numpy as np

from mypackage import core
from mypackage.utils import helpers
```

```python
# Bad — unordered, mixed groups
from mypackage.utils import helpers
import requests
import os
from pathlib import Path
import sys
import numpy as np
from mypackage import core
```

**Absolute imports preferred; explicit relative imports where appropriate:**

```python
# Absolute (preferred for clarity)
import mypackage.core
from mypackage.core import process

# Explicit relative (fine inside a package)
from . import core      # same package
from ..utils import helpers  # parent package
```

**Never `from module import *` in production code:**

```python
# Bad — pollutes namespace, hides origin, breaks linters
from os import *

# Good — explicit origin, grep-able
import os
os.path.join("a", "b")

# Acceptable compromise for well-known re-exports
from pathlib import Path
from collections import defaultdict

# Import alias for long names or conventional abbreviations
import numpy as np
import matplotlib.pyplot as plt
```

**One import per line for `import` statements; multiple `from` imports may share a line if short:**

```python
# Good
import os
import sys

# Good — multi-import on one from line
from subprocess import PIPE, Popen

# Good — parenthesized multi-line from import
from mypackage.core import (
    Result,
    process_data,
    validate,
)

# Bad — multiple imports on one `import` line
import os, sys  # harder to diff, harder to sort
```

**Module-level `__all__` to define public API (controls `from package import *`):**

```python
# mypackage/__init__.py
from .core import process_data, Result

__all__ = ["process_data", "Result"]  # only these are public
```

### 3.6 Whitespace — The Small Rules That Compound

| Rule | Good | Bad |
|---|---|---|
| No extra spaces inside parens/brackets/braces | `spam(ham[1], {eggs: 2})` | `spam( ham[ 1 ], { eggs: 2 } )` |
| No space before comma/semicolon, one after | `x, y = (1, 2)` | `x ,y = (1,2)` |
| No space before `:` in slices, one after `:` in dicts | `ham[1:9]`, `d = {"k": v}` | `ham[1 : 9]`, `d = {"k":v}` |
| One space around `=` for assignment; no spaces for keyword args or annotated assignment `:` | `x = 1`, `def f(x: int = 1)` | `x=1`, `def f(x : int=1)` |
| One space around operators | `i = i + 1` | `i=i+1` |
| No trailing whitespace | (invisible but real) | `x = 1   ` |
| No whitespace before `(` for calls/indexing | `spam(1)` | `spam (1)` |

```python
# Whitespace examples — recommended
x = 1
y = 2
long_variable = 3

# Operator spacing
i = i + 1
submitted += 1
x = x * 2 - 1
hypot2 = x * x + y * y
c = (a + b) * (a - b)

# Keyword arguments — no spaces around =
def complex(real, imag=0.0):
    return magic(r=real, i=imag)

# Annotated assignments — one space after :, no space before
code: int
name: str = "Ada"
# For annotated function signatures, PEP 8 asks for one space around `=` in defaults:
def greet(name: str = "world", loud: bool = False) -> str:
    return f"Hello, {name}!"

# Slices — no spaces around :
ham[1:9]
ham[1:9:3]
ham[:9:3]
ham[lower:upper]
ham[lower + offset : upper + offset]  # spaces around + still apply inside slice bounds

# But omit space when slice param is omitted on one side — no extra spaces:
ham[lower + offset:upper + offset]  # equivalent, choose one style and be consistent

# Dict literal — one space after :
my_dict = {"key": "value", "other": 42}
```

### 3.7 Naming Conventions

PEP 8 naming is a *signal* — readers infer scope and mutability from spelling. This table is the heart of PEP 8 to memorize:

| Type | Convention | Example |
|---|---|---|
| **Package** | `lowercase`, short, no underscores if possible | `mypackage`, `requests` |
| **Module** | `lowercase` with underscores | `my_module`, `path_utils` |
| **Class** | `CapWords` / `PascalCase` | `MyClass`, `HTTPResponse` |
| **Exception** | `CapWords` ending in `Error` | `ValueError`, `MyAppError` |
| **Function** | `lowercase` with underscores | `my_function`, `process_data` |
| **Variable** | `lowercase` with underscores | `my_variable`, `total_count` |
| **Method** | `lowercase` with underscores | `my_method`, `to_string` |
| **Constant** | `UPPERCASE` with underscores | `MAX_SIZE`, `DEFAULT_TIMEOUT` |
| **Private** | Leading single underscore `_` | `_internal_helper`, `_cache` |
| **Name-mangled** | Leading double underscore `__` | `__private` (mangled to `_ClassName__private`) |
| **Dunder** | Double underscores on both sides | `__init__`, `__len__` (never invent your own) |
| **Unused / throwaway** | Single underscore `_` | `for _ in range(5)` |

```python
# Naming — complete example
import math

MAX_RETRIES = 3            # constant
DEFAULT_TIMEOUT = 30.0     # constant

class DataProcessor:       # CapWords
    """Process numeric data."""

    def __init__(self, data: list[float]) -> None:
        self.data = data
        self._cache: dict[str, float] = {}   # private by convention
        self.__secret = 42                   # name-mangled (rare, usually avoid)

    def process(self, scale: float = 1.0) -> list[float]:
        """Scale each value.""" 
        local_result = [x * scale for x in self.data]  # lowercase variable
        return local_result

    def _helper(self) -> float:
        """Private helper — not part of public API."""
        return sum(self.data)

def public_api_function(items: list[int]) -> int:
    total_count = 0        # local variable
    for _ in range(3):     # _ means "unused"
        total_count += len(items)
    return total_count
```

Two common confusions:

**Single underscore `_var` vs double underscore `__var`:**

```python
class Demo:
    def __init__(self):
        self._internal = 1    # convention — "private, don't touch from outside"
        self.__mangled = 2    # name-mangled to _Demo__mangled

d = Demo()
print(d._internal)           # 1 — accessible, by convention you shouldn't
# print(d.__mangled)         # AttributeError
print(d._Demo__mangled)      # 2 — mangling exists to avoid subclass collisions, not security

# Use _single_underscore for "internal." Use __double only to avoid name clashes
# in inheritance hierarchies — it is rare in application code.
```

**`CapWords` for classes vs `lowercase` for everything else:**

You can tell at a glance whether `MyClass()` constructs an object or `my_function()` calls a function. Breaking this convention confuses readers and tools (e.g., `pylint` flags it).

### 3.8 String Quotes

PEP 8 says: pick one and be consistent. Both `'` and `"` are correct; triple-quoted strings (`"""` or `'''`) are for docstrings and multiline strings. The de facto community standard (and Black's default) is `"` for most strings.

```python
# All equivalent — choose one style per project
a = "hello"
b = 'hello'

# Prefer double quotes if your formatter does (Black does) — then be consistent
# Triple double quotes for multiline / docstrings
doc = """This is a
multiline string."""

# Implicit concatenation must use the same quote style — formatter will normalize
message = (
    "first part "
    "second part"
)
```

### 3.9 Comparisons, Booleans, and Membership

PEP 8 embeds several idioms that read like English and avoid subtle bugs:

```python
# None checks — always use `is`, not `==` (None is a singleton)
if x is None:
    pass
if x is not None:
    pass
# Bad: if x == None  — could be overridden by __eq__, slower, not idiomatic

# Truthiness — don't compare to True/False/len
if my_list:          # good — empty list is falsy
    pass
if not my_list:      # good
    pass
# Bad:
# if len(my_list) > 0:  — verbose
# if my_list == []:     — slower, less general
# if x == True:         — wrong for truthy non-booleans; just `if x:`

# Membership — `in` / `not in`
if key in my_dict:        # good
    pass
if key not in my_dict:    # good

# Type checks — isinstance, not type equality
if isinstance(obj, int):  # good — respects subclasses (bool is subclass of int)
    pass
# Bad:
# if type(obj) == int:    — fails for subclasses

# Avoid `type(obj) is int` unless you explicitly want to exclude subclasses.

# Equality for value objects, identity only for singletons
if x == 42:       # value equality
    pass
if x is None:     # identity for singleton
    pass
```

### 3.10 Programming Recommendations — A Selection

PEP 8 ends with behavioral advice, not just formatting:

- **Compare to singletons with `is`**, not `==` (`None`, optionally `True`/`False` when you mean identity).
- **Use `is not` rather than `not ... is`**: `if x is not None` not `if not x is None`.
- **Do not use bare `except:`** — it catches `SystemExit` and `KeyboardInterrupt`. Write `except Exception:` or a specific exception.
- **Use `def` with `bytes`/`str` handling deliberately** — do not mix `str` and `bytes` without explicit encode/decode (ties to Python 3 string model).
- **Prefix unused variables with `_`** when unpacking: `a, _b, c = (1, 2, 3)` if `_b` is intentionally ignored; some linters treat `_` specially.
- **Use `with` for resources** — files, locks, connections.

```python
# Bad — bare except hides Ctrl-C and SystemExit
try:
    do_something()
except:  # catches BaseException — too broad
    pass

# Good — specific
try:
    do_something()
except ValueError as exc:
    print(f"bad value: {exc}")

# Acceptable — catch all regular exceptions explicitly
try:
    do_something()
except Exception:
    pass  # only if you truly want to catch everything except special control-flow

# Context manager — preferred for resources
with open("data.txt", encoding="utf-8") as f:
    content = f.read()
# f is closed even if an exception occurs — no explicit close needed
```

## 4. PEP 257 — Docstring Conventions

PEP 257 extends PEP 8 to docstrings. A docstring is the first string literal in a module, class, function, or method. Tools (`help()`, Sphinx, VS Code hover) display it as documentation.

### 4.1 One-Line Docstrings

For obvious, short callables:

```python
def add(a: int, b: int) -> int:
    """Return the sum of a and b."""
    return a + b
```

Rules: triple double quotes (`"""`), single line, ends with a period, no blank line before or after inside the quotes.

### 4.2 Multi-Line Docstrings

For anything needing parameters, examples, or notes:

```python
def greet(name: str, loud: bool = False) -> str:
    """Return a greeting for *name*.

    Args:
        name: Person to greet.
        loud: If True, return an uppercase greeting.

    Returns:
        A greeting string.

    Example:
        >>> greet("Ada")
        'Hello, Ada!'
        >>> greet("Ada", loud=True)
        'HELLO, ADA!'
    """
    msg = f"Hello, {name}!"
    return msg.upper() if loud else msg
```

PEP 257 rules for multi-line:

- Opening `"""` on the first line, summary on the same line.
- Blank line after summary.
- More detail after the blank line.
- Closing `"""` on its own line.

The summary should be imperative mood ("Return…", "Compute…", "Parse…"), not "Returns…" or "This function returns…" — though both are seen; pick one style per project.

### 4.3 Docstrings for Modules, Classes, and Attributes

```python
"""mypackage.core — core processing utilities.

This module provides :func:`process_data` and :class:`Result` for
transforming raw records into validated results.
"""

from dataclasses import dataclass


@dataclass
class Result:
    """Container for a processed record.

    Attributes:
        value: Computed numeric value.
        valid: Whether the record passed validation.
    """

    value: float
    valid: bool


def process_data(raw: list[float]) -> list[Result]:
    """Process raw values into Results.

    Each value is validated (must be finite) and scaled.

    Args:
        raw: Input values.

    Returns:
        List of Result objects, one per input.

    Raises:
        ValueError: If *raw* is empty.
    """
    if not raw:
        raise ValueError("raw must not be empty")
    return [Result(value=x, valid=True) for x in raw]
```

Access docstrings at runtime via `__doc__` or `help()`:

```python
help(process_data)
print(process_data.__doc__)
print(Result.__doc__)
```

Two common styles for Args/Returns sections exist — **Google** (above) and **NumPy** / **Sphinx reStructuredText** (`:param name:`, `:type name:`). Both satisfy PEP 257; the difference is tooling (Sphinx vs MkDocs) and team preference. Do not mix them in one project.

### 4.4 Comments vs Docstrings — A Sharp Distinction

| Aspect | Comment (`# ...`) | Docstring (`"""..."""`) |
|---|---|---|
| Stored at runtime? | No — stripped by parser | Yes — `obj.__doc__` |
| Seen by `help()`? | No | Yes |
| Purpose | Explain *why* / *how* for maintainers | Describe *what* / *how to use* for callers |
| Scope | Anywhere inside code | First statement of module/class/function/method |

```python
# Comment — explains a non-obvious choice for future maintainers
# We use 0.5 as epsilon because sensor noise is ~0.3 and we want hysteresis.
EPSILON = 0.5

def is_close(a: float, b: float) -> bool:
    """Return True if *a* and *b* differ by less than EPSILON."""
    # abs() handles negative differences; no need for two branches
    return abs(a - b) < EPSILON
```

When a function name and signature make the behavior obvious, a one-line docstring suffices. When behavior is subtle (preconditions, side effects, performance notes), a multi-line docstring plus inline comments is appropriate.

## 5. Tooling — Automating Style So You Do Not Have To

Humans should not spend review time arguing about trailing commas. Tools do.

### 5.1 Linters — Detect Problems

A **linter** reads your code *without running it* and reports style and correctness issues.

#### flake8

The classic linter — wraps `pycodestyle` (PEP 8 checks), `pyflakes` (logic errors), and `mccabe` (complexity).

```bash
python3 -m pip install flake8
flake8 mypackage/
# mypackage/core.py:3:1: F401 'os' imported but unused
# mypackage/core.py:7:80: E501 line too long (82 > 79 characters)
# mypackage/core.py:12:5: E303 too many blank lines (3)
```

Configure in `setup.cfg`, `.flake8`, or `pyproject.toml`:

```ini
# .flake8 or setup.cfg
[flake8]
max-line-length = 88
extend-ignore = E203, W503
exclude = .venv, __pycache__, build
```

```toml
# pyproject.toml (flake8 6+)
[tool.flake8]
max-line-length = 88
extend-ignore = ["E203", "W503"]
exclude = [".venv", "__pycache__"]
```

`E203`/`W503` are ignored when using Black, because Black's formatting conflicts with those two rules — standard practice.

Common flake8 codes:

| Code | Meaning |
|---|---|
| `E501` | Line too long |
| `E302`/`E303` | Too many/few blank lines |
| `F401` | Imported but unused |
| `F821` | Undefined name |
| `W291` | Trailing whitespace |
| `C901` | Complexity too high (McCabe) |

#### pylint

More opinionated and thorough than flake8 — checks naming, design, refactoring suggestions, and potential bugs. Noisier; best with a config file.

```bash
python3 -m pip install pylint
pylint mypackage/core.py
# ************* Module mypackage.core
# mypackage/core.py:1:0: C0114: Missing module docstring (missing-module-docstring)
# mypackage/core.py:5:0: C0103: Constant name "myConstant" doesn't conform to UPPER_CASE (invalid-name)
```

```bash
# Generate a starting config and tune it
pylint --generate-rcfile > .pylintrc
```

Teams often run **flake8** (fast, low-noise) in pre-commit and **pylint** (thorough) in CI on changed files, or replace both with **Ruff** (see below).

#### Ruff — The Modern Replacement

[Ruff](https://docs.astral.sh/ruff/) (written in Rust) reimplements flake8 + pylint + isort + more at 10–100× speed. It is the current default for new projects:

```bash
python3 -m pip install ruff
ruff check .          # lint
ruff check --fix .    # auto-fix many issues
```

```toml
# pyproject.toml
[tool.ruff]
line-length = 88
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "C4"]  # pycodestyle, pyflakes, isort, flake8-bugbear, comprehensions
ignore = ["E501"]  # line length handled by formatter
```

If you start a new project today, reach for Ruff before flake8/pylint individually. The rest of this lesson describes flake8/pylint because the prompt names them and because understanding their messages helps you understand Ruff's.

### 5.2 Formatters — Rewrite Code to Be Compliant

A **formatter** *changes* your files to match a style. You run it, it rewrites. No arguments about aesthetics.

#### Black — The Uncompromising Formatter

[Black](https://black.readthedocs.io/) formats code deterministically. It has almost no configuration — line length is the main knob (default 88, chosen to be 10% over 80 for readability).

```bash
python3 -m pip install black
black mypackage/          # format in place
black --check mypackage/  # CI mode — fail if not formatted
black --diff mypackage/   # show what would change
```

Example transformation:

```python
# Before Black
x = {  'a':37,'b':42,
'c':927}

y = some_function(a_very_long_argument_name,
                  another_argument, yet_another=True)

# After `black` (88-char line)
x = {"a": 37, "b": 42, "c": 927}

y = some_function(
    a_very_long_argument_name, another_argument, yet_another=True
)
```

Black's choices (double quotes, trailing commas, parenthesized wrapping) are intentional tradeoffs for *consistency* and *diff-friendliness*. Do not fight it — configure your linter to agree (`extend-ignore = E203, W503` for flake8 when using Black) and stop thinking about formatting.

```toml
# pyproject.toml
[tool.black]
line-length = 88
target-version = ["py312"]
include = '\.pyi?$'
```

#### isort — Import Sorter

[isort](https://pycqa.github.io/isort/) sorts and groups imports per PEP 8. Ruff and Black handle imports too, but isort as a standalone is still common.

```bash
python3 -m pip install isort
isort mypackage/          # sort in place
isort --check --diff mypackage/  # CI mode
```

```python
# Before isort
import requests
import os
from mypackage.utils import helpers
import sys
from pathlib import Path

# After isort
import os
import sys
from pathlib import Path

import requests

from mypackage.utils import helpers
```

Configuration to harmonize with Black:

```toml
# pyproject.toml
[tool.isort]
profile = "black"   # ensures isort's wrapping matches Black's 88
```

If you use Ruff, it includes isort rules (`I` prefix) so you may not need a separate isort step.

#### Putting It Together — Pre-commit

The idiomatic developer loop:

```bash
# One-time setup
python3 -m pip install black isort flake8 mypy ruff  # or just ruff + black + mypy
# Or with pre-commit framework:
python3 -m pip install pre-commit
```

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format  # or use black
```

### 5.3 Type Checker — `mypy` (and Alternatives)

Python's type hints (PEP 484) are *not* enforced at runtime. A **type checker** is a separate static analysis pass that reads your annotations and reports mismatches — the closest Python gets to a compiler's type pass.

#### mypy

The reference checker, by Python's typing maintainers.

```bash
python3 -m pip install mypy
mypy mypackage/
# mypackage/core.py:10: error: Argument 1 to "greet" has incompatible type "int"; expected "str"
```

Example with errors:

```python
# typed_example.py
def greet(name: str) -> str:
    return f"Hello, {name}!"

greet("Ada")   # OK
greet(42)      # mypy error: Argument 1 has incompatible type "int"; expected "str"

def add(a: int, b: int) -> int:
    return a + b

x: int = "hello"  # mypy error: Incompatible types in assignment
reveal_type(x)    # mypy note: Revealed type is "builtins.int" — useful for debugging
```

Configuration:

```toml
# pyproject.toml
[tool.mypy]
python_version = "3.12"
warn_return_any = true
warn_unused_configs = true
disallow_untyped_defs = true   # require annotations on all functions
ignore_missing_imports = true  # for untyped third-party libs
```

**Alternatives you will encounter:**

| Checker | Notes |
|---|---|
| **pyright** (Microsoft) | Powers Pylance in VS Code. Faster than mypy, stricter in places. `pyright` CLI. |
| **pyre** (Meta) | Scales to very large monorepos. |
| **Ruff** | Does not do deep type checking — lint only. Use alongside mypy/pyright. |

All checkers understand the same PEP 484 annotations; they differ in inference and error messages. Large codebases often enable `mypy` or `pyright` in CI and require `mypy --strict` for new modules.

A minimal annotated file that passes `mypy --strict`:

```python
"""example — strict mypy demo."""

from collections.abc import Sequence

def average(values: Sequence[float]) -> float:
    """Return the arithmetic mean of *values*.

    Raises:
        ValueError: If *values* is empty.
    """
    if not values:
        raise ValueError("values must not be empty")
    return sum(values) / len(values)

print(average([1.0, 2.0, 3.0]))  # 2.0
```

## 6. How to Structure a File

PEP 8 prescribes a module layout. Following it makes every file scannable: a new reader knows *where* to look for imports, constants, and entry points without reading top-to-bottom.

### 6.1 Canonical File Template

```python
#!/usr/bin/env python3
"""mypackage.core — one-line summary.

Longer description if needed. Explain the module's purpose, not every
function (those have their own docstrings).
"""

# 1. Future imports (if any) — must be first
from __future__ import annotations

# 2. Standard library imports
import os
import sys
from pathlib import Path

# 3. Third-party imports
import requests

# 4. Local / relative imports
from . import utils
from .config import Settings

# 5. Module-level constants (UPPERCASE)
DEFAULT_TIMEOUT = 30.0
MAX_RETRIES = 3

# 6. Module-level globals (discouraged — prefer constants or class state)
# _cache: dict[str, str] = {}  # if truly needed, leading underscore

# 7. Class definitions
class Processor:
    """Process records."""

    def __init__(self, settings: Settings) -> None:
        self.settings = settings

    def run(self, data: list[str]) -> list[str]:
        """Run processing pipeline."""
        return [self._process_one(x) for x in data]

    def _process_one(self, item: str) -> str:
        return item.strip().upper()

# 8. Function definitions
def main(argv: list[str] | None = None) -> int:
    """CLI entry point."""
    import argparse
    parser = argparse.ArgumentParser(description="Process records.")
    parser.add_argument("input", help="input file")
    args = parser.parse_args(argv)
    print(f"Processing {args.input}")
    return 0

# 9. Dunder guard — last in file
if __name__ == "__main__":
    raise SystemExit(main())
```

Why this order matters:

- **Docstring first** — `help(module)` shows it; tools extract it.
- **`__future__` imports first** — required by the parser.
- **Imports grouped and sorted** — deterministic, no hidden dependencies.
- **Constants before classes/functions** — definitions can reference them.
- **Classes/functions before imperative code** — import side effects are minimized; the module is safe to `import` without running anything.
- **`if __name__ == "__main__"` last** — clearly marks the script entry point; absent in pure library modules.

### 6.2 What Not to Do at Top Level

```python
# Bad — side effects at import time
print("loading module")           # runs on every import
data = open("config.json").read() # I/O at import — slow, untestable, surprising
result = expensive_computation()  # same

# Good — side effects behind functions or the main guard
def load_config(path: str = "config.json") -> dict:
    with open(path, encoding="utf-8") as f:
        import json
        return json.load(f)

def expensive_computation() -> int:
    return sum(i * i for i in range(10000))

if __name__ == "__main__":
    print(expensive_computation())
```

Reason: `import mypackage.core` should be *cheap and safe*. Code that runs unconditionally at import time makes testing, mocking, and parallel imports painful. Defer work to functions.

### 6.3 `__all__` and Public API

For package `__init__.py` or any module that re-exports names:

```python
# mypackage/__init__.py
"""mypackage — public API."""

from .core import Processor, process_data
from .config import Settings

__all__ = ["Processor", "process_data", "Settings"]
```

With `__all__`, `from mypackage import *` imports only those three, and documentation tools know what to surface. Without it, `import *` imports every non-underscore name — usually a mistake.

## 7. Comments — When and How

PEP 8 distinguishes **block comments**, **inline comments**, and **docstrings**. Use each where it belongs.

### 7.1 Block Comments

One or more lines starting with `#`, indented to the surrounding code, complete sentences with a period. Use to explain *why*, not *what*.

```python
# We retry with exponential backoff because the upstream API throttles
# aggressively under load. See https://api.example.com/docs/rate-limits.
for attempt in range(MAX_RETRIES):
    try:
        return fetch(url)
    except TimeoutError:
        if attempt == MAX_RETRIES - 1:
            raise
        time.sleep(2 ** attempt)
```

Block comments precede the code they describe, separated by no blank line from it.

### 7.2 Inline Comments

Same-line `#` comments, separated by at least two spaces from code:

```python
x = x + 1                 # compensate for border
total = price * quantity  # type: ignore[operator]  # noqa — linter overrides live here too
```

Use sparingly — if a line needs an inline comment to be understood, consider renaming variables or extracting a function instead.

### 7.3 TODO and Other Conventions

```python
# TODO(ada): handle pagination — API returns at most 100 items
# FIXME: this breaks when input contains NUL bytes
# HACK: workaround for upstream bug #42, remove when fixed in v2.1
# NOTE: the order here matters because later steps depend on earlier normalization
```

These are searchable markers. Many teams enforce formats like `TODO(username):` via linter rules.

### 7.4 Linter Directives — When to Silence a Tool

Occasionally a tool is wrong or a rule should not apply to one line. Silence *narrowly*:

```python
import typing

x: int = typing.cast(int, some_dynamic_value)  # noqa: F401 — false positive example

# Black: skip formatting for a hand-aligned table
# fmt: off
MATRIX = [
    [1, 0, 0],
    [0, 1, 0],
    [0, 0, 1],
]
# fmt: on

# mypy: ignore a specific error code on one line
result = legacy_function()  # type: ignore[no-untyped-call]

# pylint: disable one check for a block
# pylint: disable=invalid-name
myVar = 1  # legacy API requires this spelling
# pylint: enable=invalid-name
```

Rules for silencing:

- Always specify the **code** being silenced (`noqa: F401`, `type: ignore[attr-defined]`), never bare `noqa` / `type: ignore`.
- Prefer fixing the underlying issue; silencing is a last resort.
- Add a brief reason after the directive if the intent is not obvious.

## 8. Putting It All Together — A Realistic File

```python
#!/usr/bin/env python3
"""wordcount — count words in text files.

Example:
    $ python -m wordcount sample.txt
    sample.txt: 42 words
    $ python -m wordcount --top 5 sample.txt
    the: 6
    and: 4
    ...
"""

from __future__ import annotations

import argparse
import collections
import re
import sys
from collections.abc import Iterable
from pathlib import Path

_WORD_RE = re.compile(r"\b\w+\b")
DEFAULT_TOP = 10


def tokenize(text: str) -> list[str]:
    """Return lowercase word tokens from *text*."""
    return [m.group(0).lower() for m in _WORD_RE.finditer(text)]


def count_words(tokens: Iterable[str]) -> collections.Counter[str]:
    """Count occurrences of each token."""
    return collections.Counter(tokens)


def most_common(counter: collections.Counter[str], n: int = DEFAULT_TOP) -> list[tuple[str, int]]:
    """Return the *n* most common words."""
    return counter.most_common(n)


def process_file(path: Path) -> collections.Counter[str]:
    """Read *path* and return word counts.

    Raises:
        FileNotFoundError: If *path* does not exist.
        OSError: On I/O errors.
    """
    text = path.read_text(encoding="utf-8")
    return count_words(tokenize(text))


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(description="Count words in text files.")
    parser.add_argument("files", nargs="+", type=Path, help="files to process")
    parser.add_argument("--top", type=int, default=DEFAULT_TOP, help="show top N words")
    args = parser.parse_args(argv)

    exit_code = 0
    for path in args.files:
        try:
            counter = process_file(path)
        except FileNotFoundError:
            print(f"error: {path}: file not found", file=sys.stderr)
            exit_code = 1
            continue
        total = sum(counter.values())
        print(f"{path}: {total} words")
        for word, count in most_common(counter, args.top):
            print(f"  {word}: {count}")
    return exit_code


if __name__ == "__main__":
    raise SystemExit(main())
```

What makes this idiomatic:

- Module docstring explains usage.
- Imports sorted in three groups; stdlib only here.
- Constants `UPPERCASE`, compiled regex precomputed at module level.
- Each function has a docstring, type hints, and a single responsibility.
- `main` returns an exit code; the `__main__` guard maps it to the process status.
- No top-level side effects — `import wordcount` does nothing except define names.

## 9. Editor and CI Integration

Style without automation decays. Wire tools into the places you already work:

| Place | How |
|---|---|
| **Editor on save** | VS Code: set `"editor.formatOnSave": true`, default formatter to Black, enable `isort` and `Ruff` extensions. PyCharm: enable Black/isort in Tools → External Tools or use the Ruff plugin. |
| **Pre-commit hook** | `pre-commit install` with the config from Section 5.2 — blocks commits that violate style. |
| **CI** | Run `black --check`, `ruff check`, `mypy` in GitHub Actions / GitLab CI and fail the build on violations. |
| **CI with auto-fix bot** | Some teams run `pre-commit autoupdate` or a bot that pushes formatting commits. |

A minimal GitHub Actions snippet:

```yaml
# .github/workflows/lint.yml
name: lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install black ruff mypy
      - run: black --check .
      - run: ruff check .
      - run: mypy .
```

## 10. Summary

- PEP 8 is the community's layout and naming contract. PEP 20 gives the philosophy behind it; PEP 257 specifies docstring form.
- Follow the rules for indentation (4 spaces), line length (79/72 or a team-agreed 88/100), blank lines, import grouping, whitespace, naming (`PascalCase` classes, `snake_case` functions, `UPPERCASE` constants), and comparisons (`is None`, truthiness, `isinstance`).
- PEP 257: every public module/class/function deserves a docstring — one-line for obvious cases, multi-line with Args/Returns/Raises for the rest. Comments explain *why*; docstrings explain *what/how to use*.
- Automate: **lint** with flake8/pylint (or **Ruff**), **format** with **Black** + **isort**, **type-check** with **mypy** (or pyright). Wire them into editor, pre-commit, and CI so style is never a manual task.
- Structure a file: shebang → docstring → `__future__` → stdlib → third-party → local imports → constants → classes → functions → `if __name__ == "__main__"` guard. No top-level side effects.
- When a tool must be silenced, do so narrowly with an explicit code (`# noqa: F401`, `# type: ignore[attr-defined]`).

With these habits, your code will look like it was written by the same author as the standard library — which is precisely the point.
