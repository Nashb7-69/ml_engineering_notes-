# 00.1 What is Python

Python is a high-level, general-purpose programming language designed to maximize readability, developer productivity, and correctness. It is dynamically and strongly typed, garbage-collected, multi-paradigm (procedural, object-oriented, and functional styles coexist), and built on the principle that *everything is an object*. If you already program in languages like Java, C++, JavaScript, or Go, Python will feel familiar at the control-flow level — variables, loops, functions, and classes all exist — but its execution model, object system, and philosophy differ in fundamental ways that this lesson makes precise.

---

## 1. Definition at a Glance

At the implementer level, the most accurate one-sentence description of modern Python is:

> **Python is a dynamically typed, garbage-collected language whose reference implementation compiles source to bytecode and executes that bytecode on a virtual machine, where every value is a heap-allocated object described by a type, a reference count, and a value.**

Unpacking that sentence gives you most of Python's character:

| Property | What it means in Python |
|---|---|
| **High-level** | You do not manage memory manually, pointer arithmetic does not exist, and the standard library abstracts operating system details. |
| **General-purpose** | Not domain-specific. Suitable for scripting, web backends, data analysis, automation, tooling, and teaching. |
| **Dynamically typed** | Variable names are not bound to types. Types live on *objects*, not on variables. Type checks happen at runtime. |
| **Strongly typed** | The runtime will not silently coerce unrelated types. `"3" + 4` raises `TypeError`; it does not produce `"34"` or `7`. |
| **Garbage-collected** | Objects are freed automatically. CPython uses reference counting plus a cyclic garbage collector. |
| **Everything is an object** | Integers, functions, classes, modules, and even `None` are objects with identity, type, attributes, and methods. |
| **Bytecode-compiled** | Source (`.py`) is compiled to bytecode (`.pyc` in `__pycache__`) and run on the Python VM. This is automatic and mostly invisible. |
| **Multi-paradigm** | You can write imperative scripts, class hierarchies, or functional pipelines (first-class functions, closures, comprehensions) — often mixed in one file. Idiomatic Python leans procedural + OOP with functional seasoning. |

A small demonstration of several of these at once:

```python
# Every value is an object — even an integer has methods and attributes.
x = 42
print(type(x))        # <class 'int'>
print(isinstance(x, object))  # True — everything inherits from object
print(x.bit_length()) # 6 — int objects carry methods
print(dir(x)[:5])     # ['__abs__', '__add__', ...] — dunder methods define behavior

# Types live on objects, not variables: the same name can rebound to any type.
name = "Ada"
print(type(name))  # <class 'str'>
name = 42
print(type(name))  # <class 'int'> — the name was rebound, no declaration needed

# Strong typing: no implicit cross-type coercion
try:
    result = "age: " + 42
except TypeError as exc:
    print(exc)  # can only concatenate str (not "int") to str

# But explicit conversion is idiomatic
result = "age: " + str(42)
print(result)  # age: 42
```

What this code demonstrates:

- `type()` and `isinstance()` reveal that values carry their type.
- Rebinding a name to a different type is legal — the name `name` is just a label pointing at an object.
- The `TypeError` on `"age: " + 42` proves strong typing: Python refuses to guess whether you wanted string concatenation or numeric addition. The Zen principle *explicit is better than implicit* is enforced by the type system.

## 2. History

### 2.1 Origins: Guido van Rossum and ABC

Python was created by **Guido van Rossum**, a Dutch programmer working at CWI (Centrum Wiskunde & Informatica) in the Netherlands. Work began in **December 1989** as a holiday project; the first public release (**Python 0.9.0**) appeared in **February 1991**.

Key influences:

- **ABC language** — an experimental teaching language Guido helped build at CWI. ABC contributed Python's use of indentation for grouping, high-level data types (lists, dicts), and emphasis on readability. Guido has called ABC a direct predecessor: many ABC ideas succeeded; its closed, monolithic environment failed, and Python was designed to be open and extensible instead.
- **C and Unix** — Python was implemented in C from day one and designed to interoperate with C libraries and Unix system calls.
- **Modula-3** — influenced the module and exception system.
- **Monty Python** — the name itself comes from the British comedy group *Monty Python's Flying Circus*, not the reptile. Guido wanted a short, slightly irreverent name. Expect Monty Python references throughout the documentation and examples (`spam`, `eggs`, `knights`).

### 2.2 Timeline

| Year | Version / Event | Significance |
|---|---|---|
| 1989–1990 | Conception at CWI | Guido starts Python as a successor to ABC for the Amoeba distributed OS project. |
| 1991 | **0.9.0** | Initial public release. Modules, classes, exceptions, functions, `str`/`list`/`dict` already present. |
| 1994 | **1.0** | Functional tools (`map`, `filter`, `reduce`, `lambda`). |
| 2000 | **2.0** | List comprehensions, cycle-detecting garbage collector, unified `int`/`long` groundwork. Introduction of `PEP` process (see PEP 1). |
| 2001 | PEP 20 — *The Zen of Python* | Codifies design philosophy. |
| 2008 | **3.0 (Python 3000)** | Major *backward-incompatible* cleanup: `print` statement → function, `str` is always Unicode, `int`/`long` unified, `xrange` → `range`, iterator-centric APIs. |
| 2010 | **2.7** | Last 2.x release, intentionally made to overlap with 3.x for migration. Originally EOL 2015, extended to **2020-01-01**. |
| 2014–present | **3.4 → 3.13+** | `async`/`await` (3.5), f-strings (3.6), data classes (3.7), walrus operator (3.8), structural pattern matching `match`/`case` (3.10), major speedups (3.11's Faster CPython, ~25% faster), `except*` and improved error messages (3.11/3.12). |

### 2.3 Python 2 vs Python 3 — Why It Matters to You

If you encounter older tutorials, StackOverflow answers, or enterprise code that says `print x` or `xrange`, that is Python 2. The two lineages coexisted for twelve years (2008–2020), which caused real fragmentation. Today the distinction is settled:

- **Python 2 is dead.** No security patches since 2020. Do not start new projects in it. If you inherit Python 2 code, port it.
- **Python 3 is Python.** When anyone says "Python" without qualification in 2026, they mean Python 3 (currently 3.12 or 3.13 in most environments; details in Lesson 00.2).
- The migration pain was deliberate: Python 3 fixed design mistakes that could not be fixed without breaking compatibility. The most important fix was the string model.

```python
# Python 2 (historical — do NOT write this)
# print "hello"        # statement, not a function
# name = raw_input()   # vs input() which eval'd
# s = "café"           # bytes masquerading as text

# Python 3 (current)
print("hello")          # function — composable, overridable
name = input()          # always returns str (text)
s = "café"              # str is Unicode text; b"..." is bytes
data = "café".encode("utf-8")  # b'caf\xc3\xa9' — explicit encoding
print(type(s), type(data))     # <class 'str'> <class 'bytes'>
```

The `str` vs `bytes` split is the clearest practical win: in Python 2, text and binary data were conflated, which caused encoding bugs that only surfaced with non-ASCII input. In Python 3 they are distinct types and mixing them is a `TypeError`, forcing you to be explicit about encodings. That is strong typing in service of correctness.

Other notable cleanups (as a reference if you read legacy code):

| Python 2 | Python 3 | Why it changed |
|---|---|---|
| `print x` | `print(x)` | Uniformity — everything else is a function call. |
| `xrange(n)` | `range(n)` | Old `range` built a list; new `range` is a lazy sequence. |
| `dict.keys()` returns list | `dict.keys()` returns view | Views are lazy and reflect mutations. |
| `5 / 2 == 2` | `5 / 2 == 2.5`, `5 // 2 == 2` | True division is the default; `//` is explicit floor division. |
| `cmp(a, b)` | Removed (use `key=` functions) | Simpler sorting model. |

You do not need to memorize the full migration guide, but recognize the symptoms if you copy a snippet and it fails with `SyntaxError` on `print`.

## 3. Implementations

"Python" describes a *language specification* (plus a de facto reference behavior). Multiple programs implement that specification. When someone says "Python 3.12.4," they almost always mean **CPython 3.12.4**.

### 3.1 CPython — The Reference

- **Written in C**, maintained by the Python core team, hosted at [python.org](https://www.python.org).
- The implementation you get from `python.org` installers, most Linux package managers, and `pyenv`.
- Compiles `.py` → bytecode (`.pyc`) → executes on a stack-based VM written in C.
- Defines the language: if CPython does it, that *is* the behavior (other implementations follow).
- Has the **GIL (Global Interpreter Lock)** — in standard 3.12 and earlier, only one thread executes Python bytecode at a time. This simplifies memory management but limits CPU-bound threading. Python 3.13 introduces an experimental *free-threaded* build (`--disable-gil`) that removes the GIL; the ecosystem is still adapting.
- Includes the broadest C-extension ecosystem (NumPy, etc., target CPython's C API).

You will use CPython unless you have a specific reason not to.

### 3.2 Other Important Implementations

| Implementation | Language | Key idea | When to consider it |
|---|---|---|---|
| **PyPy** | RPython (subset of Python) → C | JIT compiler; often 3–7× faster on tight loops, compatible with pure-Python code. | CPU-bound pure-Python workloads where NumPy is not involved. Slower startup, higher memory, weaker C-extension compat. |
| **Jython** | Java | Runs on the JVM; can import Java classes as if they were Python modules. | Integrating Python scripting into a Java application. Stuck on Python 2.7 syntax; largely dormant. |
| **IronPython** | C# | Runs on .NET CLR; interoperates with C# libraries. | Scripting inside .NET. Python 3 support via IronPython 3. |
| **GraalPy** | Java (GraalVM) | Polyglot VM; runs Python alongside Java, JS, Ruby with low interop overhead. | Polyglot enterprise GraalVM stacks. |
| **MicroPython** | C | Lean Python for microcontrollers (ESP32, RP2040). Subset of stdlib. | Embedded / bare-metal hardware with kilobytes of RAM. |
| **CircuitPython** | C (fork of MicroPython) | Adafruit's beginner-friendly MicroPython variant. | Education and hobbyist hardware. |
| **Stackless Python** | C (CPython fork) | Microthreads / tasklets without OS threads. | Historically used in EVE Online server; concepts merged partly into `asyncio`. |
| **Brython / Skulpt / Pyodide** | JS / WASM | Run Python in the browser. Pyodide compiles CPython to WebAssembly. | Browser-based editors, notebooks, demos. Not for production backends. |
| **Cython** | Python-like → C | Superset that compiles to C extensions. Not a standalone runtime. | Speeding hot spots by adding static types. |

Practical takeaway: **write for CPython; be aware PyPy exists** if profiling shows interpreter overhead. For hardware or browser demos, the micro/browser ports are deliberately incomplete — check their docs before assuming stdlib availability.

A quick way to see which you are running:

```python
import platform
import sys

print(platform.python_implementation())  # 'CPython', 'PyPy', etc.
print(sys.version)          # '3.12.4 (main, Jun  6 2024, ...) [GCC ...]'
print(sys.implementation)   # namespace with name, version, cache_tag
```

## 4. Philosophy

### 4.1 The Zen of Python (PEP 20)

Run this in any interpreter:

```python
import this
```

It prints nineteen aphorisms by Tim Peters that guide language design. The full text:

```
The Zen of Python, by Tim Peters

Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
Complex is better than complicated.
Flat is better than nested.
Sparse is better than dense.
Readability counts.
Special cases aren't special enough to break the rules.
Although practicality beats purity.
Errors should never pass silently.
Unless explicitly silenced.
In the face of ambiguity, refuse the temptation to guess.
There should be one-- and preferably only one --obvious way to do it.
Although that way may not be obvious at first unless you're Dutch.
Now is better than never.
Although never is often better than *right* now.
If the implementation is hard to explain, it's a bad idea.
If the implementation is easy to explain, it may be a good idea.
Namespaces are one honking great idea -- let's do more of those!
```

These are not decorative. They have concrete consequences:

- **"Readability counts" / "Explicit is better than implicit"** → `import` is explicit, indentation is syntactically meaningful, and APIs avoid hidden magic. Compare Python's `len(obj)` (explicit protocol `__len__`) with languages that hide length behind `.length` vs `.size()` vs `.count` inconsistently.
- **"There should be one obvious way"** → stdlib prefers a single idiomatic path (e.g., one recommended way to format strings in modern code: f-strings) even if older alternatives remain for compatibility.
- **"Errors should never pass silently"** → bare `except: pass` is a code smell. Python makes you name the exception you are silencing.
- **"Flat is better than nested"** → deep nesting triggers refactoring (guard clauses, early returns).

Try reading `import this` as a checklist during code review; many PEP 8 and stdlib design choices trace directly to a Zen line.

### 4.2 "Batteries Included"

Python ships with a large standard library — *batteries included* — so common tasks need no third-party install:

- `pathlib` / `os` / `shutil` for filesystem work
- `datetime`, `zoneinfo` for dates and time zones
- `json`, `csv`, `sqlite3` for data formats
- `http.server`, `urllib`, `email` for basic networking
- `unittest`, `argparse`, `logging`, `collections`, `itertools`, `functools`

This is a deliberate contrast with minimalist languages that ship almost nothing and push you to an ecosystem immediately. The battery set is curated conservatively: modules are added slowly and removed rarely, which keeps long-running scripts stable but means the freshest tools (e.g., HTTP clients, async frameworks) live on PyPI, not in the stdlib.

### 4.3 Readability as a Feature

Python treats readability as a performance feature for *humans*:

- **Indentation defines blocks.** There are no braces. A miscounted indent is a `IndentationError`, not a silent logic bug.
- **One statement per line** is idiomatic. Semicolons can separate statements but are discouraged except in throwaway cases.
- ** snake_case for functions/variables, `PascalCase` for classes** — conventions carry meaning (expanded in Lesson 00.4).
- **Comprehensions and context managers** replace boilerplate loops and try/finally blocks with declarative forms that read like English.

## 5. Use Cases and Non-Use Cases

### 5.1 Where Python Excels

| Domain | Typical libraries / tools | Why Python fits |
|---|---|---|
| **Scripting & automation** | `pathlib`, `subprocess`, `argparse`, `shlex`, `re` | Fast to write, readable in six months, excellent OS interop, no compile step. |
| **Web backends & APIs** | Django, Flask, FastAPI, SQLAlchemy, Starlette | Mature frameworks, ORMs, and deployment stories; async support since 3.5. |
| **Data analysis & ML** | NumPy, pandas, Matplotlib, scikit-learn, PyTorch | C-backed numeric libraries give C speed with Python ergonomics; the lingua franca of the field. |
| **DevOps & infrastructure** | Ansible, SaltStack, AWS CLI / boto3, Fabric | Agent + library ecosystem matches ops workflows. |
| **Testing & tooling** | pytest, tox, mypy, black, ruff | Meta-programming and introspection make great tooling platforms. |
| **Education** | stdlib only | Minimal syntax to trip over; errors tend to be descriptive. |

### 5.2 Where Python Is a Weaker Fit

| Concern | Symptom | Mitigation |
|---|---|---|
| **CPU-bound single-threaded speed** | Pure-Python tight loops can be 20–100× slower than C/Rust/Go. | Push hot loops into NumPy / C extensions / Cython / PyPy / `numba`. |
| **GIL limits CPU parallelism with threads** | `threading` helps I/O concurrency, not CPU. | Use `multiprocessing`, `concurrent.futures.ProcessPoolExecutor`, or free-threaded 3.13+; `asyncio` for I/O. |
| **Mobile / browser native apps** | No first-class iOS/Android toolchain. | Kivy / BeeWare exist but are niche; prefer platform-native stacks. |
| **Hard real-time / tiny memory** | GC pauses, heap allocation, late binding. | MicroPython for micros; C/Rust for hard RT. |

Net: Python optimizes for *developer time* over *machine time* by default. When machine time dominates, the idiomatic move is to keep Python as the orchestration layer and delegate number crunching to compiled code — a pattern the data stack embodies explicitly.

## 6. Python's Tradeoffs — A Systems View

| Tradeoff | What you gain | What you pay | Idiomatic response |
|---|---|---|---|
| **Dynamic typing** | Rapid prototyping, less boilerplate, powerful metaprogramming, REPL-driven exploration. | Type errors surface at runtime; large refactors need tooling. | Add gradual types (`mypy`/`pyright`) + tests for large codebases. |
| **Interpreted + GC'd** | No manual malloc/free, no borrow checker to satisfy, quick edit-run cycle. | Higher memory footprint, GC pauses, less predictable latency. | Profile (`cProfile`, `tracemalloc`), then optimize hot paths. |
| **High-level data structures built in** | `list`, `dict`, `set` are fast, built in C, and syntactically light. | Abstractions hide cost (e.g., `dict` resize, `list` over-allocation) | Learn asymptotic costs (Section 8 below gives the object model to reason about them). |
| **Batteries included** | Stable stdlib, fewer dependencies. | Stdlib evolves slowly; newest patterns live outside. | Use stdlib for foundations, PyPI for innovation. |

## 7. Dynamic Typing, Strong Typing, and Gradual Typing

These three terms are often conflated. Python cleanly separates them.

- **Dynamic typing** — *when* types are checked. In Python, a name has no declared type; the object it points to does. `x = 3; x = "hi"` is legal. The check `x + 1` happens when that line runs, not when the file is compiled.

- **Strong typing** — *how strictly* types are enforced. Python is strong: it rarely coerces across unrelated types implicitly. Compare JavaScript (`"3" + 4 === "34"`), where the `+` coerces, with Python which raises.

- **Gradual (optional) typing** — *whether* you can add static type hints. Since PEP 484 (Python 3.5), you can annotate with `x: int = 3` and check with `mypy`/`pyright` *without* changing runtime behavior. Hints are ignored at runtime unless you introspect them.

```python
# Dynamic: names are labels, objects have types.
x = [1, 2, 3]
print(type(x))  # <class 'list'>
x = {1, 2, 3}
print(type(x))  # <class 'set'> — same name, different object type

# Strong: no silent coercion.
print(3 + 4.5)    # 7.5 — int + float is defined (numeric tower)
print(True + 1)   # 2 — bool is a subclass of int (historical, intentional)
# print("3" + 4)  # TypeError — str + int is NOT defined

# Explicit is correct:
print("3" + str(4))   # "34" — you said you wanted string concatenation
print(int("3") + 4)   # 7    — you said you wanted numeric addition

# Gradual typing: annotations are hints, not runtime contracts (by default).
def greet(name: str) -> str:
    return f"Hello, {name}!"

print(greet("Ada"))   # Hello, Ada!
print(greet(42))      # Hello, 42! — runs fine, type checker would flag it
# mypy would report: error: Argument 1 to "greet" has incompatible type "int"

# If you WANT runtime enforcement, add it explicitly:
def strict_greet(name: str) -> str:
    if not isinstance(name, str):
        raise TypeError(f"name must be str, got {type(name).__name__}")
    return f"Hello, {name}!"
```

Common mistake: treating `x: int` as a runtime guarantee. It is not. The runtime disregards it. The guarantee comes from running `mypy` in CI and from defensive `isinstance` checks at API boundaries.

The `bool`-is-`int` case surprises newcomers:

```python
print(isinstance(True, int))  # True
print(True == 1, True is 1)   # True, False — equal value, different identity
print(False + False + True)   # 1 — booleans sum as ints
# This is intentional (PEP 285) for backward compatibility and is relied upon
# by code that counts truthy values: sum(x > 0 for x in data)
```

## 8. Garbage Collection — How Python Frees Objects

Python manages memory automatically. Most objects die as soon as nothing references them.

### 8.1 Reference Counting (primary mechanism, CPython)

Every Python object in CPython carries a `ob_refcnt` field. Assigning a name or appending to a container increments it; deleting a name or removing from a container decrements it. When the count hits zero, the object's `__del__`-equivalent deallocator runs immediately and memory is reclaimed.

```python
import sys

a = [1, 2, 3]
print(sys.getrefcount(a))  # e.g. 2 — one from `a`, one from the argument to getrefcount

b = a              # alias — refcount increments
print(sys.getrefcount(a))  # 3

del b              # remove one reference
print(sys.getrefcount(a))  # 2

# Containers hold references, not copies:
container = [a]
print(sys.getrefcount(a))  # 3 — container[0] points to the same list object
print(container[0] is a)   # True — identity check, same object
```

Implication: aliasing is the default. `b = a` does not copy the list; it creates a second name pointing at the same object. Mutating through one name is visible through the other — the most common source of "why did my list change over there?" bugs.

```python
# Aliasing vs copying — a critical distinction
original = [1, 2, 3]
alias = original          # same object
shallow = original.copy() # new list, same element objects
print(alias is original)    # True
print(shallow is original)  # False
print(shallow == original)  # True — equal values, different containers

alias.append(4)
print(original)   # [1, 2, 3, 4] — alias mutated the shared object
print(shallow)    # [1, 2, 3]    — copy is independent (for flat lists)
```

### 8.2 Cycle Collector (for reference cycles)

Reference counting alone cannot free cycles:

```python
# A reference cycle — neither object's count can reach zero by decrements alone
a = {}
b = {}
a["b"] = b
b["a"] = a
del a
del b
# The two dicts still reference each other. CPython's cyclic GC (enabled by default)
# periodically traces container objects (list, dict, set, user classes) and frees
# unreachable cycles. No action needed from you unless you define __del__.
```

The `gc` module lets you inspect and tune this:

```python
import gc
print(gc.isenabled())   # True
print(gc.get_threshold())  # (700, 10, 10) — generation thresholds
# gc.collect()  # force a collection — rarely needed
```

### 8.3 What This Means for Your Code

- Do not rely on deterministic finalization via `__del__`. Use context managers (`with open(...) as f:`) for prompt resource release.
- Avoid creating unbounded cycles in hot paths if you care about pause times (or call `gc.disable()` in latency-sensitive sections with care).
- For files, sockets, and locks, *explicit close* via `with` is idiomatic precisely because GC timing is not prompt for cycles.

## 9. Everything Is an Object — The Object Model

If dynamic typing explains Python's flexibility and GC explains its memory style, the object model explains its uniformity.

In Python, *every* value is an object with three properties:

1. **Identity** — where it lives in memory (`id(obj)`, unique for its lifetime).
2. **Type** — what it is and what it can do (`type(obj)`, pointer to a type object).
3. **Value** — the data it holds (which may be mutable or immutable).

This is true for values you might not expect to be objects in other languages.

```python
# Even "primitive" things are full objects
for obj in [42, 3.14, "hello", b"bytes", True, None]:
    print(f"{obj!r:12}  id={id(obj):<12} type={type(obj).__name__:10} is_object={isinstance(obj, object)}")

# Functions are objects — they have attributes and can be passed around
def square(n: int) -> int:
    """Return n squared."""
    return n * n

print(type(square))          # <class 'function'>
print(square.__name__)       # 'square'
print(square.__doc__)        # 'Return n squared.'
print(callable(square))      # True

# You can attach attributes to functions (unusual but legal)
square.calls = 0  # type: ignore[attr-defined]

# Classes are objects, and types are objects
print(type(int))    # <class 'type'> — int is an instance of type
print(type(type))   # <class 'type'> — type is an instance of itself
print(isinstance(int, object))  # True

# Modules are objects
import math
print(type(math))        # <class 'module'>
print(math.__name__)     # 'math'
print(math.pi)           # 3.14159...

# None is a singleton object
print(type(None))        # <class 'NoneType'>
print(None is None)      # True — identity check for singletons
x = None
print(x is None)         # True — idiomatic None check uses `is`, not `==`
```

Why `is` for `None`? Because `None` is a singleton — there is only one `None` object per interpreter. `is` tests identity (same address), which is faster and more precise than `==` (which could be overridden by `__eq__`). The same applies to other singletons like `True`/`False` in identity-sensitive code, though `==` is fine for booleans in most application logic.

A deeper look at attributes and dunder methods:

```python
# Objects communicate via the dunder (double-underscore) protocol.
# `len(obj)` calls `obj.__len__()`, `obj + other` calls `obj.__add__(other)`, etc.

class Demo:
    def __init__(self, value: int) -> None:
        self.value = value
    def __len__(self) -> int:
        return self.value
    def __repr__(self) -> str:
        return f"Demo({self.value})"

d = Demo(5)
print(len(d))    # 5 — len delegates to __len__
print(repr(d))   # Demo(5)
print(d.__dict__)  # {'value': 5} — instance attributes live in a dict

# Introspection works because everything is an object with discoverable attributes
print(dir(d))          # list of attribute names
print(hasattr(d, "value"))  # True
print(getattr(d, "value"))  # 5
setattr(d, "extra", 99)
print(d.extra)         # 99 — attributes can be added dynamically (for most classes)
```

The uniformity has practical consequences you will rely on constantly:

- **First-class functions** — pass `square` as an argument, return it, store it in a dict. Decorators and higher-order functions fall out naturally.
- **Introspection** — `dir()`, `help()`, `type()`, `isinstance()`, `.__dict__`, `.__class__` let you inspect any value at runtime. The REPL and debuggers exploit this.
- **Duck typing** — code cares about *what an object can do*, not what it was declared to be. If it has `__len__` and `__getitem__`, it is sequence-like enough for most purposes. Formalized gradually by `collections.abc` and `typing.Protocol`.

```python
# Duck typing in action — no interface declaration needed
def total_length(items) -> int:
    """Sum len() of each item. Works for any iterable of sized objects."""
    return sum(len(x) for x in items)

print(total_length(["hello", "world"]))  # 10
print(total_length([[1, 2], [3, 4, 5]])) # 5

# First-class functions — the object model makes this natural
def apply_twice(func, value):
    return func(func(value))

print(apply_twice(square, 2))  # 16 — square(square(2)) == square(4) == 16

# Storing functions in data structures
ops = {"square": square, "cube": lambda n: n ** 3}
print(ops["cube"](3))  # 27
```

### 9.1 Mutable vs Immutable Objects

Whether an object's *value* can change after creation determines aliasing behavior:

| Immutable (value cannot change; operations return new objects) | Mutable (value can change in place; aliasing is observable) |
|---|---|
| `int`, `float`, `bool`, `str`, `bytes`, `tuple`, `frozenset`, `None` | `list`, `dict`, `set`, `bytearray`, most user-defined classes |

```python
# Immutable: rebinding vs mutation
s = "hello"
print(id(s))
s = s + " world"      # new string object, old "hello" untouched
print(s)              # hello world

t = (1, 2, 3)
# t[0] = 99            # TypeError: 'tuple' object does not support item assignment

# Mutable: in-place change visible through aliases
a = [1, 2]
b = a
a.append(3)
print(b)              # [1, 2, 3] — b sees the mutation

# Defensive copy when you need independence
a = [1, 2]
b = list(a)           # or a.copy() or a[:]
a.append(3)
print(b)              # [1, 2]
```

This is why default mutable arguments are a classic pitfall (covered in depth in the functions chapter): the default list is a single object shared across calls.

## 10. How Python Runs Your Code

You rarely need to think about this, but the mental model helps debug import and performance issues:

```
.py source  --(compile)-->  bytecode (.pyc)  --(execute)-->  Python VM  -->  result
```

- On first import, CPython compiles each `.py` file to bytecode and caches it as `__pycache__/module.cpython-312.pyc`. Subsequent imports load the cached bytecode if the source has not changed.
- Running `python script.py` compiles and executes without necessarily writing a `.pyc` (though `PYTHONDONTWRITEBYTECODE` aside, imports still cache).
- You can inspect bytecode with the `dis` module — rarely needed, useful when optimizing or learning.

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
#  0 RESUME                   0
#  1 LOAD_FAST                0 (a)
#  2 LOAD_FAST                1 (b)
#  3 BINARY_OP                0 (+)
#  4 RETURN_VALUE
```

## 11. Common Misconceptions — Distinctions That Matter

| Misconception | Reality |
|---|---|
| "Python is interpreted, so it has no compilation" | It *is* compiled — to bytecode, automatically. The compilation step is just hidden. |
| "Variables have types" | *Names* have no type; *objects* do. `x: int = 3` is a hint for tools, not a runtime constraint. |
| "Python is weakly typed because it is dynamic" | It is dynamically *and* strongly typed. Dynamic says *when* checking happens; strong says *how strictly* coercion is refused. |
| "Everything is an object means everything is slow" | Object uniformity costs something, but `list`/`dict`/`int` internals are highly optimized C. Hot loops still benefit from pushing work into built-ins and C extensions. |
| "Garbage collection means I can ignore resources" | GC reclaims *memory*; it does not promptly close files or release locks. Use `with` for resources. |
| "There are primitives vs objects" | No. `int` and `str` are objects. There is no unboxed primitive tier visible to Python code (small-int caching is an invisible CPython optimization). |

## 13. Summary

- Python is a high-level, dynamically and strongly typed, garbage-collected language where every value is an object. Source is compiled to bytecode and run on a VM — most visibly CPython.
- Created by Guido van Rossum (1991, successor to ABC), the language cleaned up major warts in Python 3 (text vs bytes, iterators, division). Python 2 is end-of-life; all current work is Python 3.
- CPython is the reference implementation. PyPy (JIT), MicroPython (micros), and browser ports serve niches; write for CPython by default.
- The Zen of Python and "batteries included" philosophy explain why the language favors explicit, readable, single-obvious-way APIs and a rich stdlib.
- Python trades raw CPU speed for developer speed. The idiomatic response is to keep Python as the orchestration layer and delegate hot paths to optimized built-ins and C extensions.
- Dynamic typing means types live on objects and are checked at runtime; strong typing means mismatches raise rather than coerce; gradual typing lets you add static hints checked by `mypy`/`pyright`.
- CPython reclaims memory by reference counting plus a cyclic collector. Aliasing (`b = a`) is the default — copying must be explicit.
- The object model is uniform: ints, functions, classes, and modules are all objects with identity, type, value, and introspectable attributes. Mutable vs immutable determines whether aliasing is observable.
