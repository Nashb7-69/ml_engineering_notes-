# 8.2 Generators

Generators are Python's most ergonomic tool for *lazy* iteration. A generator function looks like a normal function but contains `yield`; calling it returns a **generator object** — a special kind of iterator that suspends and resumes execution. Generator expressions provide a compact literal form. Together they enable memory-efficient pipelines, infinite sequences, and cooperative control flow.

---

## 1. Generator Functions vs Generator Objects

### 1.1 Definitions

| Term | What it is | Contains | Calling it produces |
|------|------------|----------|---------------------|
| **Generator function** | A function defined with `def` that contains `yield` (or `yield from`) anywhere in its body | `yield` statement/expression | A generator object (an iterator) |
| **Generator object** | The iterator returned by a generator function | Execution frame + suspension point | Values via `__next__` / `send` |

The presence of `yield` in the *function body* — even unreachable — turns the entire function into a generator function:

```python
import inspect

def regular():
    return 42

def gen_func():
    yield 1

def sneaky():
    if False:
        yield  # never executed, but still makes this a generator function!

print(inspect.isgeneratorfunction(regular))   # False
print(inspect.isgeneratorfunction(gen_func))  # True
print(inspect.isgeneratorfunction(sneaky))    # True

print(inspect.isgenerator(gen_func()))        # True — the object is a generator
print(inspect.isgenerator(regular()))         # False

# Calling a generator function does NOT execute its body immediately
def demo():
    print("enter demo")   # not printed until first next()
    yield 1
    print("after 1")      # not printed until second next()
    yield 2
    print("done")         # printed when generator exhausts

g = demo()
print("generator created, body not yet run")
print(next(g))  # enter demo -> 1
print(next(g))  # after 1 -> 2
try:
    next(g)     # done -> StopIteration
except StopIteration:
    print("exhausted")
```
Explanation: The function body becomes a *factory* for generator objects. Each call creates an independent generator with its own execution frame. Code inside runs only when the generator is advanced.

### 1.2 Generator objects are iterators

```python
from collections.abc import Iterator, Iterable, Generator

def countdown(n: int):
    while n > 0:
        yield n
        n -= 1

g = countdown(3)
print(isinstance(g, Iterator))   # True
print(isinstance(g, Iterable))   # True
print(isinstance(g, Generator))  # True — generators are a subtype of iterators

# So all iterator behavior applies: exhaustion, single-pass, iter(g) is g
print(list(g))  # [3, 2, 1]
print(list(g))  # [] — exhausted
```

## 2. Execution Model: Suspension and Resumption

This is the core mental model that distinguishes generators from ordinary functions.

### 2.1 How `yield` suspends

```python
def simple_gen():
    print("A: start")
    yield 1
    print("B: after first yield")
    yield 2
    print("C: end -> StopIteration")

g = simple_gen()
print("before first next")
print(f"got {next(g)}")   # A: start, got 1
print("between yields")
print(f"got {next(g)}")   # B: after ..., got 2
print("before exhaustion")
try:
    next(g)               # C: end
except StopIteration:
    print("stopped")
```
Explanation: At each `yield`, the generator:
1. Evaluates the yielded expression.
2. **Saves** its entire state: local variables, instruction pointer, exception handlers, `try` blocks.
3. Returns the value to the caller.
4. **Suspends** — the stack frame is frozen, not destroyed.
5. On the next `next()` (or `send()`), it **resumes** immediately after the `yield`.

This is cooperative — the generator decides *when* to suspend. The caller decides *when* to resume.

### 2.2 State diagram

```
  GEN_CREATED ──next()──► GEN_RUNNING ──yield──► GEN_SUSPENDED
       │                      │                      │
       │                      ├──return──► GEN_CLOSED (raises StopIteration)
       │                      └──raise──► GEN_CLOSED (propagates)
       │                      │
       └────close()──────────► GEN_CLOSED

  GEN_SUSPENDED ──next()/send()──► GEN_RUNNING
                ──throw()────────► GEN_RUNNING (exception injected)
                ──close()────────► GEN_CLOSED
```

You can inspect state via `g.gi_running`, `g.gi_frame`, and in 3.12+ `inspect.getgeneratorstate`:

```python
import inspect

def gen():
    yield 1
    yield 2

g = gen()
print(inspect.getgeneratorstate(g))  # GEN_CREATED
next(g)
print(inspect.getgeneratorstate(g))  # GEN_SUSPENDED
list(g)  # exhaust
print(inspect.getgeneratorstate(g))  # GEN_CLOSED
```

## 3. `next()`, `send()`, `throw()`, `close()` — The Generator API

Generators implement more than `__next__`. Understanding the full API unlocks coroutines and resource cleanup.

### 3.1 `next(generator)` and `generator.__next__()`

```python
def nums():
    yield 10
    yield 20

g = nums()
print(next(g))        # 10 — equivalent to g.__next__()
print(g.__next__())   # 20
# next(g, default) works for generators too:
print(next(g, "done"))  # done — no StopIteration
```

### 3.2 `generator.send(value)` — yield as an *expression*

`yield` is not just a statement; it is an expression that evaluates to the value *sent in* by the caller. `next(g)` is equivalent to `g.send(None)`.

```python
def accumulator():
    total = 0
    while True:
        # yield total pauses and evaluates to whatever caller sends
        received = yield total
        print(f"  generator received: {received!r}")
        if received is None:
            continue
        total += received

acc = accumulator()
print(f"start: {next(acc)}")     # start: 0  (primes the generator to first yield)
print(f"after send 5: {acc.send(5)}")   # generator received: 5, after send 5: 5
print(f"after send 3: {acc.send(3)}")   # generator received: 3, after send 3: 8
print(f"after send None: {acc.send(None)}")  # generator received: None, 8

# Realistic pattern: running average coroutine
def running_average():
    total = 0.0
    count = 0
    avg = None
    while True:
        value = yield avg
        if value is None:
            continue
        total += value
        count += 1
        avg = total / count

avg_gen = running_average()
next(avg_gen)  # prime
print(avg_gen.send(10))  # 10.0
print(avg_gen.send(20))  # 15.0
print(avg_gen.send(30))  # 20.0

# Gotcha: first send must be None (use next() to prime)
# g = accumulator()
# g.send(5)  # TypeError: can't send non-None value to a just-started generator
```
Explanation: To send a value, the generator must already be suspended at a `yield`. On creation it is not — you must prime it with `next(g)` first. The *first* `yield` expression then receives the sent value.

### 3.3 `generator.throw(exc_type, exc_val, tb)`

Injects an exception at the suspension point — as if the `yield` raised it.

```python
def resilient():
    try:
        while True:
            try:
                val = yield "ready"
                print(f"got {val}")
            except ValueError as e:
                print(f"caught ValueError inside generator: {e}")
                yield f"recovered from {e}"
    except GeneratorExit:
        print("GeneratorExit — generator is being closed")
        return

r = resilient()
print(next(r))              # ready
print(r.throw(ValueError, ValueError("oops")))  # caught ..., recovered from oops
print(next(r))              # ready — resumes normally after recovery
r.close()                   # GeneratorExit

# Use case: timeout / cancellation signaling in cooperative pipelines
```
Explanation: `throw` lets the caller signal error conditions without a separate channel. The generator can catch and handle the exception, or let it propagate (which terminates the generator).

### 3.4 `generator.close()`

Raises `GeneratorExit` at the suspension point. If the generator does not handle it (or re-raises), it terminates cleanly. If the generator yields after catching `GeneratorExit`, Python raises `RuntimeError`.

```python
def with_cleanup():
    try:
        yield 1
        yield 2
    finally:
        print("cleanup in finally — always runs on close() or exhaustion")

g = with_cleanup()
print(next(g))  # 1
g.close()       # cleanup in finally —

# Compare: garbage collection also closes, but non-deterministically
# Always close explicitly or use context managers when cleanup matters.
# CPython's refcounting closes promptly; PyPy / other GCs may delay.

# finally runs even on normal exhaustion:
for x in with_cleanup():
    print(f"consumed {x}")
# consumed 1, consumed 2, cleanup ...
```
Explanation: `close()` is how consumers signal "I won't need more values." The generator's `finally` blocks execute, allowing resource release. This is why generators that hold resources should be used in `try/finally` or wrapped with `contextlib.contextmanager`.

## 4. `yield` vs `return` in Generators

```python
def gen_with_return(n):
    for i in range(n):
        yield i
    return "done"  # return value becomes StopIteration.value (see §8.3)

g = gen_with_return(2)
print(next(g))  # 0
print(next(g))  # 1
try:
    next(g)
except StopIteration as e:
    print(f"return value: {e.value!r}")  # 'done'

# Bare return is equivalent to return None
def gen_bare_return():
    yield 1
    return
    yield 2  # unreachable

print(list(gen_bare_return()))  # [1]

# return with value in generator — only accessible via StopIteration or yield from
```
Explanation: `return <value>` inside a generator does not produce a yielded value; it terminates the generator, attaching `value` to the `StopIteration` exception. Normal `for` loops discard this value. `yield from` captures it (covered in §8.3).

## 5. Generator Expressions (GenExps) vs List Comprehensions

### 5.1 Syntax

```python
# List comprehension — eager, builds full list in memory
squares_list = [x*x for x in range(10)]

# Generator expression — lazy, produces values on demand
squares_gen = (x*x for x in range(10))

print(type(squares_list))  # list
print(type(squares_gen))   # generator

# Genexp syntax allows omitting parens when sole argument:
total = sum(x*x for x in range(10))  # no extra parens needed
# vs sum((x*x for x in range(10)))

# Dict and set comps for comparison:
d = {x: x*x for x in range(3)}   # dict comp
s = {x*x for x in range(3)}      # set comp (no colon)
```

### 5.2 Memory and laziness

```python
import sys
import tracemalloc

# Memory: list holds all elements; generator holds only state
lst = [x for x in range(10_000)]
gen = (x for x in range(10_000))
print(sys.getsizeof(lst))  # ~80k bytes (scales with N)
print(sys.getsizeof(gen))  # ~100 bytes (constant!)

# Laziness: genexp evaluates element-by-element, only when consumed
def noisy(x):
    print(f"  computing {x}")
    return x * x

print("creating genexp — no computation yet")
g = (noisy(x) for x in range(3))
print("consuming one:")
print(next(g))  # computing 0 -> 0
print("consuming rest:")
print(list(g))  # computing 1, computing 2

# List comp computes everything immediately:
print("creating list comp — computes all now:")
lc = [noisy(x) for x in range(3)]  # computing 0,1,2 immediately
```
Explanation: GenExps are ideal when you only need to iterate once and want O(1) memory. List comps are better when you need `len()`, indexing, or multiple passes.

### 5.3 Scope and variable leakage

```python
# List comp in Python 3 has its own scope (no leakage) — genexp too
x = "original"
lst = [x for x in range(3)]
print(x)  # original — not overwritten

# But genexp is lazy — late binding pitfall
funcs = [(lambda: i) for i in range(3)]  # list comp — each lambda captures i late
print([f() for f in funcs])  # [2,2,2] — all see final i

# Same with genexps:
funcs2 = list((lambda: i) for i in range(3))
print([f() for f in funcs2])  # [2,2,2]

# Fix: capture via default argument (early binding)
funcs_ok = [(lambda i=i: i) for i in range(3)]
print([f() for f in funcs_ok])  # [0,1,2]
```

### 5.4 When to use which

| Scenario | Prefer |
|----------|--------|
| Need result multiple times, index, `len` | List comp |
| Passing to a function that consumes once (`sum`, `any`, `join`) | GenExp |
| Large or infinite source | GenExp / generator function |
| Filtering/mapping pipeline | GenExp chain or generator function |
| Readability of complex logic | Named generator function over nested genexp |

## 6. Infinite Generators

Because generators are lazy, they can represent infinite sequences without infinite memory.

```python
from itertools import islice

def naturals(start: int = 0):
    n = start
    while True:
        yield n
        n += 1

def fibonacci():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

# Consume finite slice
print(list(islice(naturals(), 5)))        # [0,1,2,3,4]
print(list(islice(fibonacci(), 7)))       # [0,1,1,2,3,5,8]
print(list(islice(naturals(10), 3)))      # [10,11,12]

# Infinite generator + filtering (lazy)
def odd_naturals():
    for n in naturals():
        if n % 2 == 1:
            yield n

print(list(islice(odd_naturals(), 5)))    # [1,3,5,7,9]

# Danger: accidental materialization
# list(naturals())  # NEVER — hangs / MemoryError
# sum(naturals())   # NEVER — infinite loop
# Always bound infinite generators with islice, takewhile, or break.
```

## 7. Realistic Pipeline — Lazy Text Processing

This is the canonical generator use case: chaining stages where each stage yields to the next, keeping memory O(1) in the size of the input.

```python
from pathlib import Path
import re
from itertools import islice

# Stage 1: lazy line reader (simulated file)
def gen_lines(text: str):
    """Yield lines one by one — never loads all lines as a list."""
    for line in text.splitlines():
        # Simulate stripping / skipping empty
        stripped = line.strip()
        if stripped:
            yield stripped

# Stage 2: tokenize each line into words
_WORD_RE = re.compile(r"\w+")

def gen_words(lines):
    for line in lines:
        for word in _WORD_RE.findall(line.lower()):
            yield word

# Stage 3: filter stop words
STOP = {"the", "and", "is", "in", "a", "of", "to"}

def gen_filtered(words):
    for w in words:
        if w not in STOP:
            yield w

# Stage 4: count frequencies (terminal — consumes pipeline)
from collections import Counter

def count_top(text: str, n: int = 5):
    lines = gen_lines(text)
    words = gen_words(lines)
    filtered = gen_filtered(words)
    counter = Counter(filtered)  # consumes lazily — one word at a time
    return counter.most_common(n)

sample = """
The quick brown fox jumps over the lazy dog.
The dog is lazy and the fox is quick.
Python generators are lazy and memory efficient.
"""

print(count_top(sample, 3))
# [('quick', 2), ('lazy', 2), ('fox', 2)]  (order may vary)

# Equivalent as chained genexps (shorter, less reusable):
def count_top_genexp(text: str, n: int = 5):
    words = (
        w
        for line in text.splitlines()
        if (s := line.strip())
        for w in _WORD_RE.findall(s.lower())
        if w not in STOP
    )
    return Counter(words).most_common(n)

print(count_top_genexp(sample, 3))

# Memory test: each intermediate is a generator — at any moment only
# one line / one word is in memory, not the entire file.
# For a 10 GB log file, you'd write:
# with open("huge.log") as f:
#     lines = (line.strip() for line in f if line.strip())
#     words = (w for line in lines for w in line.split())
#     for w in words:  # processes streaming
#         ...
```
Explanation: Each generator suspends until the downstream consumer asks for the next value. Data flows *pull-based*: `Counter` calls `next(filtered)`, which calls `next(words)`, which calls `next(lines)`. No intermediate list is ever built. This pattern scales to arbitrarily large inputs with constant memory overhead.

## 8. Generator Pitfalls and Subtleties

### 8.1 Yield inside `try` / `finally` and resource handling

```python
def managed_resource():
    print("acquire")
    try:
        yield "resource"
    finally:
        print("release — runs on exhaustion, close(), or GC")

g = managed_resource()
print(next(g))  # acquire, resource
# If consumer abandons generator without exhausting:
del g  # release (in CPython immediately; in PyPy maybe later)
# Prefer explicit close:
g2 = managed_resource()
print(next(g2))
g2.close()  # release — deterministic

# For file-like resources, prefer contextlib.contextmanager (see §8.5)
# over manual yield+finally in a generator when possible.
```

### 8.2 Generators are single-pass; sharing causes confusion

```python
def gen():
    yield from [1, 2, 3]

g = gen()
a = g  # alias, not copy
print(next(a))  # 1
print(next(g))  # 2 — same object!

# If you need to fork, use itertools.tee (with memory cost) or recreate
import itertools
g1, g2 = itertools.tee(gen(), 2)
print(list(g1), list(g2))  # [1,2,3] [1,2,3]
# tee buffers values — if one branch lags, memory grows
```

### 8.3 `yield` precedence and `yield` in expressions

```python
# yield has very low precedence — parentheses often needed
def precedence_demo():
    # yield 1 + 2 yields 3, not (yield 1) + 2
    x = (yield 1) + 10  # yield 1, then when sent a value, x = sent + 10
    yield x

g = precedence_demo()
print(next(g))      # 1
print(g.send(5))    # 15 (5+10)
print(next(g, None))

# List with yield
def yield_in_list():
    yield from [1, 2]
    # yield inside comprehension is SyntaxError in some contexts
```

### 8.4 Generator `return` and PEP 479

```python
def gen_with_stopiteration_bug():
    # In Python 3.6 and earlier, this StopIteration would silently
    # terminate the generator. In 3.7+ it becomes RuntimeError.
    yield 1
    # Simulating buggy code that calls next() on empty iterator inside generator:
    # next(iter([]))  # raises StopIteration inside generator frame
    # If not caught, PEP 479 converts it to RuntimeError to surface the bug.
    try:
        next(iter([]))
    except StopIteration:
        print("caught correctly — no PEP 479 issue")
    yield 2

print(list(gen_with_stopiteration_bug()))  # [1, 2] — correctly handled

def pep479_demo():
    yield 1
    # Uncommenting next line without try/except would raise RuntimeError in 3.7+:
    # next(iter([]))  # RuntimeError: generator raised StopIteration
    yield 2

# Fix: always catch StopIteration from inner next() calls inside generators,
# or use next(it, default) to avoid raising.
def safe_inner_next():
    it = iter([10, 20])
    while True:
        val = next(it, None)
        if val is None:
            break
        yield val
```

### 8.5 Performance note

```python
# Generators have per-yield overhead (frame suspension). For tight numeric loops
# where you need all values anyway, list comps may be faster despite memory.

def gen_squares(n):
    for i in range(n):
        yield i*i

# Time these for n=1_000_000 to see crossover — list comp often wins on speed
# but loses on memory. Choose based on whether the dataset fits in RAM.
```

## 9. Quick-Reference Table

| Concept | Syntax | When to use |
|---------|--------|-------------|
| Generator function | `def f(): yield x` | Multi-step lazy logic, resources, infinite seq |
| Generator object | `g = f()` | Iterator — call `next(g)` or `for x in g` |
| GenExp | `(x for x in it if cond)` | One-liner lazy transform/filter |
| `yield` | `yield val` | Produce value and suspend |
| `yield from` | `yield from iterable` | Delegate (see §8.3) |
| `g.send(v)` | `received = yield val` | Coroutine-style input |
| `g.throw(...)` | inject exception | Cancellation / error signaling |
| `g.close()` | `GeneratorExit` at yield | Deterministic cleanup |
