# 8.3 Yield Delegation — `yield from`

`yield from` (PEP 380) lets one generator *delegate* part of its operations to another generator or iterable. It is not mere syntactic sugar for a loop: it correctly forwards `send()`, `throw()`, `close()`, and — crucially — captures the subgenerator's **return value**. This section explains the full mechanics, common patterns, and the bridge it forms toward `async`/`await`.

---

## 1. The Problem `yield from` Solves

Without delegation, manually iterating a subgenerator is verbose and subtly broken for advanced generator features:

```python
def inner():
    yield 1
    yield 2
    return "inner done"

def outer_manual():
    # Naive delegation — loop + yield
    for value in inner():
        yield value
    # How to get inner's return value? Lost — for loop discards StopIteration.value
    # How to forward send()/throw()? Not handled — caller’s send goes to outer, not inner

# Test
g = outer_manual()
print(list(g))  # [1, 2] — return value gone, no forwarding
```

`yield from` solves all of this in one expression:

```python
def outer_delegating():
    result = yield from inner()
    print(f"inner returned: {result!r}")
    yield 3

print(list(outer_delegating()))  # inner returned: 'inner done'  -> [1, 2, 3]
```
Explanation: `yield from inner()` *delegates* — values produced by `inner` are yielded directly to the caller of `outer_delegating`, and the final `return` value of `inner` becomes the *value of the `yield from` expression*.

## 2. Basic `yield from` Semantics

### 2.1 Delegation to an iterable (simplest case)

```python
def gen():
    yield from [1, 2, 3]        # any iterable, not just generators
    yield from "ab"
    yield from range(2)

print(list(gen()))  # [1, 2, 3, 'a', 'b', 0, 1]
# Equivalent to:
# for x in [1,2,3]: yield x
# for x in "ab":    yield x
# ...
# but yield from is faster (C-level loop) and handles close/throw correctly.
```

### 2.2 Delegation to a generator — capturing return value

```python
def subgen():
    yield 1
    yield 2
    return "finished"

def delegator():
    val = yield from subgen()
    print(f"subgen returned {val!r}")
    yield 3

g = delegator()
print(next(g))  # 1
print(next(g))  # 2
print(next(g))  # subgen returned 'finished' -> 3
print(next(g, "exhausted"))  # exhausted
```
Explanation: When `subgen` executes `return "finished"`, Python raises `StopIteration("finished")` inside `subgen`. `yield from` catches that exception, extracts its `.value`, and that becomes the result of the expression. Normal `for` loops discard this value; `yield from` preserves it.

### 2.3 Any iterable's "return value"?

Only generators have meaningful return values. For plain iterables like lists, `yield from` evaluates to `None` (because exhausting a list raises bare `StopIteration` with no value).

```python
def delegator_list():
    val = yield from [1, 2]
    print(f"list delegation returned {val!r}")  # None
    yield 3

print(list(delegator_list()))  # [1,2,3] + prints None
```

## 3. Full Mechanics — What `yield from` Actually Does

PEP 380 defines precise expansion. The statement `result = yield from expr` is *semantically* equivalent to:

```python
# Pseudocode expansion (simplified; real CPython handles more edge cases)
_iterator = iter(expr)
try:
    _value = next(_iterator)
except StopIteration as _e:
    result = _e.value
else:
    while True:
        try:
            _sent = yield _value
        except GeneratorExit as _e:
            try:
                _iterator.close()
            except AttributeError:
                pass
            raise _e
        except BaseException as _e:
            # throw() path — inject into subgenerator
            try:
                _thrown = _iterator.throw(_e)
            except StopIteration as _e2:
                result = _e2.value
                break
            except BaseException:
                raise
            else:
                _value = _thrown
        else:
            # send() / next() path — forward sent value
            try:
                if _sent is None:
                    _value = next(_iterator)
                else:
                    _value = _iterator.send(_sent)
            except StopIteration as _e:
                result = _e.value
                break
```

Key observations from this expansion:

| Feature | How `yield from` handles it |
|---------|-------------------------------|
| `next(delegator)` | Calls `next(subiterator)` |
| `delegator.send(v)` | Calls `subiterator.send(v)` |
| `delegator.throw(E)` | Calls `subiterator.throw(E)` |
| `delegator.close()` | Calls `subiterator.close()` if it exists |
| Subgenerator `return val` | Becomes value of `yield from` expression |
| Subgenerator raises other exception | Propagates to delegator caller |

> **Mnemonic:** `yield from` makes the delegator *transparent* — the caller cannot tell whether values come from the delegator or the subgenerator.

## 4. `send()` / `throw()` / `close()` Forwarding — Concrete Demos

### 4.1 `send()` forwarding

```python
def accumulator():
    total = 0
    while True:
        received = yield total
        if received is None:
            continue
        total += received

def delegating_acc():
    # All sends go straight to accumulator
    result = yield from accumulator()
    print(f"accumulator returned {result!r}")  # only if accumulator ever returns

acc = delegating_acc()
print(next(acc))        # 0 — primes through delegation
print(acc.send(5))      # 5
print(acc.send(10))     # 15
print(acc.send(3))      # 18
# Without yield from, outer would need manual send-loop to forward values
```
Explanation: When the caller does `acc.send(5)`, `delegating_acc` is suspended at `yield from`. Python forwards `5` as `accumulator.send(5)`, gets back the next yielded value, and yields it to the caller. The delegator never sees the sent value.

### 4.2 `throw()` forwarding

```python
def inner_catch():
    try:
        while True:
            val = yield "inner ready"
            print(f"inner got {val}")
    except ValueError as e:
        print(f"inner caught ValueError: {e}")
        yield f"recovered: {e}"
        return "inner recovered"

def outer():
    val = yield from inner_catch()
    print(f"outer sees return: {val!r}")
    yield "outer after"

o = outer()
print(next(o))                    # inner ready
print(o.throw(ValueError("oops"))) # inner caught ..., recovered: oops
print(next(o))                    # outer after (outer sees return)
print(next(o, "done"))            # done
```
Explanation: `o.throw(ValueError(...))` injects the exception *into* `inner_catch` at its suspension point, as if `inner`'s `yield` raised it. If inner handles it and yields again, that value is yielded to the outer caller through delegation.

### 4.3 `close()` forwarding

```python
def inner_with_cleanup():
    try:
        yield 1
        yield 2
    finally:
        print("inner cleanup")

def outer_with_cleanup():
    try:
        yield from inner_with_cleanup()
    finally:
        print("outer cleanup")

g = outer_with_cleanup()
print(next(g))  # 1
g.close()       # inner cleanup, outer cleanup — both finally blocks run
```
Explanation: `close()` on the delegator calls `close()` on the subiterator (if it has one), which raises `GeneratorExit` inside the subgenerator, triggering its `finally`. Then the delegator's own `finally` runs.

## 5. Return Values from Generators — The Hidden Channel

### 5.1 How `return` becomes `StopIteration.value`

```python
def gen():
    yield 1
    return "result"
    # Any code after return is unreachable, but finally still runs

g = gen()
print(next(g))  # 1
try:
    next(g)
except StopIteration as e:
    print(e.value)  # result

# Python 3.3+ also allows:  yield from gen()  to capture this
def wrapper():
    val = yield from gen()
    print(f"captured: {val}")  # captured: result

print(list(wrapper()))  # [1] + prints captured
```
Explanation: `return value` in a generator is syntactic sugar for `raise StopIteration(value)`. Before PEP 380, this value was inaccessible to normal iteration. `yield from` made it accessible, enabling generators to act like *callable subroutines* that produce both a stream of values and a final result.

### 5.2 StopIteration value mechanics and PEP 479 guard

```python
# Explicit StopIteration with value
def explicit():
    yield 1
    raise StopIteration("explicit value")  # same as return "explicit value"

# In modern Python, raising StopIteration *inside* a generator to signal
# "I'm done" is deprecated — use return. And unhandled StopIteration from
# inner next() is converted to RuntimeError (PEP 479):
def buggy():
    yield 1
    next(iter([]))  # StopIteration leaks — becomes RuntimeError in 3.7+
    yield 2

# Correct patterns:
def correct_a():
    it = iter([1, 2])
    # Option 1: catch
    try:
        val = next(it)
    except StopIteration:
        val = None
    yield val

def correct_b():
    it = iter([1, 2])
    # Option 2: default
    val = next(it, None)
    yield val
```

### 5.3 Using return values for recursive / tree traversals

A powerful pattern: recursive generator that returns an aggregate while yielding leaves.

```python
# Count nodes while yielding values
from typing import Union

Tree = Union[int, list]  # int is leaf, list is subtree

def walk_and_count(tree: Tree):
    """Yield leaves; return total leaf count."""
    if isinstance(tree, int):
        yield tree
        return 1
    count = 0
    for subtree in tree:
        # yield from returns the subtree's count
        n = yield from walk_and_count(subtree)
        count += n
    return count

def count_tree(tree: Tree):
    gen = walk_and_count(tree)
    leaves = []
    try:
        while True:
            leaves.append(next(gen))
    except StopIteration as e:
        total = e.value
    return leaves, total

tree = [1, [2, 3], [4, [5, 6]]]
leaves, total = count_tree(tree)
print(leaves, total)  # [1,2,3,4,5,6] 6

# Cleaner with wrapper that uses yield from capture:
def walk_wrapper(tree):
    total = yield from walk_and_count(tree)
    print(f"total leaves: {total}")
    # wrapper itself yields what walk_and_count yielded (via delegation)

print(list(walk_wrapper(tree)))  # [1,2,3,4,5,6] + prints total
```
Explanation: Each recursive call's return value (count) is captured by its parent's `yield from`, summed, and re-returned up the call stack — all while leaves stream to the ultimate caller without intermediate lists.

## 6. Realistic Patterns

### 6.1 Flattening nested iterables

```python
from collections.abc import Iterable

def flatten(nested, *, strings_as_atoms=True):
    """Yield leaves of arbitrarily nested iterables.
    Strings treated as atoms (not iterated char-by-char) by default."""
    for item in nested:
        is_str = isinstance(item, (str, bytes))
        if strings_as_atoms and is_str:
            yield item
        elif isinstance(item, Iterable):
            yield from flatten(item, strings_as_atoms=strings_as_atoms)
        else:
            yield item

data = [1, [2, 3], [[4], 5], "hello", [6, [7, 8]]]
print(list(flatten(data)))
# [1, 2, 3, 4, 5, 'hello', 6, 7, 8]

# With strings expanded:
print(list(flatten(["ab", ["cd"]], strings_as_atoms=False)))
# ['a', 'b', 'c', 'd']
```

### 6.2 Pipeline delegation — composable stages

```python
def read_lines(text: str):
    for line in text.splitlines():
        if line.strip():
            yield line.strip()

def parse_records(lines):
    for line in lines:
        # Simulate CSV: "name,age"
        name, age = line.split(",")
        yield {"name": name.strip(), "age": int(age.strip())}

def pipeline(text: str):
    # Delegation makes pipeline stages swappable
    yield from parse_records(read_lines(text))

sample = "Alice, 30\nBob, 25\nCharlie, 35"
print(list(pipeline(sample)))
# [{'name': 'Alice', 'age': 30}, ...]

# With return value: count records while streaming
def parse_and_count(lines):
    count = 0
    for line in lines:
        name, age = line.split(",")
        count += 1
        yield {"name": name.strip(), "age": int(age.strip())}
    return count

def pipeline_counted(text: str):
    n = yield from parse_and_count(read_lines(text))
    print(f"parsed {n} records")

print(list(pipeline_counted(sample)))  # records + prints parsed 3
```

### 6.3 Cooperative breadth-first traversal with delegation

```python
from collections import deque

def bfs_tree(root):
    """Yield nodes BFS; subgenerators delegate for subtrees."""
    queue = deque([root])
    while queue:
        node = queue.popleft()
        value, children = node  # node = (value, [children])
        yield value
        # Delegate child iteration if children is itself a generator
        # (here just extend queue — but yield from shines for DFS)
        queue.extend(children)

def dfs_tree(node):
    value, children = node
    yield value
    for child in children:
        yield from dfs_tree(child)

tree = ("root", [("a", [("a1", []), ("a2", [])]), ("b", [])])
print(list(dfs_tree(tree)))  # ['root', 'a', 'a1', 'a2', 'b']
print(list(bfs_tree(tree)))  # ['root', 'a', 'b', 'a1', 'a2']
```

## 7. `yield from` vs Manual Loops — When Each Wins

| Scenario | Best choice | Why |
|----------|-------------|-----|
| Simple delegation, no send/throw/return value needed | Either; `yield from` is faster | C-level loop, less bytecode |
| Need to transform values in flight | Manual `for x in sub: yield transform(x)` | `yield from` is transparent — cannot intercept |
| Need to capture subgenerator return value | `yield from` (only way) | Manual loop discards it |
| Need send/throw/close forwarding | `yield from` | Manual loop does not forward |
| Delegating to non-generator iterable | `yield from` is fine | Evaluates to `None` |

If you need to *both* transform and capture return value, combine:

```python
def transform_and_capture():
    # Interpose transformation manually, but still capture return
    sub = inner_generator()
    try:
        while True:
            val = next(sub)
            yield val * 10  # transform
    except StopIteration as e:
        result = e.value
    print(f"result={result!r}")
```

## 8. Preview: From `yield from` to `async` / `await`

PEP 380's delegation is the direct ancestor of `asyncio` coroutines:

```python
# Old asyncio style (Python 3.4) — generators as coroutines
# @asyncio.coroutine
# def fetch(url):
#     response = yield from aiohttp.request("GET", url)
#     return response

# Modern style (Python 3.5+) — async/await replaces yield from for concurrency
# async def fetch(url):
#     response = await aiohttp.request("GET", url)
#     return response

# Under the hood, async def + await reuse the same suspension/resumption
# machinery as generators, but with an event loop driving them.

# Analogy:
#   yield from  <-->  await
#   generator   <-->  coroutine
#   return val  <-->  return val (both become StopIteration.value / coroutine result)
#   yield       <-->  await on something that suspends

# Minimal async preview (no event loop needed to illustrate syntax):
import asyncio

async def async_inner():
    await asyncio.sleep(0)  # suspension point like yield
    return "async result"

async def async_outer():
    val = await async_inner()  # like yield from — captures return value
    print(f"async inner returned {val!r}")
    return "outer done"

# To run: asyncio.run(async_outer())
# The conceptual link: both yield from and await delegate to a suspendable
# sub-computation and resume with its result.
```
Explanation: If you understand `yield from`'s forwarding and return-value capture, you already understand `await`'s core semantics. The difference is *who* drives resumption: for generators, the consumer calls `next`/`send`; for coroutines, the event loop does.

## 9. Edge Cases and Common Mistakes

```python
# Mistake 1: yield from on a non-iterable
# yield from 42  # TypeError: 'int' object is not iterable

# Mistake 2: expecting yield from to materialize — it is lazy
def lazy_check():
    print("before yield from")
    yield from [1, 2, 3]
    print("after")

g = lazy_check()
print("generator created — no prints yet")
print(next(g))  # before yield from, 1 — lazy

# Mistake 3: yield from inside async def is SyntaxError
# async def f():
#     yield from gen()  # SyntaxError — use async for / await instead

# Mistake 4: using yield and yield from in same function is fine,
# but mixing can confuse readers — keep delegation coherent

# Mistake 5: forgetting that yield from consumes the subgenerator
# — you cannot partially delegate and then reuse the same subgenerator object
def sub():
    yield 1
    yield 2

s = sub()
def outer1():
    yield from s

def outer2():
    yield from s  # s is already exhausted!

print(list(outer1()))  # [1, 2]
print(list(outer2()))  # [] — s exhausted

# Fix: create fresh subgenerator inside delegator, or pass a factory
def outer_fresh():
    yield from sub()  # fresh each time

print(list(outer_fresh()))  # [1, 2]
print(list(outer_fresh()))  # [1, 2] — works
```

## 10. Quick-Reference Table

| Expression | Value | Side effects |
|------------|-------|--------------|
| `yield from iterable` | `None` (iterable exhausted) or subgenerator's return value | Yields each item to caller; forwards send/throw/close |
| `result = yield from gen()` | `gen`'s `return result` | Same as above + captures result |
| `yield from` with exception in sub | Propagates unless caught by delegator/sub | Exception flows outward |
| `yield from` + `close()` | N/A | Calls sub's `close()` then delegator's `finally` |
