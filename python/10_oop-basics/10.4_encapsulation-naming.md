# 10.4 Encapsulation and Naming Conventions

> **Mental model:** Python has no `private`, `protected`, or `public` keywords. Instead it has a social contract expressed through naming conventions, plus one mechanical transformation — name mangling — that exists to prevent *accidental* collisions in inheritance, not to enforce secrecy. Python's philosophy is "we're all consenting adults": the language makes it easy to do the right thing and possible to do the wrong thing, trusting programmers to respect conventions rather than fighting the compiler.

---

## 1. Why Python Has No Access Modifiers

### 1.1 The Java/C++ Model vs the Python Model

In Java and C++:

```java
// Java — access enforced by the compiler:
public class Account {
    private double balance;          // compiler error if accessed externally
    protected String owner;          // visible only to subclasses / same package
    public void deposit(double amt) { balance += amt; }
}
// account.balance = 1000000;  // compile error: balance has private access
```

In Python:

```python
# Python — access governed by convention, not enforcement:
class Account:
    def __init__(self, owner, balance):
        self.owner = owner            # public — anyone may use it
        self._balance = balance       # "private" by convention — don't touch directly
        self.__secret = "shh"         # name-mangled — harder to collide accidentally

a = Account("Alice", 1000)
print(a.owner)       # fine — public
print(a._balance)    # works! Python does NOT prevent access — but you SHOULDN'T
print(a.__secret)    # AttributeError — name was mangled to _Account__secret
print(a._Account__secret)  # "shh" — accessible if you really insist
```

**Explanation:** Python deliberately chose not to enforce access control at the language level. The reasoning (from the Python FAQ and Guido van Rossum's writings):

1. **Encapsulation via convention is sufficient** — programmers who want privacy can follow `_single_underscore` and be understood.
2. **Enforcement adds complexity** — `private`/`protected`/`public` require access-control checks at every attribute access, complicating the object model and introspection.
3. **Debugging and testing need access** — rigid privacy makes it harder to inspect, test, and monkey-patch objects during development.
4. **"We're all consenting adults"** — Python trusts you not to break your own objects. If you *really* need to access `_balance`, you can, but the underscore warns you that you accept the risk.

This is not a flaw — it is a deliberate design choice that makes Python's object model simpler and more flexible at the cost of requiring discipline.

### 1.2 What Encapsulation Means in Python

| Concept | Meaning in Java/C++ | Meaning in Python |
|---------|---------------------|-------------------|
| Encapsulation | Hiding internal state behind access modifiers enforced by the compiler | Hiding internal state behind naming conventions and properties, enforced by social contract |
| Information hiding | `private` members are inaccessible outside the class | `_private` members are accessible but flagged as internal |
| Interface vs implementation | Compiler prevents misuse | Documentation + underscore + properties guide correct use |
| Subclass access | `protected` controls subclass visibility | `_single_underscore` visible to subclasses; `__mangled` uses name transformation to avoid collisions |

Python achieves encapsulation through **API design**: expose a clean public interface, mark internals with `_`, and use `property` (see 10.5) to add validation or computed access without changing the public API.

## 2. Public Names — No Underscore

### 2.1 What "Public" Means

```python
class BankAccount:
    """Public API — what users of this class should rely on."""

    def __init__(self, owner, balance=0):
        self.owner = owner        # public attribute — part of the contract
        self.balance = balance    # public attribute — but should it be? (see properties)

    def deposit(self, amount):    # public method
        self.balance += amount

    def withdraw(self, amount):   # public method
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount

    def __repr__(self):           # "dunder" — public protocol method (see Section 5)
        return f"BankAccount({self.owner!r}, {self.balance})"

acc = BankAccount("Alice", 1000)
acc.deposit(500)        # public — intended use
print(acc.balance)      # public — but allows acc.balance = -999 without validation!
```

**Convention:** Names without any leading underscore are public. They constitute the class's API — the author promises to maintain backward compatibility for these names. Users may freely read, write, and call them.

**Java/C++ equivalent:** `public`.

### 2.2 Designing a Good Public API

```python
# Good — minimal public surface, internals hidden:
class Circle:
    def __init__(self, radius):
        self.radius = radius      # public — the fundamental parameter

    @property
    def area(self):               # public computed attribute
        import math
        return math.pi * self.radius ** 2

    @property
    def diameter(self):
        return self.radius * 2

# Users interact only with radius, area, diameter — not internal caches or helpers.
```

```python
# Bad — exposing internals as public:
class CircleBad:
    def __init__(self, radius):
        self.radius = radius
        self._area_cache = None           # should be _private (internal cache)
        self._compute_area_call_count = 0 # should be _private (instrumentation)

# If these are public, users may depend on them, and you can never rename or remove them.
```

## 3. Single Underscore — `_private` by Convention

### 3.1 The Convention

A single leading underscore (`_name`) means **"internal use — not part of the public API."** It is a signal to other programmers (and to tools) that this name is an implementation detail.

```python
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self._balance = balance          # internal — don't access directly
        self._transactions = []          # internal — bookkeeping

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self._balance += amount
        self._transactions.append(amount)
        self._audit(f"deposit {amount}")

    def _audit(self, message):
        """Internal helper — not part of public API."""
        print(f"[AUDIT] {message}")

    @property
    def balance(self):
        """Public read-only view of balance."""
        return self._balance

acc = Account("Alice", 1000)
acc.deposit(500)
print(acc.balance)       # 1500 — public property
# print(acc._balance)    # works, but violates convention — linter will warn
# acc._balance = -999    # bypasses validation — you're on your own if you do this
```

**What `_` does mechanically:** Nothing. Python treats `_balance` exactly like `balance` — it is stored in `__dict__` under the key `"_balance"`, fully accessible via `getattr`, `hasattr`, `vars`, etc. The underscore is purely a naming convention.

### 3.2 What `_` Signals to Different Audiences

| Audience | Interpretation of `_name` |
|----------|---------------------------|
| Human programmer | "This is an implementation detail. Don't rely on it; it may change without notice. If you access it, you accept that your code may break in a future version." |
| Linter (`pylint`, `flake8`, `ruff`) | Warns on `from module import _private` and on external access `obj._private` (configurable) |
| `from module import *` | **Skips** names starting with `_` (see 3.4) |
| Documentation tools (`Sphinx`, `pdoc`) | Often hide `_private` names from public docs by default |
| Subclasses | `_protected` is accessible — subclasses may use parent's `_` names if they coordinate, but should treat them as non-public |
| `dir()` and `help()` | Still shows `_` names — they are not hidden, just flagged |

### 3.3 `_` Is Not Enforcement — And That Is Intentional

```python
class Counter:
    def __init__(self):
        self._count = 0

    def increment(self):
        self._count += 1

    @property
    def count(self):
        return self._count

c = Counter()
c.increment()
print(c.count)     # 1 — public property
print(c._count)    # 1 — directly accessible! No error.
c._count = 999     # directly mutated — bypasses any logic
print(c.count)     # 999 — property reflects the mutated internal

# You CAN do this. Python WON'T stop you. But you SHOULDN'T.
```

**Why this is a feature:** During debugging, testing, or emergency patching, you *need* to inspect and modify internals. In Java, you would need reflection or need to temporarily change `private` to `public`. In Python, you just access `_count` directly — no ceremony. The convention trusts you to do this only when appropriate.

### 3.4 `from module import *` and `_`

```python
# mymodule.py:
public_var = 42
_private_var = 99
__mangled_var = 100  # also skipped

def public_func(): pass
def _private_func(): pass

# other.py:
from mymodule import *
print(public_var)    # 42 — imported
# print(_private_var)  # NameError — NOT imported by `import *`
# print(_private_func) # NameError — NOT imported

# But explicit import still works:
from mymodule import _private_var
print(_private_var)  # 99 — explicit import bypasses the filter
```

**Explanation:** `from module import *` copies every name from the module's namespace *except* those starting with `_` (unless the module defines `__all__`, which explicitly lists what `import *` should import — `__all__` takes precedence). This is the one place where `_` has a mechanical effect at the module level.

```python
# mymodule2.py — with __all__:
__all__ = ["public_var", "_private_var"]  # explicitly include _private_var

# Now `from mymodule2 import *` WILL import _private_var because __all__ says so.
```

At the **class level**, `from module import *` filtering and `__all__` apply to module names, not class attributes. Inside a class, `obj._private` is always accessible regardless.

### 3.5 Single Trailing Underscore — `name_` (Avoiding Keyword Collisions)

A single *trailing* underscore (`class_`, `type_`, `id_`) is a related convention for avoiding collisions with Python keywords or builtins:

```python
# `class` is a keyword — can't use as parameter name:
# def create(class): ...  # SyntaxError

def create(class_):       # trailing underscore avoids collision
    print(f"creating {class_}")

# Common in stdlib and ORMs:
import tkinter
# tkinter uses `class_` as a parameter name to avoid shadowing `class`

# Also for shadowing builtins:
def print_list(list_):    # avoid shadowing builtin `list`
    print(list_)

# This is purely a naming convention — no mechanical effect.
```

### 3.6 Underscore in the Standard Library — Examples

```python
# The stdlib uses _single_underscore extensively:

import collections

# collections.OrderedDict internals:
#   _OrderedDict__root, _OrderedDict__map — see name mangling
#   _OrderedDict__hardroot — internal tree pointers

# datetime module:
#   _days_in_month, _is_leap — internal helpers

# re module:
#   _compile, _cache — internal

# asyncio:
#   _loop, _callbacks — internal state

# In all cases, the stdlib authors expect you NOT to depend on _ names,
# and they may rename them between Python versions without deprecation warnings.
```

## 4. Double Underscore — `__mangled` Name Mangling

### 4.1 What Name Mangling Does

When a name inside a class starts with **two underscores** and ends with **at most one** trailing underscore (`__name` or `__name_` but not `__name__`), Python **textually rewrites** it at compile time to `_ClassName__name`, where `ClassName` is the name of the class where it is defined.

```python
class Account:
    def __init__(self, balance):
        self.__balance = balance     # Python rewrites to self._Account__balance

    def __audit(self):               # rewrites to _Account__audit
        print(f"auditing {self.__balance}")  # rewrites to self._Account__balance

    def deposit(self, amount):
        self.__balance += amount     # rewrites to self._Account__balance
        self.__audit()               # rewrites to self._Account__audit()

acc = Account(1000)
print(acc.__dict__)          # {'_Account__balance': 1000} — mangled key!
# print(acc.__balance)       # AttributeError: 'Account' object has no attribute '__balance'
print(acc._Account__balance) # 1000 — the real key
acc._Account__audit()        # auditing 1000 — mangled method is callable if you know the name

# Inside the class body, both spellings refer to the mangled name:
print(Account.__dict__.keys())
# dict_keys(['__module__', '__init__', '_Account__audit', 'deposit', ...])
# Note: `_Account__audit` and `_Account__balance` (via instance), NOT `__audit` / `__balance`
```

**Explanation:** Mangling happens during **compilation** (bytecode generation), not at runtime. The compiler scans every name in a class scope; any name matching `__name` (two leading underscores, at most one trailing) is rewritten to `_ClassName__name`. This is a purely lexical transformation — it happens before the code runs. You can verify with `dis`:

```python
import dis
class Foo:
    def method(self):
        self.__x = 1
        return self.__x

dis.dis(Foo.method)
# Look for STORE_ATTR with '_Foo__x' — the compiler already rewrote it
```

### 4.2 Mangling Rules — Precise Definition

```python
# Rule: mangle if name starts with __ AND does NOT end with __
# (and did not already start with _ClassName__ — avoid double-mangling)

class Demo:
    __mangled = 1        # → _Demo__mangled     (starts with __, no trailing __)
    __mangled_ = 2       # → _Demo__mangled_    (starts with __, one trailing _)
    __not_mangled__ = 3  # NOT mangled          (starts AND ends with __: dunder)
    ___triple = 4        # → _Demo___triple     (starts with __, still mangled — third _ is part of name)
    _single = 5          # NOT mangled          (only one leading _)

print(Demo.__dict__.keys())
# Includes: '_Demo__mangled', '_Demo__mangled_', '__not_mangled__', '_Demo___triple', '_single'

# Dunders (__name__) are NEVER mangled — they are protocol names:
class WithDunder:
    __init__ = "not mangled"
    __str__ = "not mangled"
    __private = "mangled to _WithDunder__private"
```

| Name pattern | Mangled? | Stored as |
|--------------|----------|-----------|
| `__name` | Yes | `_ClassName__name` |
| `__name_` | Yes | `_ClassName__name_` |
| `__name__` | No (dunder) | `__name__` |
| `_name` | No | `_name` |
| `___name` | Yes | `_ClassName___name` |
| `__` | No (too short — needs at least one char after `__` in CPython's logic) | `__` — actually CPython does NOT mangle bare `__` |

### 4.3 Why Mangling Exists — Preventing Accidental Collisions in Inheritance

The primary purpose is **not** privacy — it is **inheritance safety**. Without mangling, a subclass could accidentally override a parent's internal attribute:

```python
# WITHOUT mangling — collision:
class Base:
    def __init__(self):
        self._state = "base state"   # single underscore — no mangling
    def _helper(self):
        return f"base helper: {self._state}"

class Child(Base):
    def __init__(self):
        super().__init__()
        self._state = "child state"  # OOPS — overwrites Base's _state!
        # Base._helper now sees "child state" — unintended!

c = Child()
print(c._helper())  # "base helper: child state" — Base's logic sees Child's data!

# WITH mangling — no collision:
class Base2:
    def __init__(self):
        self.__state = "base state"   # → _Base2__state
    def _helper(self):
        return f"base helper: {self.__state}"  # → self._Base2__state

class Child2(Base2):
    def __init__(self):
        super().__init__()
        self.__state = "child state"  # → _Child2__state — DIFFERENT key!

c2 = Child2()
print(c2._helper())          # "base helper: base state" — Base2's logic preserved!
print(c2.__dict__)           # {'_Base2__state': 'base state', '_Child2__state': 'child state'}
print(c2._Base2__state)      # "base state"
print(c2._Child2__state)     # "child state"
```

**Explanation:** Each class mangles `__state` with its *own* class name. `Base2.__state` becomes `_Base2__state` and `Child2.__state` becomes `_Child2__state` — two distinct keys in the same instance `__dict__`. Neither overwrites the other. The parent's internal state is isolated from the child's internal state without any coordination between the two authors — and neither author needs to know the other's internal names.

This is especially important for **library and framework classes** where the base class author cannot predict what attribute names subclasses will use.

### 4.4 Mangling Is Not Privacy — It Is Easily Bypassed

```python
class Secret:
    def __init__(self):
        self.__value = 42

s = Secret()
# s.__value          # AttributeError — mangled
print(s._Secret__value)  # 42 — trivially accessible if you know the class name
s._Secret__value = 999   # trivially mutable
print(s._Secret__value)  # 999

# Even without knowing the class name, you can find mangled names:
print([k for k in s.__dict__ if "value" in k])  # ['_Secret__value']
print([k for k in dir(s) if "value" in k])      # ['_Secret__value']

# getattr works too:
print(getattr(s, "_Secret__value"))  # 42
```

Python's documentation explicitly states: *"Name mangling is intended to give classes an easy way to define 'private' instance variables and methods, without having to worry about instance variables defined by derived classes... Note that the mangling rules are designed mostly to avoid accidents; it still is possible to access or modify a variable that is considered private."*

**If your goal is to signal "don't touch this," use `_single_underscore`.** Mangling adds obfuscation without adding security — and it adds complexity (see pitfalls below).

### 4.5 When to Use Mangling — Guidelines

**Use `__mangled` when:**

- You are writing a **base class that will be subclassed by unknown code** (library, framework, mixin) and you need to protect internal state from accidental collisions.
- You are writing a **mixin** where attribute name collisions between cooperating classes would be catastrophic.
- You are following an existing codebase that already uses mangling for a particular attribute.

**Do NOT use `__mangled` when:**

- You just want "private" — use `_single` instead. It is simpler, more readable, and not prone to mangling pitfalls.
- The class is not intended for inheritance — mangling adds no value.
- You are writing application code where you control both parent and child — just coordinate names with `_`.
- The name might need to be accessed from outside (testing, debugging, serialization) — mangling makes this awkward.

```python
# Good — stdlib-inspired library base class using mangling for collision safety:
class CacheBase:
    def __init__(self):
        self.__cache = {}            # mangled — subclasses won't collide

    def _get_cached(self, key):
        return self.__cache.get(key) # always accesses _CacheBase__cache

    def _set_cached(self, key, value):
        self.__cache[key] = value

class TimedCache(CacheBase):
    def __init__(self):
        super().__init__()
        self.__cache = "oops if not mangled, but safe because mangled"
        # self.__cache here is _TimedCache__cache — distinct from _CacheBase__cache
        self.expiry = {}

c = TimedCache()
c._set_cached("k", "v")
print(c._get_cached("k"))   # "v" — CacheBase's cache untouched by TimedCache's __cache
print(c.__dict__)
# {'_CacheBase__cache': {'k': 'v'}, '_TimedCache__cache': 'oops...', 'expiry': {}}
```

```python
# Bad — unnecessary mangling in application code:
class User:
    def __init__(self, name):
        self.__name = name   # why mangle? No inheritance collision risk.
        # Just use self._name or even self.name with a property.

    def __greet(self):       # mangled method — harder to test, mock, or override
        return f"Hello, {self.__name}"
```

### 4.6 Mangling Pitfalls — Read Carefully

#### Pitfall 1: Mangling Uses the *Defining* Class's Name, Not the Instance's Class

```python
class Base:
    def __init__(self):
        self.__value = "base"

    def get_value(self):
        return self.__value  # compiled as self._Base__value — ALWAYS Base

class Child(Base):
    def __init__(self):
        super().__init__()
        self.__value = "child"  # compiled as self._Child__value

c = Child()
print(c.get_value())      # "base" — get_value is defined in Base, so it reads _Base__value
print(c.__dict__)         # {'_Base__value': 'base', '_Child__value': 'child'}
# get_value will NEVER see _Child__value — it is hard-wired to _Base__value at compile time.
```

**Implication:** If you call a parent method that accesses `__mangled`, it always accesses the parent's mangled slot — even when `self` is a child instance. This is the *point* (collision avoidance), but it surprises people who expect `self.__value` in a parent method to find the child's `__value`.

#### Pitfall 2: Assignment Outside the Class Body Does NOT Mangle

```python
class Foo:
    __x = 1            # inside class → mangled to _Foo__x

print(Foo.__dict__.keys())  # '_Foo__x' present

Foo.__y = 2            # OUTSIDE class body → NOT mangled! Stored as '__y'
print(Foo.__y)         # 2 — stored as '__y', not '_Foo__y'
print(Foo._Foo__y)     # AttributeError — it was never mangled

obj = Foo()
obj.__z = 3            # OUTSIDE class body → NOT mangled! Stored as '__z' in instance dict
print(obj.__z)         # 3 — no mangling
print(obj.__dict__)    # {'__z': 3} — not '_Foo__z'
```

Mangling only applies to names that appear **textually inside a class definition**. Code outside the class (or inside a function defined outside the class) does not mangle.

#### Pitfall 3: Mangling Breaks `super()` Intuitions and Refactoring

```python
class Base:
    def __init__(self):
        self.__value = 1
    def __helper(self):
        return self.__value * 2

class Child(Base):
    def get_helper(self):
        # return self.__helper()  # AttributeError — mangled to _Child__helper, not _Base__helper
        return self._Base__helper()  # must use mangled name explicitly — ugly!

# Renaming Base to NewBase silently breaks all mangled names:
# _Base__value → _NewBase__value — every reference must be recompiled.
```

If you rename a class, every mangled attribute's storage key changes. This is invisible in source code (you still write `self.__value`) but can break **pickles**, **serialized data**, and **manual `_ClassName__attr` access** outside the class.

#### Pitfall 4: Mangling and `getattr` / `setattr`

```python
class Foo:
    def __init__(self):
        self.__value = 42

f = Foo()
# getattr with the unmangled name fails:
# getattr(f, "__value")  # AttributeError

# Must use mangled name:
print(getattr(f, "_Foo__value"))  # 42

# setattr with unmangled name creates a DIFFERENT attribute:
setattr(f, "__value", 999)
print(f.__dict__)  # {'_Foo__value': 42, '__value': 999} — two distinct entries!
print(f._Foo__value)  # 42 — original mangled one
print(f.__value)      # 999 — new unmangled one (outside class, no mangling)
```

### 4.7 Single vs Double Underscore — Decision Table

| Naming | Stored as | Mechanical effect | Purpose | Access from outside |
|--------|-----------|-------------------|---------|---------------------|
| `name` | `name` | None | Public API — stable contract | `obj.name` — encouraged |
| `_name` | `_name` | None (convention only); `import *` skips at module level | Internal — "don't depend on this" | `obj._name` — possible but discouraged |
| `__name` | `_ClassName__name` | Name mangling at compile time | Avoid accidental collisions in inheritance | `obj._ClassName__name` — possible but awkward |
| `__name__` | `__name__` | None (dunder protocol) | Python protocol / special method (`__init__`, `__str__`, etc.) | `obj.__name__` — but these are language-defined |
| `__name_` | `_ClassName__name_` | Mangled (at most one trailing `_` still counts) | Rare — internal + trailing `_` | `obj._ClassName__name_` |
| `name_` | `name_` | None (convention) | Avoid keyword/builtin collision | `obj.name_` — normal |
| `__` | `__` | Not mangled (CPython) | Avoid — confusing | `obj.__` — but why? |

## 5. Dunder Names — `__name__` (Double Underscore Both Sides)

Names with **two leading and two trailing underscores** (`__init__`, `__str__`, `__dict__`, `__class__`) are **not mangled** and are not private. They are Python's **protocol names** — hooks into language behavior.

```python
class MyClass:
    def __init__(self, value):    # not private — Python calls this on construction
        self.value = value
    def __repr__(self):           # not private — called by repr()
        return f"MyClass({self.value})"
    def __eq__(self, other):      # not private — called by ==
        return isinstance(other, MyClass) and self.value == other.value

# Rules for dunders:
# - Never invent your own __name__ for "really private" — it won't be mangled
#   and it pollutes the protocol namespace. Use _single or __mangled instead.
# - Dunders are for Python's use. Defining __my_custom__ is legal but bad style —
#   future Python versions might assign it a meaning.
```

**Never use `__name__` to mean "extra private"** — this is a common misunderstanding from developers coming from languages where more underscores means more privacy. In Python, `__name__` means the opposite of private — it means "this name has a language-defined meaning."

## 6. The Getters/Setters Anti-Pattern — Why Python Prefers Properties

### 6.1 The Java Way (Anti-Pattern in Python)

```python
# Java-style — verbose, un-Pythonic:
class AccountJava:
    def __init__(self, balance):
        self._balance = balance

    def get_balance(self):          # getter
        return self._balance

    def set_balance(self, value):   # setter
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

acc = AccountJava(1000)
print(acc.get_balance())   # 1000 — awkward for such a simple access
acc.set_balance(1500)      # awkward for such a simple mutation
```

### 6.2 The Python Way — Public Attributes + Properties When Needed

```python
# Pythonic — start with a plain public attribute:
class Account:
    def __init__(self, balance):
        self.balance = balance   # public, simple

acc = Account(1000)
print(acc.balance)   # 1000 — clean
acc.balance = 1500   # clean

# Later, when you need validation, add a property WITHOUT changing the public API:
class Account:
    def __init__(self, balance):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

acc = Account(1000)
print(acc.balance)   # 1000 — SAME API as before!
acc.balance = 1500   # SAME API — now with validation
# acc.balance = -5   # ValueError — validation works transparently
```

**Why this is better:**

| Aspect | `get_`/`set_` methods | `property` |
|--------|----------------------|------------|
| Call site | `obj.get_balance()` / `obj.set_balance(5)` | `obj.balance` / `obj.balance = 5` — looks like plain attribute access |
| API evolution | Changing from attribute to `get_`/`set_` breaks every caller | Changing from plain attribute to `property` breaks nothing — callers still use `obj.balance` |
| Discoverability | Two methods to find | One name to find |
| Pythonic | Java-ism — unnecessary boilerplate | Idiomatic — "simple first, add complexity only when needed" |

**Rule:** Start with public attributes. Only introduce `property` when you need computed values, validation, or side effects. Never write `get_x`/`set_x` in Python unless you have a strong reason (e.g., the getter takes arguments, or you are wrapping a Java-style API). See 10.5 for full `property` treatment.

## 7. Underscores Outside Classes — Module and Variable Conventions

### 7.1 Module-Level `_private`

```python
# mymodule.py
import math

_public_constant = 100  # not really — this is still public! Convention says internal.
_INTERNAL_CACHE = {}    # internal by convention — even SCREAMING_SNAKE with _ prefix

def public_api():       # public
    return _helper()    # uses internal helper

def _helper():          # internal — not part of module's public API
    return 42

__all__ = ["public_api"]  # explicit public API — controls `from mymodule import *`
```

### 7.2 `_` as a Throwaway Variable

```python
# Loop variable you don't care about:
for _ in range(10):
    print("hello")  # _ signals "I won't use this value"

# Unpacking — ignore parts:
a, _, c = (1, 2, 3)  # ignore middle value
first, *_, last = [1, 2, 3, 4, 5]  # ignore middle

# In REPL — _ holds last result:
# >>> 2 + 3
# 5
# >>> _ * 2
# 10

# Internationalization convention:
# import gettext; _ = gettext.gettext; print(_("Hello"))
```

### 7.3 `__all__` — Explicit Public API

```python
# mymodule.py — explicit is better than implicit:
__all__ = ["public_func", "PublicClass", "CONSTANT"]

def public_func(): pass
class PublicClass: pass
CONSTANT = 42

def _internal(): pass       # not in __all__ — excluded from `import *` and often from docs
__mangled = 1               # not in __all__ — also excluded

# Tools (Sphinx, type checkers, linters) use __all__ to determine the public surface.
# If __all__ is defined, `from mymodule import *` imports ONLY names in __all__.
# Without __all__, `from mymodule import *` imports all names NOT starting with _.
```

## 8. Realistic Example — Putting Conventions Together

```python
from __future__ import annotations
from typing import ClassVar

class BankAccount:
    """
    A bank account with public balance access and internal bookkeeping.

    Public API: owner, balance (property), deposit(), withdraw(), statement()
    Internal:   _balance, _transactions, _audit(), _validate_amount()
    Mangled:    __account_number (collision-safe — base class for many account types)
    """

    # Class-level public constant (could also be _private if internal):
    default_currency: ClassVar[str] = "USD"

    def __init__(self, owner: str, balance: float = 0, account_number: str | None = None) -> None:
        self.owner = owner                          # public — stable API
        self._balance = float(balance)               # _private — internal storage
        self._transactions: list[tuple[str, float]] = []  # _private — bookkeeping
        self.__account_number = account_number or self._generate_number()  # mangled — collision-safe

    # ── Public properties and methods ──────────────────────────

    @property
    def balance(self) -> float:
        """Current balance — read-only via property (write goes through deposit/withdraw)."""
        return self._balance

    @property
    def account_number(self) -> str:
        """Masked account number — last 4 digits only."""
        return "****" + self.__account_number[-4:]  # accesses mangled name

    def deposit(self, amount: float) -> None:
        self._validate_amount(amount)
        self._balance += amount
        self._transactions.append(("deposit", amount))
        self._audit(f"deposit {amount}")

    def withdraw(self, amount: float) -> None:
        self._validate_amount(amount)
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
        self._transactions.append(("withdraw", -amount))
        self._audit(f"withdraw {amount}")

    def statement(self) -> str:
        lines = [f"Statement for {self.owner} ({self.account_number})"]
        for kind, amt in self._transactions:
            lines.append(f"  {kind}: {amt:+.2f}")
        lines.append(f"  balance: {self.balance:.2f}")
        return "\n".join(lines)

    # ── Internal helpers (_private) ────────────────────────────

    def _validate_amount(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")

    def _audit(self, message: str) -> None:
        # In production, log to a real audit trail
        print(f"[AUDIT {self.__account_number}] {message}")  # mangled access

    def _generate_number(self) -> str:
        import random
        return "".join(str(random.randint(0, 9)) for _ in range(10))

    # ── Dunder protocol methods ────────────────────────────────

    def __repr__(self) -> str:
        return f"BankAccount(owner={self.owner!r}, balance={self.balance:.2f})"


# Subclass — mangling protects base internals from collision:
class SavingsAccount(BankAccount):
    def __init__(self, owner, balance=0, interest_rate=0.02):
        super().__init__(owner, balance)
        self.interest_rate = interest_rate
        self.__account_number = "SAVINGS-OVERRIDE"
        # This is _SavingsAccount__account_number — does NOT overwrite _BankAccount__account_number
        # BankAccount's methods still see the original account number via _BankAccount__account_number

    def apply_interest(self):
        self.deposit(self.balance * self.interest_rate)

sav = SavingsAccount("Alice", 1000)
print(sav.account_number)   # ****<last 4 of BankAccount's number> — not "RIDE"!
print(sav.__dict__)
# {'owner': 'Alice', '_balance': 1000, ..., '_BankAccount__account_number': '...', '_SavingsAccount__account_number': 'SAVINGS-...'}
print(sav.statement())
```

**Explanation of the design:**

| Name | Convention | Reason |
|------|-----------|--------|
| `owner` | Public | Stable API — callers depend on it |
| `balance` (property) | Public | Controlled access — read-only; mutation via `deposit`/`withdraw` |
| `_balance` | `_private` | Internal storage behind the property |
| `_transactions` | `_private` | Bookkeeping — not part of public contract |
| `_validate_amount`, `_audit` | `_private` | Helpers — may change without notice |
| `__account_number` | `__mangled` | Collision-safe — base class used in an inheritance hierarchy |
| `__repr__` | Dunder | Python protocol — not private |
| `default_currency` | Public `ClassVar` | Shared constant — public configuration |

## 9. Summary

- Python has **no enforced access modifiers** — encapsulation is by convention, not by compiler.
- **`name`** — public. Part of the stable API. Callers may freely use it.
- **`_name`** — internal / "private" / "protected" by convention. Stored normally, fully accessible, but flagged as implementation detail. Linters warn on external access. `from module import *` skips `_` names (unless `__all__` says otherwise). This is the **default choice** for internal state.
- **`__name`** — name-mangled to `_ClassName__name` at compile time. Purpose is **inheritance collision avoidance**, not privacy. Easily bypassed via `obj._ClassName__name`. Use only when writing base classes / mixins that will be subclassed by unknown code and need collision safety. Otherwise prefer `_name`.
- **`__name__`** — dunder protocol. Never invent your own for privacy; they are reserved for Python's object protocol (`__init__`, `__str__`, `__eq__`, etc.).
- **`name_`** — trailing underscore to avoid keyword/builtin collisions. No mechanical effect.
- **"We're all consenting adults"** — Python trusts you to respect conventions. You *can* access `_private` and `__mangled` from outside, but you accept the maintenance risk.
- **Getters/setters (`get_x`/`set_x`) are an anti-pattern in Python** — start with public attributes and introduce `property` when you need validation or computation. This keeps the public API clean and stable.
- For modules, use `__all__` to declare the explicit public surface.
