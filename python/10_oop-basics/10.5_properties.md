# 10.5 Properties

> **Mental model:** A `property` is a descriptor that lets you intercept attribute access — `obj.x`, `obj.x = val`, `del obj.x` — and run code instead of a plain dict lookup. To the caller it looks like a normal attribute; to the implementer it is a set of methods (`getter`, `setter`, `deleter`) disguised as an attribute. This is how Python achieves encapsulation without the `get_`/`set_` boilerplate of Java/C++: start with a plain attribute, and if you later need validation or computation, wrap it in a property without changing any caller's code.

---

## 1. Why Properties Exist — The API Evolution Problem

### 1.1 The Java/C++ Trap

In Java, you must decide up front whether an attribute needs validation:

```java
// Java — you commit to get/set boilerplate from day one,
// because changing a public field to a method breaks every caller:
public class Account {
    private double balance;
    public double getBalance() { return balance; }
    public void setBalance(double v) {
        if (v < 0) throw new IllegalArgumentException();
        balance = v;
    }
}
account.getBalance();       // verbose
account.setBalance(100);    // verbose — and you must do this for EVERY attribute
```

If you start with `public double balance` and later need validation, you must change every `account.balance` to `account.getBalance()` / `account.setBalance()` — a breaking API change.

### 1.2 The Python Solution

```python
# Phase 1 — simple public attribute, no ceremony:
class Account:
    def __init__(self, balance):
        self.balance = balance   # plain attribute — clean, simple

acc = Account(1000)
print(acc.balance)    # 1000
acc.balance = 1500    # simple assignment

# Phase 2 — need validation? Wrap in a property. CALLERS DON'T CHANGE:
class Account:
    def __init__(self, balance):
        self._balance = balance  # internal storage (renamed)

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

acc = Account(1000)
print(acc.balance)    # 1000 — SAME syntax as before!
acc.balance = 1500    # SAME syntax — now validated
# acc.balance = -5    # ValueError — validation works, transparently
```

**Key insight:** `acc.balance` looks identical in both phases — plain attribute access. The property intercepts that access and runs code. No caller needs to change. This is why Python's advice is: *"Start with plain attributes. Add properties only when you need them."*

## 2. The `@property` Decorator — Syntax and Mechanics

### 2.1 Basic Getter

```python
class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        """Computed attribute — no setter, so read-only."""
        import math
        return math.pi * self.radius ** 2

    @property
    def diameter(self):
        return self.radius * 2

c = Circle(5)
print(c.area)       # 78.539816... — looks like attribute access, runs a method
print(c.diameter)   # 10 — same
# c.area = 100      # AttributeError: can't set attribute — no setter defined
# c.area()          # TypeError — it's not a method, don't call it!

# What Python stored:
print(type(Circle.__dict__["area"]))  # <class 'property'>
print(isinstance(Circle.__dict__["area"], property))  # True
```

**Explanation:** `@property` is a builtin that takes a function and wraps it in a `property` descriptor object. That descriptor implements `__get__` so that `c.area` triggers the getter function with `self` bound to `c`. Accessing via the class (`Circle.area`) returns the `property` object itself. Never call `c.area()` — the property already called the function for you.

### 2.2 Getter + Setter

```python
class Temperature:
    def __init__(self, celsius=0):
        self._celsius = float(celsius)

    @property
    def celsius(self):
        """Getter — called on `obj.celsius` (read)."""
        print("getter called")
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        """Setter — called on `obj.celsius = value` (write)."""
        print(f"setter called with {value}")
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = float(value)

    @property
    def fahrenheit(self):
        """Computed — converts on the fly."""
        return self._celsius * 9/5 + 32

    @fahrenheit.setter
    def fahrenheit(self, value):
        self.celsius = (value - 32) * 5/9  # reuses celsius setter (with validation)

t = Temperature(25)
print(t.celsius)      # getter called → 25.0
t.celsius = 30        # setter called with 30
print(t.celsius)      # getter called → 30.0
print(t.fahrenheit)   # 86.0 — computed via getter
t.fahrenheit = 212    # setter: celsius = (212-32)*5/9 = 100 — validated
print(t.celsius)      # 100.0
# t.celsius = -300    # ValueError: below absolute zero
```

**Explanation of the decorator chaining:**

```python
# What @property + @celsius.setter desugars to:
class Temperature:
    def _get_celsius(self):
        return self._celsius
    def _set_celsius(self, value):
        if value < -273.15:
            raise ValueError(...)
        self._celsius = float(value)

    celsius = property(_get_celsius)            # step 1: create property with getter
    celsius = celsius.setter(_set_celsius)      # step 2: attach setter, returns new property

# Or equivalently with the decorator syntax:
class Temperature2:
    @property
    def celsius(self): return self._celsius
    @celsius.setter
    def celsius(self, value): self._celsius = float(value)
```

`property` objects are immutable in the sense that `.setter()` / `.getter()` / `.deleter()` return a **new** `property` object. The `@celsius.setter` decorator replaces the old property in the class dict with the new one that has both getter and setter. This is why the setter method must have the same name as the property.

### 2.3 Getter + Setter + Deleter

```python
class Account:
    def __init__(self, balance):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("negative balance")
        self._balance = value

    @balance.deleter
    def balance(self):
        print("deleting balance — resetting to 0")
        self._balance = 0

acc = Account(1000)
print(acc.balance)   # 1000
acc.balance = 500    # setter
print(acc.balance)   # 500
del acc.balance      # deleter — calls the deleter method
print(acc.balance)   # 0 — deleter reset it

# Without a deleter, `del acc.balance` raises AttributeError.
```

Deleters are rarely used in practice — most properties omit them, making `del obj.prop` an error, which is usually the correct behavior.

### 2.4 Manual `property()` Construction (Without Decorators)

```python
class Temperature:
    def __init__(self, celsius=0):
        self._celsius = float(celsius)

    def _get_celsius(self):
        return self._celsius

    def _set_celsius(self, value):
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = float(value)

    def _del_celsius(self):
        del self._celsius

    # property(fget, fset, fdel, doc)
    celsius = property(
        fget=_get_celsius,
        fset=_set_celsius,
        fdel=_del_celsius,
        doc="Temperature in Celsius."
    )

print(Temperature.celsius.__doc__)  # Temperature in Celsius.
```

The `property(fget, fset, fdel, doc)` signature is the underlying constructor. The decorator syntax is sugar for this. Use the manual form when you already have standalone functions or want to set a custom docstring without writing a getter docstring.

```python
# Getter docstring becomes property docstring automatically:
class Foo:
    @property
    def x(self):
        """This docstring becomes Foo.x.__doc__."""
        return self._x

print(Foo.x.__doc__)  # This docstring becomes Foo.x.__doc__.
```

## 3. How Properties Work — The Descriptor Protocol

A `property` is a **data descriptor** — it implements both `__get__` and `__set__` (and optionally `__delete__`). This is why it takes precedence over instance `__dict__` (see 10.6 for full lookup order).

```python
class MyProp:
    """A minimal property-like descriptor — simplified version of builtin property."""

    def __init__(self, fget=None, fset=None):
        self.fget = fget
        self.fset = fset

    def __get__(self, instance, owner):
        if instance is None:
            return self          # accessed via class → return descriptor itself
        if self.fget is None:
            raise AttributeError("unreadable attribute")
        return self.fget(instance)

    def __set__(self, instance, value):
        if self.fset is None:
            raise AttributeError("can't set attribute")
        self.fset(instance, value)

    def setter(self, fset):
        return type(self)(self.fget, fset)

class Demo:
    def __init__(self, x):
        self._x = x

    @MyProp
    def x(self):
        return self._x

    @x.setter
    def x(self, value):
        if value < 0:
            raise ValueError("negative")
        self._x = value

d = Demo(10)
print(d.x)    # 10 — MyProp.__get__ calls fget(d)
d.x = 20      # MyProp.__set__ calls fset(d, 20)
print(d.x)    # 20
print(Demo.__dict__["x"])  # <MyProp object> — the descriptor
print(Demo.x)              # <MyProp object> — via class, __get__(None, Demo) returns self
```

**Why data descriptor matters:** Because `property` implements `__set__`, it wins over instance `__dict__`. You cannot shadow a property by writing to `instance.__dict__`:

```python
class Foo:
    @property
    def x(self): return 42
    @x.setter
    def x(self, v): print(f"setter: {v}")

f = Foo()
f.__dict__["x"] = 999    # sneak into instance dict
print(f.__dict__["x"])   # 999 — it's in the dict
print(f.x)               # 42 — but property STILL wins! Data descriptor takes precedence
f.x = 100                # setter: 100 — property.__set__ wins over dict
print(f.__dict__["x"])   # 999 — dict value untouched; setter used _x or other storage
```

Only by using `object.__setattr__` tricks or deleting the property from the class can you bypass it — by design.

## 4. Common Property Patterns

### 4.1 Validation

The most common reason to introduce a property — enforce invariants on assignment:

```python
class Person:
    def __init__(self, name, age):
        self.name = name      # uses setter — validated
        self.age = age        # uses setter — validated

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError("name must be a non-empty string")
        self._name = value.strip()

    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        if not isinstance(value, int) or value < 0:
            raise ValueError("age must be a non-negative integer")
        self._age = value

p = Person("Alice", 30)
print(p.name, p.age)  # Alice 30
# p.age = -5          # ValueError
# p.name = ""         # ValueError
# Person("", -1)      # ValueError — __init__ goes through setters!
```

**Important:** `__init__` assignments like `self.name = name` go through the setter — so construction is validated too. If you want to bypass validation during `__init__` (rare), assign to `self._name` directly.

### 4.2 Computed / Derived Attributes

A property can compute a value from other attributes — no storage needed:

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):
        return self.width * self.height

    @property
    def perimeter(self):
        return 2 * (self.width + self.height)

    @property
    def is_square(self):
        return self.width == self.height

    def __repr__(self):
        return f"Rectangle({self.width}×{self.height}, area={self.area})"

r = Rectangle(3, 4)
print(r.area)       # 12 — computed
print(r.perimeter)  # 14 — computed
r.width = 4
print(r.area)       # 16 — recomputed, reflects new width
print(r.is_square)  # True
```

**When to use `@property` vs a method:**

| Situation | Use | Call site |
|-----------|-----|-----------|
| Cheap computation, no arguments, feels like an attribute | `@property` | `obj.area` |
| Expensive computation or has side effects | Method | `obj.compute_area()` |
| Takes arguments | Method (properties can't take args) | `obj.scale(2)` |
| Setter makes sense (assignable) | `@property` + setter | `obj.value = 5` |

Guideline from the Python docs: if the operation is cheap and attribute-like, a property is appropriate. If it does significant work, hits a database, or has side effects, use a method so the call site (`obj.method()`) signals "work is happening."

### 4.3 Read-Only Attributes

Omit the setter to make a property read-only:

```python
class Circle:
    def __init__(self, radius):
        self._radius = radius

    @property
    def radius(self):
        return self._radius

    # No setter — read-only!
    @property
    def area(self):
        import math
        return math.pi * self._radius ** 2

c = Circle(5)
print(c.radius)   # 5
print(c.area)     # 78.5...
# c.radius = 10   # AttributeError: can't set attribute
# c.area = 100    # AttributeError: can't set attribute

# "Read-only" is enforced by the descriptor, not by convention.
# But you can still bypass via the private name:
c._radius = 10    # works — you're accessing the backing store directly
print(c.radius)   # 10 — now reflects new value
```

**Note:** Read-only via property is the strongest read-only you can get in Python without `__slots__` tricks. But `_radius` is still mutable — "read-only" means "read-only through the property name." Determined code can always access `obj._radius` directly. This is the consenting-adults model — the property guides correct use; it does not create an impenetrable wall.

### 4.4 Property with Backing Store vs Computed

```python
# Backing store — property wraps a stored value with logic:
class Account:
    def __init__(self, balance):
        self._balance = balance   # actual storage

    @property
    def balance(self):
        return self._balance      # returns stored value

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("negative")
        self._balance = value     # stores validated value

# Computed — property derives value, no dedicated storage:
class FullName:
    def __init__(self, first, last):
        self.first = first
        self.last = last

    @property
    def full_name(self):
        return f"{self.first} {self.last}"

    @full_name.setter
    def full_name(self, value):
        self.first, self.last = value.split(" ", 1)

    @full_name.deleter
    def full_name(self):
        self.first = ""
        self.last = ""

p = FullName("Ada", "Lovelace")
print(p.full_name)       # Ada Lovelace — computed from first + last
p.full_name = "Grace Hopper"
print(p.first, p.last)   # Grace Hopper — setter decomposed
del p.full_name
print(p.full_name)       # " " — deleter cleared
```

### 4.5 Lazy / Cached Computation

```python
# Without caching — recomputes every access:
class DataAnalyzer:
    def __init__(self, data):
        self.data = data

    @property
    def mean(self):
        print("computing mean...")
        return sum(self.data) / len(self.data)

a = DataAnalyzer([1, 2, 3, 4, 5])
print(a.mean)  # computing mean... 3.0
print(a.mean)  # computing mean... 3.0 — recomputed!

# With manual caching:
class DataAnalyzerCached:
    def __init__(self, data):
        self.data = data
        self._mean = None

    @property
    def mean(self):
        if self._mean is None:
            print("computing mean...")
            self._mean = sum(self.data) / len(self.data)
        return self._mean

    def invalidate(self):
        self._mean = None  # force recompute next access

a2 = DataAnalyzerCached([1, 2, 3, 4, 5])
print(a2.mean)  # computing mean... 3.0
print(a2.mean)  # 3.0 — cached, no recompute

# With functools.cached_property (Python 3.8+):
from functools import cached_property

class DataAnalyzerAuto:
    def __init__(self, data):
        self.data = data

    @cached_property
    def mean(self):
        print("computing mean...")
        return sum(self.data) / len(self.data)

a3 = DataAnalyzerAuto([1, 2, 3, 4, 5])
print(a3.mean)  # computing mean... 3.0
print(a3.mean)  # 3.0 — cached
print(a3.__dict__["mean"])  # 3.0 — cached_property stores result in instance dict!

# Invalidation for cached_property:
a3.__dict__.pop("mean", None)  # delete cached value
print(a3.mean)  # computing mean... 3.0 — recomputed
```

## 5. `property` vs `cached_property` — When to Use Each

| Feature | `@property` | `@functools.cached_property` |
|---------|-------------|------------------------------|
| Storage | No caching — runs getter every access | Caches result in `instance.__dict__` after first access |
| Recomputation | Every access recomputes | First access computes, subsequent reads return cached value from `__dict__` |
| Setter | Can define `@prop.setter` | No setter — but you can overwrite `obj.__dict__["prop"]` or `obj.prop = val` (see below) |
| Descriptor type | Data descriptor (`__get__` + `__set__` if setter defined) | Non-data descriptor (`__get__` only) — so instance `__dict__` shadows it after caching |
| Invalidation | Automatic if computed from mutable state (always fresh) | Manual — `del obj.prop` or `obj.__dict__.pop("prop")` |
| Thread safety | Depends on getter | Not thread-safe by default (use `functools.cached_property` is thread-safe via lock in CPython 3.12+ or use `threading.Lock`) |
| Use when | Value may change between accesses, or computation is cheap, or you need a setter | Expensive computation on immutable (or rarely changing) data; value won't change during object lifetime |

```python
from functools import cached_property

class Circle:
    def __init__(self, radius):
        self.radius = radius

    @cached_property
    def area(self):
        print("computing area...")
        import math
        return math.pi * self.radius ** 2

c = Circle(5)
print(c.area)   # computing area... 78.5...
print(c.area)   # 78.5... — no print, cached
c.radius = 10
print(c.area)   # 78.5... — STALE! Still cached from radius=5

# Fix: invalidate after mutation
del c.area      # removes from __dict__, next access recomputes
print(c.area)   # computing area... 314.15... — fresh, uses radius=10

# How cached_property works internally (simplified):
# class cached_property:
#     def __init__(self, func): self.func = func
#     def __get__(self, instance, owner):
#         if instance is None: return self
#         if self.func.__name__ in instance.__dict__:
#             return instance.__dict__[self.func.__name__]  # return cached
#         value = self.func(instance)
#         instance.__dict__[self.func.__name__] = value     # cache in instance dict
#         return value
# Key: it is a NON-data descriptor (no __set__), so instance.__dict__ takes precedence
# after the first cache write. That's why del / pop invalidates it.
```

**Common mistake with `cached_property` — mutating the source without invalidating:**

```python
from functools import cached_property

class Document:
    def __init__(self, text):
        self.text = text

    @cached_property
    def word_count(self):
        return len(self.text.split())

doc = Document("hello world")
print(doc.word_count)  # 2 — cached
doc.text = "hello wonderful world of Python"
print(doc.word_count)  # 2 — STALE! text changed but word_count is cached
# Must invalidate:
del doc.word_count
print(doc.word_count)  # 6 — correct after invalidation
```

If the underlying data changes frequently, use `@property` (always fresh) instead of `@cached_property`.

## 6. Performance Considerations

```python
import timeit

# Plain attribute — fastest (direct dict access):
class Plain:
    def __init__(self, x): self.x = x

# Property — adds a function call per access:
class WithProp:
    def __init__(self, x): self._x = x
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v

# Benchmark (CPython 3.11, approximate):
# Plain attribute read:   ~40 ns
# Property read:          ~80-120 ns  (2-3× slower — one Python function call)
# cached_property read:   ~40 ns after first access (dict lookup, same as plain)
# Plain attribute write:  ~50 ns
# Property write:         ~100-150 ns

# In practice, this overhead is negligible for application code.
# Only hot loops over millions of accesses need to care.

# If a property getter does real work (validation, computation, I/O),
# the descriptor overhead is dwarfed by the getter's own cost.
```

**Takeaway:** Properties are slightly slower than plain attributes (one extra function call). For >99% of code, this is irrelevant. If profiling shows a property in a tight loop is a bottleneck, consider caching or using a plain attribute — but measure first.

## 7. Properties and Inheritance

```python
class Base:
    def __init__(self, value):
        self._value = value

    @property
    def value(self):
        return self._value

    @value.setter
    def value(self, v):
        if v < 0:
            raise ValueError("negative")
        self._value = v

class Child(Base):
    @property
    def value(self):
        # Override getter — must re-specify setter if you want it!
        print("Child getter")
        return super().value * 2

    # Without re-defining setter, Child().value = 5 will raise AttributeError!
    # Because @property without .setter creates a read-only property.

    @value.setter
    def value(self, v):
        print("Child setter")
        # Delegate to parent's setter logic:
        Base.value.fset(self, v)  # or: super(Child, Child).value.__set__(self, v)
        # Simpler: just set _value with extra logic:
        # if v < 0: raise ValueError(...)
        # self._value = v

c = Child(10)
print(c.value)   # Child getter → 20
c.value = 5      # Child setter
print(c.value)   # Child getter → 10

# Alternative — override only the setter, keep parent's getter:
class Child2(Base):
    @Base.value.setter
    def value(self, v):
        print("Child2 setter — allows negatives")
        self._value = v  # no validation

c2 = Child2(10)
print(c2.value)  # 10 — uses Base's getter (inherited)
c2.value = -5    # Child2 setter — allows it
print(c2.value)  # -5
```

**Inheritance subtlety:** When you override a property in a subclass with `@property`, you create a **new** property object that has only a getter. The parent's setter is not automatically inherited. You must explicitly re-attach it with `@value.setter` or by referencing `Base.value.fset`.

```python
# If you want to extend rather than replace, access the parent's property object:
class VerboseChild(Base):
    @property
    def value(self):
        val = super().value  # calls Base.value.__get__
        print(f"read value={val}")
        return val

    @value.setter
    def value(self, v):
        print(f"write value={v}")
        super(VerboseChild, VerboseChild).value.__set__(self, v)
        # Or more readably: Base.value.fset(self, v)
```

## 8. Why Properties Over `get_`/`set_` — The Full Argument

### 8.1 API Stability

```python
# Starting point — plain attribute (no property):
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

# Users write:
p = Point(3, 4)
print(p.x)    # 3
p.x = 10      # assignment

# Later you need to clamp x to [0, 100]. With properties, NO caller changes:
class Point:
    def __init__(self, x, y):
        self._x = x
        self._y = y

    @property
    def x(self):
        return self._x
    @x.setter
    def x(self, value):
        self._x = max(0, min(100, value))

    @property
    def y(self):
        return self._y
    @y.setter
    def y(self, value):
        self._y = max(0, min(100, value))

# Callers STILL write p.x and p.x = 10 — zero breakage.

# With Java-style get/set, the initial design forces verbosity on every attribute,
# and changing from field to method is a breaking change.
```

### 8.2 Discoverability and Tooling

```python
class Account:
    @property
    def balance(self):
        """Current balance in USD."""
        return self._balance

# help(Account.balance) shows the docstring
# IDE autocomplete shows `balance` as an attribute (with special icon)
# dir(Account) includes 'balance' alongside other attributes
# isinstance(Account.__dict__["balance"], property) → True — introspectable

# With get_balance() / set_balance():
# Two names to discover, no attribute-like grouping, no unified docstring.
```

### 8.3 When `get_`/`set_` IS Appropriate

Properties cannot take arguments. When the "getter" needs parameters, use a method:

```python
class Config:
    def __init__(self):
        self._data = {"debug": True, "port": 8080}

    # Property — no args, attribute-like:
    @property
    def debug(self):
        return self._data["debug"]

    # Method — takes args, not attribute-like:
    def get(self, key, default=None):
        return self._data.get(key, default)

    def get_formatted(self, key, fmt=str):
        return fmt(self._data[key])

# Also appropriate: when getting has side effects or is expensive enough
# that `obj.method()` better signals "work is happening":
class DataStore:
    def fetch(self, key):        # method — hits database, use verb
        return self._db.query(key)

    @property
    def count(self):             # property — cheap, attribute-like
        return len(self._cache)
```

## 9. Practical Example — Validated, Computed, Cached Model

```python
from __future__ import annotations
from functools import cached_property
import re

class User:
    """
    A user with validated email, computed display name,
    and cached expensive lookup.
    """

    def __init__(self, first_name: str, last_name: str, email: str) -> None:
        # All go through setters — validated at construction:
        self.first_name = first_name
        self.last_name = last_name
        self.email = email
        self._login_count = 0

    # ── Validated string properties ────────────────────────────

    @property
    def first_name(self) -> str:
        return self._first_name

    @first_name.setter
    def first_name(self, value: str) -> None:
        if not isinstance(value, str) or not value.strip():
            raise ValueError("first_name must be a non-empty string")
        self._first_name = value.strip().title()

    @property
    def last_name(self) -> str:
        return self._last_name

    @last_name.setter
    def last_name(self, value: str) -> None:
        if not isinstance(value, str) or not value.strip():
            raise ValueError("last_name must be a non-empty string")
        self._last_name = value.strip().title()

    @property
    def email(self) -> str:
        return self._email

    @email.setter
    def email(self, value: str) -> None:
        value = value.strip().lower()
        if not re.match(r"^[^@]+@[^@]+\.[^@]+$", value):
            raise ValueError(f"invalid email: {value!r}")
        self._email = value

    # ── Computed property (no storage) ─────────────────────────

    @property
    def display_name(self) -> str:
        """Full display name — always computed from current first/last."""
        return f"{self.first_name} {self.last_name}"

    @display_name.setter
    def display_name(self, value: str) -> None:
        parts = value.strip().split(None, 1)
        if len(parts) != 2:
            raise ValueError("display_name must be 'First Last'")
        self.first_name, self.last_name = parts

    @property
    def initials(self) -> str:
        """Read-only computed — no setter."""
        return f"{self.first_name[0]}.{self.last_name[0]}."

    # ── Counter with property + side effect ────────────────────

    @property
    def login_count(self) -> int:
        return self._login_count

    def record_login(self) -> None:
        # Mutate backing store — property reflects new value:
        self._login_count += 1

    # ── Cached expensive property ──────────────────────────────

    @cached_property
    def audit_key(self) -> str:
        """
        Expensive key derivation — cached after first access.
        In real code this might hash, hit a DB, or call an API.
        """
        print("(computing audit_key...)")
        # Simulate expensive work:
        return f"{self.email}:{self.display_name}".lower().replace(" ", "_")

    def __repr__(self) -> str:
        return f"User({self.display_name!r}, {self.email!r})"


# Usage:
u = User("  ada  ", "lovelace", "ADA@EXAMPLE.COM")
print(u)                  # User('Ada Lovelace', 'ada@example.com') — setters normalized
print(u.display_name)     # Ada Lovelace — computed
print(u.initials)         # A.L. — read-only computed
# u.initials = "X.Y."     # AttributeError: can't set attribute

u.display_name = "Grace Hopper"  # setter decomposes
print(u.first_name, u.last_name)  # Grace Hopper
print(u.display_name)             # Grace Hopper

print(u.audit_key)        # (computing audit_key...) grace_hopper:ada@example.com — wait, email still ada@
# Actually: audit_key uses self.email (still ada@example.com) and display_name (now Grace Hopper)
print(u.audit_key)        # cached — no recompute print

u.email = "grace@example.com"
print(u.audit_key)        # STALE — still old cached value!
del u.audit_key           # invalidate
print(u.audit_key)        # (computing audit_key...) grace@example.com:grace_hopper — fresh

# Validation:
# u.email = "not-an-email"  # ValueError
# u.first_name = ""         # ValueError
# User("", "", "bad")       # ValueError at construction — setters validate __init__ too
```

## 10. Edge Cases and Subtleties

### 10.1 Properties and `__dict__` / `__slots__`

```python
class WithDict:
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v

obj = WithDict()
obj.x = 10
print(obj.__dict__)  # {'_x': 10} — property stores in _x, not x
print("x" in obj.__dict__)   # False — x is a descriptor, not in instance dict
print("_x" in obj.__dict__)  # True

# Bypassing the property via __dict__:
obj.__dict__["_x"] = -999  # bypasses setter validation!
print(obj.x)                # -999 — setter was not called

# For __slots__ classes, properties still work — the backing store
# is a slot, not a dict entry:
class Slotted:
    __slots__ = ("_x",)
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v

s = Slotted()
s.x = 42
print(s.x)  # 42 — property works with slots
```

### 10.2 Property Setter Must Use Different Storage Name

```python
# WRONG — infinite recursion:
class Bad:
    @property
    def x(self):
        return self.x      # calls self.x → getter → self.x → infinite recursion!

    @x.setter
    def x(self, value):
        self.x = value     # calls setter → self.x = value → setter → infinite recursion!

# b = Bad()
# b.x = 5  # RecursionError

# CORRECT — use a different name for storage:
class Good:
    @property
    def x(self):
        return self._x     # reads _x — not the property

    @x.setter
    def x(self, value):
        self._x = value    # writes _x — not the property

# Alternative backing names: _x, __x (mangled), _x_internal, etc.
```

### 10.3 Deleting and Re-adding

```python
class Foo:
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v
    @x.deleter
    def x(self): del self._x

f = Foo()
f.x = 10
print(f.x)    # 10
del f.x       # calls deleter → del self._x
# print(f.x)  # AttributeError: 'Foo' object has no attribute '_x'
f.x = 20      # setter creates _x again
print(f.x)    # 20
```

### 10.4 Subclass Override Without Setter Becomes Read-Only

```python
class Base:
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v

class Child(Base):
    @property          # new property — only getter!
    def x(self): return self._x * 2

c = Child()
c._x = 10
print(c.x)    # 20 — Child's getter
# c.x = 5     # AttributeError: can't set attribute — setter was lost!
# Must re-add: @x.setter def x(self, v): self._x = v
```

## 11. Summary

- A `property` is a **data descriptor** that intercepts `obj.attr` (getter), `obj.attr = val` (setter), and `del obj.attr` (deleter), letting you run code while preserving plain attribute syntax.
- **Start with plain attributes.** When you need validation, computation, or side effects, wrap the attribute in a property — callers do not change.
- `@property` creates a property with a getter. `@prop.setter` / `@prop.deleter` attach setter/deleter by returning a new property object. The setter method must have the same name as the property.
- `property(fget, fset, fdel, doc)` is the manual constructor; decorator syntax is sugar for it.
- **Read-only** properties omit the setter — `obj.prop = val` raises `AttributeError`. This is the strongest read-only available for normal classes.
- **Computed properties** derive values from other attributes with no dedicated storage. **Validated properties** guard assignment. **Cached properties** (`@functools.cached_property`) store the first result in `instance.__dict__` as a non-data descriptor — fast on subsequent reads, requires manual invalidation when the source changes.
- Properties are **data descriptors** — they take precedence over instance `__dict__`. You cannot shadow a property by writing to `instance.__dict__`.
- Overriding a property in a subclass with `@property` creates a new property with only a getter — the parent's setter is lost unless you re-attach it.
- **Never write `get_x`/`set_x` methods** when a property will do — properties keep the API attribute-like and allow transparent evolution from simple storage to logic.
