# 10.2 Instance vs Class Attributes

> **Mental model:** Every object — class and instance alike — carries its own namespace dict. The class dict holds shared state and behavior; each instance dict holds per-object state. Attribute access walks a chain: instance dict first, then the class, then its ancestors. Assignment always writes to the object you assign *on*. Understanding who owns what — and how lookup vs assignment differ — eliminates an entire category of Python bugs.

---

## 1. Two Kinds of Attributes, Two Dicts

### 1.1 Defining Them

```python
class Dog:
    # Class attributes — defined in the class body, owned by Dog.__dict__
    species = "Canis familiaris"
    kingdom = "Animalia"
    counter = 0                        # shared counter example

    def __init__(self, name, age):
        # Instance attributes — assigned to self, owned by instance.__dict__
        self.name = name
        self.age = age

buddy = Dog("Buddy", 3)
rex   = Dog("Rex", 5)

print(Dog.__dict__.keys())    # dict_keys(['__module__', 'species', 'kingdom', 'counter', '__init__', ...])
print(buddy.__dict__)         # {'name': 'Buddy', 'age': 3}
print(rex.__dict__)           # {'name': 'Rex', 'age': 5}
```

**Explanation:** `species`, `kingdom`, and `counter` live in `Dog.__dict__` (actually a `mappingproxy` — see 10.6). `name` and `age` live in each instance's `__dict__`. There is one copy of each class attribute regardless of how many instances exist; there is one instance dict per instance.

Visually:

```
Dog.__dict__  ──►  { species: "Canis familiaris",
                      kingdom: "Animalia",
                      counter: 0,
                      __init__: <function> }

buddy.__dict__ ──► { name: "Buddy", age: 3 }
rex.__dict__   ──► { name: "Rex",   age: 5 }

buddy ──► class ──► Dog
rex   ──► class ──► Dog
```

### 1.2 Reading: The Lookup Chain

```python
class Dog:
    species = "Canis familiaris"
    def __init__(self, name):
        self.name = name

buddy = Dog("Buddy")

# Instance attribute — found in buddy.__dict__
print(buddy.name)       # "Buddy" — found on instance, search stops

# Class attribute — NOT in buddy.__dict__, so Python checks Dog.__dict__
print(buddy.species)    # "Canis familiaris" — found on class
print(Dog.species)      # "Canis familiaris" — direct class access

# getattr mirrors the same chain:
print(getattr(buddy, "species"))  # "Canis familiaris"
```

**Rule:** `obj.attr` — Python checks in order:
1. Data descriptors on the class (see 10.6; e.g., `property` with a setter).
2. `obj.__dict__` (instance dict).
3. Non-data descriptors / plain class attributes on `type(obj)` and its MRO ancestors.
4. `__getattr__` fallback if defined.

For non-descriptor attributes (plain values), this simplifies to: **instance dict first, then class hierarchy**. Assignment is different — it always writes to the target object directly, never walking the chain.

### 1.3 Writing: Assignment Always Targets the Receiver

This asymmetry between reading (walks the chain) and writing (does not) is the source of most confusion:

```python
class Dog:
    species = "Canis familiaris"
    tricks = []  # mutable class attribute — danger!

buddy = Dog()
rex   = Dog()

# Reading via instance — walks to class:
print(buddy.species)    # "Canis familiaris" (from Dog)

# Writing via instance — creates/overwrites INSTANCE attribute:
buddy.species = "Canis lupus"
print(buddy.species)    # "Canis lupus" — now in buddy.__dict__
print(Dog.species)      # "Canis familiaris" — class unchanged
print(rex.species)      # "Canis familiaris" — other instances unaffected

print(buddy.__dict__)   # {'species': 'Canis lupus'} — shadowing entry
print(Dog.__dict__["species"])  # "Canis familiaris"
```

**Explanation:** `buddy.species = "Canis lupus"` does **not** modify `Dog.species`. It inserts `species` into `buddy.__dict__`, which now *shadows* the class attribute for that instance only. Reads on `buddy` will find the instance entry first and stop. Reads on `rex` or `Dog` are unaffected. This is true even if you use `setattr(buddy, "species", ...)` — same mechanism.

To actually modify the class attribute, assign on the class:

```python
Dog.species = "Canis lupus"      # modifies Dog.__dict__
print(buddy.species)              # still "Canis lupus" — buddy has its own shadowing copy
# To see the class change, need an instance without a shadow:
print(rex.species)                # "Canis lupus" — rex has no shadow, so sees class change
del buddy.species                 # remove the shadow
print(buddy.species)              # "Canis lupus" — now falls through to class again
```

## 2. The Mutable Class Attribute Pitfall

This is the single most common OOP bug in Python and it bites everyone at least once.

### 2.1 The Bug

```python
class Team:
    members = []          # ONE list object, owned by Team

    def __init__(self, name):
        self.name = name

    def add_member(self, person):
        self.members.append(person)  # mutates the SHARED list!

t1 = Team("Alpha")
t2 = Team("Beta")

t1.add_member("Alice")
print(t1.members)   # ['Alice'] — looks right...
print(t2.members)   # ['Alice'] — WHAT?! Beta has Alice too!
print(Team.members) # ['Alice'] — it's the same object

print(t1.members is t2.members is Team.members)  # True — all three names point to one list
```

**Explanation:** `self.members.append(...)` does **not** assign — it *mutates* the object found via lookup. Lookup finds `Team.members` (since no instance has its own `members`), and `.append` modifies that list in place. No instance `__dict__` entry is created. Every instance sees the same list.

Contrast with assignment, which would shadow:

```python
class Team:
    members = []

t1 = Team()
t1.members = ["Alice"]   # ASSIGNMENT — creates t1.__dict__["members"], shadows class attr
print(t1.members)        # ["Alice"] — instance's own list
print(Team.members)      # []        — class list untouched
```

The bug only occurs with **mutation** (`append`, `extend`, `+=` on lists, `update` on dicts, etc.) not **rebinding** (`=`).

### 2.2 The Fix — Initialize Mutables in `__init__`

```python
class Team:
    # Immutable class attributes are fine as shared defaults:
    default_role = "member"

    def __init__(self, name):
        self.name = name
        self.members = []       # each instance gets its OWN list

    def add_member(self, person):
        self.members.append(person)  # mutates the instance's own list

t1 = Team("Alpha")
t2 = Team("Beta")
t1.add_member("Alice")
print(t1.members)  # ['Alice']
print(t2.members)  # [] — independent!
print(t1.members is t2.members)  # False
```

### 2.3 More Pitfall Variations

```python
# Pitfall with dict:
class Registry:
    data = {}                       # shared!

    def register(self, key, value):
        self.data[key] = value      # mutates shared dict — bug!

# Pitfall with set:
class Graph:
    edges = set()                   # shared!

# Pitfall with nested mutables:
class Config:
    options = {"debug": False, "tags": []}  # shared dict containing shared list!

# Pitfall via += (which for lists is .extend, i.e., mutation):
class Counter:
    history = []
    def record(self, n):
        self.history += [n]  # for lists, += mutates in place if attribute found on class
        # Actually: self.history = self.history.__iadd__([n])
        # But __iadd__ mutates and returns same object — subtle!
```

For `+=` on lists found via class lookup, CPython *does* mutate the class's list in place (`list.__iadd__` extends and returns `self`), but the subsequent implicit assignment (`self.history = result`) also creates an instance attribute pointing to the same (now-extended) list — so the first `+=` appears to create a per-instance list, but the class list has already been corrupted:

```python
class A:
    items = []
a1 = A(); a2 = A()
a1.items += [1]
print(a1.__dict__)   # {'items': [1]} — a1 now has instance attr
print(A.items)       # [1] — class list was ALSO mutated!
print(a2.items)      # [1] — a2 sees the mutated class list
a2.items += [2]
print(A.items)       # [1] — wait, a1 shadowed so A.items stays [1]? Let's trace...
# a2 had no instance attr, so a2.items lookup found A.items ([1]),
# then [1].__iadd__([2]) mutated it to [1,2], then a2.__dict__["items"] = [1,2]
# But a1.__dict__["items"] is the SAME object as A.items was at that moment!
print(a1.items)      # [1, 2] — a1's list was mutated too because a1.items IS A.items!
print(a1.items is A.items)  # True before a1's shadowing? After first +=, a1.items is A.items
```

This `+=` aliasing is exceptionally subtle. **Rule of thumb:** never use mutable class attributes for per-instance state. Initialize in `__init__`.

## 3. Shadowing — Instance Hides Class

### 3.1 Basic Shadowing

```python
class Config:
    timeout = 30
    retries = 3

c1 = Config()
c2 = Config()

print(c1.timeout)   # 30 (from class)

c1.timeout = 60     # creates c1.__dict__["timeout"] = 60
print(c1.timeout)   # 60 (from instance)
print(c2.timeout)   # 30 (still from class)
print(Config.timeout)  # 30 (class unchanged)

del c1.timeout      # remove instance shadow
print(c1.timeout)   # 30 (falls through to class again)
```

### 3.2 Shadowing Methods (Don't Do This)

```python
class Dog:
    def bark(self):
        return "woof"

buddy = Dog()
print(buddy.bark())  # woof

buddy.bark = lambda: "meow"  # shadows the method on this instance only
print(buddy.bark())  # meow — instance attr shadows class function
print(Dog.bark)      # still the original function

other = Dog()
print(other.bark())  # woof — other instances unaffected

del buddy.bark
print(buddy.bark())  # woof — falls through to class again
```

While legal, shadowing a method with instance data is almost always a design mistake. It breaks polymorphism and surprises readers.

### 3.3 When Shadowing Is Intentional — Instance Defaults

A deliberate and Pythonic use of class attributes is as **defaults** that instances can override:

```python
class Request:
    timeout = 30          # default for all requests
    retries = 3           # default retry count
    headers = None        # sentinel — must not be mutable default (see below)

    def __init__(self, url, timeout=None, retries=None):
        self.url = url
        if timeout is not None:
            self.timeout = timeout   # shadow only if explicitly provided
        if retries is not None:
            self.retries = retries

r1 = Request("https://example.com")              # uses class defaults: 30, 3
r2 = Request("https://example.com", timeout=60)  # shadows timeout: 60, retries still 3

print(r1.timeout, r1.retries)  # 30 3  (both from class)
print(r2.timeout, r2.retries)  # 60 3  (timeout shadowed, retries from class)

# Changing the class default affects instances that haven't shadowed:
Request.timeout = 45
print(r1.timeout)  # 45 — r1 had no shadow, sees new class value
print(r2.timeout)  # 60 — r2 shadowed, unaffected
```

This pattern is common in frameworks (Django models, `http.client`, `logging`). It lets you define a default once on the class and override per-instance only when needed.

**Mutable default pitfall applies here too** — if the default is mutable, shadowing via `if x is not None` avoids the shared-mutation bug, but a careless `self.headers = self.headers or {}` pattern can still bite.

## 4. Modifying Class Attributes — Three Paths and Their Effects

```python
class Counter:
    count = 0

    def increment_via_class(self):
        Counter.count += 1       # explicit class assignment — always modifies class

    def increment_via_self_wrong(self):
        self.count += 1          # BUG if count started as class attr!

    def increment_via_type(self):
        type(self).count += 1    # works even for subclasses — more robust

c1 = Counter()
c2 = Counter()
print(Counter.count)  # 0

c1.increment_via_class()
print(Counter.count)  # 1
print(c2.count)       # 1 — sees class change (no shadow)

# The self.count += 1 pitfall:
Counter.count = 0
c3 = Counter()
c3.increment_via_self_wrong()
# What happens: Python evaluates `self.count + 1` → 0 + 1 = 1 (reads from class)
# then assigns `self.count = 1` → creates instance shadow!
print(c3.count)       # 1 (instance shadow)
print(Counter.count)  # 0 (class unchanged!)
print(c2.count)       # 0 (other instances see class, not c3's shadow)

# Subsequent calls on c3 increment the SHADOW, not the class:
c3.increment_via_self_wrong()
print(c3.count)       # 2 (incrementing instance shadow)
print(Counter.count)  # 0 (still)
```

**Lesson:** To modify a class attribute, always assign via the class (`ClassName.attr =` or `type(self).attr =`), never via `self.attr =` or `self.attr +=`.

| Operation | Target | Effect |
|-----------|--------|--------|
| `Counter.count += 1` | `Counter.__dict__` | Modifies class — visible to all non-shadowing instances |
| `type(self).count += 1` | `type(self).__dict__` | Same, but respects subclass (`self` might be subclass instance) |
| `self.count += 1` | `self.__dict__` (after reading class value) | Creates instance shadow — class unchanged, bug for shared counters |
| `self.count = 5` | `self.__dict__` | Creates instance shadow |
| `del self.count` | `self.__dict__` | Removes shadow, if any; next read falls through to class |
| `del Counter.count` | `Counter.__dict__` | Removes class attribute entirely |

## 5. Class Attributes as Shared State — Legitimate Uses

Not every class attribute is a bug. Shared state is intentional when you *want* all instances to see the same data:

### 5.1 Constants and Configuration

```python
import math

class Circle:
    pi = math.pi          # constant — immutable, safe to share
    default_color = "red" # default — instances can shadow if needed

    def __init__(self, radius, color=None):
        self.radius = radius
        if color is not None:
            self.color = color  # shadow only when overridden

    @property
    def area(self):
        return self.pi * self.radius ** 2  # reads pi via instance → finds class

c = Circle(5)
print(c.area)           # 78.5...
print(c.pi)             # 3.14159... (from class)
Circle.pi = 3.14        # change affects all circles without shadow
```

### 5.2 Shared Counters and Registries

```python
class Widget:
    count = 0
    registry: list["Widget"] = []  # intentionally shared — but careful!

    def __init__(self, name):
        self.name = name
        type(self).count += 1              # correctly increments class counter
        # For registry, we WANT shared mutation — so class-level mutation is correct:
        type(self).registry.append(self)   # intentional shared state

    @classmethod
    def total(cls):
        return cls.count

w1 = Widget("a")
w2 = Widget("b")
print(Widget.count)     # 2
print(Widget.registry)  # [Widget(a), Widget(b)]

# WARNING: registry = [] as class attr is intentionally shared mutation.
# Document it clearly. Alternative: use a module-level dict or class-level
# dict managed via classmethods.
```

### 5.3 Sentinel Values

```python
class Node:
    _unset = object()   # unique sentinel — immutable identity check

    def __init__(self, value=_unset):
        if value is Node._unset:
            value = self._default_value()
        self.value = value

    def _default_value(self):
        return 0
```

Class-level sentinels (`object()`) are safe because they are immutable and compared with `is`.

## 6. Inheritance and Attribute Lookup

Class attributes participate in the Method Resolution Order (MRO) — the linearized chain of base classes:

```python
class Animal:
    kingdom = "Animalia"
    def speak(self): return "..."

class Dog(Animal):
    species = "Canis familiaris"
    def speak(self): return "woof"

class Labrador(Dog):
    pass  # inherits everything

lab = Labrador()
print(lab.kingdom)   # "Animalia" — found via Labrador → Dog → Animal
print(lab.species)   # "Canis familiaris" — found via Labrador → Dog
print(lab.speak())   # "woof" — found via Labrador → Dog (overrides Animal)

# Each class has its own dict:
print("kingdom" in Animal.__dict__)     # True
print("kingdom" in Dog.__dict__)        # False — not shadowed, just inherited
print("species" in Dog.__dict__)        # True
print("species" in Labrador.__dict__)   # False

# Shadowing in a subclass:
class Cat(Animal):
    kingdom = "Feline?"  # shadows Animal.kingdom for Cat and its subclasses

print(Cat.kingdom)      # "Feline?"
print(Animal.kingdom)   # "Animalia" — parent unchanged
```

**Key rule:** Assignment to `Child.attr` never affects `Parent.attr` — it creates an entry in `Child.__dict__` that shadows the parent for `Child` and its descendants.

```python
class Base:
    x = 10

class Child(Base):
    pass

print(Child.x)    # 10 (from Base)
Child.x = 20      # creates Child.__dict__["x"]
print(Child.x)    # 20 (from Child)
print(Base.x)     # 10 (unchanged)
del Child.x
print(Child.x)    # 10 (falls through to Base again)
```

## 7. Introspection — Seeing Who Owns What

```python
class MyClass:
    class_attr = "on class"
    def __init__(self, value):
        self.instance_attr = value
    def method(self):
        pass

obj = MyClass(42)
obj.extra = "bonus"

# Who owns what?
print("class_attr" in MyClass.__dict__)     # True
print("class_attr" in obj.__dict__)          # False — only on class
print("instance_attr" in obj.__dict__)       # True
print("instance_attr" in MyClass.__dict__)   # False — only on instance

# vars() and dir() differences (see 10.6 for full treatment):
print(vars(obj))          # {'instance_attr': 42, 'extra': 'bonus'} — instance dict only
print(vars(MyClass))      # mappingproxy — class dict (read-only view)

# dir() walks the entire MRO and instance dict:
print([x for x in dir(obj) if not x.startswith("_")])
# ['class_attr', 'extra', 'instance_attr', 'method']

# getattr with MRO walk vs direct dict check:
print(getattr(obj, "class_attr"))                    # "on class" (walks MRO)
print(obj.__dict__.get("class_attr", "NOT FOUND"))   # "NOT FOUND" (instance dict only)
print(MyClass.__dict__.get("class_attr", "NOT FOUND"))  # "on class"

# Check ownership precisely:
def owns(instance, name):
    return name in instance.__dict__

def owns_anywhere(obj, name):
    return any(name in cls.__dict__ for cls in type(obj).__mro__)

print(owns(obj, "instance_attr"))        # True
print(owns(obj, "class_attr"))           # False
print(owns_anywhere(obj, "class_attr"))  # True
```

## 8. When to Use Each — Decision Guide

| Situation | Use | Why |
|-----------|-----|-----|
| Per-instance state (name, balance, data) | Instance attribute (`self.x` in `__init__`) | Each object needs independent value |
| Mutable per-instance state (list, dict, set) | Instance attribute in `__init__` | Avoid shared-mutation bug |
| Constant shared across all instances (`PI`, `DEFAULT_TIMEOUT`) | Class attribute (immutable value) | One copy, accessible via class or instance |
| Default that instances may override | Class attribute + conditional shadow in `__init__` | Instances without override see class default; class change propagates |
| Shared mutable state you *intend* to share (registry, counter) | Class attribute + always mutate via `ClassName.attr` or `type(self).attr` | Explicit class-level mutation is correct when sharing is intentional |
| Per-subclass configuration | Class attribute overridden in subclass | Each subclass gets its own copy shadowing the parent |

```python
# Comprehensive idiomatic example:
from typing import ClassVar

class Employee:
    # Class attributes — shared / defaults:
    company: ClassVar[str] = "Acme Corp"     # ClassVar annotation signals "class attr"
    default_department: ClassVar[str] = "General"
    employee_count: ClassVar[int] = 0         # shared counter
    _registry: ClassVar[list["Employee"]] = []  # shared registry (intentional)

    def __init__(self, name: str, department: str | None = None):
        self.name = name                          # instance attr — per-employee
        self.department = department or self.default_department  # shadow if given
        self.tasks: list[str] = []                # instance attr — mutable, per-instance!

        # Update shared state via class:
        type(self).employee_count += 1
        type(self)._registry.append(self)

    def add_task(self, task: str) -> None:
        self.tasks.append(task)  # mutates instance's own list — safe

    @classmethod
    def total_employees(cls) -> int:
        return cls.employee_count

    @classmethod
    def all_employees(cls) -> list["Employee"]:
        return list(cls._registry)
```

**Annotation note:** `ClassVar` from `typing` tells type checkers "this is a class attribute, not an instance attribute." It has no runtime effect but improves tooling and documents intent.

## 9. Common Mistakes Summary

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Mutable class attribute for per-instance data (`members = []` in body) | All instances share same list; adding to one appears in all | Initialize `self.members = []` in `__init__` |
| `self.counter += 1` to increment a shared counter | Creates instance shadow after first call; class counter never changes | Use `type(self).counter += 1` or `ClassName.counter += 1` |
| `self.items.append(x)` thinking it creates per-instance list | Mutates shared class list | Initialize list in `__init__` |
| Assigning via instance expecting to change class | `obj.attr = val` shadows instead of updating class | Assign via `ClassName.attr = val` |
| Forgetting that reading walks MRO but writing does not | Confusion about where attribute lives | Remember: `obj.attr` (read) walks chain; `obj.attr = val` (write) targets `obj.__dict__` |
| Using class attribute for instance-specific mutable default in `__init__` signature | `def __init__(self, items=[])` — same shared-mutation bug | Use `def __init__(self, items=None): self.items = items if items is not None else []` |

## 10. Edge Cases

### 10.1 `__dict__` Absence with `__slots__` (Preview)

```python
class Slotted:
    __slots__ = ("x", "y")

s = Slotted()
s.x = 10
# s.__dict__  # AttributeError — no instance dict when __slots__ used (see 10.6)
# This changes the instance-vs-class storage story entirely.
```

### 10.2 Descriptors Override Instance Dict (Preview)

```python
class ReadOnly:
    def __get__(self, instance, owner):
        if instance is None:
            return self
        return 42
    def __set__(self, instance, value):
        raise AttributeError("read-only!")

class MyClass:
    x = ReadOnly()

obj = MyClass()
obj.__dict__["x"] = 999   # sneak into instance dict directly
print(obj.x)               # 42 — descriptor wins over instance dict for data descriptors!
print(obj.__dict__["x"])   # 999 — still there, but hidden
```

Data descriptors take precedence over instance dict — the only exception to "instance dict first." Covered in 10.6.

### 10.3 Class Attributes That Are Functions

```python
class MyClass:
    def method(self): return "method"
    func = lambda self: "lambda assigned as class attr"

obj = MyClass()
print(obj.method())  # "method" — function descriptor binds self
print(obj.func())    # "lambda assigned as class attr" — same binding

# But plain values don't bind:
class MyClass2:
    value = 42
    text = "hello"

obj2 = MyClass2()
# obj2.value  # just returns 42, no binding — not a descriptor
```

## 11. Summary

- **Two dicts:** `ClassName.__dict__` holds class attributes (shared); `instance.__dict__` holds instance attributes (per-object).
- **Reading** `obj.attr` walks instance dict → class → ancestors (MRO). **Writing** `obj.attr = val` always creates/overwrites in `obj.__dict__`, shadowing any class attribute of the same name.
- **Mutating** a mutable class attribute via an instance (`self.items.append(...)`) modifies the shared object — the most common bug. Fix: initialize mutables as `self.items = []` in `__init__`.
- **Incrementing** a shared counter via `self.count += 1` shadows after the first call. Use `type(self).count += 1` or `ClassName.count += 1`.
- **Class attributes as defaults:** define `timeout = 30` on the class, shadow with `self.timeout = val` in `__init__` only when the caller provides a value. Changes to the class default propagate to non-shadowing instances.
- **Intentional sharing** (registries, counters) is valid — always mutate/read via the class, never via `self`, and document the intent.
- Use `ClassVar` annotations and `vars()`/`__dict__` inspection to make ownership explicit.
