# 10.1 Classes, Instances, and `self`

> **Mental model up front:** In Python, a `class` is not a compile-time blueprint that disappears after compilation. It is a live object — an instance of `type` — created at runtime when the interpreter executes the `class` block. Instances are separate objects that delegate attribute lookup to their class. `self` is merely the conventional name for the explicit first parameter that Python binds to the instance for you.

---

## 1. What a `class` Really Is

### 1.1 `class` Is an Executable Statement

If you come from Java or C++, you think of a class definition as a declaration processed by the compiler. In Python it is a **runtime statement** — syntactic sugar for building an object.

```python
# This code RUNS top-to-bottom when Python reaches it.
print("before class")

class Dog:
    print("inside class body — this executes NOW")
    species = "Canis familiaris"
    print(f"species just bound to {species}")

print("after class")
print(Dog)                     # <class '__main__.Dog'>
print(type(Dog))               # <class 'type'>
```

**Explanation:** The prints inside the class body execute immediately at class-definition time, not when you create an instance. The body is executed in a temporary namespace dict; after the body finishes, Python calls `type(name, bases, namespace)` to create the class object and binds it to the name `Dog` in the enclosing scope. This is why you can put arbitrary code inside a class body — loops, conditionals, even `print` — though idiomatic code limits itself to attribute and method definitions.

### 1.2 A Class Is an Object — An Instance of `type`

```python
class Dog:
    pass

print(isinstance(Dog, object))  # True — everything is an object
print(isinstance(Dog, type))    # True — classes are instances of type
print(type(type))               # <class 'type'> — type is its own instance

# You can pass a class around like any value:
def make_instance(factory):
    return factory()

make_instance(Dog)   # creates a Dog, because Dog is callable
alias = Dog          # alias refers to the same class object
```

**Explanation:** Unlike Java where `Class<Dog>` is a reflective mirror, Python's `Dog` *is* the object itself. You can store it in lists, pass it to functions, assign attributes to it at runtime, and even create classes dynamically with `type("Dog", (), {"species": "Canis"})`. The metaclass `type` is the factory for classes exactly as your class is the factory for instances.

### 1.3 `type` — The Three-Argument Form

```python
# These two are equivalent:
class Point:
    origin = (0, 0)
    def move(self, dx, dy):
        self.x += dx

Point2 = type("Point2", (), {"origin": (0, 0), "move": lambda self, dx, dy: None})
# type(name, bases_tuple, namespace_dict)
```

Understanding that `class` desugars to a `type()` call demystifies decorators, metaclasses, and dynamic class creation — all of which simply intercept or call that same construction.

## 2. Defining a Class — Syntax Deep Dive

```python
class ClassName(Base1, Base2, keyword_arg=value):
    """Optional docstring — becomes ClassName.__doc__."""
    # class body
```

| Component | Meaning |
|-----------|---------|
| `ClassName` | Name bound in enclosing scope; also stored as `__name__` and `__qualname__` |
| `Base1, Base2` | Base classes (inheritance). Omit for `object` base in Python 3 |
| `keyword_arg=value` | Passed to metaclass (e.g., `metaclass=ABCMeta`) |
| `"""docstring"""` | First string literal becomes `__doc__` |
| Body | Executed once to populate the class `__dict__` |

```python
class Account:
    """A simple bank account."""

print(Account.__name__)      # 'Account'
print(Account.__qualname__)  # 'Account' (nested classes get 'Outer.Inner')
print(Account.__doc__)       # 'A simple bank account.'
print(Account.__bases__)     # (<class 'object'>,)
print(Account.__dict__)      # mappingproxy({...}) — read-only view
```

**Java/C++ contrast:** Java class definitions are visible to the compiler for static type checking and produce `.class` bytecode. Python class definitions produce no separate file — they are imperative instructions that build a dict and hand it to `type`.

## 3. Creating Instances — Calling the Class

```python
class Dog:
    species = "Canis familiaris"
    def __init__(self, name, age):
        self.name = name
        self.age = age

buddy = Dog("Buddy", 3)    # Looks like a function call — because it IS one
print(buddy)               # <__main__.Dog object at 0x...>
print(type(buddy))         # <class '__main__.Dog'>
print(isinstance(buddy, Dog))  # True
```

**Explanation:** `Dog("Buddy", 3)` calls `Dog.__call__` as defined by `type`. That trigger runs a two-phase protocol:

```
instance = Dog.__new__(Dog, "Buddy", 3)   # phase 1: create bare object
if isinstance(instance, Dog):
    instance.__init__("Buddy", 3)          # phase 2: initialize it
```

Most classes never define `__new__`, so `object.__new__` creates a bare object with an empty `__dict__` and no initialization. Then `__init__` populates it. This split is critical — see Section 5.

### 3.1 `__new__` vs `__init__` — Constructor vs Initializer

| Method | Role | Receives | Returns | Typical use |
|--------|------|----------|---------|-------------|
| `__new__(cls, *args, **kwargs)` | **Constructor** — creates and returns the new instance | The class (`cls`) | A new instance (usually via `super().__new__(cls)`) | Immutable types, singletons, caching, subclassing immutables |
| `__init__(self, *args, **kwargs)` | **Initializer** — configures an already-created instance | The instance (`self`) | Must return `None` (enforced) | 99% of your initialization logic |

```python
class Dog:
    def __new__(cls, name, age):
        print(f"__new__ called with cls={cls.__name__}")
        instance = super().__new__(cls)   # actually allocate the object
        print(f"  allocated {instance}")
        return instance

    def __init__(self, name, age):
        print(f"__init__ called with self={self}, name={name}")
        self.name = name
        self.age = age
        # return "oops"  # TypeError: __init__() should return None

buddy = Dog("Buddy", 3)
# __new__ called with cls=Dog
#   allocated <__main__.Dog object at 0x...>
# __init__ called with self=<__main__.Dog object at 0x...>, name=Buddy
```

**Explanation:** The fact that `__init__` receives `self` — an already-allocated object whose identity is the same as returned by `__new__` — proves it does not construct. Java's constructor both allocates and initializes in one opaque step; Python separates the two so you can hook either. If `__new__` returns an object that is *not* an instance of the class, `__init__` is silently skipped:

```python
class Sneaky:
    def __new__(cls, value):
        if value < 0:
            return "negative — not even a Sneaky!"
        return super().__new__(cls)
    def __init__(self, value):
        print("__init__ ran")
        self.value = value

print(Sneaky(-5))   # "negative — not even a Sneaky!" — __init__ never ran
print(Sneaky(10))   # __init__ ran — then the instance
```

**Common mistake:** Trying to `return self.name` from `__init__` or thinking `buddy = Dog(...)` receives whatever `__init__` returns. It always receives the instance from `__new__`.

## 4. `self` — Explicit Is Better Than Implicit

### 4.1 Why Python Requires Explicit `self`

```python
class Counter:
    def increment(self):
        self.count += 1

    def increment_wrong():        # missing self — what happens?
        pass

c = Counter()
c.count = 0
c.increment()          # works: Python passes c as self automatically
# c.increment_wrong()  # TypeError: increment_wrong() takes 0 positional arguments but 1 was given
```

In Java/C++, `this` is an implicit keyword magically in scope. Python's design philosophy — *"explicit is better than implicit"* (Zen of Python) — makes the instance reference an explicit first parameter. The name `self` is only a convention, but it is a **universally followed** convention; linters, IDEs, and every Python programmer expect it.

```python
class Counter:
    def increment(this):          # legal, but NEVER do this
        this.count += 1
    def increment2(me):           # also legal, equally frowned upon
        me.count += 1
```

**Explanation:** Python could have made `this` implicit, but explicit `self` gives three advantages:
1. **Clarity** — you always see where instance state comes from (`self.x` vs bare `x`).
2. **Explicit class vs instance access** — `self.attr` vs `ClassName.attr` is visually distinct.
3. **Method/function duality** — methods are just functions that happen to receive the instance; there is no separate "method" declaration.

### 4.2 How Binding Works — Functions Are Descriptors

```python
class Dog:
    def bark(self):
        return f"{self.name} says woof!"

buddy = Dog()
buddy.name = "Buddy"

# Accessing via instance gives a *bound method*:
print(buddy.bark)           # <bound method Dog.bark of <...Dog object>>
print(type(buddy.bark))     # <class 'method'>
print(buddy.bark())         # Buddy says woof!

# Accessing via class gives the raw function:
print(Dog.bark)             # <function Dog.bark at 0x...>
print(type(Dog.bark))       # <class 'function'>

# They are the same underlying function object:
print(Dog.bark is buddy.bark.__func__)  # True (CPython 3)
# Calling the unbound function requires passing self manually:
print(Dog.bark(buddy))      # Buddy says woof! — identical to buddy.bark()

# What binding actually does:
import types
print(isinstance(Dog.__dict__['bark'], types.FunctionType))  # True
# Function objects implement __get__, so Dog.__dict__['bark'].__get__(buddy, Dog)
# returns a method that curries `buddy` as the first argument.
```

**Explanation:** This is the descriptor protocol in action (previewed fully in 10.3 and 10.6). A `function` object implements `__get__(self, instance, owner)`. When you write `buddy.bark`, Python finds `bark` in `Dog.__dict__`, sees it has `__get__`, and calls `Dog.__dict__['bark'].__get__(buddy, Dog)` which returns a `method` object that remembers `buddy`. Calling `buddy.bark()` is shorthand for `Dog.bark(buddy)`. Java's `this` binding is hard-wired by the VM; Python's is a pluggable protocol you can replicate.

```python
# Manual binding demo — not idiomatic, but illuminating:
unbound = Dog.__dict__['bark']
bound = unbound.__get__(buddy, Dog)
print(bound())  # Buddy says woof!
```

### 4.3 Common `self` Pitfalls

```python
class Account:
    def __init__(self, balance):
        self.balance = balance

    def deposit(self, amount):
        # Forgot self. — creates a LOCAL variable, not instance state!
        balance = self.balance + amount   # BUG: no self. on assignment

    def deposit_fixed(self, amount):
        self.balance += amount            # correct

    def __init__confused(self, balance):
        # Forgetting self. on the left side silently creates a local
        balance = balance  # does nothing to the instance!
        self.balance = balance  # what you meant

acc = Account(100)
acc.deposit(50)
print(acc.balance)  # still 100 — bug!
```

Another pitfall — calling a method without an instance:

```python
# Dog.bark()  # TypeError: bark() missing 1 required positional argument: 'self'
# You must provide an instance:
Dog.bark(buddy)  # works — you supplied self explicitly
```

And the classic "lost self" when passing methods as callbacks:

```python
class Button:
    def __init__(self, label):
        self.label = label
    def click(self):
        print(f"Clicked {self.label}")

b = Button("OK")
callback = b.click       # bound method — retains self, safe to call later
callback()               # Clicked OK

callback2 = Button.click # unbound function — needs an instance
# callback2()            # TypeError: missing self
callback2(b)             # Clicked OK — must pass instance manually
```

## 5. `__init__` In Depth

### 5.1 Signature and Arguments

```python
class Point:
    def __init__(self, x=0, y=0, *, label=None):
        self.x = x
        self.y = y
        self.label = label

p1 = Point()                    # x=0, y=0
p2 = Point(3)                   # x=3, y=0
p3 = Point(3, 4, label="A")     # x=3, y=4
# p3 = Point(3, 4, "A")         # TypeError: label is keyword-only

# __init__ can use any parameter features: defaults, *args, **kwargs, keyword-only
class Flexible:
    def __init__(self, *args, **kwargs):
        print(f"args={args}, kwargs={kwargs}")
        self.data = args

Flexible(1, 2, key="value")  # args=(1, 2), kwargs={'key': 'value'}
```

**Explanation:** Arguments to `Dog("Buddy", 3)` are forwarded verbatim to both `__new__` and `__init__` (minus `cls`/`self`). So `__init__`'s signature *defines* the constructor's call signature. If you add a parameter to `__init__`, callers must pass it when constructing.

### 5.2 No Overloading — One `__init__` Only

```python
# Java allows: Dog(String name) and Dog(String name, int age)
# Python does NOT — the last definition wins:

class Dog:
    def __init__(self, name):
        self.name = name
        self.age = 0

    def __init__(self, name, age):  # silently replaces the previous one!
        self.name = name
        self.age = age

# Dog("Buddy")  # TypeError: __init__() missing 1 required positional argument: 'age'
```

**Pythonic alternatives** for multiple construction paths (see also 10.3):

```python
class Dog:
    def __init__(self, name, age=0):  # default argument
        self.name = name
        self.age = age

# Or use classmethods as named constructors:
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    @classmethod
    def newborn(cls, name):
        return cls(name, 0)

    @classmethod
    def from_dict(cls, data):
        return cls(data["name"], data["age"])

Dog("Buddy", 3)
Dog.newborn("Puppy")
Dog.from_dict({"name": "Rex", "age": 5})
```

### 5.3 `__init__` Must Return `None`

```python
class Bad:
    def __init__(self):
        return 42  # TypeError: __init__() should return None, not 'int'

class Good:
    def __init__(self):
        self.x = 1
        # implicit return None — correct
        # explicit `return None` also allowed but unnecessary
```

### 5.4 The Instance `__dict__`

```python
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

buddy = Dog("Buddy", 3)

print(buddy.__dict__)   # {'name': 'Buddy', 'age': 3}
print(vars(buddy))      # same as buddy.__dict__ — vars() is the builtin accessor

# You can manipulate __dict__ directly (not idiomatic, but revealing):
buddy.__dict__["breed"] = "Labrador"
print(buddy.breed)      # Labrador — attribute lookup finds it in __dict__

# Each instance has its OWN dict:
rex = Dog("Rex", 5)
print(rex.__dict__)     # {'name': 'Rex', 'age': 5} — no 'breed'
print(buddy.__dict__)   # {'name': 'Buddy', 'age': 3, 'breed': 'Labrador'}
```

**Explanation:** In CPython, `self.name = value` is syntactic sugar for `self.__dict__["name"] = value` (when no data descriptor intervenes). The instance `__dict__` is a plain `dict` that holds per-instance state. This is fundamentally different from Java/C++ where instance fields are fixed slots determined at compile time — Python instances are open-ended bags of attributes you can add or remove at runtime.

```python
buddy.favorite_toy = "ball"   # add new attribute any time
del buddy.age                  # remove an attribute
print(buddy.__dict__)          # {'name': 'Buddy', 'breed': 'Labrador', 'favorite_toy': 'ball'}

# hasattr / getattr / setattr / delattr all operate on this dict (or via descriptors):
print(hasattr(buddy, "name"))      # True
print(getattr(buddy, "name"))      # Buddy
setattr(buddy, "name", "Bud")      # same as buddy.name = "Bud"
delattr(buddy, "breed")            # same as del buddy.breed
```

### 5.5 What If `__init__` Is Missing?

```python
class Bare:
    pass

b = Bare()
print(b.__dict__)  # {} — empty, no __init__ to populate it
b.x = 10           # you can still set attributes dynamically
print(b.__dict__)  # {'x': 10}

# Inheritance: if you don't define __init__, you inherit your parent's
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    pass  # inherits Animal.__init__

d = Dog("Buddy")
print(d.name)  # Buddy

class Cat(Animal):
    def __init__(self, name, lives=9):
        super().__init__(name)  # must explicitly call parent — Python never does implicitly
        self.lives = lives
```

**Critical difference from Java/C++:** Python **never** implicitly calls a parent `__init__`. If you define `__init__` in a subclass and want parent initialization, you *must* call `super().__init__(...)` yourself. Forgetting is a common bug that leaves parent state uninitialized.

## 6. Putting It Together — A Realistic Example

```python
from typing import Optional

class BankAccount:
    """A bank account with an owner and balance."""

    # Class attribute — shared default interest rate (see 10.2)
    interest_rate: float = 0.02

    def __init__(self, owner: str, balance: float = 0.0) -> None:
        # Instance attributes — per-account state
        self.owner = owner
        self.balance = float(balance)
        self._transactions: list[float] = []  # "private" by convention (see 10.4)

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("deposit amount must be positive")
        self.balance += amount
        self._transactions.append(amount)

    def withdraw(self, amount: float) -> None:
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount
        self._transactions.append(-amount)

    def apply_interest(self) -> None:
        # Accessing class attribute via self — works but see 10.2 for nuance
        self.balance *= (1 + self.interest_rate)

    def __repr__(self) -> str:
        return f"BankAccount(owner={self.owner!r}, balance={self.balance:.2f})"


# Usage:
alice = BankAccount("Alice", 1000)
bob = BankAccount("Bob")               # balance defaults to 0.0
alice.deposit(500)
alice.withdraw(200)
print(alice)                           # BankAccount(owner='Alice', balance=1300.00)
print(alice.__dict__)
# {'owner': 'Alice', 'balance': 1300.0, '_transactions': [500, -200]}
print(bob.__dict__)
# {'owner': 'Bob', 'balance': 0.0, '_transactions': []}
```

**Walk-through:**
1. `BankAccount("Alice", 1000)` calls `BankAccount.__new__` (inherited from `object`) to allocate a bare object, then `BankAccount.__init__(self, "Alice", 1000)` to set `owner`, `balance`, and `_transactions`.
2. Each instance gets its own `__dict__` — Alice and Bob's balances and transaction lists are independent.
3. `interest_rate` lives on the *class*, not on any instance (covered in 10.2).
4. `self` is explicit in every method signature and every attribute access.
5. No parent `__init__` call is needed because `BankAccount` inherits only from `object`.

## 7. Edge Cases and Subtleties

### 7.1 `__init__` Is Not Called on `__new__` Bypass

```python
class Point:
    def __init__(self, x, y):
        print(f"init: {x}, {y}")
        self.x = x
        self.y = y

# Bypass __init__ entirely via __new__:
p = Point.__new__(Point)   # allocates bare instance, NO __init__
print(p.__dict__)          # {}
print(hasattr(p, "x"))     # False — never initialized!

# `copy` and `pickle` and ORMs use this trick internally.
# You must manually initialize if you bypass:
p.__init__(3, 4)           # now initialize it manually
print(p.__dict__)          # {'x': 3, 'y': 4}
```

### 7.2 Calling `__init__` Twice

```python
p = Point(1, 2)
print(p.__dict__)   # {'x': 1, 'y': 2}
p.__init__(99, 99)  # legal — just a normal method call, re-initializes!
print(p.__dict__)   # {'x': 99, 'y': 99}
```

`__init__` is an ordinary method after construction. Nothing prevents calling it again. This is occasionally useful (object pooling) but usually a bug.

### 7.3 `self` Is Not Special Inside `__init__` Either

```python
class Weird:
    def __init__(self, value):
        # `self` is just a local variable name — you could rebind it
        # (but NEVER do this — shown only to prove it's a plain parameter):
        other = self
        self.value = value
        print(self is other)  # True
```

### 7.4 Class Body vs `__init__` — When Each Runs

```python
# Class body: runs ONCE at definition time
# __init__: runs EVERY time you create an instance

class Timer:
    print("class body: this runs once")

    def __init__(self):
        print("__init__: this runs per instance")

# Output at import time: "class body: this runs once"

Timer()  # __init__: this runs per instance
Timer()  # __init__: this runs per instance
```

**Common mistake:** putting mutable defaults or per-instance logic in the class body instead of `__init__`:

```python
# WRONG — shared list!
class Team:
    members = []            # class attribute — ONE list shared by all teams!

    def __init__(self, name):
        self.name = name

# RIGHT — per-instance list
class Team:
    def __init__(self, name):
        self.name = name
        self.members = []   # instance attribute — each team gets its own list
```

This pitfall is explored in depth in 10.2.

## 8. Comparison Table — Python vs Java/C++

| Concept | Java / C++ | Python |
|---------|-----------|--------|
| Class definition | Compile-time declaration; type-checked statically | Runtime statement; creates a `type` object |
| Class itself | Not a first-class value (reflection needed) | First-class object; pass it, store it, modify it |
| Instance creation | `new Dog("Buddy")` — keyword required | `Dog("Buddy")` — just call the class |
| `this`/`self` | Implicit `this` keyword | Explicit first parameter `self` (convention) |
| Constructor | Special method that both allocates and inits; name = class name | Two methods: `__new__` (allocates) + `__init__` (initializes); `__init__` is not the constructor |
| Overloading | Multiple constructors with different signatures | One `__init__`; use defaults, `*args`, or `@classmethod` factories |
| Parent init | Implicit `super()` call (Java inserts if omitted) | Never implicit; must call `super().__init__()` manually |
| Fields | Fixed at compile time; per-class layout | Dynamic `__dict__`; add/remove attributes at runtime |
| Method binding | `this` bound by VM at call site | Functions are descriptors; `__get__` produces bound methods |

---

## 9. Summary

- A `class` block **executes** its body once at definition time and creates a live object that is an instance of `type`.
- Creating an instance means **calling the class** — `ClassName(args)` — which invokes `__new__` (allocate) then `__init__` (initialize).
- `__init__` is an **initializer**, not a constructor. It receives an already-allocated `self` and must return `None`.
- `__new__` is the true constructor; you rarely override it unless you need to control allocation or subclass immutable types.
- `self` is an **explicit first parameter**, not a keyword. Methods are functions whose descriptor `__get__` curries `self` into a bound method.
- Each instance has its own `__dict__` holding per-instance attributes. `self.attr = value` writes into that dict.
- Python never implicitly calls a parent `__init__`; use `super().__init__(...)` when needed.
- There is no constructor overloading — use default arguments or `@classmethod` alternative constructors.
