# 11.3 Designing Good Classes — Cohesion, Responsibility, Value Objects, and SOLID in Python

> **Mental model up front:** A class is not a folder for random functions that happen to share a noun. It is a **cohesive unit of state + behavior that maintains an invariant**. Good classes are small, focused, honest about what they encapsulate, and open to extension without surgery. Bad classes are grab-bags of data with getters/setters that do nothing — or god objects that know everybody else's business. Python makes the boundary especially fluid because you can add attributes at runtime and because duck typing lets any object stand in for any interface — so the discipline must come from design, not from the compiler.

---

## 1. What Makes a Class "Good"? — Four Lenses

| Lens | Question | Bad sign | Good sign |
|---|---|---|---|
| **Cohesion** | Do all members belong together? | Methods that ignore most attributes; 50/50 split of unrelated responsibilities | Every method uses most attributes; single theme names the class |
| **Encapsulation** | Does it own and protect its invariant? | Public fields mutated willy-nilly; `a.balance = -9999` valid | No state reachable in an invalid form; mutations go through guarded methods |
| **Coupling** | How many other classes does it know? | Imports 8 modules; constructs its own dependencies | Receives collaborators via `__init__`; depends on Protocols |
| **Size / complexity** | Can you fit it in your head? | >300 lines, 10+ public methods | <100 lines, 2–5 public methods, fitting on one screen |

Python's additional lens: **Is this a class at all?** Python prefers flat functions, dataclasses, or named tuples for many jobs where Java would require a class. A good Python designer asks first: *"Does this need identity + evolving state + an invariant?"* If not, a function or `dataclass(frozen=True)` may be clearer.

## 2. Cohesion — How Tightly the Parts Belong Together

### 2.1 Levels of Cohesion (Bridging to Structured Design)

| Level | Strength | Description | Python smell |
|---|---|---|---|
| **Coincidental** | Weakest | Random utilities bundled by file proximity | `class Utils: @staticmethod def hash(x): ... @staticmethod def send_email(): ...` |
| **Logical** | Weak | Members share a category but not a workflow | `class FileHandler: def read_csv, def write_json, def send_ftp` |
| **Temporal** | Weak | Members happen at the same time | `class Startup: def load_config, def init_db, def warm_cache` |
| **Procedural** | Moderate | Members must be called in a fixed sequence | `class Parser: step1_tokenize, step2_validate, step3_build` (enforced only by docs) |
| **Communicational** | Moderate | Members operate on the same data | Many `self.data` helpers that could be methods of `Data` itself |
| **Sequential** | Strong | Output of one is input to next | `class Pipeline: fetch -> transform -> load` inside one class (better split) |
| **Functional** | Strongest | Single well-defined task; all members contribute | `class BankAccount` — balance + deposit/withdraw/interest, one invariant |

**Goal:** Push every class toward **functional cohesion** — it does *one thing* and every method exists to do that one thing.

```python
# WEAK cohesion — coincidental grouping
class StringUtils:  # utility bucket — not a real abstraction
    @staticmethod
    def slugify(text: str) -> str: ...
    @staticmethod
    def truncate(text: str, n: int) -> str: ...
    @staticmethod
    def to_camel_case(text: str) -> str: ...

# Pythonic fix — just functions in a module, no class needed:
# string_utils.py
def slugify(text: str) -> str: ...
def truncate(text: str, n: int) -> str: ...
def to_camel_case(text: str) -> str: ...
```

```python
# WEAK cohesion — logical grouping with split state
class ReportGenerator:
    def generate_sales_report(self): ...   # uses self.sales_data
    def generate_audit_log(self): ...      # uses self.audit_data — different data
    def send_email(self, report): ...      # unrelated to generation

# Measurement: any method uses <50% of attributes => suspect
# Split:
class SalesReport:
    def __init__(self, data): self.data = data
    def generate(self) -> str: ...

class AuditLog:
    def __init__(self, events): self.events = events
    def generate(self) -> str: ...

class ReportSender:  # or a plain function
    def send(self, report: str, to: str): ...
```

```python
# STRONG cohesion — all members collaborate on one invariant
class BankAccount:
    """Invariant: balance >= 0 and balance == sum(transactions)."""
    def __init__(self, balance: float = 0) -> None:
        if balance < 0:
            raise ValueError
        self._balance = balance
        self._transactions: list[float] = []

    def deposit(self, amount: float) -> None:
        self._validate_positive(amount)
        self._balance += amount
        self._transactions.append(amount)

    def withdraw(self, amount: float) -> None:
        self._validate_positive(amount)
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
        self._transactions.append(-amount)

    def _validate_positive(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("amount must be positive")

    @property
    def balance(self) -> float:
        return self._balance

    @property
    def can_withdraw(self) -> bool:
        return self._balance > 0
# Every method touches _balance; the class name tells you its single job.
```

### 2.2 Measuring Cohesion — LCOM (Lack of Cohesion in Methods)

Informally: count how often methods share attributes.

```python
# HIGH LCOM (bad) — methods touch disjoint attribute sets
class Bad:
    def __init__(self):
        self.a = 0  # only m1 uses a
        self.b = 0  # only m2 uses b
    def m1(self): self.a += 1
    def m2(self): self.b += 1
# m1 and m2 never share state — why are they in the same class?

# LOW LCOM (good) — methods share attributes
class Good:
    def __init__(self):
        self.x = 0
        self.y = 0
    def move(self, dx, dy): self.x += dx; self.y += dy
    def distance_from_origin(self): return (self.x**2 + self.y**2) ** 0.5
# Both methods touch x and y — cohesive.
```

**Python tools:** `vulture`, `pylint` (`too-many-instance-attributes`, `too-few-public-methods`), or manual review. The cheapest heuristic: *"Can I describe the class's job in one sentence without 'and'?"*

## 3. Single Responsibility Principle (SRP) — One Reason to Change

> *A class should have only **one reason to change** — one axis of variation, one stakeholder, one source of requirement pressure.*

SRP is the class-level statement of cohesion. A violation is a class with **two jobs** that change for different reasons and at different rates.

### 3.1 Example — The Fat `Order` Class

```python
# BEFORE — SRP violation: order knows pricing, persistence, email, export, logging
class Order:
    def __init__(self, items): self.items = items

    def calculate_total(self): ...          # job 1: pricing
    def apply_discount(self): ...           # job 1: pricing
    def save_to_db(self): ...               # job 2: persistence
    def send_confirmation_email(self): ...  # job 3: notification
    def to_json(self): ...                  # job 4: serialization
    def to_csv(self): ...                   # job 4: serialization

# Any change to email templates, DB schema, pricing rules, or JSON format touches THIS class.
# Merge conflicts, test bloat, and fear of change follow.
```

```python
# AFTER — each responsibility becomes its own class/function
from dataclasses import dataclass
from typing import Protocol
import json

@dataclass
class Order:
    """Single responsibility: hold ordered line items and expose domain rules."""
    order_id: int
    items: list["LineItem"]

    @property
    def subtotal(self) -> float:
        return sum(i.total for i in self.items)

    def total(self, pricing: "PricingService") -> float:
        return pricing.apply(self.subtotal)  # delegates pricing

# Responsibility 1 — pricing
class PricingService(Protocol):
    def apply(self, subtotal: float) -> float: ...

class LoyaltyPricing:
    def apply(self, subtotal: float) -> float:
        return subtotal * 0.9

# Responsibility 2 — persistence
class OrderRepository(Protocol):
    def save(self, order: Order) -> None: ...

class SqlOrderRepository:
    def save(self, order: Order) -> None:
        print(f"[DB] saving order {order.order_id}")

# Responsibility 3 — notification
class Notifier(Protocol):
    def notify(self, order: Order) -> None: ...

class EmailNotifier:
    def notify(self, order: Order) -> None:
        print(f"[Email] confirm order {order.order_id} to customer")

# Responsibility 4 — serialization (better as plain functions)
def order_to_json(order: Order) -> str:
    return json.dumps({"order_id": order.order_id, "total": order.subtotal})

# Orchestration — not a class, just a function:
def place_order(order: Order, repo: OrderRepository, notifier: Notifier) -> None:
    repo.save(order)
    notifier.notify(order)
```

**Why this is better in Python:**

* Each class is **<30 lines**, testable in isolation with fakes.
* `Order` has no import of `smtplib` or `sqlite3` — collaboration is **injected**.
* Serialization as **functions** (`order_to_json`) is idiomatic — no need for a `Serializer` class when a function will do (Python is not Java).
* Adding `SmsNotifier` or `MongoOrderRepository` touches zero existing classes (OCP, see Section 8.2).

### 3.2 SRP Heuristics — When You Suspect Violation

* Class name contains `and`/`or`/`Manager`/`Handler`/`Util` — vague names signal multiple jobs.
* `import` list mixes domains (e.g., `import smtplib, sqlite3, jinja2` in one class).
* A change to requirement X forces you to edit a class that also handles requirement Y.
* A class has >5–7 public methods that cluster into unrelated groups.
* You need to mock 3 unrelated collaborators to test one method.

### 3.3 SRP at Method Scale

```python
# Violates SRP inside a single method — does 3 things:
def process(order: Order) -> None:
    total = sum(i.total for i in order.items)       # pricing
    db.execute("INSERT INTO orders ...", total)     # persistence
    smtp.send("confirm ...")                        # notification

# Split:
def price(order: Order) -> float:
    return sum(i.total for i in order.items)

def persist(order: Order, total: float, db) -> None:
    db.execute("INSERT ...", total)

def notify(order: Order, mailer) -> None:
    mailer.send("confirm ...")
```

## 4. Encapsulation — Owning the Invariant, Python-Style

Encapsulation is not about hiding data — it is about **preserving invariants**: the promises that make the object valid.

### 4.1 Python's Encapsulation Model — Consent, Not Walls

Python has **no `private` keyword**. The design philosophy is *"we're all consenting adults"* — encapsulation is by **convention + property + naming**, not by access denial.

| Mechanism | Syntax | Enforcement | Meaning |
|---|---|---|---|
| **Public** | `self.attr` | None | Part of the stable API |
| **Internal (`_`)** | `self._attr` | Convention + linter warning | Not part of public API; may change |
| **Name-mangled (`__`)** | `self.__attr` | Renamed to `_ClassName__attr` | Avoid subclass name collisions; rarely needed for "privacy" |
| **`@property`** | `@property` / `@attr.setter` | Descriptor enforces on access | Controlled access + invariant checks |
| **`__slots__`** | `__slots__ = (...)` | Prevents arbitrary new attributes | Memory + strictness |
| **`dataclass(frozen=True)`** | Frozen dataclass | Runtime `FrozenInstanceError` | Immutability |

```python
class Account:
    def __init__(self, balance: float) -> None:
        self._balance = balance   # internal — callers should use .balance / .deposit

    @property
    def balance(self) -> float:
        return self._balance

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

acc = Account(100)
print(acc.balance)   # 100 — reads property
# acc.balance = 50   # AttributeError — no setter
acc._balance = -9999 # Python ALLOWS this — convention says don't!
# Tools catch it: pylint, mypy, and code review. Runtime does not block.
```

**Explanation:** The `_` prefix is a **signal to humans and tooling**, not a lock. `from account import Account; acc._balance = -9999` compiles and runs, but any reviewer, linter (`protected-access`), or `__all__` contract will flag it. This matches Python's open-object model where debugging and testing legitimately need to touch internals.

```python
# Name-mangled __ — NOT "more private", but collision avoidance:
class Base:
    def __init__(self): self.__value = 1  # stored as _Base__value

class Derived(Base):
    def __init__(self):
        super().__init__()
        self.__value = 2  # stored as _Derived__value — does NOT overwrite Base's

b = Base(); print(b._Base__value)  # 1
d = Derived(); print(d._Derived__value, d._Base__value)  # 2 1

# Use __ only to prevent accidental override in subclasses.
# NEVER use __ to "secure" data — it is trivially bypassed via _ClassName__attr.
```

### 4.2 Invariant Enforcement — `__init__` + Property + `__post_init__`

```python
from dataclasses import dataclass, field

class Email:
    """Value object with invariant: must contain '@' and be lowercase."""
    def __init__(self, address: str) -> None:
        norm = address.strip().lower()
        if "@" not in norm or not norm:
            raise ValueError(f"invalid email: {address!r}")
        self._address = norm  # invariant established here

    @property
    def address(self) -> str:
        return self._address

    @address.setter
    def address(self, value: str) -> None:
        # Re-validate on mutation — or make immutable and remove setter
        norm = value.strip().lower()
        if "@" not in norm:
            raise ValueError
        self._address = norm

@dataclass(frozen=True)
class EmailFrozen:
    """Same invariant but immutable — no setter, validation in __post_init__."""
    address: str

    def __post_init__(self) -> None:
        norm = self.address.strip().lower()
        if "@" not in norm or not norm:
            raise ValueError(f"invalid email: {self.address!r}")
        # frozen dataclass requires object.__setattr__ to mutate inside __post_init__
        object.__setattr__(self, "address", norm)
    # Any later mutation: email.address = "x"  # FrozenInstanceError
```

### 4.3 The Boundary: What to Encapsulate vs Expose

* **Encapsulate:** invariants (`balance >= 0`), derived state (`_cache`), internal collaborators (`_repo`), mutation logic.
* **Expose:** domain queries (`is_overdue`, `total`), safe views (`items -> tuple`), actions that preserve invariants (`deposit`, `withdraw`).

```python
class ShoppingCart:
    def __init__(self):
        self._items: list[str] = []                # encapsulated — list identity matters
    @property
    def items(self) -> tuple[str, ...]:             # expose a READ-ONLY view
        return tuple(self._items)
    @property
    def count(self) -> int:
        return len(self._items)
    def add(self, item: str) -> None:               # mutation via method that can validate
        if not item.strip():
            raise ValueError
        self._items.append(item)
    def clear(self) -> None:
        self._items.clear()

cart = ShoppingCart()
cart.add("apple")
# cart.items.append("sneaky")  # AttributeError — tuple
# cart._items.append("sneaky") # would work — convention says don't
```

## 5. Tell, Don't Ask — Behavior with Its Data

### 5.1 The Principle

> **Tell the object what to do; don't ask it for its data and do it yourself.**

Asking leaks the callee's internals into the caller, duplicates logic, and scatters invariants.

```python
# ASKING — caller knows Balance's internals and rule:
class AccountAsking:
    def __init__(self, balance): self.balance = balance

if account.balance >= amount:        # caller checks the invariant
    account.balance -= amount        # caller mutates
else:
    raise ValueError("insufficient funds")
# Every caller duplicates the check; any caller can forget.

# TELLING — object owns the rule:
class AccountTelling:
    def __init__(self, balance): self._balance = balance
    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

account.withdraw(amount)  # one call, one place for the rule
```

```python
# REALISTIC asking — discount logic outside the domain object
def invoice_total_asking(order) -> float:
    # Caller asks for internals, applies rules that belong to Order/Pricing
    total = 0
    for item in order.items:
        total += item.price * item.qty
        if item.qty > 10:  # bulk discount rule — leaks Product knowledge
            total -= item.price * 0.05 * item.qty
    if order.customer.is_vip:  # VIP rule — also leaked
        total *= 0.9
    return total
# Adding a new discount requires editing EVERY caller like this.

# TELLING — behavior lives with data
@dataclass
class LineItem:
    price: float
    qty: int
    def total(self) -> float:
        raw = self.price * self.qty
        return raw * 0.95 if self.qty > 10 else raw  # bulk rule owned here

class Order:
    def __init__(self, items, customer):
        self._items = list(items); self.customer = customer
    def total(self, pricing: PricingService) -> float:
        subtotal = sum(i.total() for i in self._items)  # item owns bulk rule
        return pricing.apply(subtotal, self.customer)    # order owns aggregation, pricing owns VIP rule

order.total(LoyaltyPricing())  # callers just tell the order to price itself
```

### 5.2 When Asking Is OK

* **Value objects / DTOs** with no invariant — data carriers are *meant* to be asked.
* **Boundaries** (ORM models, JSON payloads) where behavior lives in a service.
* **Reporting / serialization** — `order_to_json` must *ask* for every field.

The rule is about **domain invariants**, not about all data access.

## 6. When to Split a Class — Signals and Techniques

### 6.1 Signals It Is Time to Split

* **Name needs `and`** — `OrderManagerAndNotifier` or vague `*Manager` / `*Service`.
* **Two rates of change** — half the methods change when the database changes; the other half when pricing changes.
* **Unrelated imports** — `smtplib` + `sqlite3` + `jinja2` in one class.
* **Methods ignore fields** — `m1` uses only `self.a`, `m2` only `self.b` — disjoint cohesion islands.
* **Test setup explodes** — a single unit test needs to mock DB, email, and tax service.
* **Size** — >200 lines or >7 public methods in one class is a trigger to review (not a rule, but a nudge).

### 6.2 Splitting Technique — Extract Class

```python
# BEFORE — one class does validation + formatting + delivery
class UserRegistration:
    def __init__(self, email, password, db, mailer):
        self.email = email; self.password = password; self.db = db; self.mailer = mailer
    def register(self):
        if "@" not in self.email: raise ValueError
        if len(self.password) < 8: raise ValueError
        self.db.save(self.email, self.password)
        self.mailer.send(self.email, "welcome")

# AFTER — extract three cohesive collaborators
class CredentialsValidator:  # pure logic, no I/O
    def validate(self, email: str, password: str) -> None:
        if "@" not in email: raise ValueError("invalid email")
        if len(password) < 8: raise ValueError("password too short")

class UserRepository:  # I/O — persistence
    def save(self, email: str, password: str) -> None:
        print(f"[DB] saving {email}")

class WelcomeMailer:  # I/O — delivery
    def send(self, email: str) -> None:
        print(f"[Email] welcome {email}")

class UserRegistrationService:  # orchestration — thin
    def __init__(self, validator, repo, mailer):
        self.validator, self.repo, self.mailer = validator, repo, mailer
    def register(self, email: str, password: str) -> None:
        self.validator.validate(email, password)
        self.repo.save(email, password)
        self.mailer.send(email)
```

> **Note:** `UserRegistrationService` is itself a candidate to be a **plain function** `register_user(...)` that takes the collaborators — Python does not require a class for orchestration. Use whatever is more testable/readable.

### 6.3 Extract Value Object

When a cluster of fields travels together and has its own invariant, promote it to a value object:

```python
# BEFORE — primitive obsession: 6 fields scattered
class OrderBefore:
    def __init__(self, street, city, zip_code, country, lat, lon): ...

# AFTER — cohesive value objects
from dataclasses import dataclass

@dataclass(frozen=True)
class Address:
    street: str
    city: str
    zip_code: str
    country: str = "US"
    def __post_init__(self):
        if not self.zip_code:
            raise ValueError

@dataclass(frozen=True)
class GeoPoint:
    lat: float
    lon: float
    def __post_init__(self):
        if not (-90 <= self.lat <= 90 and -180 <= self.lon <= 180):
            raise ValueError

class OrderAfter:
    def __init__(self, shipping: Address, location: GeoPoint): ...
```

## 7. Python's Small Classes Idiom

### 7.1 Why Small Is Better — and Why Python Pushes Harder

Java/C# need classes for things Python can do with **functions, closures, generators, comprehensions, enums, or dataclasses**. So any Python class that *doesn't* need identity/invariant/lifetime is suspicious.

```python
# Java-style over-engineering in Python — a class with one method:
class Slugifier:
    def slugify(self, text: str) -> str:
        return text.lower().replace(" ", "-")

# Pythonic — a function:
def slugify(text: str) -> str:
    return text.lower().replace(" ", "-")

# A callable object only when you need to HOLD STATE:
class SlugifierWithCache:
    def __init__(self):
        self._cache: dict[str, str] = {}
    def __call__(self, text: str) -> str:
        if text not in self._cache:
            self._cache[text] = text.lower().replace(" ", "-")
        return self._cache[text]
# Still tiny (~8 lines), stateful, cohesive — justified.
```

### 7.2 What a "Small Class" Looks Like

* **10–40 lines** including docstring and validation.
* **1–3 instance attributes** (plus maybe one collaborator).
* **2–5 public methods/properties**.
* **One invariant** (maybe one derived property).
* **No I/O in the domain core** — I/O at the edges, injected.

```python
from dataclasses import dataclass, field

@dataclass
class Money:
    """Value object — composite, immutable, always non-negative."""
    cents: int  # store as minor units to avoid float errors

    def __post_init__(self):
        if self.cents < 0:
            raise ValueError("money cannot be negative")

    @property
    def dollars(self) -> float:
        return self.cents / 100

    def __add__(self, other: "Money") -> "Money":
        if not isinstance(other, Money):
            return NotImplemented
        return Money(self.cents + other.cents)

    def __str__(self) -> str:
        return f"${self.dollars:.2f}"

@dataclass
class LineItemSmall:
    """Value object — immutable line."""
    product_sku: str
    quantity: int
    unit_price: Money

    def __post_init__(self):
        if self.quantity <= 0: raise ValueError

    @property
    def total(self) -> Money:
        return Money(self.unit_price.cents * self.quantity)
```

Two focused classes, ~15 lines each, each with one invariant, each composable.

### 7.3 Smell: The God Object vs The Anemic Model — Both Bad

| Anti-pattern | Symptom | Fix |
|---|---|---|
| **God object** | One class knows everything, does everything | Split by responsibility (see 6.2) |
| **Anemic model** | Domain classes are pure data bags; logic in `*Service` classes | Move behavior to domain objects (see 7.5) |
| **Single-method class with no state** | `class X: def do(self, args): ...` | Replace with function |
| **Bag-of-attributes** | `class Data: a; b; c; ...` with no invariants | Use `@dataclass(frozen=True)` or `NamedTuple` as a value object |

## 8. Data vs Behavior — Value Objects, Entities, Rich vs Anemic Models

### 8.1 The Spectrum

```
             pure data ───────────────────── pure behavior
             ┌──────────┬──────────┬──────────┬──────────┐
             │  tuple   │  value   │  entity  │ service  │
             │  dict    │  object  │ (domain) │ (stateless) │
             │          │          │          │          │
             │ no id    │ no id    │ HAS id   │ no state │
             │ mutable  │ frozen   │ mutable  │ called   │
             │          │ equality │ identity │ per use  │
             │          │ by value │ by id    │          │
             └──────────┴──────────┴──────────┴──────────┘
```

### 8.2 Value Objects — Equality by Value, Immutability, No Identity

```python
from dataclasses import dataclass
from typing import Self

@dataclass(frozen=True, order=True)
class Money:
    cents: int

    def __post_init__(self):
        if self.cents < 0:
            raise ValueError

@dataclass(frozen=True)
class Address:
    street: str
    city: str
    zip_code: str

# Value equality — two objects with same data are "the same value":
print(Money(1000) == Money(1000))   # True — value equality
print(Address("123 Main","SF","94105") == Address("123 Main","SF","94105"))  # True

# Hashable — usable as dict keys or set members (because frozen):
prices: dict[Money, str] = {Money(1999): "Widget"}
print(Money(1999) in prices)  # True

# Safe sharing — immutability means aliasing is harmless:
addr = Address("123 Main","SF","94105")
order_addr = addr  # shared, but frozen so cannot be mutated through alias
# addr.city = "LA"  # FrozenInstanceError
```

**Value-object rules in Python:**

* `@dataclass(frozen=True)` or hand-written `__slots__ + __hash__ + __eq__`.
* Validate invariants in `__post_init__` or `__init__`.
* All fields should themselves be immutable (or copied).
* Implement `__hash__` consistently with `__eq__` (frozen dataclass does this).
* Keep behavior focused on the value itself (e.g., `Money.__add__`, `Address.normalized`).

### 8.3 Entities — Equality by Identity, Mutable Lifecycles

```python
from dataclasses import dataclass, field

@dataclass(eq=False)  # identity, not value — two entities with same data are still distinct
class Customer:
    id: int              # identity — the one field that defines sameness
    name: str
    email: str

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Customer): return NotImplemented
        return self.id == other.id

    def __hash__(self) -> int:
        return hash(self.id)

    def rename(self, new_name: str) -> None:
        if not new_name.strip(): raise ValueError
        self.name = new_name.strip()

    def change_email(self, new_email: str) -> None:
        norm = new_email.lower().strip()
        if "@" not in norm: raise ValueError
        self.email = norm

# Two customers with same name/email are NOT equal if ids differ:
print(Customer(1,"Alice","a@x.com") == Customer(2,"Alice","a@x.com"))  # False
print(Customer(1,"Alice","a@x.com") == Customer(1,"Bob","b@y.com"))    # True — same id
```

**Entity rules:** encapsulates lifecycle (active/inactive), enforces identity invariants, exposes domain commands (`customer.rename(...)`) rather than raw field assignment.

### 8.4 Rich vs Anemic Models

```python
# ── ANEMIC — data bag + procedural service (smell in domain-rich apps) ──
@dataclass
class OrderData:
    items: list[LineItem]
    customer_type: str
    subtotal: float = 0

class OrderService:
    @staticmethod
    def calculate_total(order: OrderData) -> float:
        order.subtotal = sum(i.total for i in order.items)
        if order.customer_type == "vip":
            order.subtotal *= 0.9
        return order.subtotal
    @staticmethod
    def add_item(order: OrderData, item: LineItem) -> None:
        if item.quantity <= 0: raise ValueError
        order.items.append(item)
# Every invariant check lives in OrderService — callers can bypass it: order.items.append(bad_item)

# ── RICH — behavior lives with data ──
class OrderRich:
    def __init__(self, items: list[LineItem], pricing: PricingService) -> None:
        self._items = list(items)
        self._pricing = pricing

    @property
    def items(self) -> tuple[LineItem, ...]:
        return tuple(self._items)

    def add_item(self, item: LineItem) -> None:
        if item.quantity <= 0: raise ValueError  # invariant enforced here
        self._items.append(item)

    def total(self) -> float:
        return self._pricing.apply(sum(i.total for i in self._items))

# Anemic is fine at SYSTEM BOUNDARIES (ORM rows, API schemas).
# Rich is preferred in the DOMAIN CORE where invariants matter.
```

**When anemic is appropriate:**

* **DTOs / API schemas** (`pydantic.BaseModel`, `@dataclass` for JSON mapping) — deliberately dumb.
* **ORM models** (`sqlalchemy.orm.DeclarativeBase`) — behavior usually lives elsewhere to avoid mixing persistence with domain logic.
* **Pipeline/transformation scripts** — functions over data win over rich domains.

**When rich is appropriate:**

* **Domain entities** with invariants and business rules (billing, inventory, scheduling).
* **Value objects** with self-contained arithmetic/validation.

## 9. SOLID Principles — Mapped to Python

SOLID is five OO design principles. The Python nuance is that duck typing, Protocols, and first-class functions often deliver the same benefits with less ceremony than the Java/C++ interpretations.

### 9.1 SRP — Single Responsibility Principle

*Already covered in Section 3. Recap for SOLID context:*

> **One class, one reason to change.**

```python
# Violation: User does auth + profile + notification
class User:
    def authenticate(self): ...
    def update_profile(self): ...
    def send_welcome_email(self): ...

# FIX — one class / function per reason:
class Authenticator:
    def authenticate(self, credentials): ...

@dataclass
class UserProfile:
    name: str; bio: str
    def update_bio(self, bio: str): self.bio = bio

def send_welcome(email: str, mailer): mailer.send(email, "welcome")
```

### 9.2 OCP — Open-Closed Principle

> *A module should be **open** to extension (new behavior via new code) but **closed** to modification (existing code need not change).*

Python's primary OCP tools: **polymorphism via Protocol/ABC**, **composition/strategies**, and **registration/decorators**.

#### Violation — `isinstance` branch that grows forever

```python
# BEFORE — every new payment type modifies this function
def process_payment(amount: float, method: str) -> None:
    if method == "credit":
        print(f"charging credit ${amount}")
    elif method == "paypal":
        print(f"paypal ${amount}")
    elif method == "crypto":
        print(f"crypto ${amount}")
    else:
        raise ValueError(f"unknown {method}")
# Adding "apple_pay" edits this function — OCP violation.

# AFTER — strategy objects + registry; new types add NEW code, not edits
from typing import Protocol, Callable

class PaymentMethod(Protocol):
    def pay(self, amount: float) -> None: ...

class CreditCard:
    def pay(self, amount: float) -> None:
        print(f"credit ${amount}")

class PayPal:
    def pay(self, amount: float) -> None:
        print(f"paypal ${amount}")

class Crypto:
    def pay(self, amount: float) -> None:
        print(f"crypto ${amount}")

# Generic — closed to modification:
def process_payment(amount: float, method: PaymentMethod) -> None:
    method.pay(amount)  # polymorphism — no branching

process_payment(100, CreditCard())
process_payment(100, Crypto())  # new type — no change to process_payment
```

**Registry pattern — extensible without touching core dispatch:**

```python
# OCP via registry / decorator
PAYMENT_HANDLERS: dict[str, Callable[[float], None]] = {}

def payment_handler(name: str):
    def decorator(fn: Callable[[float], None]):
        PAYMENT_HANDLERS[name] = fn
        return fn
    return decorator

@payment_handler("credit")
def pay_credit(amount: float): print(f"credit ${amount}")

@payment_handler("paypal")
def pay_paypal(amount: float): print(f"paypal ${amount}")

# Adding a new handler elsewhere — NO edit to the registry file:
@payment_handler("apple_pay")
def pay_apple(amount: float): print(f"apple ${amount}")

def process_payment_named(amount: float, name: str) -> None:
    PAYMENT_HANDLERS[name](amount)
```

### 9.3 LSP — Liskov Substitution Principle

> *If `S` is a subtype of `T`, any code that works with `T` must work with `S` without knowing it is `S`.*

LSP is about **contract fidelity**: preconditions cannot be strengthened, postconditions cannot be weakened, invariants must hold, and the subtype must not produce surprising side-effects.

#### What violating LSP looks like in Python

```python
class Rectangle:
    def __init__(self, width: float, height: float) -> None:
        self.width, self.height = width, height
    def set_width(self, w: float) -> None:  self.width = w
    def set_height(self, h: float) -> None: self.height = h
    def area(self) -> float: return self.width * self.height

class Square(Rectangle):  # Liskov trap
    def set_width(self, w: float) -> None:
        self.width = self.height = w
    def set_height(self, h: float) -> None:
        self.width = self.height = h

def scale(rect: Rectangle) -> None:
    rect.set_width(5); rect.set_height(4)
    assert rect.area() == 20

scale(Rectangle(2, 3))  # passes
scale(Square(2, 2))     # FAILS — area 16 — LSP violated
# Square broke Rectangle's contract: set_width should NOT affect height.
```

```python
# LSP violation via strengthened preconditions:
class FileReader:
    def read(self, path: str) -> str:
        return open(path).read()

class RestrictedFileReader(FileReader):
    def read(self, path: str) -> str:
        if not path.startswith("/allowed/"):
            raise PermissionError  # NEW precondition — callers of FileReader don't expect it
        return super().read(path)
# Any code doing `reader.read(path)` now needs to handle PermissionError even though
# FileReader's contract didn't promise it — substitution broke.
```

#### Enforcing LSP in Python

Python has no compiler-enforced contract check, but you can practice and hint:

```python
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable

# 1. ABC — abstract base with documented contracts:
class Bird(ABC):
    @abstractmethod
    def move(self) -> None:
        """Move the bird. Must not raise for flightless birds — contract is movement, not flight."""
        ...

# 2. Separate too-broad contracts (ISP helps) — don't make flightless birds violate:
@runtime_checkable
class Flyer(Protocol):
    def fly(self) -> None: ...

@runtime_checkable
class Walker(Protocol):
    def walk(self) -> None: ...

class Sparrow:
    def fly(self): print("fly")
    def walk(self): print("hop")

class Ostrich:
    def walk(self): print("run")
    # no fly() — correctly not a Flyer

def migrate(f: Flyer): f.fly()  # only Flyers accepted
migrate(Sparrow())  # OK
# migrate(Ostrich())  # mypy error: Ostrich has no fly — caught statically
# isinstance(Ostrich(), Flyer)  # False at runtime if @runtime_checkable

# 3. Behavioral subtyping — postconditions must hold:
import math

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...
    @property
    @abstractmethod
    def is_valid(self) -> bool: ...

class Circle(Shape):
    def __init__(self, r: float):
        if r <= 0: raise ValueError  # same or weaker precondition OK (value check)
        self.r = r
    def area(self) -> float: return math.pi * self.r ** 2
    @property
    def is_valid(self) -> bool: return self.r > 0
# Circle requires r > 0 — weaker than "any float"? Actually stricter.
# If Shape's contract says "any float accepted", Circle strengthened the precondition — LSP violation.
# Fix: Shape's doc must specify "r must be positive" so Circle doesn't tighten.
```

**LSP checklist for Python inheritance:**

* [ ] Subtype does not strengthen preconditions (demand rarer inputs).
* [ ] Subtype does not weaken postconditions (return less/garbage).
* [ ] Subtype preserves base invariants.
* [ ] Subtype does not introduce new exceptions callers don't expect.
* [ ] `isinstance` checks remain unnecessary — polymorphism is sufficient.
* [ ] Consider composition or Protocol if `is-a` is questionable.

### 9.4 ISP — Interface Segregation Principle

> *Many specific interfaces are better than one general-purpose interface. No client should be forced to depend on methods it does not use.*

In Python, "interface" means **Protocol / ABC** with abstract methods. Fat interfaces force implementations to stub out irrelevant methods with `raise NotImplementedError` — a sign of segregation failure.

#### Fat interface violation

```python
from abc import ABC, abstractmethod

class Machine(ABC):  # FAT — bundles unrelated capabilities
    @abstractmethod
    def print(self, doc: str) -> None: ...
    @abstractmethod
    def scan(self, doc: str) -> None: ...
    @abstractmethod
    def fax(self, doc: str) -> None: ...

class SimplePrinter(Machine):  # only prints — forced to stub the rest
    def print(self, doc): print(f"print {doc}")
    def scan(self, doc): raise NotImplementedError("no scanner")
    def fax(self, doc):  raise NotImplementedError("no fax")

# Any code depending on Machine can call scan() on a SimplePrinter — runtime crash.
# Also forces tests to mock three methods when only one matters.
```

#### Segregated interfaces

```python
from typing import Protocol

class Printer(Protocol):
    def print(self, doc: str) -> None: ...

class Scanner(Protocol):
    def scan(self, doc: str) -> None: ...

class Fax(Protocol):
    def fax(self, doc: str) -> None: ...

class SimplePrinter:
    def print(self, doc: str) -> None: print(f"print {doc}")
    # implements only Printer — no stubs needed

class MultiFunction:
    def print(self, doc): print(f"print {doc}")
    def scan(self, doc):  print(f"scan {doc}")
    def fax(self, doc):   print(f"fax {doc}")

# Clients depend only on what they use:
def print_job(printer: Printer, doc: str) -> None:
    printer.print(doc)  # scanner irrelevant

def scan_job(scanner: Scanner, doc: str) -> None:
    scanner.scan(doc)

print_job(SimplePrinter(), "hello")   # OK
print_job(MultiFunction(), "hello")   # OK
# print_job(Scanner(), ...)           # mypy error — Scanner is not a Printer
```

**Python note on ISP and duck typing:** Python's `Protocol` *is* ISP mechanized — protocols are small, structural, and composable. Unlike Java where each interface requires `implements`, a Python class implicitly satisfies any `Protocol` whose methods it happens to have. Segregate into tiny Protocols and compose them where needed:

```python
class Printable(Protocol): ...
class Scannable(Protocol): ...

class AllInOne(Printable, Scannable, Protocol):  # composition of protocols
    ...
```

### 9.5 DIP — Dependency Inversion Principle

> *High-level modules should not depend on low-level modules. Both should depend on **abstractions**. Abstractions should not depend on details — details should depend on abstractions.*

The classic Python rendering: **inject dependencies against a Protocol/ABC, not a concrete class. Construct the concrete wiring at the outermost layer (composition root).**

#### Before — high-level directly constructs low-level (DIP violation)

```python
# DIP violation — OrderService KNOWS and CREATES concrete details:
import smtplib
import sqlite3

class OrderService:
    def place(self, order) -> None:
        # Direct dependencies on low-level modules
        conn = sqlite3.connect("app.db")
        conn.execute("INSERT INTO orders VALUES (?)", (order.id,))
        conn.commit()

        smtp = smtplib.SMTP("smtp.example.com")
        smtp.sendmail("noreply@app.com", order.email, "order confirmed")
# Untestable without a real DB and SMTP; cannot swap to Postgres or SES
# without editing OrderService.
```

#### After — depend on abstractions, inject concretions

```python
from typing import Protocol
from dataclasses import dataclass

# ── Abstractions (owned by the high-level module) ──
class OrderRepository(Protocol):
    def save(self, order: "Order") -> None: ...

class Notifier(Protocol):
    def send_confirmation(self, order: "Order") -> None: ...

@dataclass
class Order:
    order_id: int
    email: str

# ── High-level module — depends only on Protocols ──
class OrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier) -> None:
        self.repo = repo
        self.notifier = notifier

    def place(self, order: Order) -> None:
        self.repo.save(order)           # abstraction call
        self.notifier.send_confirmation(order)

# ── Low-level details — implement the abstractions ──
import sqlite3

class SqliteOrderRepository:
    def __init__(self, path: str) -> None:
        self.path = path
    def save(self, order: Order) -> None:
        with sqlite3.connect(self.path) as conn:
            conn.execute("INSERT INTO orders VALUES (?)", (order.order_id,))
            conn.commit()

class SmtpNotifier:
    def send_confirmation(self, order: Order) -> None:
        print(f"[SMTP] confirming order {order.order_id} to {order.email}")

class FakeRepository:  # for tests
    def __init__(self): self.saved: list[Order] = []
    def save(self, order: Order) -> None: self.saved.append(order)

class FakeNotifier:
    def __init__(self): self.sent: list[Order] = []
    def send_confirmation(self, order: Order) -> None: self.sent.append(order)

# ── Composition root — wire conc retions at the edge (main, factory, DI container) ──
def make_production_service() -> OrderService:
    return OrderService(SqliteOrderRepository("app.db"), SmtpNotifier())

def make_test_service() -> tuple[OrderService, FakeRepository, FakeNotifier]:
    repo, notifier = FakeRepository(), FakeNotifier()
    return OrderService(repo, notifier), repo, notifier

# Usage:
service = make_production_service()
service.place(Order(1, "alice@example.com"))

# Test — no DB/SMTP, full inspection:
service, repo, notifier = make_test_service()
service.place(Order(42, "bob@example.com"))
assert repo.saved[0].order_id == 42
assert notifier.sent[0].email == "bob@example.com"
```

**Why this is DIP in Python terms:**

Visualizes dependency direction:

```
Before (bad):
  OrderService ──▶ sqlite3 (detail)
  OrderService ──▶ smtplib (detail)
  # arrows point DOWN — high-level depends on low-level

After (good):
  OrderService ──▶ OrderRepository (abstraction, defined by/by high-level)
  SqliteOrderRepo ──▶ OrderRepository  (implements)
  SmtpNotifier   ──▶ Notifier          (implements)
  # arrows point UP — details depend on abstraction; high-level free
```

**DIP patterns in Python ecosystem:**

| Pattern | Example | DIP role |
|---|---|---|
| Constructor injection | `Service(repo, mailer)` | Pass any `Protocol` implementer |
| Factory function | `make_service()` | Composition root builds the graph |
| `functools` / closur es | `make_handler(deps)` returning a closure | Inject deps into a function, not a class |
| `contextlib` + enter | Provide deps via context managers | Lifecycle-aware injection |
| Optional deps | `Service(repo, cache=None)` | Depend on abstraction, default to null object |
| `typing.Protocol` | Structural typing — no inheritance required | Implementer need not import abstraction |

## 10. YAGNI & KISS — The Counterweights to Over-Design

SOLID and clean design can drift into speculation. YAGNI and KISS pull back.

### 10.1 YAGNI — You Aren't Gonna Need It

> *Do not build for hypothetical futures. Build what the current requirements demand, leaving seams where change is plausible.*

**Violations in OOP:**

* Premature abstraction — an `AbstractFactory` when only one `Factory` exists.
* Speculative layer of `Strategy` objects when there is currently one algorithm.
* `Mixin` hierarchies for reuse that hasn't happened yet.

```python
# YAGNI violation — building for 5 payment types when 1 is needed:
from abc import ABC, abstractmethod

class PaymentProcessor(ABC): ...          # maybe not needed yet
class StrategyA(PaymentProcessor): ...
class StrategyB(PaymentProcessor): ...
class StrategyFactory: ...                # factory to choose strategies
class PaymentContext: ...                 # context wrapper
# 4 classes when `def charge(amount): ...` would suffice.

# Faithful YAGNI — start simple:
def charge_credit_card(amount: float, card_token: str) -> None:
    print(f"charge ${amount} to {card_token}")

# Evolve WHEN needed — when a second payment type appears:
# THEN extract a Protocol and strategies. The simple function's call sites
# are the seam — replacing one function with two strategy classes is a small diff.
```

**Rule:** Introduce a design pattern **at the point you feel pain** — duplication, branching on type, or a second concrete case — not in anticipation.

### 10.2 KISS — Keep It Simple, Stupid

> *Simplicity is the shortest path between intention and implementation.*

KISS is measured by **reader cost** — how long it takes a competent Python developer to understand the code's intent:

```python
# Clever but NOT KISS — metaclass-driven registry with auto-discovery:
import inspect

class AutoRegistry(type):
    handlers = {}
    def __new__(mcs, name, bases, ns):
        cls = super().__new__(mcs, name, bases, ns)
        if name != "Handler":
            AutoRegistry.handlers[name.lower()] = cls
        return cls

class Handler(metaclass=AutoRegistry):
    def handle(self): raise NotImplementedError
class EmailHandler(Handler):
    def handle(self): print("email")

# KISS — explicit registry dict, three lines:
HANDLERS = {}

def register(name): return lambda cls: HANDLERS.__setitem__(name, cls) or cls

@register("email")
class EmailHandler2:
    def handle(self): print("email")

# Second version: no metaclass magic, visible data structure, trivial to debug.
```

**KISS heuristics for Python classes:**

* Prefer **functions over single-method classes**.
* Prefer **dataclass over hand-written `__init__`/`__repr__`/`__eq__`**.
* Prefer **explicit `dict`/`if` over dispatch tables you don't yet need**.
* Prefer **`@property` over `get_*`/`set_*` pairs**.
* Use **metaclasses only when you are building a framework**, not an application.

### 10.3 Balanced Guidance — When to Layer Complexity

```
Complexity
  │   over-engineering zone (YAGNI warns here)
  │   ┌───────────────┐
  │   │  abstractions  │  2+ concrete cases, clear variation axis
  │   │  protocols     │  composition roots, registry patterns
  │───┤───────────────┤
  │   │ simple classes │  one invariant, few methods
  │   │ dataclasses    │
  │   │ functions      │
  └───┴───────────────┴──▶ time / requirements
       day one         growing system
```

*Start in the lower band. Move to the upper when you have evidence (a second case, a painful conditional, or a test that is hard to write).*

## 11. Putting It All Together — A Worked Design Evolution

### 11.1 Domain: Event Ticketing (from Anemic Mess to SOLID)

**Requirement:** Sell event tickets, apply pricing rules, persist orders, notify customers.

#### Stage 1 — Anemic + Coupled (Before)

```python
# BEFORE — one big class, many reasons to change, asking everywhere
class TicketOrderSystem:
    def __init__(self, customer, items, email, db_uri):
        self.customer, self.items, self.email, self.db_uri = customer, items, email, db_uri
        self.total = 0

    def process(self):
        self.total = sum(i.price * i.qty for i in self.items)
        if self.customer.is_vip: self.total *= 0.9         # pricing rule leaked
        if len(self.items) > 5: self.total *= 0.95         # another rule leaked
        import sqlite3; conn = sqlite3.connect(self.db_uri)  # persistence baked in
        conn.execute("INSERT INTO orders ...", (self.total,)); conn.commit()
        import smtplib; smtp = smtplib.SMTP("smtp.example.com")  # notification baked in
        smtp.sendmail("noreply@x.com", self.email, f"total {self.total}")
```

Smells: SRP (4 jobs), DIP (depends on sqlite3/smtplib concretely), OCP (pricing edits touch process), KISS fails.

#### Stage 2 — Decomposed + SOLID (After)

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import Protocol
from datetime import datetime

# ---- Value objects (frozen, cohesive, rich) ----
@dataclass(frozen=True)
class TicketLine:
    event_id: str
    qty: int
    unit_price_cents: int

    def __post_init__(self):
        if self.qty <= 0: raise ValueError("qty must be positive")
        if self.unit_price_cents < 0: raise ValueError

    @property
    def total_cents(self) -> int:
        return self.qty * self.unit_price_cents

@dataclass(frozen=True)
class Customer:
    id: int
    name: str
    is_vip: bool

# ---- Entity (cohesive, encapsulates invariant, tells don't asks) ----
class Order:
    """Entity — identity by order_id, rich behavior, owns its lines (composition)."""
    def __init__(self, order_id: int, customer: Customer, lines: list[TicketLine] | None = None):
        if order_id <= 0: raise ValueError
        self.order_id = order_id
        self.customer = customer          # aggregation — Customer lives independently
        self._lines: list[TicketLine] = list(lines or [])
        self.placed_at: datetime | None = None

    def add_line(self, line: TicketLine) -> None:
        self._lines.append(line)  # no qty check — TicketLine already validated

    @property
    def lines(self) -> tuple[TicketLine, ...]:
        return tuple(self._lines)

    @property
    def subtotal_cents(self) -> int:
        return sum(l.total_cents for l in self._lines)

    def total_cents(self, pricing: "Pricing") -> int:
        return pricing.apply(self.subtotal_cents, self.customer, len(self._lines))

    def place(self, pricing: "Pricing") -> int:
        """Domain action — mark as placed. Keeps orchestration out; returns final total."""
        total = self.total_cents(pricing)
        self.placed_at = datetime.now()
        return total

# ---- Policies as strategy objects (OCP — open to new pricing rules) ----
class Pricing(Protocol):
    def apply(self, subtotal: int, customer: Customer, item_count: int) -> int: ...

class BasePricing:
    def apply(self, subtotal, customer, item_count): return subtotal

class VipPricing:
    def __init__(self, wrapped: Pricing, rate: float = 0.10):
        self.wrapped, self.rate = wrapped, rate
    def apply(self, subtotal, customer, item_count):
        total = self.wrapped.apply(subtotal, customer, item_count)
        return round(total * (1 - self.rate)) if customer.is_vip else total

class BulkPricing:
    def __init__(self, wrapped: Pricing, threshold: int = 5, rate: float = 0.05):
        self.wrapped, self.threshold, self.rate = wrapped, threshold, rate
    def apply(self, subtotal, customer, item_count):
        total = self.wrapped.apply(subtotal, customer, item_count)
        return round(total * (1 - self.rate)) if item_count > self.threshold else total

# Compose pricing at the composition root:
pricing_chain: Pricing = BulkPricing(VipPricing(BasePricing()))

# ---- Abstractions for DIP (high-level depends on these, not on sqlite/smtplib) ----
class OrderRepository(Protocol):
    def save(self, order: Order) -> None: ...

class Notifier(Protocol):
    def confirm(self, order: Order, total_cents: int) -> None: ...

# ---- Details implement abstractions ----
import sqlite3

class SqliteOrderRepository:
    def __init__(self, uri: str): self.uri = uri
    def save(self, order: Order) -> None:
        with sqlite3.connect(self.uri) as conn:
            conn.execute("INSERT INTO orders(order_id) VALUES (?)", (order.order_id,))
            conn.commit()

class EmailNotifier:
    def __init__(self, from_addr: str): self.from_addr = from_addr
    def confirm(self, order: Order, total_cents: int) -> None:
        print(f"[Email] from {self.from_addr} to order {order.order_id}: ${total_cents/100:.2f}")

# Fakes for tests:
class FakeRepository:
    def __init__(self): self.saved: list[Order] = []
    def save(self, order): self.saved.append(order)

class FakeNotifier:
    def __init__(self): self.sent: list[tuple[int, int]] = []
    def confirm(self, order, total): self.sent.append((order.order_id, total))

# ---- Application service — thin orchestration (tell, don't ask applied) ----
class PlaceOrderService:
    def __init__(self, repo: OrderRepository, notifier: Notifier, pricing: Pricing) -> None:
        self.repo, self.notifier, self.pricing = repo, notifier, pricing

    def execute(self, order: Order) -> int:
        # Telling: order places itself; pricing is a collaborator, not branching in this method
        total = order.place(self.pricing)
        self.repo.save(order)
        self.notifier.confirm(order, total)
        return total

# ---- Composition root ----
def make_prod_service() -> PlaceOrderService:
    return PlaceOrderService(SqliteOrderRepository("app.db"), EmailNotifier("noreply@x.com"), pricing_chain)

def make_test_service():
    repo, notifier = FakeRepository(), FakeNotifier()
    return PlaceOrderService(repo, notifier, pricing_chain), repo, notifier

# ---- Usage ----
order = Order(101, Customer(1, "Alice", is_vip=True))
order.add_line(TicketLine("evt-1", 3, 2000))  # $20 each
order.add_line(TicketLine("evt-2", 4, 1500))  # $15 each — 7 items triggers bulk

svc = PlaceOrderService(FakeRepository(), FakeNotifier(), pricing_chain)
svc.execute(order)  # pricing chain applies VIP + bulk; repo+notifier are fakes
```

**What changed and why:**

* **SRP** — `TicketLine`, `Customer` (value/entity), `Order` (domain), `*Pricing` (policy), `*Repository`/`*Notifier` (I/O), `PlaceOrderService` (orchestration) each have one reason to change.
* **Cohesion** — each class uses its own data; no field is ignored by all methods.
* **Encapsulation** — `Order._lines` private, validated `TicketLine`, `total_cents` via collaboration not raw math in the caller.
* **Tell, don't ask** — `order.place(pricing)` rather than `if order.customer.is_vip: ...` in the service.
* **Small classes** — each is <40 lines.
* **Rich vs anemic** — domain rich (`Order`, `TicketLine`), I/O thin, serialization (not shown) would be simple functions.
* **OCP** — new pricing (`EarlyBirdPricing`) adds a new class, no edit to `Order` or service.
* **LSP** — `VipPricing`/`BulkPricing` wrap any `Pricing`; callers work with `Pricing` without knowing the decorator.
* **ISP** — `OrderRepository` has one method, `Notifier` has one; no class forced to implement unused ops.
* **DIP** — `PlaceOrderService` depends on Protocols; `SqliteOrderRepository` and `FakeRepository` both satisfy them. Tests use fakes, prod uses real — zero change to service.
* **YAGNI/KISS** — no factory for `Pricing` until a third rule appears; no metaclass auto-discovery; `TicketLine` started as `frozen=True` dataclass, not a full-blown class.

## 12. Common Mistakes and Edge Cases

### 12.1 Over-Encapsulation — Property for Every Field Without Invariant

```python
# Noise — no validation, just ceremony:
class Point:
    def __init__(self, x, y): self._x, self._y = x, y
    @property
    def x(self): return self._x
    @x.setter
    def x(self, v): self._x = v  # no check — @property adds nothing
    @property
    def y(self): return self._y
    @y.setter
    def y(self, v): self._y = v

# Better — public attributes; add @property WHEN you need enforcement:
@dataclass
class PointSimple:
    x: float
    y: float
# Add validation later without breaking callers: replace with @property seamlessly.
```

**Python advantage:** You can convert `self.x` to `@property` later without changing call sites — `obj.x` looks the same. So start public; encapsulate when an invariant appears.

### 12.2 SRP Taken Too Far — Nanoclasses

```python
# Too fine — every tiny validation as its own class is noise:
class EmailLengthValidator: ...
class EmailAtSignValidator: ...
class EmailDomainValidator: ...

# Better — one cohesive validator with small methods:
class EmailValidator:
    def validate(self, email: str) -> None:
        self._check_length(email)
        self._check_at_sign(email)
        self._check_domain(email)
    def _check_length(self, email): ...
```

**Heuristic:** A class should justify its own file/module existence and its test file. If it is tested only through its parent, maybe it is a private helper method, not a class.

### 12.3 Protocol Drift — Structural Duck Typing Without a Contract Test

```python
class SmtpNotifier:
    def confirm(self, order, total): ...  # satisfies Notifier today

# Refactor adds an extra param — silently breaks structural conformance:
class SmtpNotifier2:
    def confirm(self, order, total, urgent: bool = False): ...  # extra param — still satisfies?

# mypy with compatible signature analysis may catch some drift, but not behavioral.
# Fix — add a contract test:
def test_notifier_conforms():
    def _uses_notifier(n: Notifier): n.confirm(order, 100)  # type-check target
    _uses_notifier(SmtpNotifier2())  # mypy in CI will warn if signature drifts
```

### 12.4 LSP Subtype in Type Hints — `list` vs `Sequence`

```python
# Violates LSP expectation — function says it accepts Sequence but mutates:
def append_item(items: list[int], x: int): items.append(x)
# If a caller passes a tuple (which is a Sequence), it fails — the function
# promised to work with the supertype but requires the subtype's mutability.
# FIX — hint the actual requirement:
def append_item_correct(items: list[int], x: int): ...  # honestly requires list
def read_only(items: Sequence[int]): ...                 # honestly read-only
```

### 12.5 Mixing SRP and DIP — Where to Put the Wire

```python
# Mistake — domain knows how to construct its own repo (SRP + DIP violation):
class Order:
    def save(self):
        import sqlite3; conn = sqlite3.connect("app.db"); ...

# Correct — domain is persistence-ignorant:
class Order: ...
repo = SqliteOrderRepository("app.db")
repo.save(order)  # caller (orchestration) assembles — domain stays clean
```

## 13. Quick Reference Tables

### 13.1 Cohesion vs Coupling Matrix

|               | High cohesion | Low cohesion |
|---|---|---|
| **Low coupling** | Ideal — small, focused, injected | Stable but mismatched (utility bucket) — split |
| **High coupling** | Fragile even if focused — decouple via Protocols | Worst — god object |

### 13.2 Value Object vs Entity Cheat Sheet

| Question | Value object | Entity |
|---|---|---|
| Does it have an `id`? | No | Yes |
| Equal by `==`? | All fields | Only `id` |
| Mutable after creation? | No (`frozen=True`) | Often yes, via methods |
| Hashable? | Yes (for sets/dicts) | Often yes (by `id`) |
| Example | `Money`, `Address`, `TicketLine` | `Customer`, `Order` |
| Python form | `@dataclass(frozen=True)` | Class with `id` + methods / `@dataclass(eq=False)` |

### 13.3 SOLID One-Liners with Python Tag

| Principle | Tagline | Python signal / fix |
|---|---|---|
| **S — SRP** | One reason to change | Class has `and` in name / many import domains → split |
| **O — OCP** | Open for extension, closed for edit | `if method == "x"` → `Protocol` + strategy |
| **L — LSP** | Subtypes must be substitutable | Subclass raises new exceptions / changes semantics → use composition/Protocol |
| **I — ISP** | Small interfaces, not fat ones | `raise NotImplementedError` in subclass → split Protocol |
| **D — DIP** | Depend on abstractions | `sqlite3.connect` inside domain → inject `Protocol` |

## 14. Summary

* **Cohesion** asks *"do all pieces belong?"* — functional cohesion (one job, every method contributes) beats coincidental/logical dumping.
* **SRP** restates cohesion as change: one class → one stakeholder → one rate of change. Split by extracting collaborators, but don't split past the point where each class justifies itself.
* **Encapsulation** in Python is **convention (`_`, `@property`) plus invariants**, not compiler locks. Use `_` for internal, `__` only for name-collision avoidance, `@property` for invariant enforcement, and `frozen=True` for immutability. You can start with public attributes and evolve to properties without breaking callers.
* **Tell, don't ask** — put behavior with the data it protects. Asking leaks invariants into callers; telling keeps rules in one place.
* **Split** when you see naming confusion, divergent change rates, disjoint field usage, import-domain mixing, or ballooning test setup — via Extract Class and Extract Value Object.
* **Small classes** — Python favors tiny, <40-line cohesive units; single-method stateless classes should usually be functions, and data-bags without invariants should be `frozen` dataclasses.
* **Value objects** (`frozen=True`, equality by value, hashable) vs **entities** (identity by `id`, equality by id, mutable via domain methods) form the core taxonomy; rich models place business rules inside entities, anemic models leave logic in services — the latter is fine at boundaries (DTOs/ORM rows) but wasteful in the domain.
* **SOLID in Python:** SRP→split by reason to change; OCP→`Protocol` + strategies/registry; LSP→subtypes honor base contracts (verify with ABCs/Protocols/tests); ISP→many small Protocols over fat interfaces; DIP→depend on Protocols injected at a composition root — the Python variant of DI without a container framework.
* **YAGNI** (don't build for hypothetical futures) and **KISS** (minimize reader cost) temper SOLID — introduce each abstraction at the point you have a second concrete case or real pain.

> **One-line takeaway:** *Make classes so small, so cohesive, and so honest about their dependencies that their job is obvious from their name, their invariant is impossible to break, and their test needs only one or two fakes.*
