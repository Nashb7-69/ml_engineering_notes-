# 11.2 Aggregation, Association & Composition — Ownership, Lifetimes, and References in Python

> **Mental model up front:** In Python, a variable is not a box that *contains* an object — it is a *name tag* tied to an object with a string. Assignment (`self.part = obj`) does not copy or embed — it ties another string. The three "has-a" flavors — **association**, **aggregation**, and **composition** — differ not in syntax (they all look like `self.x = x`) but in **ownership and lifetime semantics**: who creates the part, who is responsible for keeping it alive, whether it is shared, and what happens when the whole disappears.

---

## 1. The Spectrum of "has-a" — One Syntax, Three Meanings

UML distinguishes relationships by **lifetime and exclusivity**, even though Python implements all three with the same assignment:

| Relationship | UML notation | Lifetime / ownership | Shared? | Python visual |
|---|---|---|---|---|
| **Association** | `A ─── B` (solid line) | `A` *uses* `B` temporarily; neither owns the other | Yes — B exists independently | `def method(self, b: B): b.do()` or stored briefly |
| **Aggregation** | `A ◇── B` (hollow diamond) | `A` *has* `B` but `B` lives independently; `A` may share `B` | Yes — multiple A's can reference same B | `self.b = b  # b passed in` |
| **Composition** | `A ◆── B` (filled diamond) | `A` *owns* `B` exclusively; `B` dies with `A` | No — B is private to one A | `self.b = B(...)  # A creates B` |

```
Association:  Order ─── CustomerService   (Order asks CustomerService to do work)
Aggregation:  Order ◇── Customer           (Order references a Customer who exists anyway)
Composition:  Order ◆── LineItem           (LineItems exist only as part of an Order)
```

> **Key insight:** Python cannot enforce these distinctions at the language level. There is no `owned` keyword. The distinctions are **design intent** expressed through *who creates the object*, *who holds references*, and *documentation*. Understanding them prevents lifetime bugs — like deleting an Order and accidentally keeping LineItems alive, or sharing a mutable Product catalog entry and mutating it through one Order into every other.

### 1.1 The Reference Underneath

```python
customer = Customer("Alice")  # customer is a name tag -> Customer object #42
order = Order(customer)       # order.customer is another tag -> SAME object #42

print(order.customer is customer)  # True — same object, two tags
print(id(customer) == id(order.customer))  # True — identical identity

# Assignment never copies:
import copy
order2 = Order(customer)
order2.customer is order.customer  # True — still the same single Customer

# To get a distinct copy, you must be explicit:
order_copy_customer = copy.copy(customer)  # shallow
order_copy_customer is customer             # False
```

**Explanation:** Python's `self.customer = customer` adds a new reference (refcount +1) to the existing `Customer` object. No bytes are copied. The garbage collector will collect the `Customer` only when **all** references drop to zero (plus cycle handling). This single fact underlies every ownership question in Python.

## 2. Association — "Uses-a" (Ephemeral, No Storage)

Association is the weakest, most transient link: object `A` *uses* object `B` for the duration of a method call, without storing it.

### 2.1 Simple Association — Parameter Only

```python
class TaxCalculator:
    def calculate(self, amount: float) -> float:
        return amount * 0.2

class Order:
    def __init__(self, subtotal: float) -> None:
        self.subtotal = subtotal

    # Association: Order USES TaxCalculator transiently
    def total_with_tax(self, calculator: TaxCalculator) -> float:
        return self.subtotal + calculator.calculate(self.subtotal)

calc = TaxCalculator()
order = Order(100.0)
print(order.total_with_tax(calc))  # 120.0
# calc lives independently; Order never stores it
print(hasattr(order, "calculator"))  # False — no lasting link
```

**Explanation:** The `calculator` parameter is associated *only* for this call. No reference is retained after `total_with_tax` returns. UML would draw a plain line labeled `«use»`. This is the least coupled relationship — ideal when you want maximum flexibility and testability.

### 2.2 Association vs Dependency

In UML strict terms, a **dependency** (`A - - -> B` dashed) is even weaker — `A` mentions `B` but does not hold it at all. In Python both look like parameter or local-variable use; the difference is documentation frequency:

```python
import json

class OrderExporter:
    def export(self, order: "Order") -> str:
        # Dependency on `json` module — uses it but never stores
        return json.dumps({"total": order.subtotal})
```

**Pythonic take:** Do not over-classify dependency vs association in Python. The practical question is: *"Does `self` store a reference after the method returns?"* If no → association/dependency. If yes → aggregation or composition.

## 3. Aggregation — "Has-a" Shared, Independent Lifetime

Aggregation means *"I reference you, but you live independently and could be shared."*

### 3.1 The Defining Pattern — Inject, Don't Create

```python
from dataclasses import dataclass

@dataclass
class Customer:
    id: int
    name: str
    email: str

@dataclass
class Product:
    sku: str
    name: str
    price: float
    # Imagine: products live in a catalog, shared across many orders

class Order:
    """Aggregation: Order HAS a Customer and HAS Products, but none are owned."""
    def __init__(self, order_id: int, customer: Customer, products: list[Product]) -> None:
        self.order_id = order_id
        self.customer = customer          # aggregation — Customer passed in
        self.products = list(products)    # aggregation — Products are shared catalogue objects

# Products and customers exist BEFORE the order:
alice = Customer(1, "Alice", "alice@example.com")
widget = Product("W01", "Widget", 19.99)
gadget = Product("G02", "Gadget", 29.99)

# Multiple orders share the SAME customer and product objects:
order1 = Order(101, alice, [widget, gadget])
order2 = Order(102, alice, [widget])

print(order1.customer is order2.customer)  # True — same Alice
print(order1.products[0] is order2.products[0])  # True — same Widget

# Deleting an order does NOT delete the customer or product:
del order1
print(alice.name)    # Alice — still alive via `alice` and `order2`
print(widget.name)   # Widget — still alive via `widget`, `order2`
```

**Explanation:**

* **Creation outside, injection inside:** `Customer` and `Product` are created *before* `Order` and passed in. The `Order` constructor does `self.customer = customer` — a reference copy, not a new object.
* **Shared:** `alice` is referenced by two orders and a local variable. Changing `alice.email` via any reference is visible everywhere — aliasing.
* **Independent lifetime:** `del order1` drops one reference to `alice` but `alice` persists because other references remain. The whole (`Order`) can die without killing the part.

### 3.2 When Aggregation Bites — Mutable Shared State

```python
widget = Product("W01", "Widget", 19.99)
order1 = Order(101, alice, [widget])
order2 = Order(102, alice, [widget])

# Someone puts Widget on sale:
widget.price = 9.99  # mutation through the SHARED object

print(order1.products[0].price)  # 9.99 — both orders see the sale
print(order2.products[0].price)  # 9.99 — even completed orders change!

# If orders must freeze prices at time-of-purchase, you need copies:
from copy import copy, deepcopy

class OrderSnapshot:
    def __init__(self, order_id: int, customer: Customer, products: list[Product]) -> None:
        self.order_id = order_id
        self.customer = customer
        # Snapshot: copy each product so price is frozen:
        self.products = [copy(p) for p in products]
        # Or deep-copy if Product contains nested mutable state

# Alternatively, make Product immutable:
from dataclasses import dataclass

@dataclass(frozen=True)  # aggregation with immutability — safe sharing
class ProductImmutable:
    sku: str
    name: str
    price: float

# Now `product.price = 9.99` would raise FrozenInstanceError.
# Price changes create a NEW Product; old orders keep the old instance.
```

> **Rule:** Aggregated objects that are **mutable and shared** are a bug farm. Prefer **immutable** (`frozen=True`, `tuple`, `str`) or **copy-on-capture** for aggregated references.

### 3.3 Aggregation with Collections — Ownership Ambiguity

```python
class ShoppingCart:
    def __init__(self, products: list[Product]) -> None:
        # DANGER — aliasing the caller's list:
        self.products = products  # aggregation? But caller can mutate our list!

cart_products = [widget, gadget]
cart = ShoppingCart(cart_products)
cart_products.append(Product("N03", "NewItem", 5.0))  # caller's mutation leaks in
print(len(cart.products))  # 3 — surprise!

# FIX — defensive copy:
class ShoppingCartSafe:
    def __init__(self, products: list[Product]) -> None:
        self.products = list(products)  # shallow copy — new list, same product objects
        # Or: self.products = products.copy()

# Now caller mutations to the LIST don't leak:
# But mutations to a PRODUCT inside the list still leak (shared product objects):
# That's aggregation semantics — products themselves ARE shared.
```

**Decision matrix for collection parameters:**

| Want | Code |
|---|---|
| Shared list (rare, intentional) | `self.items = items` |
| Private list, shared items (aggregation) | `self.items = list(items)` |
| Private list, frozen items (aggregated snapshot) | `self.items = [copy(x) for x in items]` |
| Fully private (composition) | `self.items = [Item(**vars(x)) for x in items]` or create new items inside |

## 4. Composition — "Owns-a" Exclusive, Lifetime-Coupled

Composition is the strongest "has-a": the part is **created by**, **exclusive to**, and **dies with** the whole.

### 4.1 The Defining Pattern — Create Inside

```python
from dataclasses import dataclass, field

@dataclass
class LineItem:
    """A line on an order — meaningless outside its order."""
    product_sku: str
    quantity: int
    unit_price: float

    @property
    def total(self) -> float:
        return self.quantity * self.unit_price

@dataclass
class Order:
    """Composition: Order OWNS its LineItems and its Address snapshot."""
    order_id: int
    customer_id: int
    _items: list[LineItem] = field(default_factory=list, repr=False)

    def add_item(self, sku: str, quantity: int, unit_price: float) -> None:
        # Composition — LineItem is CREATED here, owned exclusively
        self._items.append(LineItem(sku, quantity, unit_price))

    @property
    def items(self) -> tuple[LineItem, ...]:
        return tuple(self._items)  # read-only view

    @property
    def total(self) -> float:
        return sum(item.total for item in self._items)

order = Order(order_id=101, customer_id=1)
order.add_item("W01", 2, 19.99)
order.add_item("G02", 1, 29.99)
print(order.total)   # 69.97
print(order.items)   # (LineItem(...), LineItem(...))

# LineItems were created INSIDE the order:
first = order.items[0]
print(first.product_sku)  # W01

# Deleting the order lets line items be collected (no external references):
order_id = order.order_id
del order
# No variable holds those LineItems — they become garbage
```

**Explanation:**

* **Created inside:** `LineItem(...)` is instantiated within `Order.add_item`. No external code created it.
* **Exclusive:** No other `Order` holds the same `LineItem` instance. Each is private.
* **Lifetime-coupled:** When `order` is deleted and no other reference to its `_items` list exists, the `LineItem` objects lose their last reference and become eligible for garbage collection. If `Order` held an open file or network connection per line item, `Order` would be responsible for closing it.

### 4.2 Composition vs Encapsulation

```python
# Composition reinforces encapsulation — internals are not shared:
order = Order(101, 1)
order.add_item("W01", 2, 19.99)

# Attempt to mutate internals:
# order._items.append(LineItem(...))  # possible but violates convention (_ prefix)
# Better: expose a tuple copy so callers can't mutate:

items = order.items
# items.append(...)  # AttributeError — tuple has no append

# For truly defensive designs, return copies:
@property
def items_copy(self) -> list[LineItem]:
    from copy import copy
    return [copy(item) for item in self._items]
```

### 4.3 Distinguishing Composition and Aggregation — The Three Tests

Ask these about `self.part`:

| Test | Aggregation | Composition |
|---|---|---|
| **1. Who creates it?** | Outside caller, passed in | Inside the whole (`self.part = Part(...)`) |
| **2. Is it shared?** | Yes — multiple wholes may hold the same instance | No — each part belongs to exactly one whole |
| **3. What happens when the whole is deleted?** | Part lives on (other owners exist) | Part dies (or becomes garbage) |

If all three point to "inside / exclusive / dies" → composition.
If any points to "outside / shared / lives" → aggregation.

```python
# Quick classifier function — a thinking tool, not runtime enforcement:
def classify_relationship(part_is_created_inside: bool,
                          part_is_shared: bool,
                          part_lives_after_whole: bool) -> str:
    if part_is_created_inside and not part_is_shared and not part_lives_after_whole:
        return "Composition (●)"
    if not part_is_created_inside and part_is_shared and part_lives_after_whole:
        return "Aggregation (◇)"
    return "Association or mixed — examine intent"
```

## 5. UML → Python — Translating Diagrams to Code

UML's distinctions are visual intent; Python's implementation is uniform. Here is the canonical mapping:

### 5.1 UML Class Diagram → Python Code

```
┌──────────┐        ┌──────────┐        ┌───────────┐        ┌─────────────┐
│  Customer│◇───────│  Order   │◆───────│ LineItem  │───────▶│   Product   │
│  id      │ 1   *  │  id      │ 1   *  │  sku      │  *   1 │  sku        │
│  name    │        │  date    │        │  qty      │        │  name       │
└──────────┘        └──────────┘        └───────────┘        └─────────────┘
  Aggregation         Composition          Association
  (independent)       (owned)              (references)
```

```python
from __future__ import annotations
from dataclasses import dataclass, field
from datetime import date

# --- Independent entity (aggregation target): lives without Orders ---
@dataclass
class Customer:
    id: int
    name: str

# --- Catalog entity (association target): LineItem knows about Product but doesn't own it ---
@dataclass(frozen=True)
class Product:
    sku: str
    name: str
    price: float

# --- Owned entity (composition target): only exists inside an Order ---
@dataclass
class LineItem:
    """Composition part — owned by exactly one Order."""
    product_sku: str       # denormalized — avoids holding a Product reference
    quantity: int
    unit_price: float      # price snapshot — frozen at order time

    @property
    def total(self) -> float:
        return self.quantity * self.unit_price

# --- Whole (owner) ---
@dataclass
class Order:
    """Order aggregates Customer, composes LineItems, associates with Products via sku lookup."""
    order_id: int
    customer: Customer                         # ◇ aggregation — injected
    _items: list[LineItem] = field(default_factory=list, repr=False)

    # Association: uses a product catalog transiently to create a snapshot
    def add_product(self, product: Product, quantity: int) -> None:
        # product is association param; we store a COMPOSED snapshot:
        self._items.append(LineItem(
            product_sku=product.sku,
            quantity=quantity,
            unit_price=product.price,  # snapshot — immune to future price changes
        ))

    @property
    def items(self) -> tuple[LineItem, ...]:
        return tuple(self._items)

    @property
    def total(self) -> float:
        return sum(i.total for i in self._items)
```

**Mapping notes:**

* **Aggregation (`Order ◇── Customer`):** `Customer` created externally, passed into `Order.__init__`. Stored as `self.customer`. Customer outlives Order.
* **Composition (`Order ◆── LineItem`):** `LineItem` created *inside* `Order.add_product`, stored in `self._items`. No external reference. LineItems die with Order.
* **Association (`LineItem ── Product`):** We *deliberately* avoid `self.product = product` (which would be aggregation with lifetime coupling to price). Instead we store `product_sku` (a value) — an even weaker association that eliminates the reference entirely. An alternative is `self._product_ref: weakref` if you need live lookup — see Section 7.

### 5.2 Multiplicity and Containers in Python

| UML multiplicity | Python implementation |
|---|---|
| `1` (exactly one) | `self.part: Part` (required `__init__` arg) |
| `0..1` (optional) | `self.part: Part | None = None` |
| `*` or `0..*` | `self.parts: list[Part] = []` (watch mutable default!) |
| `1..*` (at least one) | `self.parts: list[Part]` + validation `if not parts: raise` |
| Ordered `*` | `list[Part]` |
| Unordered unique `*` | `set[Part]` or `dict[key, Part]` |

```python
# WRONG — mutable default is shared across all Orders!
@dataclass
class OrderBad:
    items: list[LineItem] = []  # ONE list for every Order instance!

# CORRECT — default_factory gives each instance its own list:
@dataclass
class OrderGood:
    items: list[LineItem] = field(default_factory=list)

# REQUIRED multiplicity — enforce at runtime:
@dataclass
class OrderStrict:
    order_id: int
    customer: Customer
    items: list[LineItem]  # required — dataclass enforces no default

    def __post_init__(self):
        if not self.items:
            raise ValueError("order must have at least one line item")
```

## 6. Shared References — Aliasing, Identity, and Bugs

### 6.1 The Alias Trap — Mutation via Shared Reference

```python
@dataclass
class Address:
    street: str
    city: str

# Aggregation — two orders share one Address object:
addr = Address("123 Main", "Springfield")
order1 = Order(1, Customer(1, "Alice"), [])
order2 = Order(2, Customer(2, "Bob"), [])
# (pretend Order stored an Address via aggregation)
order1.shipping_address = addr  # type: ignore
order2.shipping_address = addr  # same object

# Mutating through one alias mutates the other:
addr.city = "Shelbyville"
print(order1.shipping_address.city)  # Shelbyville — surprise if you thought orders had snapshots!
print(order2.shipping_address.city)  # Shelbyville

# Fix 1: immutable address
@dataclass(frozen=True)
class AddressFrozen:
    street: str
    city: str
# addr.city = "x"  # FrozenInstanceError

# Fix 2: copy on assignment (defensive)
import copy
class OrderWithCopy:
    def __init__(self, address: Address):
        self.shipping_address = copy.copy(address)  # private snapshot
```

### 6.2 `copy` vs `deepcopy` — Shallow Is Often Enough, Deep Can Surprise

```python
import copy

@dataclass
class CatalogEntry:
    product: Product
    tags: list[str]

original = CatalogEntry(Product("W01", "Widget", 10.0), ["sale", "new"])

# Shallow copy — new CatalogEntry, but `product` and `tags` still shared:
shallow = copy.copy(original)
print(shallow is original)               # False — different wrapper
print(shallow.product is original.product)  # True — same Product
print(shallow.tags is original.tags)        # True — same list!

shallow.tags.append("clearance")
print(original.tags)  # ['sale', 'new', 'clearance'] — leaked!

# Deep copy — fully independent tree:
deep = copy.deepcopy(original)
print(deep.product is original.product)  # False
print(deep.tags is original.tags)        # False
deep.tags.append("deep-only")
print(original.tags)  # unchanged
```

**Guidance:** For aggregation with value-object parts (simple dataclasses without nested mutables), `copy.copy` is sufficient and faster. For composed graphs with nested mutables, use `deepcopy` or — better — immutable types.

### 6.3 Identity Checks — `is` vs `==`

```python
alice1 = Customer(1, "Alice")
alice2 = Customer(1, "Alice")  # same VALUE, different IDENTITY

print(alice1 == alice2)  # True  — @dataclass gives value equality (if eq=True)
print(alice1 is alice2)  # False — distinct objects

order1 = Order(1, alice1, [])
order2 = Order(2, alice1, [])
print(order1.customer is order2.customer)  # True — aggregation shares identity
print(order1.customer == alice2)           # True — equality by value, but NOT shared
```

> **Design implication:** If you use `==` to compare, two orders with "equal" but distinct customers will look like they share a customer when they do not. For ownership reasoning, `is` is the truth.

## 7. Weak References — Sharing Without Owning (and Breaking Cycles)

### 7.1 The Problem — Reference Cycles and Unwanted Lifetime Extension

Aggregation's shared references can create **cycles** and **leaks**:

```python
class Customer:
    def __init__(self, name: str) -> None:
        self.name = name
        self.orders: list["Order"] = []  # Customer knows its Orders

class Order:
    def __init__(self, order_id: int, customer: Customer) -> None:
        self.order_id = order_id
        self.customer = customer           # Order knows its Customer
        customer.orders.append(self)       # cycle: Customer -> Order -> Customer

alice = Customer("Alice")
o1 = Order(101, alice)
o2 = Order(102, alice)

# Reference graph: alice -> [o1, o2] -> alice -> [o1, o2] -> ...
# Even after:
del o1
# Order 101 is STILL alive via alice.orders[0] — not garbage!
# And if you hold only `alice`, all orders are kept alive even if you wanted them freed.
```

Python's cyclic GC *will* eventually collect unreachable cycles, but:

* Objects with `__del__` in a cycle may not be collected (pre-3.4) or require `gc` intervention.
* Even without `__del__`, cycles keep objects alive **as long as any entry point** (`alice`) is alive — extending lifetimes unexpectedly.
* Caches and observer lists that hold strong references prevent garbage collection of the observed objects entirely.

**Solution:** Hold the *non-owning* side with a **weak reference** — a reference that does not increment the refcount and does not keep the target alive.

### 7.2 `weakref` — The Module

```python
import weakref
import gc

# --- Basic weak reference ---
class Order:
    def __init__(self, order_id: int, customer: "Customer") -> None:
        self.order_id = order_id
        # Weak aggregation — Order references Customer but does not keep it alive
        self._customer_ref = weakref.ref(customer)

    @property
    def customer(self) -> "Customer | None":
        return self._customer_ref()  # call the ref to dereference; None if collected

    @property
    def customer_or_raise(self) -> "Customer":
        c = self._customer_ref()
        if c is None:
            raise ReferenceError("customer has been garbage-collected")
        return c

class Customer:
    def __init__(self, name: str) -> None:
        self.name = name
        self.orders: list[Order] = []  # strong — Customer OWNS its order list (composition-ish)

alice = Customer("Alice")
order = Order(101, alice)
print(order.customer is alice)  # True — still points to Alice
print(order.customer.name)      # Alice

del alice                       # last strong reference to Customer is gone
gc.collect()                    # force collection for demo (normally automatic)
print(order.customer)           # None — weak ref went dead, no leak
# order.customer_or_raise        # would raise ReferenceError
```

**Explanation:**

* `weakref.ref(customer)` creates a weak reference object. It does not increment `customer`'s refcount.
* Calling `ref()` dereferences — returns the object if alive, `None` if collected.
* When `alice` is deleted, the `Order`'s weak reference automatically becomes `None` — the cycle is broken.

#### Types of weak references

| Factory | Returns | Holds | Common use |
|---|---|---|---|
| `weakref.ref(obj)` | `weakref` callable | Nothing — just watches `obj` | Single back-pointer (Order → Customer) |
| `weakref.proxy(obj)` | proxy object | Proxies attribute access; raises `ReferenceError` if dead | Transparent delegation |
| `weakref.WeakSet()` | set of weak refs | Each member weakly | Cache of instances (e.g., registry) |
| `weakref.WeakKeyDictionary()` | dict with weak keys | Keys weakly; values strong | Auxiliary data keyed by objects |
| `weakref.WeakValueDictionary()` | dict with weak values | Values weakly; keys strong | Cache / interning (e.g., catalog) |
| `weakref.WeakMethod` | weak ref to bound method | Method weakly | Event / callback registries |

### 7.3 `weakref.proxy` — Transparent Weak Association

```python
import weakref

class Product:
    def __init__(self, sku: str, price: float) -> None:
        self.sku = sku
        self.price = price

class LineItem:
    def __init__(self, product: Product, quantity: int) -> None:
        # Use proxy so self.product behaves like a Product but is weak
        self.product = weakref.proxy(product)
        self.quantity = quantity

p = Product("W01", 19.99)
item = LineItem(p, 2)
print(item.product.price)  # 19.99 — proxy forwards attribute access

del p
# item.product.price  # ReferenceError: weakly-referenced object no longer exists
# The LineItem's association to Product died with the Product — correct for weak association.
```

**When to use `ref` vs `proxy`:**

* `ref` — you want explicit control (`if obj_ref() is None: handle`).
* `proxy` — you want transparent use (`obj.price`) and are okay with `ReferenceError` on dead targets.

### 7.4 Observer / Event Pattern — The Classic Weak-Reference Use

```python
import weakref

class EventManager:
    """Holds listeners weakly so listeners can be GC'd without unsubscribing."""
    def __init__(self):
        self._listeners: weakref.WeakSet = weakref.WeakSet()

    def subscribe(self, listener) -> None:
        self._listeners.add(listener)

    def emit(self, event: str) -> None:
        for listener in list(self._listeners):  # snapshot — weak set may shrink during iteration
            listener.on_event(event)

class OrderListener:
    def on_event(self, event: str) -> None:
        print(f"Listener got: {event}")

mgr = EventManager()
listener = OrderListener()
mgr.subscribe(listener)
mgr.emit("order_created")  # Listener got: order_created

del listener               # no explicit unsubscribe needed
import gc; gc.collect()
mgr.emit("order_created")  # silently no listeners — no leak, no stale callback
```

Without `WeakSet`, `EventManager._listeners` would hold a *strong* reference, keeping the listener alive forever and leaking memory for every subscribed-but-logically-dead object.

### 7.5 Cache and Interning with `WeakValueDictionary`

```python
import weakref

class ProductCatalog:
    """Catalog that interns Products — weak values allow GC when no Order uses them."""
    def __init__(self):
        self._by_sku: weakref.WeakValueDictionary[str, Product] = weakref.WeakValueDictionary()

    def get_or_create(self, sku: str, name: str, price: float) -> Product:
        p = self._by_sku.get(sku)
        if p is None:
            p = Product(sku, price)
            self._by_sku[sku] = p  # weak — catalog does NOT keep Product alive alone
        return p

catalog = ProductCatalog()
w1 = catalog.get_or_create("W01", "Widget", 19.99)
w2 = catalog.get_or_create("W01", "Widget", 19.99)  # same object
print(w1 is w2)  # True — interning works

del w1, w2
gc.collect()
print(catalog._by_sku.get("W01"))  # None — no strong refs left, catalog entry evaporated
# If some Order still held a strong ref to the Product, it would remain in the catalog.
```

### 7.6 Weak References and Supported Types

```python
import weakref

# Weak-referencable: user-defined classes (have __weakref__ slot)
class MyClass: pass
obj = MyClass()
weakref.ref(obj)  # OK

# NOT weak-referencable by default: tuple, str, int, list, dict (no __weakref__)
# weakref.ref([1, 2])  # TypeError: cannot create weak reference to 'list' object

# FIX — add __slots__ with __weakref__, or wrap:
class WeakableList(list):
    __slots__ = ("__weakref__",)

wl = WeakableList([1, 2])
weakref.ref(wl)  # OK
```

**Rule:** Most built-in types cannot be weakly referenced. Wrap or subclass with `__slots__ = ("__weakref__",)` if you must.

### 7.7 Callbacks on Collection — `weakref.ref(obj, callback)`

```python
import weakref

def on_customer_collected(ref):
    print("Customer was garbage-collected — cleaning up...")

alice = Customer("Alice")
alice_ref = weakref.ref(alice, on_customer_collected)

del alice
gc.collect()  # prints: Customer was garbage-collected — cleaning up...
```

Use callbacks to evict related entries, close resources, or notify owners — but keep callbacks short and avoid resurrecting the object.

## 8. Comprehensive Realistic Example — Order / Customer / Product with All Relationships

This extended example weaves **association, aggregation, composition, and weak references** into a coherent domain, annotated with UML intent.

### 8.1 Domain and UML Intent

```
┌──────────┐  ◇─────  ┌───────────┐  ◆─────  ┌───────────┐  ────  ┌──────────┐
│Customer  │ 1    *   │  Order    │ 1    *   │ LineItem  │ *    1 │ Product  │
│(indep.)  │          │(own Line) │          │(owned)    │        │(catalog) │
│  id,name │          │  id,date  │          │ qty,price │        │ sku,price│
└──────────┘          └───────────┘          └───────────┘        └──────────┘
       ▲                     │  ─ ─ ─ ─ ─ ─ ─ ─  ┌──────────────────┐
       │  weak back-ref      │  uses             │ PricingService    │
       └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┘                   │ (association)     │
                                                 └──────────────────┘
       ┌──────────────────┐
       │CustomerRegistry  │◇──── weakly holds Customers (WeakValueDictionary)
       └──────────────────┘
```

* **Aggregation:** `Order ◇── Customer` — Customer exists independently; Orders share one.
* **Composition:** `Order ◆── LineItem` — LineItems are owned, private, die with Order.
* **Association:** `LineItem ── Product` (via snapshot) and `Order ── PricingService` (transient).
* **Weak aggregation:** `Order ──→ Customer` back-ref via `weakref` + `CustomerRegistry` via `WeakValueDictionary`.

### 8.2 Full Implementation

```python
from __future__ import annotations
import weakref
import gc
from dataclasses import dataclass, field
from datetime import date, datetime
from typing import Protocol
from copy import copy

# ── Independent entities ──────────────────────────────────

@dataclass
class Customer:
    """Independent entity — exists before and after any Order."""
    id: int
    name: str
    email: str
    # Strong reference to orders is avoided here — would create a hard cycle.
    # Instead, the registry tracks orders separately, or orders are queried
    # via a repository. For demo we keep a WEAK back-ref pattern elsewhere.

@dataclass(frozen=True)
class Product:
    """Catalog entry — immutable so aggregation sharing is safe."""
    sku: str
    name: str
    price: float

# ── Association: pricing strategy (transient use) ──────────

class PricingService(Protocol):
    def apply_discount(self, subtotal: float, customer: Customer) -> float: ...

class NoDiscount:
    def apply_discount(self, subtotal: float, customer: Customer) -> float:
        return subtotal

class LoyaltyDiscount:
    def __init__(self, rate: float = 0.1, min_orders: int = 5) -> None:
        self.rate = rate
        self.min_orders = min_orders

    def apply_discount(self, subtotal: float, customer: Customer) -> float:
        # In a real app, look up customer's order count from a repo
        return subtotal * (1 - self.rate)  # simplified

# ── Composition part ──────────────────────────────────────

@dataclass
class LineItem:
    """Owned by exactly one Order. Price frozen at addition time."""
    product_sku: str
    product_name: str
    quantity: int
    unit_price: float

    @property
    def total(self) -> float:
        return self.quantity * self.unit_price

# ── Whole ─────────────────────────────────────────────────

class Order:
    """
    Order aggregates Customer (shared, injected),
    composes LineItems (owned, created inside),
    associates with PricingService (transient) and Product (via snapshot).
    """

    def __init__(
        self,
        order_id: int,
        customer: Customer,                          # ◇ aggregation — shared
        pricing: PricingService | None = None,       # association — transient
    ) -> None:
        self.order_id = order_id
        self._customer_ref = weakref.ref(customer)   # weak aggregation — avoid cycle
        self._items: list[LineItem] = []             # ◆ composition — owned
        self.pricing: PricingService = pricing or NoDiscount()  # association
        self.created_at: datetime = datetime.now()

    # ── Aggregation access (weak) ──
    @property
    def customer(self) -> Customer | None:
        return self._customer_ref()

    # ── Composition management ──
    def add_product(self, product: Product, quantity: int = 1) -> None:
        """Create a COMPOSED LineItem snapshot from an associated Product."""
        if quantity <= 0:
            raise ValueError("quantity must be positive")
        self._items.append(LineItem(
            product_sku=product.sku,
            product_name=product.name,
            quantity=quantity,
            unit_price=product.price,  # snapshot — immune to catalog price changes
        ))

    def remove_line(self, index: int) -> None:
        del self._items[index]

    @property
    def items(self) -> tuple[LineItem, ...]:
        return tuple(self._items)

    # ── Derived behavior using association ──
    @property
    def subtotal(self) -> float:
        return sum(item.total for item in self._items)

    def total(self) -> float:
        c = self.customer
        if c is None:
            # Customer GC'd — charge without discount rather than crash,
            # or raise ReferenceError depending on policy.
            return self.subtotal
        return self.pricing.apply_discount(self.subtotal, c)

    def __repr__(self) -> str:
        c = self.customer
        cname = c.name if c else "<collected>"
        return f"Order({self.order_id}, customer={cname!r}, items={len(self._items)}, total={self.total:.2f})"

# ── Weak aggregation registry ─────────────────────────────

class CustomerRegistry:
    """Holds customers weakly — does not prevent GC, acts as an intern cache."""
    def __init__(self) -> None:
        self._by_id: weakref.WeakValueDictionary[int, Customer] = weakref.WeakValueDictionary()

    def register(self, customer: Customer) -> None:
        self._by_id[customer.id] = customer

    def get(self, customer_id: int) -> Customer | None:
        return self._by_id.get(customer_id)

    def __len__(self) -> int:
        return len(self._by_id)
```

### 8.3 Exercising Every Relationship

```python
# --- Setup: independent entities exist first ---
registry = CustomerRegistry()
alice = Customer(1, "Alice", "alice@example.com")
registry.register(alice)

catalog = {
    "W01": Product("W01", "Widget", 19.99),
    "G02": Product("G02", "Gadget", 29.99),
}

# --- Create orders that AGGREGATE the same customer ---
order1 = Order(101, alice, pricing=LoyaltyDiscount(rate=0.1))
order1.add_product(catalog["W01"], 2)
order1.add_product(catalog["G02"], 1)
print(order1)          # Order(101, customer='Alice', items=2, total=62.97)
print(order1.subtotal) # 69.97 before discount

order2 = Order(102, alice)
order2.add_product(catalog["W01"], 1)
print(order2)          # Order(102, customer='Alice', items=1, total=19.99)

# Aggregation proof — shared identity:
print(order1.customer is order2.customer is alice)  # True

# --- Composition proof — line items are snapshots, not live products ---
catalog["W01"] = Product("W01", "Widget", 9.99)  # price drop (new immutable object)
print(order1.items[0].unit_price)  # 19.99 — frozen at order time
print(order2.items[0].unit_price)  # 19.99

# Line items are exclusive:
print(order1.items[0] is order2.items[0])  # False — distinct snapshots

# Deleting an order collects its line items:
items_ref = order1.items[0]
del order1
# items_ref still alive because we hold it, but Order 101's _items list is gone
# If we also `del items_ref`, the LineItem would be GC'd (no composition owner)

# --- Weak aggregation — orders do not keep Alice alive ---
del alice              # remove the strong reference (registry is weak)
gc.collect()
print(order2.customer) # None — weak ref died, registry no longer has it
print(len(registry))   # 0  — registry entry evaporated
print(order2.total())  if False else print(order2.total)  # total() handles None gracefully

# Recreate Alice — new identity, not the old object:
alice2 = Customer(1, "Alice", "alice@example.com")
print(order2.customer is alice2)  # False — order2's weak ref is still None
# To reconnect, you'd need to re-create or re-associate the order.

# --- Association — pricing service can be swapped at runtime ---
order2.pricing = LoyaltyDiscount(rate=0.2)
# (customer is None, so discount not applied in this demo; with a live customer it would)
```

**What this demonstrates:**

* **Aggregation sharing** — two orders see the same `Customer` identity.
* **Composition exclusivity and lifetime** — `LineItem` snapshots are private, frozen, and die with their `Order`.
* **Immutability as a sharing strategy** — `Product` is `frozen=True` so catalog updates create new objects rather than mutating shared state.
* **Weak references break cycles** — `Order → Customer` is weak, `CustomerRegistry` is a `WeakValueDictionary`, so neither extends `Customer` lifetimes unexpectedly.
* **Association flexibility** — `PricingService` is a transient strategy, swappable at runtime without inheritance.

## 9. Python's Garbage Collection and `__del__` — Why Ownership Still Matters

### 9.1 Reference Counting + Cycle Collector

CPython uses **reference counting** (immediate) plus a **generational cycle collector** (`gc` module) for unreachable cycles:

```python
import gc

# Reference counting — immediate:
a = Customer(1, "Alice")
print(gc.get_referrers(a))  # list of objects that reference Alice (debug)

# Cycle not immediately freed but eventually collected:
# alice -> order -> alice (weak ref breaks the cycle, so not needed here)
# With strong cycle: collected by gc.collect(), not instantly.

# You can control generational thresholds:
gc.get_threshold()  # (700, 10, 10) defaults
# Or disable GC for performance in tight loops:
# gc.disable(); ...; gc.enable()
```

**Implication for composition:** Owned objects (LineItems) held only by their whole are collected *immediately* when the whole dies (refcount 0). Aggregated objects with external owners are not — they persist. This is the runtime realization of the UML lifetime distinction.

### 9.2 `__del__` (Finalizer) — Fragile and Usually Wrong

```python
class FileOrder:
    def __init__(self, path: str) -> None:
        self.file = open(path, "w")
    def __del__(self):
        # WARNING: __del__ is NOT a reliable destructor.
        print(f"finalizing {self}")
        try:
            self.file.close()
        except Exception:
            pass

order = FileOrder("/tmp/demo.txt")
del order  # may or may not print immediately — CPython usually does (refcount), PyPy later

# Why __del__ is fragile:
# - Not called if object is in an uncollectable cycle (older Python) or if interpreter exits
# - Exceptions inside __del__ are ignored with a warning
# - Resurrection: __del__ can create a new reference to self, preventing collection
# - Order of finalization is unpredictable

# Pythonic alternatives:
# 1. Context manager (deterministic):
class FileOrderCM:
    def __init__(self, path): self.path = path
    def __enter__(self):
        self.file = open(self.path, "w")
        return self
    def __exit__(self, *args):
        self.file.close()

with FileOrderCM("/tmp/demo2.txt") as o:
    o.file.write("hello")
# file closed deterministically at `with` exit — no __del__ needed.

# 2. weakref.finalize — more reliable than __del__:
import weakref
def _cleanup(path: str):
    print(f"cleanup for {path}")

obj = FileOrder("/tmp/demo3.txt")
weakref.finalize(obj, _cleanup, "/tmp/demo3.txt")
# _cleanup called when obj is GC'd, even if in a cycle
```

> **Guideline:** Never rely on `__del__` to enforce composition lifetimes (e.g., "when Order dies, close its LineItem resources"). Use **context managers** (`with`), **explicit `close()`**, or **`weakref.finalize`** for deterministic cleanup. Composition's lifetime coupling is a *design* guarantee for logical ownership — not a substitute for resource management.

### 9.3 Ownership and `copy` — Does Copying Respect Ownership?

```python
import copy

alice = Customer(1, "Alice", "alice@example.com")
order = Order(201, alice)
order.add_product(Product("W01", "Widget", 10.0), 3)

# Shallow copy — new Order shell, but shares Customer and LineItems!
shallow = copy.copy(order)
print(shallow is order)                      # False
print(shallow.customer is order.customer)    # True — aggregation shared (may be intended)
print(shallow._items is order._items)        # True — OOPS: shared mutable list!

shallow._items.append(LineItem("X", "Xtra", 1, 1.0))
print(len(order._items))  # 2 — mutated the original!

# Correct copy for composition — deep or explicit:
deep = copy.deepcopy(order)  # note: weakref inside deepcopy has subtleties
print(deep._items is order._items)           # False
print(deep._items[0] is order._items[0])     # False — distinct LineItems

# Custom __copy__ / __deepcopy__ / __getstate__ for ownership control:
class OrderWithCopySemantics(Order):
    def __copy__(self):
        new = self.__class__.__new__(self.__class__)
        new.order_id = self.order_id
        new._customer_ref = self._customer_ref  # aggregation — share weak ref
        new._items = list(self._items)         # composition — copy list
        new.pricing = self.pricing             # association — share strategy (stateless)
        new.created_at = self.created_at
        return new
    def __deepcopy__(self, memo):
        new = self.__class__.__new__(self.__class__)
        memo[id(self)] = new
        new.order_id = self.order_id
        new._customer_ref = self._customer_ref  # still weak — don't deepcopy the customer
        new._items = copy.deepcopy(self._items, memo)
        new.pricing = copy.deepcopy(self.pricing, memo)
        new.created_at = self.created_at
        return new
```

## 10. Edge Cases and Common Mistakes

### 10.1 Optional Aggregation — `Customer | None`

```python
class GuestOrder(Order):
    """Order that may have no registered customer."""
    def __init__(self, order_id: int, customer: Customer | None = None) -> None:
        self.order_id = order_id
        self._customer_ref = weakref.ref(customer) if customer else lambda: None
        self._items: list[LineItem] = []
```

Beware: `weakref.ref(None)` is illegal. Guard optional weak refs with a lambda or store `None` directly and branch on `is None`.

### 10.2 Bidirectional Aggregation Without Weak Refs — The Leak

```python
# LEAK — strong bidirectional aggregation
class Department:
    def __init__(self, name): self.name = name; self.employees: list[Employee] = []
class Employee:
    def __init__(self, name, dept: Department):
        self.name = name; self.dept = dept; dept.employees.append(self)

eng = Department("Eng")
alice = Employee("Alice", eng)
# eng -> alice, alice -> eng — cycle keeps both alive as long as EITHER is alive
# With weak ref on the non-owning side, lifetime is clear:
class EmployeeFixed:
    def __init__(self, name, dept: Department):
        self.name = name; self._dept_ref = weakref.ref(dept); dept.employees.append(self)
    @property
    def dept(self): return self._dept_ref()
```

**Ownership rule for bidirectional links:** Exactly one side should be **strong (owning)**, the other **weak (observing)**. Choose the parent/collection as strong.

### 10.3 Frozen Dataclass + Weak Ref — Needs `__slots__`

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class WeakableProduct:
    __slots__ = ("sku", "price", "__weakref__")  # frozen + weakable
    sku: str
    price: float

import weakref
p = WeakableProduct("W01", 10.0)
weakref.ref(p)  # OK now — has __weakref__ slot
```

### 10.4 `__slots__` and Ownership

```python
class LineItemSlots:
    __slots__ = ("product_sku", "quantity", "unit_price")
    def __init__(self, sku, qty, price):
        self.product_sku = sku; self.quantity = qty; self.unit_price = price
# No __dict__ — smaller, faster, but cannot hold arbitrary attributes.
# Add "__weakref__" to __slots__ if you need weak references to LineItemSlots.
```

## 11. Decision Flowchart — Which Relationship?

```
Does A store a reference to B after the method returns?
├─ No  → Association (use-a, transient)
└─ Yes → Does A CREATE B (B wouldn't exist without A)?
         ├─ Yes → Composition (● owned, exclusive, dies with A)
         └─ No  → Aggregation (◇ shared, injected, lives on)
                  ├─ Is B mutable and shared? → Make immutable or copy-on-capture
                  └─ Is there a back-reference cycle? → Make one side weak
```

### Checklist for each `self.x = y` in `__init__` or methods

* [ ] Is `y` created inside or passed in? *(Inside → composition; outside → aggregation/association)*
* [ ] Is `y` shared between multiple owners? *(Shared → aggregation)*
* [ ] Is `y` mutable? If shared, can mutations leak across owners? *(Consider `frozen=True` or copy)*
* [ ] Does `y` reference me back? *(Cycle → one side must be `weakref`)*
* [ ] Should `y` outlive me? *(No → composition; yes → aggregation)*
* [ ] Do I need deterministic cleanup when I die? *(Use `with` / `weakref.finalize`, not `__del__`)*

## 12. Summary

* **All three relations look like `self.x = x` in Python** — UML distinguishes them by intent and lifetime, Python distinguishes them by *who creates the object, whether it is shared, and what keeps it alive*.
* **Association** is ephemeral — a method parameter, no retention. Lowest coupling.
* **Aggregation** is shared — the whole receives a pre-existing object, does not exclusively own it, and does not control its lifetime. Dangerous with mutable shared objects; prefer immutable parts or defensive copies.
* **Composition** is exclusive — the whole creates and owns the part; the part dies with the whole. Strongest guarantee; enforce by creating the part inside the whole and never leaking its mutable internals.
* **Shared references are aliases**, not copies. `order1.customer is order2.customer` is the test for sharing. Mutations through one alias are visible through all.
* **Weak references** (`weakref.ref`, `proxy`, `WeakSet`, `WeakKeyDictionary`, `WeakValueDictionary`) let you hold a non-owning reference that does not extend lifetime and that automatically dies — essential for observer lists, caches, parent back-pointers, and cycle breaking.
* **Garbage collection** gives you composition-like reclamation for free via refcounting, but **resource cleanup must never rely on `__del__`**. Use context managers and `weakref.finalize`.
* Model thoughtfully: make `Product` immutable, `LineItem` compositionally owned, `Customer` aggregated, and `PricingService` associated. Code that matches its ownership reality is code that does not leak or surprise.
