# 11.1 Composition vs Inheritance — Parts, Taxonomies, and Who Owns the Behavior

> **Mental model up front:** Inheritance says *"I am a specialized version of you — I share your identity and your contract."* Composition says *"I have a part that does that job for me — I delegate to it."* In Python, inheritance wires classes together at definition time through the MRO — a tight, invisible coupling. Composition wires objects together at *runtime* through references you can see, inspect, replace, and test in isolation. That is why the Pythonic default is composition: prefer holding a reference and asking it nicely over inheriting a family tree you cannot divorce.

---

## 1. The Core Distinction — `is-a` vs `has-a`

Every object relationship answers one question: **how do you describe the link in plain English?**

| Relationship | English test | Meaning | UML | Python mechanism |
|---|---|---|---|---|
| **Inheritance** | `X is a Y` | X is a specialized kind of Y, substitutable for Y | `X ──▷ Y` (open arrow) | `class X(Y):` |
| **Composition** | `X has a Y` | X is built from Y as a part, delegates work to Y | `X ◆── Y` (filled diamond) | `self.y = Y(...)` |

### 1.1 `is-a` — Identity Inheritance

```python
class Animal:
    def speak(self) -> str:
        raise NotImplementedError

class Dog(Animal):
    def speak(self) -> str:
        return "woof"

buddy = Dog()
print(isinstance(buddy, Dog))     # True
print(isinstance(buddy, Animal))  # True — Dog IS-AN Animal
print(issubclass(Dog, Animal))    # True
```

**Explanation:** `class Dog(Animal)` declares that every `Dog` *is* an `Animal`. The consequence is **identity coupling**: `isinstance` checks pass, `MRO` chains are merged, and any code expecting an `Animal` must accept a `Dog`. This is a promise about behavior, not just code reuse.

```python
# The promise breaks if we lie about is-a:
class Ostrich(Bird):  # Ostrich is-a Bird, right?
    def fly(self) -> None:
        raise RuntimeError("ostriches can't fly!")

# Any function written for Bird will crash on Ostrich:
def migrate(bird: Bird) -> None:
    bird.fly()  # Ostrich violates Bird's contract — Liskov failure

# Prefer composition here — Ostrich HAS wings but is NOT a flying Bird.
```

> **Rule of thumb:** If you hesitate to say *"X is a kind of Y"* out loud — *"A Car is a kind of Engine"* — you do not want inheritance.

### 1.2 `has-a` — Structural Assembly

```python
class Engine:
    def start(self) -> None:
        print("Engine started")

class Car:
    def __init__(self, engine: Engine) -> None:
        self.engine = engine  # Car HAS-A Engine

    def start(self) -> None:
        print("Car starting...")
        self.engine.start()   # delegation

car = Car(Engine())
car.start()
print(isinstance(car, Engine))  # False — Car is NOT an Engine
print(hasattr(car, "engine"))   # True  — Car HAS an Engine
```

**Explanation:** `Car` does not become an `Engine`. It *holds* an `Engine` in `self.engine` and **delegates** the `start` work. You can see the link (`car.engine`), replace it at runtime (`car.engine = ElectricEngine()`), and test each class in isolation. The relationship exists between **objects**, not between **classes**.

### 1.3 A Subtle Third Category — "Implemented in Terms Of"

Sometimes you inherit purely to reuse code without meaning `is-a`:

```python
# TEMPTING but WRONG — Stack is NOT a list semantically
class Stack(list):  # inherits all 40+ list methods
    def push(self, item):
        self.append(item)
    def pop(self):
        return super().pop()

s = Stack([1, 2])
s.sort()          # Why can you sort a stack? Leaky abstraction!
s.insert(0, 99)   # Why can you insert in the middle?
s[1] = 999        # Why can you random-access?
```

```python
# CORRECT — Stack HAS a list, exposes only stack operations
class Stack:
    def __init__(self) -> None:
        self._items: list = []

    def push(self, item) -> None:
        self._items.append(item)

    def pop(self):
        if not self._items:
            raise IndexError("pop from empty stack")
        return self._items.pop()

    def __len__(self) -> int:
        return len(self._items)

    def __repr__(self) -> str:
        return f"Stack({self._items!r})"
```

> **Litmus test:** Would you want *all* of the parent's public interface? If not, you want composition ("implemented in terms of"), not inheritance.

## 2. Inheritance — What Python Actually Does and Why It Couples Tightly

### 2.1 Inheritance Is MRO Concatenation

When you write `class Child(Parent)`, Python does not copy methods. It builds a **Method Resolution Order** — a linearized search chain:

```python
class A:
    def save(self): print("A.save")

class B(A):
    pass

class C(B):
    def save(self): print("C.save")

print(C.__mro__)
# (<class 'C'>, <class 'B'>, <class 'A'>, <class 'object'>)
# Attribute lookup walks THIS chain on every access.
```

So `c.save()` does not "call B or A" — it walks `type(c).__mro__` until it finds `save`. This has consequences:

* **Every method on a parent is implicitly available on the child**, even if you never intended it.
* **Changing the parent changes all children** — downstream breakage without touching downstream files.
* **Name collisions are silent** — a new method on a parent can shadow or be shadowed by a child.

### 2.2 The Fragile Base Class Problem

```python
# v1 — Base class
class Logger:
    def log(self, message: str) -> None:
        self._write(message)

    def _write(self, message: str) -> None:
        print(f"[LOG] {message}")

# Subclass overrides internal helper
class TimestampLogger(Logger):
    def _write(self, message: str) -> None:
        from datetime import datetime
        super()._write(f"{datetime.now().isoformat()} {message}")

# Later, base class author adds batching — calls _write internally:
class Logger:  # v2 — updated in a library release
    def log(self, message: str) -> None:
        self._buffer.append(message)  # new buffering
        if len(self._buffer) >= 10:
            self.flush()

    def flush(self) -> None:
        for m in self._buffer:
            self._write(m)  # _write now called in a NEW context
        self._buffer.clear()

    def _write(self, message: str) -> None:
        print(f"[LOG] {message}")
```

**What broke?** The subclass `TimestampLogger` overrides `_write` assuming one call per `log`, but now `flush()` calls `_write` in a loop. If `_write` had side effects (opening files, counting calls), the subclass interaction changed *without any change in the subclass file*.

This is **tight coupling in time and space**: the child depends on *implementation details* of the parent, not just its public contract. In large Python codebases — where base classes often live in other packages or frameworks — this is the number-one source of inheritance-related bugs.

### 2.3 Multiple Inheritance Amplifies Coupling

```python
class FileMixin:
    def save(self): print("FileMixin.save")

class NetworkMixin:
    def save(self): print("NetworkMixin.save")

class Document(FileMixin, NetworkMixin):
    pass

print(Document.__mro__)
# Document -> FileMixin -> NetworkMixin -> object
# Which save() do you get? FileMixin's — first in MRO.

# Swapping order changes behavior silently:
class Document2(NetworkMixin, FileMixin):
    pass  # now NetworkMixin.save wins
```

Inheritance with multiple bases adds **C3 linearization**, `super()` complexity, and ordering sensitivity. Composition avoids all of it — you call `self.file_store.save()` or `self.network.save()` explicitly.

### 2.4 Metrics: How Coupled Are You?

| Coupling signal | Inheritance | Composition |
|---|---|---|
| Change blast radius | Changing base class may break all descendants | Changing a component only breaks explicit delegators |
| Surface area inherited | Entire public + protected interface (~dozens of methods) | Only methods you explicitly forward |
| Test replaceability | Need to subclass or monkey-patch parent to mock | Pass a fake/mock object into constructor |
| Runtime flexibility | Fixed at class-definition time | Can swap components at runtime |
| Namespace pollution | Child namespace polluted by all parent names | Child namespace contains only `self.part` |

## 3. Composition — Delegation as Design

### 3.1 The Simplest Composition — Manual Delegation

```python
class EmailSender:
    def send(self, to: str, subject: str, body: str) -> None:
        print(f"Email to {to}: {subject}")

class SMSSender:
    def send(self, to: str, message: str) -> None:
        print(f"SMS to {to}: {message}")

# Naive inheritance attempt — Notification IS-NOT an EmailSender:
# class Notification(EmailSender): ...  # wrong — what about SMS?

# Composition — Notification HAS senders, delegates to them:
class NotificationService:
    def __init__(self, email_sender: EmailSender, sms_sender: SMSSender) -> None:
        self.email_sender = email_sender
        self.sms_sender = sms_sender

    def notify_user(self, user, message: str) -> None:
        if user.prefers_email:
            self.email_sender.send(user.email, "Notification", message)
        else:
            self.sms_sender.send(user.phone, message)
```

**Explanation:** `NotificationService` has no inheritance. It holds two collaborators as ordinary attributes. The `notify_user` method contains the *orchestration logic* — which sender to use — and delegates the actual transport. Adding a `PushSender` requires adding a parameter and a branch, not a new base class.

### 3.2 Constructor Injection — The Pythonic Wiring Pattern

```python
from typing import Protocol

class Sender(Protocol):
    def send(self, to: str, message: str) -> None: ...

class EmailSender:
    def send(self, to: str, message: str) -> None:
        print(f"[email] {to}: {message}")

class FakeSender:  # for tests
    def __init__(self):
        self.sent: list[tuple[str, str]] = []
    def send(self, to: str, message: str) -> None:
        self.sent.append((to, message))

class Notifier:
    def __init__(self, sender: Sender) -> None:
        self.sender = sender  # dependency injected

    def notify(self, to: str, message: str) -> None:
        self.sender.send(to, message)

# Production:
notifier = Notifier(EmailSender())
# Test:
fake = FakeSender()
test_notifier = Notifier(fake)
test_notifier.notify("alice", "hi")
assert fake.sent == [("alice", "hi")]
```

**Why this matters in Python:** Because Python resolves attribute access at runtime, you can inject *any* object that has a `send` method — no interface inheritance required (duck typing). Using `typing.Protocol` adds static checking without runtime inheritance. This is composition's superpower for testability.

### 3.3 Python's Preference Is Cultural and Technical

* **Zen of Python:** *"Explicit is better than implicit."* `self.engine.start()` is explicit; `super().start()` is implicit MRO magic.
* **Dynamic typing:** Python rarely needs inheritance for polymorphism — if it walks like a duck, you can pass it. Composition + duck typing gives you polymorphism without a type hierarchy.
* **Standard library evidence:** `collections.abc`, `pathlib`, `io`, `http.client` — all favor composition or thin inheritance with heavy delegation. Even `collections.UserList`/`UserDict`/`UserString` exist *specifically* to let you compose around `list`/`dict`/`str` instead of inheriting from them (because inheriting from `list`/`dict` has C-level method-resolution quirks).
* **The `super()` tax:** Inheritance in Python demands understanding `super()`, MRO, `__init__` chaining, and cooperative multiple inheritance. Composition demands understanding... attribute access.

## 4. Delegation Techniques — From Manual to Automatic

### 4.1 Level 1 — Explicit Forwarding (Most Readable, Most Pythonic)

```python
class Engine:
    def start(self) -> None: print("Engine start")
    def stop(self) -> None:  print("Engine stop")

class Car:
    def __init__(self, engine: Engine) -> None:
        self._engine = engine

    # One method per delegated operation — verbose but crystal clear
    def start(self) -> None:
        self._engine.start()

    def stop(self) -> None:
        self._engine.stop()

    # Car's own behavior
    def drive(self) -> None:
        self.start()
        print("Car driving")
```

**Trade-off:** Every method you want exposed must be written explicitly. Tedious for large interfaces, but each forwarding method is a natural **interception point** — you can add logging, validation, or transformation without touching `Engine`.

```python
class Car:
    def start(self) -> None:
        print("[Car] pre-start checks...")
        if not self._has_fuel():
            raise RuntimeError("no fuel")
        self._engine.start()  # decoration opportunity
        print("[Car] engine started")

    def _has_fuel(self) -> bool:
        return True
```

### 4.2 Level 2 — `__getattr__` Automatic Forwarding

When the interface is large (e.g., wrapping a file object with 20 methods), manual forwarding is boilerplate. Python offers `__getattr__` — called only when normal lookup **fails**:

```python
class Engine:
    def start(self) -> None: print("Engine start")
    def stop(self) -> None:  print("Engine stop")
    def get_rpm(self) -> int: return 3000

class Car:
    def __init__(self, engine: Engine) -> None:
        self._engine = engine

    def drive(self) -> None:
        print("Car driving")

    def __getattr__(self, name: str):
        """Delegate any unknown attribute to the engine."""
        # Only called if `name` not found via normal MRO on Car
        print(f"  [delegating {name!r} to engine]")
        return getattr(self._engine, name)

car = Car(Engine())
car.drive()      # found on Car — __getattr__ NOT called
car.start()      # not on Car — __getattr__ delegates to engine
car.get_rpm()    # delegated
print(car.get_rpm())  # 3000
# car.nonexistent  # delegated -> AttributeError from engine
```

**Explanation step-by-step:**

1. `car.start` — Python searches `Car.__dict__` → `object.__dict__` → fails → calls `Car.__getattr__(car, "start")` → returns `Engine.start` bound method.
2. `car.drive` — found on `Car`, returned immediately, `__getattr__` never invoked.
3. The returned `Engine.start` is still a **bound method** to the `Engine` instance — `self` inside `Engine.start` is the engine, not the car. This is usually what you want.

**Critical difference — `__getattr__` vs `__getattribute__`:**

| Method | When called | Risk |
|---|---|---|
| `__getattr__(self, name)` | Only after normal lookup fails | Low — safe for delegation, cannot infinite-loop easily |
| `__getattribute__(self, name)` | On **every** attribute access | High — must use `object.__getattribute__(self, name)` or you get recursion |

```python
# DANGER — __getattribute__ with a bug causes infinite recursion
class BadCar:
    def __init__(self, engine):
        self._engine = engine

    def __getattribute__(self, name):
        # BUG: self._engine triggers __getattribute__ again!
        return getattr(self._engine, name)  # RecursionError!

# CORRECT __getattribute__:
class GoodCar:
    def __init__(self, engine):
        self._engine = engine

    def __getattribute__(self, name):
        try:
            return object.__getattribute__(self, name)  # normal lookup first
        except AttributeError:
            engine = object.__getattribute__(self, "_engine")
            return getattr(engine, name)
```

**Recommendation:** Prefer `__getattr__` for composition forwarding. Reach for `__getattribute__` only when you must intercept *every* access (proxy objects, lazy loading).

#### Caveats of `__getattr__` forwarding

```python
class Car:
    def __init__(self, engine):
        self._engine = engine
    def __getattr__(self, name):
        return getattr(self._engine, name)

car = Car(Engine())

# 1. Dunder methods are NOT routed through __getattr__:
#    Python looks up __len__, __iter__, etc. on the TYPE, not the instance.
class EngineWithLen:
    def __len__(self): return 42

class Car2:
    def __init__(self, engine): self._engine = engine
    def __getattr__(self, name): return getattr(self._engine, name)

car2 = Car2(EngineWithLen())
# len(car2)  # TypeError: object of type 'Car2' has no len() — __getattr__ not consulted!

# Fix: explicitly forward dunders you need:
class Car3:
    def __init__(self, engine): self._engine = engine
    def __getattr__(self, name): return getattr(self._engine, name)
    def __len__(self): return len(self._engine)

# 2. hasattr / getattr trigger __getattr__ — be intentional about AttributeError
# 3. Type checkers can't see __getattr__ forwarding — use Protocol or explicit stubs
```

### 4.3 Level 3 — `__getattr__` with Caching and Introspection

```python
class DelegatingCar:
    """Car that delegates to Engine but caches the lookup and preserves metadata."""
    def __init__(self, engine: Engine) -> None:
        self._engine = engine

    def __getattr__(self, name: str):
        attr = getattr(self._engine, name)
        # Cache on the instance so next access is direct (avoids re-delegation)
        # Only safe if engine never changes; otherwise skip caching
        object.__setattr__(self, name, attr)
        return attr

    def __dir__(self):
        # Make dir() and tab-completion see delegated members
        return sorted(set(super().__dir__() + dir(self._engine)))
```

### 4.4 `functools.wraps`-style forwarding vs inheritance — A side-by-side

```python
# Inheritance: 3 lines, invisible coupling
class SportsCar(Engine):
    def drive(self): print("vroom")

# Composition with __getattr__: explicit, interceptable, swappable
class SportsCar2:
    def __init__(self, engine: Engine): self._engine = engine
    def drive(self): print("vroom")
    def __getattr__(self, name): return getattr(self._engine, name)
```

Pick the second when `SportsCar` is not *really* an `Engine`.

## 5. Refactoring — From Inheritance Hierarchy to Composition

This is the canonical skill: recognizing when a hierarchy is screaming for composition and systematically extracting it.

### 5.1 The Before — Inheritance Gone Wild

**Domain:** A document-processing pipeline that supports multiple storage backends and multiple export formats. A junior design uses inheritance:

```python
# ---- BEFORE: inheritance tree ----
class Document:
    def __init__(self, title: str, content: str) -> None:
        self.title = title
        self.content = content

    def save(self) -> None:
        raise NotImplementedError

    def export(self) -> str:
        raise NotImplementedError

class TextDocument(Document):
    def save(self) -> None:
        with open(f"{self.title}.txt", "w") as f:
            f.write(self.content)

    def export(self) -> str:
        return self.content

class PdfDocument(Document):
    def save(self) -> None:
        # imagine PDF writing
        print(f"[PDF] saving {self.title}")

    def export(self) -> str:
        return f"%PDF {self.content}"

class TextDocumentOnS3(TextDocument):
    def save(self) -> None:
        print(f"[S3] uploading {self.title}.txt")

class PdfDocumentOnS3(PdfDocument):
    def save(self) -> None:
        print(f"[S3] uploading {self.title}.pdf")

# Adding HTML export? Need HTMLDocument, HTMLDocumentOnS3 — combinatorial explosion!
# 2 formats x 2 storages = 4 classes. 3 formats x 3 storages = 9 classes.
```

**Problems visible:**

* **Cartesian product explosion** — each new format × storage multiplies classes.
* **Duplicated save logic** — `TextDocumentOnS3` and `PdfDocumentOnS3` duplicate S3 logic.
* **Cannot mix at runtime** — a document's storage is fixed by its class.
* **Violates OCP** (Open-Closed Principle) — adding a `DatabaseStorage` requires new subclasses for every format.

### 5.2 The After — Composition with Strategy Objects

Extract the varying axes into **independent collaborators** injected at construction:

```python
from __future__ import annotations
from typing import Protocol
from dataclasses import dataclass
import pathlib

# ---- Collaborator 1: Storage strategy ----
class Storage(Protocol):
    def save(self, title: str, data: bytes) -> None: ...

class LocalStorage:
    def __init__(self, directory: pathlib.Path = pathlib.Path(".")) -> None:
        self.directory = directory

    def save(self, title: str, data: bytes) -> None:
        path = self.directory / title
        path.write_bytes(data)
        print(f"[LocalStorage] wrote {path} ({len(data)} bytes)")

class S3Storage:
    def __init__(self, bucket: str) -> None:
        self.bucket = bucket

    def save(self, title: str, data: bytes) -> None:
        # stub — real code would call boto3
        print(f"[S3Storage] s3://{self.bucket}/{title} ({len(data)} bytes)")

# ---- Collaborator 2: Export strategy ----
class Exporter(Protocol):
    def export(self, content: str) -> bytes: ...

class TextExporter:
    def export(self, content: str) -> bytes:
        return content.encode("utf-8")

class PdfExporter:
    def export(self, content: str) -> bytes:
        # stub — real code would use reportlab
        return f"%PDF-1.4\n{content}\n%%EOF".encode("utf-8")

class HtmlExporter:
    def export(self, content: str) -> bytes:
        return f"<html><body>{content}</body></html>".encode("utf-8")

# ---- Core: Document COMPOSED of strategies ----
@dataclass
class Document:
    title: str
    content: str
    storage: Storage
    exporter: Exporter

    def save(self) -> None:
        data = self.exporter.export(self.content)
        self.storage.save(self.title, data)

    def export(self) -> bytes:
        return self.exporter.export(self.content)

# ---- Usage — mix and match at runtime ----
doc1 = Document("report", "Hello world",
                storage=LocalStorage(), exporter=TextExporter())

doc2 = Document("report", "Hello world",
                storage=S3Storage("my-bucket"), exporter=PdfExporter())

doc3 = Document("report", "Hello world",
                storage=S3Storage("my-bucket"), exporter=HtmlExporter())

for doc in (doc1, doc2, doc3):
    doc.save()

# Swap exporter at runtime — impossible with inheritance:
doc1.exporter = HtmlExporter()
doc1.save()  # now saves as HTML to local storage
```

**What improved:**

* **No explosion** — `3 exporters × 2 storages = 6 combinations` with **zero** combinatorial classes — just 6 object configurations.
* **Single responsibility** — `Document` orchestrates; `Storage` handles persistence; `Exporter` handles formatting.
* **Open-closed** — add `DatabaseStorage` or `MarkdownExporter` without touching `Document`.
* **Testability** — inject `FakeStorage` that records saves in memory.
* **Runtime flexibility** — swap `doc.storage` after construction.

### 5.3 Refactoring Steps — A Repeatable Recipe

1. **Identify axes of variation** — what changes together vs independently? In our example: storage and format vary independently → two axes.
2. **Extract each axis into a Protocol / ABC** — defines the contract without inheritance.
3. **Create concrete strategy classes** — one per variant (e.g., `S3Storage`).
4. **Rewrite the original class to hold references** — `self.storage`, `self.exporter`.
5. **Delegate** — replace `self.save_s3_logic()` with `self.storage.save(...)`.
6. **Wire in constructors / factories** — dependency injection at creation time.
7. **Delete the hierarchy** — remove the now-empty subclasses.

> **Python tip:** Use `typing.Protocol` (structural subtyping) for strategy interfaces. Unlike `abc.ABC`, `Protocol` does not require inheritance to type-check — any object with a matching `save` method passes. This keeps composition lightweight.

### 5.4 When `__getattr__` Would Be Overkill Here

The `Document` example uses **explicit delegation** (`self.storage.save(...)`). We did *not* use `__getattr__` because:

* `Document` has only two methods to forward (`save`-like) — manual forwarding is clearer.
* Forwarding everything would expose `bucket`, `directory`, etc. — leaking internals.
* Explicit methods document the `Document` API for readers and type checkers.

Reserve `__getattr__` for **transparent proxies** (e.g., an ORM lazy wrapper) where the wrapper should look *exactly* like the wrapped object.

## 6. When Inheritance *Is* Warranted

Composition is the default, not a dogma. Inheritance earns its keep when **all** of these hold:

### 6.1 The Checklist

| Condition | Why it matters | Example |
|---|---|---|
| **True `is-a`** | Substitution must be valid everywhere the base is used | `SavingsAccount is-a BankAccount` |
| **Interface + behavior reuse** | You inherit to share a contract AND its implementation | `collections.abc.MutableMapping` → `dict`-like class |
| **Shared invariants** | Base class enforces rules all children must follow | `Animal` requiring `weight > 0` |
| **Framework demands it** | Some frameworks (Django models, `unittest.TestCase`) require subclassing | `class MyTest(unittest.TestCase)` |
| **No composition gain** | Composition would add indirection without flexibility | Simple value types with one variation axis |

### 6.2 Legitimate Inheritance Example — Template Method

```python
from abc import ABC, abstractmethod

class DataParser(ABC):
    """Template method: subclasses fill in ONE step, base controls the algorithm."""

    def parse(self, raw: str):
        cleaned = self._clean(raw)       # shared logic
        records = self._tokenize(cleaned)  # delegated to subclass
        return self._validate(records)   # shared logic

    def _clean(self, raw: str) -> str:
        return raw.strip()

    def _validate(self, records: list) -> list:
        if not records:
            raise ValueError("no records parsed")
        return records

    @abstractmethod
    def _tokenize(self, cleaned: str) -> list:
        ...

class CsvParser(DataParser):
    def _tokenize(self, cleaned: str) -> list:
        import csv, io
        return list(csv.reader(io.StringIO(cleaned)))

class JsonParser(DataParser):
    def _tokenize(self, cleaned: str) -> list:
        import json
        return json.loads(cleaned)

# Composition alternative would be awkward here — the algorithm skeleton IS the shared identity.
```

Here inheritance models a **single axis of variation** (tokenization strategy) *within* a fixed algorithm. The base class is an **abstract skeleton** — not a concrete thing you would compose around. Still, note: you could also refactor `_tokenize` into a strategy object. Inheritance wins here because the variation is one method and the base class is not supposed to be instantiated alone.

### 6.3 Legitimate Inheritance — Mixins (Carefully)

```python
class JsonMixin:
    """Mixin: adds JSON serialization to any class with __dict__."""
    def to_json(self) -> str:
        import json
        return json.dumps(self.__dict__, default=str)

class TimestampMixin:
    """Mixin: adds creation timestamp."""
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        from datetime import datetime, timezone
        self.created_at = datetime.now(timezone.utc)

# Mixin composition via multiple inheritance — the ONE place MI is idiomatic:
class AuditedRecord(TimestampMixin, JsonMixin):
    def __init__(self, title: str) -> None:
        super().__init__()
        self.title = title

rec = AuditedRecord("hello")
print(rec.to_json())
print(rec.created_at)
```

**Mixin rules in Python:**

* Mixins should be **small**, **focused**, and **not instantiable alone**.
* They should not carry essential state that collides (`__init__` must be cooperative via `super()`).
* Order matters — put mixins **before** the main base in the MRO.
* Prefer composition if the mixin needs significant state — mixins with state are the hardest to reason about.

### 6.4 Inheriting from Standard Library ABCs

```python
from collections.abc import MutableMapping

# You MUST inherit to be recognized as a mapping by isinstance checks
# in code that does `isinstance(x, MutableMapping)`.
class CaseInsensitiveDict(MutableMapping):
    def __init__(self):
        self._data: dict[str, str] = {}

    def __getitem__(self, key): return self._data[key.lower()]
    def __setitem__(self, key, value): self._data[key.lower()] = value
    def __delitem__(self, key): del self._data[key.lower()]
    def __iter__(self): return iter(self._data)
    def __len__(self): return len(self._data)
```

Here inheritance is required for **registration** with the ABC ecosystem. Even then, you *compose* internally (`self._data` is a dict) — you inherit the *interface*, not the *implementation* of `dict`.

## 7. LSP Preview — Why Inheritance Demands Substitutability

The **Liskov Substitution Principle** (covered fully in 11.3) is the law that makes inheritance honest:

> *If `S` is a subtype of `T`, objects of type `T` may be replaced with objects of type `S` without altering the correctness of the program.*

Inheritance **promises** LSP. Composition **does not need to** — there is no subtype claim.

### 7.1 Violating LSP with Inheritance

```python
class Rectangle:
    def __init__(self, width: float, height: float) -> None:
        self.width = width
        self.height = height

    def set_width(self, w: float) -> None:  self.width = w
    def set_height(self, h: float) -> None: self.height = h
    def area(self) -> float: return self.width * self.height

class Square(Rectangle):
    """Square IS-A Rectangle? Mathematically yes, behaviorally NO."""
    def set_width(self, w: float) -> None:
        self.width = self.height = w
    def set_height(self, h: float) -> None:
        self.width = self.height = h

def scale_rectangle(rect: Rectangle) -> None:
    rect.set_width(5)
    rect.set_height(4)
    assert rect.area() == 20  # passes for Rectangle, FAILS for Square (16)!

scale_rectangle(Rectangle(2, 3))  # OK
scale_rectangle(Square(2, 2))     # AssertionError — LSP violated
```

**Diagnosis:** `Square` cannot be substituted for `Rectangle` without breaking callers. The inheritance is semantically wrong. Fix with composition or separate classes:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Rectangle:
    width: float
    height: float
    def area(self) -> float: return self.width * self.height

@dataclass(frozen=True)
class Square:
    side: float
    def area(self) -> float: return self.side ** 2
    def to_rectangle(self) -> Rectangle:
        return Rectangle(self.side, self.side)  # conversion, not inheritance
```

### 7.2 How Composition Avoids LSP Pressure

```python
class Bird:
    def fly(self): print("flapping")

class Ostrich:
    def __init__(self):
        self._bird = Bird()  # composition — no false promise

    def run(self): print("running at 70 km/h")
    # No fly() method — callers can't assume fly() exists.

# Code expecting a Bird will not accidentally receive an Ostrich.
# If you DO need polymorphism, make the capability explicit:
from typing import Protocol

class Flyer(Protocol):
    def fly(self) -> None: ...

def make_it_fly(f: Flyer) -> None:
    f.fly()  # only Flyers accepted — Ostrich correctly excluded
```

> **Takeaway:** Before inheriting, ask: *"Can I substitute the child everywhere the parent is expected, without `if isinstance` checks or changed behavior?"* If the answer is no — or "only sometimes" — use composition.

## 8. Python-Specific Gotchas and Idioms

### 8.1 Inheriting from Built-ins Is Tricky

```python
# Subtle bug: inheriting from set — __init__ and mutation methods have C-level shortcuts
class SortedSet(set):
    def __init__(self, iterable=None):
        super().__init__(iterable or [])
        # set.__init__ may bypass your overridden add/update!
    def add(self, item):
        print(f"adding {item}")
        super().add(item)

s = SortedSet([3, 1, 2])
s.add(4)         # prints "adding 4" — OK
s.update([5, 6]) # does NOT print per-item — C-level update bypasses add()
# len(s) still works but set internals are opaque
```

**Solution:** Use `collections.UserList` / `UserDict` / `UserSet` or compose with a `set` internally. They are Python-level wrappers without C shortcuts.

### 8.2 Cooperative `super()` — Only Works When Everyone Cooperates

```python
class A:
    def __init__(self, **kwargs):
        print("A.__init__")
        super().__init__(**kwargs)

class B:
    def __init__(self, **kwargs):
        print("B.__init__")
        super().__init__(**kwargs)

class C(A, B):
    def __init__(self):
        print("C.__init__")
        super().__init__()

C()  # C -> A -> B -> object — works because ALL call super().__init__
# If ANY class in the chain omits super().__init__, the chain breaks.
```

Composition has no such global coordination requirement.

### 8.3 `isinstance` and `issubclass` Checks — Inheritance Entangles Types

```python
class Engine: pass
class ElectricEngine(Engine): pass

class Car:
    def __init__(self, engine: Engine): self.engine = engine

# With inheritance, type checks proliferate:
def service(vehicle):
    if isinstance(vehicle, ElectricEngine):
        print("check battery")
    elif isinstance(vehicle, Engine):
        print("check oil")

# With composition, dispatch is on the component:
def service_composed(car: Car):
    if isinstance(car.engine, ElectricEngine):
        print("check battery")
    # Still a check, but isolated to the engine — Car doesn't need subclasses
```

Better yet, use polymorphism on the component:

```python
class Engine(Protocol):
    def service(self) -> None: ...

class GasEngine:
    def service(self): print("check oil")

class ElectricEngine:
    def service(self): print("check battery")

class Car:
    def __init__(self, engine: Engine): self.engine = engine
    def service(self): self.engine.service()  # no isinstance needed
```

### 8.4 Dataclasses and Composition — A Natural Fit

```python
from dataclasses import dataclass

@dataclass
class Address:
    street: str
    city: str

@dataclass
class Person:
    name: str
    address: Address  # composition — Person HAS an Address

    def move_to(self, new_address: Address) -> None:
        self.address = new_address  # swap component at runtime

p = Person("Alice", Address("123 Main", "Springfield"))
p.move_to(Address("456 Oak", "Shelbyville"))
```

Dataclasses make composition almost free — type hints document the relationship, and you get `__init__`, `__repr__`, `__eq__` for nothing.

## 9. Side-by-Side Decision Table

| Question to ask | If **yes** → | If **no** → |
|---|---|---|
| Is there a true `is-a` relationship valid in all contexts? | Consider inheritance | Prefer composition |
| Do you need substitutability (LSP) for polymorphism? | Inherit from ABC/Protocol | Use composition + duck typing |
| Are there multiple independent variation axes? | Inheritance will explode — use composition | Single axis might tolerate inheritance |
| Do you need to reuse only *some* of the parent's interface? | Composition — don't inherit what you won't support | Inherit if you want the whole interface |
| Will the parent class change over time (library code)? | Composition insulates you | Inheritance couples you |
| Do you need to swap behavior at runtime? | Composition — swap `self.strategy` | Inheritance is static |
| Do you need to mock the dependency in tests? | Composition — inject a fake | Inheritance requires subclassing/mocking parent |
| Does a framework require subclassing? | Inherit (you have no choice) | — |
| Is the hierarchy deeper than 2 levels? | Refactor to composition | — |

### Quick heuristic (from *Effective Python* & *Python Tricks*)

> **"Inheritance is for sharing an interface; composition is for sharing implementation."**
>
> If you want to say *"You can use me wherever they can be used"* → inheritance (or Protocol).
> If you want to say *"I reuse their code internally"* → composition.

## 10. Edge Cases and Advanced Patterns

### 10.1 Delegation with `__getattr__` vs Explicit — When Each Wins

```python
# EXPLICIT — API is curated, documented, type-checkable
class AudioPlayer:
    def __init__(self, decoder): self._decoder = decoder
    def play(self, data: bytes): return self._decoder.decode(data)
    def stop(self): self._decoder.stop()

# __getattr__ — API is fully transparent, like a proxy
class AudioPlayerProxy:
    def __init__(self, decoder): self._decoder = decoder
    def log_play(self, data: bytes):
        print("playing...")
        return self._decoder.decode(data)
    def __getattr__(self, name): return getattr(self._decoder, name)
    # Now AudioPlayerProxy has decode(), stop(), seek(), volume, ...
    # without listing them — useful for decorators/proxies.
```

### 10.2 Composition Can Still Create Cycles

```python
class Node:
    def __init__(self, name: str, parent: "Node | None" = None) -> None:
        self.name = name
        self.parent = parent  # composition — Node HAS a parent
        self.children: list["Node"] = []
        if parent:
            parent.children.append(self)  # cycle: parent -> child -> parent

# Python's GC handles reference cycles, but __del__ and weak refs matter — see 11.2.
```

### 10.3 Runtime Strategy Swapping

```python
class PaymentProcessor:
    def __init__(self, strategy): self.strategy = strategy
    def pay(self, amount: float): return self.strategy.pay(amount)

class StripeStrategy:
    def pay(self, amount): print(f"Stripe ${amount}")

class PayPalStrategy:
    def pay(self, amount): print(f"PayPal ${amount}")

proc = PaymentProcessor(StripeStrategy())
proc.pay(100)              # Stripe $100
proc.strategy = PayPalStrategy()  # swap at runtime
proc.pay(100)              # PayPal $100
# Impossible with inheritance without creating a new object.
```

### 10.4 Testing Composition vs Inheritance

```python
# Composition: trivial to test with fakes
class FakeEngine:
    def __init__(self): self.started = False
    def start(self): self.started = True

def test_car_starts_engine():
    fake = FakeEngine()
    car = Car(fake)
    car.start()
    assert fake.started

# Inheritance: must mock the parent or subclass further
class CarInherits(Engine):
    def start(self): super().start()

def test_car_inherits():
    # How to verify Engine.start was called without a real engine side effect?
    # Need unittest.mock.patch — more ceremony, more brittle.
    from unittest.mock import patch
    with patch.object(Engine, "start") as mock:
        CarInherits().start()
        mock.assert_called_once()
```

### 10.5 The `super()` Trap in Deep Hierarchies

```python
class Base:
    def save(self): print("Base.save")

class MixinA(Base):
    def save(self):
        print("MixinA.save start")
        super().save()
        print("MixinA.save end")

class MixinB(Base):
    def save(self):
        print("MixinB.save start")
        super().save()
        print("MixinB.save end")

class Combined(MixinA, MixinB):
    pass

Combined().save()
# MixinA -> MixinB -> Base — order determined by MRO, NOT by the order you think.
# With composition: save order is explicit — self.a.save(); self.b.save()
```

## 11. Summary — The Pythonic Default

* **Inheritance** means `is-a` + shared identity + MRO coupling + LSP obligation. It is powerful when you truly model a taxonomy or must integrate with an inheritance-based framework.
* **Composition** means `has-a` + delegation + runtime wiring. It is flexible, testable, explicit, and resistant to base-class changes.
* **Python prefers composition** because duck typing already gives you polymorphism without type hierarchies, and because `self.part.method()` is more explicit than `super().method()`.
* When you do delegate heavily, choose **explicit forwarding** for curated APIs and **`__getattr__` forwarding** for transparent proxies — understanding that `__getattr__` only fires after normal lookup fails and does not intercept dunder methods.
* Before inheriting, run the checklist: true `is-a`? Need substitutability? Single axis? No explosion? If any answer is uncomfortable, compose.
* The LSP preview: inheritance that violates substitutability is a bug, not a design. See 11.3 for the full principle with Python enforcement techniques (`abc.ABC`, `Protocol`, `isinstance` contracts).

> **One-line takeaway:** *Inherit to be something; compose to have something. In Python, you more often need to *have* than to *be*.*
