# 01.2 Typing: Dynamic, Strong, Gradual, and Duck

> **One-line summary:** Python is *dynamically* typed (types live on objects, checked at runtime) and *strongly* typed (never silently coerces unrelated types), with an optional *gradual* static layer via type hints that tools — not the runtime — enforce.

If you come from Java/C# (static + strong) or JavaScript (dynamic + weak), Python occupies a third quadrant: dynamic + strong. This lesson explains what that means mechanically, how it shapes the way you write code, and how the modern gradual-typing ecosystem (`mypy`, `pyright`, `typing`) layers static checks on top without changing runtime behaviour.

---

## 1. Static vs Dynamic — When Are Types Checked?

| Dimension | Static typing (Java, Rust, Go) | Dynamic typing (Python, Ruby, JS) |
|---|---|---|
| **Type lives on** | Variable / declaration | Object / value |
| **Checked when** | Compile time | Runtime (when the operation executes) |
| **Variable can hold** | Only its declared type | Any type over its lifetime |
| **Error for mismatch** | Compiler error before running | `TypeError` at runtime |

### In Python, types belong to objects, not names

```python
# A name has no fixed type — it can point at any object over time.
x = 42            # x → int object
print(type(x))    # <class 'int'>

x = "hello"       # x now → str object (rebound, no error)
print(type(x))    # <class 'str'>

x = [1, 2, 3]     # x now → list object
print(type(x))    # <class 'list'>

# Even within a single function, a parameter can receive any type:
def describe(value):
    print(f"value={value!r}, type={type(value).__name__}")

describe(42)        # value=42, type=int
describe("hello")   # value='hello', type=str
describe([1, 2])    # value=[1, 2], type=list
```

Contrast with a statically typed language where `int x = 42; x = "hello";` is a compile error. In Python there is no declaration step that locks `x` to `int`.

### Types are checked at the operation, not the assignment

```python
# Assignment always succeeds — Python does not check whether the value
# "makes sense" for future use.
name = 42       # perfectly legal, even if `name` suggests a string
count = "oops"  # also legal

# The error appears only when you USE the value in a type-specific way.
# This is "late binding" of type errors.
try:
    result = name.upper()   # int has no .upper() → AttributeError at runtime
except AttributeError as e:
    print(f"AttributeError: {e}")

try:
    total = count + 10      # str + int → TypeError at runtime
except TypeError as e:
    print(f"TypeError: {e}")
```

> **Mental model:** Think of Python names as untyped sockets. You can plug any object into any socket. The mismatch is discovered only when you try to draw power — i.e., call a method or operator that the object does not support.

## 2. Strong vs Weak — Does the Language Silently Coerce?

| Dimension | Strong typing (Python, Ruby) | Weak typing (JavaScript, Perl, C) |
|---|---|---|
| **Implicit coercion** | Minimal — refuses most mixed-type ops | Extensive — silently converts |
| **`"5" + 3`** | `TypeError` | `"53"` (JS) or `8` (Perl) |
| **`"5" * 3`** | `"555"` (but this is `str.__mul__`, not coercion) | `15` or `"555"` depending on language |
| **Truthiness coercion** | Explicit `bool()` / `if` context only | Many contexts coerce automatically |

### Python refuses implicit nonsense

```python
# JavaScript: "5" + 3 === "53"  (number coerced to string silently)
# Python: hard error — you must be explicit.
try:
    result = "5" + 3
except TypeError as e:
    print(f"TypeError: {e}")
    # unsupported operand type(s) for +: 'int' and 'str'

# You must convert explicitly:
print("5" + str(3))   # "53"
print(int("5") + 3)   # 8

# Same for other mixed operations:
try:
    print("hello" - "h")
except TypeError as e:
    print(f"TypeError: {e}")  # str doesn't support -

try:
    print([1, 2] + (3, 4))   # list + tuple — different types
except TypeError as e:
    print(f"TypeError: {e}")
```

### The one famous exception — `bool` is `int`, and `int`/`float` coerce

Python *does* allow numeric coercion within the numeric tower, and `bool` is a subclass of `int` (see Lesson 01.4). This is narrow and well-defined:

```python
# Numeric tower — int and float interoperate by design
print(3 + 4.5)       # 7.5 — int promoted to float
print(True + True)   # 2 — bool is int
print(True * 10)     # 10
print(isinstance(True, int))  # True — the famous wart

# But even numerics won't coerce strings:
try:
    print(3 + "4.5")
except TypeError as e:
    print(e)
```

> **Why "strong" matters:** Strong typing forces you to be explicit about conversions. Bugs that in JavaScript silently produce `"53"` or `NaN` become loud `TypeError`s in Python — failing fast at the point of the mistake.

## 3. The Four Quadrants — Where Python Sits

```
                  Strong
                    │
       Python ──────┼────── Ruby
       Java         │        │
       C#           │        │
                    │        │
  Static ───────────┼─────────── Dynamic
                    │        │
       C            │      JavaScript
       Rust         │      Perl
       Go           │      PHP
                    │
                  Weak
```

- **Static + Strong (Java, C#):** Types on variables, checked at compile time, no silent coercion.
- **Dynamic + Strong (Python):** Types on objects, checked at runtime, no silent coercion.
- **Dynamic + Weak (JavaScript):** Types on values, checked at runtime, extensive silent coercion.
- **Static + Weak (C):** Types on variables, but the compiler allows many implicit conversions (and you can cast anything).

Python's combination gives you flexibility (no boilerplate declarations, heterogeneous containers) while still catching type mismatches loudly.

## 4. Duck Typing — "If It Walks Like a Duck..."

Because Python checks types at the operation site, it does not care *what* an object is — only *what it can do*. This philosophy is called **duck typing**: "If it walks like a duck and quacks like a duck, it's a duck."

### EAFP vs LBYL

Pythonic code tends toward **EAFP** (Easier to Ask Forgiveness than Permission) over **LBYL** (Look Before You Leap):

```python
# LBYL — check the type before acting (less Pythonic, brittle)
def read_data_lbyl(obj):
    if isinstance(obj, list):
        return obj[0]
    elif isinstance(obj, dict):
        return obj["key"]
    elif isinstance(obj, str):
        return obj.split()[0]
    else:
        raise TypeError("unsupported type")

# EAFP / duck typing — just try the operation, handle failure
def read_data_duck(obj):
    """Works with ANY object that supports the needed protocol."""
    try:
        # Try dict-like access first
        return obj["key"]
    except (KeyError, TypeError):
        pass
    try:
        # Fall back to sequence access
        return obj[0]
    except (IndexError, TypeError, KeyError):
        raise TypeError(f"Cannot read from {type(obj).__name__!r}")

# Both work, but the duck-typed version handles novel types for free:
class CustomStore:
    def __getitem__(self, key):
        if key == "key":
            return "custom_value"
        raise KeyError(key)

print(read_data_duck(CustomStore()))  # custom_value — no isinstance check needed
```

### Protocols — The Formal Face of Duck Typing

Since Python 3.8, `typing.Protocol` lets you name the duck:

```python
from typing import Protocol

class Drawable(Protocol):
    """Any object with a .draw() -> None method satisfies Drawable."""
    def draw(self) -> None: ...

class Circle:
    def draw(self) -> None:
        print("Drawing a circle")

class TextLabel:
    def draw(self) -> None:
        print("Drawing text")

class Spreadsheet:
    def calculate(self) -> None:
        print("Calculating...")

def render(item: Drawable) -> None:
    item.draw()  # type checker ensures `item` has .draw()

render(Circle())      # OK
render(TextLabel())   # OK
# render(Spreadsheet())  # mypy/pyright error: Spreadsheet has no draw()
```

At runtime, `render` would still accept a `Spreadsheet` if you called it — the `Protocol` is only enforced by the static checker. This is the gradual-typing bridge.

### Duck Typing in the Standard Library

```python
# `len()` works on ANY object with __len__ — not just lists
print(len([1, 2, 3]))    # 3
print(len("hello"))      # 5
print(len({"a": 1}))     # 1

class MyContainer:
    def __len__(self):
        return 42

print(len(MyContainer()))  # 42 — duck typing in action

# `for x in obj` works on ANY object with __iter__
# `with obj` works on ANY object with __enter__/__exit__
# `obj[key]` works on ANY object with __getitem__
```

## 5. Introspection — `type()` vs `isinstance()`

### `type(obj)` — Exact Type

```python
x = True
print(type(x))              # <class 'bool'>
print(type(x) is bool)      # True
print(type(x) is int)       # False — exact match only, no inheritance
print(type(42) is int)      # True

# type() with three args creates a new type dynamically (rare, metaprogramming)
MyClass = type("MyClass", (object,), {"greet": lambda self: "hello"})
print(type(MyClass))        # <class 'type'>
print(MyClass().greet())    # hello
```

### `isinstance(obj, type)` — Inheritance-Aware

```python
print(isinstance(True, bool))   # True
print(isinstance(True, int))    # True — bool subclasses int!
print(isinstance(42, int))      # True
print(isinstance(42, bool))     # False — int is not bool
print(isinstance([], list))     # True
print(isinstance([], object))   # True — everything is an object

# isinstance supports tuples — "is it any of these?"
value = 3.14
print(isinstance(value, (int, float)))  # True — numeric check

# Prefer this over `type(x) in (int, float)` — handles subclasses correctly
class MyInt(int):
    pass

print(type(MyInt(5)) is int)       # False — misses subclass
print(isinstance(MyInt(5), int))   # True  — correct
```

### When to Use Each

| Use `isinstance()` | Use `type() is` |
|---|---|
| Almost always — respects inheritance | When you need to *exclude* subclasses |
| Validating inputs that may be subclassed | Serialization that must distinguish `bool` from `int` |
| Checking against ABCs / Protocols | Metaprogramming, exact-type dispatch |

```python
import numbers

# isinstance with Abstract Base Classes — checks the interface, not just lineage
print(isinstance(42, numbers.Integral))   # True
print(isinstance(3.14, numbers.Real))     # True
print(isinstance(42, numbers.Real))       # True — Integral is a Real

# type() cannot do this
print(type(42) is numbers.Integral)       # False — exact match fails

# Practical example — distinguishing bool from int
def process(value):
    # bool is int, so `isinstance(value, int)` matches True/False.
    # If you truly need to separate them:
    if type(value) is bool:   # exact check — only bool
        print("it's a bool")
    elif isinstance(value, int):
        print("it's an int (not bool)")

process(True)   # it's a bool
process(42)     # it's an int (not bool)
```

### `issubclass()` — The Class-Level Analogue

```python
print(issubclass(bool, int))    # True
print(issubclass(int, object))  # True
print(issubclass(list, object)) # True
```

## 6. Gradual Typing — Type Hints Are Not Enforced at Runtime

Since Python 3.5 (PEP 484), you can annotate types. These hints are **ignored at runtime** — they are metadata for tools, IDEs, and humans.

### Basic Syntax

```python
# Variable annotations
name: str = "Alice"
count: int = 42
price: float = 19.99

# Function annotations
def greet(name: str) -> str:
    return f"Hello, {name}"

def add(a: int, b: int) -> int:
    return a + b

# Class annotations
class User:
    name: str
    age: int

    def __init__(self, name: str, age: int) -> None:
        self.name = name
        self.age = age

# Python does NOT enforce these — all of this runs fine:
greet(42)           # no runtime error, even though 42 is not str
add("a", "b")      # returns "ab" — str.__add__ works, no TypeError from hints
name: str = 12345   # no error — annotation is just a hint
print(name)         # 12345
```

### Why "Gradual"?

- You can add hints incrementally — one function, one file at a time.
- Unhinted code is treated as `Any` (compatible with everything).
- You can mix typed and untyped code freely.

### The `typing` Module — Building Blocks

```python
from typing import Optional, Union, Any, List, Dict, Callable, Sequence

# Optional[X] means X | None (i.e., Union[X, None])
def find_user(user_id: int) -> Optional[str]:
    if user_id == 1:
        return "Alice"
    return None

# Union — value can be one of several types
def parse_value(raw: str) -> Union[int, float, str]:
    try:
        return int(raw)
    except ValueError:
        try:
            return float(raw)
        except ValueError:
            return raw

# Any — compatible with every type (escape hatch)
def debug(value: Any) -> None:
    print(f"debug: {value!r} (type={type(value).__name__})")

debug(42)
debug("hello")
debug([1, 2, 3])

# Modern syntax (Python 3.10+): use X | Y instead of Union[X, Y]
# and X | None instead of Optional[X]
def find_user_modern(user_id: int) -> str | None:
    if user_id == 1:
        return "Alice"
    return None

def parse_modern(raw: str) -> int | float | str:
    return parse_value(raw)

# Callable — for function arguments
from collections.abc import Callable

def apply(func: Callable[[int], str], value: int) -> str:
    return func(value)

print(apply(str, 42))  # "42"

# Generics — containers with element types
from collections.abc import Sequence, Mapping

def total(scores: Sequence[int]) -> int:
    return sum(scores)

print(total([90, 85, 92]))   # 267
print(total((10, 20, 30)))   # 60 — tuple is also a Sequence
```

### `Any` — The Top Type

- `Any` is compatible with every type and every type is compatible with `Any`.
- Using `Any` effectively disables type checking for that value — use it sparingly.
- `object` is similar but stricter: you can pass anything *to* `object`, but you cannot call arbitrary methods on it without narrowing.

```python
from typing import Any

def with_any(x: Any) -> None:
    # No error — Any lets you do anything
    print(x.foo.bar.baz())  # type checker says OK (but may fail at runtime)

def with_object(x: object) -> None:
    # Error from checker — object has no attribute `foo`
    # print(x.foo)  # mypy: "object" has no attribute "foo"
    # You must narrow first:
    if isinstance(x, str):
        print(x.upper())  # OK — narrowed to str
```

### Runtime Cost — Zero

```python
import dis

def annotated(x: int) -> int:
    return x * 2

def unannotated(x):
    return x * 2

# Annotations are stored in __annotations__ but don't affect bytecode
print(annotated.__annotations__)    # {'x': <class 'int'>, 'return': <class 'int'>}
print(unannotated.__annotations__)  # {}

# The bytecode is identical (minus annotation storage)
# dis.dis(annotated) and dis.dis(unannotated) produce the same core instructions.
```

## 7. How Type Checkers Use Hints

```
  Your code (.py) ──►  mypy / pyright / pyre ──► errors & warnings
         │
         ▼
     Python runtime ──► ignores all hints, runs normally
```

```python
# example.py
def average(scores: list[int]) -> float:
    return sum(scores) / len(scores)

# This passes at runtime but fails type checking:
result = average("hello")  # runtime: TypeError (str has no len? actually it does,
                           # but sum("hello") fails). Checker catches it statically.

# Running the checker:
# $ mypy example.py
# error: Argument 1 to "average" has incompatible type "str"; expected "list[int]"

# Or with pyright (used by Pylance in VS Code) — same idea, real-time feedback.
```

### Strictness Levels

```python
# mypy.ini / pyproject.toml can configure strictness:
# [tool.mypy]
# strict = true           # all checks on
# disallow_untyped_defs = true  # require annotations on every function
# warn_return_any = true

# pyright has similar: typeCheckingMode = "strict" | "basic" | "off"
```

## 8. Common Mistakes and Misconceptions

### Mistake 1 — Expecting Hints to Prevent Runtime Errors

```python
def divide(a: int, b: int) -> float:
    return a / b

# Hints suggest int, but nothing stops you from passing strings at runtime:
try:
    print(divide("10", "2"))  # TypeError at runtime — hints didn't prevent it
except TypeError as e:
    print(f"TypeError: {e}")

# If you need runtime enforcement, add explicit checks or use a library:
def divide_safe(a: int, b: int) -> float:
    if not isinstance(a, (int, float)) or not isinstance(b, (int, float)):
        raise TypeError(f"Expected numbers, got {type(a).__name__}, {type(b).__name__}")
    return a / b

# Or use pydantic / beartype / typeguard for automatic runtime checking:
# from beartype import beartype
# @beartype
# def divide_checked(a: int, b: int) -> float:
#     return a / b
# divide_checked("10", "2")  # beartype raises BeartypeCallHintParamViolation
```

### Mistake 2 — Using `type(x) == SomeType` Instead of `isinstance`

```python
# Fragile — breaks for subclasses
def is_number_bad(x):
    return type(x) == int or type(x) == float  # misses bool, numpy types, subclasses

# Robust — respects inheritance and ABCs
def is_number_good(x):
    return isinstance(x, (int, float))

# Even better — use the numeric tower ABC
import numbers
def is_number_best(x):
    return isinstance(x, numbers.Number)
```

### Mistake 3 — Thinking `list` and `List` Are the Same

```python
# Python 3.9+: built-in generics work directly
scores: list[int] = [1, 2, 3]       # preferred in 3.9+
mapping: dict[str, int] = {"a": 1}

# Older style (still valid, needed for 3.8 and below)
from typing import List, Dict
scores_old: List[int] = [1, 2, 3]
mapping_old: Dict[str, int] = {"a": 1}

# At runtime, list[int] and List[int] are just hints — no difference in behaviour.
```

### Mistake 4 — Confusing `Any` with `object`

```python
from typing import Any

def handle_any(x: Any):
    x.anything_goes()  # checker allows it — Any is unchecked

def handle_object(x: object):
    # x.anything_goes()  # checker ERROR — object is checked
    # Must narrow first:
    if isinstance(x, str):
        print(x.upper())  # OK
```

## 9. Realistic Example — Typed Data Pipeline

```python
from __future__ import annotations  # defer annotation evaluation (PEP 563)

from collections.abc import Callable, Sequence
from typing import Any

# --- Domain types ---
RawRecord = dict[str, Any]
CleanRecord = dict[str, str | int | float]

def clean_record(raw: RawRecord) -> CleanRecord | None:
    """
    Validate and clean a raw record.
    Returns None if the record is invalid — caller must handle it.
    Demonstrates Optional via X | None, duck typing, and gradual typing.
    """
    # Duck typing — we don't check `isinstance(raw, dict)` strictly;
    # we just try to use it as a mapping.
    try:
        name = raw["name"]
        age = raw["age"]
    except KeyError as e:
        print(f"Missing field: {e}")
        return None

    # Strong typing in action — explicit coercion, no silent conversion
    if not isinstance(name, str):
        print(f"Bad name type: {type(name).__name__}")
        return None

    # Explicit conversion — Python won't coerce "42" to 42 automatically
    try:
        age_int = int(age)  # works for int, float, or numeric string
    except (ValueError, TypeError):
        print(f"Bad age value: {age!r}")
        return None

    return {"name": name.strip(), "age": age_int}

def process_records(
    records: Sequence[RawRecord],
    on_error: Callable[[RawRecord], None] | None = None,
) -> list[CleanRecord]:
    """Process a batch of records, optionally calling on_error for failures."""
    cleaned: list[CleanRecord] = []
    for raw in records:
        result = clean_record(raw)
        if result is not None:
            cleaned.append(result)
        elif on_error is not None:
            on_error(raw)
    return cleaned

# --- Usage — all of this type-checks with mypy/pyright ---
raw_data: list[RawRecord] = [
    {"name": " Alice ", "age": "30"},
    {"name": "Bob", "age": 25},
    {"name": "Charlie"},               # missing age
    {"name": 12345, "age": 40},        # bad name type
    {"name": "Diana", "age": "  28 "}, # string age — int() handles it
]

def log_error(record: RawRecord) -> None:
    print(f"  [error handler] bad record: {record}")

results = process_records(raw_data, on_error=log_error)
print(f"\nCleaned {len(results)} records:")
for r in results:
    print(f"  {r}")

# Output:
#   [error handler] bad record: {'name': 'Charlie'}
#   Bad name type: int
#     [error handler] bad record: {'name': 12345, 'age': 40}
#   Cleaned 3 records:
#     {'name': 'Alice', 'age': 30}
#     {'name': 'Bob', 'age': 25}
#     {'name': 'Diana', 'age': 28}

# --- The gradual part: untyped code interoperates ---
# An untyped function can still call our typed pipeline — no runtime barrier.
def legacy_loader():
    return [{"name": "Eve", "age": 22}]

print(process_records(legacy_loader()))  # works fine — hints don't block calls
```

## 10. Summary

| Concept | Python's Choice | What It Means |
|---|---|---|
| **When types are checked** | Dynamic (runtime) | Types live on objects; names can point at any type |
| **How strictly** | Strong | No silent coercion between unrelated types — `TypeError` instead of `NaN`/`"53"` |
| **Style** | Duck typing + EAFP | Care what an object *does*, not what it *is* |
| **Static analysis** | Gradual (opt-in) | Type hints are metadata for tools; runtime ignores them |
| **Introspection** | `isinstance()` preferred | Respects inheritance and ABCs; `type() is` only for exact matches |
| **`Any`** | Escape hatch | Disables checking for that value — use narrowly |

> **Key takeaway:** Python's dynamic + strong combination gives you the flexibility to write concise, generic code (duck typing, heterogeneous containers, no boilerplate declarations) while still failing loudly on type mismatches. The gradual typing layer adds IDE support and CI-time safety without changing runtime semantics — but remember: *hints are promises to humans and tools, not contracts enforced by the interpreter*. If you need runtime guarantees, add explicit `isinstance` checks or use a runtime enforcement library.
