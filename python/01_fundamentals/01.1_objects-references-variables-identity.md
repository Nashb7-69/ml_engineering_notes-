# 01.1 Objects, References, Variables, and Identity

> **Mental model:** In Python, variables are not boxes that contain values. They are *names* — sticky notes — attached to *objects* that live independently on a managed heap. Assignment moves the sticky note; it never copies the object.

This lesson dismantles the "variable as box" intuition you bring from C, Java, or Go, and replaces it with Python's uniform object-reference model. Every value you touch in Python is an object, every name is a reference, and understanding that distinction explains aliasing bugs, `is` vs `==`, `del` semantics, and garbage collection.

---

## 1. Everything Is an Object

In CPython (the reference implementation), literally every value is a `PyObject` in C — a heap-allocated structure carrying a type pointer, a reference count, and the payload.

```python
# All of these are objects — they have a type, an identity, and a value.
x = 42              # int object
s = "hello"         # str object
f = 3.14            # float object
lst = [1, 2, 3]     # list object
d = {"a": 1}        # dict object
func = lambda x: x  # function object
cls = int           # type object (classes are objects too)
none = None         # NoneType singleton object

# Objects carry metadata you can inspect:
print(type(x))   # <class 'int'>
print(id(x))     # 1400... — identity (memory address in CPython)
print(dir(x)[:5]) # attributes — even ints have methods
# Output: ['__abs__', '__add__', '__and__', ...]
```

Even constructs that look like "primitives" in other languages are full objects with methods:

```python
# ints have methods — because they are objects
n = 42
print(n.bit_length())   # 6
print((42).__class__)   # <class 'int'>
print((True).__doc__[:30])

# Functions and classes are objects too
def greet(name: str) -> str:
    return f"Hello, {name}"

print(type(greet))          # <class 'function'>
print(greet.__name__)       # 'greet'
print(hasattr(greet, "__code__"))  # True — functions carry their bytecode
```

**Why this matters:** Because everything is an object, everything lives on the heap, everything has identity, and uniform operations (`type()`, `id()`, `is`, attribute access) work on everything.

## 2. Variables Are Names — References to Objects

### The Name → Object Binding Model

When you write `x = 42`, Python does three things:

1. Creates (or finds) an `int` object with value `42`.
2. Creates a *name* `x` in the current namespace (if it does not already exist).
3. *Binds* the name `x` to that object — `x` now *refers to* the object.

There is no "variable slot containing 42." There is a name pointing at an object.

```python
# Assignment binds a name to an object.
x = 300
print(id(x))  # e.g. 140234567890

# Reassignment rebinds the SAME name to a DIFFERENT object.
# The old object is unaffected (unless nothing else refers to it, it gets GC'd).
x = 400
print(id(x))  # different — x now points elsewhere

# Multiple names can point to the SAME object (aliasing).
a = [1, 2, 3]
b = a              # b is NOT a copy — it is a second name for the same list
print(a is b)      # True — same object
print(id(a) == id(b))  # True
```

Visualise it:

```
# a = [1, 2, 3]; b = a

  Namespace              Heap
  ┌───────┐         ┌─────────────┐
  │ a ────┼────────►│ [1, 2, 3]   │
  │ b ────┼────────┘ └─────────────┘
  └───────┘     Two names, ONE object
```

### Assignment Never Copies, Never Declares

```python
# No declaration, no type annotation needed — just bind a name.
y = "hello"

# Assigning one name to another copies the REFERENCE, not the object.
original = [10, 20]
alias = original          # both names → same list
alias.append(30)
print(original)           # [10, 20, 30] — surprise if you expected a copy!

# To actually copy, be explicit:
import copy
shallow = original.copy()          # or list(original) or original[:]
deep = copy.deepcopy(original)     # for nested structures
print(shallow is original)         # False — different object
print(shallow == original)         # True  — equal contents
```

### Augmented Assignment — Subtle Distinction

```python
# For immutables, += creates a NEW object and rebinds.
n = 1000
print(id(n))
n += 1               # n = n + 1 → new int object, n rebound
print(id(n))         # different id

# For mutables, += mutates IN PLACE (when possible).
lst = [1, 2]
print(id(lst))
lst += [3, 4]        # calls lst.__iadd__ → mutates the same object
print(id(lst))       # SAME id — mutated in place!

# Contrast with lst = lst + [3, 4] which ALWAYS creates a new list.
lst2 = [1, 2]
old_id = id(lst2)
lst2 = lst2 + [3, 4]  # new list, rebinding
print(id(lst2) == old_id)  # False
```

> **Rule of thumb:** `x += y` tries `x.__iadd__(y)` first (in-place if available), falling back to `x = x + y`.

## 3. Identity: `id()` and `is`

### `id(object)` — The Identity

- Returns an integer that is guaranteed unique and constant for the object's lifetime.
- In CPython, `id()` returns the memory address of the `PyObject` — but **never rely on this**; other implementations (PyPy, Jython) return different values.
- Two objects with non-overlapping lifetimes *may* have the same `id()`.

```python
x = [1, 2, 3]
print(id(x))          # e.g. 140234567890123
print(hex(id(x)))     # hex address in CPython

# id is unique only while the object lives.
a = [1, 2]
id_a = id(a)
del a
b = [3, 4]
# id(b) COULD equal id_a — the old address was recycled.
```

### `is` — Identity Comparison

`a is b` is equivalent to `id(a) == id(b)` — it asks "are these the *same object* in memory?"

`a == b` asks "do these objects have *equal value*?" (calls `a.__eq__(b)`).

```python
# Two lists with equal contents but different identities
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)   # True  — same value
print(a is b)   # False — different objects
print(id(a) == id(b))  # False

# Same object via aliasing
c = a
print(a is c)   # True — same object
print(a == c)   # True

# Classic pitfall — string equality vs identity
s1 = "hello world!"   # longer strings are less likely interned
s2 = "hello world!"
# s1 == s2 is True, but s1 is s2 may be True or False depending on interning.
# NEVER use `is` to compare values — only for singletons (None, sentinel).
```

### When to Use `is` vs `==`

| Use `is` | Use `==` |
|---|---|
| `x is None` / `x is not None` | Value equality (`a == b`) |
| `x is other_singleton` | All other comparisons |
| Checking sentinel objects | Comparing numbers, strings, lists, etc. |

```python
# CORRECT — singleton check
if x is None:
    print("no value provided")

# WRONG — relies on identity for value comparison (fragile, may warn)
if x == None:          # works but unidiomatic; linter will flag
    pass
if s is "hello":       # NEVER do this — may appear to work due to interning
    pass               # then break in production

# The ONLY correct way to compare values:
if s == "hello":
    pass
```

## 4. Interning and Caching — Why `is` Sometimes "Works" for Values

Python interns (reuses) certain immutable objects as an optimisation. This is an **implementation detail** — never write code that depends on it.

### Small Integer Caching

CPython pre-allocates `int` objects for `-5` through `256` at startup. Any reference to a value in that range reuses the same object.

```python
# Small ints — same object (cached)
a = 100
b = 100
print(a is b)   # True — both point to the cached 100 object

# Large ints — NOT cached (usually different objects)
a = 1000
b = 1000
print(a is b)   # False in most contexts (but see below!)

# Edge: in a single code block / REPL line, the compiler may fold constants
a, b = 1000, 1000
print(a is b)   # May be True — compiler created one constant for the block!

# Demonstrate — even large ints can be `is`-identical due to constant folding
def foo():
    a = 1000
    b = 1000
    return a is b

print(foo())  # Often True — same code object, same constant

# But dynamically created large ints are distinct
a = int("1000")
b = int("1000")
print(a is b)  # False — constructed at runtime, different objects
```

### String Interning

- String literals that look like identifiers (`[a-zA-Z0-9_]*`) and short strings may be interned.
- Explicitly intern with `sys.intern()` for performance when you have many duplicate strings (e.g., parsing CSV columns).

```python
import sys

# Implicit interning — identifier-like strings
s1 = "hello_world"
s2 = "hello_world"
print(s1 is s2)  # Likely True — interned

# Strings with spaces/special chars — usually NOT interned
s1 = "hello world!"
s2 = "hello world!"
print(s1 is s2)  # Likely False (but not guaranteed!)

# Explicit interning for deduplication
a = sys.intern("some_dynamic_string_" + str(42))
b = sys.intern("some_dynamic_string_" + str(42))
print(a is b)  # True — explicitly interned
```

> **Takeaway:** `is` appearing to work for small ints/strings is an accident of caching. Code that uses `is` for value comparison is **buggy** — it will break when values leave the cached range or when the optimisation changes.

## 5. Mutable Aliasing Surprises

This is the single most common source of confusion for newcomers.

### Aliasing Through Assignment

```python
# List aliasing
original = [1, 2, 3]
alias = original        # alias → same list
alias.append(4)
print(original)         # [1, 2, 3, 4] — original mutated!

# Dict aliasing
config = {"host": "localhost", "port": 8080}
backup = config
backup["port"] = 9090
print(config["port"])   # 9090 — oops!

# Fix: explicit copy
safe_backup = config.copy()          # shallow copy — top-level keys copied
safe_backup["port"] = 3000
print(config["port"])                # 9090 — unaffected

# Shallow vs deep — nested mutables still shared
nested = {"a": [1, 2]}
shallow = nested.copy()
shallow["a"].append(99)
print(nested)  # {'a': [1, 2, 99]} — inner list is still shared!

import copy
deep = copy.deepcopy(nested)
deep["a"].append(100)
print(nested)  # {'a': [1, 2, 99]} — deep copy isolated the inner list
```

### Aliasing Through Function Arguments

```python
def add_item(item, target):
    """Appends item to target — MUTATES the caller's list."""
    target.append(item)

my_list = [1, 2, 3]
add_item(4, my_list)
print(my_list)  # [1, 2, 3, 4] — mutated!

# Defensive pattern — don't mutate arguments unless documented
def add_item_safe(item, target):
    """Returns a NEW list; does not mutate the input."""
    return target + [item]

my_list = [1, 2, 3]
new_list = add_item_safe(4, my_list)
print(my_list)   # [1, 2, 3] — unchanged
print(new_list)  # [1, 2, 3, 4]
```

### The Mutable Default Argument Pitfall

This deserves its own spotlight — it bites every Python programmer once:

```python
# BROKEN — default list is created ONCE at function definition time
def append_to(value, target=[]):
    target.append(value)
    return target

print(append_to(1))  # [1]
print(append_to(2))  # [1, 2] — surprise! Same list object reused
print(append_to(3))  # [1, 2, 3]

# Why? `target=[]` creates ONE list object when `def` executes.
# Each call without an argument reuses that same object.

# CORRECT — use None as sentinel
def append_to_fixed(value, target=None):
    if target is None:
        target = []          # new list each call
    target.append(value)
    return target

print(append_to_fixed(1))  # [1]
print(append_to_fixed(2))  # [1] — independent
print(append_to_fixed(2, target=[10]))  # [10, 2] — explicit list still works
```

The same trap applies to `dict` and `set` defaults, and to any mutable. The fix is always `None` + creation inside the function.

### Rebinding vs Mutating — The Critical Distinction

```python
def try_rebind(lst):
    lst = [99, 99, 99]   # rebinds LOCAL name `lst` — caller unaffected
    print(f"  inside try_rebind: {lst}")

def try_mutate(lst):
    lst.append(99)        # mutates the SHARED object — caller sees it
    print(f"  inside try_mutate: {lst}")

data = [1, 2, 3]
try_rebind(data)
print(f"after try_rebind: {data}")  # [1, 2, 3] — unchanged

try_mutate(data)
print(f"after try_mutate: {data}")  # [1, 2, 3, 99] — mutated
```

```
# try_rebind:  `lst` is a local name. `lst = [99,...]` points it at a new
#              list. The caller's name still points at the old list.
#
# try_mutate:  `lst.append(99)` follows the reference to the shared object
#              and mutates it. Both names see the change.
```

## 6. `del` — Deleting Names, Not Objects

`del` removes a *name* from its namespace. It does **not** necessarily destroy the object — the object lives as long as at least one reference exists.

```python
x = [1, 2, 3]
y = x              # two names, one list

del x              # removes name `x` from namespace
# print(x)         # NameError: name 'x' is not defined
print(y)           # [1, 2, 3] — object still alive via `y`

del y              # last reference gone — object now unreachable
                   # becomes eligible for garbage collection

# del can also remove items/attributes/slices
numbers = [10, 20, 30, 40]
del numbers[1]     # removes element at index 1
print(numbers)     # [10, 30, 40]

del numbers[0:2]   # slice deletion
print(numbers)     # [40]

info = {"a": 1, "b": 2}
del info["a"]
print(info)        # {'b': 2}

class Temp:
    value = 42

del Temp.value     # deletes class attribute
# print(Temp.value)  # AttributeError
```

> **Common misconception:** `del x` does not "free memory." It decrements the reference count by one. Memory is reclaimed only when the count reaches zero (or the cyclic GC collects it).

## 7. Garbage Collection — Reference Counting + Cycle Collector

### Reference Counting (Primary Mechanism)

Every object carries `ob_refcnt` — a count of names and containers pointing to it.

- **Incremented** when: a name is bound to it, it is added to a container, passed as an argument, etc.
- **Decremented** when: a name is rebound or deleted, a container is deleted, a scope exits.
- When `ob_refcnt` hits **zero**, the object is deallocated immediately (in CPython).

```python
import sys

a = [1, 2, 3]
print(sys.getrefcount(a))  # e.g. 2 — `a` + temporary arg to getrefcount
b = a
print(sys.getrefcount(a))  # 3 — `a`, `b`, + temp
del b
print(sys.getrefcount(a))  # 2 — back to `a` + temp

# You can watch refcount changes, but note getrefcount itself adds one.
x = object()
print(sys.getrefcount(x))  # 2
y = x
print(sys.getrefcount(x))  # 3
del y
print(sys.getrefcount(x))  # 2
```

> **Note:** `sys.getrefcount()` returns a value one higher than you expect because passing the object to the function creates a temporary reference.

### The Cycle Problem and `gc` Module

Reference counting alone cannot collect **reference cycles** — groups of objects that reference each other but are otherwise unreachable.

```python
# A reference cycle — neither list will reach refcount 0
a = []
b = []
a.append(b)   # a → b
b.append(a)   # b → a — cycle!
# Now a and b each have refcount >= 1 from the other

del a
del b
# Both lists are unreachable from any name, but refcount is still 1 each.
# → Refcount alone cannot free them.
```

CPython's **generational cyclic garbage collector** (`gc` module) periodically scans for such unreachable cycles and breaks them.

```python
import gc

# Inspect the collector
print(gc.isenabled())        # True by default
print(gc.get_threshold())    # (700, 10, 10) — generation thresholds
print(gc.get_count())        # current generation counts

# Force a collection
collected = gc.collect()
print(f"Collected {collected} unreachable objects")

# Objects with __del__ finalisers in cycles need special handling
# (Python 3.4+ uses gc to break most such cycles via weakref +
#  `__del__` is now less dangerous, but still avoid it in cyclic structures)

# Disable/enable (rarely needed — e.g., performance-critical sections)
# gc.disable()
# ... bulk allocation ...
# gc.enable()
```

Three generations (0, 1, 2) — new objects start in gen 0; survivors are promoted. Gen 0 is collected most often. This is efficient because "most objects die young."

### `__del__` and Finalisation — A Warning

```python
class Resource:
    def __init__(self, name):
        self.name = name
        print(f"Acquired {self.name}")

    def __del__(self):
        # Called when refcount hits 0 OR during gc — but timing is NOT guaranteed.
        # Do NOT rely on __del__ for critical cleanup (e.g., closing files).
        print(f"Cleaning up {self.name}")

r = Resource("temp")
del r  # refcount → 0, __del__ called (usually) immediately in CPython
       # but in PyPy or with cycles, it may be delayed or never called.

# CORRECT pattern — use context managers, not __del__
class ManagedResource:
    def __enter__(self):
        print("Acquired")
        return self
    def __exit__(self, *exc):
        print("Released — guaranteed even on exception")
        return False

with ManagedResource() as m:
    print("Using resource")
# "Released" printed here — deterministic
```

### Weak References — Observing Without Owning

`weakref` lets you reference an object without incrementing its refcount — useful for caches and observer patterns where you do not want to prevent collection.

```python
import weakref

class Data:
    def __init__(self, value):
        self.value = value
    def __repr__(self):
        return f"Data({self.value})"

obj = Data(42)
weak = weakref.ref(obj)     # weak reference — does not prevent GC
print(weak())               # Data(42) — dereference

del obj                     # last strong reference gone
print(weak())               # None — object was collected, weak ref is dead

# WeakKeyDictionary / WeakValueDictionary for caches
import weakref
cache: weakref.WeakValueDictionary = weakref.WeakValueDictionary()
obj2 = Data(100)
cache["key"] = obj2
print(list(cache.keys()))  # ['key']
del obj2
print(list(cache.keys()))  # [] — entry vanished when object was collected
```

## 8. Putting It All Together — A Realistic Example

```python
# Configuration system — demonstrates aliasing, copying, identity, and gc.

import copy

default_config = {
    "host": "localhost",
    "port": 8080,
    "tags": ["production"],
}

def create_server_config(overrides=None, *, _defaults=default_config):
    """
    Create a server config dict.

    Why `_defaults` as a keyword-only arg with default?
    It captures the reference at definition time. But we COPY it
    to avoid aliasing bugs.
    """
    # Use None sentinel for overrides to avoid mutable default trap
    if overrides is None:
        overrides = {}

    # Shallow copy is NOT enough if values contain mutables (like `tags`)
    config = copy.deepcopy(_defaults)

    # Apply overrides
    config.update(overrides)
    return config

# --- Usage ---
cfg_a = create_server_config({"port": 9090})
cfg_b = create_server_config()

print(cfg_a)  # {'host': 'localhost', 'port': 9090, 'tags': ['production']}
print(cfg_b)  # {'host': 'localhost', 'port': 8080, 'tags': ['production']}

# Verify isolation — mutating one does not affect the other or the default
cfg_a["tags"].append("canary")
print(cfg_b["tags"])           # ['production'] — isolated via deepcopy
print(default_config["tags"])  # ['production'] — default untouched

# Identity checks — they are distinct objects
print(cfg_a is cfg_b)                  # False
print(cfg_a is default_config)         # False
print(cfg_a["tags"] is default_config["tags"])  # False — deep copied

# Cleanup — when configs go out of scope, refcount drops to 0 and they are freed
del cfg_a, cfg_b
```

## 9. Common Mistakes and Pythonic Idioms

| Mistake | Why It Fails | Correct Approach |
|---|---|---|
| `if x is 1000:` | Relies on int caching | `if x == 1000:` |
| `if s is "hello":` | Relies on string interning | `if s == "hello":` |
| `if x == None:` | Works but unidiomatic | `if x is None:` |
| `def f(lst=[])` | Shared mutable default | `def f(lst=None): if lst is None: lst = []` |
| `b = a` expecting a copy | Creates alias | `b = a.copy()` / `copy.deepcopy(a)` |
| `del x` to "free memory" | Only removes one reference | Let refcount / `gc` handle it; use `with` for resources |

**Pythonic idioms:**

```python
# Idiomatic singleton / sentinel check
if result is None:
    handle_missing()

# Idiomatic copy patterns
shallow = original.copy()           # or list(original), dict(original), set(original)
deep = copy.deepcopy(original)      # when nested mutables exist

# Idiomatic aliasing check — rarely needed, but when you must:
if a is b:
    print("a and b are the same object — mutating one mutates the other")

# Use `id()` for debugging aliasing, not for logic
print(f"a id={id(a)}, b id={id(b)}, same={a is b}")
```

## 10. Summary

- **Everything is an object** — heap-allocated, typed, with identity and refcount.
- **Variables are names** — references that *bind* to objects. Assignment rebinds the name; it never copies.
- **`id()`** gives the identity; **`is`** tests identity; **`==`** tests equality. Use `is` only for singletons.
- **Interning/caching** of small ints and some strings is an invisible optimisation — never depend on it.
- **Mutable aliasing** means `b = a` for a list/dict shares the object; mutate through one name and the other sees it. Copy explicitly.
- **`del`** removes a *name*, not necessarily the object. The object dies only when no references remain.
- **Garbage collection** is primarily reference counting (immediate) plus a generational cycle collector for unreachable cycles. Use `weakref` to avoid keeping objects alive unintentionally, and `with` / context managers instead of `__del__` for deterministic cleanup.

> **Key takeaway:** If you internalise "names point at objects; assignment moves the arrow; `is` compares arrows and `==` compares what they point at," you will understand — and avoid — the majority of Python's aliasing and identity surprises.
