# 01.4 Booleans and Truthiness

> **Mental model:** `bool` is not a separate logical universe — it is a thin subtype of `int` where `True` is `1` and `False` is `0`. On top of that, *every* object in Python has an inherent truthiness used by `if`, `while`, `and`, and `or` — and those operators return *values*, not just `True`/`False`.

This lesson covers the `bool` type itself, the full truthiness table, how `and`/`or`/`not` actually work (returning operands, not booleans), short-circuit evaluation, and the classic pitfalls that trap even experienced programmers.

---

## 1. `bool` — A Subclass of `int`

This surprises newcomers from Java/C# where `boolean` and `int` are unrelated. In Python, `bool` literally inherits from `int`.

```python
# The type hierarchy
print(issubclass(bool, int))   # True
print(isinstance(True, int))   # True — True IS an int
print(isinstance(True, bool))  # True
print(isinstance(1, bool))     # False — int is NOT bool (one-way)
print(type(True))              # <class 'bool'>
print(type(False))             # <class 'bool'>

# True and False are singletons — there is exactly one of each
print(True is True)    # True
print(False is False)  # True
print(True is 1)       # False — same value, different objects/types
print(True == 1)       # True — equal value via int comparison
print(True == 1.0)     # True — numeric tower equality
print(False == 0)      # True
print(False == 0.0)    # True

# Their numeric values
print(int(True))    # 1
print(int(False))   # 0
print(True + True)  # 2
print(True * 10)    # 10
print(False * 100)  # 0

# This enables elegant counting idioms
scores = [85, 92, 55, 78, 90, 42]
passed = sum(s >= 60 for s in scores)  # each comparison is bool → int
print(passed)  # 4

# Also works with arithmetic
print(5 + True)    # 6
print(10 * False)  # 0
print(2 ** True)   # 2
```

### Why Is `bool` a Subclass of `int`?

Historical compatibility. Before Python 2.3, there was no `bool` type — `0` and `1` were used directly. When `bool` was introduced (PEP 285), making it a subclass of `int` ensured all existing code that used `0`/`1` for truth values continued to work. The decision is now permanent and relied upon.

```python
# This historical idiom still works because bool IS int:
flags = 0
flags += True   # increment via bool
print(flags)    # 1

# Sorting — booleans sort as 0/1
print(sorted([True, False, True, False]))  # [False, False, True, True]
# Equivalent to sorted([1, 0, 1, 0])

# Arithmetic with booleans is used deliberately in some libraries
# e.g., numpy: (array > 0).sum() counts positives via bool→int
```

### Distinguishing `bool` from `int` When It Matters

```python
# isinstance(True, int) is True — can surprise validation code
def process_count(n: int) -> None:
    # If you truly need to reject booleans:
    if type(n) is not int:
        # But this rejects bool — use `type() is` for exact check
        raise TypeError(f"Expected int, got {type(n).__name__}")

    # Or more commonly — check bool first if it matters:
    if isinstance(n, bool):
        raise TypeError("Boolean not allowed where int expected")

    print(f"Processing count: {n}")

process_count(42)    # Processing count: 42
try:
    process_count(True)
except TypeError as e:
    print(e)  # Boolean not allowed...

# For most code, accepting bool as int is fine — don't over-guard.
```

## 2. Truthiness — Every Object Is Truthy or Falsy

Python does not require a `bool` in `if`/`while`/filter conditions. Any object can be evaluated in a boolean context, where it is classified as **truthy** (acts like `True`) or **falsy** (acts like `False`).

### The Complete Falsiness Table

**Every object is truthy EXCEPT these falsy values:**

| Value | Type | Why Falsy |
|---|---|---|
| `False` | `bool` | The false boolean |
| `None` | `NoneType` | Absence of value |
| `0`, `0.0`, `0j` | `int`, `float`, `complex` | Numeric zero |
| `Decimal(0)`, `Fraction(0, 1)` | `decimal`, `fractions` | Numeric zero |
| `""` | `str` | Empty string |
| `[]` | `list` | Empty list |
| `{}` | `dict` | Empty dict |
| `set()` | `set` | Empty set |
| `frozenset()` | `frozenset` | Empty frozenset |
| `()` | `tuple` | Empty tuple |
| `range(0)` | `range` | Empty range |
| `b""` | `bytes` | Empty bytes |
| `bytearray(b"")` | `bytearray` | Empty bytearray |
| Objects where `__bool__` returns `False` | custom | Explicitly falsy |
| Objects where `__len__` returns `0` | custom | Empty-like |

**Everything else is truthy** — including non-empty collections, non-zero numbers, non-empty strings, and most custom objects by default.

```python
import math
from decimal import Decimal
from fractions import Fraction

# Falsy values — all evaluate to False in boolean context
falsy_examples = [
    False, None, 0, 0.0, 0j, Decimal(0), Fraction(0, 1),
    "", [], {}, set(), frozenset(), (), range(0), b"",
]

for val in falsy_examples:
    print(f"{val!r:25s} bool={bool(val)}  is_falsy={not val}")

# Truthy values — everything else
truthy_examples = [
    True, 1, -1, 0.1, 1j, Decimal(1), Fraction(1, 2),
    "hello", " ", "0", "False",  # non-empty strings — even "0" and "False" are truthy!
    [0], [None], [[]],            # non-empty lists — even if contents are falsy
    {"": ""}, {0: 0},             # non-empty dicts
    (0,),                         # single-element tuple
    range(1),                     # non-empty range
    b"x",                         # non-empty bytes
]

for val in truthy_examples:
    assert bool(val) is True, f"Expected truthy: {val!r}"
print(f"\nAll {len(truthy_examples)} truthy examples confirmed.")

# Critical subtleties:
print(bool("0"))       # True — non-empty string, even though it looks like zero
print(bool("False"))   # True — non-empty string!
print(bool(" "))       # True — string with a space is non-empty
print(bool([0]))       # True — list with one element (even though 0 is falsy)
print(bool([[]]))      # True — list with one element (even though [] is falsy)
print(bool(0.0))       # False — numeric zero
print(bool(-0.0))      # False — negative zero is still zero
print(bool(float("nan")))  # True — NaN is truthy! (it's a non-zero float)
print(bool(float("inf")))  # True — infinity is truthy
```

### How Python Decides — `__bool__` and `__len__`

```python
# Python's truthiness protocol:
# 1. Try obj.__bool__() — if defined, use its return value (must be bool).
# 2. Else try obj.__len__() — falsy if len == 0, truthy otherwise.
# 3. Else truthy (most objects).

class AlwaysFalsy:
    def __bool__(self):
        return False

print(bool(AlwaysFalsy()))  # False — __bool__ says so
if AlwaysFalsy():
    print("truthy")
else:
    print("falsy")  # prints "falsy"

class EmptyLike:
    def __len__(self):
        return 0

print(bool(EmptyLike()))  # False — __len__ == 0

class NonEmptyLike:
    def __len__(self):
        return 5

print(bool(NonEmptyLike()))  # True — __len__ != 0

class BoolOverridesLen:
    def __bool__(self):
        return False
    def __len__(self):
        return 100  # __bool__ takes precedence — __len__ ignored

print(bool(BoolOverridesLen()))  # False — __bool__ wins

# Real-world example — a custom collection
class Stack:
    def __init__(self):
        self._items: list[int] = []

    def push(self, item: int) -> None:
        self._items.append(item)

    def pop(self) -> int:
        return self._items.pop()

    def __len__(self) -> int:
        return len(self._items)

    # No __bool__ needed — Python falls back to __len__
    # Empty stack is falsy, non-empty is truthy

s = Stack()
print(bool(s))  # False — empty
print(not s)    # True

s.push(42)
print(bool(s))  # True — has items
if s:  # Pythonic — no need for `if len(s) > 0:`
    print(f"Stack has {len(s)} items")
```

## 3. `bool()` — Explicit Conversion

```python
# bool() applies the truthiness protocol explicitly
print(bool(0))        # False
print(bool(42))       # True
print(bool(""))       # False
print(bool("hello"))  # True
print(bool([]))       # False
print(bool([1]))      # True
print(bool(None))     # False

# bool is rarely called explicitly — `if obj:` does it implicitly
# But it's useful for:
# 1. Normalising to actual True/False (e.g., for storage or API)
value = "hello"
normalised: bool = bool(value)  # True — explicit
print(normalised, type(normalised))  # True <class 'bool'>

# 2. As a function argument (e.g., filter)
# `filter(None, ...)` and `filter(bool, ...)` are equivalent
data = [0, 1, "", "hello", [], [1], None, False, True]
print(list(filter(bool, data)))  # [1, 'hello', [1], True]
print(list(filter(None, data)))  # same — None as predicate uses bool()

# 3. Counting truthy values
count = sum(map(bool, data))
print(count)  # number of truthy items
```

## 4. `and` / `or` — They Return Operands, Not Booleans

This is one of Python's most important — and most misunderstood — features. Unlike Java/C where `&&`/`||` always return `bool`, Python's `and`/`or` return **one of their operands**.

### The Rules

```python
# `a and b`:
#   - If `a` is falsy → return `a` (short-circuit, don't evaluate `b`)
#   - If `a` is truthy → return `b`

# `a or b`:
#   - If `a` is truthy → return `a` (short-circuit, don't evaluate `b`)
#   - If `a` is falsy → return `b`

# They return the LAST EVALUATED operand — which may not be a bool at all.
print(0 and 42)        # 0 — 0 is falsy, return it
print(42 and 0)        # 0 — 42 truthy, return 0
print(42 and 100)      # 100 — both truthy, return last evaluated (100)
print([] and "hello")  # [] — [] falsy, return it

print(0 or 42)         # 42 — 0 falsy, return 42
print(42 or 0)         # 42 — 42 truthy, return it (short-circuit)
print("" or "default") # "default"
print("hello" or "default")  # "hello" — already truthy

# With strings — common "default value" pattern
name = ""
display = name or "Anonymous"
print(display)  # Anonymous

name = "Alice"
display = name or "Anonymous"
print(display)  # Alice

# Chained — evaluates left to right
print(0 or "" or [] or "found" or "ignored")  # "found" — first truthy
print(1 and 2 and 3 and 0 and 4)              # 0 — first falsy stops `and`
print(1 and 2 and 3 and 4)                    # 4 — all truthy, last value

# Types are preserved — no coercion to bool
result = "hello" and [1, 2, 3]
print(result, type(result))  # [1, 2, 3] <class 'list'>

result = 0 or [1, 2, 3]
print(result, type(result))  # [1, 2, 3] <class 'list'>
```

### Short-Circuit Evaluation — Second Operand May Never Execute

```python
# Short-circuit means the right side is NOT evaluated if the result
# is already determined by the left side.

def expensive_check() -> bool:
    print("  expensive_check() called!")
    return True

def side_effect(value: str) -> str:
    print(f"  side_effect({value!r}) called!")
    return value

# `or` — if left is truthy, right is never called
print("Test 1: truthy or expensive")
result = "hello" or expensive_check()  # expensive_check NOT called
print(f"  result: {result!r}")

print("\nTest 2: falsy or expensive")
result = "" or expensive_check()       # expensive_check IS called
print(f"  result: {result!r}")

# `and` — if left is falsy, right is never called
print("\nTest 3: falsy and expensive")
result = "" and expensive_check()      # NOT called
print(f"  result: {result!r}")

print("\nTest 4: truthy and expensive")
result = "hello" and expensive_check() # IS called
print(f"  result: {result!r}")

# Practical — guard against None / errors
data = None
# Without short-circuit, data.upper() would crash when data is None
result = data and data.upper()  # data is None (falsy) → returns None, never calls .upper()
print(f"\nGuard result: {result!r}")  # None

data = "hello"
result = data and data.upper()  # data truthy → evaluates and returns "HELLO"
print(f"Guard result: {result!r}")  # HELLO

# Common pattern — safe attribute access (before `getattr` / walrus)
# (Modern code often uses `getattr(obj, "attr", None)` or `x.y if x else None`)
```

### The `or` Default Pitfall — Falsy Valid Values

```python
# `or` for defaults is concise but DANGEROUS when falsy values are valid.

def greet_bad(name=None):
    # Bug — empty string "" is a valid name the caller might pass,
    # but `or` treats it as falsy and replaces it!
    name = name or "Anonymous"
    return f"Hello, {name}!"

print(greet_bad("Alice"))  # Hello, Alice! — OK
print(greet_bad(None))     # Hello, Anonymous! — OK
print(greet_bad(""))       # Hello, Anonymous! — BUG! Caller passed "" intentionally
print(greet_bad(0))        # Hello, Anonymous! — BUG if 0 is valid

# Fix — check explicitly for None (the actual sentinel)
def greet_good(name=None):
    if name is None:
        name = "Anonymous"
    return f"Hello, {name}!"

print(greet_good(""))  # Hello, ! — respects empty string
print(greet_good(None))# Hello, Anonymous!

# Or with a sentinel for cases where None is also valid:
_SENTINEL = object()

def configure(value=_SENTINEL):
    if value is _SENTINEL:
        value = "default"
    # Now None, "", 0 are all valid explicit values
    return value

print(configure())       # default
print(configure(None))   # None — intentional
print(configure(0))      # 0 — intentional
```

## 5. `not` — Always Returns `bool`

Unlike `and`/`or`, `not` always returns `True` or `False`.

```python
print(not True)    # False
print(not False)   # True
print(not 0)       # True — 0 falsy → not falsy is True
print(not 42)      # False — 42 truthy → not truthy is False
print(not "")      # True
print(not "hello") # False
print(not [])      # True
print(not [1])     # False

# `not` has lower precedence than comparisons but higher than `and`/`or`
print(not 1 == 1)    # False — means `not (1 == 1)` → not True → False
print(not 1 == 0)    # True  — means `not (1 == 0)` → not False → True
# If you meant `(not 1) == 1`, write it explicitly — but `(not 1)` is False,
# so `False == 1` is False. Rarely what you want.

# Double negation — normalises to bool (but prefer bool() for clarity)
print(not not 42)      # True — truthy → False → True
print(not not 0)       # False
print(bool(42))        # True — clearer than `not not 42`
```

## 6. Comparison Chaining and Boolean Contexts

(This is covered in depth in Lesson 01.10; key boolean-related points here.)

```python
# Chained comparisons — Pythonic and efficient
x = 5
print(1 < x < 10)    # True — means (1 < x) and (x < 10), but x evaluated once
print(1 < x < 3)     # False

# `and`/`or` in conditions — remember they return values
# This is fine when the values are already booleans (from comparisons):
if x > 0 and x < 10:
    print("x in range")  # comparisons produce bool, `and` of bools is bool

# But watch out when mixing non-bool values in conditions:
value = ""
# `if value` checks truthiness — empty string is falsy
if value:
    print("has value")
else:
    print("empty/missing")  # prints this

# Explicit vs implicit boolean tests
items: list[int] = []
# Pythonic — rely on truthiness
if not items:
    print("no items")

# Less Pythonic but equivalent — explicit length check
if len(items) == 0:
    print("no items")

# The Pythonic form is preferred (PEP 8) — `if not items:` over `if len(items) == 0:`
# But NEVER write `if items == []:` or `if len(items):` when you mean `if items:`
```

## 7. Common Mistakes and Traps

### Trap 1 — `if x == 1 or 2:` (The Classic)

```python
# BROKEN — almost certainly not what the author intended
x = 5
if x == 1 or 2:
    print("BROKEN: always True!")
# Why? Parsed as `(x == 1) or 2` → (False) or 2 → 2 → truthy → always enters!

# Let's trace each case:
for x in [1, 2, 5]:
    result = x == 1 or 2
    print(f"  x={x}: x == 1 or 2 → {x == 1} or 2 → {result!r} → bool={bool(result)}")
# x=1: True or 2 → True → True  (enters — but for wrong reason when x==2)
# x=2: False or 2 → 2 → True     (enters — BUG! x is 2, not 1)
# x=5: False or 2 → 2 → True     (enters — BUG!)

# CORRECT — explicit comparison for each value
x = 5
if x == 1 or x == 2:
    print("x is 1 or 2")
else:
    print("CORRECT: x is neither 1 nor 2")  # prints this

# MORE PYTHONIC — membership test
if x in (1, 2):
    print("x is 1 or 2")
else:
    print("CORRECT: x is neither 1 nor 2")

# Also correct — any/all for complex conditions
valid = {1, 2, 3}
if x in valid:
    print("valid")

# The trap generalises — ANY `if a == b or c:` is suspicious
# `if name == "Alice" or "Bob":` → always True (same bug)
name = "Charlie"
if name == "Alice" or "Bob":  # BUG — always truthy
    print(f"BUG: {name!r} entered the branch!")

if name in ("Alice", "Bob"):  # correct
    print(f"{name} is Alice or Bob")
else:
    print(f"CORRECT: {name} is neither")  # prints this
```

### Trap 2 — `is` vs `==` with Booleans

```python
# `is` checks identity — works for True/False (singletons) but is fragile
print(True is True)   # True — singleton
print(True is 1)      # False — different objects!
print(True == 1)      # True — value equality

# CPython detail — `True`, `False`, `None` are singletons, so `is` happens to work
# for them. But `is` with booleans is idiomatic ONLY for None checks:
if x is True:   # works but unusual — usually just `if x:`
    pass
if x is None:   # idiomatic — correct singleton check
    pass

# Prefer `if x:` / `if not x:` for general truthiness
# Use `if x is True:` only when you must distinguish True from 1/truthy values
def strict_flag(value):
    if value is True:
        print("exactly True")
    elif value:
        print(f"truthy but not True: {value!r}")
    else:
        print(f"falsy: {value!r}")

strict_flag(True)   # exactly True
strict_flag(1)      # truthy but not True: 1
strict_flag("hi")   # truthy but not True: 'hi'
strict_flag(0)      # falsy: 0
```

### Trap 3 — Mutable Default + Truthiness Confusion

```python
# Combining two pitfalls — mutable default AND truthiness-based default

# BROKEN — `or` swallows valid falsy inputs AND mutable default is shared
def add_item_bad(item, target=[]):
    target = target or []  # redundant + still broken for other reasons
    target.append(item)
    return target

# CORRECT — None sentinel + explicit check
def add_item_good(item, target=None):
    if target is None:
        target = []
    target.append(item)
    return target

print(add_item_good(1))              # [1]
print(add_item_good(2))              # [1] — wait, this should be [2]!
# Actually add_item_good(2) creates a NEW list each time — so [2].
# Let's re-test cleanly:
print(add_item_good(1))  # [1]
print(add_item_good(2))  # [2] — independent (correct)

# But what about passing an empty list explicitly?
my_list: list[int] = []
result = add_item_good(99, my_list)
print(result)   # [99]
print(my_list)  # [99] — same object, as expected (we passed it in)
```

### Trap 4 — `filter` and Comprehensions with Truthiness

```python
# Filtering falsy values — but be careful what you filter!
data = [0, 1, "", "hello", None, False, True, [], [0]]

# Removes ALL falsy values — including 0 and False which might be valid!
print(list(filter(None, data)))  # [1, 'hello', True, [0]]
# Lost: 0, "", None, False, []

# If you only want to remove None:
print([x for x in data if x is not None])
# [0, 1, '', 'hello', False, True, [], [0]] — keeps 0, "", False, []

# If you only want to remove None and empty strings:
print([x for x in data if x is not None and x != ""])
```

## 8. Realistic Example — Validation with Truthiness and Short-Circuit

```python
from dataclasses import dataclass

@dataclass
class UserInput:
    username: str
    email: str
    age: str  # comes from a form — always a string initially
    bio: str = ""

def validate(input_data: UserInput) -> list[str]:
    """
    Validate user input. Demonstrates truthiness, short-circuit,
    and the difference between `or` defaults and explicit checks.
    """
    errors: list[str] = []

    # Truthiness for "required field" — empty string is falsy
    if not input_data.username:
        errors.append("Username is required.")
    elif len(input_data.username) < 3:
        errors.append("Username must be at least 3 characters.")

    if not input_data.email:
        errors.append("Email is required.")
    elif "@" not in input_data.email:
        errors.append("Email must contain '@'.")

    # Numeric validation — must handle the string carefully
    # `if not input_data.age` catches "" (empty form field)
    # but "0" is truthy (non-empty string) — so we parse it
    if not input_data.age:
        errors.append("Age is required.")
    else:
        try:
            age_num = int(input_data.age)
            if age_num <= 0:
                errors.append("Age must be positive.")
            elif age_num > 150:
                errors.append("Age seems unrealistic.")
        except ValueError:
            errors.append(f"Age must be a number, got {input_data.age!r}.")

    # Optional field — bio can be empty, that's fine
    # No validation needed, but demonstrate `or` for display
    display_bio = input_data.bio or "(No bio provided)"
    # Note: this is safe here because "" is the only falsy bio we care about.
    # If bio could be a list or other type, we'd use `if bio is None` instead.

    return errors

# --- Tests ---
test_cases = [
    UserInput("Al", "al@test.com", "25"),          # username too short
    UserInput("Alice", "alice@test.com", "25"),     # valid
    UserInput("Bob", "bob-at-test.com", "30"),      # bad email
    UserInput("Charlie", "c@test.com", ""),         # missing age
    UserInput("Diana", "d@test.com", "0"),          # age zero
    UserInput("Eve", "e@test.com", "abc"),          # non-numeric age
    UserInput("", "f@test.com", "22"),              # missing username
    UserInput("Grace", "", "22"),                   # missing email
]

for tc in test_cases:
    errs = validate(tc)
    status = "OK" if not errs else f"ERRORS: {errs}"
    print(f"  {tc.username!r:10s} age={tc.age!r:6s} → {status}")

# --- Short-circuit in action: safe chaining ---
# Simulate fetching a user from a cache that might return None
_user_cache: dict[int, UserInput | None] = {
    1: UserInput("Alice", "alice@test.com", "30"),
    2: None,  # cache miss
}

def get_display_name(user_id: int) -> str:
    """
    Demonstrates `and`/`or` short-circuit for safe access.
    In modern Python, you'd often use `if user is not None:` instead,
    but the short-circuit idiom is still common in concise code.
    """
    user = _user_cache.get(user_id)  # might be None
    # `and` chain — each step short-circuits if None
    # user and user.username → None if user is None, else username
    name = user and user.username
    # `or` for default
    return name or "Unknown User"

print(f"\n  User 1: {get_display_name(1)}")  # Alice
print(f"  User 2: {get_display_name(2)}")   # Unknown User
print(f"  User 99: {get_display_name(99)}") # Unknown User (not in cache → None)

# Modern alternative — explicit is None check (clearer for many teams):
def get_display_name_explicit(user_id: int) -> str:
    user = _user_cache.get(user_id)
    if user is not None and user.username:
        return user.username
    return "Unknown User"
```

## 9. Summary

| Concept | Key Insight |
|---|---|
| `bool` is `int` | `True == 1`, `False == 0`, `isinstance(True, int)` is `True`. Use `type(x) is int` to exclude `bool` if needed. |
| Truthiness | Every object is truthy except: `False`, `None`, numeric `0`, empty collections/strings/bytes. Everything else — including `"0"`, `"False"`, `[0]` — is truthy. |
| `bool()` | Explicit truthiness test; rarely needed since `if obj:` does it implicitly. Useful for `filter` and normalising. |
| `and` / `or` | Return an **operand**, not a `bool`. Short-circuit: right side may never execute. Use for guards and defaults — but beware swallowing valid falsy values. |
| `not` | Always returns `bool`. Lower precedence than comparisons. |
| `or` for defaults | `x or default` is concise but replaces ALL falsy values. Use `x if x is not None else default` when `0`/`""`/`[]` are valid. |
| `if x == 1 or 2:` | **Always True** — parsed as `(x==1) or 2`. Use `if x in (1, 2):` or `if x == 1 or x == 2:`. |
| `__bool__` / `__len__` | Custom truthiness: `__bool__` wins over `__len__`; absent both → truthy. |

> **Key takeaway:** Python's booleans are integers, and its logical operators are value-selecting, short-circuiting tools — not just truth tables. Master the falsiness table and the `and`/`or` return-value rule, and you will both write more concise Pythonic code and avoid the most common conditional bugs.
