## 1. Why Virtual Environments Exist

A Python installation has a single global `site-packages` directory. Installing every package globally creates three problems:

| Problem | Example | Consequence |
|---|---|---|
| **Version conflicts** | Project A needs `requests==2.28`, Project B needs `requests==2.32` | Cannot satisfy both — last install wins, one project breaks |
| **System pollution** | `pip install --upgrade urllib3` upgrades a dependency of `apt` or OS tools | OS utilities break (common on Linux where the OS uses Python) |
| **Reproducibility** | Colleague installs slightly different versions | "Works on my machine" — non-deterministic builds, CI failures |
| **Privilege** | Global `site-packages` is often write-protected | Every install needs `sudo` — security risk and friction |

A **virtual environment** is an isolated, lightweight Python sandbox with its own:

- `python` interpreter (a copy or symlink to the base interpreter)
- `pip` installation
- `site-packages` directory (empty at creation)
- Configuration (`pyvenv.cfg`)

Isolation means each project sees only the packages you installed inside its venv — independent of the system's or other projects' packages.

```
System Python:

/usr/bin/python3
  sys.path → [..., /usr/lib/python3.12/site-packages]  ← global, shared by every project

With virtual environments:

~/.venvs/project-a/  →  sys.path → [..., ~/.venvs/project-a/lib/.../site-packages]
~/.venvs/project-b/  →  sys.path → [..., ~/.venvs/project-b/lib/.../site-packages]
~/project-c/.venv/   →  sys.path → [..., ~/project-c/.venv/lib/.../site-packages]

Each sees ONLY its own site-packages + the stdlib. No cross-talk.
```

> **History:** `venv` (Python 3.3+) replaced the third-party `virtualenv` for standard isolation. `virtualenv` still exists and offers extras (support for Python 2, seeding extras, faster creation), but `venv` is in the stdlib and is now the default recommendation. Modern alternative front-ends (`uv`, `poetry`, `pdm`, `hatch`) all build on the same isolation principle.

## 2. Creating a Virtual Environment — `python -m venv`

### 2.1 Basic creation

```bash
# Create a venv in directory .venv (conventional name) inside your project:
python -m venv .venv

# Or Python-version-specific (if you have multiple Pythons):
python3.11 -m venv .venv
python3 -m venv .venv
# On Windows (PowerShell):
py -3.12 -m venv .venv

# Alternative location — centralised:
python -m venv ~/.venvs/myproject
```

What it creates (on macOS/Linux):

```
.venv/
├── bin/
│   ├── python          ← symlink or copy of the base interpreter
│   ├── python3
│   ├── python3.12
│   ├── pip             ← pip for this venv (independent)
│   ├── pip3
│   └── activate        ← shell activation script (bash/zsh)
│   └── activate.csh    ← csh/tcsh
│   └── activate.fish   ← fish
│   └── Activate.ps1    ← PowerShell (Windows also has activate.bat)
├── lib/
│   └── python3.12/
│       └── site-packages/   ← empty except pip, setuptools scaffolding
├── include/            ← C headers for compilation against this venv
├── lib64 → lib         ← symlink on some Linux
└── pyvenv.cfg          ← configuration (home, version, include-system-site-packages)
```

`pyvenv.cfg` example:

```ini
home = /usr/bin
include-system-site-packages = false
version = 3.12.1
executable = /usr/bin/python3.12
command = /usr/bin/python3.12 -m venv .venv
```

Key: `include-system-site-packages = false` is the isolation switch. With `false` (the default), the venv's `site-packages` is fully independent. With `true`, system site-packages is also visible (the `--system-site-packages` flag).

### 2.2 Flags

```bash
# Help:
python -m venv --help

# Common flags:
python -m venv --system-site-packages .venv  # also expose global site-packages
python -m venv --without-pip .venv           # skip pip — add it later manually
python -m venv --upgrade .venv               # upgrade an existing venv's Python symlinks
python -m venv --clear .venv                 # remove existing .venv first, then recreate
python -m venv --prompt "myapp" .venv        # custom prompt prefix (shown in shell)
```

```bash
# Example: isolated venv without system packages (default — do this):
python -m venv .venv

# Example: recreate if already exists:
python -m venv --clear .venv

# Example: venv that can still see global packages (rare — for large base envs):
python -m venv --system-site-packages .venv
```

### 2.3 How `venv` affects `sys.path`

Inside the venv, `sys.path` and `sys.prefix` point at the venv, not the system:

```bash
# Outside any venv:
python -c "import sys; print(sys.prefix); print(sys.executable)"
# /usr
# /usr/bin/python3.12

# Inside venv (after activation — or invoke the venv interpreter directly):
.venv/bin/python -c "import sys; print(sys.prefix); print(sys.executable); print(sys.path)"
# /home/user/project/.venv
# /home/user/project/.venv/bin/python
# ['', '/usr/lib/python3.12', ..., '/home/user/project/.venv/lib/python3.12/site-packages']

# Check site-packages location:
.venv/bin/python -c "import site; print(site.getsitepackages())"
# ['/home/user/project/.venv/lib/python3.12/site-packages']
```
The venv's `site-packages` comes **before** any system site-packages in `sys.path` (or completely replaces it when `include-system-site-packages = false`), so `import requests` finds the venv's copy first.

### 2.4 Removing a venv

A venv is just a directory. Deleting it removes everything installed inside:

```bash
rm -rf .venv
# All packages, pip cache inside, and configuration are gone.
# The base Python is unaffected — it was only linked, not moved.
```

There is no "uninstall venv" command. Just delete the folder.

## 3. Activation — What It Does (and Doesn't Do)

Activation is a **shell convenience**, not a requirement for isolation. It:

- Prepends `venv/bin` to your `PATH` so that `python` and `pip` resolve to the venv's binaries.
- Modifies the shell prompt to show the venv name.
- Sets `VIRTUAL_ENV` environment variable (used by some tools and for deactivation).

```bash
# Activation — bash/zsh:
source .venv/bin/activate
# Or:
. .venv/bin/activate

# fish:
source .venv/bin/activate.fish

# PowerShell (normal):
.venv\Scripts\Activate.ps1
# If execution policy blocks it:
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

# Windows cmd:
.venv\Scripts\activate.bat

# After activation:
which python          # /home/user/project/.venv/bin/python
which pip             # /home/user/project/.venv/bin/pip
python -c "import sys; print(sys.prefix)"  # /home/user/project/.venv
echo $VIRTUAL_ENV     # /home/user/project/.venv
echo $PS1             # (.venv) ...  (prompt shows venv)

# Confirmation — pip now targets the venv:
pip list              # only venv packages + pip/setuptools
```

Deactivation:

```bash
deactivate            # function defined by activate — restores PATH, prompt, removes VIRTUAL_ENV
which python          # back to /usr/bin/python3.12
```

### 3.1 The non-magical truth — you can skip activation

Activation only affects the **current shell session** and its `PATH`. The venv's interpreter is a real executable that works without activation:

```bash
# Without activation — invoke the venv interpreter explicitly:
.venv/bin/python script.py        # runs inside venv isolation
.venv/bin/pip install requests    # installs into venv's site-packages
.venv/bin/python -m pip install -r requirements.txt

# With activation — `python` is the same file, just found via PATH:
source .venv/bin/activate
python script.py                  # same as above — PATH now points here

# Both are correct. Activation is sugar; the path is the substance.
# Tools like `uv`, `pipx`, and IDEs often invoke `venv/bin/python` directly — no activation.
```

Why this matters:

- **Shebangs** — a script with `#!/path/to/project/.venv/bin/python` runs in isolation without activation.
- **IDEs** — VS Code, PyCharm let you select the venv interpreter directly; no shell activation needed.
- **CI** — `run: .venv/bin/python -m pytest` is more explicit than `source .venv/bin/activate && python -m pytest`.
- **Containers** — Dockerfiles often use `ENV PATH="/app/.venv/bin:$PATH"` as a form of activation.

### 3.2 Activation does NOT isolate `PYTHONPATH` or `PATH` completely

```bash
# If you have PYTHONPATH set in your environment, it still affects the venv:
PYTHONPATH=/opt/mylibs .venv/bin/python -c "import sys; print(sys.path)"
# /opt/mylibs is still in sys.path

# Similarly, packages in the system site-packages are invisible only if
# include-system-site-packages = false (the default). With true, they leak through.
```

## 4. `pip` — Installing and Managing Packages

`pip` is the standard package installer. It fetches from the Python Package Index (https://pypi.org) and installs into the current environment's `site-packages`.

### 4.1 Basic commands

```bash
# Always use `python -m pip` to ensure you target the intended interpreter
# (avoids the `pip` vs `pip3` ambiguity when multiple Pythons are present):

python -m pip install requests              # latest version of requests
python -m pip install "requests==2.32.0"    # exact version
python -m pip install "requests>=2.28,<3"  # version range
python -m pip install requests --upgrade    # upgrade to latest within constraints
python -m pip install --upgrade pip         # self-upgrade pip

# Inside an activated venv, plain `pip` is equivalent:
pip install requests                        # installs into the active venv

# Multiple packages at once:
pip install numpy pandas matplotlib

# Is this really the venv's pip? Verify:
pip --version                               # pip 24.x from .../.venv/lib/...
python -m pip --version                     # same path — confirms identity
```

### 4.2 Version specifiers — PEP 440

```bash
# Exact:
pip install "django==5.0.6"

# Compatible release (allows 5.0.x but not 5.1):
pip install "django~=5.0.6"   # equivalent to >=5.0.6, ==5.0.*

# Compatible release at major level (allows 5.x):
pip install "django~=5.0"     # equivalent to >=5.0, ==5.*

# Ranges:
pip install "requests>=2.28,<3"
pip install "urllib3!=2.2.0"  # exclude one broken version
pip install "numpy>=1.24; python_version >= '3.11'"  # environment marker

# Combination (space or comma — both work in requirements files):
pip install "package>=1.0,<2.0"
```

Useful `pip` queries:

```bash
pip show requests                   # metadata: version, location, requires, files
pip list                            # installed packages (name + version table)
pip list --outdated                 # which have newer versions on PyPI
pip check                           # verify no broken dependency requirements
python -m pip index versions requests  # available versions on PyPI (pip 23+)
```

### 4.3 Uninstalling

```bash
pip uninstall requests              # prompts for confirmation
pip uninstall -y requests           # without prompt
pip uninstall -y -r requirements.txt  # remove everything listed
```

### 4.4 Editable installs — developing your own package

When you are developing a package locally (with `pyproject.toml` or legacy `setup.py`), install it **editable** so that changes to your source are reflected immediately without reinstalling:

```bash
# With pyproject.toml in the project root:
pip install -e .                    # editable — creates a .pth pointing at your source tree

# Now `import mypackage` resolves to your working directory, not a copy:
python -c "import mypackage; print(mypackage.__file__)"
# /home/user/project/mypackage/__init__.py  (your source, not site-packages)

# Edit mypackage/.../*.py freely — no reinstall needed; next `python` picks up changes.

# Optional dependency groups (defined in pyproject.toml [project.optional-dependencies]):
pip install -e ".[dev]"             # editable + dev extras (testing, linting)
pip install -e ".[dev,docs]"
```

Editable installs use a `.pth` file or direct import hook that makes `sys.path` include your project root. See lesson 05.3's `.pth` discussion.

### 4.5 `pip` configuration and caching

```bash
# Config file (optional): ~/.config/pip/pip.conf  (or ~/pip/pip.ini on Windows)
# Example:
# [global]
# index-url = https://my-mirror.example.com/simple
# trusted-host = my-mirror.example.com

pip cache list                      # show cached wheels
pip cache remove requests           # remove cache for one package
pip cache purge                     # clear entire cache

# Install without cache (CI — deterministic):
pip install --no-cache-dir requests

# Dry run — see what WOULD be installed without doing it:
pip install --dry-run requests      # pip 22.2+ ; shows versions and dependencies

# Hash-checking mode (for pinned, audited requirements — forces verification):
pip install --require-hashes -r requirements.txt
```

## 5. Reproducibility — `requirements.txt`, `pip freeze`, and Locking

### 5.1 `pip freeze` — snapshot of exactly installed versions

```bash
pip freeze                          # prints every package in the environment, pinned
# Example output:
# certifi==2024.2.2
# charset-normalizer==3.3.2
# idna==3.6
# numpy==1.26.4
# requests==2.32.0
# urllib3==2.2.1

pip freeze > requirements.txt       # save snapshot to file

pip freeze | grep -v "pkg_resources"  # older pip added pkg_resources — filter if needed
```

`pip freeze` includes **transitive dependencies** (dependencies of your dependencies). A minimal `requirements.txt` hand-maintained by humans usually lists only direct dependencies, often with loose pins; a frozen file pins everything for exact reproduction.

### 5.2 `requirements.txt` — installing from a file

A `requirements.txt` is a line-per-dependency file consumed by `pip install -r`:

```
# requirements.txt — manual (direct dependencies, loose pins)
requests>=2.28,<3
numpy>=1.24
pydantic>=2.0

# requirements.txt — frozen (exact pins, includes transitives)
certifi==2024.2.2
charset-normalizer==3.3.2
idna==3.6
numpy==1.26.4
pydantic==2.7.1
pydantic_core==2.18.2
requests==2.32.0
urllib3==2.2.1
```

```bash
pip install -r requirements.txt             # install everything listed
pip install --upgrade -r requirements.txt   # upgrade to satisfy the pins

# Hash-pinned requirements (from pip-compile — most reproducible):
pip install --require-hashes -r requirements.txt
```

### 5.3 The two-file pattern — `requirements.in` vs `requirements.txt`

For reproducible yet maintainable installs, most projects use two layers:

| File | Contains | Maintained by | Pins |
|---|---|---|---|
| `requirements.in` (or `pyproject.toml` dependencies) | Direct dependencies only | Humans | Loose (`requests>=2.28`) |
| `requirements.txt` (or `requirements-lock.txt`) | Direct + all transitives | Tool (`pip-compile`, `pip-tools`, `uv pip compile`) | Exact (`requests==2.32.0`) |

```bash
# With pip-tools:
pip install pip-tools
# Write requirements.in:
#   requests
#   numpy>=1.24
pip-compile requirements.in              # generates requirements.txt (pinned transitives)
pip-sync requirements.txt                # install exactly what's in requirements.txt
                                         # (removes extraneous packages not in the file)

# With uv (modern, very fast replacement):
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt

# Without tooling — manual two-step (less robust):
pip install "requests" "numpy>=1.24"
pip freeze > requirements.txt            # pins current venv — includes unrelated packages!
# Note: pip freeze inside a venv that has other packages also installed captures those too.
# That's why pip-compile is cleaner — it resolves fresh, not from the current venv state.
```

### 5.4 `requirements.txt` features

```python
# requirements.txt supports several directives:
# Comments:
# This is a comment

# Version pins:
requests==2.32.0
numpy>=1.24,<2

# Extras:
requests[security]==2.32.0   # install requests with its `security` optional dependencies
mypackage[dev,docs]

# Environment markers:
win32-setproctitle==1.6.0; sys_platform == "win32"
uvloop==0.19.0; sys_platform != "win32"

# File / URL:
# ./dist/mypackage-0.1.0-py3-none-any.whl
# https://example.com/mypackage-1.0.tar.gz
# git+https://github.com/user/repo.git@main#egg=package

# Recursive include:
-r other-requirements.txt
-c constraints.txt          # constraint — restricts versions but does not install

# Hash checking (from pip-compile --generate-hashes):
# requests==2.32.0 \
#     --hash=sha256:...

# Editable:
-e .                        # editable install of the current project
```

### 5.5 Verifying what was installed

```bash
# After `pip install -r requirements.txt`, verify:
pip list                        # see what's actually installed
pip freeze                      # exact versions (should match if fully pinned)
pip check                       # verify no conflicts in dependency graph

# Show where a package is installed:
pip show requests | grep Location
python -c "import requests; print(requests.__file__)"

# Show why a version was selected (verbose):
pip install -v "requests==2.32.0"
```

## 6. `pyproject.toml` — Modern Packaging Metadata (Brief)

Since PEP 517 / PEP 518 and PEP 621, `pyproject.toml` is the standard way to declare project metadata, dependencies, and build configuration in one file. It replaces / complements `setup.py` + `requirements.txt` + `setup.cfg`.

### 6.1 Minimal `pyproject.toml`

```toml
# pyproject.toml — minimal package with dependencies
[build-system]
requires = ["hatchling"]         # build backend (pip uses this to build the package)
build-backend = "hatchling.build"

[project]
name = "mypackage"
version = "0.1.0"
description = "A tiny example package"
readme = "README.md"
requires-python = ">=3.11"
license = { text = "MIT" }
authors = [{ name = "Ada Lovelace", email = "ada@example.com" }]
keywords = ["example", "tutorial"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
]

dependencies = [
    "requests>=2.28",
    "pydantic>=2.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.3.0", "mypy>=1.0"]
docs = ["sphinx>=7.0"]

[project.urls]
Homepage = "https://github.com/user/mypackage"
Repository = "https://github.com/user/mypackage"

[project.scripts]
myapp = "mypackage.cli:main"     # creates a `myapp` console entry point

# Tool configuration lives in the same file:
[tool.ruff]
line-length = 88

[tool.pytest.ini_options]
testpaths = ["tests"]
```

How this interacts with installers:

```bash
# Install the project + its dependencies into the active venv:
pip install -e .                     # dependencies from [project.dependencies] auto-installed
pip install -e ".[dev]"              # plus [project.optional-dependencies].dev

# What pip does:
# 1. Reads pyproject.toml via the build backend (hatchling / setuptools / poetry)
# 2. Builds a wheel (zip-like package) in memory
# 3. Installs it into site-packages (editable: via .pth; non-editable: copy)
# 4. Generates mypackage-0.1.0.dist-info/ metadata

# Verify:
pip show mypackage
python -c "import importlib.metadata; print(importlib.metadata.version('mypackage'))"  # 0.1.0
```

### 6.2 `pyproject.toml` vs `requirements.txt` — when to use which

| File | Purpose | Used by |
|---|---|---|
| `pyproject.toml` `[project].dependencies` | **Abstract** dependencies of the **package** (library/app) | `pip install .` / `pip install -e .` — installed whenever the package is installed. This is the correct home for library dependencies. |
| `requirements.txt` | **Concrete** pinned environment for a **deployment** | `pip install -r requirements.txt` — reproduces an exact environment. Good for apps, Docker, CI. |
| Both | Many apps declare deps in `pyproject.toml` *and* generate a locked `requirements.txt` from it | `pip-compile` from `pyproject.toml` or `uv pip compile pyproject.toml` |

```bash
# Generate requirements.txt FROM pyproject.toml (with pip-tools):
pip-compile pyproject.toml -o requirements.txt
# Or with uv:
uv pip compile pyproject.toml -o requirements.txt

# Alternative: keep dependencies in pyproject.toml and let CI install with:
pip install -e ".[dev]"    # instead of pip install -r requirements.txt
```

> **Rule of thumb:** Libraries — declare in `pyproject.toml` only (let consumers pin). Applications / reproducible deployments — keep a locked `requirements.txt` (or `uv.lock` / `poetry.lock`) **in addition**.

### 6.3 Build backends — why `build-system` exists

Historically, `setup.py` with `setuptools` was hardcoded. Now the build system is pluggable (you could use `hatchling`, `setuptools`, `poetry`, `flit`, `pdm`, `maturin` for Rust, etc.). `pip` reads `[build-system].requires` to know what to install before building:

```toml
[build-system]
requires = ["setuptools>=61"]    # old projects still use setuptools
# or
requires = ["hatchling"]
# or
requires = ["poetry-core"]
```

End-users rarely change this; it is decided when the project is bootstrapped.

## 7. Isolation Deep-Dive — What the Venv Actually Does

### 7.1 `sys.path` before and after

```python
# Global Python (no venv):
import sys, site
print(sys.prefix)              # /usr
print(sys.base_prefix)         # /usr (same — not in a venv)
print(site.getsitepackages())  # ['/usr/lib/python3.12/site-packages']

# Inside a venv:
# python path: /home/user/project/.venv/bin/python
import sys, site
print(sys.prefix)              # /home/user/project/.venv  ← points at venv
print(sys.base_prefix)         # /usr                      ← still points at base
print(sys.exec_prefix)         # /home/user/project/.venv
print(sys.base_exec_prefix)    # /usr
print(site.getsitepackages())  # ['/home/user/project/.venv/lib/python3.12/site-packages']
print(sys.path)
# [
#   '',                                                  # CWD / script dir
#   '/usr/lib/python3.12',                               # stdlib (from base)
#   '/usr/lib/python3.12/lib-dynload',                   # C extensions
#   '/home/user/project/.venv/lib/python3.12/site-packages',  # venv site-packages ← isolated!
# ]
# When include-system-site-packages = false, system site-packages is NOT in sys.path.
# When true, it would appear after the venv's entry.
```

Isolation summary:

| Resource | Isolated per venv? | Shared? |
|---|---|---|
| `python` binary | Copied/symlinked — per venv | Stdlib files reused from base (not copied) |
| `site-packages` | Separate empty directory | Nothing shared by default |
| `pip` / installed wheels | Own metadata per venv | Nothing shared |
| `PYTHONPATH` | Not isolated — still read | Env var affects all venvs |
| Environment variables | Not isolated | Shell env shared |
| System `site-packages` | Hidden (default) or appended (if `--system-site-packages`) | Controlled by `pyvenv.cfg` |

### 7.2 `pyvenv.cfg` flags — inspecting the venv

```python
# Read the venv configuration programmatically:
from pathlib import Path
import configparser

cfg = configparser.ConfigParser()
# pyvenv.cfg is not a standard INI (no section header), so prepend one:
raw = Path(".venv/pyvenv.cfg").read_text()
cfg.read_string("[venv]\n" + raw)
print(dict(cfg["venv"]))
# {'home': '/usr/bin', 'include-system-site-packages': 'false', 'version': '3.12.1', ...}
```

### 7.3 Multiple venvs and per-project selection

```bash
# Two projects, two venvs — no interference:
# project-a/.venv  (requests==2.28)
# project-b/.venv  (requests==2.32)

# Tools that auto-select the right venv:
# - direnv: reads .envrc to activate the venv on `cd`
# - VS Code: python.venvPath + python.defaultInterpreterPath
# - PyCharm: auto-detects .venv in project root
# - uv / poetry / pipenv: `uv run`, `poetry run`, `pipenv run` select automatically

# Manual selection without activation:
project-a/.venv/bin/python -m pip list   # shows requests 2.28
project-b/.venv/bin/python -m pip list   # shows requests 2.32
```

## 8. Workflow — End-to-End Example

```bash
# 1. Start a project:
mkdir myapp && cd myapp

# 2. Create and activate a venv:
python -m venv .venv
source .venv/bin/activate          # or .venv\Scripts\Activate.ps1 on Windows

# Verify you're in the venv:
which python                       # .../myapp/.venv/bin/python
pip --version                      # pip ... from .../.venv/lib/...

# 3. Define dependencies (pyproject.toml example shown earlier):
#    Create pyproject.toml with [project].dependencies and [project.optional-dependencies].dev

# 4. Install your project + deps (editable so source changes are live):
pip install -e ".[dev]"

# 5. Or if using requirements.txt (alternative):
#    Create requirements.in with direct deps:  requests, pydantic>=2.0
#    pip install pip-tools
#    pip-compile requirements.in          # generate requirements.txt (pinned)
#    pip-sync requirements.txt            # install exactly those versions

# 6. Work — run tests, lint, etc. — everything sees the isolated environment:
pytest
ruff check .
mypy src/

# 7. Add a new dependency:
pip install "httpx>=0.27"
pip freeze > requirements.txt         # update snapshot (if using freeze-based workflow)

# 8. Reproduce on another machine / in CI:
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt       # exact same versions
# or with pyproject.toml lock:
pip install -e ".[dev]"

# 9. Deactivate when done:
deactivate
```

Docker variant:

```dockerfile
# Dockerfile — using venv even in containers for consistency:
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml README.md ./
COPY src/ ./src/
RUN python -m venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH"
RUN pip install --no-cache-dir -e ".[dev]"
COPY . .
CMD ["python", "-m", "myapp"]
```

## 9. Common Mistakes and Edge Cases

### 9.1 `pip` targeting the wrong Python

```bash
# Mistake — which pip is this?
pip install requests      # may be /usr/bin/pip, not .venv/bin/pip — pollutes global!

# Always verify or use `python -m pip`:
which pip                 # check before installing
python -m pip install requests  # unambiguous — targets this `python`'s site-packages
.venv/bin/python -m pip install requests  # even more explicit

# In CI, use:
python -m pip install -r requirements.txt
# Never just `pip install` without confirming the path.
```

### 9.2 Forgetting to activate — then wondering why import fails

```bash
pip install requests      # installs to global if no venv active, or to venv if active
python -c "import requests"  # ModuleNotFoundError if the `python` is not the one pip targeted

# Diagnose:
which python && which pip              # should both point inside .venv
python -c "import sys; print(sys.prefix)"  # should be .../.venv
pip show requests | grep Location      # should be .../.venv/.../site-packages
python -c "import requests; print(requests.__file__)"  # same location

# Fix: activate, or invoke via .venv/bin/python directly.
```

### 9.3 Committing the venv to version control

A venv contains binaries and absolute paths — not portable. Never commit `.venv/`:

```gitignore
# .gitignore
.venv/
venv/
__pycache__/
*.pyc
*.egg-info/
dist/
build/
```

Only commit `pyproject.toml`, `requirements.txt` / lock files, and source.

### 9.4 Using `sudo pip` — system pollution

```bash
# Never do this (unless you really mean to modify the system Python):
sudo pip install requests   # overwrites system site-packages — can break OS tools

# Always use a venv instead:
python -m venv .venv && source .venv/bin/activate && pip install requests
# Or for a one-off system tool, use pipx:
pipx install black          # installs `black` isolated, exposes `black` binary globally
```

### 9.5 `pip freeze` vs `pip list` confusion

```bash
pip list        # human-readable table — every package, versions; easy to read
pip freeze      # machine-readable `package==version` lines — for piping to requirements.txt

# `pip freeze` omits packages that were installed without metadata (rare).
# `pip list` shows everything pip knows about.

# Don't use `pip freeze > requirements.txt` blindly inside a venv that has
# dev tools (pytest, ruff) if you want a production-only lock — filter or use pip-compile.
```

### 9.6 Conflicting version constraints — the solver error

```bash
# pip install -v will show resolver conflicts:
pip install "requests==2.28" "urllib3==2.2.0"
# May succeed or conflict if requests 2.28 requires urllib3!=2.2.0 (example).

# Typical error:
# ERROR: Cannot install requests==2.28 and urllib3==2.2.0 because these package versions have conflicting dependencies.

# Fix: relax pins, or update requests to a version compatible with the urllib3 you need.
# Tools like `pip-compile` resolve conflicts at compile time and report them clearly.
```

### 9.7 Mixing Conda and `pip`/`venv`

`conda` manages environments differently (non-Python binaries, different solver). Mixing them can produce inconsistent `sys.path` and duplicate libraries:

- If you use `conda`, prefer `conda create -n env` over `python -m venv` — `conda` envs include Python itself.
- If you use `venv`/`pip`, avoid installing into a Conda env with `pip` unless `pip` was installed inside that Conda env (which Conda allows).
- `uv` now supports Conda-free isolation with fast solving and is gaining adoption as a unified alternative.

### 9.8 Network and proxy issues

```bash
# Corporate proxy / self-signed TLS:
pip install requests --proxy http://proxy:8080
pip install requests --trusted-host pypi.org --trusted-host files.pythonhosted.org

# Custom index (private PyPI / Artifactory):
pip install requests --index-url https://my-pypi.example.com/simple
# Or persist in pip.conf:
# [global]
# index-url = https://my-pypi.example.com/simple

# Offline install — download wheels first:
pip download -r requirements.txt -d ./wheels
pip install --no-index --find-links=./wheels -r requirements.txt
```
