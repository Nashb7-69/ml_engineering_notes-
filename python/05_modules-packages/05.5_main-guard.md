# 05.5 The `if __name__ == "__main__"` Guard

## Learning Objectives

By the end of this lesson you will be able to:

- Explain what `__name__` is, how it is set to `"__main__"` vs the module's import name, and why Python uses that convention.
- Write and place the `if __name__ == "__main__":` guard idiomatically (with a `main()` function).
- Predict what happens with and without the guard when a file is imported vs run directly.
- Use the guard to make modules both importable and executable, and to keep import-time side effects minimal.
- Avoid misconceptions (the guard is not access control, not required for every file, and not specific to scripts).
- Test guard-protected code effectively.

## 1. `__name__` — The Module's Identity at Runtime

Every module has a `__name__` attribute. Python sets it **before** the module's top-level code executes, based on **how the module was loaded**:

| How the module was loaded | `__name__` value | Example |
|---|---|---|
| Imported normally | Fully-qualified import name | `import mymodule` → `mymodule.__name__ == "mymodule"` |
| Imported as submodule | Dotted path | `import pkg.sub` → `pkg.sub.__name__ == "pkg.sub"` |
| Run as script: `python file.py` | `"__main__"` | `python mymodule.py` → inside `mymodule.py`, `__name__ == "__main__"` |
| Run as module: `python -m pkg.mod` | `"__main__"` (package-relative) | `python -m pkg.mod` → inside `pkg/mod.py`, `__name__ == "__main__"` |
| REPL / stdin / `-c` | `"__main__"` | `python` or `python -c "code"` → `__name__ == "__main__"` |
| Inside `importlib.util.module_from_spec` before `exec_module` | `spec.name` | Set by the loader before execution |

```python
# File: show_name.py
"""Print __name__ to demonstrate the two modes."""

print(f"__name__ is {__name__!r}")
print(f"__file__ is {getattr(__import__(__name__), '__file__', '(no file)')!r}")
print(f"__package__ is {__package__!r}")
```

```bash
# Running as a script — __name__ is __main__:
$ python show_name.py
__name__ is '__main__'
__file__ is 'show_name.py'
__package__ is None

# Importing — __name__ is the module name:
$ python -c "import show_name"
__name__ is 'show_name'
__file__ is 'show_name.py'
__package__ is ''

# Running as a module — still __main__, but __package__ is set:
$ python -m show_name
__name__ is '__main__'
__file__ is 'show_name.py'
__package__ is ''
# For a package submodule: python -m pkg.sub
#   inside pkg/sub.py: __name__ is '__main__', __package__ is 'pkg'
```

> **Key insight:** `__name__ == "__main__"` does **not** mean "this is a script file." It means "this module is the **entry point** — the one Python started executing first." Any file can be an entry point. A file that is usually imported can be run as an entry point during development, and vice versa.

## 2. The Guard Idiom — `if __name__ == "__main__":`

### 2.1 What it does

```python
# File: mymodule.py
"""Example with the guard."""

def greet(name: str) -> str:
    return f"Hello, {name}!"

def main() -> None:
    print(greet("world"))

if __name__ == "__main__":
    main()
```

- When run as `python mymodule.py` → `__name__ is "__main__"` → `main()` is called → prints `Hello, world!`
- When imported as `import mymodule` → `__name__ is "mymodule"` → condition is `False` → `main()` is **not** called; importing has no side effect beyond defining `greet` and `main`.

The guard is the boundary between **definition** (what the module provides when imported) and **execution** (what it does when run standalone).

### 2.2 Why it matters — imports should not have side effects

Without the guard, top-level executable code runs on import — surprising the importer:

```python
# File: without_guard.py — BAD
"""Module that does work at import time."""

def compute(x: int) -> int:
    return x * 2

# Top-level side effect — runs ON IMPORT:
print("Computing 5:", compute(5))  # prints on every import!
result = compute(42)
print(f"Result is {result}")

# File: app.py
import without_guard  # prints two lines as a side effect of importing!
print("app continues")
# Output:
# Computing 5: 10
# Result is 84
# app continues
```

With the guard:

```python
# File: with_guard.py — GOOD
"""Module that is safe to import."""

def compute(x: int) -> int:
    return x * 2

def main() -> None:
    print("Computing 5:", compute(5))
    result = compute(42)
    print(f"Result is {result}")

if __name__ == "__main__":
    main()

# File: app2.py
import with_guard  # no output — just definitions
print(with_guard.compute(10))  # 20 — use as a library
```

This is why nearly every Python learning resource introduces the guard on day one: **imports execute top-level code** (lesson 05.1). The guard is how you prevent execution that belongs to the entry-point use case from leaking into the import use case.

### 2.3 The guard is not magic — it is a plain `if`

There is no special syntax. The guard is an ordinary `if` statement that checks an ordinary variable:

```python
# These are equivalent to the guard — just less conventional:
if __name__ == "__main__":
    main()

# Also valid but unusual (equivalent for non-malicious values of __name__):
if __name__ != "__main__":
    pass
else:
    main()

# You can even modify __name__ (don't — but it shows it's just a variable):
__name__ = "not_main"  # now the guard would not trigger even when run as script
```

Because it is a plain `if`, you can also use `elif` or combine conditions:

```python
# Conditional entry point (useful for library-with-demo):
if __name__ == "__main__":
    import sys
    if "--test" in sys.argv:
        run_tests()
    else:
        main()
```

## 3. Idiomatic Structure — `main()` Function

The minimal guard is a single call, but the idiomatic pattern extracts a `main()` function:

```python
# Minimal — works but not testable as a function:
# File: minimal_guard.py
def greet(name: str) -> str:
    return f"Hello, {name}!"

if __name__ == "__main__":
    print(greet("world"))  # inline code — not callable from tests

# Idiomatic — testable, handles arguments, has a return value:
# File: idiomatic_guard.py
"""Greeting module — importable library + runnable program."""

import argparse
import sys


def greet(name: str) -> str:
    return f"Hello, {name}!"


def parse_args(argv: list[str] | None = None) -> argparse.Namespace:
    parser = argparse.ArgumentParser(description="Greet someone.")
    parser.add_argument("name", nargs="?", default="world", help="Name to greet")
    parser.add_argument("--shout", action="store_true", help="Uppercase the greeting")
    return parser.parse_args(argv)


def main(argv: list[str] | None = None) -> int:
    """Entry point — callable from tests with fake argv.

    Returns:
        Exit code — 0 for success, non-zero for failure (used by sys.exit).
    """
    args = parse_args(argv)
    message = greet(args.name)
    if args.shout:
        message = message.upper()
    print(message)
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

Why `main(argv)` is better than bare inline code under the guard:

| Benefit | Inline under guard | `main(argv)` |
|---|---|---|
| Testability | Must run the whole file as a subprocess to test | Call `main(["Ada"])` directly in tests |
| Reusability | No function to import — caller must `exec` or subprocess | `from idiomatic_guard import main; main(["Ada"])` |
| Argument handling | Hard-codes `sys.argv` | Accepts `argv` parameter — pass fake args in tests |
| Error signalling | `sys.exit` inside inline code is hard to manage | Return an exit code — `raise SystemExit(main())` pattern |
| Composition | Cannot be used as a library entry point by other modules | Other modules call `main()` programmatically |

```python
# Testing idiomatic_guard.main without a subprocess:
from idiomatic_guard import main, greet
import io
import contextlib

# Test greet (pure logic, no I/O):
assert greet("Ada") == "Hello, Ada!"

# Test main with captured stdout:
buf = io.StringIO()
with contextlib.redirect_stdout(buf):
    code = main(["Ada"])
assert code == 0
assert buf.getvalue() == "Hello, Ada!\n"

buf = io.StringIO()
with contextlib.redirect_stdout(buf):
    code = main(["Ada", "--shout"])
assert buf.getvalue() == "HELLO, ADA!\n"
```

The `raise SystemExit(main())` line deserves attention (section 6).

## 4. Script vs Import — Two Roles for the Same File

Any `.py` file can be used in two ways. The guard makes both safe:

```python
# File: statistics.py
"""Statistics helpers — doubles as a CLI tool."""

import sys
import statistics as _statistics

def mean(values: list[float]) -> float:
    return _statistics.mean(values)

def median(values: list[float]) -> float:
    return _statistics.median(values)

def main(argv: list[str] | None = None) -> int:
    if argv is None:
        argv = sys.argv[1:]
    if not argv:
        print(f"Usage: {__name__} <numbers...>")
        print("Example: python -m statistics 1 2 3 4 5")
        return 2
    try:
        nums = [float(x) for x in argv]
    except ValueError as e:
        print(f"Error: {e}", file=sys.stderr)
        return 1
    print(f"mean: {mean(nums):.2f}")
    print(f"median: {median(nums):.2f}")
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

Usage:

```bash
# As a library — importable, no side effects:
$ python -c "from statistics import mean; print(mean([1,2,3]))"
2.0

# As a script — runs the CLI:
$ python statistics.py 10 20 30 40
mean: 25.00
median: 25.00

# As a module — same CLI, but with correct __package__ for relative imports:
$ python -m statistics 10 20 30 40
mean: 25.00
median: 25.00

# From another module — reuse main():
>>> from statistics import main
>>> main(["1", "2", "3"])
mean: 2.00
median: 2.00
0
```

> **Contrast with languages that separate "main" structurally:** In Java, `public static void main` is always the entry point — the file has a single role. In C, `main()` is similarly entry-only. In Python, any file can be *both* a library and a program — the guard is the lightweight convention that replaces a language-level entry-point keyword.

## 5. Running as Script (`python file.py`) vs Module (`python -m file`)

Both set `__name__ == "__main__"`, but they differ in `__package__` and import resolution. This is essential when the file is inside a package and uses relative imports.

```python
# Package layout:
# project/
# ├── mypackage/
# │   ├── __init__.py
# │   ├── config.py      (Settings)
# │   └── app.py         (uses from . import config)
```

```python
# File: mypackage/app.py
from . import config  # relative import — requires package context

def main() -> None:
    print(f"Config: {config.SETTINGS}")

if __name__ == "__main__":
    main()
```

```bash
# Running as a SCRIPT — BROKEN for relative imports:
$ python mypackage/app.py
# ImportError: attempted relative import with no known parent package
# Because: __name__ is "__main__", __package__ is None — no package context,
#          so `from . import config` cannot resolve ".".

# Running as a MODULE — WORKS:
$ python -m mypackage.app
# __name__ is "__main__", __package__ is "mypackage"
# `from . import config` → `mypackage.config` ✓

# Running the package itself (if mypackage/__main__.py exists):
$ python -m mypackage
# Executes mypackage/__main__.py with __name__ == "__main__" and __package__ == "mypackage"
```

`__main__.py` — the package entry point:

```python
# File: mypackage/__main__.py
"""Allows `python -m mypackage` as an entry point."""

from .app import main

if __name__ == "__main__":
    raise SystemExit(main())
```

```bash
$ python -m mypackage             # runs mypackage/__main__.py
$ python mypackage/__main__.py    # also works but breaks relative imports — same as Script trap
```

**Best practice for entry points inside packages:**

- Put the entry-point logic in a module that does **not** use relative imports, or
- Provide a `__main__.py`, or
- Keep the runnable script **outside** the package (see section 8 and lesson 05.2).

| Invocation | `__name__` | `__package__` | Relative imports | Use case |
|---|---|---|---|---|
| `python file.py` | `__main__` | `None` | Fail | Single-file scripts, files outside packages |
| `python -m pkg.mod` | `__main__` | `pkg` | Works | Package submodules |
| `python -m pkg` | `__main__` | `pkg` (inside `__main__.py`) | Works | Package entry point (`__main__.py`) |
| `import pkg.mod` | `pkg.mod` | `pkg` | Works | Library use (no guard triggered) |

## 6. `sys.exit` and `raise SystemExit` — Exiting From the Guard

### 6.1 The three exit patterns

```python
# Pattern 1 — bare call (implicit exit code 0):
if __name__ == "__main__":
    main()  # return value ignored; process exits 0 even if main() returned 1

# Pattern 2 — explicit sys.exit (communicates exit code to the OS):
import sys

if __name__ == "__main__":
    sys.exit(main())  # main() returns int → OS exit code; non-zero means failure

# Pattern 3 — raise SystemExit (equivalent, more testable):
if __name__ == "__main__":
    raise SystemExit(main())  # sys.exit is literally `raise SystemExit`
```

`sys.exit(code)` is implemented as `raise SystemExit(code)`. The difference:

```python
import sys

# sys.exit(1) raises SystemExit(1) which, if uncaught, terminates the interpreter
# with exit code 1. Exception handling can intercept it:
try:
    sys.exit(1)
except SystemExit as e:
    print(f"Intercepted exit code {e.code}")  # 1 — we caught it!

# Similarly for raise SystemExit:
try:
    raise SystemExit(2)
except SystemExit as e:
    print(f"Intercepted {e.code}")  # 2

# None and 0 mean success; string prints to stderr and exits 1:
# sys.exit("fatal error")  → prints "fatal error" to stderr, exits 1
```

### 6.2 Mapping exit codes to shell semantics

| `main()` returns | `sys.exit(...)` does | Shell sees (`$?`) |
|---|---|---|
| `0` or `None` | Exit 0 | `0` — success |
| `int` non-zero (e.g., `1`, `2`) | Exit that code | `1` — failure (or specific code) |
| `str` (e.g., `"error"`) | Print to stderr, exit 1 | `1` |
| Raises any other exception | Uncaught traceback, exit 1 | `1` |

```bash
python mymodule.py; echo $?
# 0 if mymodule raised SystemExit(0), 1 if SystemExit(1), etc.

# CI uses this — test failure is main() returning 1:
python -m pytest tests/; echo $?  # 0 = all pass, non-zero = failure
```

### 6.3 Why `raise SystemExit(main())` is preferred in some guides

- It makes the exit **explicit** in the code (`raise` is a keyword).
- It works well with `if __name__ == "__main__":` in type checkers — they know `raise` never returns, so they don't warn about unreachable code after the guard.
- It avoids confusion with `sys.exit` being imported but not called.

Both `sys.exit(main())` and `raise SystemExit(main())` are idiomatic. `raise SystemExit` is slightly more explicit about being an exception. Pick one and be consistent.

## 7. Common Misconceptions

### 7.1 "The guard is only for scripts"

False. The guard is for **any module that contains executable code at module level**. A library module that has a demo, a CLI helper, or a self-test benefits from the guard just as much. Even a module with no current executable code should consider a guard for future safety — adding top-level code without a guard is a breaking change for importers.

```python
# File: library.py — not "just a script," but the guard still belongs:
"""Library with an optional demo when run directly."""

def core_logic(x: int) -> int:
    return x * 2

def demo() -> None:
    for val in [1, 2, 3]:
        print(f"{val} → {core_logic(val)}")

if __name__ == "__main__":
    demo()  # not a "script" — a demo attached to a library

# Importing is still side-effect-free:
# import library  → no demo printed
# python library.py → demo printed
```

### 7.2 "The guard provides access control or security"

No. It is a **convention** for controlling execution, not a security boundary. Any importer can call `library.main()` or `library.demo()` directly. The guard only prevents *automatic* execution at import time.

```python
# The guard does NOT prevent:
import library
library.main()        # caller can always call it explicitly
library.demo()        # no protection — the guard is not access control

# If you need actual access control, use underscore conventions, documentation,
# or process boundaries — not `__name__` checks.
```

### 7.3 "Every file needs the guard"

Not every file needs it, but every file that does **anything** beyond definitions benefits:

- **Needs a guard:** any file with I/O, `print`, file writes, network calls, or code that does work beyond `def`/`class`/constant definitions at the top level.
- **No guard needed:** pure definition files (`config.py` with constants, `models.py` with classes, `types.py`) — the guard would be empty and unnecessary.

Including an empty or minimal guard in pure-definition files is harmless but adds noise. Use judgment.

### 7.4 "`__name__` is only `"__main__"` or the filename"

`__name__` can be any dotted path — it reflects the import path, not the filename:

```python
# myapp/services/handlers.py
print(__name__)  # "myapp.services.handlers" when imported as `from myapp.services import handlers`

# The file is handlers.py, but __name__ is the fully-qualified package path.
# Two different import paths to the same file give different __name__ values
# (though normally a file has one canonical path — the one on sys.path).
```

### 7.5 "Checking `__name__` is the only way to detect the entry point"

`__name__ == "__main__"` is the primary, documented way. Alternatives exist but are non-idiomatic or fragile:

```python
# Fragile — checking __file__ or sys.argv[0]:
import sys
if sys.argv[0].endswith("mymodule.py"):
    main()  # breaks with `python -m mymodule` or symlink, and on import it still runs

# Fragile — checking sys.modules:
import sys
if sys.modules["__main__"].__file__ == __file__:
    main()  # works sometimes, but far less clear than __name__ check
```

Always use `if __name__ == "__main__":`.

## 8. Project Structure — Entry Points Done Right

### 8.1 Keep entry points outside the package

The cleanest layout separates the importable package from the runnable entry point:

```
project/
├── pyproject.toml          ← packaging metadata, entry-point spec
├── README.md
├── .venv/                  ← venv (not committed)
├── src/                    ← (optional src layout — prevents import confusion)
│   └── mypackage/
│       ├── __init__.py
│       ├── config.py
│       ├── models/
│       │   ├── __init__.py
│       │   └── user.py
│       ├── services/
│       │   ├── __init__.py
│       │   └── user_service.py
│       └── cli.py          ← CLI implementation (NOT the entry point itself)
├── run.py                  ← thin entry point outside the package
└── tests/
    └── test_user_service.py
```

```python
# File: src/mypackage/cli.py — CLI implementation (importable, testable)
"""CLI for mypackage."""

import argparse
import sys

from mypackage.services.user_service import create_user


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mypackage", description="User management CLI")
    sub = parser.add_subparsers(dest="command", required=True)
    p = sub.add_parser("create", help="Create a user")
    p.add_argument("name", help="User name")
    p.add_argument("email", help="User email")
    return parser


def main(argv: list[str] | None = None) -> int:
    parser = build_parser()
    args = parser.parse_args(argv)
    if args.command == "create":
        user = create_user(args.name, args.email)
        print(f"Created {user}")
        return 0
    parser.print_help()
    return 2

# No guard here — cli.py is a library module. The guard is in the entry point.
```

```python
# File: run.py — thin entry point outside the package (has the guard)
#!/usr/bin/env python3
"""Entry point — delegates to mypackage.cli.main."""

from mypackage.cli import main

if __name__ == "__main__":
    raise SystemExit(main())
```

`pyproject.toml` can also declare a console script entry point so that `pip install` creates a `mypackage` binary:

```toml
# pyproject.toml
[project.scripts]
mypackage = "mypackage.cli:main"   # after `pip install -e .`, a `mypackage` command is created
```

```bash
mypackage create "Ada" "ada@example.com"  # runs mypackage.cli:main with argv
python -m mypackage.cli create "Ada" "ada@example.com"
python run.py create "Ada" "ada@example.com"
# All three do the same thing — thin wrapper → same main() function.
```

Why this is better than putting the guard inside `mypackage/services/user_service.py`:

| Location | Issue |
|---|---|
| Guard inside `mypackage/services/user_service.py` | Couples library code with CLI; tests must import a module that may parse `sys.argv` if guard is wrong; entry point is buried inside a service module |
| Guard in `run.py` (outside) | Package is purely importable — no entry-point code mixed in; test by `from mypackage.cli import main` without touching `run.py` |
| `pyproject.toml` `[project.scripts]` | Zero manual scripts — `pip install` creates the binary; most professional projects use this |

## 9. Testing Code Behind the Guard

### 9.1 Extract and test `main(argv)`, not the `if` line

The `if __name__ == "__main__":` line itself is not worth testing through import — test the function it calls:

```python
# File: mypackage/cli.py — testable
def main(argv: list[str] | None = None) -> int:
    ...

if __name__ == "__main__":
    raise SystemExit(main())  # not tested via import — covered by subprocess test if needed
```

```python
# File: tests/test_cli.py
import io
import contextlib
import pytest
from mypackage.cli import main, build_parser

def test_main_create(capsys):
    code = main(["create", "Ada", "ada@example.com"])
    assert code == 0
    out = capsys.readouterr().out
    assert "Created" in out

def test_main_no_args_exits_with_error():
    with pytest.raises(SystemExit) as exc:
        main([])  # no subcommand → argparse exits via SystemExit(2)
    assert exc.value.code == 2

def test_build_parser_defaults():
    parser = build_parser()
    args = parser.parse_args(["create", "Bob", "bob@example.com"])
    assert args.name == "Bob"

# To test the guard line itself (rarely needed — 100% coverage purists only):
def test_module_as_script():
    import subprocess, sys, pathlib
    result = subprocess.run(
        [sys.executable, "-m", "mypackage.cli", "create", "Ada", "ada@example.com"],
        capture_output=True, text=True,
        cwd=str(pathlib.Path(__file__).parents[1]),
    )
    assert result.returncode == 0
    assert "Created" in result.stdout
```

### 9.2 Why `main(argv=None)` instead of `main()` with hard-coded `sys.argv`

```python
# Hard to test — must patch sys.argv:
def main_bad() -> int:
    import sys
    argv = sys.argv[1:]  # reads global — test must monkey-patch sys.argv
    ...

# Easy to test — inject fake argv:
def main(argv: list[str] | None = None) -> int:
    import sys
    if argv is None:
        argv = sys.argv[1:]  # default to real argv only when called without args
    ...

# Test without patching:
assert main(["create", "Ada", "ada@example.com"]) == 0
# Normal run still works:
# python -m mypackage.cli create Ada ada@example.com  → main() reads sys.argv
```

This is standard for CLI tools. Libraries like `argparse`, `click`, and `typer` all support this injection pattern.

## 10. Realistic Example — Dual-Mode Statistics Module

```python
# File: analytics.py
"""Analytics — library + CLI in one file, correctly guarded."""

from __future__ import annotations

import argparse
import csv
import json
import statistics
import sys
from pathlib import Path
from typing import Optional

# ---------------------------------------------------------------------------
# Library API — pure, testable, no I/O side effects
# ---------------------------------------------------------------------------

def summarize(values: list[float]) -> dict[str, float]:
    """Return mean, median, stdev for values (pure function — no I/O)."""
    if not values:
        raise ValueError("Need at least one value")
    result: dict[str, float] = {
        "count": float(len(values)),
        "mean": statistics.mean(values),
        "median": statistics.median(values),
    }
    if len(values) >= 2:
        result["stdev"] = statistics.stdev(values)
    else:
        result["stdev"] = 0.0
    return result


def load_numbers_csv(path: Path) -> list[float]:
    """Load numbers from a single-column CSV file (one value per row)."""
    numbers: list[float] = []
    with path.open(newline="") as f:
        reader = csv.reader(f)
        for lineno, row in enumerate(reader, start=1):
            if not row or not row[0].strip():
                continue
            try:
                numbers.append(float(row[0].strip()))
            except ValueError as e:
                raise ValueError(f"{path}:{lineno}: not a number: {row[0]!r}") from e
    return numbers


def format_summary(data: dict[str, float], as_json: bool = False) -> str:
    if as_json:
        return json.dumps(data, indent=2)
    lines = [f"{k}: {v:.4f}" for k, v in data.items()]
    return "\n".join(lines)

# ---------------------------------------------------------------------------
# CLI layer — thin, delegates to library API
# ---------------------------------------------------------------------------

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(
        prog="analytics",
        description="Compute summary statistics for numbers.",
    )
    parser.add_argument(
        "source", nargs="?", default=None,
        help="Path to CSV file with numbers (one per line). Reads from stdin if omitted.",
    )
    parser.add_argument("--json", action="store_true", help="Output as JSON")
    return parser


def main(argv: list[str] | None = None) -> int:
    parser = build_parser()
    args = parser.parse_args(argv)

    # Load
    try:
        if args.source is not None:
            values = load_numbers_csv(Path(args.source))
        else:
            # Read from stdin:
            text = sys.stdin.read().strip()
            if not text:
                parser.print_usage(sys.stderr)
                print("error: no input — provide a CSV file or pipe numbers to stdin",
                      file=sys.stderr)
                return 2
            values = [float(x.strip()) for x in text.split() if x.strip()]
    except (OSError, ValueError) as e:
        print(f"error: {e}", file=sys.stderr)
        return 1

    # Compute
    try:
        result = summarize(values)
    except ValueError as e:
        print(f"error: {e}", file=sys.stderr)
        return 1

    # Output
    print(format_summary(result, as_json=args.json))
    return 0


# ---------------------------------------------------------------------------
# Guard — the ONLY unconditional side effect in the file
# ---------------------------------------------------------------------------
if __name__ == "__main__":
    raise SystemExit(main())
```

Usage in all three modes:

```bash
# As a library:
$ python -c "from analytics import summarize; print(summarize([1,2,3,4,5]))"
{'count': 5.0, 'mean': 3.0, 'median': 3.0, 'stdev': 1.5811}

# As a script with a file:
$ echo -e "1\n2\n3\n4\n5" > /tmp/nums.csv
$ python analytics.py /tmp/nums.csv
count: 5.0000
mean: 3.0000
median: 3.0000
stdev: 1.5811
$ python analytics.py /tmp/nums.csv --json
{
  "count": 5.0,
  "mean": 3.0,
  "median": 3.0,
  "stdev": 1.5811
}

# As a module:
$ python -m analytics /tmp/nums.csv --json
# (same output — module mode)

# Piping:
$ echo "10 20 30" | python analytics.py

# Programmatic reuse of main():
>>> from analytics import main
>>> main(["--json"])
# reads from stdin in interactive mode — pass a file in practice

# (prints summary for stdin values)
```

How the guard prevents problems:

```python
# Without the guard, this line would be bare:
# main()  ← would run on import! Expensive and surprising

# With the guard, importing is safe:
import analytics  # no CLI execution, no reading files, no printing
print(analytics.summarize([10, 20, 30]))  # use as library — no side effects

# Testing without subprocess:
from analytics import summarize, format_summary, main
assert summarize([1, 2, 3]) == {"count": 3.0, "mean": 2.0, "median": 2.0, "stdev": 1.0}

import tempfile, pathlib

    f.write("4\n5\n6\n")
    fname = f.name
assert main([fname, "--json"]) == 0
pathlib.Path(fname).unlink()
```

## 11. Common Mistakes and Edge Cases

### 11.1 Forgetting the guard — silent import-time work

```python
# File: jobs.py — WITHOUT guard (bug):
import time

def expensive_setup() -> None:
    print("Setting up...")
    time.sleep(2)

expensive_setup()  # runs on import — every `import jobs` pays 2 seconds!

# File: app.py
import jobs  # surprise — 2 second delay, prints "Setting up..." on import
```

Fix: wrap `expensive_setup()` in `if __name__ == "__main__":` or expose it as a function for callers to opt into.

### 11.2 Guard with no `main()` — testing pain

```python
# Avoid — inline code under the guard is not testable:
if __name__ == "__main__":
    data = load_data()
    result = process(data)
    print(result)
    sys.exit(0 if result else 1)

# Prefer — extract to a function:
def main(argv=None) -> int:
    data = load_data(argv)
    result = process(data)
    print(result)
    return 0 if result else 1

if __name__ == "__main__":
    raise SystemExit(main())
```

### 11.3 Multiple guards (seen in notebooks)

```python
# File: utils.py — two guards is legal but confusing:
def helper():
    pass

if __name__ == "__main__":
    print("first guard")

# ... more code ...

if __name__ == "__main__":
    print("second guard")

# Both conditions test the same __name__ — both run when executed as a script.
# One guard per file is conventional. Multiple guards usually signal the file
# should be split into a library part and a script part.
```

### 11.4 `__name__` can be set manually (unusual but legal)

```python
# You CAN run a module's code under a different __name__:
import runpy

# Run show_name.py as if it were __main__:
runpy.run_path("show_name.py", run_name="__main__")  # prints __name__ is '__main__'
runpy.run_path("show_name.py", run_name="show_name")  # treated as import — guard not triggered

# exec with a custom globals dict:
code = compile(open("show_name.py").read(), "show_name.py", "exec")
exec(code, {"__name__": "custom"})  # guard sees "custom", does not run

# Jupyter does something similar — notebook cells have __name__ == "__main__"
```

### 11.5 Guard in `__init__.py` — rarely needed

```python
# File: mypackage/__init__.py
print("package init")

if __name__ == "__main__":
    print("This prints ONLY if you run `python -m mypackage` (i.e., __main__.py fallback)")
    # But `python -m mypackage` actually runs __main__.py if it exists, not __init__.py.
    # So this branch is dead code unless __main__.py is missing and you run `python -m mypackage`
    # (which fails differently in modern Python — `No module named mypackage.__main__`).
```

In practice, `__init__.py` should not contain a guard. Use `__main__.py` for the package entry point.

### 11.6 Guard and multiprocessing `fork` vs `spawn`

On Unix, `multiprocessing` defaults to `fork` — child processes inherit the parent's state. On Windows and macOS (since Python 3.8), `spawn` starts a fresh interpreter that **re-imports** the launching module:

```python
# File: mp_demo.py — needs the guard for spawn-based multiprocessing
import multiprocessing

def worker(n: int) -> int:
    return n * n

if __name__ == "__main__":
    # Without this guard, spawn would re-execute the module in the child,
    # which would spawn more children, infinitely (fork bomb on Windows/macOS).
    with multiprocessing.Pool() as pool:
        print(pool.map(worker, range(5)))

# Rule: always guard multiprocessing code — required on Windows, recommended everywhere.
```

### 11.7 Guard with `unittest` discovery

```python
# File: test_example.py
import unittest

class MyTest(unittest.TestCase):
    def test_add(self):
        self.assertEqual(1 + 1, 2)

if __name__ == "__main__":
    unittest.main()  # allows: python test_example.py → runs tests

# Also run via discovery:
# python -m unittest discover  → imports test_example (guard not triggered) → discovers MyTest
# The guard doesn't interfere — it's just one more way to run the same tests.
```

## 12. Quick Reference

| Concept | One-liner |
|---|---|
| `__name__` | Import name when imported (`"pkg.mod"`); `"__main__"` when run as entry point |
| Guard `if __name__ == "__main__":` | Plain `if` that runs code only when the file is the entry point |
| `main(argv)` | Idiomatic — testable function with injectable `argv`; returns exit code |
| `raise SystemExit(main())` | Idiomatic exit — communicates code to OS; `sys.exit(main())` equivalent |
| `python file.py` | `__name__ == "__main__"`, `__package__ == None` — relative imports fail |
| `python -m pkg.mod` | `__name__ == "__main__"`, `__package__ == "pkg"` — relative imports work |
| `python -m pkg` | Runs `pkg/__main__.py` |
| Entry point outside package | Cleanest — `run.py` imports `pkg` and calls `main()` |
| `[project.scripts]` | `pip` creates a binary — no manual run script needed |
| `multiprocessing` + guard | Required on `spawn` platforms (Windows/macOS) to prevent fork bombs |
| Misconception | Guard is not access control, not required for every file, not only for scripts |
