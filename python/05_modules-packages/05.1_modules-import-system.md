# 05.1 Modules and the Import System

## Learning Objectives

By the end of this lesson you will be able to:

- Define what a module is and identify its key attributes (`__name__`, `__file__`, `__dict__`, `__cached__`, `__package__`).
- Distinguish `import module`, `from module import name`, and `import module as alias` at the binding level.
- Explain that import executes a module's top-level code exactly once and caches the result in `sys.modules`.
- Treat modules as singletons: every import of the same module shares the same object.
- Predict and avoid circular-import failures and understand the standard fixes.
- Apply aliasing idioms and avoid `from module import *`.

## 1. What Is a Module?

A **module** is a single Python file (`.py`) — or an extension module written in C / Cython — that is loaded as an object at runtime. Colloquially "a file is a module," but technically the module is the **object** created when that file is executed. The file is the source; the module is the live namespace object.

Any `.py` file can be a module. The standard library is just a collection of such files:

```
math.py          →  math module (actually C, but same idea)
json/__init__.py →  json package (a special kind of module)
collections.py   →  collections module
your_script.py   →  your module (when imported)
```

### 1.1 Creating a module

```python
# File: mymath.py  (this file IS the module source)
"""mymath — tiny arithmetic helpers."""

PI = 3.14159

def circle_area(radius: float) -> float:
    """Return area of a circle."""
    return PI * radius * radius

def circle_circumference(radius: float) -> float:
    return 2 * PI * radius

# Top-level code — runs ONCE when the module is first imported
print(f"[mymath] loaded, PI={PI}")
```

```python
# File: app.py — the importer
import mymath

print(mymath.PI)                        # 3.14159
print(mymath.circle_area(10))           # 314.159
print(mymath.__name__)                  # 'mymath'
print(mymath.__file__)                  # '/path/to/mymath.py'
```

Explanation:

- `import mymath` locates `mymath.py` on `sys.path`, compiles it to bytecode, executes it top-to-bottom in a fresh namespace `dict`, and binds the resulting module object to the name `mymath` in the importer's namespace.
- `mymath.PI` is attribute access on that module object — exactly like `obj.attr`.
- The `print` at the bottom of `mymath.py` executes during import. If you run `app.py` you will see `[mymath] loaded...` printed once, even if `app.py` imports `mymath` ten times.

> **Mental model:** `import mymath` ≈ "if `mymath` not yet loaded: create empty module object → execute file contents inside it → cache it → bind name `mymath` locally."

### 1.2 Module attributes — introspection

Every module object carries metadata attributes. These are the same attributes you can inspect on any object via `dir()` or `__dict__`.

```python
# File: demo_attrs.py
"""Demo module for introspection."""

value = 42

def hello() -> str:
    return "hi"
```

```python
# In a REPL or another file:
import demo_attrs
import pprint

print(demo_attrs.__name__)      # 'demo_attrs'  — the import name
print(demo_attrs.__file__)      # '/path/to/demo_attrs.py' — source file path
print(demo_attrs.__cached__)    # '/path/to/__pycache__/demo_attrs.cpython-312.pyc' — bytecode cache
print(demo_attrs.__package__)   # '' for top-level module, 'pkg.sub' for submodules
print(demo_attrs.__doc__)       # 'Demo module for introspection.' — first string literal
print(demo_attrs.__dict__.keys())
# dict_keys(['__name__', '__file__', '__cached__', '__package__', '__doc__',
#            '__loader__', '__spec__', '__builtins__', 'value', 'hello'])

# The module's namespace IS its __dict__:
print(demo_attrs.__dict__["value"])  # 42 — same as demo_attrs.value
print(demo_attrs.value is demo_attrs.__dict__["value"])  # True

# Mutating through either view affects the same object:
demo_attrs.new_attr = "added after import"
print(demo_attrs.__dict__["new_attr"])  # 'added after import'
demo_attrs.__dict__["another"] = 99
print(demo_attrs.another)               # 99
```

Key attributes:

| Attribute | Meaning | Notes |
|---|---|---|
| `__name__` | Import name (`"demo_attrs"` or `"__main__"` when run as script) | Controls `if __name__ == "__main__"` guard (lesson 05.5) |
| `__file__` | Path to `.py` source | Missing for built-in / namespace / frozen modules |
| `__cached__` | Path to `.pyc` bytecode | Missing if `-B` or no write permission |
| `__package__` | Package for relative imports | `""` or `"pkg"`; `None` for some built-ins |
| `__doc__` | Module docstring | `None` if no docstring |
| `__dict__` | Namespace dict holding all module globals | Mutating it mutates the module |
| `__spec__` | `ModuleSpec` with finder/loader metadata (PEP 451) | `importlib`-level detail |
| `__loader__` | Loader that executed the module | `None` for namespace packages |

```python
import sys
import math
import demo_attrs

# Built-in modules have no __file__:
print(hasattr(math, "__file__"))    # False — math is a C extension without a .py
print(math.__spec__)                # ModuleSpec(name='math', loader=..., origin='built-in')
print(math.__loader__)              # <class '_frozen_importlib.BuiltinImporter'>

# Namespace packages (PEP 420) have no __file__ either — they have no single file:
# import my_namespace_pkg  # if it's a namespace package
# print(my_namespace_pkg.__file__)  # AttributeError — no __file__

# sys.modules holds every loaded module:
print("demo_attrs" in sys.modules)  # True
print(sys.modules["demo_attrs"] is demo_attrs)  # True — same object
print(type(sys.modules))            # <class 'dict'>
```

> **Distinction:** `__file__` is not guaranteed. Never assume it exists. Guard with `getattr(mod, "__file__", None)` or `hasattr`.

### 1.3 The module's `__dict__` is the global namespace

Recall lesson 01.9: the global namespace of a file is the module's `__dict__`. They are the same object:

```python
# File: identity_demo.py
x = 10

# At module level, globals() returns the module's __dict__
import sys
current = sys.modules[__name__]  # __name__ is 'identity_demo' when imported
print(globals() is current.__dict__)  # True — same dict object
print(globals() is __dict__ if "__dict__" in dir() else "N/A")
# Actually inside a module there is no bare __dict__ — but globals() IS it.

# Every name you define at module level lands in that dict:
y = 20
print(current.__dict__["y"])  # 20
```

This is why `globals()["z"] = 99` in lesson 01.9 created a global — it mutated the module's `__dict__`.

## 2. Import Forms — What Each One Binds

If modules are objects, import statements are **binding statements** — just like `x = 1` or `def f():`. The difference is *what* they bind and *where* they look.

### 2.1 `import module`

```python
import math
import os
import mymath

print(math.sqrt(16))        # 4.0 — access via module name
print(os.path.join("a", "b"))  # 'a/b'
print(mymath.PI)
```

What happens (precise steps, simplified):

1. Check `sys.modules["math"]` — if already present, skip to step 4.
2. Otherwise find `math` on `sys.path` (finders), load and execute it, store in `sys.modules["math"]`.
3. The module object now exists.
4. Bind the name `math` in the **current namespace** to `sys.modules["math"]`.

Diagram:

```
Before:  sys.modules = { "math": <module math>, ... }
         current globals = {}

After:   import math
         sys.modules = { "math": <module math>, ... }  # same object, maybe newly added
         current globals = { "math": <module math> }   # new local binding → same object
```

You can have multiple import statements for the same module — they all share the singleton:

```python
import math
import math as m  # alias — still sys.modules["math"]
import math       # no-op execution — already cached

print(math is m)                        # True — same object
import sys
print(math is sys.modules["math"])      # True
```

### 2.2 `import module as alias`

```python
import numpy as np
import pandas as pd
import mymath as mm
import os.path as osp   # binds only `osp`, not `os`

print(np.array([1, 2, 3]))
print(mm.PI)
print(osp.join("a", "b"))  # via osp, not os
# print(os)  # NameError — `import os.path as osp` binds ONLY `osp`
```

Rules for `import ... as`:

```python
import a.b.c           # binds `a` (top-level package) in current namespace
import a.b.c as alias  # binds `alias` → sys.modules["a.b.c"], does NOT bind `a`

# Demonstration:
import os.path          # binds `os`
print(os)               # <module 'os'>
print(os.path)          # <module 'posixpath'>

import os.path as p     # binds only `p`
print(p)                # <module 'posixpath'>
# Which `os` is visible now? The earlier `os` binding is still there
# only because the previous `import os.path` bound it. If you ONLY do
# `import os.path as p` without a prior `import os`, then `os` is NOT bound.

# Clean demonstration in a fresh namespace (simulate with a function):
def demo_alias_binding():
    # Fresh local scope
    import os.path as osp2
    print("osp2" in locals())  # True
    print("os" in locals())    # False — only alias is bound
    # But sys.modules still has both:
    import sys
    print("os" in sys.modules)       # True
    print("os.path" in sys.modules)  # True

demo_alias_binding()
```

> **Common mistake:** Thinking `import a.b as x` also binds `a`. It does not. Only `x` is bound. If you need `a`, import it separately.

### 2.3 `from module import name`

```python
from math import sqrt, pi
from mymath import circle_area
from os.path import join, exists

print(sqrt(25))          # 5.0 — no `math.` prefix
print(pi)                # 3.14159...
print(circle_area(5))    # direct name in current namespace
```

What it does:

1. Ensure `math` is loaded (same caching as `import math` — executes file once, populates `sys.modules["math"]`).
2. Look up `sqrt` inside `sys.modules["math"].__dict__`.
3. Bind the name `sqrt` in the **current namespace** to that object.

```python
# These are equivalent at the binding level (but `from` is more convenient):
import math
sqrt = math.sqrt     # manual equivalent of `from math import sqrt`

from math import sqrt  # idiomatic — does the same thing in one statement
```

Critical distinction:

| Form | What is bound locally | Module executed? | Module cached? |
|---|---|---|---|
| `import math` | `math` → module object | Once | Yes (`sys.modules`) |
| `import math as m` | `m` → module object | Once | Yes |
| `from math import sqrt` | `sqrt` → function object | Once (whole module) | Yes — entire `math` is still loaded |
| `from math import sqrt as sq` | `sq` → function object | Once | Yes |

```python
# `from` still loads the ENTIRE module — it just exposes one name:
from math import sqrt
import sys
print("math" in sys.modules)  # True — full math module is loaded
print(sys.modules["math"].sqrt is sqrt)  # True — same function object

# So `from` is NOT cheaper than `import` — same execution cost.
# The difference is purely which names appear in YOUR namespace.
```

### 2.4 `from module import name as alias`

```python
from math import sqrt as square_root
from collections import Counter as Bag
from mymath import circle_area as area

print(square_root(16))  # 4.0
print(Bag("hello"))     # Counter({'l': 2, ...})
```

Combines the `from` lookup with an alias bind. Useful to avoid collisions or to shorten long names:

```python
# Realistic aliasing for collision avoidance:
from json import load as json_load
from yaml import load as yaml_load  # if both expose `load`, alias to disambiguate

# Or to follow conventions:
from datetime import datetime as DateTime  # rare — usually just `import datetime`
```

### 2.5 `from module import *` — why not to use it

```python
# File: bad_star.py
from math import *    # imports EVERYTHING not starting with _
from os import *      # overwrites names from math without warning

print(sqrt(16))  # works, but where did sqrt come from? Hard to trace.
# print(pi) — is this math.pi or did os overwrite it? You must check.
```

Problems:

- **Namespace pollution:** Dumps dozens of names into your namespace; you may not know which module each comes from.
- **Silent overwriting:** If two modules define `open`, the second `import *` wins silently.
- **Linter blindness:** Tools like `ruff`, `pylint` cannot detect undefined names or unused imports when `*` is used.
- **Breaks on refactor:** Adding a name to a module can silently break importers that used `*` (new name shadows a local).

PEP 8:

> Wildcard imports (`from <module> import *`) should be avoided, as they make it unclear which names are present in the namespace, confusing both readers and many automated tools.

The one legitimate use is in interactive exploration and in `__init__.py` re-exports with an explicit `__all__` (see lesson 05.2), but even there `from .sub import name` is preferred.

```python
# If a module defines __all__, `from module import *` imports only those names:
# File: mymodule.py
__all__ = ["public_func", "PUBLIC_CONST"]
PUBLIC_CONST = 42
public_func = lambda: "hello"
_private_helper = lambda: "hidden"
internal = 99

# from mymodule import *  → imports only public_func, PUBLIC_CONST
# Without __all__, it imports all names not starting with _
```

### 2.6 `import` is executable and scoped

Like `def`, `import` is an **executable statement** that runs when control flow reaches it, and it respects scope:

```python
# Conditional import — common for optional dependencies or platform-specific code
try:
    import orjson as json_lib
except ImportError:
    import json as json_lib  # fallback

print(json_lib.dumps({"key": "value"}))

# Import inside a function — local binding, lazy loading
def process(data: str):
    import json  # json is local to this function
    return json.loads(data)

print(process('{"a": 1}'))
# print(json)  # NameError outside the function — json was local to process()

# Import inside an if — only executes if the branch is taken
DEBUG = False
if DEBUG:
    import logging  # not executed, not even searched, when DEBUG is False

# Import at module top is convention (PEP 8) — but not required by the language
```

PEP 8 mandates top-level imports for discoverability. Function-local imports are justified when:

- Avoiding a circular import (defer import until runtime call time).
- Avoiding heavy import cost at startup (e.g., `import tensorflow` inside a function that may not be called).
- Optional dependencies.

## 3. Import Execution Model — Once, Then Cached

This is the single most important thing to internalise about Python's import system.

### 3.1 The `sys.modules` cache

`sys.modules` is a plain `dict[str, module]` that the interpreter consults on every import. It is the **module singleton registry**.

```python
import sys

# Before any import of mymath, the key is absent:
print("mymath" in sys.modules)  # False (assuming first run)

import mymath  # executes mymath.py top-to-bottom NOW
print("mymath" in sys.modules)  # True
print(sys.modules["mymath"] is mymath)  # True — same object

# Second import — NO re-execution:
import mymath  # hits cache, does nothing except re-bind local name
import mymath as mm2
from mymath import PI

print(mymath is mm2)  # True
print(PI is mymath.PI)  # True (for immutable float, `is` may vary by interning — use == for values)

# Even `import importlib; importlib.import_module("mymath")` returns the cached object:
import importlib
print(importlib.import_module("mymath") is mymath)  # True
```

What "executes once" means concretely:

```python
# File: counted.py
print("[counted] executing top-level code")

counter = 0

def bump():
    global counter
    counter += 1
    return counter

print(f"[counted] initial counter={counter}")
```

```python
import counted  # prints both lines above
print(counted.counter)  # 0

counted.bump()
print(counted.counter)  # 1

import counted  # prints NOTHING — cached, not re-executed
print(counted.counter)  # still 1 — state preserved!

# Another module importing counted sees the SAME object:
# File: other.py
# import counted
# print(counted.counter)  # 1 — sees the bumped value!
```

This singleton property is powerful: modules are a natural place for shared state (configuration, connection pools, registries) because every importer shares the same object. It is also why **import-time side effects are dangerous** — they run once, implicitly, and the order matters.

### 3.2 What counts as "import-time" code?

Every statement at module top level that is not inside a `def` or `class` runs at import time:

```python
# File: side_effects.py
import os

# --- All of this runs at import time ---
print("side_effects is being imported")  # runs immediately

CONFIG = {"debug": True}                  # runs — creates module global
CONFIG_PATH = os.path.join("/etc", "app.conf")  # runs — calls function

for i in range(3):                        # runs — loop at import time
    print(f"  loop iteration {i}")

def helper():                             # `def` itself runs (creates function object)
    print("helper body — runs only when helper() is called")

class MyClass:                            # `class` runs (executes class body)
    print("MyClass body — runs at import time")
    attr = 42

print("side_effects import finished")
```

```python
import side_effects
# Output order:
# side_effects is being imported
#   loop iteration 0
#   loop iteration 1
#   loop iteration 2
# MyClass body — runs at import time
# side_effects import finished

# Calling helper later does NOT re-run the top-level code:
side_effects.helper()  # prints "helper body — runs only when helper() is called"
```

**Guideline:** Keep top-level code minimal — definitions, constants, and guarded executable code (`if __name__ == "__main__":`). Avoid I/O, network, or heavy computation at the top level unless the module's purpose is to perform it.

### 3.3 Shared mutable state through the singleton

Because the module object is shared, mutable globals are shared:

```python
# File: shared_config.py
settings: dict[str, str] = {"env": "production"}

def set_env(env: str) -> None:
    settings["env"] = env

def get_env() -> str:
    return settings["env"]
```

```python
# File: app_a.py
import shared_config
print(shared_config.get_env())  # production
shared_config.set_env("staging")

# File: app_b.py  (imported later in the same process)
import shared_config
print(shared_config.get_env())  # staging — sees app_a's mutation!

# This is the same dict object:
# import shared_config; shared_config.settings is the one dict in sys.modules
```

This is the foundation for patterns like `logging` configuration: `logging.basicConfig()` mutates the shared `logging` module state, and all importers see the change.

> **Contrast with other languages:** In Node.js, `require()` also caches modules as singletons (similar). In Java, each `ClassLoader` loads a class once (similar caching). In C, `#include` is textual copy-paste with no caching — every translation unit re-parses headers.

### 3.4 Reloading — re-executing a module explicitly

Since import caches, editing a file and re-importing does **not** pick up changes. Use `importlib.reload`:

```python
import importlib
import mymath

# ... edit mymath.py on disk ...

importlib.reload(mymath)  # re-executes mymath.py inside the SAME module object
print(mymath.PI)          # new value if you changed it
```

Caveats (detailed in lesson 05.3):

- Only the reloaded module object is updated; names imported via `from mymath import PI` still point to the old `PI` object.
- Instances of classes defined before reload keep the old class object.
- Reload is mainly a REPL / development convenience, not for production.

```python
import mymath
from mymath import PI  # binds local name PI to the float object 3.14159

import importlib
# Suppose you change PI to 3.14 in mymath.py and reload:
importlib.reload(mymath)
print(mymath.PI)  # 3.14 — updated
print(PI)         # 3.14159 — stale! Local name still points to old float.
# Must re-do: from mymath import PI  after reload.
```

## 4. Aliasing — When and How

Aliasing (`as`) exists to solve three problems: brevity, collision, and convention.

### 4.1 Brevity

```python
import very_long_module_name as vlmn
import xml.etree.ElementTree as ET  # standard idiom

root = ET.Element("root")
```

### 4.2 Collision avoidance

```python
# Two modules both expose `load`:
from json import load as json_load
from pickle import load as pickle_load

# Without aliasing, the second `load` would overwrite the first.
data = json_load(open("data.json"))
obj = pickle_load(open("data.pkl", "rb"))
```

### 4.3 Conventional aliases — the ecosystem's short names

These aliases are so universal that deviating confuses readers:

| Module | Conventional alias | Example |
|---|---|---|
| `numpy` | `np` | `import numpy as np` |
| `pandas` | `pd` | `import pandas as pd` |
| `matplotlib.pyplot` | `plt` | `import matplotlib.pyplot as plt` |
| `tensorflow` | `tf` | `import tensorflow as tf` |
| `xml.etree.ElementTree` | `ET` | `import xml.etree.ElementTree as ET` |
| `tkinter` | `tk` | `import tkinter as tk` |

Using a non-standard alias (`import numpy as n`) is technically fine but violates reader expectations.

### 4.4 Aliasing does not copy — it is another reference

```python
import mymath as mm
import mymath as m2

print(mm is m2)              # True — both point to sys.modules["mymath"]
print(mm is sys.modules["mymath"])  # True

# Mutating through one alias is visible through the other:
mm.NEW_CONST = 999
print(m2.NEW_CONST)          # 999
print(mymath.NEW_CONST)      # 999 — if mymath was also imported, same object
```

## 5. Circular Imports — The Classic Pitfall

### 5.1 What is a circular import?

Module A imports module B, and module B imports module A (directly or transitively).

```
a.py ──imports──► b.py
 ▲                  │
 └────imports───────┘
```

### 5.2 Minimal failing example

```python
# File: a.py
print("[a] start")
import b           # ← pauses execution of a, starts executing b
print("[a] after import b")
x = 10
print(f"[a] x={x}")
```

```python
# File: b.py
print("[b] start")
import a           # ← a is already partially in sys.modules (empty shell)
print(f"[b] trying to use a.x = {a.x}")  # AttributeError — a.x not yet defined!
print("[b] after import a")
y = 20
print(f"[b] y={y}")
```

```python
# Running: python a.py
# [a] start
# [b] start
# AttributeError: partially initialized module 'a' has no attribute 'x'
#   (most likely due to a circular import)
```

Trace of what happens step-by-step:

1. `python a.py` starts executing `a.py`. Before any code, `sys.modules["a"]` is created as an empty shell, then top-level code runs.
2. `import b` — `sys.modules["b"]` doesn't exist, so create empty shell for `b`, start executing `b.py`.
3. `import a` inside `b.py` — `sys.modules["a"]` **already exists** (empty shell from step 1), so Python does **not** re-execute `a.py`. It just binds the name `a` to that half-initialised shell.
4. `a.x` lookup fails — `x = 10` in `a.py` hasn't run yet; execution is still paused at `import b` on line 2.

> Modern Python (3.6+) raises a clearer error: `"cannot import name 'x' from partially initialized module 'a' (most likely due to a circular import)"`. Older versions raised `AttributeError` or `ImportError` with less context.

### 5.3 Variations that fail differently

```python
# File: c.py
from d import y     # from-import tries to look up y immediately
x = 10

# File: d.py
from c import x     # circular — at this point c.x doesn't exist yet
y = 20

# python c.py → ImportError: cannot import name 'y' from partially initialized module 'd'
```

`from ... import name` is **stricter** than `import module` for circular imports because it must resolve the attribute right away, while `import module` merely binds the (possibly incomplete) module object.

### 5.4 Fixes — four strategies

#### Strategy 1: Restructure — extract shared code

The best long-term fix. Move the shared dependency to a third module:

```
Before:  a.py ↔ b.py (circular)

After:   a.py → shared.py ← b.py
         a.py ↔ b.py no longer directly circular
```

```python
# File: shared.py
SHARED_CONST = 42

def shared_helper() -> str:
    return "shared"

# File: a.py (now imports shared, not b)
import shared
x = 10
print(shared.SHARED_CONST)

# File: b.py (imports shared, not a — or imports a at function scope)
import shared
y = 20
```

#### Strategy 2: Move the import inside a function (deferred import)

If the circular dependency is only needed at call time, not at import time, delay it:

```python
# File: a.py  — fixed with deferred import
print("[a] start")
x = 10  # define BEFORE any circular import

def use_b():
    import b  # deferred — executes only when called, after both modules are fully loaded
    print(f"a.use_b: b.y={b.y}")

print("[a] done, x defined")
```

```python
# File: b.py — fixed
print("[b] start")
y = 20

def use_a():
    import a
    print(f"b.use_a: a.x={a.x}")

print("[b] done")
```

```python
# app.py
import a
import b
a.use_b()  # works — both modules are fully initialised by now
b.use_a()  # works
```

Deferred imports are legitimate for breaking cycles, but document why the import is not at the top.

#### Strategy 3: Import the module, not the name — access attribute late

```python
# File: a.py — alternative fix
import b  # keep at top — but don't access b.y at top level
x = 10

def get_b_y():
    return b.y  # looked up at CALL time, after b is fully loaded

# File: b.py
import a
y = 20

def get_a_x():
    return a.x
```

This works if neither module accesses the other's attributes at **import time**. The key distinction:

```python
# BAD — access at import time (during circular execution, attribute missing):
import b
print(b.y)  # runs immediately during import — fails if b not yet fully loaded

# OK — access at call time (after all imports have finished):
import b
def get(): return b.y  # body not executed until called
```

#### Strategy 4: Guard with `if TYPE_CHECKING` for type hints

Type annotations cause circular imports when two modules annotate each other:

```python
# File: models.py
from __future__ import annotations  # defers annotation evaluation (PEP 563 / 649)
from typing import TYPE_CHECKING

if TYPE_CHECKING:          # False at runtime, True for type checkers (mypy, pyright)
    from services import UserService  # only for typing, not at runtime

class User:
    def __init__(self, name: str) -> None:
        self.name = name

    def get_service(self) -> UserService:  # string annotation — no runtime import needed
        from services import UserService    # local import if needed at runtime
        return UserService(self)
```

This is the idiomatic way to handle annotation-only cycles without restructuring.

### 5.5 Detecting and diagnosing circular imports

```python
# Helpful diagnostics when you hit an ImportError:
import sys

# 1. Check what is actually in sys.modules at the failure point:
try:
    import a
except ImportError as e:
    print(f"ImportError: {e}")
    print(f"'a' in sys.modules: {'a' in sys.modules}")
    if "a" in sys.modules:
        print(f"a module dir: {dir(sys.modules['a'])}")
        print(f"a.__spec__: {sys.modules['a'].__spec__}")

# 2. Use python -v (verbose imports) to see the import trace:
#    python -v app.py 2>&1 | grep import

# 3. Use importlib.util.find_spec to test findability without executing:
import importlib.util
print(importlib.util.find_spec("a"))  # None if not findable, ModuleSpec if findable
```

## 6. Import Styles Compared — Decision Table

| Style | Names bound locally | Use when | Avoid when |
|---|---|---|---|
| `import mod` | `mod` | Default; clarity of origin; namespace grouping | Module name is very long and used heavily |
| `import mod as alias` | `alias` | Long name, conventional shorthand (`np`, `pd`), collision | Non-standard alias confuses readers |
| `from mod import name` | `name` | Name used heavily; re-exporting; well-known names (`Path`, `dataclass`) | Namespace clarity matters; many names imported |
| `from mod import name as alias` | `alias` | Collision between two `load`/`open`/`Config` names | Unnecessary aliasing for single use |
| `from mod import *` | All public names | Never in production code | Almost always |
| `import pkg.mod` | `pkg` | Accessing submodules (packages, lesson 05.2) | You only need the leaf — consider `from pkg import mod` |

### 6.1 Which form to choose — guidance

```python
# Good — explicit, searchable, grep-friendly:
import os
import sys
from pathlib import Path
from dataclasses import dataclass, field
import numpy as np

def process(path: Path) -> None:
    config = os.environ.get("APP_CONFIG", "")
    p = Path(path)
    print(p.exists())

# Acceptable — single well-known import:
from collections import Counter, defaultdict

# Avoid — pollutes namespace, hides origin:
# from os import *
# from pathlib import *
```

A useful heuristic: **if a reader sees `foo(...)` in your code, they should be able to guess instantly where `foo` comes from**. `Path(...)` and `Counter(...)` are distinctive enough; `load(...)` is not — prefer `json.load(...)` or `json_load`.

## 7. Module Search — A Brief Preview

When Python executes `import mymath`, how does it find `mymath.py`? The full machinery is in lesson 05.3, but briefly:

```python
import sys
import pprint

pprint.pprint(sys.path)
# ['/current/working/dir',           # 0 — script's directory or '' for REPL
#  '/usr/lib/python3.12',             # stdlib
#  '/usr/lib/python3.12/lib-dynload', # C extensions
#  '/home/user/.venv/lib/.../site-packages',  # third-party
# ]

# Python searches each entry in order for a matching file or package:
#   mymath.py  |  mymath/__init__.py  |  mymath.cpython-312.so  |  etc.
```

If no entry contains the module, `ModuleNotFoundError` (a subclass of `ImportError`) is raised.

```
ImportError hierarchy:
  ImportError
  ├── ModuleNotFoundError  (module not found on sys.path)
  └── ZipImportError       (zip import failure)
```

## 8. Realistic Example — A Small Utility Module Used Two Ways

```python
# File: text_utils.py
"""Text helpers — demonstrates module structure, caching, and aliasing."""

import re
import string

# --- Module-level constants — immutable, UPPER_CASE by PEP 8 ---
_WORD_RE = re.compile(r"\b\w+\b")          # private — leading underscore
PUNCTUATION = set(string.punctuation)       # public — no underscore

# --- Public API ---
def tokenize(text: str) -> list[str]:
    """Split text into lowercase word tokens, stripping punctuation."""
    return _WORD_RE.findall(text.lower())

def word_count(text: str) -> int:
    """Return number of words in text."""
    return len(tokenize(text))

def most_common(text: str, n: int = 5) -> list[tuple[str, int]]:
    """Return n most common words as (word, count) pairs."""
    from collections import Counter  # local import — Counter only needed here
    return Counter(tokenize(text)).most_common(n)

# --- Module introspection for debugging ---
def _debug_info() -> dict:
    """Return module metadata — useful when tracing import issues."""
    import sys
    mod = sys.modules[__name__]
    return {
        "name": mod.__name__,
        "file": getattr(mod, "__file__", None),
        "cached": getattr(mod, "__cached__", None),
        "keys": [k for k in mod.__dict__ if not k.startswith("__")],
    }
```

Usage from two different styles:

```python
# File: app_import_styles.py
"""Shows three import styles for the same module."""

# Style 1 — import the module (most explicit):
import text_utils
print(text_utils.word_count("hello world hello"))  # 3
print(text_utils.most_common("hello world hello"))  # [('hello', 2), ('world', 1)]

# Style 2 — from-import selected names (convenient when used heavily):
from text_utils import tokenize, word_count
print(tokenize("Hello, World!"))  # ['hello', 'world']
print(word_count("one two three"))  # 3

# Style 3 — alias (when name is long or conflicts):
import text_utils as tu
print(tu.PUNCTUATION)  # {',', '.', '!', ...}

# All three share the SAME module object:
import sys
print(sys.modules["text_utils"] is text_utils)  # True
from text_utils import PUNCTUATION
print(PUNCTUATION is text_utils.PUNCTUATION)  # True — same set object

# Mutating through one view is visible everywhere — singleton!
text_utils.PUNCTUATION.add("§")
print("§" in tu.PUNCTUATION)  # True
print("§" in PUNCTUATION)     # True — all aliases see it

# Introspection:
import pprint
pprint.pprint(text_utils._debug_info())
```

Circular import avoidance in the same project:

```python
# File: app_main.py — avoids circular import by deferring one direction
"""Main entry point — imports both helpers without creating a cycle."""

# text_utils.py does NOT import app_main.py — no cycle.
# If it needed something from app_main, we would defer:

# Inside text_utils.py, instead of top-level `import app_main`:
# def needs_app_config():
#     import app_main  # deferred — only when called
#     return app_main.CONFIG

import text_utils

CONFIG = {"app_name": "demo"}

def main() -> None:
    text = "Hello world, hello Python, hello modules"
    print(f"App: {CONFIG['app_name']}")
    print(f"Words: {text_utils.word_count(text)}")
    print(f"Top: {text_utils.most_common(text, 2)}")

if __name__ == "__main__":
    main()
```

## 9. Common Mistakes and Edge Cases

### 9.1 Shadowing a standard library module

```python
# File: random.py  ← DON'T name your file random.py if you need `import random`!
import random  # imports YOURSELF, not the stdlib — circular or wrong module
print(random.randint(1, 10))  # AttributeError — your file has no randint

# Fix: rename your file to my_random.py or similar. Never shadow stdlib names.
# Common traps: random.py, os.py, sys.py, json.py, collections.py, email.py
```

Python searches `sys.path[0]` (the script directory) first — so a local `random.py` shadows the stdlib. This is the most common "import works on one machine but not another" bug (different working directories).

### 9.2 `from module import name` copies the reference, not a live link

```python
# File: config.py
threshold = 10
items = [1, 2, 3]

# File: app.py
from config import threshold, items

print(threshold)  # 10
print(items)      # [1, 2, 3]

# Mutating the mutable object — visible through both names:
items.append(4)
import config
print(config.items)  # [1, 2, 3, 4] — same list object, mutation visible

# Rebinding the immutable — NOT visible through the from-imported name:
config.threshold = 99
print(threshold)          # 10 — stale! Local `threshold` still points to old int 10
print(config.threshold)   # 99 — module's attribute updated

# Must re-import to see new binding:
from config import threshold as new_threshold
print(new_threshold)  # 99
```

This is the same reason `importlib.reload` caveats matter: `from` creates a separate local binding that is not updated when the source module rebinds a name. `import config` + `config.threshold` always reflects the current value.

### 9.3 Importing a submodule does not automatically import the parent's names

```python
# Package layout:
# mypkg/
#   __init__.py  (defines mypkg.helper)
#   sub.py

# mypkg/__init__.py:
# def helper(): return "helper"

# mypkg/sub.py:
# value = 42

import mypkg.sub
print(mypkg.sub.value)  # 42
print(mypkg.helper())   # works — mypkg was loaded as part of loading mypkg.sub
# But: `import mypkg.sub` binds only `mypkg`, not `sub` directly
# print(sub)  # NameError — only `mypkg` is bound, access via mypkg.sub

from mypkg import sub  # binds `sub` locally
print(sub.value)  # 42

from mypkg.sub import value  # binds `value` directly
print(value)  # 42
```

### 9.4 `import` inside a function creates a local, not a global

```python
def load_json(path: str):
    import json  # local to load_json
    with open(path) as f:
        return json.load(f)

# print(json)  # NameError — json not in module globals

# If you need it globally, import at the top:
import json
def load_json2(path: str):
    with open(path) as f:
        return json.load(f)
```

### 9.5 `__all__` and `from module import *`

```python
# File: mypackage.py
__all__ = ["public_api"]
public_api = lambda: "public"
_internal = lambda: "private"
other = lambda: "also public but not in __all__"

# from mypackage import *  → only `public_api` is imported
# Without __all__, `*` would import `public_api` and `other` (no leading underscore)
```

Define `__all__` when your module is intended to be used with `from ... import *` (rare) or to declare the public API for tools and documentation. It also affects `help()` and `pydoc` display.

### 9.6 Relative imports only work inside packages (not as scripts)

```python
# mypkg/sub.py tries:
# from . import helper  # ImportError when run as `python mypkg/sub.py`
# Because running a file as a script sets __package__ = None — relative imports need a package

# Fix — run as a module:
# python -m mypkg.sub   # works — __package__ is 'mypkg'
```

This is covered in depth in lesson 05.2.

## 10. Quick Reference

| Concept | One-liner |
|---|---|
| Module | Object created by executing a `.py` file; cached in `sys.modules` |
| `__name__` | Import name (`"pkg.mod"` or `"__main__"` when run as script) |
| `__file__` | Path to source, if any (absent for built-ins / namespace packages) |
| `__dict__` | Module's namespace dict (`globals()` inside the module) |
| `import mod` | Load (once) + cache + bind `mod` locally |
| `import mod as alias` | Load + bind `alias` only |
| `from mod import name` | Load whole `mod` + bind `name` locally (copy of reference) |
| `from mod import *` | Avoid — pollutes namespace, hides origin |
| `sys.modules` | `dict[str, module]` singleton registry; second import is a cache hit |
| Shared state | Module globals are singleton — mutation visible to all importers |
| Circular import | Two modules importing each other; half-initialised shell causes errors |
| Fix cycles | Restructure, defer `import` into function, access at call time, `TYPE_CHECKING` guard |
