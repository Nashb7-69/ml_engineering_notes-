## 1. From Module to Package — Why Directories?

A **module** is a single file. When a project grows beyond a handful of files, flat files become unwieldy — names collide, concerns mix, and discoverability drops. A **package** is a module that can contain other modules (and other packages).

Concretely, a package is a directory that Python treats as a module with a `__path__` attribute:

```
Project layout:

myproject/
├── app.py
├── utils.py          ← module (file)
├── models.py         ← module (file)
└── services/         ← package (directory)
    ├── __init__.py   ← makes it a regular package (may be empty)
    ├── email.py      ← submodule: services.email
    └── auth.py       ← submodule: services.auth
```

```python
import utils           # module — from utils.py
import services        # package — from services/__init__.py
import services.email  # submodule — from services/email.py
import services.auth   # submodule — from services/auth.py

print(type(utils))            # <class 'module'>
print(type(services))         # <class 'module'> — packages ARE modules
print(hasattr(services, "__path__"))  # True — packages have __path__, plain modules don't
print(hasattr(utils, "__path__"))     # False
```

> **Key distinction:** Every package is a module (it is a module object in `sys.modules`), but not every module is a package. The distinguishing attribute is `__path__` (a list of directory paths used to search for submodules).

| Concept | On disk | In `sys.modules` | Has `__path__` | Has `__file__` |
|---|---|---|---|---|
| Module | `mymod.py` | `sys.modules["mymod"]` | No | Yes |
| Regular package | `mypkg/__init__.py` | `sys.modules["mypkg"]` | Yes | Yes (points to `__init__.py`) |
| Namespace package (PEP 420) | `nspkg/` (no `__init__.py`) | `sys.modules["nspkg"]` | Yes | No |
| Submodule | `mypkg/sub.py` | `sys.modules["mypkg.sub"]` | No | Yes |
| Subpackage | `mypkg/subpkg/__init__.py` | `sys.modules["mypkg.subpkg"]` | Yes | Yes |

## 2. Regular Packages — The `__init__.py` File

### 2.1 What `__init__.py` does

When Python imports a regular package, it **executes `__init__.py`** top-to-bottom to initialise the package's namespace, exactly as it executes a `.py` file for a plain module. The package object is created first (empty shell in `sys.modules`), then `__init__.py` runs inside it.

```
mypkg/
├── __init__.py
├── core.py
└── helpers.py
```

```python
# File: mypkg/__init__.py
"""My package — top-level API."""

print("[mypkg] __init__.py executing")

VERSION = "1.0.0"

def package_helper() -> str:
    return "helper from mypkg"

# Eagerly import submodules to expose them as attributes:
from . import core  # relative import — mypkg.core

print(f"[mypkg] __init__ done, VERSION={VERSION}")
```

```python
# File: mypkg/core.py
"""Core submodule."""

print("[mypkg.core] loading")

def compute(x: int) -> int:
    return x * 2
```

```python
# Importer:
import mypkg

# Output at import time:
# [mypkg] __init__.py executing
# [mypkg.core] loading        ← because __init__ did `from . import core`
# [mypkg] __init__ done, VERSION=1.0.0

print(mypkg.VERSION)          # 1.0.0 — defined in __init__.py
print(mypkg.package_helper()) # helper from mypkg
print(mypkg.core.compute(5))  # 10 — submodule accessible as attribute

# Introspection:
print(mypkg.__name__)    # 'mypkg'
print(mypkg.__file__)    # '/path/to/mypkg/__init__.py'
print(mypkg.__path__)    # ['/path/to/mypkg'] — list with the package directory
print(mypkg.__package__) # 'mypkg'
```

Without that `from . import core` line, `mypkg.core` would **not** be accessible as `mypkg.core` immediately after `import mypkg` — you would need to `import mypkg.core` separately. This is a common surprise.

### 2.2 The `__init__.py` may be empty

```python
# File: mypkg/__init__.py
# (empty file — or just a docstring)
"""Empty init — package exists but defines no extra names."""
```

```python
import mypkg
print(mypkg.__path__)           # ['/path/to/mypkg'] — still a package
# print(mypkg.core)             # AttributeError — not imported, not defined
import mypkg.core               # now load it explicitly
print(mypkg.core.compute(5))    # 10 — works, and now mypkg.core is also an attribute
```

An empty `__init__.py` is enough to mark the directory as a regular package. In Python 3.3+ you can even omit it (namespace package), but an empty `__init__.py` is still the most explicit, portable, and commonly used approach — see section 6.

### 2.3 What to put in `__init__.py` — design guidance

`__init__.py` is the package's public front door. Good candidates:

- Package metadata: `__version__`, `__author__`, `__all__`.
- Re-exports: convenient short-path imports for the package's main API.
- Package-level initialisation: logging setup, plugin registration (minimal; avoid heavy I/O).

Anti-patterns for `__init__.py`:

- Heavy computation or I/O at import time — slows every import of any submodule.
- Circular import triggers — if `__init__.py` imports a submodule that imports from the package.

```python
# Good __init__.py — re-export pattern:
# File: mypkg/__init__.py
"""mypkg — public API at the top level for convenience."""

from .core import compute, Engine
from .helpers import format_result

__version__ = "2.1.0"
__all__ = ["compute", "Engine", "format_result", "__version__"]
```

```python
# Now users can do either:
from mypkg import compute          # short path — via re-export
from mypkg.core import compute     # long path — direct
import mypkg
print(mypkg.compute)               # works because __init__ re-exported it

# Both forms reference the SAME object:
from mypkg import compute as c1
from mypkg.core import compute as c2
print(c1 is c2)                    # True — re-export binds the same object
```

> **Trade-off:** Re-exports make the API convenient but add import-time cost (submodules are loaded when the package is imported) and can create circular imports. For large packages, consider a "lazy" alternative (PEP 562 `__getattr__` at package level) — see advanced section 8.

## 3. Package Structure — Subpackages and Nesting

Packages nest arbitrarily deep. Each directory level with an `__init__.py` is a subpackage.

```
ecommerce/
├── __init__.py
├── config.py
├── orders/
│   ├── __init__.py
│   ├── cart.py
│   └── checkout.py
├── payments/
│   ├── __init__.py
│   ├── gateway.py
│   └── refunds.py
└── utils/
    ├── __init__.py
    ├── money.py
    └── text.py
```

Full qualified names:

```
ecommerce                   → package (ecommerce/__init__.py)
ecommerce.config            → module  (ecommerce/config.py)
ecommerce.orders            → subpackage (ecommerce/orders/__init__.py)
ecommerce.orders.cart       → module  (ecommerce/orders/cart.py)
ecommerce.orders.checkout   → module  (ecommerce/orders/checkout.py)
ecommerce.payments.gateway  → module  (ecommerce/payments/gateway.py)
ecommerce.utils.money       → module  (ecommerce/utils/money.py)
```

```python
# Importing at various depths:
import ecommerce
import ecommerce.orders.cart
from ecommerce.payments import gateway
from ecommerce.utils.money import format_price

# Each `import` loads the parent packages first (as empty shells, then their __init__.py):
# import ecommerce.orders.cart does:
#   1. Load `ecommerce` (__init__.py executing)
#   2. Load `ecommerce.orders` (__init__.py executing)
#   3. Load `ecommerce.orders.cart` (cart.py executing)
# Each is cached in sys.modules under its fully-qualified name.

import sys
print("ecommerce" in sys.modules)                # True
print("ecommerce.orders" in sys.modules)          # True
print("ecommerce.orders.cart" in sys.modules)     # True

# Binding subtlety — what name is bound locally?
import ecommerce.orders.cart        # binds `ecommerce` (top-level)
print(ecommerce.orders.cart)        # access leaf through chain

import ecommerce.orders.cart as cart  # binds only `cart`
print(cart)                         # <module 'ecommerce.orders.cart'>

from ecommerce.orders import cart   # binds `cart`
from ecommerce.orders.cart import Cart  # binds `Cart` class, loads cart module as side effect
```

### 3.1 Subpackage `__init__.py` executes independently

```python
# File: ecommerce/__init__.py
print("[ecommerce] init")

# File: ecommerce/orders/__init__.py
print("[ecommerce.orders] init")

# File: ecommerce/orders/cart.py
print("[ecommerce.orders.cart] loading")

# Now:
import ecommerce.orders.cart
# Output:
# [ecommerce] init
# [ecommerce.orders] init
# [ecommerce.orders.cart] loading

# But importing only the top level does NOT automatically load subpackages:
# import ecommerce  → only [ecommerce] init, subpackages NOT loaded yet
```

## 4. Relative Imports — `.` and `..`

Relative imports use leading dots to mean "relative to the current package." They work **only inside packages** (when `__package__` is set).

### 4.1 Dot semantics

| Syntax | Meaning | Example inside `ecommerce.orders.cart` |
|---|---|---|
| `from . import helpers` | Same package | `ecommerce.orders.helpers` |
| `from .cart import Cart` | Same package, submodule | `ecommerce.orders.cart` |
| `from .. import config` | Parent package | `ecommerce.config` |
| `from ..utils import money` | Sibling of parent | `ecommerce.utils.money` |
| `from ... import top` | Grandparent | `ecommerce.top` (if exists) |
| `from . import *` | Same-package star import | Avoid |

```python
# File: ecommerce/orders/cart.py
"""Cart logic — demonstrates relative imports."""

# Relative import — same package:
from .checkout import Checkout        # ecommerce.orders.checkout
from . import cart_utils              # ecommerce.orders.cart_utils (if exists)

# Relative import — parent package:
from .. import config                 # ecommerce.config
from ..utils.money import format_price  # ecommerce.utils.money

# Relative import — two levels up (if nesting were deeper):
# from ... import something

def create_cart():
    price = format_price(19.99)
    cfg = config.SETTINGS
    print(f"Cart with {price}, config={cfg}")
```

Equivalent absolute form:

```python
# Absolute equivalents (either style works; PEP 8 prefers absolute):
from ecommerce.orders.checkout import Checkout
import ecommerce.config as config
from ecommerce.utils.money import format_price
```

### 4.2 When relative imports fail

```python
# Running a file as a script breaks relative imports:
# python ecommerce/orders/cart.py  →  ImportError: attempted relative import with no known parent package
# Because: __package__ is None when run as `__main__`

# Correct — run as a module so that __package__ is set:
# python -m ecommerce.orders.cart  →  works, __package__ is 'ecommerce.orders'

# Or make the file not use relative imports when run standalone:
# if __name__ == "__main__":
#     # use absolute imports or adjust sys.path — but prefer `python -m`
```

Why: relative imports resolve against `__package__`, which is derived from `__name__`. When `__name__ == "__main__"`, Python has no package context. The fix is always: run with `-m` or refactor so the script entry point is outside the package (see lesson 05.5).

### 4.3 Relative import constraints

```python
# Inside a top-level module (not inside a package), even `.` fails:
# File: standalone.py  (not inside any package)
# from . import something  # ImportError: attempted relative import with no known parent package

# You cannot go above the top-level package:
# Inside ecommerce/__init__.py:
# from .. import something  # ImportError: attempted relative import beyond top-level package
# There is no parent of the top-level package.

# Level must match nesting depth:
# Inside ecommerce/orders/cart.py (depth 3: ecommerce.orders.cart):
#   .   → ecommerce.orders        ✓
#   ..  → ecommerce               ✓
#   ... → (beyond)                ✗ ImportError
```

### 4.4 Absolute vs relative — PEP 8 guidance

PEP 8 recommends **absolute imports** as the default because they are explicit, searchable, and refactor-safe. Relative imports are preferred when:

- Avoiding hard-coding the top-level package name (useful if the package may be renamed or is a subpackage that might move).
- The package is deep and absolute names would be very long.

```python
# Absolute — explicit, recommended for most cases:
from ecommerce.utils.money import format_price
from ecommerce.config import SETTINGS

# Relative — concise for siblings:
from ..utils.money import format_price
from .. import config

# Many projects use absolute throughout for grep-friendliness:
# Searching for `ecommerce.utils.money` finds all absolute importers.
# Relative imports are invisible to such searches.
```

Both are correct. Many style guides require absolute. Pick one convention per project.

## 5. Package vs Module — Detailed Comparison

### 5.1 How to tell at runtime

```python
import ecommerce
import ecommerce.orders.cart
import math

# The reliable test is __path__:
print(hasattr(ecommerce, "__path__"))              # True — package
print(hasattr(ecommerce.orders, "__path__"))        # True — subpackage
print(hasattr(ecommerce.orders.cart, "__path__"))   # False — module
print(hasattr(math, "__path__"))                    # False — module (built-in has no __path__)

# Another test — __spec__.submodule_search_locations:
print(ecommerce.__spec__.submodule_search_locations)             # ['/path/to/ecommerce']
print(ecommerce.orders.cart.__spec__.submodule_search_locations) # None — not a package
print(math.__spec__.submodule_search_locations)                   # None

# Inspecting the file system:
import pathlib
print(pathlib.Path(ecommerce.__file__))            # .../ecommerce/__init__.py
print(pathlib.Path(ecommerce.orders.cart.__file__)) # .../ecommerce/orders/cart.py
```

### 5.2 Import behaviour differences

```python
# You can import submodules with `import package.submodule`:
import ecommerce.orders.cart
# This loads (if needed): ecommerce → ecommerce.orders → ecommerce.orders.cart
# But you CANNOT do `import module.submodule` for a plain module — it has no submodules.

# Attribute access:
# After `import ecommerce.orders.cart`, `ecommerce.orders.cart` is accessible as attribute chain:
print(ecommerce.orders.cart)  # the module object, via attribute resolution

# But after `import ecommerce`, submodules are NOT automatically loaded:
import ecommerce  # only ecommerce/__init__.py runs
# print(ecommerce.orders)  # AttributeError if __init__.py didn't import it
```

This asymmetry is intentional: loading every submodule eagerly would be slow. Python loads lazily — each submodule is loaded only when explicitly imported.

## 6. Namespace Packages (PEP 420) — Packages Without `__init__.py`

Introduced in Python 3.3, namespace packages allow a package to exist **without** an `__init__.py`, spanning multiple directories on `sys.path`.

### 6.1 Regular vs namespace

```
Regular package (needs __init__.py):

mypkg/
└── __init__.py   ← required; executed on import; defines package namespace
└── sub.py

Namespace package (no __init__.py):

nspkg/
├── sub_a.py
└── sub_b.py       ← no __init__.py — still importable as `nspkg`
```

```python
# Regular package:
import mypkg
print(mypkg.__file__)    # '/path/to/mypkg/__init__.py'
print(mypkg.__path__)    # ['/path/to/mypkg']
print(mypkg.__spec__.loader)  # SourceFileLoader for __init__.py

# Namespace package (if nspkg has no __init__.py):
import nspkg
print(hasattr(nspkg, "__file__"))  # False — no single file
print(nspkg.__path__)              # _NamespacePath(['/path/to/nspkg']) — special path object
print(nspkg.__spec__.loader)       # None — no loader
print(nspkg.__spec__.submodule_search_locations)  # ['/path/to/nspkg']
```

### 6.2 The killer feature — split across directories

A namespace package can be **distributed** across multiple directories on `sys.path`, and Python merges them:

```
# Directory structure on disk:
# /path/one/nspkg/
# └── foo.py
# /path/two/nspkg/
# └── bar.py
# (neither has __init__.py)
```

```python
import sys
sys.path.insert(0, "/path/one")
sys.path.insert(0, "/path/two")

import nspkg
print(nspkg.__path__)  # _NamespacePath(['/path/two/nspkg', '/path/one/nspkg'])

import nspkg.foo  # from /path/one/nspkg/foo.py
import nspkg.bar  # from /path/two/nspkg/bar.py
# Both found because __path__ spans both directories.
```

Use cases:

- **Large organisations** where different teams contribute subpackages to a shared namespace (e.g., `company.auth` and `company.billing` developed independently).
- **Plugin systems** where plugins register under a namespace.
- **`pkgutil`-style** distributed packages (legacy — now superseded by PEP 420).

```
Real-world example: `google` namespace
  pip install google-cloud-storage  → google/cloud/storage/
  pip install google-cloud-bigquery → google/cloud/bigquery/
  Both contribute to `google` namespace — no single __init__.py owns it.
```

### 6.3 Regular vs namespace — behaviour comparison

| Aspect | Regular package (`__init__.py` exists) | Namespace package (no `__init__.py`) |
|---|---|---|
| `__file__` | `.../__init__.py` | absent (`AttributeError`) |
| `__path__` | `[".../pkg"]` (list) | `_NamespacePath([...])` (iterable, dynamic) |
| `__loader__` / `__spec__.loader` | `SourceFileLoader` | `None` |
| Code execution on `import pkg` | Executes `__init__.py` | Nothing to execute — just creates namespace |
| Can contain `__init__` logic | Yes | No — no file to put it in |
| Can define `__all__`, `__version__` | Yes, in `__init__.py` | No top-level file — must use a submodule |
| Single vs split location | One directory | Can span multiple `sys.path` entries |
| Recommendation | Default — explicit, supports init logic | Only when split distribution is needed |

### 6.4 Migrating between the two

If a directory lacks `__init__.py`, Python 3.3+ silently treats it as a namespace package. This can mask a missing `__init__.py` bug:

```python
# You intended `mypkg` to be a regular package but forgot __init__.py:
# mypkg/
# ├── sub.py   (no __init__.py!)

import mypkg.sub  # Still works — namespace package, no error!
# But __init__ logic (version, re-exports) is silently missing.

# To catch this, many projects configure ruff/pylint to flag implicit namespace packages,
# or they add `__init__.py` explicitly to every package directory.
```

> **Recommendation for most projects:** Keep `__init__.py` in every package directory. Use namespace packages only when you intentionally need the split-directory feature. Explicit is better than implicit.

### 6.5 `pkgutil` and `pkg_resources` legacy

Before PEP 420, split packages used `pkgutil.extend_path` or `pkg_resources.declare_namespace`:

```python
# Old-style namespace package (pre-3.3) — still seen in legacy code:
# File: mypkg/__init__.py
from pkgutil import extend_path
__path__ = extend_path(__path__, __name__)
```

Modern code should not use this — omit `__init__.py` entirely for PEP 420 namespace packages, or use a regular package. The `pkgutil` shim is retained for backwards compatibility but is unnecessary in Python 3.3+.

## 7. Package Initialisation and Re-exports

### 7.1 Re-export patterns

Re-exporting makes a deep API available at a convenient shallow path:

```
mypkg/
├── __init__.py
├── core.py       (defines Engine, compute)
└── utils/
    ├── __init__.py
    └── helpers.py (defines format_result)
```

```python
# File: mypkg/__init__.py — explicit re-exports
"""mypkg public API."""

from .core import Engine, compute
from .utils.helpers import format_result

__all__ = ["Engine", "compute", "format_result"]
```

```python
# Users now have two equivalent paths:
from mypkg import Engine, compute        # short — via re-export
from mypkg.core import Engine, compute   # long — direct

# Both bind the same objects:
from mypkg import Engine as E1
from mypkg.core import Engine as E2
print(E1 is E2)  # True

# Package __all__ controls `from mypkg import *`:
# from mypkg import *  → imports Engine, compute, format_result only
```

Without `__all__`, `from mypkg import *` imports all names not starting with `_` that are present in `mypkg.__dict__` after `__init__.py` executes — which may include imported modules themselves. Always define `__all__` if you expect star-imports (and even if not, it documents intent).

### 7.2 Lazy re-exports (PEP 562) — for large packages

Eager re-exports in `__init__.py` load submodules immediately, even if the user only needs one. For large packages (e.g., `pandas`, `django`), this adds startup cost. PEP 562 allows lazy loading:

```python
# File: mypkg/__init__.py — lazy re-export via PEP 562 (Python 3.7+)
"""mypkg with lazy submodules."""

import importlib

# Declare what's available without importing it yet:
__all__ = ["Engine", "compute", "format_result"]

# PEP 562 — called when `mypkg.Engine` is accessed but not yet in __dict__
def __getattr__(name: str):
    if name in ("Engine", "compute"):
        mod = importlib.import_module(f"{__name__}.core")
        return getattr(mod, name)
    if name == "format_result":
        mod = importlib.import_module(f"{__name__}.utils.helpers")
        return getattr(mod, name)
    raise AttributeError(f"module {__name__!r} has no attribute {name!r}")

def __dir__():
    return sorted(__all__)
```

```python
# import mypkg  → does NOT load mypkg.core or helpers yet — fast!
import mypkg
print(mypkg.Engine)  # loads mypkg.core on first access — lazy
```

This pattern is used by large frameworks to keep `import mypkg` fast. For small-to-medium packages, eager re-exports are simpler and clearer.

### 7.3 `__init__.py` execution order

```python
# File: outer/__init__.py
print("[outer] init start")
from . import inner  # triggers inner/__init__.py
print("[outer] init end")

# File: outer/inner/__init__.py
print("[outer.inner] init")

# File: outer/inner/deep.py
print("[outer.inner.deep] loading")

# import outer → prints:
# [outer] init start
# [outer.inner] init
# [outer] init end

# import outer.inner.deep → additionally prints:
# [outer.inner.deep] loading
```

Package `__init__.py` files execute **before** the submodules they import, and each executes exactly once (cached in `sys.modules`). This order matters for circular imports at package level.

## 8. Relative vs Absolute — Worked Project Example

```
myapp/
├── run.py                 ← entry point (outside package)
├── myapp/
│   ├── __init__.py
│   ├── config.py
│   ├── models/
│   │   ├── __init__.py
│   │   ├── user.py
│   │   └── order.py
│   ├── services/
│   │   ├── __init__.py
│   │   ├── user_service.py
│   │   └── order_service.py
│   └── utils/
│       ├── __init__.py
│       └── helpers.py
```

```python
# File: myapp/models/user.py
from dataclasses import dataclass

@dataclass
class User:
    id: int
    name: str
    email: str

# File: myapp/config.py
SETTINGS = {"debug": True, "db_url": "sqlite:///app.db"}

# File: myapp/utils/helpers.py
def slugify(text: str) -> str:
    return text.lower().replace(" ", "-")

# File: myapp/services/user_service.py
"""Demonstrates both absolute and relative imports in a real package."""

# --- Absolute imports (PEP 8 preferred) ---
from myapp.models.user import User
from myapp.config import SETTINGS
from myapp.utils.helpers import slugify

# --- Equivalent relative imports (more concise for siblings) ---
# from ..models.user import User
# from ..config import SETTINGS        # actually .. is the parent of services → myapp
# from ..utils.helpers import slugify

def create_user(name: str, email: str) -> User:
    user = User(id=1, name=name, email=email)
    print(f"Creating {slugify(name)} with settings {SETTINGS}")
    return user

# File: myapp/__init__.py — re-export primary API
from .models.user import User
from .services.user_service import create_user

__all__ = ["User", "create_user"]
__version__ = "0.1.0"

# File: run.py — entry point OUTSIDE the package
from myapp import create_user, User
from myapp.services.order_service import create_order  # if needed

if __name__ == "__main__":
    user = create_user("Ada Lovelace", "ada@example.com")
    print(user)
```

Run it:

```bash
# From project root (myapp/ parent):
python run.py                          # ✓ run.py is outside package — absolute imports work
python -m myapp.services.user_service  # ✓ if user_service has a __main__ guard

# Wrong:
python myapp/services/user_service.py  # ✗ relative imports fail — run as script breaks __package__
```

> **Project layout lesson:** Keep entry points (`run.py`, `main.py`, `cli.py`) **outside** the package. Packages should be importable libraries; scripts should be thin wrappers that `import package` and call `main()`.

## 9. Common Mistakes and Edge Cases

### 9.1 Importing a package does not auto-import its submodules

```python
import myapp
# print(myapp.models)  # AttributeError unless myapp/__init__.py imported models
# print(myapp.services)  # same

# Must explicitly import the submodule:
import myapp.models.user
print(myapp.models.user.User)  # works — now attribute chain is populated

# Or have __init__.py re-export:
# myapp/__init__.py: from . import models  → then myapp.models exists after `import myapp`
```

This is the most common confusion when organising code into packages for the first time.

### 9.2 Forgetting `__init__.py` in a regular package (pre-3.3 thinking)

In Python 2, omitting `__init__.py` meant the directory was **not** a package at all — `import mypkg` would fail with `ModuleNotFoundError`. Since Python 3.3, it silently becomes a namespace package. This can hide bugs:

```bash
# You forgot __init__.py but tests still pass — because PEP 420 found it as namespace.
# CI on Python 3.2 would fail. Modern CI passes — silent difference.
# Fix: always add __init__.py unless you intentionally want a namespace package.
```

### 9.3 Relative import beyond top-level package

```python
# File: myapp/__init__.py
from .. import something  # ImportError: attempted relative import beyond top-level package
# .. from myapp would go above myapp — no parent exists.

# File: myapp/models/user.py
from ... import top  # ImportError — only depth is myapp.models.user (3 levels)
# .. → myapp.models, ... → myapp, .... → beyond top-level — error
```

### 9.4 Circular imports at package level

```python
# myapp/__init__.py:
from .services.user_service import create_user  # ← loads services
# myapp/services/user_service.py:
from myapp import User  # ← imports myapp — but myapp.__init__ not yet finished → partial init

# Fix options:
# 1. Have user_service import from myapp.models.user directly (not via myapp top-level):
#    from myapp.models.user import User  ← avoids the cycle through __init__.py
# 2. Move re-exports to the end of __init__.py after all needed submodules are safe
# 3. Use lazy imports (PEP 562 __getattr__) in __init__.py
```

### 9.5 Shadowing a package with a module of the same name

```python
# File: email.py  ← shadows stdlib `email` PACKAGE (which is a directory with __init__.py)
import email  # imports YOUR email.py, not stdlib — and email.mime fails
# from email.mime.text import MIMEText  # ModuleNotFoundError — your email.py has no mime subpackage

# Fix: rename your file. Never shadow stdlib package names:
# Common traps: email.py, json.py, xml.py, test.py, http.py
```

Package shadowing is even more confusing than module shadowing because the error appears as a missing submodule rather than a missing attribute.

### 9.6 `__path__` manipulation for extending packages (pre-PEP 420)

Legacy code manipulates `__path__` to extend package search locations:

```python
# File: mypkg/__init__.py (legacy extension)
import pkgutil
__path__ = pkgutil.extend_path(__path__, __name__)
```

This was needed for pre-PEP 420 namespace packages. Modern code should omit `__init__.py` entirely for namespace packages or use PEP 420 natively. Do not mix both styles.

### 9.7 `from package import submodule` vs `import package.submodule`

```python
# Both load the submodule, but bind different names locally:
import myapp.services.user_service          # binds `myapp`
from myapp.services import user_service     # binds `user_service`
import myapp.services.user_service as svc   # binds `svc`

# Attribute chain after each:
# After `import myapp.services.user_service`:
#   myapp.services.user_service  ✓
#   user_service                ✗ (not bound)

# After `from myapp.services import user_service`:
#   user_service                ✓
#   myapp                       ✗ (unless separately imported)
```

## 10. Quick Reference

| Concept | One-liner |
|---|---|
| Package | Directory that is a module with `__path__`; contains submodules/subpackages |
| Regular package | Has `__init__.py`; `__file__` points to it; `__path__` is `["dir"]` |
| Namespace package (PEP 420) | No `__init__.py` (Python 3.3+); no `__file__`; `__path__` is `_NamespacePath`; can span dirs |
| `__init__.py` | Executed on `import package`; defines package's namespace; may re-export submodules |
| Subpackage | Package inside a package (`pkg/subpkg/__init__.py` → `pkg.subpkg`) |
| `import pkg.sub` | Loads `pkg`, then `pkg.sub`; binds `pkg` locally |
| `from . import mod` | Relative — same package; works only inside packages (`__package__` must be set) |
| `from .. import mod` | Relative — parent package |
| `python -m pkg.mod` | Run as module — required for relative imports; `python pkg/mod.py` breaks them |
| `__all__` | List of public names for `from pkg import *` and documentation |
| `__path__` | Distinguishes packages (have it) from plain modules (don't) |
| PEP 562 `__getattr__` | Lazy submodule loading for large packages |
| Best practice | Keep `__init__.py` unless you need PEP 420 split; entry points outside the package |
