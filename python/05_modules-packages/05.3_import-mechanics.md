## 1. The Big Picture — What Happens When You Write `import foo`

When CPython executes `import foo`, it runs a well-defined sequence (import system, PEP 302 / PEP 451). Simplified to five steps:

```
import foo
   │
   ├─ 1. Is "foo" already in sys.modules?  ──yes──► return sys.modules["foo"] (cache hit)
   │   no
   ├─ 2. Ask each FINDER on sys.meta_path: "can you find spec for 'foo'?"
   │      If no finder says yes, try finders on sys.path (PathFinder + sys.path_hooks)
   │      If still nothing → ModuleNotFoundError
   │
   ├─ 3. Finder returns a ModuleSpec (name, loader, origin, submodule_search_locations)
   │
   ├─ 4. Create empty module object, insert into sys.modules["foo"] (for circular-import protection)
   │
   └─ 5. Ask the LOADER to exec_module(module) — executes the file inside the module's __dict__
```

```python
import sys

# Step 1 — cache check demonstration:
import math
print("math" in sys.modules)              # True
print(sys.modules["math"] is math)        # True — same object returned on cache hit

# Subsequent `import math` anywhere in the process does no work beyond step 1.
import math as m2
print(m2 is math)                         # True
```

We will now unpack each step.

## 2. Module Search — `sys.path`, `PYTHONPATH`, and Friends

### 2.1 `sys.path` — the ordered search list

`sys.path` is an ordinary `list[str]` that the interpreter initialises at startup and searches **in order**. The first matching location wins.

```python
import sys
import pprint

pprint.pprint(sys.path)
# Example output (order matters!):
# [
#   '/home/user/project',                           # 0 — script dir or '' (see 2.2)
#   '/usr/lib/python3.12',                         # 1 — stdlib
#   '/usr/lib/python3.12/lib-dynload',             # 2 — C extensions
#   '/home/user/.venv/lib/python3.12/site-packages', # 3 — third-party (site-packages)
#   '/usr/local/lib/python3.12/dist-packages',     # 4 — system site-packages
# ]
```

Each entry is tried in order. For `import foo`, Python asks the path finders to look for `foo.py`, `foo/__init__.py`, `foo.cpython-312.so`, etc., inside each directory. First match wins.

```python
# Demonstrate ordering matters:
import sys
import tempfile
import pathlib

# Create two temporary directories, each with a `demo.py` defining different values:
with tempfile.TemporaryDirectory() as dir1, tempfile.TemporaryDirectory() as dir2:
    pathlib.Path(dir1, "demo.py").write_text("value = 'from dir1'\n")
    pathlib.Path(dir2, "demo.py").write_text("value = 'from dir2'\n")

    # dir1 earlier in sys.path → found first:
    sys.path.insert(0, dir1)
    sys.path.insert(1, dir2)
    import demo
    print(demo.value)  # 'from dir1' — dir1 wins

    # To simulate the opposite, we'd need to reload or manipulate sys.modules:
    del sys.modules["demo"]
    sys.path.remove(dir1)
    sys.path.remove(dir2)
    sys.path.insert(0, dir2)
    sys.path.insert(1, dir1)
    import demo
    print(demo.value)  # 'from dir2' — now dir2 wins

    # Cleanup:
    del sys.modules["demo"]
    sys.path.remove(dir2)
    sys.path.remove(dir1)
```

### 2.2 Entry 0 — the current directory / script directory

`sys.path[0]` is special. It is set at interpreter startup based on **how you invoked Python**:

| Invocation | `sys.path[0]` | Explanation |
|---|---|---|
| `python script.py` | `"/path/to/script/dir"` | Absolute directory of the script |
| `python -m pkg.mod` | `""` (current working directory at launch) | CWD, not the module's directory |
| `python -c "import x"` | `""` | CWD |
| REPL (`python` with no args) | `""` | CWD — makes experimenting convenient |
| `PYTHONPATH=/foo python script.py` | `"/path/to/script/dir"` still first, `/foo` next | `PYTHONPATH` entries are inserted after entry 0 |

```python
import sys

# Show entry 0:
print(f"sys.path[0] = {sys.path[0]!r}")

# Meaning of "":
# "" means "the current working directory at the time of import" (resolved dynamically).
# It is NOT frozen to the startup CWD — if you chdir, imports search the new CWD.
import os
print(f"CWD: {os.getcwd()}")
print(f"sys.path[0]: {sys.path[0]}")
# If sys.path[0] == "", then `import foo` searches os.getcwd() for foo.py.
```

Why this matters:

```python
# project/
# ├── script.py
# └── helpers.py

# helpers.py:  value = 42
# script.py:   import helpers; print(helpers.value)

# Running from project/:
#   $ python script.py          → works — sys.path[0] is project/, finds helpers.py
#   $ python project/script.py  → works if project/ is CWD's child? Depends on path.
#   $ cd /tmp && python /home/user/project/script.py
#           → sys.path[0] is /home/user/project, still finds helpers.py — OK

# Common pitfall — running from the wrong directory with -m:
#   $ cd /tmp && python -m script  → sys.path[0] is /tmp, not project/ → may not find deps
```

### 2.3 `PYTHONPATH` — augmenting `sys.path` from the environment

`PYTHONPATH` is an environment variable whose contents are **prepended** to `sys.path` (after entry 0) at startup:

```bash
# Bash:
PYTHONPATH=/opt/mylibs:/home/user/libs python app.py
# sys.path becomes: [script_dir, /opt/mylibs, /home/user/libs, stdlib, site-packages, ...]
```

```python
import sys
import os

# Check if PYTHONPATH contributed:
print(os.environ.get("PYTHONPATH", "(not set)"))
# sys.path entries from PYTHONPATH appear after script dir:
for p in sys.path:
    print(f"  {p}")
```

Uses:

- Quick-and-dirty way to make a development package importable without installing it.
- Pointing at a non-standard location in CI or containers.

Prefer alternatives for permanent needs (see 2.6 — `.pth` files, `pip install -e .`, virtual environments). `PYTHONPATH` is global, affects every Python invocation in that environment, and can mask installation problems.

```bash
# Temporary, single-command injection:
PYTHONPATH=/home/user/dev/mypkg python -c "import mypkg; print(mypkg.__file__)"
```

### 2.4 `site-packages` — where `pip` puts third-party code

`site-packages` (and `dist-packages` on Debian/Ubuntu) are ordinary `sys.path` entries added by the `site` module at startup (unless `python -S` is used). They hold installed distributions:

```python
import sys
import site

print(site.getsitepackages())
# ['/home/user/.venv/lib/python3.12/site-packages', '/usr/local/lib/python3.12/dist-packages']
print(site.getusersitepackages())
# '/home/user/.local/lib/python3.12/site-packages' — per-user installs (pip install --user)

# site-packages is just another sys.path entry — no magic:
print(any("site-packages" in p for p in sys.path))  # True

# What's inside?
import pathlib
sp = pathlib.Path(site.getsitepackages()[0])
print(list(sp.glob("*.dist-info"))[:3])  # metadata directories for installed packages
print(list(sp.glob("requests*"))[:3])    # if requests is installed
```

How entries get added:

- `python -m pip install requests` → copies `requests/` and `requests-*.dist-info/` into `site-packages`, which is already on `sys.path`, so `import requests` works immediately.
- `pip install -e .` (editable) → adds a `.pth` file or direct link pointing at your source tree.
- `site` also processes `.pth` files — see 2.6.

### 2.5 `.pth` files and `site` processing

During startup, `site` scans each `site-packages` directory for `.pth` files. Each line in a `.pth` file is either:

- A path to add to `sys.path`, or
- An `import` statement to execute.

```python
# Example: suppose site-packages contains mylibs.pth with content:
#   /opt/mylibs
#   import mylibs_sitecustomize

# At startup, site.py reads it and:
#   sys.path.append("/opt/mylibs")
#   __import__("mylibs_sitecustomize")

# You can inspect the effect:
import sys
print([p for p in sys.path if "mylibs" in p])
```

Editable installs exploit this: `pip install -e .` typically creates a `.pth` like `/path/to/your/project` so that `import your_package` resolves to your working tree.

### 2.6 Manipulating `sys.path` at runtime — when and how

Because `sys.path` is a plain list, you can mutate it at runtime. This is occasionally necessary but should be a last resort:

```python
import sys
import pathlib

# Add a directory so its modules become importable:
libs_dir = str(pathlib.Path(__file__).parent / "libs")
if libs_dir not in sys.path:
    sys.path.insert(0, libs_dir)  # insert at front → highest priority
    # or sys.path.append(libs_dir) → lowest priority

import mylib  # now found in libs/

# Remove a directory:
sys.path.remove(libs_dir)
# del sys.modules["mylib"]  # if you want to force re-discovery next time (rare)

# Context-manager helper for temporary path injection:
from contextlib import contextmanager
import sys

@contextmanager
def temporary_sys_path(path: str, prepend: bool = True):
    """Temporarily add path to sys.path, removing it on exit."""
    added = False
    if path not in sys.path:
        if prepend:
            sys.path.insert(0, path)
        else:
            sys.path.append(path)
        added = True
    try:
        yield
    finally:
        if added:
            sys.path.remove(path)

# Usage:
with temporary_sys_path("/tmp/my_extra_libs"):
    import extra_module  # found only inside the context
# sys.path restored after
```

> **Warning:** Runtime `sys.path` manipulation is fragile — it depends on working directory, is invisible to static tools, and can cause import-time side effects to vary by execution path. Prefer installing packages properly (`pip install -e .`) or using `PYTHONPATH` / virtual environments.

### 2.7 `sys.path` vs `PYTHONPATH` vs `site-packages` — overview

| Mechanism | When set | Priority | Scope | Recommended for |
|---|---|---|---|---|
| `sys.path[0]` (script dir / `""`) | Interpreter startup, per invocation | Highest (first) | Per-run | Automatic — don't override |
| `PYTHONPATH` env var | Before interpreter start | After entry 0 | Per-environment | Temporary dev tweaks |
| `sys.path` mutation | Runtime | Where inserted | Process only | Tests, dynamic plugin loading |
| `site-packages` / `dist-packages` | Interpreter startup via `site` | Before stdlib tail | Per-environment (venv) | Third-party and project installs |
| `.pth` files | Startup via `site` | Same as site-packages entry | Per-environment | Editable installs, namespace expansion |
| `user site-packages` | Startup if enabled | After site-packages | Per-user | `pip install --user` |

## 3. The Import Machinery — Finders and Loaders

The import system is intentionally split into two roles: **finders** locate modules, **loaders** load them. This separation allows custom import hooks (e.g., loading from zip files, databases, or the network).

### 3.1 `sys.meta_path` — meta path finders

`sys.meta_path` is a list of **finder** objects consulted **before** `sys.path` is searched. Python asks each finder in order: "Do you know where `foo` is?" The first finder to return a `ModuleSpec` wins.

```python
import sys
import pprint

pprint.pprint(sys.meta_path)
# [
#   <class '_frozen_importlib.BuiltinImporter'>,    # built-in modules (math, sys)
#   <class '_frozen_importlib.FrozenImporter'>,     # frozen modules (_frozen_importlib, _imp)
#   <class '_frozen_importlib_external.PathFinder'> # sys.path-based finder (most imports)
# ]

# Each finder implements `find_spec(fullname, path, target=None) -> ModuleSpec | None`
import importlib.machinery

spec = importlib.machinery.PathFinder.find_spec("os", None)
print(spec)
# ModuleSpec(name='os', loader=<SourceFileLoader ...>, origin='/usr/lib/python3.12/os.py')
print(spec.name)                  # 'os'
print(spec.loader)                # <_frozen_importlib_external.SourceFileLoader ...>
print(spec.origin)                # '/usr/lib/python3.12/os.py'
print(spec.submodule_search_locations)  # None — os is a module, not a package
print(spec.origin)                # file path, "built-in", or None for namespace packages

# For a package, submodule_search_locations is not None:
spec_pkg = importlib.machinery.PathFinder.find_spec("email", None)
print(spec_pkg.submodule_search_locations)  # ['/usr/lib/python3.12/email']
```

Default `sys.meta_path` entries:

| Finder | What it finds |
|---|---|
| `BuiltinImporter` | C built-ins compiled into the interpreter (`sys`, `math`, `_thread`, …) — no file |
| `FrozenImporter` | Frozen modules baked into the executable (`_frozen_importlib`, `importlib._bootstrap`) |
| `PathFinder` | Everything on `sys.path` — `.py` files, packages, C extensions (`.so`/`.pyd`), zip imports |

You can insert custom finders (advanced — used by frameworks, test mocks):

```python
import sys
import importlib.abc
import importlib.machinery
import types

# Example: a finder that provides a synthetic module `magic_hello` without any file:
class MagicFinder(importlib.abc.MetaPathFinder):
    def find_spec(self, fullname, path, target=None):
        if fullname == "magic_hello":
            return importlib.machinery.ModuleSpec(
                fullname,
                MagicLoader(),
                origin="magic",
            )
        return None  # not ours — let other finders try

class MagicLoader(importlib.abc.Loader):
    def create_module(self, spec):
        return None  # use default module creation

    def exec_module(self, module):
        module.message = "Hello from synthetic module!"
        module.answer = 42

sys.meta_path.insert(0, MagicFinder())

import magic_hello
print(magic_hello.message)  # Hello from synthetic module!
print(magic_hello.answer)   # 42

# Cleanup:
sys.meta_path.remove(sys.meta_path[0])
del sys.modules["magic_hello"]
```

### 3.2 `sys.path_hooks` and `sys.path_importer_cache`

For `sys.path` entries, Python does not hard-code how to search. Instead `sys.path_hooks` holds callables that, given a path entry string, return a **path entry finder**:

```python
import sys

print(sys.path_hooks)
# [
#   <class 'zipimport.zipimporter'>,                           # handles .zip / .egg files on sys.path
#   <class '_frozen_importlib_external.FileFinder'>             # handles filesystem directories
# ]
print(sys.path_importer_cache)
# {'/usr/lib/python3.12': FileFinder('/usr/lib/python3.12'), ...} — cached per path entry
```

When Python scans `sys.path`, for each entry it calls the path hooks until one claims it. `FileFinder` handles normal directories; `zipimporter` handles zip files:

```python
# Zip import — Python can import directly from a zip file if it's on sys.path:
import tempfile
import zipfile
import pathlib
import sys

with tempfile.TemporaryDirectory() as tmp:
    zippath = str(pathlib.Path(tmp) / "mymods.zip")
    with zipfile.PyZipFile(zippath, mode="w") as zf:
        # Create a synthetic module inside the zip:
        zf.writestr("zmod.py", "value = 'from zip'\n")

    sys.path.insert(0, zippath)
    import zmod
    print(zmod.value)  # 'from zip' — loaded from zip without unpacking!
    print(zmod.__file__)  # '.../mymods.zip/zmod.py'
    print(zmod.__loader__)  # <zipimporter ...>

    del sys.modules["zmod"]
    sys.path.remove(zippath)
```

This is how `.egg` files (legacy) and `zipapp` (`python app.pyz`) work — the import system treats zip files as directories.

### 3.3 `ModuleSpec` — the find result

A `ModuleSpec` (PEP 451) is the data object a finder returns. It tells Python **what** was found and **how** to load it:

```python
import importlib.util

spec = importlib.util.find_spec("json")
print(f"name: {spec.name}")                # json
print(f"loader: {spec.loader}")            # SourceFileLoader
print(f"origin: {spec.origin}")            # /usr/lib/python3.12/json/__init__.py
print(f"is_package: {spec.submodule_search_locations is not None}")  # True
print(f"search_locations: {spec.submodule_search_locations}")  # ['/usr/lib/python3.12/json']
print(f"cached: {spec.cached}")            # /usr/lib/python3.12/__pycache__/json...
print(f"has_location: {spec.has_location}") # True

spec_mod = importlib.util.find_spec("math")
print(spec_mod.origin)                     # built-in
print(spec_mod.loader)                     # BuiltinImporter

spec_ns = importlib.util.find_spec("this_does_not_exist_xyz")
print(spec_ns)                             # None — not found

# Namespace package spec (no __init__.py):
# If nspkg/ has no __init__.py and is on sys.path:
# spec_ns = find_spec("nspkg")
# spec_ns.loader is None
# spec_ns.submodule_search_locations is _NamespacePath([...])
# spec_ns.origin is None
```

Fields of `ModuleSpec`:

| Field | Meaning |
|---|---|
| `name` | Fully-qualified name (`"pkg.sub"`) |
| `loader` | Loader that will call `create_module` + `exec_module` (or `None` for namespace packages) |
| `origin` | File path, `"built-in"`, `"frozen"`, or `None` |
| `submodule_search_locations` | `None` for modules; list/`_NamespacePath` for packages |
| `cached` | Path to `.pyc` bytecode, or `None` |
| `parent` | Parent package name (`"pkg"` for `"pkg.sub"`) |
| `has_location` | Whether `origin` is a meaningful path |

### 3.4 Loaders — `create_module` + `exec_module`

A **loader** does the actual work of populating the module object:

1. `create_module(spec) -> module | None` — optionally create the module object (usually returns `None` to use the default `types.ModuleType`).
2. `exec_module(module)` — execute the module inside the already-created object (set `__dict__`, run code). It must set `__spec__`, `__loader__`, and handle `__package__`.

```python
import importlib.abc
import importlib.machinery
import types

# Custom loader example — load Python source from a string (e.g., from a database):
source_code = """
greeting = "Hello from custom loader"
def greet(name: str) -> str:
    return f"{greeting}, {name}!"
"""

class StringLoader(importlib.abc.Loader):
    def __init__(self, source: str, origin: str = "<string>"):
        self.source = source
        self.origin = origin

    def create_module(self, spec):
        return None  # use default

    def exec_module(self, module):
        # Compile and exec the source inside the module's namespace:
        code = compile(self.source, self.origin, "exec")
        exec(code, module.__dict__)

# Use with find_spec or manual spec:
import sys
spec = importlib.machinery.ModuleSpec("synthetic", StringLoader(source_code, "synthetic.py"), origin="synthetic.py")
mod = importlib.util.module_from_spec(spec)
sys.modules["synthetic"] = mod
spec.loader.exec_module(mod)

print(mod.greeting)       # Hello from custom loader
print(mod.greet("Ada"))   # Hello from custom loader, Ada!

del sys.modules["synthetic"]
```

Standard loaders:

| Loader | Origin type | What it does |
|---|---|---|
| `SourceFileLoader` | `.py` source | Compiles `.py` → bytecode → `exec` inside module |
| `SourcelessFileLoader` | `.pyc` without `.py` | Loads bytecode directly |
| `ExtensionFileLoader` | `.so` / `.pyd` | Loads C extension via dynamic linking |
| `BuiltinImporter` (also a loader) | `built-in` | Initialises C built-in module |
| `FrozenImporter` | `frozen` | Loads from frozen bytecode in the executable |
| `zipimport.zipimporter` | zip entry | Loads from inside a `.zip` |
| `None` | namespace package | No loader — namespace has no code to execute |

### 3.5 Full trace — `import pkg.sub` step-by-step

For `import pkg.sub` where `pkg` is a package and `sub` is a module `pkg/sub.py`:

```
1. import pkg.sub
2. sys.modules has "pkg"? No → find "pkg" via meta_path
     → PathFinder finds pkg/__init__.py → spec with loader=SourceFileLoader
     → create module, insert sys.modules["pkg"], exec_module (runs __init__.py)
3. Now sys.modules has "pkg.sub"? No → find "pkg.sub"
     → PathFinder uses pkg.__path__ to locate sub.py (sys.path is NOT used for submodules — parent's __path__ is)
     → spec with origin=pkg/sub.py
     → create module, insert sys.modules["pkg.sub"], exec_module (runs sub.py)
     → set attribute pkg.sub = sys.modules["pkg.sub"]  (package attribute binding)
4. Binding in importer: import pkg.sub binds `pkg` locally (top-level name)
```

Notice that for submodules, the **parent's `__path__`** is searched, not `sys.path`. This is why `pkg.sub` can be found even if `pkg` is itself loaded from a zip file — the zip importer reported `pkg.__path__` as an entry inside the zip.

## 4. `importlib` — Programmatic Imports

The `importlib` package is the public API for the import system. Use it instead of `__import__` (which is low-level and rarely needed directly).

### 4.1 `importlib.import_module` — dynamic imports

When the module name is not known until runtime (plugin systems, configuration-driven imports), use `import_module`:

```python
import importlib

# Static import:
import json
# Dynamic equivalent:
json2 = importlib.import_module("json")
print(json2 is json)  # True — cache hit, same object
print(json2.dumps({"a": 1}))  # '{"a": 1}'

# Submodule:
os_path = importlib.import_module("os.path")
import os.path
print(os_path is os.path)  # True

# Relative import — supply package:
# importlib.import_module(".sub", package="mypkg") → like `from mypkg import sub`
# The package argument is required for relative names (leading dot).
# Useful inside a package when you need to import a sibling dynamically:
# sibling = importlib.import_module(".helpers", package=__name__)
# If you are inside mypkg.core, __name__ is "mypkg.core", helpers is "mypkg.helpers".

# Plugin pattern — load class by dotted path from config:
def load_class(dotted_path: str):
    """Load a class from 'pkg.module.ClassName'."""
    module_path, class_name = dotted_path.rsplit(".", 1)
    mod = importlib.import_module(module_path)
    return getattr(mod, class_name)

# Example (if config says handler: "myapp.handlers.EmailHandler"):
# HandlerCls = load_class("myapp.handlers.EmailHandler")
# handler = HandlerCls()

# Real stdlib equivalent — importlib does this too:
import importlib.util
spec = importlib.util.find_spec("pathlib")
Mod = load_class("pathlib.Path")
print(Mod("/tmp/test"))  # PosixPath('/tmp/test')
```

Why `import_module` over `__import__`:

```python
# __import__ has awkward semantics — it returns the TOP-LEVEL package, not the leaf:
mod = __import__("os.path")       # returns `os`, not `os.path`!
print(mod)                        # <module 'os'> — not what you expected
# You need: __import__("os.path", fromlist=["path"]) to get os.path — confusing.

# import_module is clear:
mod = importlib.import_module("os.path")  # returns `os.path` — the leaf
print(mod)                                # <module 'posixpath'>
```

### 4.2 `importlib.util.find_spec` — locate without loading

`find_spec` runs the finders but does not load or execute the module. Useful for checking existence or inspecting origin without side effects:

```python
import importlib.util

# Exists?
print(importlib.util.find_spec("json") is not None)        # True
print(importlib.util.find_spec("nonexistent_xyz") is not None)  # False

# Inspect without importing (no top-level code executed):
spec = importlib.util.find_spec("json")
print(spec.origin)                          # /usr/lib/python3.12/json/__init__.py
print(spec.submodule_search_locations)       # ['/usr/lib/python3.12/json']
print("json" in __import__("sys").modules)  # True already because we imported it above — but
# if we hadn't, find_spec would NOT add it to sys.modules.

# Check if something is a package without importing:
spec = importlib.util.find_spec("email")
print(spec.submodule_search_locations is not None)  # True — it's a package

spec = importlib.util.find_spec("math")
print(spec.submodule_search_locations is not None)  # False — plain module (or built-in)

# Use case — conditional feature based on optional dependency:
def has_orjson() -> bool:
    return importlib.util.find_spec("orjson") is not None

if has_orjson():
    import orjson as json_lib
else:
    import json as json_lib
```

### 4.3 `importlib.util.module_from_spec` + `exec_module` — manual loading

For advanced cases (loading from a non-standard location, or creating a module from a spec):

```python
import importlib.util
import sys

# Load a specific file as a module with a custom name:
spec = importlib.util.spec_from_file_location("my_temp_mod", "/tmp/special.py")
# spec_from_file_location builds a ModuleSpec with SourceFileLoader pointing at that file.

# Suppose /tmp/special.py contains:  value = 123
from pathlib import Path
Path("/tmp/special.py").write_text("value = 123\n")

spec = importlib.util.spec_from_file_location("my_temp_mod", "/tmp/special.py")
print(spec.name)    # my_temp_mod
print(spec.origin)  # /tmp/special.py

mod = importlib.util.module_from_spec(spec)
sys.modules[spec.name] = mod          # register before exec (circular-import safety)
spec.loader.exec_module(mod)          # execute file inside mod.__dict__

print(mod.value)                    # 123
print(sys.modules["my_temp_mod"] is mod)  # True

del sys.modules["my_temp_mod"]
```

### 4.4 Re-export of `importlib` helpers — summary table

| Function | Purpose | Executes module? | Adds to `sys.modules`? |
|---|---|---|---|
| `importlib.import_module(name)` | Import by string (dynamic) | Yes | Yes |
| `importlib.util.find_spec(name)` | Find without loading | No | No |
| `importlib.util.spec_from_file_location(name, path)` | Build spec from a path | No | No |
| `importlib.util.module_from_spec(spec)` | Create empty module from spec | No | No (caller must add to `sys.modules`) |
| `spec.loader.exec_module(mod)` | Execute module code | Yes — runs file inside `mod` | Already in `sys.modules` |
| `importlib.reload(mod)` | Re-execute module | Yes — re-runs file | Reuses existing entry |

## 5. `importlib.reload` — Re-executing a Module

`reload` re-executes a module's source code inside the **same** module object. It is the only sanctioned way to pick up file changes without restarting the process.

### 5.1 Basic usage

```python
import importlib
import mymodule  # assume mymodule.py contains: value = 1

print(mymodule.value)  # 1

# ... edit mymodule.py on disk to change value = 99 ...

importlib.reload(mymodule)  # re-reads file, re-executes top-level code in same object
print(mymodule.value)       # 99 — updated
```

### 5.2 What reload does and does not do

```python
# File: reloaded_mod.py (original):
# value = 1
# items = [1, 2]
# def greet(): return "hello"
# old_name = "will be removed in new version"

# File: reloaded_mod.py (edited version):
# value = 99
# items = [9, 9, 9]
# def greet(): return "hi there"
# new_name = "fresh"

import importlib
import reloaded_mod

print(reloaded_mod.value)     # 1
old_items_id = id(reloaded_mod.items)
old_greet = reloaded_mod.greet  # keep reference to old function object
from reloaded_mod import value as imported_value  # local binding

importlib.reload(reloaded_mod)

print(reloaded_mod.value)     # 99 — updated
print(imported_value)         # 1 — STALE! Local `imported_value` still 1
print(reloaded_mod.items)     # [9, 9, 9] — replaced with new list object
print(reloaded_mod.items is old_items_id)  # False — new list, but the module attribute was rebound
print(hasattr(reloaded_mod, "old_name"))   # True — still there! reload does NOT delete removed names
print(hasattr(reloaded_mod, "new_name"))   # True — newly added
print(old_greet())            # "hello" — still the old function object
print(reloaded_mod.greet())   # "hi there" — new function object
print(old_greet is reloaded_mod.greet)  # False — different objects
```

Rules:

| Aspect | Behaviour on `reload(mod)` |
|---|---|
| Same `sys.modules` entry | Yes — `mod` is the same object (`id` unchanged) |
| Re-executes top-level code | Yes — re-parses file, re-runs all top-level statements |
| Updates existing names | Yes — rebound to new values |
| Adds new names | Yes |
| Removes deleted names | **No** — old names persist (stale attributes remain) |
| Replaces function/class objects | New objects — old ones survive if referenced elsewhere |
| `from mod import name` bindings | **Not updated** — still point to old objects |
| Instances of old classes | Keep old class (`instance.__class__ is not new_class`) |
| Submodules | **Not reloaded** — only the named module; children must be reloaded separately |

```python
# Demonstration — instance retains old class after reload:
# File: models.py (v1):  class Widget: version = 1
# File: models.py (v2):  class Widget: version = 2

import models
w = models.Widget()
print(w.version)          # 1
print(type(w) is models.Widget)  # True

import importlib
# ... edit file to v2, then reload:
importlib.reload(models)
print(models.Widget.version)      # 2 — new class
print(w.version)                  # 1 — old instance still tied to old class object!
print(type(w) is models.Widget)   # False — w's class is the old Widget, not the new one
# w.__class__ is the old class object preserved by the `w` reference
```

### 5.3 Reload caveats and patterns

```python
# Caveat 1 — stale from-imports (most common bug with reload):
from reloaded_mod import greet
import importlib
import reloaded_mod
importlib.reload(reloaded_mod)
print(greet())            # "hello" — stale! Still the old function object
print(reloaded_mod.greet())  # "hi there" — new one
# Fix: re-do the from-import after reload, or use `reloaded_mod.greet` (module-attribute access)

# Caveat 2 — enum/identity checks break:
# File: config.py:  from enum import Enum; class Color(Enum): RED = 1
# If you reload config, Color is a new class — `is` and `isinstance` against old instances fail.

# Caveat 3 — decorators/memoization may hold old references.

# Useful pattern — notebook / REPL reload helper:
def deep_reload(package_name: str) -> None:
    """Reload a package and all its loaded submodules (best-effort)."""
    import sys
    import importlib
    # Collect loaded submodules sorted deepest-first (children before parents):
    loaded = sorted(
        [name for name in sys.modules if name == package_name or name.startswith(package_name + ".")],
        key=lambda n: n.count("."), reverse=True,
    )
    for name in loaded:
        try:
            importlib.reload(sys.modules[name])
            print(f"  reloaded {name}")
        except Exception as e:
            print(f"  failed {name}: {e}")

# deep_reload("mypackage")
```

Practical guidance: use `reload` only for interactive development (REPL, Jupyter). In production, restart the process. Packages like `autoreload` (Jupyter) and `watchdog` automate reloading with file watchers but inherit the same caveats.

## 6. Absolute vs Relative Imports — Which to Use

### 6.1 Definitions

```python
# File: mypkg/sub.py  (inside package mypkg)
# Absolute imports — fully-qualified name from the top-level:
import mypkg.helpers
from mypkg.helpers import format_name
from mypkg.core.engine import Engine

# Relative imports — dots relative to the current package:
from . import helpers              # same package — mypkg.helpers
from .helpers import format_name   # same package
from .. import other_pkg           # parent of mypkg
from .core.engine import Engine    # relative path inside package

# For top-level modules (not inside any package), all imports are absolute:
import os
from pathlib import Path
```

### 6.2 Decision guidance

| Criterion | Absolute | Relative |
|---|---|---|
| **Explicitness** | Fully explicit — grep finds all users (`grep -r "mypkg.helpers"`) | Implicit — needs package context to resolve |
| **Refactor safety** | Moving a file doesn't break absolute imports if the package name stays | Moving a file up/down a package level requires updating the dot count |
| **Package-rename safety** | Hard-codes the top-level name — renaming `mypkg` touches every file | No hard-coded top-level name — subpackage is relocatable |
| **Requirement** | Works anywhere, including scripts | Works only inside packages (`__package__` must be set); running as `python pkg/mod.py` fails |
| **PEP 8 stance** | "Absolute imports are recommended" — default choice | Acceptable inside packages; preferred when package may be renamed or deeply nested |
| **Length** | Verbose for deep nesting (`from a.b.c.d.e import foo`) | Concise for siblings (`from .e import foo`, `from ..c import bar`) |

```python
# Example — deep package where absolute becomes noisy:
# mypackage/services/handlers/notification.py

# Absolute (explicit but verbose):
from mypackage.services.handlers.base import BaseHandler
from mypackage.utils.text import truncate
from mypackage.config import settings

# Relative (concise for siblings, still absolute for distant):
from .base import BaseHandler         # sibling — short, clear
from ...utils.text import truncate    # two levels up, then down
from mypackage.config import settings # absolute — config is far away, be explicit

# Many teams standardise on "absolute only" to keep imports grep-friendly and
# avoid the script-vs-module trap. This is PEP 8's default recommendation.
```

### 6.3 The script-vs-module trap with relative imports

```python
# File: mypkg/sub.py  containing:  from . import helper  (relative)
# Running as a module — works:
# $ python -m mypkg.sub          →  __package__ is "mypkg"  →  relative resolves to mypkg.helper ✓

# Running as a script — fails:
# $ python mypkg/sub.py          →  __package__ is None  →  ImportError: attempted relative import
#                                  with no known parent package
# Because the interpreter sets __name__ = "__main__", __package__ = None for script-mode runs.
```

Fix: always run package code with `-m` (or keep entry points outside the package — lesson 05.5).

### 6.4 PEP 8 — import ordering and style

PEP 8 mandates a specific order and group separation for imports. Automated formatters (`isort`, `ruff`) enforce it.

Correct order (top to bottom, groups separated by a **blank line**):

1. **Standard library** (e.g., `os`, `sys`, `pathlib`, `collections`)
2. **Related third-party** (`requests`, `numpy`, `pydantic`)
3. **Local application / library** (`mypackage`, `.helpers`)

Within each group:

- Alphabetically sorted (case-insensitive is common; `isort` is configurable).
- `import` statements before `from ... import` statements (configurable).
- No wildcard (`from x import *`) — banned outside `__init__.py` re-exports with `__all__`.

```python
# Correctly ordered file — PEP 8 + isort style:
"""Demonstrates PEP 8 import ordering."""

# Group 1 — stdlib (blank line before)
import os
import sys
from collections import Counter
from pathlib import Path

# Group 2 — third-party (blank line between groups)
import numpy as np
import requests

# Group 3 — local (blank line between groups)
from mypackage import config
from mypackage.models.user import User
from .helpers import format_name  # relative — still group 3

# Then code below:
MY_CONSTANT = 42


def main() -> None:
    pass
```

Additional PEP 8 rules:

```python
# ✓ One import per line for `import`:
import os
import sys

# ✗ Not: import os, sys  (harder to diff, hides changes in version control)

# ✓ For `from`, multiple names can be on one line (if short) or wrapped:
from subprocess import PIPE, Popen
from collections import (
    Counter,
    defaultdict,
    deque,  # trailing comma is encouraged — cleaner diffs
)

# ✓ Use parentheses to wrap long import lines, not backslashes:
from mypackage.services.handlers.notification import (
    NotificationHandler,
    NotificationResult,
)

# ✗ Backslash is discouraged:
# from mypackage import very_long_name, \
#     another_long_name

# ✓ Module-level imports at the top — not in the middle of the file:
import json  # top of file

def foo():
    pass  # not: import json  (unless deferring to avoid a cycle or heavy cost — then comment why)

# ✓ Absolute imports preferred:
import mypackage.helpers  # explicit
# Not: from . import helpers  (unless inside a package and preferred for relocatability)

# ✓ Avoid `import *`:
# from os import *  # no

# ✓ `isort` / `ruff` configuration for enforcing order (pyproject.toml):
# [tool.ruff.lint.isort]
# known-first-party = ["mypackage"]
# known-third-party = ["numpy", "requests"]
```

## 8. Advanced — Custom Import Hooks and `sys.meta_path` Caveats

### 8.1 Inspecting the full resolution chain

```python
import sys
import importlib.util

def trace_find(name: str) -> None:
    """Trace how a name would be resolved — cache? meta_path? path?"""
    if name in sys.modules:
        print(f"  {name}: cache hit in sys.modules → {sys.modules[name]}")
        return
    for finder in sys.meta_path:
        try:
            spec = finder.find_spec(name, None)
        except Exception as e:
            print(f"  finder {finder.__class__.__name__} raised: {e}")
            continue
        if spec is not None:
            print(f"  {name}: found by {finder.__class__.__name__}")
            print(f"    origin: {spec.origin}")
            print(f"    loader: {spec.loader}")
            print(f"    is_package: {spec.submodule_search_locations is not None}")
            return
    print(f"  {name}: NOT FOUND — would raise ModuleNotFoundError")
    # Also check sys.path directly:
    print(f"  sys.path searched: {sys.path[:3]} ...")

trace_find("json")
trace_find("nonexistent_xyz")
trace_find("math")  # built-in — found by BuiltinImporter
```

### 8.2 Modifying `sys.meta_path` — pitfalls

- **Order matters:** inserting at position 0 intercepts before the stdlib finders; appending runs after them. Be intentional.
- **Must return `None` for unknown modules:** a finder that returns a spec for a module it cannot actually load will cause opaque `ImportError` later during `exec_module`.
- **Thread safety:** `sys.modules` is not fully thread-safe during import (import lock exists, but custom finders must be careful — see `importlib._bootstrap._ModuleLock`).
- **Interaction with `find_spec`:** tools like type checkers and IDEs call `find_spec` without executing; a finder that has side effects in `find_spec` will cause surprises.

## 9. Common Mistakes and Edge Cases

### 9.1 `ModuleNotFoundError` due to wrong working directory

```python
# project/
# ├── app.py
# └── mypackage/__init__.py

# Running from inside project/mypackage/:
# $ cd project/mypackage && python ../app.py  → sys.path[0] is project/ — OK
# $ cd /tmp && python project/app.py          → sys.path[0] is project/ — OK
# $ cd project/mypackage && python -c "import app"  → sys.path[0] is project/mypackage
#          → may not find sibling packages — confusing errors

# Fix: always run from the project root, or use `python -m mypackage.module` (package-aware).
# For scripts, use an entry point outside the package (lesson 05.5).
```

### 9.2 Shadowing stdlib / third-party by a file in `sys.path[0]`

```python
# project/random.py  shadows stdlib random — sys.path[0] (project/) is searched first.
# import random  → your random.py, not stdlib. Symptoms: missing attributes, wrong behaviour.

# Diagnose:
import random
print(random.__file__)  # if this prints .../project/random.py, you shadowed stdlib
# Fix: rename your file.

# Similarly, a file `requests.py` shadows the requests package — very common mistake.
```

### 9.3 Mutable `sys.path` gotcha — insertion vs append

```python
import sys

# `insert(0, ...)` gives HIGHEST priority — new path wins over stdlib
# `append(...)` gives LOWEST — stdlib wins

# If you insert a directory containing a stdlib-shadowing file, you break stdlib:
# sys.path.insert(0, "/path/with/fake_os.py")  → now `import os` finds fake!
# Prefer append for untrusted or supplementary paths.
```

### 9.4 Forgetting that submodule search uses parent `__path__`, not `sys.path`

```python
# import email.mime.text
# → finds `email` via sys.path
# → then finds `email.mime` via email.__path__, NOT via sys.path
# → then finds `email.mime.text` via email.mime.__path__

# If a package's __path__ is manipulated (e.g., pkgutil.extend_path), its submodules
# are found in different places than sys.path would suggest.
# For PEP 420 namespace packages, __path__ spans multiple directories — each searched.
```

### 9.5 Reload + `from` divergence — stale names after `reload`

Covered in section 5; included here as a reminder: after `importlib.reload(mod)`, any `from mod import name` binding still points to the old object. Use `mod.name` access or re-import.

### 9.6 `find_spec` returning `None` vs raising

```python
import importlib.util

spec = importlib.util.find_spec("not_real_xyz999")
print(spec)  # None — not an exception

# But import raises:
try:
    import not_real_xyz999
except ModuleNotFoundError as e:
    print(f"ModuleNotFoundError: {e}")
    print(f"name: {e.name}")  # 'not_real_xyz999' — the attempted name
# ModuleNotFoundError is a subclass of ImportError — catch ImportError to handle both.
```

## 10. Quick Reference

| Item | One-liner |
|---|---|
| `sys.path` | Ordered list of dirs searched for modules; `sys.path[0]` is script dir or `""` |
| `PYTHONPATH` | Env var prepended to `sys.path` (after entry 0) |
| `site-packages` | `sys.path` entry where `pip` installs; processed by `site` + `.pth` |
| `sys.meta_path` | List of meta finders (Builtin, Frozen, PathFinder) consulted before `sys.path` |
| `sys.path_hooks` | Callables per `sys.path` entry (FileFinder, zipimporter) |
| `ModuleSpec` | Finder's result: `(name, loader, origin, submodule_search_locations)` |
| Loader | `create_module` + `exec_module` — executes file inside module object |
| `importlib.import_module(name)` | Dynamic import by string; returns leaf module |
| `importlib.util.find_spec(name)` | Locate without executing — returns `ModuleSpec` or `None` |
| `importlib.reload(mod)` | Re-execute module in same object; stale `from` bindings, old class instances |
| Absolute import | Full name from top level — explicit, grep-friendly, works in scripts |
| Relative import (`.` / `..`) | Inside a package only; requires `-m` or package context |
| PEP 8 order | Stdlib → (blank line) → third-party → (blank line) → local; alphabetical within |
